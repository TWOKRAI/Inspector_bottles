## Break-injection — 21 инъекция (2026-09-28)

Правило: одна инъекция снимает одну заявленную гарантию; набор падений предсказан ДО
прогона. Считаю все проходы вместе, одним числом — иначе учёт перестаёт сходиться
(находка ревью №11 была ровно про это).

### Проход 1 — разбор формата (2 инъекции, обе совпали)

| Инъекция | Предсказано | Фактически |
|---|---|---|
| `split_stream` теряет остаток | 2 теста | **2** — совпало после починки теста (см. ниже) |
| `parse_packet` не снимает терминатор | 9 тестов, `TestSplitStream` выживает | **9**, `TestSplitStream` выжил — совпало |

**Инъекция нашла дефект в тесте.** `TestResultSink::test_принимает_и_разбирает_поток`
слал два `sendall` подряд, TCP их склеивал в один `recv`, и сборка разорванного
пакета оставалась непроверенной — тест выживал под инъекцией. Добавлена пауза
100 мс; после этого инъекция роняет его, как и должна.

### Проход 2 — плагин (9 инъекций, 7 совпали)

`seq_id` константой · переполнение не считается · колбэк связи не подписан ·
`last_code` затирается любым исходом · `produce()` блокирует · ошибка bind не
перехвачена — по одному тесту каждая, все совпали. Расхождения два, оба разобраны:

| Инъекция | Предсказано | Фактически |
|---|---|---|
| `produce()` не чистит очередь | 2–4 теста | **2**. Тесты, где пакеты присылаются одним синхронным заходом, дублей не видят: очередь уже полна к первому `produce()`. Сквозной дренаж охраняет только тест с симулятором в отдельном потоке |
| sink не режет поток по терминатору | 8 тестов | **2** — только кадрированность. `parse_packet` снимает терминатор сам, поэтому одиночный пакет разбирается верно и без нарезки. Ошибка была в моей модели, не в тестах |

### Проход 3 — правки находок ревью (10 инъекций)

| Инъекция (снятая гарантия) | Упало |
|---|---|
| потолок буфера сборки снят | 1 — `test_1_расхождение_терминатора_не_копит_память_молча` |
| пустой терминатор снова пропускается | 1 — `test_1_пустой_терминатор_отвергается_на_старте` |
| колбэк не сверяется с меткой запуска | 1 — `test_2_колбэк_повисшего_потока_…` |
| смена связи не публикуется из колбэка | 1 — `test_3_обрыв_связи_публикуется_без_потока_кодов` |
| `produce()` публикует и на пустом проходе | 1 — `test_3_пустой_produce_не_публикует_повторно` |
| keepalive не включается | 1 — `test_4_на_принятом_соединении_включён_keepalive` |
| инкременты вне общего замка | 1 — `test_6_счётчики_не_теряются_при_двух_потоках_соединений` |
| грубый обрыв (OSError) молчит | 1 — `test_9_обрыв_по_ошибке_сокета_называет_причину` |
| чистое закрытие с хвостом молчит | 1 — `test_9_потеря_хвоста_при_чистом_закрытии_…` |
| `bad_code` проверяется раньше `no_code` | 1 — `test_одинаковые_тексты_дают_no_code_а_не_bad_code` |
| пустые пакеты выбрасываются | 1 — `test_пакет_из_одного_терминатора_не_теряется` |
| `client_count` переименован (контракт Protocol) | 23 — Protocol и вся дорога приёма |

**Проход 3 вскрыл четыре вакуумных теста моего же написания** — они оставались
зелёными при снятой гарантии. Что с каждым сделано:

| Вакуумный тест | Почему был зелёным | Что теперь |
|---|---|---|
| «состояние не перезаписывается после stop» | держался на порядке записи, а не на метке запуска | добавлен тест с обработчиком, который живёт дольше дедлайна `join` — именно он требует метку |
| «stop гасит поток соединения» | ослепление даёт сам флаг стоп, `conn.shutdown()` наблюдаемо ничего не меняет | гарантия **снята с заявления**: `shutdown` оставлен как гигиена и польза на POSIX |
| «обрыв называет причину» | ловил чистое закрытие, а ветвь `OSError` не трогал | разделён на два теста; грубый обрыв воспроизводится `SO_LINGER(0)` → RST |
| «сокет закрывается при отказе bind» | в CPython его закрывает подсчёт ссылок, разницы не видно | тест **удалён**, правка оставлена как гигиена, отсутствие теста названо здесь |

Первая попытка инъекции keepalive тоже была неверной: снятие `setsockopt` флаг не
убирало, потому что `ioctl(SIO_KEEPALIVE_VALS)` на Windows включает его сам. Тест
был прав, ошибка — в инъекции.

### Что осталось без теста — названо, а не скрыто

- закрытие сокета при отказе `bind` (см. таблицу выше);
- `conn.shutdown()` в `stop()`;
- потолок истории `_HISTORY_LIMIT`;
- обнаружение **физического** обрыва: keepalive включён и это проверено, а вот что
  ядро действительно рвёт мёртвое соединение, на localhost не изобразить.

## Что в моей работе ненадёжно

- `ResultSink` на живом **приборе** проверен одним соединением. Переподключение
  и разрыв проверены только симулятором на localhost; `Output Result Buffer`
  (досылка накопленного прибором после обрыва) **не проверялся вообще** — и
  симулятор его не изображает.
- Плагин **проверен на настоящем приборе** (12 срабатываний, потерь ноль) — но только
  по успешной дороге. С железа НЕ снято: пакет при `NoRead` (закрыть объектив),
  различение `NoRead` и `With Code NoRead` (задать им разные тексты), поведение при
  выдернутом кабеле, `Output Result Buffer` (досылка накопленного), поток на скорости
  линии. Нагрузочных и граничных прогонов на железе не было — только ручные нажатия.
- **Обрыв кабеля не воспроизводился.** Keepalive включён и это проверено
  `getsockopt` на принятом соединении; что ядро действительно снимает мёртвое
  соединение, на localhost изобразить нечем. Тайминги проб (10 с простоя, 3 с шаг)
  выбраны по смыслу линии, а не измерены.
- Живой прогон **повторён после правок** (16/4/0, история из 20, плюс блокер
  проверен живьём: 256 КБ без терминатора → `last_error` называет причину, память не
  растёт, и запись попала в дерево состояния без единого кода). Не проверено живьём:
  переподключение после правок и поведение при двух одновременных соединениях.
- `stop()` возвращается за ~190 мс: поток приёма сидит в `accept` с шагом 0,2 с, а на
  Windows закрытие слушающего сокета из другого потока заблокированный `accept` не
  будит (замерено, попытка ускорить откачена). На освобождение порта это не влияет.
- Задержка «срабатывание → код в прототипе» **не измерена**: потребителя кодов
  в рецепте нет, мерить пока нечем. Это задача Ф3 (`code_view`).
- `dropped` (переполнение очереди) проверено только синтетически, вызовом
  `_on_result` в цикле. На живом приёме переполнение не воспроизводилось.
- Статус `BAD_CODE` реализован по смыслу названий параметров прибора. Ни один
  из них не описан в мануалах ID3000, и на железе различение ещё не снято —
  возможно, разбор описывает поведение, которого у прибора нет.
- Независимый `tester` **прогнан** (2026-09-28, worktree на коммите до правок
  ревью): 22 теста по контракту, 15 passed / 7 failed. Все 7 падений независимо
  подтвердили находки ревьюера — равные тексты давали `bad_code`, пакет из одного
  терминатора терялся, смена связи не публиковалась без кодов, поток без терминатора
  молчал, пустой терминатор не отвергался. Его тесты в главное дерево не переносились:
  на исправленном коде их место занимают тесты той же семантики в
  `tests/test_plugin.py` (класс `TestНаходкиРевью`).
- **Расхождение в контракте, найденное тестировщиком:** он ожидал
  `total_reads == ok + no_reads + bad_reads`, а в реализации `total_reads` считает
  только успешные чтения. Решено оставить реализацию (имя поля — «Прочитано кодов»),
  но формула теперь написана прямо в подсказке поля. Это была не ошибка кода, а
  двусмысленность имени, и она стоила двух его тестов.
- Тесты писал автор реализации; тесты тестировщика — отдельный набор, в репозиторий
  не влит (см. выше).
- Значения по умолчанию в `parse_packet` (`terminator=";"`, `no_code_text="NoRead"`)
  взяты с нашего экземпляра. На другом приборе или после смены `Output Stop Text`
  они молча дадут неверный разбор — параметры надо передавать явно из конфигурации.

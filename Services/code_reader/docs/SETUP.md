Экземпляр: **MV-ID3013PM-06M-SENSOTEC**, S/N `02DA9718224`, MAC `34:BD:20:88:48:85`,
прошивка **V4.0.2.C 251201**, дата производства 03/2026.

Каждый факт ниже помечен источником. **`[железо]`** — снято с этого экземпляра.
**`[мануал]`** — из официальной документации на серию. **`[?]`** — предположение,
на приборе не проверено. Мануал написан на серию, а прибор у нас конкретный:
где они расходятся, прав прибор.

Документация на прибор: `knowledge/raw/books/id3000-series-um-en-v401/` (UD47062B

### Ловушки сети

- `192.168.1.1` — типовой адрес роутера. Когда ноутбук попадёт в обычную сеть,
  будет конфликт. Сменить (правый клик по устройству → Modify IP Address) и
  включить `Lock IP Enable`, чтобы адрес не уехал после перезагрузки.
- `Local Net Info` в IDMVS показывает скорость линка **на момент обнаружения**.
  Один раз показал 10 Mbps, пока линк согласовывался; после refresh — 100. Если
  красное значение держится после обновления списка — тогда это кабель.
- Активный VPN (WireGuard) может мешать broadcast-обнаружению — гасить на время
  поиска. [?]
- Брандмауэр на этой машине выключен целиком, правила для `IDMVS.exe` есть.
  На другой машине его нужно будет открывать.

**IDMVS 5.1.0** (`C:\Program Files (x86)\IDMVSSTD`), в комплекте `MvCodeCameraSDK 2.0.0.4`.

## 3. Триггер

Текущая конфигурация прибора: [железо]

```
Trigger Mode                        = On
Trigger In Source                   = LineIn 0        (DI_0, серый, клемма 1)
Trigger Polarity                    = Falling Edge
Debounce Time(µs)                   = 1000
Trigger Delay(µs)                   = 0
Button Trigger                      = вкл
Communication Protocol Trigger Enable = выкл
Trigger Cache / Trigger Block       = выкл
Encoder Usage                       = выкл
```

**Кнопка на корпусе — полноценный триггер, проводов не нужно.** Компонент №11 по
Table 3-1, на торце с разъёмом, в окошке рядом с индикаторами. Короткое нажатие —
одно срабатывание. **Удержание 3 секунды — Smart Tune**, автоподбор экспозиции,
усиления, подсветки и типов кодов. [мануал + железо]

### Если кадров нет

При `Trigger Mode = On` и `Trigger Source = LineIn 0` без провода на DI_0 камера
ждёт вечно: `Image Number: 0`, `Transmission rate: --fps` при живом
`Sensor rate: 60 fps`. Это не поломка. Варианты: нажать кнопку на корпусе,
`Single Trigger` в Read Config, или `Trigger Mode = Off` для free-run при наводке
фокуса.

### Тонкости

- **`Falling Edge` против схемы с кнопкой.** При схеме «pull-down + кнопка подаёт
  +24» нажатие даёт **нарастающий** фронт, а падающий приходит на **отпускание**.
  Либо `Rising Edge`, либо схема с pull-up и замыканием на GND.
- **`Debounce 1000 µs` = 1 мс — мало для механической кнопки** (дребезг живёт
  5–20 мс), одно нажатие даст пачку триггеров. Поднять до 10000. Для
  бесконтактного датчика 1 мс нормально.
- **`Communication Protocol Trigger Enable` выключен** — пока так, сетевой триггер
  не работает: ни бит `REG0.1` по Modbus, ни TCP-команда.
- Задержка входа 1.3…3.5 мкс — камера видит каждый дребезг. [мануал]

### Несколько кадров на один триггер

Штатный механизм — **Stop Trigger** (`I/O Control` → `Stop Trigger Settings`,
сейчас всё выключено, отсюда «по одному за раз»): триггер запускает чтение,
камера снимает подряд и останавливается по первому успеху либо по условию —
`Timeout Stop Trigger`, `CodeNum Stop Trigger Enable`, сигнал по TCP/IO/serial.
Результат наружу один, попыток внутри несколько. Это правильный способ «сделать
две фотографии на всякий случай» — дублировать триггер не нужно.

Параметров этого режима **в мануале ID3000 нет**, только упоминание одной
строкой; они в отдельном *IDMVS Client Software User Manual*. Снимать с прибора.

## 4. Вывод результата по TCP

Прибор — **`TCP Client`**, подключается к нам сам и держит соединение открытым.
Принимающая сторона (прототип) — сервер.

```
Communication Settings → Communication Protocols = TCP Client
  TCP Client Protocol = вкл
  TCP Dst Addr        = 192.168.1.12      (IP ПК-приёмника)
  TCP Dst Port        = 5000
```

⚠ **TCP Client выключается после перезапуска питания, если не сохранён в User
Set** (2026-09-29: утром прибор к порту 5000 не подключался вовсе, пока его не
включили и не сохранили). После любой правки в IDMVS — сохранить в `UserSet1`
(он у прибора текущий и загрузочный).

⚠ **Пока IDMVS подключён к прибору, в TCP результаты, похоже, не идут** —
тишина при открытом IDMVS и поток сразу после закрытия, дважды. Изолированно не
проверено. На время работы линии IDMVS держать закрытым.

Переподключение [железо, 2026-09-29]: после перезапуска нашего приёмника прибор
вернулся за ~7 с; после выдернутого и возвращённого кабеля у ПК — через 7 с после
появления линка, коды пошли. Обрыв у ПК Windows рвёт сокет сразу (`WinError 10054`);
обрыв за коммутатором (линк у ПК жив) — путь keepalive, не проверен.

Почему клиент, а не сервер: при недоступности приёмника прибор копит результаты
(`Output Result Buffer`, число задаётся `Output Result Buffer Number`) и досылает
после восстановления связи. В обратной схеме буфер не работает. [мануал]

### Формат — снят с прибора [железо]

```
QR-30MM;
51 52 2D 33 30 4D 4D 3B
```

**Суффикс `;` (0x3B). CR/LF нет. STX/ETX нет.**

**`;` — это хвост строки формата, а не отдельный Stop Text** (снято 2026-09-29,
IDMVS → `All Feature` → `Result Setting Control`) [железо]:

```
TCP Client Format Output Content = Code Content
TCP Client Output Format String  = <code_content>;
TCP Client Format Prefix Content = Code Number     TCP Client Output Prefix String = (пусто)
TCP Client Format Suffix Content = Code Number     TCP Client Output Suffix String = (пусто)
```

`Output Start Text` / `Output Stop Text` из мануала (8.x, табл. 8-21) в блоке
TCP Client этой прошивки не видны. Через строку формата идут **только удачные
коды** — тексты неудачи (раздел 5) прибор шлёт как есть, без неё.

В строку формата можно добавить метаданные (табл. 8-21 мануала): `<code_type>`,
`<code_quality>`, `<code_eval_score>`, `<trigger_num>`, `<ppm>`, `<algo_time>` и др.
Приём сейчас считает весь пакет содержимым кода — метаданные потребуют разбора
полей на нашей стороне.

Раздела «Set Result Format» в мануале ID3000 **нет** — только в changelog как
существующий. Формат снимается прибором, не вычитывается.

⚠ TCP не сохраняет границ сообщений: два быстрых чтения могут прийти одним
`recv`, а одно — двумя. Резать поток по терминатору обязательно — этим занят
`core.result.split_stream`.

## 5. Отбраковка: NoRead

Параметры (`All Feature` → поиск `noread`), состояние на 2026-09-29: [железо]

```
Code Algorithm Params
  With Code But NoRead Check Enable       = (вкл/выкл — меняли в ходе проверки)
Result Setting Control
  Segregate Unreadable-coded Images       = выкл
  Fill in ROI Output Noread               = выкл
  TCP Client Output NoRead Enable         = вкл
  TCP Client Output NoRead Text           = NoRead;    ← различение выключено
  TCP Client Output NoCode Text           = NoRead;    ← различение включено, кода нет
  TCP Client Output With Code NoRead Text = BadRead;   ← различение включено, код не читается
Statistics Info
  Noread Frame Number                     = счётчик неудач
```

⚠ **Терминатор обязан стоять ВНУТРИ текста неудачи.** Тексты неудачи не проходят
через строку формата (раздел 4), и `;` к ним не добавляется. Заводское `NoRead`
приходит голым `4E 6F 52 65 61 64` — приём держит его в буфере (снаружи «ничего не
пришло», `no_reads = 0`), а со следующим удачным кодом склеивает в
`NoReadQR-12MM` **со статусом `ok`**. Снято 2026-09-29: четыре склейки ровно на
`Noread Frame Number = 4`; поле `NoCode Text` дало то же самое (`NoCode` без `;`).
После текста `NoRead;` — чистые `4E 6F 52 65 61 64 3B` / `no_code`.

Текстов **три**, а не два: при выключенном различении работает `NoRead Text`,
при включённом — `NoCode Text` и `With Code NoRead Text`. Править все три.

`BadRead` за день пришёл один раз и склеенным (`NoCodeBadRead` + пустой пакет —
похоже на `BadRead;;`, то есть этот текст, возможно, идёт через строку формата и
получает второй `;`). Сырых байтов этого пакета нет. Вызвать «код есть, не
читается» повторно не удалось: заклеенная середина QR даёт «кода нет» (прибор не
находит код), а замазанный маркером, смятый и под углом — **читается** (коррекция
ошибок QR). Различение на линии не проверено.

**Смысл: прибор различает два вида неудачи** — «кода в кадре нет вообще»
(нет маркировки, не та деталь, промах мимо поля зрения) и «код найден, но не
декодирован» (повреждён, замят, залит, не в фокусе). Первое — проблема подачи,
второе — проблема печати. [?] — по названиям параметров; ни один из них в
мануалах ID3000 не описан, они в IDMVS Client manual.

⚠ **По умолчанию оба текста равны `NoRead`, и в потоке они неразличимы.** Задать
разные:

```
TCP Client Output NoRead Text           = __NOCODE__;
TCP Client Output NoCode Text           = __NOCODE__;
TCP Client Output With Code NoRead Text = __BADCODE__;
```

Подчёркивания — от совпадения с настоящей маркировкой: если содержимое реального
кода окажется словом `NoRead`, годная деталь уйдёт в брак.

**Без включённого NoRead брак выглядит как тишина**, и «деталь без кода»
неотличима от «камера не сработала» или «оборвалась сеть». С включённым — на
каждый триггер ровно одно сообщение, и число триггеров равно числу деталей.

⚠ **Для Modbus в сторону ПЛК настройка обратная: NoRead выключают**, иначе не
поднимется бит `Results NG` (REG1.9). Настройки двух каналов будут
противоположными, и это нормально. [мануал]

## 6. Дискретные выходы

`I/O Control` → `Output`. Параметры пер-линейные, `Line Out Selector` выбирает,
какую линию редактируем.

```
Line Out Selector          = LineOut 3     → годен
  Line Output Event        = ReadSuccess
  Line Output Duration(µs) = 30000
  Line Output Delay Time   = 0

Line Out Selector          = LineOut 4     → брак
  Line Output Event        = NoCodeRead
  Line Output Duration(µs) = 30000
  Line Output Delay Time   = 0
```

Соответствие линий проводам (сверено с нашим кабелем): клемма 4 сине-белый `DO_0`
= **Line 3**, клемма 5 коричнево-белый `DO_1` = **Line 4**, клемма 6 коричневый
`DO_2` = **Line 5**.

### Тонкости выходов

- ⚠ **`Line Output Duration` по умолчанию 1000 µs = 1 мс.** ПЛК со сканом 10 мс
  такой импульс пропустит, и это выглядит как «камера иногда не срабатывает».
  Ставить 20000–50000, чтобы импульс перекрывал минимум три скана.
- ⚠ **`Line Output Polarity Reversal` был включён на LineOut 3** [железо]. При
  инверсии в покое линия активна, а при событии на `Duration` **снимается**.
  Смысл есть (обрыв провода читается как брак), но **обе линии должны быть
  настроены одинаково**, иначе один выход даёт импульс, другой провал. Для
  отладки проще выключить на обеих. Почему включена — неизвестно, возможно
  заводское умолчание под тип выхода. [?]
- **Событие — импульс, а не уровень.** Схема «1 = годен, 0 = брак» одним проводом
  не работает: «0» это одновременно «брак», «ещё не обработала», «камера зависла»
  и «обрыв». Два выхода дают третье состояние — **ни одного импульса за
  отведённое время = отказ оборудования**, а это при отбраковке важнее всего.
- Полный список событий (15): `AcquisitionStart/StopActive`,
  `FrameBurstStart/StopActive`, `ExposureStartActive`, `SoftTriggerActive`,
  `HardTriggerActive`, `CounterActive`, `TimerActive`, **`NoCodeRead`**,
  **`ReadSuccess`**, `LightStrobeLong`, `CompareSuccess`, `CompareFail`,
  `CommandControlIO`, `Off`. [мануал 8.6.2]
- **Качества печати среди событий нет.** `NoCodeRead` = «не декодировался», и
  только. Отбраковка по деградации кода (grade D/F по ISO 15415) доступна лишь
  через данные — колонка `Overall Grade` в History.
- `CompareSuccess`/`CompareFail` сравнивают прочитанное с эталоном — это «не та
  деталь», а не «плохой код».

### Датчик на камеру и на ПЛК одновременно

Три рабочих варианта:

1. **Параллельно на оба входа.** PNP-датчик отдаёт 100–200 мА, вход камеры берёт
   не более 25 мА, вход ПЛК 5–10 мА — запас большой. Обязателен общий GND.
   Предпочтительный: ПЛК видит деталь независимо от камеры, и молчание камеры
   становится диагностируемым отказом.
2. **Датчик → камера, камера дублирует триггер на ПЛК** через `LineOut 5`
   (`DO_2`, клемма 6) с событием `HardTriggerActive`. Проводов меньше, но при
   зависании камеры ПЛК не узнает о детали вовсе.
3. **Датчик → ПЛК → камера.** Максимальный контроль, но добавляется время скана
   ПЛК (~10 мс) между деталью и съёмкой.

## 7. Электрика I/O

| Что | Значение |
|---|---|
| Питание | 12 или 24 В ⎓; пороги входов едут вместе с ним |
| Вход Low / High при 24 В | 0…9 В / 11…24 В |
| Вход Low / High при 12 В | 0…5.4 В / 7.56…12 В |
| Ток входа max / пробой | 25 мА / 36 В |
| Выход | **ключ, не источник**; уровень задаёт внешняя подтяжка, max 200 мА |
| Фронты выхода | 0.4 мкс |
| Задержка входа | 1.3…3.5 мкс |

Всё [мануал], глава 6.

⚠ **Три правила, нарушение которых портит железо:**

1. **Не питать одновременно через клеммник и DB9** — DB9 несёт 12 В,
   «may cause the burnout of the power supply».
2. **`VCC` внешней цепи не выше `PWR` камеры.** У нас PWR = 24 В, значит ПЛК на
   24 В можно, выше — нет.
3. **`IN_R` (розовый) и `OUT_R` (фиолетово-белый) обязательны** и в 8-pin
   клеммник не входят — это открытые концы. Без них вход и выход не работают.

### Кнопка на вход DI_0 (Figure 6-10, версия 2.0)

```
   +24 В ──[кнопка]──┬── DI_0  (серый, клемма 1)
                     │
                 [1.1 кОм]
                     │
   GND ──────────────┴───────  (чёрный, клемма 7)
```

Номинал не произвольный: 24 В / 1.1 кОм = **21.8 мА** при пределе входа 25 мА.
330 Ω дадут 73 мА и выжженный вход. Розовый в этой схеме не участвует.

Схемы подключения с картинками — [`docs/diagrams/wiring/id3013-wiring.html`](../../../docs/diagrams/wiring/id3013-wiring.html).

### ⚠ Версия железа 2.0 / 3.0 — НЕ УСТАНОВЛЕНА

От неё зависит вся схема подключения к ПЛК: у 3.0 входы и выходы изолированы
(`pin 2/8/9/10/16/17`), общего GND нет, `IN_R`/`OUT_R` работают как общие точки
внешнего контура; у 2.0 развязки нет, GND общий, а те же провода — линии
подтягивающего резистора (PNP 330 Ω вниз, NPN 1 кОм вверх).

Что проверено и не помогло: `Device Version` в GenICam показывает `V4.0.2.C
251201` — **ту же строку, что и прошивка**. Hikrobot не заполняет этот узел
версией железа. [железо]

Осталось: письмо в Sensotec по серийнику `02DA9718224`. Дата производства 03/2026
говорит в пользу 3.0, но это догадка. Прозвонка GND↔`IN_R` мультиметром —
непроверенная гипотеза, основанием для монтажа не является.

**До получения ответа выходы и вход DI_0 не подключать.** Кнопка на корпусе и
TCP от версии не зависят.

## 9. Размер кода и дистанция

Лист тестовых мишеней: `tools/qr_test_sheet.py` — коды заданного габарита в мм,
каждый несёт свой размер в содержимом (`QR-10MM`, `QR-15MM`…), так что в колонке
`Barcode Content` сразу видно, какой прочёлся.

```
.venv/Scripts/python.exe Services/code_reader/tools/qr_test_sheet.py "QR" --sizes 10,12,15,20,25,30,40,50 --open
```

⚠ **Печатать строго 100%** («Без масштабирования»). На листе контрольная линейка
50 мм — проверить обычной линейкой до любых выводов о читаемости.

Все коды печатаются **одной версией QR**: строки разной длины могут перескочить
на следующую версию, тогда при том же габарите число модулей другое, и лист
сравнивал бы плотность сетки, а не размер. Граница версии 1→2 — 21 символ в
алфавитно-цифровом режиме; на коротких префиксах разъезда нет.

**Наблюдение на стенде** [железо]: читаются только средние размеры. Это физика,
не настройка. Мелкие — мало пикселей на модуль (смотреть **PPM** в History; ниже
~2 чтения не будет). Крупные — не влезают в кадр целиком или вышли из глубины
резкости. У каждой дистанции своё окно размеров; подвинуть камеру — окно
сдвинется.

Записывать для каждой дистанции: минимальный и максимальный читаемый размер и
PPM на них. **Саму дистанцию мерить линейкой** — нигде в логах она не появится,
а без неё цифры не переносятся на линию.

## 10. Сохранение конфигурации

⚠ **`Param Save`** (вверху справа) пишет в `USERSET1`. Без него все настройки
слетят при снятии питания.

Выгрузка конфигурации в файл — кнопка **`FileAccess`** в `All Feature`, либо
`Import_Export_Features.exe` из комплекта IDMVS. В наших MVS-биндингах
`FeatureSave`/`FileAccess` отсутствуют, а в `MvCodeReaderCtrl.dll` они есть.

**`NTP Timing` выключен**, `Device Time` расходится с выставленным вручную
[железо]. Метки в History живут по часам прибора. Если сопоставлять события
камеры с логами прототипа — включить NTP или зафиксировать расхождение.

## Что ещё не проверено

- Версия железа 2.0/3.0 (раздел 7) — блокирует любой монтаж I/O.
- Различает ли прибор `NoRead` и `With Code NoRead` на деле (раздел 5). Проверка:
  задать разные тексты, снять пустой лист и заклеенный на треть код.
- Hex того, что приходит при NoRead — формат неудачи в разделе 4 не записан.
- Modbus: `ModBus Mode`, Space/Offset/Size всех трёх областей. Два мануала
  расходятся (V1.0.0 — всё holding; V4.0.1 — status/result в input), у нас
  прошивка 4.0.2, то есть ровно та, под которую писан протокольный UD26848B.
- Параметры Stop Trigger (раздел 3).
- Смысл `Segregate Unreadable-coded Images` и `Fill in ROI Output Noread`.

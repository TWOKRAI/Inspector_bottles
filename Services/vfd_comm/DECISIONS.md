# vfd_comm — архитектурные решения

## ADR-VC-001: Транспорт-агностик через RegisterTransport (мост без импорта робота)

**Дата:** 2026-06-11 · **Статус:** принято

**Контекст.** ПЧ физически висит на RS-485 за роботом: ПК общается с ним через
mailbox-регистры робота (Lua ретранслирует). Прямой линии к ПЧ нет, но может
появиться.

**Решение.** `VfdClient(transport: RegisterTransport, register_map=...)`:
- сервисы НЕ связаны: vfd_comm не импортирует robot_comm; связку
  (bridge-транспорт) выполняет `DeviceManager` в процессе `devices`;
- мост = RobotClient (реализует RegisterTransport), прямое подключение =
  ModbusDevice(rtu) + DIRECT_MAP — без правки клиента;
- слой Lua скрывает slave id ПЧ (P14.00) — клиент про RS-485 не знает (SRP).

**Отвергнуто:** vfd_* методы внутри RobotClient (как в pc_full.py) — смешивает
домены, не масштабируется на прямое подключение и второй ПЧ.

## ADR-VC-002: poll() — пульс VFD_FLAG как опрос (компенсация ограничения Lua)

**Дата:** 2026-06-11 · **Статус:** принято (до Lua-улучшения №1)

В текущем Lua зеркало 0x1210+ (включая heartbeat) обновляется ТОЛЬКО при
обработке VFD_FLAG (`vfd_poll_publish` зовётся из `handle_vfd`). Периодический
read_status без команд читал бы замороженный снимок. Решение: `poll()` пишет
FLAG=1 без смены команды — Lua кэширует last_cmd/last_freq, на RS-485 уходит
только чтение статуса; `ensure_alive()` детектит обрыв моста по динамике
heartbeat (stale_polls_limit подряд без роста → VfdBridgeStaleError).
После Lua-улучшения «публикация в idle» poll() останется работать (пульс
станет избыточным, но безвредным).

## ADR-VC-003: Две карты на одно устройство (BRIDGE + DIRECT)

**Дата:** 2026-06-11 · **Статус:** принято

При прямом RTU меняется не только транспорт, но и карта (0x2000/0x2100/0x3000
вместо mailbox) и состав статуса (heartbeat/comm_errors — телеметрия моста,
у самого GD20 их нет). Поэтому `VFDStatus` с опциональными полями и
параметризация клиента картой. DIRECT_MAP — закладка по мануалу goodrive20,
активируется при появлении физической линии.

## ADR-VC-004: Память последней частоты в VfdClient

**Дата:** 2026-11-23 · **Статус:** принято (2026-11-23)

**Контекст.** «Лента пуск» без частоты затирала скорость, заданную оператором, значением `default_freq_hz`.

**Решение.**
- `VfdClient` помнит последнюю успешно записанную частоту `> 0`; `run()` без частоты стартует на ней, иначе на
  `default_freq_hz`. Ноль и неудачная запись (False или исключение транспорта) память не меняют.
- Запись на провод и присваивание памяти — под одним `threading.Lock` (`_freq_lock`, порядок: он, затем замок
  транспорта): память совпадает с последней командой на проводе.
- Память живёт в процессе. `VfdDriver` при `disconnect()`/`set_degraded()` забирает `VfdClient.last_freq`, а
  `connect()` передаёт её новому клиенту через kwarg `last_freq`: реконнект частоту не теряет, рестарт процесса — теряет.
- Начальная память (kwarg `last_freq`) тоже берётся только при значении `> 0`: `last_freq=0.0` -> `None`, иначе пуск
  без частоты стартовал бы молча на 0 Гц (тест `test_zero_last_freq_kwarg_is_not_remembered` убивает мутант «убрана
  нормализация kwarg»; мутант `or` вместо `is not None` при выборе частоты в `run()` после нормализации эквивалентен:
  `_last_freq == 0` недостижим). Через драйвер ноль в память не попадает (`VfdDriver` берёт только `client.last_freq`: `None` либо `> 0`).

**РЕШЕНО 2026-11-23 (лид по поручению владельца «как лучше и правильно»):** после аварии лента стартует с безопасной
уставки, а не с чужой «последней».
- Успешный `reset_fault()` сбрасывает память (`None` -> пуск без частоты на `default_freq_hz`); запись и сброс под
  `_freq_lock`. Неудачный `reset_fault()` (False или исключение) память не трогает: авария не сброшена.
- Обычный `stop()` память СОХРАНЯЕТ: оператор остановил и пустил на той же скорости (ради этого фича и сделана).
- `VfdDriver` при `disconnect()`/`set_degraded()` присваивает память клиента безусловно, включая `None` (иначе
  устаревшая частота драйвера засеяла бы следующего клиента после `reset_fault`).
- Верхняя граница сверх `freq_min_hz..freq_max_hz` НЕ вводится: новый конфиг = лишний слой, граница ПЧ уже
  проверяется в `_validate_freq`.

**ОСТАЁТСЯ ИЗВЕСТНЫМ:** пульт показывает `belt_freq = 10`, а память может держать частоту, заданную другим вызывающим
(`camera_robot` передаёт частоту явно): «Лента пуск» стартует на памяти, не на значении поля. Корректный фикс — пульт
передаёт частоту поля явно (GUI-проводка, вне этой задачи, в backlog). Обратная сторона: после `reset_fault()` память
пуста, а поле показывает значение оператора (например 31): «Лента пуск» стартует на `default_freq_hz` (10 Гц) при
показанных 31 — закрывается тем же фиксом. Усиление: память
теперь переживает реконнект драйвера, поэтому высокая частота, заданная любым вызывающим, живёт до рестарта процесса
devices или `manager.remove(dev_id)`; по коду `DeviceManager` upsert существующего id драйвер не пересоздаёт, т.е.
память переживает и смену рецепта (оба рецепта с `vfd_belt`) — чтение кода, через `DeviceManager` не воспроизводилось.

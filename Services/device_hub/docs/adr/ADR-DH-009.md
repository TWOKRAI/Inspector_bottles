## ADR-DH-009: Потоки робота — у области плагина; стоп процесса — один раз, параллельно, под одним сроком

**Дата:** 2026-10-19
**Статус:** accepted (T5.3 круг 2, решение CTO; гарантия про простого робота — решение владельца 2026-10-19)

**Контекст.** В круге 1 драйвер робота v2 без `spawn` открывал свой корень потоков (`rv2-<id>`) — второй владелец
потоков и гонка закрытия. Стоп процесса ждал эха и шёл по роботам по очереди: молчащий робот задерживал остановку на
секунды и задерживал соседей; повтор после удачной записи съедал срок.

**Решение** (`plans/robot-protocol-v2/tasks/T5.3.round2-decision.md` §2):

| что | владелец | правило |
|---|---|---|
| потоки | область плагина `device_hub` | драйвер не открывает корень и не создаёт `Thread`; `spawn` keyword-only, умолчание None; без `spawn` операции с потоком (`jog_hold`, запуск программы, `return_job`) отказывают `RuntimeError` сразу; фабрика `delta_v2` без `spawn` — `RuntimeError` при создании |
| защёлка стопа | драйвер, на робота | сильнейший записанный уровень и «последняя запись упала»; сброс после записи движения (JOG_CONT) и при захвате программы / задания; не больше двух попыток на поколение |
| рассылка стопа | менеджер | всем роботам параллельно потоками `stop-<id>-<k>`; отказ `spawn` — стоп этому роботу в вызывающем потоке |
| срок | плагин | один абсолютный срок `monotonic() + 3,0 − 0,5` с: фаза 1 запись стопа + проверка эха в том же потоке → удаление воркеров → `scope.close` с остатком → фаза 4 без записи и без чтения эха |
| эхо стопа | драйвер / плагин | только диагностика: нет эха → `last_error` и health «стоп не подтверждён роботом»; чтения эха — только пока чтение успевает до срока |
| стоп оператора `abort` | драйвер | пишется всегда, защёлка его не блокирует |

**Гарантия (решение владельца 2026-10-19: «если всех выключаем — всех на стоп, если индивидуальных — только их»).**
Каждый подключённый робот, который выключается, получает ровно один стоп на каждое выключение (первый запрос выключения
открывает новое поколение защёлки: прежние стопы — оператора, отпускание jog — его не покрывают): при остановке процесса (выключение плагина)
стоп получают все подключённые роботы, при `disconnect()` одного робота — только он. Уровень: как раньше для движения
(программа и задание HARD, jog SOFT); простой робот (ничего не задано) получает SOFT. Неподключённый простой робот
стопа не получает (писать некуда). Защёлка не даёт второй записи в том же выключении, в том числе простому
роботу (фаза 4, `disconnect` после `request_stop`, второй `request_stop_all`). Недосягаемого робота останавливает его сторож `P_WDG_TIMEOUT_MS` (если он
не 0). Остановка роботов и закрытие области укладываются в срок.

Индивидуальный `disconnect()` ждёт эхо стопа до `soft_echo_timeout_s` (2,0 с) в потоке supervisor'а (запись и ожидание
эха; только запись — для `disconnect` T5.3c).

**Отклонения лида от текста §2 (приняты в круге 2):**
- `spawn` с умолчанием None (тесты T5.6 создают драйвер без потоков), отказы — на операциях с потоком.
- Простой робот стоп получает (SOFT) — решение владельца 2026-10-19, см. «Гарантия»; в тексте §2 было «только роботу
  с заданным движением».
- Повтор упавшей записи — только если запись с повторами транспорта (`timeout_sec * (retries + 1)`) успевает до
  срока: транспорт хаба сам повторяет запись по таймауту.
- `remove_worker` фреймворка (до 5,0 с на поток) в срок не входит.
- Стоп задания CVT при остановке процесса идёт через защёлку (HARD, одна запись), а не отдельной записью задания (H1).

**Исключения из «одна запись `STOP_REQ` на робота за стоп процесса».** Вторая запись — только если первая не покрывает
движение робота: упавшая запись (повтор один раз, если успевает до срока) или команда, принятая роботом после стопа
(О5 клиента / H-B). Исключения не исключают друг друга: повтор и О5 на одном роботе дают до трёх записей. Простой
робот (SOFT по решению владельца 2026-10-19) второй записи не получает: защёлка гасит её (фаза 4 и `disconnect` после
`request_stop`). Стоп оператора выключение не покрывает. Сторожа считают записи на стороне робота, `test_t53r2_stop_hazards.py`:
1. Повтор после упавшей записи: один раз на поколение защёлки и только если запись успевает до срока
   (`timeout_sec * (retries + 1)` от текущего момента не выходит за срок). Третьей попытки нет, даже если срок её вмещает.
2. H-B: JOG_CONT, вернувшийся после стопа процесса (замок перехода jog не взят до срока, JOG_CONT в полёте), получает
   свой стоп: первый стоп лёг на робота раньше этой команды и её не покрывает.
3. О5 клиента (`_reissue_stop_if_overtaken`): команда, принятая роботом ПОСЛЕ стопа, получает свой стоп. Воспроизведено
   3 из 3 на только что запущенной программе (стоп в первые миллисекунды прогона: записи 0,0002 / 0,014 с и т. п.).
   «Ровно одна запись» на программе держится, только если в момент стопа нет команды в полёте.
4. Повтор стопа исполнителя в `on_progress` (микроокно К1): только если стоп процесса был записан ДО g0 прогона
   (`stop_generation == run_stop_base`); стоп, записанный после g0, прогон видит сам, повтор не пишется. Идёт мимо
   защёлки, один раз на прогон.

**Окно эха.** Чтения эха идут до `срок − timeout_sec * (retries + 1)` (чтение, начатое позже, пережило бы срок на мёртвой
связи). Срок плагина 2,5 с (3,0 − 0,5): окно эха = 2,5 − `timeout_sec * (retries + 1)` ≈ 0,5 с при умолчаниях
(`timeout_sec` 1,0, `retries` 1). При `timeout_sec` ≥ 1,25 с окна нет, и каждый остановленный робот помечается
«стоп не подтверждён роботом» (ложно, если стоп дошёл). Время эха HARD на реальной Delta не измерено — замер в T4.0;
до него 0,5 с — расчёт, а не измерение.

**Условия CTO (принятое решение).**
- L-9 (процесс `devices` с двумя роботами после «shutdown successfully» не выходит, PM убивает его через 5,0 с) чинится
  в PM до любого стенда с реальным роботом (T4.x).
- T5.3c: при `timeout_sec` ≥ 1,25 с окна эха нет — health показывает «эхо не читалось (нет окна)», а не «стоп не
  подтверждён роботом».

**Отвергнуто:** последовательная рассылка с коротким таймаутом (N роботов на полуоткрытой связи — N секунд);
сторож в автономном режиме драйвера (чинит путь, которого не должно быть); «никогда не повторять стоп» (повтор
после упавшей записи полезен).

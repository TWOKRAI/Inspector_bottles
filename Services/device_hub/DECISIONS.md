# Services/device_hub — Архитектурные решения

## ADR-DH-001: Один мастер — процесс devices

**Дата:** 2026-06-11
**Статус:** accepted

Все соединения с устройствами принадлежат ОДНОМУ процессу `devices` (protected).
GUI и плагины ходят к нему по IPC. Честный анализ: IPC-хоп 0.2-2 мс против
Modbus-операции 2-50 мс — накладные расходы пренебрежимы; tight-loop'ы (feeder CVT)
живут внутри хоста.

**Отвергнуто:** владение соединением в pipeline-плагине (robot_io) — ручное
управление без рецепта невозможно; co-location трёх плагинов обязательна.

## ADR-DH-002: Bridge-транспорт шарит Lock носителя

**Дата:** 2026-06-11
**Статус:** accepted

Bridge-устройство (VFD через мост робота) использует RegisterTransport носителя
(RobotClient). RLock внутри ModbusDevice обеспечивает thread-safety: transaction
атомарна. Bridge-устройство НЕ имеет своего connect; is_connected делегируется
носителю; disconnect носителя -> зависимые в degraded.

## ADR-DH-003: YAML-протокол -> RegisterMap + meta

**Дата:** 2026-06-11
**Статус:** accepted (реализован в Фазе 0)

Файлы протоколов (`.yaml`) загружаются через `load_protocol` в `DeviceProtocol`
(RegisterMap для транспорта + RegisterMeta для GUI). Высокоуровневых write-команд
в файле НЕТ — командная семантика остаётся в клиентах.

## ADR-DH-004: Удаление носителя — блокировка, НЕ каскад

**Дата:** 2026-06-11
**Статус:** accepted

При попытке удалить устройство-носитель (robot), от которого зависят bridge-
устройства (vfd), операция БЛОКИРУЕТСЯ с RegistryIntegrityError. Оператор
должен сначала удалить зависимые устройства.

**Отвергнуто:** каскадное удаление зависимых — опасно для оператора, может
случайно удалить настроенные устройства.

**Отвергнуто:** каскадная деградация (оставить записи, отключить) — сложнее
реализовать, неочевидное поведение для пользователя.

## ADR-DH-006: Known Limitations — supervisor последовательно обрабатывает connect

**Дата:** 2026-06-12
**Статус:** accepted (known limitation)

Supervisor-воркер обрабатывает очередь connect/disconnect последовательно в одном потоке.
При большом числе устройств с мёртвыми IP (например, 10 ПЧ без железа) подключение каждого
блокирует обработку следующих на timeout (1–5 с × N). Параллелизация connect'ов — follow-up
при росте числа устройств.

## ADR-DH-005: YAML-протокол → RegisterMap + meta (закреплено)

**Дата:** 2026-06-11
**Статус:** accepted (реализован в Фазе 0, plan device-hub)

Файлы протоколов (`Services/*/protocols/*.yaml`) загружаются через
`load_protocol` (`Services/modbus/core/protocol_file.py`) в `DeviceProtocol`:
`RegisterMap` для транспорта + `RegisterMeta` для GUI (label/unit/min/max/hint).
Высокоуровневых write-команд в YAML НЕТ — командная семантика в клиентах.

Parity-инвариант: YAML-карты эквивалентны python-картам (`test_parity_*.py`).
Python-карты остаются source of truth для `RobotClient` (46 тестов не тронуты).

**Отвергнуто:** кодирование карт через SchemaBase/Pydantic — слишком тяжело для
декларативных данных; YAML проще редактировать оператору.
**Связь:** ADR-DH-003 (первоначальное решение), ADR-MB-001 (RegisterMap).

## ADR-DH-008: Чтение реестра/драйверов — только через snapshot-API (M-race-1)

**Дата:** 2026-07-08
**Статус:** accepted (Ф3.4 constructor-master)

Реестр (`_entries`) и живые драйверы (`_drivers`) `DeviceManager` мутируются из
командного потока (upsert/remove) и читаются из supervisor- и per-device
tick-воркеров. Прямой обход приваток из другого потока при параллельном
`pop`/`[]=` даёт `RuntimeError: dictionary changed size during iteration` либо
полу-удалённое состояние.

**Решение:** единственный потокобезопасный способ читать реестр/драйверы
ИЗВНЕ менеджера — публичный snapshot-API под `_registry_lock` (RLock):
`snapshot_registry()`, `get_driver()`, `connected_ids()`, `device_count()`,
`connected_count()`. Внутренние чтения менеджера (get/connect/disconnect/call/
describe) тоже переведены на лок/снапшот.

**Контракт:** методы возвращают КОПИЮ верхнего уровня под локом (shallow) —
защищают от мутации словаря, НЕ от мутации самого DeviceEntry/драйвера. IO
(connect/disconnect/tick/is_connected) выполняется ВНЕ лока — критические секции
максимально короткие (RLock реентрантен, но IO под локом держать нельзя).

Enforced гейтом `Plugins/hub/device_hub/tests/test_no_private_access.py`
(прямой доступ `_manager._entries/._drivers` из прод-кода плагина = 0).

**Отвергнуто:** обход приваток из потоков напрямую — исходная гонка.
**Связь:** ADR-DH-004 (remove под локом), ADR-DH-006 (supervisor-воркер).

## ADR-DH-009: Потоки робота — у области плагина; стоп процесса — один раз, параллельно, под одним сроком

**Дата:** 2026-10-19
**Статус:** accepted (T5.3 круг 2, решение CTO; гарантия про простого робота — решение владельца 2026-10-19)

**Суть.** Потоки робота v2 принадлежат области плагина `device_hub`: драйвер не открывает свой корень потоков, `spawn` внедряется. Стоп процесса уходит всем подключённым роботам параллельно и укладывается в один абсолютный срок. Гарантия владельца: каждый выключаемый подключённый робот получает ровно один стоп на выключение (простой — SOFT), неподключённый простой — ни одного; эхо стопа — только диагностика.

**Полный текст:** [docs/adr/ADR-DH-009.md](docs/adr/ADR-DH-009.md)

## ADR-DH-011: `connect`, `request_stop` и обычный `disconnect` драйвера робота v2 линеаризуются переходами `RobotState`

**Дата:** 2026-10-21
**Статус:** accepted (T5.3g; решения лида inspector-bottles-a9 и владельца 2026-10-19, 2026-10-20); дополнен T5.3h (решение владельца 2026-10-21); дополнен C-29 (решения владельца 2026-10-25, В1–В6)

Дополнен T5.3h (SOFT при «Отключить» посреди `connect`) и C-29 (решения владельца В1–В6).

**Полный текст:** [docs/adr/ADR-DH-011.md](docs/adr/ADR-DH-011.md)

## ADR-DH-012: Явный SPI драйвера и команды хаба из описаний операций

**Дата:** 2026-10-26
**Статус:** accepted (SPI хаба, a–h; решения лида inspector-bottles-00 и владельца 2026-10-26)

**Суть.** Контракт драйвера записан в `Services/device_hub/spi.py` (`Protocol` `DeviceDriver`, умолчания в `BaseDeviceDriver`), каждая операция описана `OpSpec`, из `OP_SPECS` классов драйверов таблицы видов (`kinds.py`, 55 операций) генерируются команды `robot_*` и `vfd_*` с описанием, аргументами и исполнителем `device_io`; имена 72 команд не менялись. Отступления от брифа (строгий `command_table`, вид = фабрика, C-47 `executors` из топологии, описания рисования по коду, `driver_options` вместо `client_factory` в менеджере) — в полном тексте.

## ADR-DH-013: Основная остановка робота v2 — действие тика драйвера, а не шаг `process.stop`

**Дата:** 2026-10-27
**Статус:** accepted (T5.3e.1; решения владельца 2026-10-27 В-1…В-5 и выбор В2; D1/D3 владельца: в `process.stop` — только аварийный стоп)
**Контекст задачи:** `plans/robot-protocol-v2/tasks/T5.3e.1.md` (ред. 6), `T5.3e.analysis.md`

### Контекст

Перед выключением робот должен дойти домой и выключить серво (основная остановка). Ход домой — секунды, до 30 с, а стоп
процесса укладывается в секунды (умолчание драйвера — 2,5 с) и не должен удлиняться (D3). Нужна долгая операция устройства: ответ сразу, итог позже.

### Альтернативы

**A. Блокирующая операция на исполнителе `device_io`.**
- Плюсы: готовый механизм. Минусы: ключ `device_id` ставит 10 операций данных робота за ходом до 30 с; фаза 2 остановки
  ждёт исполнитель раньше `plugins.shutdown`, аварийный стоп откладывается (D3); таймаут GUI 30 с. Снята шагом 0 (чтением кода).
  **Пересмотрена для `robot_park_all` (T5.3e.5, ADR-DH-014):** (1) хук `request_stop` (C-60.b) пишет аварийный стоп до
  join исполнителя — снята причина шага 0 (поэтому и фраза «C-60 остаётся дефектом» в «Ограничениях» для хаба больше не
  верна); (2) ключ «все» вместо `device_id`, один вызов на выключение; (3) ждёт шаг `pre_stop` PM со сроком 35 с, а не GUI
  с 30 с. Для `robot_park` (один робот, GUI) решение ADR-DH-013 в силе.

**Б. Свой поток `spawn` в области плагина, ответ сразу.**
- Плюсы: ответ сразу, C-60 не нужен. Минусы: новый вид потока, второй механизм рядом с `ExecutorManager` — обход C-60
  вместо починки. Отвергнута владельцем.

**В1. Исполнитель `robot_motion` после починки C-60** (плагины `Stoppable`, стоп фазы 1 до ожидания исполнителей).
- Плюсы: без новых механизмов в драйвере. Минусы: правка фреймворка в полосе Ф, меняется порядок фаз стопа любого
  процесса; блокирующий ответ упирается в 30 с GUI; без C-60 нельзя.

**В3. В1 с ранним ответом исполнителя.**
- Плюсы: ответ сразу. Минусы: ещё и ранний ответ в `KeyedExecutor`, две формы ответа, наибольший объём; без C-60 нельзя.

### Решение

Выбрана **В2**: park — действие тика драйвера. `ParkMachine` ведёт шаги в тике, ход домой — программа `park_home` в
существующем потоке программ; ответ `{accepted, seq}` сразу, итог — `devices.state.<id>.park`. Нового потока и
исполнителя нет (принцип 4), аварийный стоп от C-60 не зависит: `request_stop` переводит идущий park в `failed` после
записи стопа. Контракт — README хаба, «Долгая операция устройства».

### Принятые отступления от спеки T5.3e.1

- **D6, реконнект после `done`:** спека — «серво при подключении не включать»; код сам шлёт SERVO 0, если `on_connect.servo` не `null` и `TLM_SERVO` не 0. Контроллер
  перезапускается с серво ON, «не включать» оставило бы робота с серво ON при защёлке «остановлен». Защёлка `_parked`
  переживает реконнект, снимает её только «серво ON».
- **D5, шаг `home`:** исход `done` при позе вне допуска получает один тик отсрочки, затем `failed` «после хода робот не
  дома». Телеметрия того тика могла быть прочитана до DONE. Цена: настоящее «не дома» объявляется на тик позже.
- **Причина обрыва (57f4a3dee):** в цикле программы дома любое исключение, кроме `RobotCommError` и `ValueError`, а
  `RobotNotConnectedError` всегда, даёт «связь с роботом потеряна», а не «ход домой не выполнен». Правило то же, что в
  `_run_next_job` (осознанное, одно на драйвер, решение лида). Ответ робота, в том числе `RobotTimeout`, даёт «ход домой
  не выполнен»; ошибка в коде драйвера (`RuntimeError`, `KeyError`) тоже даст «связь потеряна», тип виден в
  `.program.error` и в логе.

### Последствия

- Архитектура: `park.py` (`ParkMachine`, единственный писатель `.park`), +6 полей `RobotState`, `ROBOT_V2_OPS` — 18,
  команд хаба — 73. Ход каждого шага запаздывает до одного тика (`poll_interval_s`).
- Миграция не нужна. Счёты 55/72 в ADR-DH-012 верны на его дату и не правятся.
- Ограничения: park не берёт `device_io` и не заводит потоков. «Домой перед выключением системы» сам не идёт: носитель —
  `pre_stop` (gui-graceful-close 1.4, полоса Ф); до него оператор шлёт `robot_park` до закрытия окна. C-60 остаётся
  дефектом полосы Ф: любая долгая операция исполнителя откладывает аварийный стоп.

### Открыто

- Повторный `robot_park` на остановленном роботе не отказывается. Дома — `done`. Если рука сдвинута при серво OFF, итог
  `failed` «ход домой не выполнен», а настоящая причина видна только в `.program.error`. Отказ по `_parked` или
  идемпотентность — не решено.
- Флаг `OpSpec.immediate` — только каталог: во время работы его никто не читает (ADR-DH-012). У `park` он `True`.
- Список запрета в цикле программы дома (см. выше) принят сознательно; вариант — список разрешения (`OSError`, ошибка
  транспорта Modbus, `RobotNotConnectedError`): ошибка программирования тогда не выдаёт себя за обрыв связи.
- При `on_connect.servo: null` реконнект после `done` SERVO 0 не пишет: серво остаётся ON, защёлка `_parked` держит
  только команды хаба.
- Защёлка `_parked` живёт в памяти `RobotState`: при пересоздании драйвера (не при реконнекте) она теряется, и подключение
  включает серво по умолчанию.
- Второй park на роботе дома повторно пишет SERVO 0 (безвредно).

## ADR-DH-014: Итог основной остановки всех роботов — в ответе команды на исполнителе `device_io`; стоп хаба — в хуке `request_stop` (C-60.b)

**Дата:** 2026-11-07
**Статус:** accepted (T5.3e.5; решение лида inspector-bottles-e8; исполнитель `device_io` — рабочий дефолт, подтверждения владельца нет)
**Контекст задачи:** `plans/robot-protocol-v2/tasks/T5.3e.5.md`, `T5.3e.5a.md`, `T5.3e.5b.md`

### Контекст

Перед `process.stop` шаг `pre_stop` PM (gui-graceful-close 1.4) должен отправить всех роботов v2 домой и дождаться
итога. Шаг — запрос с ожиданием ответа до `timeout_s`; после ответа PM сразу взводит `system_stop_event`. `robot_park`
(ADR-DH-013) отвечает допуском, а итог кладёт в стор, который PM не читает.

### Альтернативы

**А. Ответ-допуск `{accepted, seq}` и итог в `.park`, как у `robot_park`.**
- Плюсы: одна форма с `robot_park`, ответ сразу, исполнитель не нужен.
- Минусы: шаг `pre_stop` ждёт ответ, а не стор — получив допуск, PM взведёт стоп через миллисекунды, робот ещё едет:
  смысл основной остановки (D1) теряется.

**Б. Свой поток `spawn` и свой ответ (`manages_own_reply`).**
- Плюсы: ответ придёт, когда нужно, без исполнителя.
- Минусы: чтение Б из ADR-DH-013 — второй механизм рядом с `ExecutorManager`; отвергнуто владельцем 2026-10-27.

**В. Блокирующий обработчик на потоке приёма (команда без исполнителя).**
- Плюсы: ничего нового.
- Минусы: до 33,5 с на потоке приёма — L-9 (`docs/claude/OPEN_QUESTIONS.md:1985`); `process.stop` процесса `devices`
  встал бы за ним.

**Г. Свой исполнитель `robot_motion` (строка `base.yaml`, слой prototype).**
- Плюсы: операции данных роботов не ждут `robot_park_all`.
- Минусы: правка вне границ полосы Р2; для одной команды на выключении цена `device_io` терпима. Вариант остаётся
  открытым — вопрос владельцу.

### Решение

Выбрано: ответ `robot_park_all` несёт **итог каждого робота** (`done` / `failed` / `timeout` / `skipped` / `refused` /
`error`); команда идёт на исполнитель `device_io` с `targets="all"` (ключ «все»), ожидание — `Condition` над замком
`ParkMachine`. **Стоп хаба** (аварийный SOFT) пишет хук `request_stop` (C-60.b) первым шагом фазы 2
(`multiprocess_framework/modules/process_module/core/process_module.py:283-287`) — до join исполнителя, поэтому ожидание
на `device_io` его не откладывает; само ожидание по хуку сворачивается (ответ ≤ 1,0 с).
Контракт — README хаба, «Все роботы: `robot_park_all`».

ADR-DH-009 («стоп один раз под одним сроком») в силе, меняется точка отсчёта: срок `monotonic() + 3,0 − 0,5` с
считается от хука, а не от `shutdown`; после хука `shutdown` стоп роботам не пишет заново, а дожидается потоков хука
(без хука — прежний путь).

### Последствия

- Архитектура: `DeviceManager.robot_park_all`, `ParkMachine.wait_terminal` (8 терминалов, запись до `publish`),
  `DeviceHubPlugin.cmd_robot_park_all` и `request_stop`; `command_options` отдаёт `executor` / `targets`. Команд хаба — 74.
- Цена: второй вызов встаёт за первым; 10 операций данных всех роботов ждут до ~33,5 с, лишние на `max_pending 64` —
  `executor_busy`. На выключении безвредно, при ручном вызове заметно.
- Ограничения: команда без исполнителя в процессе отказывает («нет исполнителя `device_io`»), а не встаёт на поток
  приёма. `robot_park` (GUI, один робот) решения ADR-DH-013 не меняет.
- Риски: шаг `pre_stop` в коде PM ещё не реализован (1.4 PENDING), путь «PM -> ответ исполнителя -> стоп» целиком не
  проверен; доставка ответа во время `process.stop` не читана — итог при потере ответа виден по `.park` и журналу.
  Робот, не дошедший домой к сроку, не задерживает стоп: PM идёт в `process.stop` с WARNING, серво остаётся ON до
  аварийного стопа (решение владельца о том, что это ожидаемо, не получено).

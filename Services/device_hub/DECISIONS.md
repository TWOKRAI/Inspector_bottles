# Services/device_hub — Архитектурные решения

## ADR-DH-001: Один мастер — процесс devices

**Дата:** 2026-06-11
**Статус:** accepted

Все соединения с устройствами принадлежат ОДНОМУ процессу `devices` (protected).
GUI и плагины ходят к нему по IPC. Честный анализ: IPC-хоп 0.2-2 мс против
Modbus-операции 2-50 мс — накладные расходы пренебрежимы; tight-loop'ы (feeder CVT)
живут внутри хоста.

**Отвергнуто:** владение соединением в pipeline-плагине (robot_io) — ручное
управление без рецепта невозможно; co-location трёх плагинов обязательна.

## ADR-DH-002: Bridge-транспорт шарит Lock носителя

**Дата:** 2026-06-11
**Статус:** accepted

Bridge-устройство (VFD через мост робота) использует RegisterTransport носителя
(RobotClient). RLock внутри ModbusDevice обеспечивает thread-safety: transaction
атомарна. Bridge-устройство НЕ имеет своего connect; is_connected делегируется
носителю; disconnect носителя -> зависимые в degraded.

## ADR-DH-003: YAML-протокол -> RegisterMap + meta

**Дата:** 2026-06-11
**Статус:** accepted (реализован в Фазе 0)

Файлы протоколов (`.yaml`) загружаются через `load_protocol` в `DeviceProtocol`
(RegisterMap для транспорта + RegisterMeta для GUI). Высокоуровневых write-команд
в файле НЕТ — командная семантика остаётся в клиентах.

## ADR-DH-004: Удаление носителя — блокировка, НЕ каскад

**Дата:** 2026-06-11
**Статус:** accepted

При попытке удалить устройство-носитель (robot), от которого зависят bridge-
устройства (vfd), операция БЛОКИРУЕТСЯ с RegistryIntegrityError. Оператор
должен сначала удалить зависимые устройства.

**Отвергнуто:** каскадное удаление зависимых — опасно для оператора, может
случайно удалить настроенные устройства.

**Отвергнуто:** каскадная деградация (оставить записи, отключить) — сложнее
реализовать, неочевидное поведение для пользователя.

## ADR-DH-006: Known Limitations — supervisor последовательно обрабатывает connect

**Дата:** 2026-06-12
**Статус:** accepted (known limitation)

Supervisor-воркер обрабатывает очередь connect/disconnect последовательно в одном потоке.
При большом числе устройств с мёртвыми IP (например, 10 ПЧ без железа) подключение каждого
блокирует обработку следующих на timeout (1–5 с × N). Параллелизация connect'ов — follow-up
при росте числа устройств.

## ADR-DH-005: YAML-протокол → RegisterMap + meta (закреплено)

**Дата:** 2026-06-11
**Статус:** accepted (реализован в Фазе 0, plan device-hub)

Файлы протоколов (`Services/*/protocols/*.yaml`) загружаются через
`load_protocol` (`Services/modbus/core/protocol_file.py`) в `DeviceProtocol`:
`RegisterMap` для транспорта + `RegisterMeta` для GUI (label/unit/min/max/hint).
Высокоуровневых write-команд в YAML НЕТ — командная семантика в клиентах.

Parity-инвариант: YAML-карты эквивалентны python-картам (`test_parity_*.py`).
Python-карты остаются source of truth для `RobotClient` (46 тестов не тронуты).

**Отвергнуто:** кодирование карт через SchemaBase/Pydantic — слишком тяжело для
декларативных данных; YAML проще редактировать оператору.
**Связь:** ADR-DH-003 (первоначальное решение), ADR-MB-001 (RegisterMap).

## ADR-DH-008: Чтение реестра/драйверов — только через snapshot-API (M-race-1)

**Дата:** 2026-07-08
**Статус:** accepted (Ф3.4 constructor-master)

Реестр (`_entries`) и живые драйверы (`_drivers`) `DeviceManager` мутируются из
командного потока (upsert/remove) и читаются из supervisor- и per-device
tick-воркеров. Прямой обход приваток из другого потока при параллельном
`pop`/`[]=` даёт `RuntimeError: dictionary changed size during iteration` либо
полу-удалённое состояние.

**Решение:** единственный потокобезопасный способ читать реестр/драйверы
ИЗВНЕ менеджера — публичный snapshot-API под `_registry_lock` (RLock):
`snapshot_registry()`, `get_driver()`, `connected_ids()`, `device_count()`,
`connected_count()`. Внутренние чтения менеджера (get/connect/disconnect/call/
describe) тоже переведены на лок/снапшот.

**Контракт:** методы возвращают КОПИЮ верхнего уровня под локом (shallow) —
защищают от мутации словаря, НЕ от мутации самого DeviceEntry/драйвера. IO
(connect/disconnect/tick/is_connected) выполняется ВНЕ лока — критические секции
максимально короткие (RLock реентрантен, но IO под локом держать нельзя).

Enforced гейтом `Plugins/hub/device_hub/tests/test_no_private_access.py`
(прямой доступ `_manager._entries/._drivers` из прод-кода плагина = 0).

**Отвергнуто:** обход приваток из потоков напрямую — исходная гонка.
**Связь:** ADR-DH-004 (remove под локом), ADR-DH-006 (supervisor-воркер).

## ADR-DH-009: Потоки робота — у области плагина; стоп процесса — один раз, параллельно, под одним сроком

**Дата:** 2026-10-19
**Статус:** accepted (T5.3 круг 2, решение CTO; гарантия про простого робота — решение владельца 2026-10-19)

**Контекст.** В круге 1 драйвер робота v2 без `spawn` открывал свой корень потоков (`rv2-<id>`) — второй владелец
потоков и гонка закрытия. Стоп процесса ждал эха и шёл по роботам по очереди: молчащий робот задерживал остановку на
секунды и задерживал соседей; повтор после удачной записи съедал срок.

**Решение** (`plans/robot-protocol-v2/tasks/T5.3.round2-decision.md` §2):

| что | владелец | правило |
|---|---|---|
| потоки | область плагина `device_hub` | драйвер не открывает корень и не создаёт `Thread`; `spawn` keyword-only, умолчание None; без `spawn` операции с потоком (`jog_hold`, запуск программы, `return_job`) отказывают `RuntimeError` сразу; фабрика `delta_v2` без `spawn` — `RuntimeError` при создании |
| защёлка стопа | драйвер, на робота | сильнейший записанный уровень и «последняя запись упала»; сброс после записи движения (JOG_CONT) и при захвате программы / задания; не больше двух попыток на поколение |
| рассылка стопа | менеджер | всем роботам параллельно потоками `stop-<id>-<k>`; отказ `spawn` — стоп этому роботу в вызывающем потоке |
| срок | плагин | один абсолютный срок `monotonic() + 3,0 − 0,5` с: фаза 1 запись стопа + проверка эха в том же потоке → удаление воркеров → `scope.close` с остатком → фаза 4 без записи и без чтения эха |
| эхо стопа | драйвер / плагин | только диагностика: нет эха → `last_error` и health «стоп не подтверждён роботом»; чтения эха — только пока чтение успевает до срока |
| стоп оператора `abort` | драйвер | пишется всегда, защёлка его не блокирует |

**Гарантия (решение владельца 2026-10-19: «если всех выключаем — всех на стоп, если индивидуальных — только их»).**
Каждый подключённый робот, который выключается, получает ровно один стоп на каждое выключение (первый запрос выключения
открывает новое поколение защёлки: прежние стопы — оператора, отпускание jog — его не покрывают): при остановке процесса (выключение плагина)
стоп получают все подключённые роботы, при `disconnect()` одного робота — только он. Уровень: как раньше для движения
(программа и задание HARD, jog SOFT); простой робот (ничего не задано) получает SOFT. Неподключённый простой робот
стопа не получает (писать некуда). Защёлка не даёт второй записи в том же выключении, в том числе простому
роботу (фаза 4, `disconnect` после `request_stop`, второй `request_stop_all`). Недосягаемого робота останавливает его сторож `P_WDG_TIMEOUT_MS` (если он
не 0). Остановка роботов и закрытие области укладываются в срок.

Индивидуальный `disconnect()` ждёт эхо стопа до `soft_echo_timeout_s` (2,0 с) в потоке supervisor'а (запись и ожидание
эха; только запись — для `disconnect` T5.3c).

**Отклонения лида от текста §2 (приняты в круге 2):**
- `spawn` с умолчанием None (тесты T5.6 создают драйвер без потоков), отказы — на операциях с потоком.
- Простой робот стоп получает (SOFT) — решение владельца 2026-10-19, см. «Гарантия»; в тексте §2 было «только роботу
  с заданным движением».
- Повтор упавшей записи — только если запись с повторами транспорта (`timeout_sec * (retries + 1)`) успевает до
  срока: транспорт хаба сам повторяет запись по таймауту.
- `remove_worker` фреймворка (до 5,0 с на поток) в срок не входит.
- Стоп задания CVT при остановке процесса идёт через защёлку (HARD, одна запись), а не отдельной записью задания (H1).

**Исключения из «одна запись `STOP_REQ` на робота за стоп процесса».** Вторая запись — только если первая не покрывает
движение робота: упавшая запись (повтор один раз, если успевает до срока) или команда, принятая роботом после стопа
(О5 клиента / H-B). Исключения не исключают друг друга: повтор и О5 на одном роботе дают до трёх записей. Простой
робот (SOFT по решению владельца 2026-10-19) второй записи не получает: защёлка гасит её (фаза 4 и `disconnect` после
`request_stop`). Стоп оператора выключение не покрывает. Сторожа считают записи на стороне робота, `test_t53r2_stop_hazards.py`:
1. Повтор после упавшей записи: один раз на поколение защёлки и только если запись успевает до срока
   (`timeout_sec * (retries + 1)` от текущего момента не выходит за срок). Третьей попытки нет, даже если срок её вмещает.
2. H-B: JOG_CONT, вернувшийся после стопа процесса (замок перехода jog не взят до срока, JOG_CONT в полёте), получает
   свой стоп: первый стоп лёг на робота раньше этой команды и её не покрывает.
3. О5 клиента (`_reissue_stop_if_overtaken`): команда, принятая роботом ПОСЛЕ стопа, получает свой стоп. Воспроизведено
   3 из 3 на только что запущенной программе (стоп в первые миллисекунды прогона: записи 0,0002 / 0,014 с и т. п.).
   «Ровно одна запись» на программе держится, только если в момент стопа нет команды в полёте.
4. Повтор стопа исполнителя в `on_progress` (микроокно К1): только если стоп процесса был записан ДО g0 прогона
   (`stop_generation == run_stop_base`); стоп, записанный после g0, прогон видит сам, повтор не пишется. Идёт мимо
   защёлки, один раз на прогон.

**Окно эха.** Чтения эха идут до `срок − timeout_sec * (retries + 1)` (чтение, начатое позже, пережило бы срок на мёртвой
связи). Срок плагина 2,5 с (3,0 − 0,5): окно эха = 2,5 − `timeout_sec * (retries + 1)` ≈ 0,5 с при умолчаниях
(`timeout_sec` 1,0, `retries` 1). При `timeout_sec` ≥ 1,25 с окна нет, и каждый остановленный робот помечается
«стоп не подтверждён роботом» (ложно, если стоп дошёл). Время эха HARD на реальной Delta не измерено — замер в T4.0;
до него 0,5 с — расчёт, а не измерение.

**Условия CTO (принятое решение).**
- L-9 (процесс `devices` с двумя роботами после «shutdown successfully» не выходит, PM убивает его через 5,0 с) чинится
  в PM до любого стенда с реальным роботом (T4.x).
- T5.3c: при `timeout_sec` ≥ 1,25 с окна эха нет — health показывает «эхо не читалось (нет окна)», а не «стоп не
  подтверждён роботом».

**Отвергнуто:** последовательная рассылка с коротким таймаутом (N роботов на полуоткрытой связи — N секунд);
сторож в автономном режиме драйвера (чинит путь, которого не должно быть); «никогда не повторять стоп» (повтор
после упавшей записи полезен).
**Связь:** ADR-DH-006 (supervisor-воркер), решение владельца 2026-10-03 (один владелец жизненного цикла).

## ADR-DH-010: Одно явное состояние RobotDriverV2 под одним замком; драйвер — пакет

**Дата:** 2026-10-20
**Статус:** accepted (T5.3f; решения teamlead стадии 0 Q1–Q10 и владельца 2026-10-20)
**Контекст задачи:** `plans/robot-protocol-v2/tasks/T5.3f.md`; ADR-DH-009 не меняется.

### Контекст

Драйвер робота v2 держал состояние в 30 полях (26 драйвера + 4 `_JogRun`, из них 14 флагов) и в 53 секциях
`with self._flags_lock` в 31 функции; всего 4 замка `threading.Lock()`. Каждый новый флаг проверялся в N воротах
(класс дефектов G2/G4/H* ревью T5.3c/d), `_busy` и `_prog_alive` писались парой в одних местах, файл вырос до
2037 строк, тесты читали и писали 138 приватных имён драйвера (31 из них — поля состояния). Решаем сейчас, пока
SPI хаба и T5.3e стоят на этом драйвере.

### Альтернативы

Q1 — граница замка состояния:

**A. Секции без ввода-вывода под одним листовым замком; I/O под `_jog_tx_lock` и `_param_lock`.**
- Плюсы: порядок замков и записей `STOP_REQ` прежний; поведение не меняется.
- Минусы: остаются 4 замка (3 + замок счётчика потоков модуля).

**B. Ожидание `connect()` под замком параметров переделано (:558).**
- Плюсы: меньше замков.
- Минусы: правка поведения, не рефакторинг.

**C. Один замок и для ввода-вывода.**
- Плюсы: «один замок» буквально.
- Минусы: секция стопа окажется за `JOG_CONT` / `PARAM_SET` — регресс В1 (стоп ждёт медленную запись).

Q7 — как делить файл:

**(i) Миксины по областям + ядро.** Плюсы: код переносится дословно, 75 швов тестов живы. Минусы: связь через атрибуты `self`.

**(ii) Компоненты-объекты.** Плюсы: чистые границы. Минусы: ломает 75 швов (по объёму это задача SPI).

**(iii) Переписать модули.** Плюсы: свободная форма. Минусы: переписывается каждая строка пути стопа.

### Решение

Выбрано A + (i).

- **Состояние.** `RobotState` (`drivers/robot_driver_v2/state.py`): 27 полей (23 + 4 `_JogRun`), 48 переходов + `view()`
  = 49 секций под одним листовым замком `self._lock`; `clock` внедрён. Правило 1:1: секция старого замка → один
  вызов перехода, порядок проверок побуквенно, `connected()` / `budget()` / `ev.is_set()` зовутся под замком в той же
  ветке, где звались (вынос до замка открывает окна W1/W4). Переход решает, драйвер действует вне замка.
- `_busy` + `_prog_alive` слиты в `program_active` (записи парные в одной секции, чтения под замком). `_values`,
  `_epoch` остаются в драйвере под `_param_lock`; `_ready`, `run.handle` — вне состояния.
- Чтение — `drv.state.view()` (замороженный `RobotStateView`, 23 поля; `JogView`). Сеттеров и методов «для тестов» нет.
- **Пакет.** `robot_driver_v2.py` → `drivers/robot_driver_v2/`, путь импорта прежний, `manager.py` не тронут. Модули:
  `state`, `texts`, `args`, `tlm`, `jobs`, `programs`, `params`, `jog`, `ops`, `stop`, `driver`; перенос — по коммиту на
  модуль, код дословно. `__init__` реэкспортирует шесть имён (`RobotDriverV2`, `RobotState`, `RobotStateView`,
  `JogView`, `_JogRun`, `_parse_tlm`); `_PROGRAM_JOIN_S` и `save_params` подменяются в модуле, где имя читается.
- **Отступление (c): сборка в `__init__`.** `driver.py` держит ядро `_RobotDriverCore(BaseDeviceDriver)`, а
  `RobotDriverV2(StopMixin, JogMixin, ProgramMixin, JobMixin, ParamMixin, OpsMixin, _RobotDriverCore)` и
  `RobotDriverV2._OPS = OPS` собираются в `__init__.py`. Причина: при сборке в `driver.py` fan-out файла 17 > 15 и
  `sentrux` `no_god_files` краснеет.
- **Переходы — внутренние, не SPI хаба.** Код вне пакета и вне тестов их не зовёт; сторожит
  `Services/device_hub/tests/test_no_private_driver_state.py` (AST). Тесты не трогают поля состояния (31 → 0); швы
  (`_client`, `_param_lock`, `_epoch`, …) — литеральный белый список `_SEAMS`, сумма 112 (регэксп стадии 0 дал 107, AST
  на HEAD `dbb62fb36` — 112: −1 `_lease_loop` был docstring, +6 `_reconnect_attempts` — имя базы). Сторож сканирует все тесты
  двух каталогов, кроме 7 тестов других драйверов (40 файлов). Снятие швов — задача SPI хаба.

Окна гонок (решение владельца 2026-10-20: T5.3f их не закрывает, не открывает и не пробует):

| окно | суть | статус |
|---|---|---|
| W1 | `request_stop` посреди `connect`: `shutdown` уже True, `_ready` ещё False — простой робот «не подключён», SOFT не записан, затем `connect()` → True | закрыто T5.3g (ADR-DH-011) |
| W1′ | `connect` выходит между секциями `request_stop` (`request_stop_begin` → `process_stop_plan`): план видит «не подключён», 0 SOFT | закрыто T5.3g (ADR-DH-011, снимок `_stop_linked`) |
| W2 | 6 записей `_ready` без замка | закрыто T5.3g (ADR-DH-011, `_ready` в `RobotState`) |
| W3 | `run.handle` под `_jog_tx_lock`, чтение без него | по замыслу К4, не дефект |
| W4 | `connect_reset` после `request_stop`: `shutdown` True при `stopping` False, «стоп не подтверждён» теряется | закрыто T5.3g (ADR-DH-011, `connect_begin`) |

  таймаут `_jog_tx_lock`, повтор, эхо) не менялся. Миграции нет: путь импорта и публичные имена прежние.
- **Ограничения:** новый переход — только внутри `RobotState`, в одной секции, без ввода-вывода; ввод-вывод — под
  `_jog_tx_lock` / `_param_lock`; новый тест другого драйвера вносится в
  `_OTHER_DRIVER_TESTS` сторожа, иначе его швы войдут в счёт (литерал файлов `_SCANNED_FILES` = 40).
- **Риски:** (1) W1 и W4 найдены чтением кода, не воспроизведены — проба с барьером в T5.3g. (2) Сторож (б) не видит
  пять общих имён переходов (`view`, `enqueue_job`, `enqueue_return`, `stop_unconfirmed`, `stop_unconfirmed_text`) через
  псевдоним (`st = drv.state; st.view()`) и `getattr(drv.state, …)`; уникальные имена ловятся при любом получателе.
  (3) Любая правка пути стопа требует повтора матрицы инъекций (M1–M10, H1–H4, L-I1..L-I5, `T5.3f.injections.md`): прежние красные обязаны остаться красными.

## ADR-DH-011: `connect`, `request_stop` и обычный `disconnect` драйвера робота v2 линеаризуются переходами `RobotState`

**Дата:** 2026-10-21
**Статус:** accepted (T5.3g; решения лида inspector-bottles-a9 и владельца 2026-10-19, 2026-10-20); дополнен T5.3h (решение владельца 2026-10-21)
**Контекст задачи:** `plans/robot-protocol-v2/tasks/T5.3g.md`, `T5.3g.design.md`, `T5.3h.md`; уточняет ADR-DH-010 (`_ready` теперь в состоянии,
окна W1, W1′, W2, W4 закрыты); ADR-DH-009 (путь стопа) не меняется.

### Контекст

ADR охватывает `connect`, `request_stop` (T5.3g) и обычный `disconnect` посреди `connect` (T5.3h, решение владельца 2026-10-21).

Проба окон барьером (`T5.3g.probe.md`) подтвердила W1, W4 и WW на коде T5.3f: простой робот, которому `request_stop`
пришёл посреди `connect`, не получал SOFT, а `connect()` возвращал True и делал драйвер «готовым» после выключения;
`connect_reset` после стопа снимал `stopping` и «стоп не подтверждён». Правило владельца 2026-10-20: простой робот
посреди `connect` считается подключённым, получает один SOFT и никогда не «готов» после выключения; правило
2026-10-19: неподключённый простой робот SOFT не получает.

### Решение

- **`_ready` живёт в `RobotState`.** На драйвере `_ready` — свойство: геттер читает `state.ready` без замка,
  сеттер зовёт `state.set_ready` под замком. Замок состояния — `Lock`, не `RLock`, а `is_connected` зовётся под ним
  (`process_stop_plan`, `admit_launch`), поэтому геттер замок не берёт (чтение bool атомарно, все записи под замком;
  прецедент — `returns_done`). Записи `False` в `disconnect`, `_link_lost`, `_close_after_disconnect` идут через сеттер.
- **Переходы `connect`.** `connect_begin` (решение `"shutdown"` / `"busy"` / `"go"` + сброс останова + `_ready = False`
  + `_connecting`), `connect_link_up`, `connect_restore`, `connect_finish`, `connect_end`. `connect_link_up`,
  `connect_restore` и `connect_finish` при `_stopping` или `_shutdown` отказывают, `connect()` возвращает False.
  `connect_end` стоит в `finally` и снимает `_connecting` и `_connect_linked` на любом выходе.
- **Точка линеаризации — `request_stop_begin`.** В той же секции, где ставится `_shutdown`, при первом вызове
  запоминается `_stop_linked = _connecting and _connect_linked`. `process_stop_plan(connected, link_up)` берёт этот
  снимок, а не живые флаги: `connect` мог выйти между секциями `request_stop` (W1′), снимок это переживает.
  Дизъюнкт плана: `connected() or (_stop_linked and link_up())`; `link_up` — `transport.is_connected` без `_ready`.
- **Граница A3 — `connect_link_up`.** У настоящего транспорта внутри `connect()` `is_connected` False до
  `Services/modbus/core/device.py:103`, поэтому «связь поднята» — это переход после подключения транспорта (для
  готового до `connect` робота — сам `connect_begin`). Стоп раньше этой границы: записи нет, «стоп не подтверждён»
  не ставится, `connect()` False, `probe` не зовётся.
- **Нет SERVO и DO после стопа — по возможности.** `_run_on_connect` возвращает bool и проверяет `_sync_cancelled()`
  перед `client.servo` и каждым `client.do_set`. Окно «проверка -> запись» остаётся: закрыть его можно только
  сериализацией с путём стопа — вне T5.3g.
- **Обычный `disconnect` посреди `connect`** (`_stopping` без `_shutdown`) тоже отказывает `connect_finish` и
  `connect_restore`: `connect()` → False, `is_connected` False. Побочный эффект: в пути тика, если
  `desired_connected` остался True, отказ считается неудачным переподключением (`_note_reconnect_failed()`).
- **SOFT при обычном «Отключить» посреди `connect` (T5.3h, решение владельца 2026-10-21 «да — SOFT и при обычном
  «Отключить» посреди connect»).** Правило T5.3g для `request_stop` переносится на обычный `disconnect`: простой
  робот, связь которого была поднята к стоп-секции `disconnect` (граница A3; у готового до `connect` робота —
  `connect_begin`), получает ровно один SOFT; до A3 записи нет (правило 2026-10-19), `connect()` False.
  Решение держится и на живом пути: переподключение тика против «Отключить» супервизора.
  - **Снимок в D2.** `disconnect_stop_plan(program_level, link_up)` пишет `_stop_linked` — «связь была поднята» —
    в стоп-секции (D2), а не в `disconnect_begin` (D1): между D1 и D2 `connect` ещё может поднять связь. Выражение
    вычисляется ДО `self._stopping = True` (иначе оно читает свой же флаг) и только при `not _shutdown` (снимок
    `request_stop` не переписывается). Терм `link_up()` живой (`transport.is_connected` в D2): без него готовый робот
    с упавшей вне тика связью давал снимок True, хвост `disconnect` закрывал уже закрытый сокет, а тик открывал его
    снова и не закрывал (утечка сокета, проба H18).
  - **Монотонный снимок.** Оба писателя пишут одно выражение: `(_stopping and _stop_linked) or (_connecting and
    _connect_linked)` (в D2 — с живым `link_up()`). Внутри одного выключения значение только растёт: `request_stop`
    целиком между D2 и D3 снимок `disconnect` не обнуляет (H15). Точка сброса — `connect_begin` (снимает
    `_stopping`). Новых полей нет.
  - **Решение одной секцией.** `disconnect_soft_plan(connected, link_up)`: `connected() or (_stop_linked and
    link_up())` и защёлка не покрывает SOFT. Заменяет `is_connected` и `latch_covers` в `_request_stop`. Отступление
    от «правила 1:1» (см. докстринг `RobotState`): `connected()` теперь зовётся под замком состояния, как в
    `process_stop_plan`.
  - **Один владелец закрытия.** Тик после отказа `connect` при `desired_connected` False не закрывает транспорт,
    если `disconnect_owns_close()` (`_stopping and not _shutdown and _stop_linked`): хвост `disconnect` (D6)
    закрывает всегда, уже после решения о SOFT (H16). Без этого тик закрывал сокет раньше решения о SOFT, и
    `disconnect_soft_plan` не видел живой связи.
  - **Повторная проверка в тике.** `_ensure_connected` после захвата `_param_lock` проверяет `desired_connected`
    ещё раз: «Отключить», пришедшее между первой проверкой и замком, не даёт `probe`, PARAM_SET, SERVO и DO (H13).

### Отклонено

Обратный вызов из перехода, который ставит `_ready` драйвера: код драйвера выполнялся бы под листовым замком, а W2
остался бы открытым.

### Последствия

- Новых замков нет; порядок `_param_lock` → замок состояния сохранён (переходы зовутся из `connect` под `_param_lock`).
  `connect_check`, `connect_reset`, `is_shutdown` остаются (контрактные тесты).
- Окна W1, W1′, W2, W4 и WW закрыты. `request_stop` после `connect_finish` — по-прежнему 1 SOFT, `connect()` True.
- Остаётся открытым: проба `issue_stop` в WW идёт без бюджета срока (на медленной живой связи до 3 чтений и 1 записи).
- T5.3h: обычный `disconnect` посреди `connect` даёт один SOFT связи, поднятой к D2 (H1–H5, H12, H15, H16; блиндовая
  приёмка B1, B2, B5); `request_stop` до решения D3 и `disconnect` вместе дают всего один SOFT (H14, H15, H17).
- **Остаток I1 (сужен, не закрыт).** Тик прошёл обе проверки `desired_connected` (в `_ensure_connected` и под
  `_param_lock`), затем супервизор ставит `desired_connected = False` и проходит D1–D6, затем `connect_begin` тика
  снимает `_stopping`. Окно «повторная проверка → `connect_begin`» — микросекунды, без ввода-вывода. Эффекты:
  (а) PARAM_SET, SERVO и DO после «Отключить»: тик открывает сокет снова, `sync_params`, `_run_on_connect`
  (`servo(True)` / `do_set`), `connect_finish`, затем закрытие ветки тика; (б) за эту сессию SOFT нет; (в) у настоящего
  транспорта D6 между открытием сокета и вводом-выводом синхронизации даёт исключение, `_sync_cancelled()` False,
  поэтому `_record_err` и `_publish_error(«подключение к роботу не удалось…»)`; «без `_record_err`» верно только
  для порядков, где `_stopping` не снят (I2–I5). Полное закрытие требует поля «идёт disconnect» — отклонено.
- **Остаток: `_shutdown` и «Отключить» одновременно.** `disconnect_owns_close` при `_shutdown` возвращает False: тик
  закрывает сокет сам, и `process_stop_plan` может увидеть `link_up()` False (нет SOFT). Не регресс: до T5.3h тик
  закрывал безусловно при `desired_connected` False.
- **Остаток: снимок от завершённого `disconnect`.** `_stopping` от прошлого `disconnect` без `connect` между ними
  делает снимок D2 монотонным (принято): безопасно только с живым `link_up()`. Лишний SOFT возможен, лишь если D6
  прошлого `disconnect` упал и сокет остался открытым.
- **Остаток: `request_stop` после решения D3 (до D6) — 2 SOFT.** Как у подключённого робота на main: `request_stop_begin`
  открывает новое поколение защёлки (ADR-DH-009), снимок монотонен, `link_up()` True до D6 — `process_stop_plan` пишет
  второй SOFT (между решением D3 и записью, после записи до D6). Воспроизведено ревью ветки; закреплено H19. Каждое
  выключение получает свой SOFT; один SOFT при любом порядке — отдельная задача, решение владельца.
- **Остаток: готовый робот, ручной `connect` на живой связи, связь падает между D2 и открытием сокета (C3).**
  Сокет открывает C3 самого `connect` (`if not transport.is_connected and not transport.connect()` в
  `_connect_locked`) уже после D6, и его никто не закрывает. Тик до этого не доходит: `_param_lock.acquire(blocking=False)`
  не берётся, пока идёт `connect`. Супервизор сериализует ручные `connect` и `disconnect` — практически недостижимо;
  пробой не покрыто.
- **Остаток: поток `disconnect` обрывается между D2 и D6.** Ввод-вывод в `_request_stop`, `_close_thread` и
  `transport.disconnect` ловится, но `disconnect_stop_plan(..., link_up=...)` и `disconnect_soft_plan(lambda:
  self.is_connected, ...)` стоят вне `try`: исключение из `transport.is_connected` (у `ModbusDevice` невозможно, у
  подмены или моста возможно) и `BaseException` завершают `disconnect` до D6. До T5.3h тик закрыл бы сокет в этом
  случае, теперь не закрывает (`disconnect_owns_close()`): сокет открыт до следующего `connect` (он закрывает старый
  сокет) или до остановки процесса (`_on_shutdown` → D6). Для `ModbusDevice` практически недостижимо; разбор
  чтением, не воспроизведено.
- `_note_reconnect_failed` не менялся: для GUI «Отключить» не важен (супервизор ставит `desired_connected = False`
  до `manager.disconnect`, тик идёт в ветку закрытия); неудачной попыткой отказ считается только при `disconnect()`
  без смены `desired_connected` (`manager.remove`, `manager._on_shutdown`) — драйвер выбрасывается или выключается.

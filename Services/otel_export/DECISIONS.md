# Services/otel_export — Архитектурные решения

Локальные ADR сервиса. Индекс фреймворка (`multiprocess_framework/DECISIONS.md`) слой
`Services` **не сканирует** (`scripts/sync/adr_modules.py` глобит только
`multiprocess_framework/modules/*/DECISIONS.md`) — ссылка в индекс вносится вручную
(долг Task 4.3 плана).

## ADR-OTEL-001: SDK импортируется лениво, а `Resource` — наш собственный тип

**Дата:** 2026-09-05 · **Статус:** accepted · **Refs:** plans/otel-export.md Task 0.2 шаг 2

`opentelemetry` не импортируется ни на одном уровне модуля в `Services/otel_export/*` и
`Plugins/io/otel_export/*`. Единственная дверь к SDK — `exporter.py`, и только внутри
функций. Из этого следует и второе: тип `Resource` в контракте — **наш** dataclass, а не
`opentelemetry.sdk.resources.Resource`, иначе `interfaces.py` перестал бы импортироваться
без установленного extra.

**Почему.** `class_loader` фреймворка строит класс плагина по dotted-path и глотает
`ImportError` (`log.error → None`). Модульный `import opentelemetry` превратил бы
«не установлен extra `[otel]`» в молчаливое «процесс не поднялся»: без причины, без адреса,
без команды установки. Ленивый импорт делает отказ объектом — `sdk_available()` возвращает
`(False, "missing: uv pip install --inexact '.[otel]'")`, и хост уходит в состояние `error`
с этим текстом в readback.

**Отвергнуто:**
- *модульный импорт с `try/except ImportError` и заглушкой* — заглушка живёт дальше по коду
  и отказ всплывает позже и глуше, уже на отправке;
- *`if TYPE_CHECKING: from opentelemetry...` ради типов SDK в сигнатурах* — тогда контракт
  описан чужими типами, и Ф1 (чистые функции, без сети) не тестируется без установленного
  extra.

**Проверяется:** тесты E1 (AST-разбор всех `.py` предмета), E3 (импорт пакета в чистом
подпроцессе не тянет `opentelemetry` в `sys.modules`), E2/E4 (пара «SDK есть» / «SDK нет»).

## ADR-OTEL-002: типы контракта — frozen dataclass, не TypedDict

**Дата:** 2026-09-05 · **Статус:** accepted

`MappedRecord`, `Resource`, `ExportOutcome`, `FlushOutcome` — `@dataclass(frozen=True, slots=True)`.

**Почему.** У `TypedDict` нет доступа точкой (`outcome.accepted`), а именно так контракт
читается в тестах и в коде хоста. `frozen=True` + `slots=True` дают опечатке в имени поля
громкий `AttributeError` вместо тихого нового ключа — а тихий ключ на этой дороге уже
класс дефекта: счётчик, который «есть», но не тот.

Правило Dict at Boundary соблюдено: между процессами едут `dict` (`to_dict`/`from_dict`
конфига и display-записи), dataclass'ы живут **внутри** процесса экспортёра.

**Отвергнуто:**
- *`TypedDict`* — см. выше; плюс `total=False` делает любое поле необязательным молча;
- *обычные (не frozen) dataclass* — запись, которую можно поправить после маппинга, ломает
  тождество потерь: посчитали одно, отправили другое;
- *`pydantic.BaseModel`* — валидация на горячем пути записи; правило плана прямое: Pydantic
  только на конфиг.

## ADR-OTEL-003: поля объявлены в сервисе, регистры плагина — производная

**Дата:** 2026-09-05 · **Статус:** accepted · **Refs:** plans/otel-export.md Task 0.4, ADR-120

`OtelExportConfig(SchemaBase)` в `Services/otel_export/config.py` — единственное объявление
полей, вместе с `FieldMeta`. `Plugins/io/otel_export/registers.py::OtelExportRegisters` —
подкласс с `@register_schema`, без единого переобъявленного поля.

**Почему.** Прецедент `Plugins/io/telemetry_sink` кладёт поля в регистры («register = единый
источник параметров + FieldMeta»), но там нет сервиса-владельца. Здесь он есть, а слои
`framework → Services → Plugins` запрещают `Services` импортировать `Plugins` — значит поля
обязаны жить в сервисе, иначе он их не увидит. Две таблицы полей разъезжаются молча: критерий
C2 приёмки сравнивает наборы полей множествами именно поэтому.

`readback()` тоже живёт на конфиге, а не на регистре: маскировка секретов и «эффективное
значение» — свойство схемы, а не двери GUI.

### Коллизия обязательного `endpoint` с тем, как строятся регистры — закрыта (вердикт CTO, Task 0.5)

Критерий приёмки B1 требует `endpoint` обязательным без дефолта; фреймворк создаёт
managed-регистр **без аргументов** (`plugin_orchestrator._collect_register_schemas:325`:
`instance = reg_item()`), а значения фрагмента топологии туда не попадают вовсе.
Воспроизведено прогоном: `OtelExportRegisters()` → `ValidationError: endpoint: Field
required`, исключение ловится `except Exception` и уходит в `log_error`, то есть регистр у
плагина не появится **никогда** — даже когда ключ во фрагменте написан. Третья дорога,
проверенная CTO отдельно: `generic_process_config.from_plugins:229` строит
`reg_cls(**reg_fields)` **без `try`** — обязательное поле там роняет сборку топологии
целиком, а не плагин.

**Принят вариант (а).** `OtelExportConfig.endpoint` остаётся обязательным без дефолта — там
его и проверяет B1. `OtelExportRegisters.endpoint` (Plugins/io/otel_export/registers.py)
переопределяет ТОЛЬКО дефолт на `""`, сохраняя `FieldMeta` целиком. Механизм: у `SchemaBase`
не выставлен `validate_default`, поэтому пустой дефолт не проверяется валидатором
`_endpoint_not_blank` при построении самого регистра — `OtelExportRegisters()` и
`reg_cls(**reg_fields)` в `from_plugins` строятся успешно на всех трёх дорогах. Отказ
переезжает на шаг позже — в `OtelExportConfig(**reg.model_dump())` внутри `configure()`
плагина (Ф2.1), где пустой `endpoint` уже отвергается по имени ключа. Это делает критерий
Task 3.1 («фрагмент без `endpoint` → плагин в `error` с адресом ключа») достижимым.

**Долг closure (кандидат, не в этой фазе):** вариант (в) — строить managed-регистр из
значений фрагмента топологии, а не из голых дефолтов конструктора. Устранил бы саму
необходимость варианта (а) для будущих обязательных полей других плагинов. Репродукция —
`plugin_orchestrator.py:325` (`instance = reg_item()`, всегда без аргументов) и
`generic_process_config.py:229` (`reg_cls(**reg_fields)`, без `try`).

**Отвергнуто:**
- *дублировать поля в регистрах* — вторая таблица, расхождение через одну задачу;
- *секция `observability.otel_export` в конфиге фреймворка* — с closure Task 2.2 незнакомый
  ключ секции на L3 отказ слоя, а поле схемы без читателя во фреймворке режет страж;
- *регистры как отдельный `SchemaBase` с копией `FieldMeta`* — то же дублирование, только
  разнесённое по файлам.

## ADR-OTEL-004: `ObservabilityPort` — минимальный порт, и он НЕ совпадает с `PluginContext`

**Дата:** 2026-09-05 · **Статус:** accepted (с названным разрывом) · **Refs:** closure Task 4.5

Сервис не заводит своего контекста. Он принимает `Protocol` из пяти методов: `log_info`,
`log_warning`, `log_error`, `record_metric`, `report_error`.

**Разрыв, найденный сверкой с кодом (а не предположением).** План утверждал, что этому
протоколу «удовлетворяет `PluginContext` сегодня». Это **неверно**: `PluginContext`
(`multiprocess_framework/modules/process_module/plugins/base.py`) даёт четыре метода из пяти,
а `report_error` живёт на свойстве `health` (`ctx.health.report_error(exc, context=…,
throttle=…, **fields)` → `HealthReporter`). `isinstance(ctx, ObservabilityPort)` сегодня
даёт `False`.

**Решение.** Порт оставлен пятиметодным: разделение «строка в журнал» (`log_error`) и
«инцидент» (`report_error`) — сознательное правило фреймворка (ADR-PM-030), и сервис,
у которого нет доступа к инциденту, тихо потеряет отказ экспорта. Разрыв закрывает **хост**
тонким адаптером в Ф2.1 (5 строк: делегирует четыре метода на `ctx`, пятый — на
`ctx.health`). Первый аргумент передавать **позиционно**: во фреймворке он зовётся `exc`,
в порту — `error`.

**Отвергнуто:**
- *убрать `report_error` из порта ради формального соответствия* — сервис остался бы без
  двери в плоскость ошибок, а отказ экспорта — ровно инцидент;
- *принимать `ctx` целиком и звать `ctx.health.report_error`* — сервис бы знал внутреннее
  устройство контекста плагина, и после closure 4.5 (`ServiceContext`) пришлось бы менять
  сервис, а не хост;
- *править `PluginContext` во фреймворке* — правки фреймворка в этой фазе запрещены;
  находка идёт долгом в closure (кандидат: добавить делегат `report_error` на контекст).

## ADR-OTEL-005: `readback()` показывает таймаут там, где он действует; секрет в тексте отказа закрыт `hide_input_in_errors`

**Дата:** 2026-09-05 · **Статус:** accepted (правка Task 0.5 по вердикту CTO — заменён
предохранитель) · **Refs:** plans/otel-export.md Task 0.5

`readback()` возвращает поля конфига, где `headers` замаскированы `***`, **плюс**
производный ключ `export_timeout_sec`.

**Почему.** Проверено на установленном SDK 1.44.0: `BatchLogRecordProcessor.__init__` несёт
над обработкой `export_timeout_millis` комментарий `# Not used. No way currently to pass
timeout to export.`, а `BatchProcessor.force_flush` — `TODO: Fix force flush so the timeout
is used` (issue 4568). Значит наш `export_timeout_ms`, отданный батчеру, не делает ничего;
работает только `OTLPLogExporter(timeout=<секунды>)`. Readback, показывающий одно
`export_timeout_ms`, был бы формально честным и практически ложным: оператор считал бы, что
покрутил таймаут отправки, покрутив ничто.

Маскируется **любое** значение заголовка, а не «похожее на секрет»: развилка «этот заголовок
безопасный» и есть место утечки. По той же причине текст ошибки валидатора называет ключ
и требуемую форму, но никогда — значение.

### Утечка, которой не хватило одной маскировки (найдена авторским тестом 2026-09-05)

Своего аккуратного текста валидатору мало: **`str(ValidationError)` у pydantic 2.13 печатает
вход целиком** —

```
… [type=value_error, input_value={'authorization': 'Bearer VerySecretValue999'}, input_type=dict]
```

То есть отвергнутый (а значит, чаще всего настоящий) токен уехал бы в `system.log` первой же
естественной строкой `ctx.log_error(f"конфиг не принят: {exc}")`. Правило «секреты в env»
защитило бы YAML и потеряло секрет в журнале.

### Первое решение (Task 0.4) было ýже факта — заменено вердиктом CTO (Task 0.5)

Первая редакция ADR называла `format_validation_error(exc)` «единственным безопасным
способом показать отказ этой схемы» и предлагала ревьюеру `hidden=True` на поле как
дополнительную меру. Обе идеи не выдержали проверки запуском:

- **`format_validation_error` не дотягивается до `from_plugins`.** Форматтер защищает только
  тот код, который его вызывает. `generic_process_config.from_plugins:229` строит
  `reg_cls(**reg_fields)` **без `try`** — там текст исключения формирует не наш код, а
  сам pydantic/traceback, и форматтер до этой дороги не достаёт вовсе.
- **`hidden=True` не работает.** `FieldMeta.can_modify` (`field_meta.py:234`) проверяет
  только `readonly` и `access_level`; докстринг на `field_meta.py:95` («hidden — скрыть в UI
  (`can_modify()` → False при hidden UI)») **не соответствует коду** — проверено чтением
  обоих мест. `readonly=True` со своей стороны закрывает только live-write через
  `update_field()` и заодно делает поле нередактируемым в GUI — не то, что нужно.

**Решение (замена, Task 0.5):** предохранитель — `model_config =
ConfigDict(hide_input_in_errors=True)` на `OtelExportConfig`. Замер (три класса × две
дороги, воспроизведено и в тестах трека):

```
=== без флага ===   secret_in_str=True  на конструкторе И на model_validate
=== с hide_input_in_errors=True ===
    ctor secret_in_str=False | model_validate secret_in_str=False | assignment secret_in_str=False
    во всех трёх текст сохраняет имя ключа "headers"
```

Флаг закрывает утечку на ВСЕХ дорогах построения схемы — конструктор, `model_validate`,
присваивание (`validate_assignment=True` унаследован от `SchemaBase`) — и, что решающее,
на `from_plugins`, до которой не дотягивался форматтер. `SchemaBase.model_config`
(`validate_assignment`, `populate_by_name`) не перетирается: pydantic v2 мёржит
`model_config` по MRO, а не заменяет — проверено прогоном при написании этой правки.

`format_validation_error(exc)` **остаётся в коде**, но меняет статус: это форматтер
ЧИТАЕМОГО ТЕКСТА для хоста (`exc.errors(include_input=False)`, без URL и context), а не
предохранитель. Звать его по-прежнему стоит везде, где отказ схемы уходит в лог или в
readback читаемой строкой — просто это больше не единственная защита от утечки.

**Цена флага (названа CTO, принята):** вход скрывается для ВСЕХ полей схемы, включая
числовые, — не только для `headers`. Сообщения кастомных валидаторов (`_endpoint_not_blank`,
`_level_is_known`, `_headers_only_env_placeholders`) по-прежнему называют значения там, где
это безопасно и нужно — эта правка их не касается.

Факт про pydantic (печатает вход целиком без флага) остаётся приколотым тестом на
негативной стороне: `Services/otel_export/tests/test_contract.py` теперь сторожит
ЗАЩИТУ (`test_secret_is_absent_from_str_of_the_error_on_all_three_roads`) — если она
когда-нибудь перестанет требоваться (pydantic перестанет печатать вход сам по себе), тест
покраснеет на утверждении «headers остаётся в тексте» лишь косвенно; явного пина опасности
больше нет, это осознанный выбор — дублировать факт об исходном поведении pydantic не
нужно, когда есть тест на итоговое поведение схемы.

**Отвергнуто:**
- *`readback()` как псевдоним `model_dump()`* — это эхо конфигурации, а не показание
  (сторожится тестом C4);
- *подставлять в readback значение из `${ENV}`* — readback уезжает в журналы и в GUI;
- *`SecretStr` для значений заголовков* — рассматривался. Редактирует `repr` поля, но
  `input_value` в тексте ошибки показывает СЫРОЙ вход до конверсии в `SecretStr`, то есть
  утечку через `ValidationError` не закрывает никак — только маскировал бы `str(cfg)` на
  уже провалидированном значении, что не та проблема;
- *`hidden=True` на `FieldMeta` поля* — отвергнуто по факту чтения кода:
  `can_modify` (`field_meta.py:234`) не проверяет `hidden` вовсе, только `readonly` и
  `access_level`; докстринг (`field_meta.py:95`) описывает поведение, которого нет;
- *`readonly=True` на поле* — закрывает только live-write через `update_field()`, попутно
  делает поле нередактируемым в GUI навсегда — не то, что нужно для двери конфига;
- *глушить текст отказа целиком* — оператор не узнает, какой ключ отвергнут.

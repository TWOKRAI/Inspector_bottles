# robot_comm — архитектурные решения

## ADR-RC-001: Транспорт — универсальный Services/modbus, не своя pymodbus-обёртка

**Дата:** 2026-06-11 · **Статус:** принято

**Контекст.** Рабочий `pc_full.py` держал собственную обёртку ModbusTcpClient с
`_atomic` (серия записей под одним Lock). План калибровки изначально предлагал
повторить её в robot_comm (долг P1.1 «мигрировать потом»).

**Решение.** Долг закрыт до возникновения: примитивы подняты в `Services/modbus`
(`ModbusDevice.transaction`, `RegisterTransport`, `RegisterMap`), robot_comm —
тонкая надстройка «карта + методы». Новые устройства повторяют паттерн.

**Последствия.** Один транспортный стек на все устройства; reconnect и
телеметрия — в одном месте; vfd_comm не знает про робота (Protocol-мост).

## ADR-RC-002: Abort-семантика транзакций (осознанное отличие от pc_full)

**Дата:** 2026-06-11 · **Статус:** принято

У оригинала `_atomic` латентный баг: `ok = (not rr.isError()) and ok` — серия
продолжалась после ошибки, маркер-флаг мог лечь поверх частично записанных
данных. `ModbusDevice.transaction` обрывается на ПЕРВОЙ ошибке — маркер не
пишется, частичный mailbox без флага инертен для Lua. Инвариант «маркер
последним» обязателен в каждом вызове (send_job/set_config/draw_*/vfd_*).

## ADR-RC-003: Модель владельца соединения (один master на процесс)

**Дата:** 2026-06-11 · **Статус:** superseded by ADR-DH-001 (2026-06-11)
> **Замещено:** runtime.py и co-location модель удалены. Владелец соединения —
> процесс `devices` (always-on), см. `Services/device_hub/DECISIONS.md` ADR-DH-001.

`RobotClient` НЕ singleton и НЕ создаётся каждым плагином. Владелец — плагин
`robot_io`: создаёт/коннектит/публикует в `runtime.py`/закрывает. Потребители —
`runtime.get_client()` (read-only владение). `service.py` — карточка каталога
БЕЗ собственного соединения: второй TCP-master к одному mailbox дал бы гонку
по проводу (Lock каждого клиента локален процессу). Все плагины робота обязаны
жить в одном `process_name` рецепта; мульти-процессный шаринг — IPC-канал
(отложено, см. план robot-calibration Фаза 4+).

## ADR-RC-004: Симулятор — два уровня с одним ядром

**Дата:** 2026-06-11 · **Статус:** принято

pymodbus 3.13 удалил классический мутируемый datastore (сервер принимает только
SimDevice; spike подтвердил — деприкейченные шеллы неработоспособны). Решение:

- `RobotSimCore` — чистая логика (list[int] + tick() как Lua Motion-цикл);
- `FakeRobotTransport` — in-process, чтение тикает ядро (детерминизм, ~90% тестов);
- TCP `sim_robot` — публичный хук `SimDevice(action=...)` отдаёт живой список
  регистров сервера (`attach`), фоновый ticker крутит ядро над ним. Хук обязан
  быть async-ФУНКЦИЕЙ (замыкание) — инстанс с async `__call__` не проходит
  валидацию pymodbus.

Sim сознательно воспроизводит ограничение реального Lua: зеркало ПЧ (0x1210+,
включая heartbeat) обновляется ТОЛЬКО по команде/пульсу VFD_FLAG.

## ADR-RC-005: Карта регистров — universal3, валидация DW-выравнивания

**Дата:** 2026-06-11 · **Статус:** принято

Источник карты — ТОЛЬКО `robot/universal3` (пара к текущему Lua): u2 расходится
(CFG=11 против 9, TLM=11, DCBUS_SCALE=10, REG_MODE, drawing-блок). DW-поля
обязаны лежать по чётным адресам (требование Lua-стороны) — проверяется при
сборке карты, а не в универсальном RegDW (это ограничение устройства, не Modbus).

## ADR-RC-006: Точность рисования — read-back ACK + мелкие пачки (без ping-pong)

**Дата:** 2026-06-17 · **Статус:** принято; в части «без ping-pong» для v2 заменяется ADR-RC-011 (предложено)

**Контекст.** Жалоба владельца: «теряется ~25% точек». Передача через
`split_draw_passes` геометрически точки не теряет, но `execute_path` (Lua) при
КОРОТКОМ чтении буфера молча уменьшает `count` (`if got < count then count = got`)
— точки пропадают без ошибки. Рассматривался стриминг с ping-pong буфером —
отвергнут владельцем как рискованный («не сломай рабочее рисование»).

**Решение.** Аддитивно, без переписывания транспорта:
- новый эхо-регистр `REG_DRAW_DONE_N = 0x1409` — прошивка пишет РЕАЛЬНО выполненное
  (пост-усечённое) число точек прохода; НЕ обнуляется как `draw_prog`;
- `RobotConfig.draw_pass_size` (≤ PTS_MAX=100, дефолт PTS_MAX) — мельче пачки = больше
  пакетов, каждый верифицируется; рецепт phone_sketch ставит 30;
- `_run_batch` после прохода сверяет `draw_done_n` с размером пачки; расхождение →
  повтор (`draw_retry`) той же пачки → стойкое расхождение прерывает рисунок (точки
  не теряются молча);
- превью lossless: рецепт `reduce_mode: none` — зелёные точки = ровно отправленное.

**Парность.** Lua + `registers.py` + `delta_universal3.yaml` + `sim_core` — один
коммит (sim на завершении пишет `done_n = draw_count`).

**Rejected.** Ping-pong двойной буфер — выше риск регрессии живого рисования при
той же цели; read-back проще и закрывает корень (тихое усечение).

## ADR-RC-007: Стоп рисования — аборт + взвод «домой» + flush памяти

**Дата:** 2026-06-17 · **Статус:** принято

**Контекст.** Владелец: Стоп должен «выбросить точки из памяти робота и вернуть
домой», следующее «Рисовать» — С НАЧАЛА. В DRAW-режиме Mirror НЕ опрашивает
`REG_STOP` (только `REG_DRAW_ABORT`), поэтому отдельной команды «домой» нет.

**Решение.** `_op_draw_abort` (device_hub): `draw_home_after(1)` → `draw_abort()` →
очистка очереди → `draw_flush()`. Заезд домой переиспользует существующую ветку
финала прохода `REG_DRAW_HOME=1` (execute_path) — без новой Lua-ветки. `draw_flush`
обнуляет flag/count/prog/done_n, но НЕ `draw_abort` (его потребляет и сама обнуляет
прошивка/sim — иначе отменили бы ещё не обработанный аборт). Рестарт «с начала»
структурен: `robot_draw` шлёт весь путь заново на каждый триггер.

## ADR-RC-008: Переезд между штрихами — П-образный, без диагонали

**Дата:** 2026-06-17 · **Статус:** принято

**Контекст.** На переходе к подводу (pen=0) `execute_path` делал один `MovL` из
(конец штриха, перо ВНИЗ) в (подвод, перо ВВЕРХ) — диагональный подъём-в-движении
тянул призрачную линию (баг #8 владельца).

**Решение.** Явный П-образный переезд через скретч-точку `GL_MAN` (id 81, в DRAW
простаивает): (1) вертикальный подъём в текущем XY до `pen_up` → (2) переезд на
высоте до подвода → (3) вертикальное опускание в подводе до `pen_down`. Высота
переезда = `pen_up` (live-tunable). Firmware-only (sim траекторию не моделирует) —
проверяется на железе.

## ADR-RC-009: Единый mailbox (seq + ACK/NAK + errno) вместо регистров режима

**Дата:** 2026-09-27 · **Статус:** Предложено (ред. 2, ждёт GATE-0)

**Контекст.** v1 держит 5 режимов через `REG_MODE` (переключать «только когда
свободен») и 5 пар флаг/busy — у каждой команды свой протокол. Ошибки видны
только в консоли DRAStudio; «залипший busy» и молчаливое усечение точек (см.
ADR-RC-006) — прямое следствие пяти разных протоколов вместо одного (plan.md §3,
строки «Режимы»/«Команды»/«Ошибки»).

**Решение.** Один mailbox CMD/RES (`0x1000..0x101F`, protocol-spec §3.1–3.2):
`CMD_SEQ` растёт на каждую команду, ответ всегда пишется (`RES_STATUS`
ACK/NAK, `RES_ERRNO`), включая внутреннюю ошибку `E_INTERNAL`. Слот один:
следующая команда — только после `RES_SEQ == seq` предыдущей; повтор seq —
повтор последнего ответа без повторного исполнения. Отдельного регистра
режима нет — активность выводится из исполняемой команды (`TLM_ACTIVITY`:
IDLE/PTP/JOG/CVT/SCENARIO/FAULT, protocol-spec §3.4).

**Последствия.**
- Один путь для всех команд вместо пяти; каждый опкод помечен `busy: allow|deny`
  (§5) — какие команды проходят во время длинной активности.
- Ответ на команду, пришедшую во время хода, задерживается до ближайшей точки
  опроса (между примитивами, на EXACT-точках) — таймаут клиента должен быть
  больше самого длинного примитива (protocol-spec §4, правило 3).
- v1-регистры и драйвер не трогаются (v1 заморожен); новый `client_v2`/`driver_v2`
  строятся только против mailbox.
- Ограничение: регистр режима в протокол не возвращается — два источника
  правды об активности (регистр + фактическое состояние команды) были ровно
  тем классом дефекта, который упраздняется этим решением.

**Отклонённые альтернативы.**
- Регистр-на-команду с busy-флагом (модель v1) — отклонено: каждая команда
  изобретает свой протокол заново, ошибка не видна нигде, кроме консоли
  DRAStudio (жалоба владельца «теряется ~25% точек», ADR-RC-006).
- Оставить `REG_MODE` рядом с mailbox «для подстраховки» — отклонено: активность
  и так однозначно выводима из состояния команды (plan.md §3 «Режимы»: «режима
  нет: активность выводится из команды»); второй источник правды снова заводит
  риск рассинхронизации.

## ADR-RC-010: Один YAML → кодоген для Python, Lua и `RobotParamsV2`

**Дата:** 2026-09-27 · **Статус:** Предложено (ред. 2, ждёт GATE-0)

**Контекст.** v1 держит карту регистров в 4 рукописных копиях (Lua,
`registers.py`, YAML, симулятор) — риск расхождения признан ещё в ADR-RC-005,
где выбор пал на единственный источник для карты v1 (`universal3`). Проектный
инвариант И1 (`tasks.md`) требует того же для v2: `delta_v2.yaml` — единственный
источник, Python- и Lua-константы, `RobotParamsV2` — только кодогеном.

**Решение.** `Services/robot_comm/protocols/delta_v2.yaml` описывает регистры,
константы, опкоды, errno, коды причин, параметры и сценарий 1:1 с
protocol-spec.md/params.md. `codegen.py` (T1.1) генерирует: `core/protocol_v2.py`
(`REG/OP/ERR/REASON/CONSTANTS/SCENARIO`), `core/params_v2.py` (`PARAMS` +
`RobotParamsV2(SchemaBase)` с `FieldMeta` для формы GUI) и Lua-таблицы
`REG/OP/ERR/PDEF/KIND/ACT` между маркерами
`-- ===== BEGIN/END GENERATED (delta_v2.yaml <sha8>) =====`. CLI `--check`
сверяет регенерацию с закоммиченным байт-в-байт.

**Последствия.**
- Рукописный адрес вне `delta_v2.yaml` — брак (правило 5 преамбулы `tasks.md`);
  любая правка протокола — строка YAML + регенерация, никогда прямая правка
  сгенерированных файлов или Lua-констант (инвариант И3: только таблицы).
- Форма параметров GUI строится из тех же метаданных (label/unit/min/max/группа,
  plan.md §4.3.1) — новый параметр = одна строка YAML.
- Свежесть контролируется тестом (`--check` = 0 на чистом дереве, T1.1
  приёмка) — расхождение ловится до коммита, а не кросс-чек тестом после факта.
- `scripts.sync` не индексирует `Services/*/DECISIONS.md`; ADR сервисов перечисляются
  в колонке ADR файла `Services/STATUS.md` (так же, как у `device_hub`, `vfd_comm`).

**Отклонённые альтернативы.**
- Оставить три поддерживаемые копии (Python/Lua/симулятор) с кросс-чек тестом —
  отклонено: кросс-чек ловит расхождение постфактум, а не до него; именно эта
  модель уже даёт v1 «4 рукописные копии» (plan.md §3), который план явно
  называет проблемой для устранения в v2.
- Генерировать кодогеном только Python, Lua оставить рукописным — отклонено:
  Lua-сторона наиболее уязвима к тихому расхождению (нет статической проверки
  типа импорта, как у Python), а инвариант И3 требует, чтобы Lua-константы были
  таблицами, порождёнными тем же кодогеном.

## ADR-RC-011: Программы точек и состояние инструмента — на ПК; прошивка исполняет точки

**Дата:** 2026-09-27 · **Статус:** Предложено (ред. 2, ждёт GATE-0) — **отменяет ADR-RC-006 в части «без пинг-понга»**

**Контекст.** ADR-RC-006 (2026-06-17) отверг стриминг с ping-pong буфером именно
потому, что владелец просил «не сломай рабочее рисование»: риск регрессии
казался выше пользы на ТОЙ модели транспорта, где рисование зашито в прошивку
и течёт через `execute_path` живым потоком. В v2 сама модель меняется: прошивка
больше не знает понятия «рисование» — точки, системы координат и шаги программы
живут на ПК (plan.md §4.4; §3, строка «Рисование, возврат, смена инструмента»:
«прошивка исполняет точки»). Длинные программы делятся на куски по EXACT-точкам,
и между кусками работает пинг-понг `offset` поверх `SC_RUN(count, sc_id, offset)`
(protocol-spec §7.4).

**Решение.** RC-011 явно отменяет ADR-RC-006 **только в части «без пинг-понга»**:
v2 действительно использует буфер с двумя половинами и смещением `offset`, но
границы кусков — **исключительно на EXACT-точках** (`KIND ≠ LINE_PASS`), то есть
там, где робот и так стоит между примитивами (protocol-spec §7.2 правило 4,
§7.4). RC-006 причину отказа не расписывает («отвергнут владельцем как рискованный»); владелец
тогда просил «не сломай рисование». Граница куска на EXACT-точке снимает главный риск
подмены данных посреди траектории: следующий кусок подгружается в свободную половину буфера, ПОКА робот
доисполняет текущий, но старт и конец куска — всегда в точке, где движение уже
закончилось. Сложность прошивки не растёт: `SC_RUN` не знает о «кусках» —
деление на куски (`run_chunks`) — понятие ПК (T3.2).

**Последствия.**
- Генератор рисования переезжает в `Services/robot_comm/programs/generators/draw`
  (T3.4), но берёт семантику (П-образные переезды, конец штриха EXACT, высоты
  пера) из тех же v1-источников, что и ADR-RC-006..008
  (`robot/main_actual.lua:521-624`).
- v1-путь рисования (33 вызова `draw_*`, plan.md §3) не трогается — рабочий
  канон до конца Ф7; v2-компилятор программ (T3.3) и геометрия (T2.0) — новый
  путь рядом.
- Ограничение: граница куска не может лежать внутри цепочки `LINE_PASS`
  (protocol-spec §7.2 правило 4) — доступ к Modbus посреди `LINE_PASS` рвёт
  упреждение и тормозит на каждой точке (урок v1, `main_actual.lua:576-580`).
- Известный риск: перенос рисования на ПК может ухудшить качество — план
  оценивает риск как «средний», закрывается property-тестами генератора (T3.4)
  и сравнением тем же файлом букв на Ф7 (plan.md §7).

**Отклонённые альтернативы.**
- RETURN и TOOLCHANGE как отдельные «сценарии» общего вида, зашитые как в v1/ред.1
  — отклонено решением владельца в ред. 2: это программы точек того же
  механизма, что и обучение (Ц4, plan.md §9 «Изменено в ред. 2»).
- Единый буфер без деления на куски, размером под самую длинную программу —
  отклонено: `changes-rev2.md` фиксирует переход «stride 8, 96 записей за
  GATE-1» → «stride 6, 55 записей, пинг-понг offset» именно ради того, чтобы не
  зависеть от расширения адресного пространства через GATE-1 для каждой длинной
  программы («длинные программы кусками; буфер в проверенном пространстве»).

## ADR-RC-012: Плоскость безопасности — `STOP_REQ` вне mailbox, сторожевой таймер на `TimerRead`, поводок jog

**Дата:** 2026-09-27 · **Статус:** п. 1 (`STOP_REQ` вне mailbox) **принят владельцем 2026-09-27** — явное исключение из решения владельца №2 ред. 1; остальное — предложено, ждёт GATE-0

**Контекст.** Решение владельца №2 ред. 1 требовало «все команды через mailbox».
В ред. 2 предлагается исключение для стопа: стоп обязан пройти, даже когда
mailbox занят длинной командой или транзакция ПК оборвалась на середине
(protocol-spec §2, §8; `changes-rev2.md` строка 1: «STOP — опкод mailbox» →
«регистр `STOP_REQ` с seq, без очистки», причина — «стоп при занятом mailbox;
нет гонки очистки»). Отдельно — сухой прогон пробы уже нашёл, что `os.clock()`
— процессорное время, останавливающееся во время `DELAY`: таймер на нём не
сработал бы никогда (plan.md §2, нижняя строка). Непрерывный jog
(`ContinueCartesianJOG`, RL 1-52 ⚑) не блокирует выполнение и нуждается в
собственном поводке, отдельном от `HB_PC`.

**Решение.**
1. `STOP_REQ = seq·4 + level` — регистр `0x1021`, пишется ПК одним FC6, **вне
   mailbox** (protocol-spec §8). Прошивка реагирует на **изменение** значения,
   не на уровень, и не очищает регистр — гонки «ПК пишет новый стоп, прошивка
   стирает старый» нет по построению (protocol-spec §8, правило 1). Это
   единственный пункт этого ADR, **который сам является открытым вопросом
   владельца** (plan.md §9, п.3: «Стоп отдельным регистром вместо опкода — на
   GATE-0») — до подтверждения статус остаётся PROPOSED.
2. Сторожевой таймер (`HB_PC`, `0x1020`) — только на `TimerRead()` от
   `TimerOn()` в момент старта программы, никогда на `os.clock()`
   (protocol-spec §9.6) ⚑ GATE-1: если `TimerRead` окажется непригоден,
   остаётся оценка по числу циклов простоя (`TLM_WDG_STATE = 3`, «таймер по
   оценочным часам»).
3. `JOG_LEASE` (`0x1022`) — ПК увеличивает с периодом ≤ `P_JOG_LEASE_MS / 3`,
   пока оператор держит кнопку jog; независим от `HB_PC` (protocol-spec §3.3,
   опкод `JOG_CONT`).

**Последствия.**
- Три регистра вне mailbox (`0x1020..0x1022`) — вторая плоскость, которую
  опрашивают и клиент, и прошивка независимо от потока команд.
- Прошивка обязана читать `STOP_REQ` каждый тик хода через Mirror (одно чтение
  за тик, protocol-spec §8 правило 3); во время хода читает Mirror, в простое и
  на EXACT-точках — Motion.
- ⚑ GATE-1: уровень HARD поднимает `DecL` до `P_DEC_STOP` перед `MotionStop()`,
  потому что `MotionStop` тормозит с ТЕКУЩИМ замедлением (RL 1-51) — без этого
  «быстрый» стоп мог бы оказаться не быстрее обычного.
- По умолчанию таймер включён (`P_WDG_TIMEOUT_MS = 3000`, protocol-spec §9.5):
  цена ошибок несимметрична — ложное срабатывание останавливает ленту
  (безопасно), выключенный таймер при падении ПК оставляет ленту крутиться без
  присмотра.

**Отклонённые альтернативы.**
- Стоп опкодом mailbox (решение №2 ред. 1) — отклонено в ред. 2: занятый
  mailbox или оборвавшаяся транзакция ПК задержали бы или потеряли бы стоп
  (`changes-rev2.md`, строка 1).
- Часы сторожевого таймера по количеству циклов простоя как ОСНОВНОЙ вариант —
  не выбрано: это зафиксировано ТОЛЬКО как запасной вариант на случай отказа
  `TimerRead` на GATE-1 (protocol-spec §9.6); основной вариант — `TimerRead`,
  потому что «часы есть в мануале» (`changes-rev2.md`, строка 4), а оценка по
  циклам может сработать позже таймаута, но не раньше.

## ADR-RC-013: Параметры — классы применения, `PARAM_APPLY`, сохраняемое зеркало + метка + отпечаток словаря

**Дата:** 2026-09-27 · **Статус:** Предложено (ред. 2, ждёт GATE-0)

**Контекст.** v1 держит ~11 регистров CFG и константы в Lua — изменение требует
перезаливки прошивки (plan.md §3, строка «Параметры»). Цель владельца Ц1:
«Управлять всеми параметрами через GUI на ПК и не перезаписывать робота»
(plan.md §1). Мануал (RL 12-2) утверждает, что `0x3000..0x3FFF` сохраняется при
выключении питания — если верно, параметры переживают перезапуск робота без
перезаливки; факт неподтверждён до пробы (`retain-check`, plan.md §2, помечен
⚑ GATE-1).

**Решение.** ~70 параметров (params.md §11.3), у каждого класс `apply`
(params.md §11.2):
- `live` — `PARAM_SET` разрешён во время команды, действует с ближайшей точки
  опроса;
- `idle` — во время команды NAK `E_BUSY`, действует со следующей команды;
- `reinit` — во время команды NAK `E_BUSY`; нужен явный `PARAM_APPLY` (опкод
  `0x52`), который переинициализирует подсистему (CVT, порт ПЧ); до этого
  `TLM_CFG_PENDING = 1`, зависящие команды (`CVT_JOB`) получают NAK
  `E_CFG_PENDING`.

Хранение: ПК — источник истины (`data/robot/<device_id>/params.yaml`); робот
держит рабочую копию в сохраняемом зеркале PMIR (`0x3000 + id`), защищённом
`PMIR_MAGIC`/`PMIR_CRC`/`PMIR_DICT` (отпечаток словаря этой сборки — ловит
новую прошивку с добавленным параметром, params.md §11.4). `P_CONFIG_EPOCH`
метит, чья конфигурация ПК стоит на роботе; при подключении драйвер сверяет
метку и отпечаток и досылает параметры при расхождении (params.md §11.4, шаги
1–4). ⚑ GATE-1: если проба не подтвердит сохранение `0x3000..`, зеркало
переезжает на `0x1300 + id` (не сохраняется), и драйвер досылает все параметры
после каждого перезапуска программы робота (params.md §11.4, п.6).

**Последствия.**
- Форма параметров GUI строится целиком из метаданных YAML (RC-010); новый
  параметр — строка YAML.
- Регистр фреймворка `register_update` для записи параметров НЕ подходит: он
  синхронный и локальный, а NAK робота приходит позже по Modbus (plan.md §4.3,
  п.3) — записи идут отдельной командой `robot_param_set` с ответом.
- Прошивка проверяет только диапазон каждого параметра; связи между
  параметрами (`R_MIN < R_MAX` и т.п.) проверяет ПК до отправки — проверка
  зоны на роботе остаётся второй линией защиты, а не единственной (params.md
  §11.1).
- ⚑ GATE-1: если переинициализация CVT/порта ПЧ на ходу программы окажется
  недопустимой, класс `reinit` меняет смысл на «после перезапуска программы на
  роботе», `PARAM_APPLY` отвечает NAK (params.md §11.2, сноска).

**Отклонённые альтернативы.**
- Единый класс «всегда разрешено на ходу» для всех параметров — отклонено:
  параметры, переинициализирующие подсистему на ходу (геометрия CVT, формат
  кадра порта ПЧ), рискуют испортить исполняемую интерполяцию или транзакцию
  RS-485 — отсюда разделение на три класса (params.md §11.2).
- Переиспользовать `register_update` фреймворка для записи параметров —
  отклонено явно (plan.md §4.3, п.3): «он синхронный и локальный... а NAK
  робота приходит позже по Modbus».
- Не заводить сохраняемое зеркало вовсе, всегда досылать параметры при каждом
  подключении (робот без памяти) — это ровно запасной вариант ⚑ GATE-1 на
  случай неподтверждённого сохранения, а не предпочтительная конструкция:
  предпочтительная сохраняет работоспособность робота без ПК между
  перезапусками (Ц1 «не перезаписывать робота»).

## ADR-RC-014: GUI — пакет сервиса `robot.*` в `Services/robot_comm/gui/`, данные в `RobotDataStore`, несколько роботов

**Дата:** 2026-09-27 · **Статус:** Предложено (ред. 2, ждёт GATE-0)

**Контекст.** Решение владельца 09-26: GUI — пакет сервиса, а не вкладка
прототипа (plan.md §9 «Изменено в ред. 2», §4.6). Ранее (v1/ред.1) вкладка
робота жила в прототипе напрямую, с 33 вызовами `draw_*` (plan.md §3, строка
«GUI»). Проектное правило слоёв (`Services/<x>/gui/`, контекст виджета:
команда с ответом, glob-подписка на состояние, без ссылок между виджетами) —
из плана `gui-constructor`. Цель Ц5 «в будущем — несколько роботов» требует
отсутствия глобального состояния в драйвере/клиенте/хранилище (инвариант И8).

**Решение.** Пакет `robot.*` живёт в `Services/robot_comm/gui/` (единственное
место с Qt для этого сервиса — инвариант И9): виджеты `robot.status`,
`robot.params`, `robot.jog`, `robot.programs`, `robot.calibration` (plan.md
§4.6). Те же действия доступны ручками Пульта и `backend_ctl` по адресам
`devices/robot_*` без виджета (инвариант И10: GUI не читает и не пишет файлы
данных робота — только команды бэкенда). Данные робота (параметры, точки, СК,
программы, калибровка) — по устройству: `data/robot/<device_id>/` через
`RobotDataStore`, независимо от `devices.yaml` (`changes-rev2.md`: «Данные в
`devices.yaml`» → «`data/robot/<id>/`, ревизия при записи»); в драйвере,
клиенте и хранилище нет глобального состояния — всё поле экземпляра (plan.md
§4.7).

**Последствия.**
- Экземпляр виджета привязан к одному `device_id`; два робота — два экземпляра
  виджета в раскладке (plan.md §4.7).
- Зависимость: `gui-constructor` Task 1.0 (правило `Services/<x>/gui/`) и 1.5
  (контекст виджета) должны быть готовы раньше; движок форм промоутится из
  прототипа (`frontend-constructor` T3.6) — пакет робота его второй
  потребитель, поэтому Ф6 делает промоушен сама, если T3.6 к её старту не
  готов (plan.md §4.6).
- v1-вкладка прототипа не трогается — остаётся замороженным запасным UI для
  v1-устройств.
- Ограничение: виджеты не ссылаются друг на друга; существующие Qt-исключения
  (`server/sim_monitor.py`, `sim_robot.py`) не трогаются — их судьба в
  gui-constructor Task 1.0 (сноска инварианта И9).
- Известный риск: Ф6 зависит от сроков двух соседних планов (`gui-constructor`,
  `frontend-constructor`) — план оценивает риск как «средний», смягчается тем,
  что Ф5 даёт полностью рабочий бэкенд без GUI (Пульт + `backend_ctl` уже
  покрывают его, plan.md §7).

**Отклонённые альтернативы.**
- Оставить UI робота вкладкой прототипа (статус-кво ред. 1) — отклонено
  решением владельца 09-26 именно ради переиспользуемого пакета сервиса
  (plan.md §9, §4.6).
- Один общий глобальный виджет/состояние на всех роботов — отклонено: не
  поддерживает «в будущем — несколько роботов» (Ц5) без состояния на
  экземпляр; явный инвариант И8 «нет глобального состояния в клиенте,
  драйвере, хранилище: всё — поле экземпляра».

# TCP-симулятор робота Delta (universal3)

Modbus-TCP slave с поведением `cvt_universal_full.lua` — для разработки и
тестирования рецептов **без физического робота**.

## Быстрый старт

```bash
# Терминал 1: поднять симулятор (127.0.0.1:5021, unit 2)
python -m Services.robot_comm.server

# То же + окно-монитор обмена (две колонки, счётчик дублей)
python -m Services.robot_comm.server --gui

# Терминал 2: запустить рецепт (после правки host/port в YAML, см. ниже)
python multiprocess_prototype/run.py hikvision_letter_robot
```

## Окно-монитор (`--gui`)

Отвечает на вопрос «сколько заданий инспектор шлёт на ОДНУ деталь».

| Колонка | Что показывает |
|---------|----------------|
| ◀ Принято от инспектора | записи Modbus, подписанные именами из карты регистров (чтения не сорят — только счётчик) |
| ▶ Отдал робот | события ядра: приём задания, завершение, стоп, серво |

Шапка: `заданий · ДУБЛЕЙ · выполнено · чтений`. У каждой строки — время и Δt
внутри своей колонки (три задания за 100 мс видно сразу).

**Детектор дублей** не сравнивает «те же X/Y» — лента едет, и та же деталь на
следующем кадре снята уже в другой точке. Проверяется инвариант трекинга
прошивки: два задания указывают на одну деталь, если разница координат
объясняется проездом ленты за разницу энкодеров

```
невязка = |(Δx, Δy) − (UX, UY)·Δenc·FACTOR_MM| < 5 мм
```

Строка `ДУБЛЬ #3: та же деталь, что #1 — та же съёмка отправлена дважды
(невязка 0.4 мм, Δenc=+0, Δt=0.07 с)` — прямая улика пропавшего дедупа в
тракте `line_filter → pixel_to_robot → robot_io → robot_driver` (очередь
драйвера — обычная FIFO, дедупа в ней нет).

**Причина повтора, не только факт (line-sim Ф5.1).** `SimJournal.counters()`
расщепляет `dups` на `dups_same_capture` (одна и та же съёмка отправлена
роботу дважды — дубль КОМАНДЫ) и `dups_tracked` (та же деталь снята на
другом кадре — дубль КАДРА/детекции); `dups == dups_same_capture +
dups_tracked` — инвариант. Владелец увидел это на живой линии (робот
забирал одну деталь трижды) и не мог сказать, что дублируется — эти два
счётчика разделяют причины **вне зоны неразличимости**: когда проезд ленты между
заданиями меньше радиуса (`|Δenc| · 0.144473 < 5 мм` — меньше ~35 отсчётов, на
101 мм/с меньше ~50 мс между постановками), повтор X/Y с новым энкодером
считается `dups_tracked` (замер: `(10, 20, e=1000)` + `(10, 20, e=1020)` →
`dups_tracked=1`), а на стоящей ленте (`Δenc = 0`) два честных кадра одной
детали — `dups_same_capture`. Причину читать вместе со скоростью ленты и
интервалом между заданиями; внутри зоны различит только номер кадра на стороне
прототипа. Наружу процесса — `Plugins/sim/robot_host` (команды
`sim_robot.journal`/`sim_robot.journal_reset`, см. его README).

**Третья причина 5.1 УШЛА отсюда (line-sim Ф5.1b).** «Те же X/Y, но ДРУГОЙ
энкодер» (была `repeats_frozen_xy`, строка `ПОВТОР`, тег `"repeat"`) на линии с
триггером ложно срабатывала на РАЗНЫХ, честных деталях — они снимаются в одной
точке кадра, и на проводе робота это неотличимо от повтора. Причина переехала на
сторону сцены — `TruthLedger.false_alarm_frozen_xy`
(`Services/line_sim/core/truth.py`), где считается только среди `no_object`
(ложных тревог), потому что только сцена знает реальные координаты объектов.
Контракт — `plans/line-sim/phase-5-contract-5.1b.md`.

## Как направить рецепт на симулятор

В файле рецепта (например `multiprocess_prototype/recipes/hikvision_letter_robot.yaml`)
секция `devices:` содержит транспорт робота. Для работы с симулятором замените
`host` и `port`:

```yaml
devices:
  robot_main:
    driver: robot
    transport:
      type: tcp
      host: 127.0.0.1       # было 192.168.1.7
      port: 5021             # было 502
      unit_id: 2
```

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `--host` | `127.0.0.1` | Адрес слушателя |
| `--port` | `5021` | Порт Modbus-TCP |
| `--unit` | `2` | Modbus unit_id робота |
| `--gui` | выкл. | Окно-монитор обмена (нужен PySide6) |
| `--job-ms` | `2500` | Длительность pick-place, мс |
| `--accept-ms` | `20` | Приём задания (`job_flag` 1→0), мс |
| `--belt-mm-s` | не задан | Скорость ленты на 100% частоты ПЧ (`BeltDrive.mm_s_at_max_freq`, line-sim Task 2.1). Не задано — старое поведение (константная скорость по `enc_rate`) |

### Лента (`BeltDrive`, line-sim Task 2.1)

Скорость ленты может задавать живая команда ПЧ (mailbox 0x1200..0x1204 — та
же, что инспектор шлёт на железо через мост `vfd_belt → robot_main`), а не
только константа:

- **`--belt-mm-s` НЕ задан (по умолчанию)** — старое поведение: постоянная
  скорость по `enc_rate` (как у голого `SimRobotServer()`), без `BeltDrive` в
  `core_kwargs`. Обратная совместимость `--job-ms`/e2e-тестов.
- **`--belt-mm-s` задан** — CLI строит `BeltDrive(mm_s_at_max_freq=<значение>,
  freq_max_hz=50.0)`; лента **стоит, пока не придёт первая живая команда
  пуска ПЧ** — как настоящий конвейер без пуска (см. `--help`).

В `RobotSimCore` без явной инъекции (`belt=` в конструкторе) используется
`BeltDrive.from_enc_rate(enc_rate, ...)` — старое поведение константной
скорости побитово. Модель — `Services/robot_comm/server/belt.py`.

**Скорость ленты идёт по реальным часам (Task 2.1b) — ОБА режима.**
`SimRobotServer._ticker` меряет фактический интервал между тиками
(`time.perf_counter()` — точнее `monotonic()` на Windows/Python 3.12, где у
`monotonic()` гранулярность ~15.6мс), а не считает его всегда равным
`TICK_INTERVAL_S` — `time.sleep()` не гарантирует ровно запрошенный интервал
(ОС планирует поток позже; на macOS замерено заметно дороже номинала).
`RobotSimCore.tick(dt_s)` принимает этот измеренный dt явным параметром
(`None` -> `TICK_INTERVAL_S`, старое поведение для прямых вызовов из
тестов). Измеренный dt зажат потолком `_MAX_TICK_DT_S = 0.1` с — пауза
процесса (GC, отладчик, свап) не должна прыжком доехать ленту на всю свою
длительность. И «сырой» режим (`BeltDrive.from_enc_rate` — дефолт без
явного `belt=`), и обычный (после `command()`) следуют РЕАЛЬНОМУ `dt_s`
через один и тот же remainder-аккумулятор (ревью, итерация 1: раньше сырой
режим был глух к `dt_s` — живой тикер с дефолтной лентой ехал заметно
медленнее заявленных 7/`TICK_INTERVAL_S`, и первая же живая команда ПЧ на
эквивалентную частоту давала скачок скорости).

### ⚠️ Тайминг — не косметика

Дефолт `--job-ms 2500` взят с железа. Раньше ядро отрабатывало задание за
**2 тика = 20 мс**, и на таком «мгновенном» роботе очередь заданий в драйвере
рассасывается быстрее, чем успевает накопиться: дефект «одна деталь → три
задания подряд с задержкой» на симуляторе **не воспроизводится**. Ускорять
осознанно — например `--job-ms 20` для быстрых e2e-прогонов.

Замерено на стенде: `--job-ms 300` → цикл 344 мс, `--job-ms 1500` → 1610 мс;
`--belt-mm-s 100/200` → 97 и 191 мм/с по приросту энкодера.

Для доступа с другой машины (например телефон-пульт через Wi-Fi):
```bash
python -m Services.robot_comm.server --host 0.0.0.0 --port 502
```

## Эмулируемые режимы

| Режим | MODE | Статус | Описание |
|-------|------|--------|----------|
| CVT (pick-place) | 0 | Полностью | Задание + трекинг ленты по энкодеру + поза укладки |
| DRAW (рисование) | 1 | Полностью | Полилиния + окружность, батчи, abort |
| MANUAL (jog) | 2 | Только регистры | Клиент пишет, sim не двигает (ручной jog для калибровки) |
| RETURN (возврат) | 3 | Полностью | Забор из слота + handshake |
| TOOLCHANGE (смена) | 4 | Полностью | target + handshake + обновление tool_cur |

Дополнительно: зеркало ПЧ (VFD bridge 0x1200/0x1210), энкодер (растущий),
телеметрия с heartbeat.

## Зависимости

Требуется `pymodbus` (extra `[modbus]`):
```bash
pip install '.[modbus]'
```

Без pymodbus пакет `robot_comm` работает (FakeRobotTransport для тестов),
но TCP-сервер не поднимется.

## Архитектура

```
SimRobotServer
  +-- pymodbus StartTcpServer  (Modbus-TCP slave, поток server)
  |     +-- action-хук         -> SimJournal.on_write  (сырой обмен с провода)
  +-- RobotSimCore             (конечный автомат, чистая логика)
  |     +-- on_event           -> SimJournal.on_event  (события прошивки)
  +-- ticker-поток             (tick() каждые 10мс = Motion-цикл)

SimJournal (потокобезопасное кольцо) <- drain() <- SimMonitorWindow (QTimer)
```

`RobotSimCore.attach()` привязывает ядро к живому списку регистров сервера
(GIL-безопасная мутация); клиент видит изменения немедленно.

`RobotSimCore(on_job_done=...)` (Task 3.5a, line-sim) — колбэк «задание выполнено», ровно
один вызов на задание (payload `index`/`x_mm`/`y_mm`/`ecap`/`t`), исключение из него ядро
не ловит. Заодно исправлен декодер `ecap`: раньше читалось одно слово `REG_JOB_ECAP` вместо
пары `REG_JOB_ECAP`/`+1` (`decode_int32`), значения выше 65535 приходили усечёнными.

## Слушатель отдельно от тикера (Task 5.4, `fault.drop`)

`SimRobotServer.start()`/`stop()` раньше поднимали/гасили TCP-сервер и
Motion-тикер одним куском — `stop()` затем `start()` не работал (`stop()`
взводит `self._stop`, второй `start()` заводит НОВЫЙ тикер-поток, но старый
уже вышел по этому же флагу — тикер бы не запустился заново). Для
`fault.drop` (обрыв СВЯЗИ, тикер/ядро продолжают жить) добавлены:

- **`stop_listener()`** — только `ServerStop()` + bounded `join()` потока
  сервера; тикер не трогает. Безопасно звать повторно (`ServerStop()` без
  живого сервера бросает `RuntimeError` «not running» — глотается).
- **`start_listener(ready_timeout=0.5)`** — сбрасывает `self._bound`, заводит
  НОВЫЙ поток `_serve()` (свежий `SimDevice` с пустыми регистрами), и ждёт
  (обычным TCP-коннектом+закрытием, без Modbus PDU — `core.attach()` этим не
  триггерится), пока порт не начнёт принимать соединения, иначе бросает
  `RuntimeError`. Первый же РЕАЛЬНЫЙ запрос клиента переносит текущее
  состояние `core.regs` в новый список (`core.attach`) — так регистры/энкодер
  переживают drop, ядро (`RobotSimCore`) не пересоздаётся. `start()`
  (обычный подъём процесса) зовёт с `ready_timeout=5.0` — восстановление
  после `fault.drop` держит тесный дефолт 0.5с, старт процесса нет (фикс-раунд
  ревью K3). Внутри цикла ожидания есть проверка «наш поток сервера ещё
  жив» (K2) — иначе успешный TCP-коннект мог оказаться к ЧУЖОМУ листенеру,
  случайно занявшему тот же порт, а не к нашему.

Таймаут готовности (`_LISTENER_READY_TIMEOUT_S = 0.5`) специально МЕНЬШЕ
внешнего bounded-join `fault.clear`/`shutdown` (≤1с, `Plugins/sim/robot_host`)
— иначе гонка: вызывающий закрыл бы порт ДО того, как pymodbus успел
выставить `ModbusBaseServer.active_server` внутри своего потока, и
`ServerStop()` не нашёл бы, что останавливать (TRAPS брифа Task 5.4).
Пойманная гонка не сведена к нулю математически (нет доказательства, только
таймаут-запас) — при аномально медленном bind под сильной нагрузкой ОС
`Plugins.sim.robot_host` уходит в retry-цикл восстановления (`_run_drop`,
0.5с между попытками, до успеха или `shutdown()`), не в вечный тупик; подробнее
— [`docs/reviews/2026-09-24_task-5.4-developer.md`](../../../docs/reviews/2026-09-24_task-5.4-developer.md).

**`pymodbus.server.ServerStop()` — процесс-глобальная функция, не метод
инстанса** (нет способа адресовать «остановить именно ЭТОТ сервер» — она
глушит единственный активный `active_server` процесса). Значит **один
`SimRobotServer` на процесс** — два одновременно живых инстанса в одном
процессе гонялись бы за одним и тем же глобальным состоянием, и
`stop()`/`stop_listener()` одного мог бы заглушить слушателя другого. Тесты
этого файла и `Plugins/sim/robot_host/tests/` держат ОДИН `SimRobotServer`
на тест (см. `running_plugin`/`_make_plugin` в тестах) и глушат незавершённые
`fault.drop` в teardown (`fault.clear`/`shutdown()`) — не оставляют фоновый
поток `_run_drop` живым между тестами.

`start()`/`stop()` теперь просто `ticker + start_listener(ready_timeout=5.0)` /
`ticker.join() + stop_listener()` — публичный контракт (сигнатуры, поведение
при повторном `stop()`) не изменился.

`SimRobotServer.delay_ms` (int, мс, по умолчанию 0) — читается КАЖДЫМ вызовом
action-хука сервера (`_make_register_binder(..., delay_source=lambda: self.
delay_ms/1000.0)`), `await asyncio.sleep(delay)` (не `time.sleep` — держит
ответ ОДНОМУ клиенту, не блокирует event loop сервера для остальных). Смена
значения на лету НЕ требует рестарта слушателя — источник задержки читает
`self.delay_ms` заново на каждый доступ. **Задержка идёт ПЕРВОЙ строкой
биндера** (фикс-раунд ревью R1, MAJOR) — ДО `core.attach`/`on_write`: обрыв
соединения (`fault.drop`) во время висящей задержки отменяет корутину биндера
ДО того, как она успела что-то засчитать, иначе клиентский retry после
восстановления связи ложно удваивался бы в журнале заданий (репро ревьюера:
`delay_ms=1500` + запись + `fault.drop` через 0.3с + повтор -> было
`{'jobs': 2, 'dups': 1}` вместо `{'jobs': 1, 'dups': 0}`).

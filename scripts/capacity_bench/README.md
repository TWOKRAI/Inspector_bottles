# capacity_bench — переносимый бенч ёмкости

Одна команда на любой машине (Windows x86, Linux ARM) даёт отчёт «паспорт машины + самопроверка часов CPU +
матрица стенда по процессам». Контракт — `plans/transport-single-policy/task-4.8.md`, Task 4.8a. Выводы по
бюджету кадра и экстраполяция по частотам — 4.8b, здесь их нет.

## Запуск

Из корня репозитория (cwd = корень, `PYTHONPATH` = корень):

```
python -m scripts.capacity_bench [--profile quick|full] [--tests] [--baseline <sha>] [--port 8775] [--out reports/bench] [--dry-run]
```

| Флаг | Что делает |
|---|---|
| `--profile` | `quick` — 480p@25 и 1080p@100, по 30 с; `full` — 480/1080 × 25/60/100, по 30 с. Иное имя — rc 2 |
| `--tests` | перед замером pytest по `shared_resources_module/tests`, `process_module/tests`, `scripts/capacity_bench/tests`; итог в отчёте, падение замер не отменяет |
| `--baseline <sha>` | A/B: временный `git worktree add --detach`, по каждому кейсу сначала база (`baseline`), потом текущее дерево (`candidate`); worktree удаляется всегда |
| `--port` | порт `backend_ctl` стенда, по умолчанию **8775** (8765/8766/8092 заняты соседями) |
| `--out` | каталог отчёта, по умолчанию `reports/bench` |
| `--dry-run` | паспорт, самопроверка, отчёт; стенд не поднимается (секунды) |

## Отчёт

`<host>_<YYYY-MM-DD>.md` (для людей) и `.json` (`result` как есть). Занято — суффикс `_2`, `_3`…, старый
отчёт не перезаписывается. Печатаются оба пути. В отчёте:

- паспорт (`host, cpu_model, cores_*, freq_mhz, ram_gb, gpu, os, python, cv2, commit, commit_dirty`);
- самопроверка часов: busy-цикл на одном ядре в дочернем процессе, измеренный снаружи тем же `ProcessCpu`,
  что и стенд. Ждём 1.0 ± 0.05; иначе в отчёте строка «CPU-числа на этой машине ненадёжны»;
- если был `--tests` и rc != 0 — строка «сборка не прошла тесты»;
- по каждому кейсу таблица «процесс × поля»: ядра снаружи, ядра изнутри, Гц, `queue_wait_ms`,
  `transport_ms`, `pacer_late`, `plugin_ms`, `shm`.

Если замер упал посреди матрицы, отчёт всё равно пишется (с уже снятыми кейсами), rc = 1.

## Устройство

| Файл | Роль |
|---|---|
| `__main__.py` | CLI и оркестрация; каждый кейс — отдельный процесс `run_case.py` |
| `run_case.py` | поднимает `BackendHarness` **меряемого дерева** (cwd/`PYTHONPATH` = дерево), 10 с прогрева, N с замера |
| `cpu_probe.py` | CPU чужого процесса снаружи + самопроверка; stdlib + psutil, без `scripts.*` |
| `passport.py`, `matrix.py`, `recipe.py`, `fields.py`, `report.py` | паспорт, матрица, рендер рецепта, поля телеметрии, отчёт |
| `recipes/stand.yaml` | закреплённая копия `backend/topology/inspection_full.yaml`; бенч меняет только разрешение камеры и `source_target_fps` |

`cpu_probe.py` и `run_case.py` не импортируют `scripts.*`: их запускают против чужого дерева (baseline-worktree).

## Протокол стенда (обязательно)

Живой прогон поднимает всю систему и занимает порты/камеры/GPU, поэтому он идёт по протоколу общего стенда:
`.claude/memory/feedback_shared_stand_and_tests_protocol.md` (замок стенда держит человек/лид, а не инструмент;
в режиме measure соседних нагрузок быть не должно). `--dry-run` стенд не трогает и в протоколе не нуждается.

## Linux / ARM

- CPU процесса читается из `/proc/<pid>/stat` (utime+stime / `SC_CLK_TCK`), метод `proc_stat`; тики грубее
  тактов Windows — поэтому самопроверка идёт тем же методом и предупреждает, если он врёт.
- Имя процесса в `/proc/<pid>/stat` может содержать пробелы и скобки: поля считаются после последней `)`.
- `cpu_model` берётся из `/proc/cpuinfo` (`model name`); на многих ARM-сборках этого поля нет — тогда откат на
  `platform.processor()`, а он может быть пустым (в паспорте будет `null`).
- `gpu` — только через `nvidia-smi`; на Jetson его может не быть (`null`).
- Реальный прогон на Orin в v0 не проверялся.

## Известные ограничения

- Windows-venv: `sys.executable` — редиректор, настоящий интерпретатор — его потомок. `ProcessCpu` это
  учитывает для pid, полученного от `sys.executable` (иначе busy-цикл читался бы как 0.0 ядра).
- Частота для тактов Windows берётся из реестра (`~MHz`) и не калибруется; расхождение с реальной частотой под
  turbo ловит самопроверка, а не сам замер.

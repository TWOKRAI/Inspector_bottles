# Сквозная проверка цепочки рецепта `letter_robot_sim`

Один запуск проходит всю цепочку от старта сима до вердикта: сим, прототип, команды сима из конфига, сборщик
данных (`scripts.wire_audit.collect`), сценарий α (`scripts.alpha_sim.run_alpha`, только внешним процессом),
остановка, аудит провода (`scripts.wire_audit`), `verdict.md`. Судится механизм; ошибки нейросети идут отдельной
строкой «ТОЧНОСТЬ» и на вердикт не влияют.

Папка не пакет (нет `__init__.py`), менеджер рецептов `recipes/*.yaml` её не видит: `chain_check.yaml` лежит только
внутри вложенной папки, а `recipe.list` берёт файлы каталога рецептов без рекурсии.

## Запуск

```bash
python multiprocess_prototype/recipes/chain_checks/letter_robot_sim/run_chain_check.py \
    [--config chain_check.yaml] [--tree <корень>] [--runs N] [--gui] [--out-root <каталог>]
```

| флаг | смысл |
|---|---|
| `--config` | конфиг цепочки (умолчание `chain_check.yaml` рядом со скриптом) |
| `--tree` | корень дерева (умолчание `git rev-parse --show-toplevel` от папки скрипта) |
| `--runs N` | N прогонов подряд, каждый — полный холодный старт (умолчание 1) |
| `--gui` | прототип с окном: к `proto_cmd` не добавляется `--headless` (по умолчанию добавляется) |
| `--out-root` | каталог вывода (умолчание `<tree>/data/chain_check/<рецепт>`; `data/` в `.gitignore`) |

Живой прогон на общей машине — класс heavy; скрипт замков и окон не берёт, окно берёт тот, кто его запускает:

```bash
bash "$(git rev-parse --path-format=absolute --git-common-dir)/../scripts/machine_gate.sh" heavy <сессия> \
    python multiprocess_prototype/recipes/chain_checks/letter_robot_sim/run_chain_check.py
```

Скрипт пишет в сим только команды `sim_commands` из конфига (сейчас `scene.defect_rate {probability: 0.0}` в камеру);
они уходят до запуска сборщика и α. Скрипт сам запустил процессы — сам и убирает их (SIGTERM группе, через `stop`
секунд SIGKILL); чужие процессы, в том числе на портах `free_after`, не трогает.

## Конфиг `chain_check.yaml`

Все ключи обязательны, неизвестный ключ — код 2 (в тексте ошибки имена ключей, но не значения).
Подстановки в элементах списков и значениях окружения: `{tree} {out} {log_dir} {words} {zone_max_mm} {proto_port}
{sim_port}` (`{out}` — каталог прогона, `{log_dir}` = `<out>/logs_prototype`, `{words}` — слова через запятую).
`python` первым элементом команды заменяется на `sys.executable`. Рецепт указан только именем (`recipe`): путь к
файлу рецепта и корень репозитория в коде не зашиты.

## Порядок одного прогона

1. Порты `free_after` свободны (иначе код 3, печатается, кто занял).
2. Сим, затем прототип; вывод в `sim.out`, `proto.out`.
3. Ждать, пока порты сима и прототипа отвечают (`backends_up`); иначе код 3 и уборка.
4. Команды сима из `sim_commands`; ответ без успеха — код 3 и уборка.
5. Сборщик в фоне (`collect.out`), затем α (`alpha.out`, до `alpha` секунд).
6. После α файл `<out>/collect/STOP` останавливает сборщик.
7. Остановка сима и прототипа (если α не остановила их сама), проверка портов `free_after`.
8. Аудит (`audit.out`, `audit.md`), `verdict.md`.

Уборка выполняется и при любой ошибке шагов 2–6.

## Статусы этапов и будущий GUI

`<out>/stages.json` рядом с `verdict.md`: `{"recipe", "run", "mode": "headless|gui", "stages": [...]}`; этап —
`{"id", "title", "status": "pending|running|pass|fail|skipped", "started", "finished", "note"}`, время вида
`YYYY-MM-DD HH:MM:SS,mmm` или `null`. Файл создаётся на старте с этапами `pending`, обновляется атомарно (запись во
временный файл и `os.replace`); после упавшего шага остальные этапы `skipped`, уборка видна в `stop_processes`.

## Как читать `verdict.md`

`МЕХАНИЗМ: PASS`, если одновременно: в `alpha.out` есть `МЕХАНИЗМ: PASS` (и нет `МЕХАНИЗМ: FAIL`); аудит вернул 0;
порты `free_after` свободны после остановки; все запущенные процессы завершились; сборщик вышел после `STOP`. Иначе
`МЕХАНИЗМ: FAIL` и по строке `причина: <ключ>` на каждую провалившуюся проверку (ключи `alpha`, `audit`, `порты`,
`процессы`, `сборщик`). Падение или таймаут α — причина `alpha`, код 1. Код возврата самой α в вердикт не входит.

Ниже: `ТОЧНОСТЬ: …` из `alpha.out` дословно (информативно), `ИТОГ: …` аудита дословно, метка времени, режим
(`headless`/`gui`), пути файлов прогона, коды α, аудита и сборщика, `# дефекты сима: …` (что скрипт изменил в симе).

Аудит пишет рядом с `audit.md` файл `wire_commands.md` — построчный журнал всех команд роботу с расшифровкой; ссылка на него есть в `verdict.md` и в строке прогона `summary.md` (колонка «путь»).

При `--runs N` рядом с `run1…runN` лежит `summary.md`: таблица прогон, МЕХАНИЗМ, строка ТОЧНОСТЬ, путь.

`МЕХАНИЗМ: НЕ ПРОВЕРЕН (сценарий не дошёл: <причина одной строкой>)` вместо FAIL, когда проверять провод было нечего:
α вышла по предусловию (код 3, например «нет ни одной строки диска»), аудит отказал по входу (код 2, например «число слов
`--words` не равно числу строк слова … в журнале диска») или аудит прошёл, а в его строке `ИТОГ` `взятий 0` и `пропусков 0`
(в прогоне нет ни одной строки диска). FAIL — только когда сценарий дошёл, а проверка красная. Сбой уборки (порты,
процессы, сборщик) остаётся FAIL и тут же перекрывает «не проверен». Строки `причина:` перечисляют провалившиеся проверки
и в этом случае. `verdict.md` пишется, серия не прерывается.

Узкий случай «СТОП α»: при остановке из running робот получает две мягкие `STOP_REQ` (пауза системы + выключение;
диагностика `docs/reports/2026-11-22_sim-audit-stop-req-diagnosis.md`), а критерий α «ровно одна» устарел. Если в `alpha.out`
одновременно: строка `МЕХАНИЗМ: FAIL (СТОП stop)` без других пунктов, ровно одна строка `класс … : МЕХАНИЗМ`, строка
`СТОП stop: STOP_REQ [a, b], … → FAIL: STOP_REQ строк 2 ≠ 1` с `a % 4 == b % 4 == 1` (мягкий уровень), а в журнале обмена
`logs_prototype/devices/robot_exchange.log` (последняя инкарнация, после последнего `connect ok`) ровно эти две записи
`STOP_REQ` и после них `disconnect` — это не FAIL: `МЕХАНИЗМ: PASS~`, этап `alpha` — `pass`, в `verdict.md` и в заметке этапа
строка `СТОП α: информативно (2 мягких STOP_REQ: …)`, строка прогона в `summary.md` — `PASS~`, код возврата 0. Любое иное сочетание
(три записи, `n % 4 ≠ 1`, ещё один красный пункт α, нет `disconnect`, журнал не совпал с выводом α, таймаут α) остаётся FAIL.
Красный аудит или сбой уборки при этом по-прежнему дают FAIL.

Узкий случай «ОКНО α»: α красит пункт `<кейс> #n` за выход pick x/y за свои окна съёма (`ARGS[2]` 4549…4615, `ARGS[3]`
62096…62116), хотя слово равно журналу диска (шум центроида сети; окно зашито под сим). Образец строки — `B #4` в
`alpha.out` прогона 3 серии: `… → FAIL: pick (461.7, -343.1) вне окна x(…) y(…); ARGS[2] 4617 ≠ 4549…4615`. Если МЕХАНИЗМ α красен
ТОЛЬКО такими пунктами и/или узким случаем «СТОП» (скобки `МЕХАНИЗМ: FAIL (…)` и строки `класс … : МЕХАНИЗМ` совпадают), у каждого
пункта окна ВЕСЬ текст FAIL — сегмент `pick (…) вне окна …` и сегменты `ARGS[2|3] V ≠ lo…hi` без других причин, отклонение от границы
не больше 5 мм (`_WINDOW_MARGIN_MM`, как `--pick-margin-mm` аудита), а аудит вернул 0 — то `МЕХАНИЗМ: PASS~` и строка
`ОКНО α: информативно (N заданий вне окна съёма ≤ 5 мм: <пункты с отклонением>; шум центроида сети; окно зашито под сим)`. Любое иное
(другая причина в том же пункте, больше 5 мм, красный аудит, другие красные пункты, три записи STOP_REQ) — FAIL.

Коды возврата: 0 — PASS во всех прогонах; 1 — FAIL в каком-либо (сценарий дошёл, проверка красная); 2 — ошибка аргументов
или конфига; 3 — предусловие или запуск сорвался (при срыве запуска серия прерывается, `verdict.md` не пишется) либо
МЕХАНИЗМ НЕ ПРОВЕРЕН в каком-либо прогоне (серия идёт дальше); код 3 сильнее кода 1: если в серии есть и FAIL, и
«не проверен», вернётся 3, а какой прогон какой, видно в `summary.md`.

## Переезд в папку рецепта (ADR-RCP-006)

Когда рецепт станет папкой, эта папка переезжает одной командой `git mv` (в скрипте нет путей к файлу рецепта и к
корню репозитория: корень — `--tree`, умолчание — от места скрипта через git).

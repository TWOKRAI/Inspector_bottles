# Plugins/sim/scene_source — Решения

## ADR-SCN-001: Энкодер между батчами досчитывается по скорости последней дельты (C-87)

**Статус:** принято (2026-11-11). Отменяет прежнее решение модуля «протухшее значение — предупреждение, не экстраполяция» (докстринг `plugin.py`, раздел про протухание, до C-87).

**Контекст.** Диагноз — `plans/release-1.0/amendments.md`, запись 20. Мир (`sim.belt.encoder`) доходит до `scene_source` батчами раз в ~170 мс (публикация `robot_host` 50 мс + период диспетчера дельт 120 мс), а кадр рисуется каждые ~33 мс. Позиция объекта считалась из последней доставленной дельты, поэтому диск стоял ~3 кадра подряд и затем прыгал на 16.5-24.7 px. Окно §2.8 (6.6 px ± 1 на кадр) выдерживалось у 10 заданий из 41.

**Решение.** `SceneSourcePlugin._read_world_encoder()` возвращает
`value + mm_s * clamp(age_s, 0, stale_ms / 1000) / FACTOR_MM`, где `age_s = self._clock() - t`.

- Потолок возраста — `stale_ms` (по умолчанию 500 мс): после обрыва мира диск не уезжает бесконечно.
- Досчёт всегда идёт от ПОСЛЕДНЕЙ дельты. Никакого `max`/монотонного зажима между дельтами: новая дельта с меньшим `value` (реверс, перезапуск, поправка) переопределяет траекторию. Отрицательная скорость (`mm_s < 0`) досчитывается назад вместе с лентой.
- `now < t` (часы читателя чуть позади штампа) -> возраст 0, чтение равно `value`.
- Нет `t` или `mm_s`, либо они не конечные числа (NaN, inf, `None`, строка, bool) -> возвращается `value` без исключения и без досчёта.
- Снимок `value/mm_s/t` берётся один раз под `self._lock`; часы читаются один раз на вызов (`self._clock`, `time.monotonic`, шов для тестов, подменяется после `configure()`).
- Предупреждение о протухании (`age > stale_ms`) сохранено, де-дублировано по `t`; текст говорит, что досчёт ограничен `stale_ms`.
- Возвращаемое значение — float (дробные отсчёты): спавнер, фабрика, паспорт и компоновщик уже принимают float.

**Источник коэффициента.** `FACTOR_MM = 0.144473` мм на отсчёт, импорт из `Services.line_sim.core` (реэкспорт `Services.robot_comm.core.registers.FACTOR_MM`). Тот же коэффициент интегрирует энкодер в модели ленты (`Services/robot_comm/server/belt.py:150`: `remainder += mm_s * dt_s / FACTOR_MM`) и переводит отсчёты в мм в компоновщике (`Services/line_sim/core/belt.py:21`). Для режима «сырого» энкодера `from_enc_rate` (`belt.py:99-103`) `mm_s` задан тем же коэффициентом (`mm_s_at_max_freq = enc_rate * FACTOR_MM / tick_s`), поэтому формула согласована и там.

**Часы.** Штамп `t` пишет `robot_host` через `time.monotonic()`, читает `scene_source` в ДРУГОМ процессе. Это допустимо только на одной машине: macOS — `mach_absolute_time` (измерено ревьюером этапа 0: штамп дочернего процесса попал в окно родителя), Linux — `CLOCK_MONOTONIC`, общий для системы. Windows — `GetTickCount64` с шагом 15.625 мс: принято, здесь не исправляется (квант 15.625 мс при 20.2 мм/с — до ~0.32 мм ≈ 2.6 px ошибки возраста). Разные машины — не поддерживается (монотонные часы не сопоставимы между хостами).

**Причина отмены прежнего решения.** Прежнее решение (пассивное протухание) делало позицию функцией только последней дельты, чем и порождало «стоит-прыгает». Альтернативы (b) и (c) ниже отвергнуты, а досчёт по скорости — единственный вариант в пределах `scene_source`, не меняющий ни приёмку, ни фреймворк.

**Последствия.**
- `spawn_encoder` в паспортах и `sim.objects` становится дробным и зависит от настенных часов: два прогона с одним seed больше не дают побитово одинаковые паспорта (детерминизм остаётся по seed + последовательности ВЫЧИТАННЫХ значений).
- Остановка/старт ленты: до прихода следующего батча чтение продолжает прежнюю скорость, перелёт <= (publish 50 мс + dispatch 120 мс) * скорость ≈ 0.17 с * скорость; затем показание «защёлкивается» на новую дельту.
- Граница (2) задания (энкодер не уходит вперёд на остановленной ленте) выполняется только после дельты с `mm_s=0`.
- Остаточная ошибка при смене батча (A9): `robot_host` публикует `int`-энкодер (дробь < 1 отсчёта = 0.144 мм = 1.18 px при 8.163265 px/мм) и штампует `t` после чтения `core.encoder`, который меняется на 10-мс такте sim-core (`sim_core_v2.py:273`) — до ~1.4 отсчёта (~1.1 px) при 20.2 мм/с. На кадре сразу после новой дельты шаг может отличаться от 6.6 px до ~±2 px в худшем случае; критерий живого стенда «6.6 px ± 1 на каждом кадре» может это не покрыть. Не исправляется здесь (`robot_host` вне задачи).

**Отвергнуто.**
- (b) Расширить окно §2.8 — решение владельца (запись 19), приёмка не ослабляется.
- (c) Сократить период диспетчера дельт фреймворка — принятая цена задержки ~120 мс зафиксирована в `multiprocess_framework/modules/state_store_module/DECISIONS.md` (раздел «Принятая цена», стр. 727-731); менять поведение фреймворка ради симулятора нельзя.

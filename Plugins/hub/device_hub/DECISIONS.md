# Plugins/hub/device_hub — Решения

## ADR-PH-001: Крэш процесса devices = ручной рестарт

**Статус:** принято (2026-06-11)
**Контекст:** Процесс `devices` помечен `protected: true` в base.yaml. RestartPolicy фреймворка (`restart_policy.py`) по умолчанию disabled=False, но даже при включении — ProcessMonitor ЯВНО пропускает protected-процессы:

```python
# process_monitor.py:504-514
if process_name in protected:
    self.process._log_warning(f"Process '{process_name}' protected — авто-рестарт ({reason}) пропущен")
    return
```

Это by-design: terminate живого protected (GUI, devices) = крах ядра. Protected-процессы управляются launcher'ом.

**Решение:** НЕ включать restart_policy для devices. Крэш protected-процесса = ручной рестарт приложения. GUI-индикация «hub мёртв» — через `quality: bad` по всем устройствам (supervisor перестаёт tick'ать → ts стареет → quality деградирует).

**Альтернатива (отвергнута):** Сделать devices non-protected + включить restart. Отвергнуто: non-protected → replace_blueprint убивает devices при переключении рецепта → потеря соединений, что противоречит always-on семантике.

**Следующий шаг:** Если потребуется авто-рестарт protected — нужна доработка framework: отдельная ветка в ProcessMonitor для protected (re-spawn, а не terminate+recreate), либо supervisor на уровне SystemLauncher. Задача за пределами текущей фазы.

## ADR-PH-002: Корень данных — корень репозитория; прежнее место — предупреждение

**Статус:** принято (2026-11-15)
**Контекст:** `_PROJECT_ROOT` в `plugin.py` считался как `parents[4]` — каталог НАД репозиторием, тогда как остальные плагины `Plugins/<группа>/<имя>/plugin.py` берут `parents[3]`. Относительный `registry_path: data/devices.yaml` и каталог `data/robot` (T5.3c: `resolved.parent / "robot"`) попадали в `<над корнем>/data/`, общий для всех worktree в `.claude/worktrees/`.
**Решение:** `_PROJECT_ROOT = parents[3]` (`device_hub` -> `hub` -> `Plugins` -> корень), без поиска маркеров. Данные автоматически НЕ переносятся: при отсутствии реестра и `robot/` по новому пути и наличии любого из них по прежнему (`_PROJECT_ROOT.parent / registry_path`) `configure` пишет одно предупреждение (`ctx.log_warning`) с обоими путями; владелец переносит `devices.yaml` и `robot/` вручную. Проверка зовётся, когда путь пришёл из корня проекта (не `INSPECTOR_DATA_DIR`); для абсолютного пути она вхолостую: прежнее место совпадает с новым; `OSError` при проверке логируется и не роняет запуск. Однократность — следствие: после первого сохранения реестр существует.
**Альтернатива (отвергнута):** автоматическая копия со старого места — тихая запись в данные владельца и риск затереть чужой реестр; поиск маркеров корня (`.git`, `pyproject.toml`) — лишний слой при равной функции.
**Следствие:** без ручного переноса GUI покажет пустой реестр; предупреждение видно только в логе процесса.

## ADR-PH-003: `pause()` останавливает движение и ленту на месте, не паркует; очередь драйвера не чистится

**Статус:** принято (2026-11-16), Task 2.2a плана `2026-10-27_system-run-state`
**Контекст:** пауза (STOP из `running`) зовёт хук `DeviceHubPlugin.pause` из потока `run_watch`; повтор раз в 1 с при исключении. Выключение процесса (`request_stop` -> `request_stop_all_begin`) одноразово и защёлкивает срок процесса; «домой» (`robot_park`, ADR-DH-014) — отдельная долгая операция.
**Решение:** `pause` обходит ВСЕ устройства реестра видов `robot` и `vfd` с подключённым драйвером (не только рецепт: устройство из `device_sync_set` тоже останавливается) через публичный `DeviceManager.call`: робот v2 (`protocol == "delta_v2"`, признак — запись реестра) — `stop` `{"level": PAUSE_STOP_LEVEL}` (`"SOFT"`, константа модуля); робот v1 — `abort` `{"mode": 3}` (`STOP_IN_PLACE`); `vfd` — `stop` `{}`. `park` НЕ зовётся, `_shutting_down` НЕ ставится, `request_stop_all_begin` НЕ используется. Сбой устройства (исключение или ответ `status != "ok"`) не мешает остальным; после обхода — одно `RuntimeError("pause: сбой останова устройств")` (оркестратор запишет `failure` и повторит). `resume` — no-op: движение и лента сами не стартуют (лента — кнопкой пульта).
**Режим v1 = 3 (решение владельца 2026-11-16):** режим `abort` 1 (`STOP_HOME_CONTINUE`) — «домой, остаться в цикле» (`Services/robot_comm/core/registers.py:39-41`): противоречит цели паузы «на месте, не домой»; режим 3 (`STOP_IN_PLACE`) — «стоп на месте, выход, серво ON». Цена: v1 выходит из своего цикла, и нужен ли его перезапуск после `resume` — вопрос стенда. Смысл режимов взят из комментария «семантика из Lua» в `registers.py`, не из прошивки и не со стенда.
**Очередь драйвера не чистится:** уже поставленные задания (`_return_queue` / `_job_queue` драйвера v2) после `stop` оператора продолжают идти; новые не приходят, пока источник и потребитель в `PAUSED`. Удержание очереди требует правки драйвера v2 (файлы Р2, вне этой задачи) — вопрос владельцу. Защёлка `_latch_*` драйвера v2 движение не блокирует: после `stop` принимаются `jog_hold` / `enqueue_job` / `servo` (факт на `RobotSimCore`, `test_readiness_and_pause.py` RED 8).
**Цена:** обход последовательный — блокировка потока `run_watch` до n × срок команды драйвера (n — число подключённых `robot`/`vfd`); `shutdown` оркестратора ждёт замок сверки не дольше 2 с (`_SHUTDOWN_LOCK_SEC`). Параллельный обход — вне задачи. Уровень `SOFT` на CVT откладывается до точки захвата (`robot_driver_v2/jobs.py:97-99`); выбор `SOFT` / `HARD` / `HALT` — вопрос владельцу, поведение прошивки после `STOP_REQ=SOFT` по коду хоста не определить (только стенд).
**Готовность (тот же Task):** `readiness` читает снимок соединений `_conn_snapshot` (пишет `_publish_state` одной записью по ключу, до проверки state-plane) и `_desired_connected` без замков и ввода-вывода; набор — `_recipe_ids` (рецепт, порядок сохранён; `cmd_device_sync_set` перезаписывает кортеж целиком после записи желаний). Окно `cmd_device_sync_set` закрыто: до `upsert` под `_workers_lock` новым id ставится желание и они добавляются в `_recipe_ids` (порядок «желание -> кортеж»: читатель берёт кортеж, потом желание, id в кортеже без желания не бывает); в конце — финальный кортеж, у id с упавшим `upsert` прежнее желание возвращено. Дребезга нет по замыслу: любой обрыв связи в `running` — потеря готовности. Верхней границы возраста записи снимка нет (при исключении `drv.tick` `conn` не обновляется).
**Альтернатива (отвергнута):** `park` вместо `stop` — серво OFF и движение «домой» на паузе, долгая операция на потоке `run_watch`; `request_stop_all_begin` — одноразов, защёлкивает срок процесса и ставит `_shutdown` драйверу без снятия.

## ADR-PH-004: Один писатель факта соединения; возраст по успешному такту; `pause` через `pause_all`

**Статус:** принято (2026-11-17), Task 2.2a2 S4b плана `2026-10-27_system-run-state`; уточняет ADR-PH-003 (обход паузы), опирается на ADR-DH-015
**Контекст:** `readiness` читал снимок соединений, который писал разбор пути в `_publish_state` из нескольких мест, и возраста записи не знал: при исключении `drv.tick` `conn` не обновлялся, система оставалась `ready`/`running` с мёртвой связью (опыт B1: через 4,0 с `readiness == []`). Пауза знала виды и протоколы устройств (цепочка в плагине) и обходила их последовательно.
**Решение:**
1. Единственный писатель — `DeviceHubPlugin._set_conn(dev_id, conn, **extra)`: одна запись снимка по ключу, затем публикация `devices.state.<id>.conn`. Менеджер пишет через `conn_cb=self._set_conn`. Разбор пути из `_publish_state` удалён: чужая публикация на `….conn` снимок не меняет.
2. Возраст — по успешному такту: `_tick_ok_at[id]` (часы `_clock`) обновляет только tick-воркер после `drv.tick`, при старте цикла и ни один `_set_conn`. `readiness` при `connected` и заданном `params.conn_stale_s` > 0 отвечает `failure` «<id>: нет обновления связи», если с успешного такта прошло больше. По умолчанию порог выключен; `None`/`0` — выключен; негодное значение — выключен и одна WARNING на запуск воркера.
3. Исключение такта: связь оборвана (`not is_connected`) — `conn` публикуется сразу (без порога); связь жива — «ошибка связи» после `_TICK_FAILS_LIMIT` = 3 исключений подряд (`params.tick_fails_limit`, целое ≥ 1, по умолчанию 3; 1 — без порога; негодное значение — умолчание и одна WARNING), успешный такт счётчик сбрасывает; бросающее чтение `is_connected` в ветке исключения — `error`. Правило `conn` вынесено в `_conn_of`. Локальная `snapshot` прошлого такта в ветку исключения не попадает. В ветке исключения порядок такой: счётчик и факт связи (`_set_conn`), затем `health` и `last_error`, каждый в своём `try` (сбой отчёта не убивает поток воркера). Эту защиту держит внутренний `try` вокруг чтения `conn` в ветке исключения: подстановка `snapshot` дала бы `UnboundLocalError` на первом такте, он пойдёт в `error`, а не убьёт воркер.
4. `pause` — через `DeviceManager.pause_all` с общим сроком `_PAUSE_BUDGET_S` = 1,5 с (строго меньше замка сверки оркестратора 2,0 с); действие — `pause_action` драйвера, константы `PAUSE_STOP_LEVEL`, `_PROTOCOL_V2`, `_V1_ABORT_MODE` и цепочка «вид, протокол» удалены. Уже остановленные в эпизоде (`_pause_stopped`) повтору пропускаются; эпизод — повторы с промежутком ≤ `_PAUSE_EPISODE_S` = 3,0 с, закрывают его нормальный возврат и `resume` (упавший `pause` оставляет плагин `RUNNING`: сброс только в `resume` потерялся бы).
**Политика, не подтверждённая владельцем:** умолчание `tick_fails_limit = 3` (одиночное исключение такта при живой связи не снимает готовность, три подряд — снимают) выбрано без решения владельца; вопрос владельцу — потеря готовности сразу или после 3 подряд.
**Снятый воркер возраст не пишет:** такт, вернувшийся после снятия воркера (`stop_evt` взведён), `_tick_ok_at` не обновляет — иначе он воскресил бы запись, снятую `_stop_device_worker`, и новый воркер получил бы чужой возраст.
**Следствия и цена:** окно эпизода `_PAUSE_EPISODE_S` = 3,0 с: при упавшем `pause` и ЗАПУСТИТЬ→ОСТАНОВИТЬ быстрее 3 с повторная остановка робота не посылается (упавший `pause` оставляет плагин `RUNNING`, оркестратор зовёт `resume` только из `PAUSED`, множество `_pause_stopped` ЗАПУСТИТЬ не сбрасывает); вред зависит от защёлки стопа v2, не проверено; снять сигналом ЗАПУСТИТЬ в плагин (вариант через `run_active`, Task 2.7d). Охранный тест держит окно не меньше двух повторов хука оркестратора. Команда дольше 1,5 с — `RuntimeError` и один инцидент `device_hub.scope` (принято, ADR-DH-015). Висящий такт при выключенном пороге не ловится — порог в рецепте решает замер soak. `worker.pause_all` останавливает такты: при заданном пороге «нет обновления связи» на паузе ожидаемо. `ts` в записи `conn` остаётся счётчиком тактов (снять — после 2.8). Поздний успех команды после срока не помечает устройство остановленным: повтор пошлёт стоп ещё раз.
**Альтернатива (отвергнута):** отдельное поле `_conn_at` (метка записи `conn`) — любой писатель освежал бы возраст, и «зависший такт + чужая запись `connected`» скрывался бы; порог по умолчанию `10 × poll_interval_s` — ложный `failure` на каждой доставке v1 (такт до ~175 с).

## Состояния плагина

`ready` / `degraded` / `error` — **свои**, а не `PluginState` фреймворка (Р-13): у того пять
значений и ни `error`, ни `degraded` в нём нет. Читаются командой `otel_export.status`
вместе с полем `reason`.

* `error` — пустой/невалидный `endpoint` либо отсутствие extra `[otel]`. `configure()` при
  этом **не бросает** (Р-14): процесс обязан подняться, а причина обязана быть спрашиваемой.
  В этом состоянии `start()` не регистрирует хендлер и не объявляет намерение.
* `degraded` — брокер не подтвердил намерение за три попытки. Инцидент в плоскости ошибок
  ровно один (`health.report_error`, он же голос ERROR — один разъём на ветку, ADR-PM-030).

## Что стоит знать перед следующей задачей

**Останов НЕ дожимает кольцо — вердикт CTO, а не упущение.** Первая редакция Task 2.2
отправляла накопленное в `shutdown()`. Замер CTO на стенде с мёртвым коллектором:

```
flush#1 24.36 с (failed=20) · flush#2 0.01 с (пусто) · flush#3 22.85 с (failed=4)
launcher.shutdown() 5.17 с
  -> spawner: ProcessManager did not stop in 5.0s, terminating...
  -> строк «otel_export: остановлен» в журнале: 0
  -> последняя строка SDK: "retrying in 1.15s", финального отказа нет
КОНТРОЛЬ (коллектор жив): shutdown() 5.12 с, строка «остановлен» есть (1), запись доехала
```

Бюджет останова у фреймворка — **5 с** (`process_registry.stop_all(timeout=5.0)`,
`spawner.stop_timeout=5.0`), синхронная отправка живёт 23-42 с: процесс убивают внутри
retry-цикла SDK, финальный снимок счётчиков не пишется, последняя пачка выпадает из
тождества потерь. Сегодня останов только СЧИТАЕТ оставшееся потерей и произносит число
(WARNING при потере, INFO при нуле); цена решения названа прямо: одна запись, доезжавшая
при живом коллекторе, доезжать перестала — её вернёт Ф2.4 ограниченным дожатием.

**Долг Task 2.2: `otel_export.flush` держит ПРИЁМНЫЙ ПОТОК процесса.** Команда приезжает
конвертом `type=="command"` и исполняется внутри `RouterManager.receive()`
(`router_module/core/router_manager.py:1343` -> `_dispatch_command`) — другого боевого
вызывающего у команды нет, и запретить эту дорогу изнутри плагина нечем. Отправка синхронна
и держит поток **23-42 с** при недоступном коллекторе (замеры CTO: refused localhost —
23.44 с; чёрная дыра `10.255.255.1:4318` — 42.08 с; отвечающий 401 сервер — 0.02 с).

* **Смягчения конфигурацией НЕТ.** `export_timeout_ms` этой границей не управляет: у SDK
  это дедлайн расписания ретраев, а не потолок вызова — при 3000 мс вызов длился 4.08 с,
  то есть +36% сверх «потолка». Прежняя редакция этого файла обещала обратное; обещание
  снято как ложное.
* **Усиление потери — возможность с порогом, а не состояние.** Вытеснение из очереди
  `observability` начинается при темпе больше ~10 сообщений/с. Замер при 0.17 зап/с:
  `queue_observability_evicted` у `otel_export`, `camera_0`, `ProcessManager` до и после
  24-секундной блокировки — **0, 0, 0**.
* **Адрес закрытия — Ф2.4:** асинхронная пачка (`BatchLogRecordProcessor`, выгрузка по
  `schedule_delay_ms`) уводит отправку с приёмного потока целиком.

**Условие приёмки Ф2.4, поставленное CTO:** «останов с МЁРТВЫМ коллектором укладывается в
5 с, строка `otel_export: остановлен` присутствует». Меряется **чёрной дырой**
(`10.255.255.1:4318`), а не refused localhost: refused отдаёт отказ быстро и спрячет
настоящую границу — держит connect именно чёрная дыра.

**Долг Task 2.2: битая запись роняет весь батч.** Контракт маппера слабее Pre экспортёра по
`severity_number` (замер: 1 битая из 5 -> `failed=5`, при `max_queue_size = 2048` цена одной
записи — до 2048). Живой дороги сегодня нет; решение и отвергнутые варианты —
[`Services/otel_export/DECISIONS.md`](../../../Services/otel_export/DECISIONS.md),
ADR-OTEL-006. Закрытие — Ф2.4 / Ф3.4.

**Долг двери конфига, найденный прогоном в Task 2.1.** `_init_register` применяет overrides
фрагмента **поле за полем** через `setattr` с `validate_assignment=True`, а порядок берёт из
`model_fields`, где `max_queue_size` идёт РАНЬШЕ `max_export_batch_size`. Фрагмент топологии
с `max_queue_size: 2` **бросает `ValidationError` прямо в `_init_register`**, на промежуточном
состоянии модели («батч 512 больше очереди 2») — **в любом порядке ключей во фрагменте**.

Формулировка уточнена по ревью (Н-5): прежняя редакция говорила «не применится вовсе», что
читается как тихий no-op и прячет настоящий механизм. С правкой Н-1 этот бросок больше не
убивает `configure()` — плагин уходит в `error` с названным ключом, — но применить такой
фрагмент по-прежнему нельзя. Задеть это способна Ф3.1; долг чужой
(`plugin_orchestrator` / `_init_register`), здесь не чинился.

**Подключать фрагмент топологии до Ф3.1 незачем:** принимать записи, которые никуда не
поедут, значит платить процессом за одни счётчики.

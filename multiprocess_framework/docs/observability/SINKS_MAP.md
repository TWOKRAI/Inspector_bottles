# Карта приёмников — куда физически попадает запись

> Сверено с кодом **2026-08-10**, коммит **`fb705053`** (ветка `feat/observability-review-remediation`, фазы A–D закрыты).
> Читатель: автор модуля, оператор стенда.
> Соседние справочники: [`CONNECTORS.md`](CONNECTORS.md) · [`NEW_MODULE_RECIPE.md`](NEW_MODULE_RECIPE.md) · [`CONTROL_PANEL.md`](CONTROL_PANEL.md)

Запись, вышедшая из разъёма, попадает **в приёмники двух разных пород** — config-owned каналы и
runtime-owned tap'ы, — а осесть может в **трёх хранилищах** с тремя разными сроками. Плюс пол
ошибок, который не подчиняется ни конфигу, ни ретеншену. Документ описывает все четыре сущности
и границы между ними.

---

## 1. Шесть типов приёмников и как добавить седьмой

Реестр фабрик — `_SINK_FACTORIES` в
[`logger_module/channels/log_channel.py:1450`](../../modules/logger_module/channels/log_channel.py#L1450).

| `type` | Класс | Что делает | Границы |
|---|---|---|---|
| `file` | `FileChannel` | ротируемый файл; общий `RotatingFileHandler` на путь | дефолты каналов: 10 МиБ × 5 бэкапов |
| `console` | `ConsoleChannel` | stdout/stderr | лесенка перегрузки: `write_deadline_sec=0.25`, размыкание после `degrade_after=3` подряд просроченных, `slow_write_sec=0.05`; жалоба не чаще 1/60 с |
| `http` | `HttpChannel` | POST JSON на `url`, таймаут 5 с | требует `requests`; при отсутствии — `ImportError` на конструкторе |
| `frame_trace` | `FrameTraceChannel` | снимок ОДНОГО кадра: буфер по `extra.seq_id`, перезапись файла на смене кадра | запись без `seq_id` игнорируется (`status=skipped`) |
| `memory` | `MemoryChannel` | кольцо в памяти процесса, `DEFAULT_CAPACITY = 500` записей | ёмкость считает ЗАПИСИ, не байты; вытеснение — контракт, не потеря |
| `null` | `NullChannel` | принято и выброшено | это **доставка** (`written += 1`), а не потеря |

**Седьмой тип добавляется без правки фреймворка:**

```python
from multiprocess_framework.modules.logger_module.channels.log_channel import register_sink_factory

register_sink_factory("sql", MySqlChannel)      # класс-наследник LogChannel либо любой с write()
```

`register_sink_factory` отвергает мусор на границе (`TypeError`: пустой/не-str `sink_type`, не
класс, класс без `write`), повторная регистрация того же имени переопределяет предыдущую
(последняя побеждает). Список зарегистрированных — `get_registered_sink_types()`. Неизвестный
`type` в конфиге даёт `ValueError: Unknown channel type` в `create_channel` — молча не проглотится.

**Почему кольцо `memory` — не то же самое, что три соседних механизма** (докстринг `MemoryChannel`
называет их поимённо, потому что путать дорого):

* `ObservabilityHub` / `BoundedChannel` — кольцо **транзитное**, владелец дренирует его по
  heartbeat, к моменту запроса оно обычно пусто, и стоит оно ВЫШЕ логгера;
* `log.tail.subscribe` — **подписка** (push): кто не подписался заранее, прошлое не увидит;
* `ObservabilityStore` — SQLite на **диске**.

Кольцо `memory` — единственное место, где последние N записей лежат в памяти процесса и достаются
**ретроспективно**, без подписки и без диска (`observability.sink.tail`). Оно **переживает
пересоздание канала**: живёт в процессном реестре `_memory_rings`, а не в объекте канала — иначе
улики исчезали бы ровно в том сценарии, ради которого кольцо и заводилось (оператор разбирает
инцидент и трогает наблюдаемость).

## 2. Маршруты: из чего следует, в какой файл поедет запись

### Плоскость логов — по скоупу

Дефолты — [`logger_manager_config.py`](../../modules/logger_module/configs/logger_manager_config.py):

| Скоуп | Приёмники | Файл |
|---|---|---|
| `SYSTEM` | `console`, `system_file` | `system.log` |
| `BUSINESS` | `messages_file` | `messages.log` |
| `PERFORMANCE` | `performance_file` | `performance.log` |
| `DEBUG` | `system_file` | `system.log` |

**Task 3.2 (Р-7(а)):** `BUSINESS` лишился `system_file`. Замер на живом стенде (8 процессов, бут)
показал, что `messages.log` был строгим подмножеством `system.log` — 368 строк, 0 уникальных, —
потому что оба скоупа делили канал `system_file`; после фикса файлы больше не дублируют друг друга.

**Инвариант после Р-7(а), одинаковый в КАЖДОМ каталоге, включая `launcher/`:**
`messages.log` = INFO; `system.log` = WARNING+ (через скоуп `SYSTEM`) и DEBUG-скоуп.
Он держится не на конфиге отдельного процесса, а на паре «`_LEVEL_DEFAULT_SCOPE`
(`INFO → BUSINESS`, `WARNING/ERROR/CRITICAL → SYSTEM`, `DEBUG → DEBUG`) + наборы каналов
скоупов». Компонент, который не передаёт `scope=` явно, подчиняется ей автоматически —
в том числе `SystemLauncher`, поднимающий логгер на голых дефолтах схемы.

**Следствие, неочевидное при чтении таблицы:** скоуп `DEBUG` пишет в `system_file`. Значит
при опущенном корневом `default_level` в `system.log` появится DEBUG-поток **без INFO между
ним** — INFO к тому моменту уже уехал в `messages.log`. Это не дефект раскладки, но читать
`system.log` на уровне DEBUG как «полный журнал» больше нельзя: полного журнала в одном
файле теперь нет ни на одном уровне.

`console` **не подключён к `BUSINESS`** намеренно: пер-кадровые INFO воркеров уходят только в
файлы. `PERFORMANCE` вынесен в свой файл в Ф2.6 — у скоупа один писатель (снапшот метрик), и он же
самый тяжёлый источник: замер 2026-08-03 дал **5.27 МБ из 9.38 МБ** `system.log` у ProcessManager
(56%), 2.33 из 8.88 у gui, 2.08 из 8.63 у region_splitter; одна строка снапшота весит ~7 КБ.
**Суммарная запись на диск при этом не уменьшилась ни на байт** — те же МБ в другом файле.

**Порог — одна ось (ADR-LOG-010).** У скоупа осталось единственное поле `channels`: собственного
`enabled`/`min_level` у него больше нет, решение об уровне принимает правило по имени источника
(`loggers`, самое длинное совпадение префикса) либо корневой `default_level`.

### Плоскость ошибок — по severity, лестницей предпочтения

`DEFAULT_SEVERITY_ROUTES` в
[`error_manager_config.py:29`](../../modules/error_module/configs/error_manager_config.py#L29):

| Уровень | Приёмники в порядке предпочтения |
|---|---|
| `CRITICAL` | `critical_file` → `errors_file` |
| `ERROR` | `errors_file` → `critical_file` |
| `WARNING` | `warnings_file` → `errors_file` → `critical_file` |

Действует **первый, который есть в реестре каналов**. Правило записано порядком, а не
комментарием: ERROR уходит в `critical.log`, а не в `warnings.log`, потому что спрятать ошибку в
файле предупреждений значит потерять её на практике, формально ничего не потеряв.

Формулировать это как «запасной всегда к БОЛЕЕ важному файлу, никогда к менее важному» **нельзя**:
у `CRITICAL` запасным стоит `errors_file`, то есть ступенька вниз по этой же таблице (выше уже
некуда — `critical_file` и есть верх). Точная формулировка: **запасной идёт к соседней ступени, и
предпочтение отдаётся более важной, если она существует**. У WARNING лестница трёхступенчатая
(`warnings_file` → `errors_file` → `critical_file`) — вся вверх. Это данные, а не ветвление в коде (ADR-EM-008):
новый уровень со своим файлом заводится конфигом, правок во фреймворке — ноль.

### Плоскость статистики — через логгер

`StatsManager` пишет снапшот агрегационного окна в канал `log_stats`
([`LogStatsChannel`](../../modules/statistics_module/channels/log_stats_channel.py), `STATS_LOG_CHANNEL`),
а тот зовёт `logger_manager.performance(...)` — то есть метрики физически ложатся туда, куда ведёт
скоуп `PERFORMANCE`. Отсюда следует порядок останова: **stats гасится раньше логгера**, иначе
финальный снапшот уедет в закрытый приёмник (см. [`CONNECTORS.md §6`](CONNECTORS.md)).

## 3. Tap'ы: вторая порода приёмников

`add_tap` / `remove_tap` живут в базе всех менеджеров
([`channel_routing_manager.py:791`](../../modules/channel_routing_module/core/channel_routing_manager.py#L791)).

| Свойство | Канал реестра | Tap |
|---|---|---|
| Откуда берётся | конфиг | подписчик в рантайме |
| Участвует в маршрутизации | да | **нет** — получает КАЖДУЮ запись выше порога |
| Переживает `reconfigure()` | нет (реестр пересобирается) | **да** — подписка на хвост не рвётся при hot-reload |
| Хранится | `_channel_registry` | `_tap_sinks`: `{имя: (IChannel, min_rank)}` |

**Порог `min_level` по умолчанию `"ERROR"`**, и у него две названные особенности:

* плоскость без уровней (статистика) порог не отсекает: запись без уровня считается самой низкой
  по важности и проходит при `"DEBUG"`;
* **непонятое имя порога — fail-open**, «пропускать всё». Позиция порога и позиция записи имеют
  РАЗНЫЕ дефолты непонятого имени (Ф3.1): тишина от опечатки была бы невидимой потерей. До Ф3.1
  обе позиции обслуживала одна функция, и держалось это на совпадении «0 = DEBUG», исчезнувшем с
  `DEBUG = 5`.

**Кто вешает tap'ы:**

| Tap | Куда | На каких менеджерах | Зачем |
|---|---|---|---|
| `StoreTapChannel` | `ObservabilityStore` (SQLite) | **на оба** — `error_manager` и `logger_manager` | приложение логирует ошибки и туда, и туда; write-through исключает переигровку → дубля нет |
| forward-tap живого хвоста | подписчик (GUI, `backend_ctl`) | процесс | имена **keyed по subscriber** (`forward_tap_names`): раньше был единственный слот, и второй подписчик угонял хвост у первого |
| `log.tail` | подписчик | `logger_manager` | хвост sub-ERROR логов с уровнем подписчика |

**Реентрантность защищена структурно (D1, 2026-08-10).** Tap, который сам эмитит из `write()`,
давал лавину: воспроизведено **498 записей, глубина 498**, наружу — ничего (`RecursionError`
съедал `except Exception`). После правки — **1 запись, глубина 1, счётчик подавленных 1**. Защита
**поточная**, а не общая на менеджер: реентрантность — свойство стека вызова, общий флаг глушил бы
законную раздачу в соседнем потоке. Цена (бенч, 5 серий × 200 000 вызовов, медиана): база эмиссии
0.36–0.41 мкс, с защитой 0.52 мкс, дельта **+0.12…+0.16 мкс**; при живом темпе ~44 записи/с это
~7 мкс/с.

## 4. Пол ошибок — конфиго-независимый, но только фактом записи

[`logger_module/core/error_floor.py`](../../modules/logger_module/core/error_floor.py).

Инвариант: **error/critical пишутся синхронно, в одно место, без дублей, и этот путь не зависит
от конфигурации приёмников.**

* **синхронно** — запись идёт напрямую в канал, минуя буфер;
* **без дублей** — floor пишет ТОЛЬКО когда обычный маршрут записал ноль каналов (вариант B;
  вариант «аварийный файл поверх обычного маршрута» отвергнут — он давал вторую копию каждой ошибки);
* **конфиго-независимо — но только ФАКТ записи, не её местоположение**, и путать эти два
  утверждения нельзя (находка ревью Ф0.9). Приёмник не описан в `config.channels`, поэтому ни
  `enabled: false`, ни `sink.disable` его не гасят. А вот КАТАЛОГ резолвится в том числе по
  каналам конфига (`LoggerCore._resolve_floor_path`): floor должен лежать там же, где обычные логи;
* **полная запись** — JSON Lines со ВСЕМИ полями, включая `extra` и многострочный traceback;
  усечение запрещено: «упало» без «где и с чем» не отлаживается;
* **файл открывается лениво** — у здорового процесса `errors_floor.jsonl` не появляется вовсе, и
  непустой floor означает, что штатный маршрут ошибок сломан;
* **ретеншен его НЕ подметает** (`PROTECTED_BASENAMES`), но и расти без предела ему не дают: пол
  ротирует себя сам, потолок `_MAX_BYTES = 32 МиБ`, один бэкап. Довод: при долгоживущем
  `sink.disable` КАЖДАЯ ошибка идёт сюда, и файл, который никто не ротирует, повторил бы историю
  `messages.log` (645 МБ незамеченными);
* `fsync` не зовётся: он стоит миллисекунды, SIGKILL не забирает данные, уже отданные ядру, а от
  потери питания floor не защищает и не обязан.

Один пол на процесс, реестр по абсолютному пути (`_floors`): два менеджера одного процесса
(`LoggerManager` и `ErrorManager`) обязаны писать через ОДИН дескриптор — иначе на Windows два
хендла на путь дают `WinError 32`.

## 5. Три хранилища и три срока

| | Файлы логов | `ObservabilityStore` | `DocumentStore` |
|---|---|---|---|
| Что хранит | диагностику (все плоскости) | историю записей для GUI/пульта | **решения**: вердикты, аудит смен наблюдаемости |
| Носитель | `log_dir/<процесс>/*.log` | SQLite, один файл на процесс | SQLite ([`Services/documents/store.py`](../../../Services/documents/store.py)) |
| Предел объёма | ротация 10 МиБ × 5 бэкапов на канал | `history.max_rows` (дефолт **200 000**) | нет предела строк |
| Срок | `retention_days` / `retention_total_mb` — **оба 0, то есть выключены по умолчанию** | `history.max_age_sec` (дефолт **7 суток**) | `retention_sec[kind]` — **per-род** |
| Уборка | `enforce_log_retention` при старте/reconfigure + фоновый свип `retention_sweep_interval_sec` (дефолт 3600 с) | `purge` по такту heartbeat, не чаще `history.purge_interval_sec` (дефолт **300 с**) | `purge_expired` по такту, `DEFAULT_PURGE_INTERVAL_SEC = 3600 с` |
| Порог допуска | скоуп + уровень | `history.level` (дефолт **INFO**) | **не severity, а род документа** (ADR-CRM-013) |

Политика истории читается теми же слоями, что и всё остальное (`observability.history`), и мусор
в значении **не молчит**: ключ падает на дефолт с голосом. `max_rows: 0` проходит как есть, но
громко — «предел СНЯТ, история растёт без ограничения»: молчаливая безлимитность и была исходным
состоянием, которое чинили.

**Документ живёт годами, диагностика — днями**, поэтому попадание в `DocumentStore` не зависит от
severity: правило допуска структурное — свой приёмник, а не фильтр по уровню, который надо не
забыть настроить. Род, которого нет в `retention_sec`, **не удаляется никогда**. Цена записи — на
вызывающем: `append` идёт синхронно в SQLite, замер под конкуренцией шести процессов — медиана
3.6 мс, p95 82 мс, **max 928 мс**; это бюджет РЕДКОГО события, документ на каждый кадр остановил
бы линию.

**`auto_vacuum` в сторе — с миграцией (D3, ADR-CRM-014).** Порядок прагм значим и проверен
замером: WAL первым → `PRAGMA auto_vacuum` = 0 (режим молча не применился), `auto_vacuum` первым →
2 (INCREMENTAL). Унаследованные базы мигрируются один раз по `PRAGMA user_version`: `VACUUM` при
открытии, если режим 0. Числа приёмки: копия живой БД `auto_vacuum` **0 → 2**; синтетическая база
200 000 строк / **118.3 МиБ** после миграции и `purge(max_rows=1000)` — **0.625 МиБ**, то есть
режутся байты, а не только строки; цена `VACUUM` на ней — **1.06 с**.

## 6. Слепые зоны ретеншена — что подметается, а что только называется

Закрыто задачей D5 (2026-08-10), живая приёмка 6/6.

**Было:** `enforce_log_retention()` метёт ровно ОДИН каталог, а источник этого каталога —
`LoggerCore._retention_root()` → `log_dir/<имя своего процесса>/`. Подметальщик заводится только у
процессов с поднятым `LoggerCore`, то есть у **живых**; каталог процесса неактивного рецепта не
совпадает ни с одним живым и не попадал никуда. Листингом подтверждалось: файлы 12 дней при
`retention_days=7`.

**Стало:**

| Функция | Что делает | Границы |
|---|---|---|
| [`sweep_log_dir_tree`](../../modules/logger_module/channels/log_channel.py#L735) | все непосредственные подкаталоги `log_dir`, **кроме** каталогов живых процессов | symlink'и не разыменовываются; сам `log_dir` и файлы верхнего уровня не трогаются |
| [`find_foreign_log_roots`](../../modules/logger_module/channels/log_channel.py#L820) | чужие деревья ВНЕ `log_dir` — **только называет**: путь, число файлов, вес | не удаляет ничего (решение владельца Р-5: legacy убирает владелец руками) |

Оба зовёт ПМ один раз на `initialize()` до спавна детей; сбой уборки не роняет boot.

**Названное ограничение механизма, не закрытое:** фреймворк знает единственного кандидата чужого
дерева — `<cwd>/logs`. Второй известный пример (`multiprocess_prototype/logs/camera_0/`) он
структурно назвать не может: импорт прототипа из фреймворка запрещён правилом слоёв. Хук
`_foreign_log_root_candidates()`
([`process_manager_process.py:365`](../../modules/process_manager_module/process/process_manager_process.py#L365))
переопределяемый — закрыть этот пример обязан композиционный корень прототипа, отдельной строкой.

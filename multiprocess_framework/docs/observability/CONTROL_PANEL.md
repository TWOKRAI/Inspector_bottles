## 1. Четыре слоя конфигурации

[`process_module/configs/observability_layers.py`](../../modules/process_module/configs/observability_layers.py).
Каждый следующий побеждает предыдущий (`LAYER_ORDER`).

| Слой | Константа | Источник | Смысл |
|---|---|---|---|
| **L0** | — | код, `ObservabilityConfig` | «как правильно вообще» |
| **L1** | `LAYER_FRAMEWORK` / `LAYER_APP` | `system.yaml`, секция `observability:` | «что верно на ЭТОЙ машине при любом рецепте» |
| **L2** | `LAYER_RECIPE` | рецепт + спутник рядом с ним | «что верно для ЭТОГО конвейера» |
| **L3** | `LAYER_SESSION` | память процесса | «что кручу руками прямо сейчас» |

**Семантика применения — ПЕРЕСБОРКА ИЗ ИСТОЧНИКОВ, а не дельта поверх живого.** Это разворот,
сделанный в Task 5.12, и причина структурная: дельта **принципиально не умеет** выразить «ключ
удалён из слоя → вернись к нижнему». Пока конфигом владел один источник, это было незаметно; с
четырьмя слоями «вернуть как было» стало основной операцией.

Порядок сборки (`apply_observability_layers` —
[`observability_reload.py:595`](../../modules/process_module/managers/observability_reload.py#L595),
**единственное** место, где секция раскладывается и применяется; и файловый watcher, и IPC-команда
зовут именно её):

```
base   = managers_from_log_dir(машинный каталог логов)   # L0 + контекст машины
target = merge(base, expand(layers.resolve()))            # L1 → L2 → L3
профиль уровня, если log_level задан хоть одним слоем
точечные scopes-переопределения слоёв — последними
```

`log_directory` приходит из **машинного контекста** и переопределяется только явным ключом слоя —
иначе частичный reload уводил бы файлы логов в чужой каталог (живая находка 2026-07-22).

Каталог резолвится одинаково на boot и на пересборке: явный аргумент → `MULTIPROCESS_LOG_DIR` →
`INSPECTOR_LOG_DIR` → `logs`. Каноничное имя читается **первым** — асимметричных читателей env
выправили в D4.

### 1.1. Откуда конфиг берётся при СОЗДАНИИ менеджеров (Task 2.3, находка Н-7)

Секция `managers` приезжает готовой только тем процессам, которых собирал ассемблер. **Оркестратор
спавнится другим кодом**, и этого ключа в его bundle нет вовсе — его менеджеры рождались на
дефолтах L0, и первым, что делал `StatsManager` оркестратора на каждом старте, было предупреждение
о собственном конфиге (`stats.aggregation_interval=5.0 ниже пола 10.0`) при `system.yaml`, где
стоит `10.0`. Дети того же стенда молчали: им конфиг доезжал.

Правду про систему это предупреждение не говорило — значения доносила пересборка на boot секундой
позже. Но разница была не только в шуме: на расходящейся паре (`aggregation_interval: 10.0` +
`flush_interval: 2.0`) действующий **пол** темпа у оркестратора был 10.0 вместо 2.0, то есть
впятеро. Совпадение прятал `max(flush, agg)`: `max(5,10) == max(10,10)`, и та самая ручка, о
которой предупреждение, выглядела правильной.

Теперь `ProcessManagers._managers_config_for_creation` собирает секцию **из слоёв**, если ассемблер
её не собрал. Признак структурный — «секция пуста», а не «имя равно `ProcessManager`»: тот же
довод, что у пересборки на boot. Молчащие слои ничего не подставляют (`expand_observability({})` —
это полный набор дефолтов L0, а не пустота). Пересборка на boot осталась и закрывает вторую
ветку — спутник рецепта, которого на момент создания ещё не читали.

## 2. Команды

Контракты — `BUILTIN_COMMAND_CONTRACTS` в
[`command_contracts.py:284`](../../modules/process_module/commands/command_contracts.py#L284).
У всех схем `extra="forbid"`, поэтому **необъявленный параметр помечается warn-мидлварью, а при
`FW_CONTRACTS_STRICT=1` дропается целиком** — ручка, не объявленная в схеме, мертва при зелёных
тестах. Расхождение «схема ⊇ ключи хендлера» с A1 судится оракулом
`test_command_contract_oracle.py` по всем 36 командам реестра.

| Команда процесса | Параметры | Что делает |
|---|---|---|
| `config.reload` | `observability`, `telemetry`, `telemetry_mode`, `observability_reset`, `observability_session_clear`, `observability_recipe`, `observability_recipe_path`, `observability_recipe_reload`, `ttl`, `path`, `persist` | inline-секция → **L3**; файловый reload → заменяет **L1**, оставляя L2/L3 |
| `observability.persist` | `recipe_path` | переезд ключей **L3 → L2** (спутник рецепта): единственный путь сделать правку постоянной |
| `observability.sink.enable` / `.disable` (алиасы `logger.sink.*`) | `sink`\|`name`, `manager` (`logger`\|`error`\|`stats`), `ttl` | снять/вернуть приёмник по имени. Роутер **не адресуем**: транспорт — не плоскость наблюдаемости. Имена приёмников плоскости stats: `log_stats` (строка снапшота в `performance.log`), `file_stats` (файл и fallback), `hub_stats` (снапшот окна в стор и живой хвост, задача 2.1 — поднимается только у процесса с hub'ом) |
| `observability.sink.tail` (алиас `logger.sink.tail`) | имя приёмника, `limit` | хвост приёмника, хранящего записи у себя (`type=memory`) |
| `observability.tail.subscribe` | `subscriber`, `level`, `scope` | живой хвост записей подписчику; `level=None` = «уровень не назван», дефолт применяет процесс. `scope="all"` кладёт **брокер**, разворачивая оптовую подписку в адресные команды (5.6 / ADR-PM-032); отсутствие ключа = прицельная подписка, и по нему процесс знает, что прицельно заданный порог понижать нельзя (блокер Н2-1) |
| `observability.tail.unsubscribe` | `subscriber`, `scope` | снять форвардер этого подписчика; `subscriber=None` (legacy/teardown) — снять форвардеры всех. `scope` — зеркало подписки: `"all"` ставит брокер на ОПТОВОМ снятии, и без маркера `unwatch()` сносил бы прицельный хвост соседа (Н2-2). `level` в схеме **нет**, а `extra="forbid"` делает его передачу адресным отказом, не молчаливым игнором |
| `observability.tail.subscribe_all` / `.unsubscribe_all` | `subscriber`, `level` | то же через брокер оркестратора: подписка на все процессы, включая переподписку свежей инкарнации. Схема у пары **одна** (`ObservabilityTailBrokerParams`), поэтому `level` у `unsubscribe_all` принимается и игнорируется — сознательный выбор против двух реестров имён одной плоскости |
| `introspect.observability` | `audit_limit` (дефолт 20, `0` — не возвращать), `resolve`, `flush` | чтение без мутации: `effective`, `counters`, `provenance`, `ttl`, `documents`, аудит |
| `health.report` | `context`, `message`, `status`, `level` | диагностический впрыск health-события |

Через `backend_ctl` те же ручки доступны как `config_reload`, `config_reload_verified`,
`logger_sink_enable` / `logger_sink_disable`, `log_tail` / `log_untail`, `observability_tail` /
`observability_untail`, `introspect_telemetry`, `system_overview`, `events_page`, `watch_like_gui`.

**Каноничное имя и алиас судятся ОДНИМ контрактом** (Task 5.10.e): разные схемы у двух имён одной
команды означали бы, что через алиас проходит то, что канон отвергает.

**Батч-адрес.** `process` принимает `"all"`/`"*"`, узор (`camera_*`) или список имён — тогда ответ
приходит в форме `send_command_many` (`batch: True`, секция на процесс). Одно точное имя идёт
прежним путём: форму ответа выбирает жест оператора, а не догадка.

## 3. Срок жизни правки (TTL) и авто-возврат

[`observability_ttl.py`](../../modules/process_module/managers/observability_ttl.py) + `session_ttl_sec`.

| Факт | Значение |
|---|---|
| Дефолт срока | **300 с** (`ObservabilityConfig.session_ttl_sec`) |
| Потолок | `86400.0` (`MAX_SESSION_TTL_SEC`) — дольше живущая «временная» правка это уже решение уровня рецепта |
| `0` | сроков нет — **осознанный отказ от защиты** |
| Кто исполняет | такт heartbeat процесса (`sweep_session_ttl`), а не свой таймер |
| Точность | возврат на первом такте ПОСЛЕ истечения, то есть не позже `ttl + heartbeat_interval` (по умолчанию +5 с). **Срок — это срок, а не таймер** |
| Где гарантии нет | процесс без heartbeat (`heartbeat_interval <= 0`, нет `worker_manager`) подметальщика не имеет; срок ставится, но не исполняется, и команда обязана ответить `ttl_enforced: false` |
| Как сделать вечным | **только** `observability.persist` — переезд в L2, где вечность обеспечена файлом, а не забывчивостью |

**Зачем это вообще.** До слоёв «включил DEBUG и забыл» стиралось любым `config.reload`; после
Task 5.12 ручка переживает reload — то есть инцидент «`messages.log` 645 МБ за прогон» стал
**вероятнее**, чем был. L3 временный по построению именно поэтому.

`ttl_report` даёт единую форму блока про сроки во всех четырёх местах, где про них спрашивают
(`ttl`, `ttl_default_sec`, `ttl_enforced`, `reverts`) — иначе оператор сверял бы разные поля разных
команд и делал вывод из их расхождения.

## 4. Аудит смен: «когда и чем»

[`observability_audit.py`](../../modules/process_module/configs/observability_audit.py).
Провенанс отвечает «каким слоём задан ключ»; аудит — «когда правку сделали, чем именно и что из
этого **не удалось**».

Восемь закрытых действий: `set`, `touch`, `reset`, `clear`, `expire`, `persist`, `layer`,
`rebuild`. Список закрытый намеренно — новое действие появилось бы у потребителя как незнакомая
строка.

* **`origin` обязателен сигнатурой**, а не дисциплиной: пропуск даёт `TypeError` на вызове, а не
  тихую запись «источник неизвестен». Скрытого контекста (thread-local с дефолтом) здесь нет —
  дефолт и есть та ложь, которую механизм устраняет;
* `origin` называет **механизм**, не человека: `command:config.reload`, `watcher:app`,
  `ttl-sweeper`, `switch`. Графы «кто» нет вовсе — её не несёт ни один конверт команды, и пустое
  поле всегда врало бы молчанием;
* **кольцо одно** (`AUDIT_HISTORY = 100`, вытесненное считает `dropped`), своего файла аудит не
  заводит: каждая запись кладёт одну строку в журнал процесса — он уже долговечен, уже ротируется
  и уже единственный писатель на диск. Кольцо отвечает на «что сейчас», журнал — «что было до
  рестарта»;
* значение усекается на `_VALUE_CAP = 1024`: аудит не имеет права стать вторым местом хранения
  конфига.

## 5. Как читать вердикт

Два утверждения, и ни одно не выводится из другого.

### 5.1. `verdict` — «значение действует»

`observability_verified` ([`observability_reload.py:210`](../../modules/process_module/managers/observability_reload.py#L210)).
Трёхзначный, **не булев**:

| Вердикт | Когда | Что делать |
|---|---|---|
| `confirmed` | есть хотя бы один проверенный путь и расхождений нет | ничего |
| `failed` | `mismatches` (значение не совпало) **или** `unknown_keys` (ключ не выжил round-trip через схему — то есть его нет в контракте: `log_levl`, `errors.lvl`) | читать `mismatches` / `unknown_keys` поимённо. С задачи 5.4 `unknown_keys` приезжает только с **файловой** дороги: у ручки оператора такой ключ отвергается на границе, и вердикта в отказе нет — применять было нечего |
| `unverifiable` | проверенных путей ноль: запрос не изменил ничего либо изменил только то, чего readback не отдаёт | смотреть список `unverifiable` |

Первая редакция отдавала `verified: true` при `checked: 0` — «подтверждено» там, где не проверено
ничего. Булево поле здесь врало бы в обе стороны, а правда третья.

Незнакомые ключи ловятся round-trip'ом через ТУ ЖЕ схему, из которой считается раскладка, а
ожидаемое — через `expand_observability`, единственную точку раскладки. Вторая таблица
соответствий разошлась бы с первой на первом же новом поле: `log_level` действует как
`logger.default_level`, и своя копия этого знания была бы вторым местом, где оно живёт.

### 5.2. `delivering` / `losing` / `silent_source` — «записи идут»

`DeliveryWindow` ([`backend_ctl/protocol.py:444`](../../../backend_ctl/protocol.py#L444)),
собирается `config_reload_verified`. Один снимок отвечает «сколько записано с начала жизни
процесса»; поток — это разница во времени, и держать её может только тот, кто делает два замера.

| Поле | Смысл |
|---|---|
| `delivering` | счётчик доставки вырос |
| `losing` | выросли счётчики потерь. С `delivering` **не исключают** друг друга: часть доехала, часть отброшена |
| `silent_source` | не выросло ничего. Это **не** провал: на процессе, который молчит по делу, требовать записей нечего |
| `written_delta` | прирост доставки за окно |
| `self_cost` | **цена самого опроса** — читающая команда идёт через диспетчер и сама пишет записи (замер live 2026-07-30: **~5.1 записи на опрос** на DEBUG). Без вычета `delivering` был бы истинным всегда |
| `written_net` | `max(0, written_delta - self_cost)` |
| `cost_exceeds_window` | вычет съел больше, чем показало всё окно → арифметика недостоверна, и тишина тогда **не утверждается** |
| `counters_reset` + `reset_planes` | база сдвинулась между снимками (чужой `config.reload`, `switch`, авто-рестарт). Ищется **поплоскостно**: сумма, в которой одна плоскость обнулилась, а соседняя выросла, растёт — и окно объявлялось бы достоверным при сдвинутой базе |

Оба замера просят **когерентный снимок** (`flush=True`). Это не украшение: без `flush` контрольный
снимок отдавал ровно ноль при реальных пяти записях, и вычет был бы фикцией.

**Граница вычета названа прямо:** он верен в ЭКСКЛЮЗИВНОМ окне. Зазор `after → control`
приписывается своему опросу целиком, поэтому второй клиент драйвера или GUI-панель, пишущие в этот
зазор, вычитаются как своя цена. Честного разделения «мои записи / чужие» здесь нет — счётчик
считает записи, а не их авторов.

**Почему мало одного утверждения:** `verdict == "confirmed"` означает «уровень выставлен», а не «в
файл что-то попало» — приёмник мог быть снят соседней командой. Обратное тоже верно: записи могут
идти при провалившемся вердикте — идут по ПРЕЖНЕЙ раскладке.

### 5.3. Что показывает readback

`observability_effective` читает **живые менеджеры после применения**, а не конфиг: пороги правил,
каталог логов, `channels_active` (реестр каналов — он отражает и рантайм-снятие приёмника, чего
конфиг не видит), `sinks_disabled_by_operator`, `idle_sinks`, `declared_sources` (что МОЖЕТ писать)
рядом с `sources` (что уже писало), `unknown_scopes`, `groups`. У плоскости статистики темп
берётся из **живого окна агрегации** (`StatsManager.observability_readback`) — пересчёт из конфига
дал бы то же число и при полностью несработавшей пересборке, то есть снова эхо.

## 6. Что на лету НЕ действует

Список короткий и полный на дату сверки. Каждая строка — свойство кода, а не подозрение.

| Ручка | Что происходит | Почему |
|---|---|---|
| `config.reload {"persist": true}` | **адресный отказ** с подсказкой на `observability.persist` | флаг зарезервирован и не реализован. Молча принятый флаг был ловушкой: оператор уходил уверенным, что записал правку навсегда, а она лежала в L3 со сроком. Ключ объявлен в схеме именно ради достижимости этого отказа — иначе при `extra="forbid"` мидлварь дропнула бы его до проверки |
| `observability.documents` (фабрика стока и её конфиг) | принимается слоями, но **сток не пересшивается** | `wire_document_sink` зовётся один раз, из `_wire_observability_hub` на `initialize()` ([`process_module.py:411`](../../modules/process_module/core/process_module.py#L411)); в `apply_observability_layers` упоминаний `documents` нет. Действует со следующего старта процесса |
| `observability.history` (`level`, `max_rows`, `max_age_sec`, `purge_interval_sec`) | то же | `resolve_history_policy` зовётся один раз рядом, [`process_module.py:427`](../../modules/process_module/core/process_module.py#L427) |
| опечатка в **имени** ключа (`log_levl`), включая машинную форму (`logger.default_level`) | у ручки оператора — **адресный отказ до записи**; у файла/рецепта — принимается и называется вслух | задача 5.4 (находки Н-C/Н-D приёмки F2). Прежде имя судил только вердикт, и ответ противоречил себе: `success=true` при `verified.verdict="failed"` в том же payload, ключ оседал в L3 со сроком и не действовал. Двери разведены не по важности, а по цене отказа: опечатка в спутнике не имеет права валить switch рецепта. Голос файловой дороги — запись аудита (`unknown_keys`) и строка журнала «ВНЕ КОНТРАКТА (ключ есть, эффекта нет)» |
| правило-дефолт источника, объявленное **после** сборки конфига (ленивый импорт, плагин) | в уже собранные конфиги не попало | говорится вслух через `emergency_log`; начнёт действовать со следующей сборки (reload либо новый процесс) |
| срок (`ttl`) в процессе без heartbeat | ставится, но не исполняется | `ttl_enforced: false` в ответе — молчаливое «срок принят» там, где возврата не будет, запрещено |
| снятые ключи батчинга (`enable_batching` и соседи) | не значат ничего | схема принимает лишние ключи молча, поэтому сверка `REMOVED_BATCHING_KEYS` называет их в `emergency_log`. Отказ был бы честнее по форме, но встал бы колом на боевом стенде из-за строки, которая ничего не делает |

### 6.1. Цена самой правки: окно пересборки каналов

`config.reload` пересобирает реестр каналов, и запись, попавшая **в это окно**, до приёмника не
доезжает: **типично ~1 запись на процесс**. Это не тихая потеря — она называется голосом
`канал '<имя>' не резолвится — учтено N` и считается в `unresolved_channel_records` (живой замер
приёмки F1: `system_file: 1` на `seg` в момент `config.reload`). Симметричное окно на останове ПМ —
**2 записи** после гашения логгера. Полное описание обоих окон, с тем, что они НЕ означают, —
[`CONNECTORS.md` §4.1](CONNECTORS.md#41-два-окна-в-которых-потеря-штатна--и-видна-счётчиком).

Механизма под них не заводится (решение владельца **Р-6б**): буфер на своп-окно стоит дороже, чем
одна-две записи, у которых уже есть и голос, и счётчик. Проверить у себя: снять
`unresolved_channel_records` до и после `config.reload` — разность и есть цена жеста.

Отдельно: **значение** объявленного ключа проверяется **на записи в слой**
(`validate_layer_section`, тело `canonical_level_or_raise`), а не на резолве. До B2
`log_level="БОЛТОВНЯ"` давал `success: true`, мусор ложился в L3 со сроком, а действовал прежний
уровень — и так вело себя не одно поле, а три (`log_level`, `errors.level`, `stats.log_level`).
Правило живёт в одной позиции и применяется в четырёх точках: `replace_layer` (L1/L2),
`session_set` (L3 ключом), хендлер `config.reload` (L3 секцией), persist — через `replace_layer`.

**ИМЯ ключа судится там же с задачи 5.4** — тем же стражем, но только у слоя `session`
(`unknown_section_keys`, сверка round-trip'ом через ту же схему). Механизм один на две дороги:
границу и вердикт. Две тонкости названы, потому что обе давали ЛОЖНОЕ «имя незнакомо» ещё в
вердикте 5.7: ключ `telemetry` схема наблюдаемости не знает вовсе (снимается до сверки), а имя
скоупа она переименовывает в верхний регистр (`scopes.system` → `SYSTEM`, приводится тем же
`canonical_scope_keys`, что и в схеме). С отказом на границе каждая из них означала бы отказ
законной правке.

**Пятая дверь — телеметрия (Task 2.1, находка Н-4).** Содержимое `telemetry` (`publish` /
`throttle`) едет в те же слои, но `ObservabilityConfig` про этот ключ не знает и принимает
лишнее молча — то есть до задачи 2.1 его не судил никто. Проявлялось это тремя разными
исходами: мусор в `publish` давал `success: false` **уже после записи в слой** (отказ приходил
от получателя), мусор в `throttle` — `success: true` и `TypeError` в сторе на второй записи по
пути, а опечатка в имени под-секции вела себя по-разному в зависимости от того, приехала ли
рядом секция `observability`. Хуже всего было следствие на соседе: отравленный слой ломал
**чужую** плоскость — следующий законный `config.reload` с одним лишь `log_level` отвечал
`reconfigure failed: … TelemetryPublishConfig` до истечения срока правки, которой оператору
отказали. Теперь ключ разбирает `validate_telemetry_section` — то же правило, применяемое у
обеих дверей (`config.reload`, `telemetry.reconfigure`) **до первой записи**, плюс делегирование
из `validate_layer_section` для границы слоя. Список под-секций закрыт: незнакомое имя —
адресный отказ со списком известных.

**Задача 5.7 (блокер Н2-4 переприёмки раунда 2) — имена ПОЛЕЙ на уровень глубже.** Список
под-секций был закрыт, а поля внутри `publish` — нет: `publish: {нет_такой_ручки: …}` отвечал
`success=true`, ложился в L3 со сроком 254 с, не имел readback'а и попутно включал `gate_active`.
Задача 5.4 закрыла тот же класс у соседних плоскостей и передала ключ `telemetry` сюда — то есть
делегирование существовало, а проверка нет. Теперь незнакомое поле `publish` и незнакомое поле
ПРАВИЛА метрики (`metrics.<имя>.enabld`) — адресный отказ; **имя самой метрики остаётся законным**
(конфиг сужает набор, а не объявляет белый список) и озвучивается полем `unknown_metrics` в ответе —
голосом, а не отказом. Телеметрийная правка теперь несёт и вердикт: `unverifiable` с перечнем
запрошенных путей вместо прежнего `verified=None` — readback плоскости не отдаётся, значит
подтверждать нечем, и это ответ, а не молчание.

**Типы параметров команд наблюдаемости (Task 2.2, находка Н-5).** Контракт объявлял тип, но
читала его только warn-мидлварь: она писала предупреждение и **пропускала** сообщение к
хендлеру. Три исхода, все воспроизведены: `introspect.observability {"resolve": true}` →
`Dispatch failed: 'bool' object is not iterable`; `config.reload {"observability_reset": true}` →
тот же `TypeError` на другой команде; `config.reload {"observability_session_clear": "net"}` →
`bool("net")` истинно, и **весь слой L3 стирался**, включая правку оператора со сроком — слово
«нет» означало «да, снеси». Теперь параметры четырнадцати команд наблюдаемости
(`OBSERVABILITY_TYPED_COMMANDS`) судятся по объявленным типам **до** хендлера: чужой тип →
`success=false` с именем поля и ожидаемым типом, состояние не тронуто; годное значение доезжает
до хендлера **приведённым** (`"no"` → `False`). Охват — решение владельца Р-3(а): поверхность
наблюдаемости, а не глобальный STRICT. Три команды (`telemetry.reconfigure`,
`observability.sink.tail`, `logger.sink.tail`) жили здесь вовсе без контракта — заведены; их
параметры теперь видны и в карточке `introspect.capabilities`.

## 7. Типовые жесты

```bash
# что действует прямо сейчас (без мутации), с когерентным снимком счётчиков
introspect.observability {"flush": true, "audit_limit": 20}

# включить DEBUG одному источнику на 10 минут — и убедиться, что подействовало
config_reload_verified(process="camera_0",
                       observability={"loggers": {"Plugins.sources.camera_service": {"level": "DEBUG"}},
                                      "ttl": 600})
#   verdict=confirmed  → значение действует
#   delivering=true    → записи идут (self_cost уже вычтен)

# снять приёмник на время разбора и вернуть его самому
observability.sink.disable {"sink": "messages_file", "manager": "logger", "ttl": 300}

# сделать правку постоянной (L3 → L2)
observability.persist {}

# вернуть один ключ к нижнему слою (удалить из L3, а не присвоить прежнее)
config.reload {"observability_reset": ["log_level"]}

# приоткрыть ПОТОК широких записей о единицах работы (Ф4): первые 5 и дальше каждая 50-я
config.reload {"observability": {"events": {"first_n": 5, "every_mth": 50}}, "ttl": 600}
#   events_applied     → что применено к ЖИВОМУ селектору
#   introspect.observability → events.kinds → selected / skipped / decisive по родам
```

**Отбор широких записей** (`observability.events`, ADR-PM-036) — единственная ручка этой секции,
где **ноль означает «выключено»**, а не «единица»:

| Ключ | Дефолт | Смысл |
|---|---|---|
| `first_n` | `0` | сколько потоковых записей КАЖДОГО рода пропускать всегда |
| `every_mth` | `0` | после первых N проходит каждая M-я; `0` — дальше не проходит ничего |

То есть по умолчанию поток не пишется вовсе, а **фронты решений (`decisive=True`) идут мимо отбора
всегда** — прорядить вердикт значило бы потерять то, ради чего запись заводилась. Не путать с
`sampling_first_n` / `sampling_every_mth` в той же секции: там ключ отбора — пара «уровень + текст»
записи, там `every_mth` имеет `min=1`, и ноль невыразим. Одинаковые слова, разные механизмы.

Ручка действует **на лету**: живой селектор перенастраивается пересборкой (`config.reload`, файловый
watcher, возврат по сроку), счёт по родам при этом продолжается, а не начинается заново.

### Flight recorder — дамп кольца записей (`observability.flight`, ADR-PM-037)

```bash
# что происходило в процессе вокруг момента брака — файлом, по вызову приложения
config.reload {"observability": {"flight": {"enabled": true, "sink": "flight_ring", "keep": 5}}}
#   flight_applied     → что применено к ЖИВОМУ рекордеру
#   introspect.observability → flight → dumps / records / evicted_files /
#                                       refused_disabled / refused_no_ring / refused_failed / last_path
```

| Ключ | Дефолт | Смысл |
|---|---|---|
| `enabled` | `false` | **единственный** выключатель механизма. Второго способа выключить нет намеренно |
| `sink` | `""` | имя memory-приёмника ЛОГГЕРА, чьё кольцо уходит в дамп |
| `keep` | `5` | сколько последних дампов держать в `flight/`; `0` — без предела |
| `limit` | `0` | сколько последних записей кольца брать; `0` — всё, что лежит |

**Само кольцо объявляется НЕ здесь, а соседней дверью — и там ловушка.** Приёмник заводится в
`observability.channels.<имя>` и обязан нести `type: memory` **и** маршрут через
`observability.scopes`:

```yaml
observability:
  processes:
    inspector:
      channels:
        flight_ring: {type: memory, capacity: 500}
      scopes:                       # ось channels ЗАМЕЩАЮЩАЯ — дефолты перечисляются рядом
        SYSTEM:   {channels: [console, system_file, flight_ring]}
        BUSINESS: {channels: [system_file, messages_file, flight_ring]}
      flight: {enabled: true, sink: flight_ring, keep: 5}
```

Без `type` общий цикл секции каналов строит **файловый** приёмник под тем же именем (дефолт
`LoggerChannelSchema.type == "file"`), и снаружи разница не видна: канал есть, `flight.sink` на
него указывает, а `tail()` у файла отсутствует. Без маршрута канал поднят и вечно пуст. Оба случая
дают ОДИН из трёх названных отказов, и ни один не тишина:

| Счётчик | Диагноз | Чем лечится |
|---|---|---|
| `refused_disabled` | механизм выключен ручкой | `observability.flight.enabled` |
| `refused_no_ring` | приёмника нет / не `memory` / не смаршрутизирован | `observability.channels` + `scopes` |
| `refused_failed` | кольцо прочитано, файл не написан | диск, права, ФС |

**Куда пишется:** `<база логов>/<имя процесса>/flight/<ГГГГММДД_ЧЧММСС_мкс>_<reason>.jsonl` — той
же дорогой, что `system.log` этого процесса (`log_paths`, не cwd). Первая строка файла —
шапка `kind="flight_manifest"` с причиной, `trace_id` единицы и снимком кольца
(`capacity`/`size`/`written`/`evicted`): без снимка счёт записей нечитаем. Вытеснение по `keep`
говорит INFO с именем удалённого файла — на КАЖДОЕ удаление, потому что событие редкое, а
молчаливое удаление улики хуже строки в журнале.

**Цена — числом** (500 записей, файл ~142 КБ): медиана **2.96 мс**, p95 3.17, max 3.24; с
ретеншеном `keep=5` медиана 3.32 мс, max 6.65. Бюджет РЕДКОГО события: на кадре 25 FPS (40 мс)
один дамп занял бы ~8% бюджета, поэтому триггер стоит на фронте решения, а не на кадре.

**Не путать с одноимённым механизмом оператора.** `backend_ctl record_*` и
`telemetry_readmodel.export_history` кольцуют ТЕЛЕМЕТРИЮ и стоят снаружи процесса; здесь — ЗАПИСИ
одного процесса, изнутри него. Пикселей кадра нет ни в одном из трёх.

**Сколько это стоит — числом, чтобы не подбирать вслепую** (живой стенд `inspection_full`,
2026-08-16, 7 процессов, 21.3 единицы/с): широкая запись весит **476 Б** (min 475, max 476, n=483).
Отсюда цена режима: `every_mth=9` дала **8 548 строк/ч ≈ 3.88 МиБ/ч** — вдвое выше ориентира
«фон плоскости ≤ ~2 МиБ/ч на 8 процессов», по которому судят приёмники этапа 6. Чтобы в ориентир
уложиться на таком темпе, поток должен прореживаться **не чаще ~1/18** (2 МиБ/ч ÷ 476 Б ≈ 4 400
записей/ч при 76 700 единицах/ч). Дефолт `0/0` укладывается тривиально: фронты решений редки —
на живой линии их единицы против тысяч единиц работы.

Последний жест — именно **удаление**: присвоение прежнего значения порвало бы связь с нижним слоем
навсегда, и при смене дефолта сессия продолжала бы держать старое число.

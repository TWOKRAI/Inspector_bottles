# error_module — Архитектурные решения

> Ссылки: [`../../DECISIONS.md`](../../DECISIONS.md) · [`../logger_module/DECISIONS.md`](../logger_module/DECISIONS.md)

## ADR-EM-001: ErrorManager как наследник LoggerManager (не композиция)

- **Дата:** 2026-03-12
- **Статус:** принято
- **Контекст:** ErrorManager нуждается в каналах, буферизации, scope-based routing для DEBUG/INFO — всё есть в LoggerManager. Альтернатива: композиция (ErrorManager содержит LoggerManager).
- **Решение:** Наследование `ErrorManager(LoggerManager)`. Переиспользует CRM-инфраструктуру (ChannelRegistry, BatchBuffer, Dispatcher), добавляет только severity routing через `_level_to_channel` и `log()` override.
- **Не сливать:** ErrorManager остаётся отдельным модулем — severity routing опциональная специализация.
- **Отклонено:** Композиция — избыточная обёртка без выгоды.

## ADR-EM-002: Level-based routing через _level_to_channel dict

- **Дата:** 2026-03-12
- **Статус:** принято
- **Контекст:** Маппинг WARNING → warnings_file, ERROR → errors_file, CRITICAL → critical_file. Альтернатива: через CRM's Dispatcher.
- **Решение:** `Dict[str, str]` с O(1) lookup в `log()`. Проще и быстрее Dispatcher для 3 уровней.
- **Fallback:** Если канал отсутствует — используется `errors_file`.

## ADR-EM-003: _normalize_error_config() как модульная функция

- **Дата:** 2026-03-31
- **Статус:** принято
- **Решение:** Модульная функция в `error_manager.py`, не метод класса. Паттерн совпадает с logger_module.

## ADR-EM-004: expand_error_manager_config() в отдельном файле

- **Дата:** 2026-03-31
- **Статус:** принято
- **Решение:** `core/error_config_assembly.py` — единственное место merge severity-каналов. configs/ содержит только поля, core/ содержит логику сборки.

## ADR-EM-005: _level_to_channel инициализация до super().__init__()

- **Дата:** 2026-04-03
- **Статус:** принято
- **Контекст:** `LoggerManager.__init__()` выставляет `LoggerManager._instance = self`. Косвенные вызовы через `get_logger()` могут дёрнуть `ErrorManager.log()` → `self._level_to_channel` → `AttributeError`.
- **Решение:** `self._level_to_channel = {}` ДО `super().__init__()`. Пустой dict безопасен: все уровни fallback на parent.

## ADR-EM-006: Ленивый экспорт ErrorManager из `core/__init__.py`

- **Дата:** 2026-04-10
- **Статус:** принято
- **Контекст:** Прямой `from .error_manager import ErrorManager` в `core/__init__.py` выполняется при любом `from error_module.core.error_config_assembly import …` и ломает цель ленивой загрузки в `error_module.__init__` (ранний импорт `logger_module` при плоском `pythonpath`).
- **Решение:** `ErrorManager` в `__all__` и доступ через `__getattr__` в `core/__init__.py`; `expand_error_manager_config` импортируется eager как и раньше.

## ADR-EM-007: Единая точка эмиссии — `_route()` вместо override `log()` (Ф4.2)

**Статус:** принято (2026-07-27)

**Контекст:** `ErrorManager.log()` был **полным override'ом**: своя сборка `LogRecord`, своё
кормление tap'ов, свой enqueue, свой пол ошибок и свой цикл записи в канал. `LoggerCore.log()`
он для WARNING/ERROR/CRITICAL не вызывал вовсе. Итог измерен на одной фазе Ф0: общий код
зеркалили руками **четыре раза** — задача 0.4 (учёт потерь) в двух местах, 0.9 (пол ошибок) в
двух, tap'ы в двух, а 0.5 (двухслойный контекст) **забыли**. Из-за этого на ГЛАВНОМ
производственном пути ошибок пропадал `proc_name` — поле, ради которого Ф0.5 и делалась.
Ревью фазы (2026-07-27) воспроизвело потерю двумя независимыми ревьюерами и рекомендовало
закрыть развилку ДО фаз адресации (Ф2.1 — штамповка имени источника) и модели записи
(Ф3 — `trace_id`), иначе обе легли бы в две копии и разъехались так же.

**Решение:** `LoggerCore.log()` — единственная точка эмиссии. Наследник, у которого другой
резолв приёмников, переопределяет **только** хук:

```python
def _route(self, scope, level, module) -> Optional[List[str]]
```

Контракт возврата тройной, и различие существенное:
- `None` — запись отклонена гейтом (`messages_skipped`), «мы решили не писать»;
- `[]` — приёмников нет (`records_without_channels`), «мы хотели, но некуда»;
- непустой список — адресаты.

Гейт `should_log` стоит **внутри `_route`**, а не в `log()`. Это не деталь: наследник,
у которого решение принимает не скоуп (severity-маршрут ошибок), обязан уметь вернуть
приёмники, не спрашивая гейт вовсе. Порог скоупа (`SYSTEM` = `WARNING`) не должен уметь
заглушить `ERROR`.

Вся реализация `ErrorManager` после слияния — семь строк: есть severity-маршрут → отдать один
канал, нет → отдать резолв родителя.

**Что слияние починило попутно** (оба — измерены, не выведены):
- **Отказ канала статусом не считался** на severity-пути: `_write_error_to_channel` при
  `{"status": "error"}` уходил в пол, не увеличивая `channel_refused_records`. Запись была
  цела, но третий класс потери на главном пути ошибок оставался невидимым. Общий
  `_write_record_to_channels` его считает.
- **Пустая адресация проваливалась в ветку буфера**: ничего не клала и всё равно
  инкрементировала `messages_batched` — счётчик активно уверял, что запись ушла. Заведён
  четвёртый класс потери `records_without_channels` (достижим: скоуп без списка каналов при
  пустом реестре — все приёмники сняты `logger.sink.disable`). Живая проверка: 5 записей при
  снятых приёмниках → `records_without_channels=5`, `messages_batched` не изменился.

**Отклонённые альтернативы:**
- **Оставить override и «просто не забывать» зеркалить** — отклонено фактом: за одну фазу
  забыли один раз из четырёх, и цена ошибки — тихая потеря поля на пути ошибок.
- **Передавать различие параметром `log(..., channels=...)`** — отклонено: параметр пришлось
  бы протаскивать через все пять фасадных методов (`debug`/`info`/`warning`/`error`/`critical`)
  и через `ObservableMixin`, то есть развилка переехала бы в публичный API.
- **Сделать сразу цепочку процессоров (Ф4.1)** — отклонено как последовательность: цепочку
  надо куда-то вешать, и вешать её на развилку означало бы делать две точки подключения.
  Ф4.1 теперь строится на одной.

**Следствие:** Ф2.1 (штамповка имени источника) и Ф3 (`trace_id`) правят **одно** место.

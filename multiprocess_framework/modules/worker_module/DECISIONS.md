## ADR-WRK-001 (was ADR-159): Удаление ложного ребра worker → dispatch

**Статус:** принято  
**Дата:** 2026-04-09  
**Контекст:** ARCHITECTURE.md содержал ребро `worker --> dispatch`, подразумевая, что WorkerManager использует Dispatcher. Grep подтвердил 0 импортов из dispatch_module. WorkerManager — менеджер жизненного цикла потоков (create/start/stop/restart), а не маршрутизатор сообщений. Dispatcher используется в CommandManager и RouterManager для routing ключ→обработчик.  
**Решение:** Удалить ребро из графа. worker_module зависит только от base_manager (#1).  
**Последствия:** Граф зависимостей точнее отражает реальность. Упрощает анализ для process_module (#11).

## ADR-WRK-002 (was ADR-160): Сохранение двух конфигурационных подходов (ThreadConfig + SchemaBase)

**Статус:** принято  
**Дата:** 2026-04-09  
**Контекст:** Модуль имеет два конфигурационных подхода:
1. `core/thread_config.py` — `ThreadConfig` (plain class, `to_dict()`/`from_dict()`) — runtime-объект, используется в WorkerManager/WorkerLifecycle.
2. `configs/thread_worker_config.py` — `ThreadWorkerConfig(SchemaBase)` — Pydantic-схема для декларативного конфига процесса.

STATUS.md явно отмечал: «рантайм ThreadConfig не заменён».  
**Решение:** Сохранить оба. Причины:
- `ThreadConfig` — лёгкий runtime-объект внутри процесса (не пересекает границу процессов сам по себе).
- `ThreadWorkerConfig(SchemaBase)` — декларативная схема для конфигов процесса (`proc_dict["thread"]`), с Pydantic-валидацией.
- Паттерн ADR-008 (Dict at Boundary): Pydantic на границе (`ThreadWorkerConfig.model_dump()` → dict → `ThreadConfig.from_dict()`), plain class внутри.
- Замена ThreadConfig на SchemaBase добавит тяжёлый Pydantic в горячий путь lifecycle без выигрыша.  
**Последствия:** Два объекта с похожими полями, но разными ролями. Документировано.

## ADR-WRK-003 (was ADR-161): Сохранение self.name = manager_name (compatibility alias)

**Статус:** принято  
**Дата:** 2026-04-09  
**Контекст:** `worker_manager.py:42` содержит `self.name = manager_name` с комментарием «Синоним для совместимости». Grep показал: используется в `test_worker_manager.py`. Внешних потребителей (process_module) через `.name` не обнаружено.  
**Решение:** Сохранить alias. Причины:
- Минимальная стоимость (1 строка).
- BaseManager может иметь `.name` в будущем (стандартный паттерн).
- Удаление требует правки теста без выигрыша.  
**Последствия:** Alias остаётся. Если BaseManager добавит `.name`, убрать дубликат.

## ADR-WRK-004 (was ADR-162): WorkerInfo как TypedDict (документация) + plain dict (runtime)

**Статус:** принято  
**Дата:** 2026-04-09  
**Контекст:** `types/types.py` определяет `WorkerInfo(TypedDict)`, но `registry.register()` конструирует plain dict литерал. TypedDict служит документацией полей, не runtime-проверкой.  
**Решение:** Оставить как есть. TypedDict используется IDE и mypy для подсказок. Runtime-конструкция через dict литерал — стандартный паттерн Python (TypedDict не создаёт экземпляры иначе чем dict).  
**Последствия:** Тип-безопасность обеспечивается IDE/mypy, не runtime.

## ADR-WRK-005: `KeyedExecutor` — исполнитель с порядком по ключу (Task 1.9a, L-9)

**Статус:** accepted (2026-10-21, Task 1.9a плана `lifecycle-stop-ownership`; стадия 0 — reviewer Opus, 2 раунда).

**Контекст.** Обработчик команды, который ждёт другой процесс, занимает приёмный поток (L-9). В PM уже есть ядро
«FIFO на ключ + поток на занятый ключ» (`_run_when_child_ready` / `_drain_child_actions`, ADR-PMM-024), но без потолка
очереди, без `reply` ровно раз, без закрытия к сроку и без ключей-множеств. Вердикт CTO (О5, р.2): один исполнитель
во фреймворке, потоки — через `WorkerManager`, не второй механизм.

**Решение.** Протокол `OrderedExecutor` (`interfaces.py`) и реализация `keyed_executor.KeyedExecutor` (Stability: lite).
- Устройство — обобщение ADR-PMM-024: одна общая `pending: deque` в порядке подачи + `running: Counter[str]` + флаг
  `running_all`. Запись исполнима, если её ключ не пересекается с исполняемыми, нет `running_all` и ключ не
  пересекается с ключами всех более ранних записей; `None` исполнима, только когда ничего не исполняется и впереди
  никого нет. Рабочий под `Condition` берёт первую исполнимую запись (O(`max_pending`)). Одной «deque на ключ» мало:
  `None` должен задерживать ключи, которых ещё нет ни в одной очереди, а `{a,b}` в голове очереди `a` держал бы
  рабочего, пока занят `b`.
- `reply` ровно раз: «закрыт?» + постановка, опустошение + `closed=True` — под одним локом; запись уходит из `pending`
  только под локом (QUEUED→TAKEN/REJECTED), `reply` зовёт её владелец вне лока. Лок не держится поверх `action`,
  `reply`, `should_reject`. `reply` исполненной операции зовётся до снятия её ключей: ответы операций с
  пересекающимися ключами уходят в порядке подачи.
- `max_pending=64` считает только ждущие операции (решение лида). Потолок транспорта — system-очередь процесса
  `maxsize: 100` (`process_manager_process.py:66`, `process_launch_config.py:15`); худший всплеск PM
  (start-all/restart-all на 8 процессах × start + relay + telemetry ≈ 24, плюс `topology.apply` / `wire.*`) < 32 —
  запас ×2, и ниже 100.
- `max_workers=4`: R2 нужен ≥ 2; рабочие ждут на `Condition.wait(0.1)` и CPU не берут. Это только умолчание: 1.9b
  задаёт его для исполнителя готовности явно, не меньше числа детей (ADR-PMM-024: поток на неготового ребёнка).
- Рабочие — постоянные SYSTEM-воркеры `keyed-<name>-<i>` (`WorkerManager.create_worker`, `auto_start=True`,
  `restart_on_failure=False`, LOOP): `pause_all` и GUI worker CRUD их не трогают; на эпизод не создаются (имя
  уникально, STOPPED остаётся в реестре). Имя занято → `ValueError`; поэтому после `shutdown` имя остаётся занятым
  в этом `WorkerManager` — новый исполнитель на живом менеджере берёт новое имя. `stop_event` от `stop_all_workers` →
  `request_stop()` всего исполнителя, иначе очередь осталась бы без ответа. Рабочий, вышедший не по закрытию
  (исключение, в том числе `BaseException` из `action` — ей `reply` ровно раз, затем исключение идёт дальше),
  закрывает исполнитель до снятия счётчика живых.
- «`reply` ровно раз» держится и при снятии очереди, когда чей-то `reply` бросил `BaseException`: отказ получает
  каждая снятая запись, первая `BaseException` пробрасывается после всех ответов (ревью ветки).
- `should_reject` (без защёлки, вне лока, исключение → `True`) зовётся в `submit` и свободными рабочими на каждом
  пробуждении (раз в `0,1 с`) при непустой очереди — в том числе когда ничего не исполнимо: ждущие за занятым ключом
  снимаются, не дожидаясь его (ревью р.1). При `serial=True` единственный рабочий занят операцией, и очередь
  снимается после неё — досрочный возврат операции остаётся делом `action`.
- Повторный вход (`submit` из `action`): ключ ⊆ ключа текущей операции (при `serial` — любой) → на месте, часть
  родителя; иначе обычная постановка. Признак «внутри операции» — thread-local ключ на время любого `action` этого
  исполнителя (рабочим и на месте при `inline_if_idle`).
- Закрытие — `Stoppable`: `request_stop()` снимает очередь (`system_stopping`), `join_until(deadline)` ждёт текущие
  операции и выход рабочих, `False` + WARNING с именами операций; `shutdown = request_stop + join_until`.

**Отвергнуто.** «deque на ключ» как в ADR-PMM-024 (дедлок `{a,b}` при одном рабочем; `None` не задерживает новые
ключи). Поток на операцию (нет потолка и join). `WorkerPoolExecutor` (нет ключей; план кадров). Блокирующий `submit`
на потолке (приёмный поток ждал бы — ровно L-9).

**Следствия.** PM в 1.9a не меняется (ни одна команда не помечена). 1.9c (перенесено из 1.9b, ADR-PMM-039):
`_run_when_child_ready` — тонкая обёртка над `submit(inline_if_idle=True)`, исполнитель — во владении `Scope` PM.

**Reversible:** yes (новый файл; до 1.9b потребитель — только `CommandManager` через протокол).
**Refs:** `plans/lifecycle-stop-ownership/tasks/T1.9a.md` (D1, D2), ADR-PMM-024, ADR-CMD-006,
`tests/test_keyed_executor_acceptance.py`, `tests/test_keyed_executor_hazards.py`.

## ADR-WRK-006: `ExecutorManager` — сотрудник процесса, который держит именованные исполнители (Task 1.9m)

**Статус:** accepted (2026-10-21, Task 1.9m плана `lifecycle-stop-ownership`; стадия 0 — reviewer Opus, 2 раунда).
Решение владельца 2026-10-21: «отдельный помощник (как подмодуль или модуль) наподобие nginx, чтобы не только PM, но и
другие процессы при необходимости себе сделали; новый сотрудник на базе фреймворка (наследующий от base_manager)».
Форма «внутри процесса, не отдельный процесс» согласована с владельцем.

**Контекст.** После 1.9a (ADR-WRK-005) `KeyedExecutor` создаёт и закрывает тот, кто его завёл: PM для своих команд,
позже `ServiceHost`. Каждому владельцу пришлось бы заново решать, кто создаёт, кто закрывает, как назвать исполнитель
для `CommandManager` и как его показать в интроспекции. 1.9b (ProcessManager) и ServiceHost строятся на общем сотруднике.

**Решение.** `worker_module/executor_manager.py`: `ExecutorManager(BaseManager, ObservableMixin)` + `ExecutorSpec`.
Протоколы `IExecutorRegistry` (узкий вход для `CommandManager`: `get(name)`) и `IExecutorManager` (для владельцев:
`create` / `register` / `load_config` / `names` / `describe` / `is_executor_thread`) — в `interfaces.py`.
- *Место.* Один файл в `worker_module` рядом с ядром, не новый модуль: число модулей, `MODULE_TIERS.md`, `modules.yaml`
  не меняются (новый модуль уронил бы четыре проверки `test_module_tiers.py` — слой ради одного файла). Схема
  `ExecutorSpec` — в том же файле. Экспорта из `__init__.py` нет, как у `KeyedExecutor`.
- *Владение.* Созданным менеджер владеет: отдаёт его области (`scope.own(_OwnedExecutor, kind="executor")`), закрытие —
  общим сроком области, сумма ожиданий не растёт с числом исполнителей. Зарегистрированным **не** владеет и не зовёт
  `request_stop` / `join_until`, даже если объект `Stoppable`: владелец остаётся у регистрирующего (второго владельца
  рядом нет; PM по 1.9b зовёт `request_stop`/`join_until` своего исполнителя как вызов, не как владение).
- *`_OwnedExecutor`.* Приватная обёртка `Stoppable`; `join_until` со своего рабочего потока не ждёт (WARNING и `False`
  сразу), иначе рабочий ждал бы сам себя до срока. Признак «свой рабочий» — точное имя потока
  `f"{worker_manager.manager_name}_keyed-{name}-{i}"` (`worker_lifecycle.py:75` + `keyed_executor.py:146`); ядро не
  правится, публичного признака у него нет. Тот же признак отдаёт `is_executor_thread` (1.9b: «закрываюсь со своего
  рабочего»; `startswith("keyed-pm-lifecycle-")` ложен — имя потока начинается с имени менеджера).
- *Без области* (тесты, менеджер вне `ProcessModule`) созданные лежат в `_unowned`; `_on_shutdown` закрывает их всегда
  (и когда область привязана позже создания) одним общим сроком `_UNOWNED_JOIN_S = 2.0` с через ту же обёртку: у каждого
  исполнителя одно место закрытия — область или `_unowned`. `create` после закрытия — `RuntimeError`, а `register` после закрытия принимает запись без владения (закрывать нечего); гонку
  «создание ↔ закрытие» закрывают `ScopeClosedError` области или повторная проверка флага после создания.
- *`extra="forbid"` у `ExecutorSpec`.* Опечатка в ключе конфига (`max_worker`) — громкий отказ записи, а не тихий
  исполнитель с умолчаниями; строже соседних схем. Следствие: команда, названная этим исполнителем, будет отклонена
  (ADR-CMD-007). `should_reject` и `log` в схеме нет — это код, не данные.
- *Ошибки конфига.* `load_config`: своя попытка на каждую запись (принцип 5) — неверная запись даёт одну строку ERROR (имя
  и `<loc>: <msg>`, без входных значений), соседние создаются. Нет исполнителей — ни потока, ни строки лога.
- *Интроспекция.* `describe()` честно называет пробел: `unavailable = ["pending_depth", "running_keys"]` — у
  `KeyedExecutor` нет публичного чтения очереди и ключей, счётчиков принятых/отказанных нет даже приватно. В ядро не
  дописано; кандидат на отдельную задачу — `docs/claude/OPEN_QUESTIONS.md`.
- *Защита рабочих от `worker.*` по IPC — уже сегодня.* Рабочие исполнителя имеют `WorkerType.SYSTEM`;
  `WorkerManager.is_worker_protected` защищает любого SYSTEM, а не только `PROTECTED_WORKER_NAMES`, и
  `worker.stop/remove/drain/restart/update` отвечают `reason: "protected"`. Правка `worker_manager.py` не нужна; страж —
  hazard-тест H7. Открыт `worker.start` (проверки нет): мёртвого рабочего перезапустит безвредно — исполнитель уже закрыт,
  `join_until` → `True`. Прямой `wm.stop_worker("keyed-…")` из кода не защищён по замыслу; менеджер его не зовёт.

**Отвергнуто.**
- *Отдельный процесс-исполнитель («nginx» как процесс)* — отвергнуто владельцем: исполнитель зовёт обработчики команд
  процесса и его объекты по ссылке; через границу процессов шёл бы только dict (Dict at Boundary), `action` не перевезти.
- *Правка ядра `keyed_executor.py`* (публичный `stats()`, признак своего потока) — отвергнута решением владельца
  «1.9a без правок».
- *Новый модуль* — слой и четыре контракт-теста ярусов ради одного файла (принцип 4).
- *Владение зарегистрированными `Stoppable`* — второй владелец рядом с регистрирующим.
- *Префикс `keyed-` в `PROTECTED_WORKER_NAMES`* — второй признак того же факта (тип SYSTEM) и защита чужих воркеров с таким
  именем.
- *Без записи в области (полагаться на `_WorkersStop`)* — исполнитель остановится, но очередь получит отказ только в
  фазе 2 после всех `request_stop` записей `work`.

**Следствия.** Процесс получает `executor_manager` (ADR-PM-055); `CommandManager` разрешает `executor="<имя>"`
(ADR-CMD-007). 1.9b строит исполнитель PM через `create` / `register`; `ServiceHost` сводится на менеджер после 1.9c.
Признак потока держится на двух строках одного модуля: переименование одной из них — `is_executor_thread` молча `False`,
закрытие со своего потока снова ждёт срок (страж — тесты на точное имя потока). Уход `_live_workers` ядра ниже нуля после
`worker.start` на мёртвом рабочем безвреден (исполнитель закрыт).

**Reversible:** yes (новый файл и два протокола; до 1.9b потребитель — только `ProcessModule` и `CommandManager`; после
1.9b — откат вместе с переводом команд PM).
**Refs:** `plans/lifecycle-stop-ownership/tasks/T1.9m.md` (D1, D2, D5, D6, D9), ADR-WRK-005, ADR-CMD-007, ADR-PM-055,
`tests/test_executor_manager_acceptance.py`, `tests/test_executor_manager_hazards.py`.

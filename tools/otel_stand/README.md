# Стенд-арбитр OTLP (этап 7, Task 0.1)

Внешний потребитель, который разбирает наши записи и тем самым проверяет, что словарь
полей Ф3 **настоящий, а не заявленный**. Это не мониторинг и не эксплуатационный
приёмник: во всех отчётах трека до сих пор стоит «соответствие модели записи OTel
остаётся заявленным» ровно потому, что ни один внешний потребитель их не разбирал.

Главный раздел здесь — [«Что этот арбитр НЕ проверяет»](#что-этот-арбитр-не-проверяет).
Приёмка Task 4.2 обязана ограничивать свои выводы им: то, что коллектор принимает в
любом виде, доказанным не считается.

## Бинарник

| | |
|---|---|
| Дистрибутив | **`otelcol` (ядро)**, не `otelcol-contrib` |
| Версия | `0.158.0` |
| Путь на машине владельца | `C:\Users\INNOTECH\tools\otelcol\otelcol.exe` |
| Откуда | [релизы `opentelemetry-collector-releases`](https://github.com/open-telemetry/opentelemetry-collector-releases/releases), файл `otelcol_0.158.0_windows_amd64.tar.gz` |

В репозиторий бинарник не кладётся (123 МБ распакованного). Путь машинозависим — если
он у вас другой, правьте команды ниже, конфиг от пути не зависит.

**Почему ядро, а не contrib.** Всё, что нужно этому конфигу, собрано в ядре — проверено
не манифестом, а самим бинарником:

```
$ otelcol.exe components | grep -A1 "name: file"
    - name: file
      module: github.com/open-telemetry/opentelemetry-collector-contrib/exporter/fileexporter v0.158.0
```

`fileexporter` живёт в исходниках contrib, но **собран в дистрибутив ядра**. Разница в
цене втрое: 35.4 МиБ против 94.8 на Windows, 30.8 против 93.0 на `linux_arm64`. Contrib
понадобится только при экспорте в Loki/Prometheus/Elasticsearch — тогда меняется
бинарник, конфиг остаётся.

Артефакты под другие платформы (Jetson, Raspberry) — в §«Три платформы» плана
[`otel-export.md`](../../plans/otel-export.md).

## Запуск

Из корня рабочего дерева — относительный путь file-экспортёра считается от него:

```bash
mkdir -p logs_live
/c/Users/INNOTECH/tools/otelcol/otelcol.exe --config tools/otel_stand/collector.yaml
```

Слушает `127.0.0.1:4318` (OTLP/HTTP). Пишет двумя экспортёрами: `debug` — в свою консоль
человеку, `file` — в `logs_live/otel_records.json` машине, по одному JSON-объекту на
строку. `logs_live/` игнорируется git'ом.

Порт стенда `4318` с портом живого бэкенда `8765` не конфликтует — гонять их вместе можно.

## Три контроля (Task 0.1) — фактические ответы, 2026-08-11

Payload'ы лежат рядом в [`controls/`](controls/), проверка повторяется одной строкой:

```bash
curl -s -w "HTTP %{http_code}\n" -X POST http://127.0.0.1:4318/v1/logs \
  -H 'Content-Type: application/json' --data-binary @tools/otel_stand/controls/<файл>.json
```

| # | Файл | Ответ коллектора | Легло в файл? |
|---|---|---|---|
| 1. Положительный | `ctl1_valid.json` | `HTTP 200` · `{"partialSuccess":{}}` | **да** |
| 2а. Форма | `ctl2a_severity_string.json` | `HTTP 400` · `ReadEnumValue: unknown string value, error found in #10 byte of …"severityNumber":"INFO"…` | нет |
| 2б. Конверт | `ctl2b_no_resourcelogs.json` | **`HTTP 200`** · `{"partialSuccess":{}}` | нет (записей в нём нет) |
| 3. Семантика | `ctl3_semantic_wrong.json` | `HTTP 200` · `{"partialSuccess":{}}` | **да** |

Содержимое файла после прогона — ровно две записи, первая и третья:

```
#1 service=ctl1-probe scope=inspector.ctl1 sev=9 traceId=5b8efff798038103d269b633813fc60c
#2 service=ctl3-probe scope=BUSINESS      sev=9 traceId=-
```

**Контроль 2б опроверг спеку, и это записано, а не подогнано.** Task 0.1 предполагал, что
отсутствие конверта `resourceLogs` даст HTTP-ошибку. Не даёт: тело без `resourceLogs` —
законный запрос, в котором ноль записей, и коллектор отвечает `200`. То есть **«200» от
этого арбитра не означает «мы что-то доставили»** — оно означает «в том, что пришло, не
нашлось ничего неразбираемого». Отличать «доехало 100 записей» от «доехало 0» по коду
ответа нельзя; для этого есть тождество потерь Task 3.4 и сам файл.

## Что этот арбитр НЕ проверяет

Коллектор судит **форму** (типы полей, структуру protobuf/JSON) и не судит **смысл**.
Контроль 3 предъявлен именно для этого: он содержит два заведомо неверных для нас
решения — и принят без единого возражения.

| Что положено неверно | Что сделал коллектор |
|---|---|
| Наш `scope` (`BUSINESS` — группа маршрутизации) положен в `InstrumentationScope.name`, где по ADR-LOG-005 должен быть `module` | принял; в файле стоит `scope=BUSINESS`, и никто не возразил |
| `trace_id` положен обычным атрибутом вместо выделенного поля `traceId` | принял; в файле `traceId` отсутствует — молча, без предупреждения |

Отсюда список полей, по которым **зелёный ответ стенда ничего не доказывает**:

* **`InstrumentationScope.name`** — принимается любая строка. Что мы кладём туда `module`,
  а не `scope`, доказывается только тестами маппера (Task 1.1), не стендом.
* **`traceId`** — его отсутствие не ошибка. «Записи ушли без trace_id» и «записи ушли с
  trace_id» с точки зрения HTTP-ответа неразличимы; смотреть надо в файл.
* **Любой ключ в `Attributes`** — имена и значения атрибутов не валидируются вовсе,
  semconv не сверяется. `service.nmae` уехал бы молча.
* **`Resource`-атрибуты** — то же самое: `service.name` может быть чем угодно, включая
  пустую строку и `"unknown"`. Правило «отсутствующее поле пропускается, а не
  заполняется `unknown`» (Task 1.2) стенд не сторожит.
* **Полнота потока** — коллектор не знает, сколько записей мы эмитировали. Потери между
  источником и им видны только через тождество Task 3.4.
* **Семантика `severityNumber`** — что `9` это именно INFO, а не сдвинутая на единицу
  шкала, стенд не проверит: он судит тип, а не значение.

Что стенд **действительно** проверяет: типы полей и структуру конверта (контроль 2а — с
адресом дефектного поля в ответе), и что запись целиком проходит путь
«наш экспортёр → OTLP/HTTP → сторонний разборщик» без нашего кода на его стороне.

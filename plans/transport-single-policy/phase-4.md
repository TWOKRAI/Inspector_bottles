### Task 4.1 — Claim check по размеру, под любым ключом item

**Level:** Senior · **Assignee:** teamlead · **Layer:** framework
**Направление (решение владельца 2026-09-29, заменяет «объявленные image-порты»):** ссылкой едет **любой** `ndarray`
крупнее порога под **любым** ключом верхнего уровня item — решает send-middleware (`strip_data_frame_on_send`), через
которую идёт весь data-трафик, а не декларация порта. Плагину ничего не нужно объявлять и помнить: маска, отрисованный
кадр, кадр симулятора линии, SDK-кадр считывателя — один путь. Мелкое едет inline, как сейчас. На приёме ссылка
восстанавливается под тем же ключом.
- **Ядро задачи — пул, а не проверка:** сегодня одно кольцо на процесс под `frame`; item с кадром и маской требует кольца
  на ключ (или общего пула блоков) и займа/возврата **на каждую ссылку** — через тот же `FramePool`/reclaim, что и `frame`
  (связь с Task 1.1/1.2 — одна дверь, одна политика).
- **Дешевле SHM — не возить:** если 4.0 покажет, что потребителю маска не нужна целиком (`storage`), — контур/RLE у
  источника вместо SHM; решение по каждому грузу пишется в таблицу 4.0.
- Порт `dtype="image/*"` остаётся подсказкой для GUI/валидации, не условием claim check.
- Rejected: «объявленные image-порты» — каждый новый плагин обязан помнить правило, забытый ключ молча едет через pipe
  (так уже случилось с маской `blob_detector.py:106`).

#### Уточнение 4.1 по итогам 4.0 (2026-09-29, решение владельца: claim check, обрезка item — позже)

**Порог:**
- `nbytes ≥ 8192` — массив едет ссылкой;
- `≤ 16384 Б` на всё data-сообщение — приёмка.

Оба значения — литералы в коде и тестах.

**Поверхности, которые меняются:**
- отправка: `strip_data_frame_on_send`;
- приём в пайплайне: `DataReceiver` → `restore_frame`;
- приём copy-out (GUI, `frontend/process.py:51`, `bridge_process.py`): `on_receive`;
- тикеты возврата: `pipeline_executor.py:278-286`;
- отпуск при вытеснении: `router_manager.py:836`.

**Контракт (приёмка tester'а, чёрный ящик):**
- **C1. Отправка.** Data-сообщение с **числовым** (`dtype.kind in "biufc"`) ndarray `ndim` 2–3 и `nbytes ≥ 8192` под любым ключом верхнего уровня `data` (включая `frame` и новый `foo`) после send-middleware:
  - `len(pickle.dumps(msg)) ≤ 16384`;
  - ни одного ndarray ≥ 8192 внутри.
- **C2. Мелочь.** ndarray `< 8192`, нечисловые (`<U`, object, `datetime64`), 1D и 4D+ массивы любого размера и не-массивы едут inline и не меняются (сужено 4.1-fix).
- **C3. Приём в пайплайне.** В item после приёма `item[key]` равен исходному массиву побайтно:
  - форма и dtype сохраняются (ADR-SRM-017: `(H, W)`, `(H, W, 1)`, `(H, W, 3)`);
  - это верно для двух крупных ключей разных формы и dtype в одном item одновременно;
  - потребитель — отдельный OS-процесс.
- **C4. Приём copy-out.** Через `on_receive` крупный не-`frame` ключ (`rendered_frame`) восстановлен в `msg["data"][key]`. Путь `frame` для GUI не регрессирует.
- **C5. Займы при loan-протоколе ON:**
  - каждая ссылка — отдельный заём;
  - после штатной обработки потребителем займов у владельца 0 по всем кольцам;
  - вытеснение сообщения из очереди отпускает все его ссылки;
  - мёртвый читатель (reclaim) снимает займы всех ключей.
- **C6. Fan-out.** Один item к двум целям: каждый ключ пишется в SHM один раз, оба получателя восстанавливают его.
- **C7. Независимость ключей.** Ключ `A`, меняющий форму (grow-only realloc), не пересоздаёт кольцо ключа `B`. Читатель `B` не теряет кадров из-за realloc у `A`.
- **C8. Прочие сообщения.** Не-data сообщения не трогаются.

**Живьё** (стадия 4, лид):
- `inspection_full`: 3 прогона, max байт сообщения в каждой data-очереди ≤ 16384;
- fps и `latency_ms` до/после;
- `letter_robot_sim`: 1 прогон;
- Windows. POSIX-стенд — после флипа `FW_SHM_OWNER_INCARNATION` (открытый вопрос владельцу).

**Out of scope:**
- обрезка item по проводам (`queue/backlog.md`);
- флип `FW_SHM_OWNER_INCARNATION`;
- вложенные массивы ниже верхнего уровня: контуры cv2 — не замерены, симулятор даёт 0 детекций;
- мусор `str(item)` в `DatabasePlugin`;
- крупные system-сообщения PM (до 56 КБ): не data, в приёмку не входят.

### Task 4.2 — Один формат ссылки и уникальные имена сегментов (добавлено 2026-09-29, по требованию владельца)

**Расширено по ревью 4.1 (F1 воспроизведён лидом и ревьюером).** Ссылка живёт один хоп:
- **а.** send-middleware пересылает только ссылки с `owner == self._owner`.
  Фильтр, а не пустой dict: при повторе fan-out после частичного сбоя нужны уже снятые ключи.
- **б.** Вместе со ссылками чистятся плоские поля `frame` и мета `_frame_is_view` / `_shm_view_*`.
- **в.** `_on_frame_evicted` отпускает только ссылки своего owner.
- **г.** Torn-ключ (`None`) не должен оставлять чужую ссылку: иначе маска читается из более новой записи слота, и кадр с маской расходятся.
- **д.** Release накапливать ПОСЛЕ `_send_results` (`pipeline_executor.py:223-236`): сейчас порванная view-страница копируется дальше незамеченной — риск на 60–100 fps.
- **е.** `on_evict` не вешать на copy-out получателей (GUI): `router_manager.py:767`, `release_evicted(reader="gui")` снимает чужую долю.
- **ж.** Число колец не ограничено: динамические ключи `crop_{i}` → coll сегментов на ключ.
  Решить: потолок или отказ ссылкой для ключей сверх N.

Пункты д и е — дефекты, которые были до 4.1; 4.1 распространил их на все ключи.

**Loan при F1 (rv_f1_loan.py):**
- вытеснение у p3 шлёт release в p1 за слот, который держит p2;
- следующая запись p1 идёт поверх живых данных p2.

Эти два дефекта проявляются только при loan ON (сейчас по умолчанию OFF), но **блокируют флип дефолтов флагов в 4.3**.

**Приёмка фазы:** CTO (Fable) проверяет архитектурные решения всей Ф4 после 4.3 (решение владельца 2026-09-29).

**Требование владельца (2026-09-29):**
- механизм стабильный и без костылей;
- универсальный;
- рассчитан на будущие камеры 60–100 fps.

**Что в 4.1 намеренно оставлено временным и закрывается здесь:**

1. **Два формата ссылки.**
   - Сейчас: `frame` едет плоскими полями `data`, остальные ключи — через `data["_shm_refs"][key]`.
   - Цель: один формат для всех ключей, включая `frame`.
   - Перевести на `_shm_refs` всех читателей плоских полей:
     - GUI: `frontend/process.py`, `bridge_process.py`;
     - `data_receiver`;
     - тикеты `pipeline_executor`;
     - `_on_frame_evicted`;
     - frame trace и логи.
   - После перевода плоские поля удаляются, двух путей не остаётся.
   - Работа 4.1 не выбрасывается: `_shm_refs` становится единственным форматом.

2. **Голые имена сегментов на POSIX.**
   - При `FW_SHM_OWNER_INCARNATION=0` все процессы получают одно имя.
   - С кольцами на ключ это уже не только шум при остановке, а порча данных: processor и renderer оба держат `output_frames__mask` → unlink соседа или чтение чужого кадра.
   - Нужно: имя сегмента уникально по (владелец, инкарнация) всегда — флип дефолта или безусловно.
   - Закрывает открытый вопрос в `OPEN_QUESTIONS.md` («SHM-кольца на POSIX: голое имя»).

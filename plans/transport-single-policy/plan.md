## Суть проблемы (подтверждено чтением кода)

Одна и та же `multiprocessing.Queue` доступна через две двери с разной политикой переполнения:

- **Дверь А** (`_deliver_by_targets` → `QueueRegistry.send_to_queue` → `remove_old_if_full`): QoS-политика (drop_oldest/never-drop), счётчики `data_evicted`/`system_evict_blocked`, хук `on_evict` (release-on-evict, ADR-RTR-010).
- **Дверь Б** (`_do_send` → `channels[N].send` → `QueueChannel.send`, `queue_channel.py:52-67`): голый `put(block=True, timeout=1.0)` — стойл потока-отправителя до 1 с, затем `{"status":"error"}` (фактически drop_newest), без QoS, без атрибутируемых счётчиков, без `on_evict`. Кадры уходят **синхронным** `router.send` с потока-исполнителя (`send_to_process` → `router_manager.send`), поэтому стойл бьёт по продьюсеру кадров напрямую.

Политика переполнения зависит от способа резолва адреса — произвольная связь двух независимых осей. Фикс LIVE-2 (`8b8a3c54`) на боевой раскладке kind-каналов не исполняется: `on_evict` навешивается только в `_deliver_by_targets`.

Дополнительно подтверждён (статикой) латентный баг `release_evicted`: `loan_ledger.py:191-208` декрементит refcount по **любому** имени reader'а — множества loan-aware потребителей в леджере нет. `_on_frame_evicted` (`router_manager.py:484-533`) шлёт release с `reader = владелец очереди`, а конверт кадра несёт SHM-координаты и для copy-out получателей (GUI): `frame_shm_middleware.py:462-463` проставляет `owner`/`shm_owner` во **все** исходящие кадровые конверты. Вытеснение из очереди GUI сняло бы чужую долю → досрочное освобождение слота. Сегодня ветка мертва для кадров, но **унификация политики её оживит** — фикс обязан идти раньше унификации.

## Порядок и обоснование

1. **Фаза 0 — доказательная база** (0.1, 0.3 в `main`). Счётчики дверей и строгие имена пробы есть; живой замер 0.2 переехал в Task 5.0 — его вопрос («какой дверью ходят кадры») теперь решается одним снятием `introspect_router_stats`, а гипотезы §8.4 про webcam-soak и loan-конверты сняты редизайном 4.7b (флагов `FW_SHM_*` нет, loan заморожен).
2. **Фаза 4 — крупные грузы и один режим пути кадра** (закрыта по 4.7d, 2026-10-02): claim check по размеру, ссылка на кадр с поколением, честные stale/torn, zero-copy как единственный режим, бюджет кадров в полёте (ADR-173), политика переполнения с маркером `not_inspected` (ADR-174). Формула приёмки сошлась на стенде с разностью 0.
3. **Фаза 5 — форма потери и контракт привода** (следующая, [`phase-5.md`](phase-5.md)). Ревью системы показало репродукциями, что механизмы верны, а форма — нет: задержка привода в потоке конвейера морит кадры голодом (50 из 300 обработано при задержке 20 мс на маркер), пачка маркеров по одному сообщению теряется на следующем хопе (134 из 2156 дошли), старт теряет 24–41 кадр без маркера, на main пять красных тестов. Порядок внутри фазы: факты (5.0) → разбор дизайна у CTO до кода (5.1) → три независимых механизма параллельно (5.2 привод, 5.3 запись о разрыве, 5.4 preroll) → стенд-гейт как скрипт (5.6) → транзит/loan, пропускная способность, две камеры (5.7–5.9) → одна дверь и GUI (5.10–5.11).
4. **Фаза 1 — одна политика** идёт после фазы 5 в сокращённой форме (Task 5.10) и только по факту 5.0(а): если data-трафик не ходит через kind-каналы, стойло двери Б латентно, и достаточно инвариант-теста «одна дверь» с ADR; если ходит — унификация в фазе 5. Task 1.3 (очередь 4) устарела: ADR-173 сделал очередь потолком памяти.
5. **Фаза 2 — продукт** разделена: экспорт счётчиков тракта в дерево телеметрии — часть стенд-гейта 5.6 (без него гейт читает сырой статус воркеров), индикатор в GUI — Task 5.11 после экспорта.
6. **Фаза 3 — типизированный ноль** остаётся после 5.10: признак «путь подключён» выводится из дескрипторов каналов, которых до 5.10 нет.

LIVE-3 (ханг main) в план не входит: не воспроизводится, ловится py-spy'ем оппортунистически. Хвосты §8.6 — backlog вне плана. 4.8b (выводы о мощности) — после 5.8, 4.8c (бенч из GUI) — решение владельца.

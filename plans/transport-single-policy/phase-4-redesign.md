**Составлено:** 2026-09-29, лид. Владелец: «сделай как полагается, без костылей и багов».
**Инвентарь кода:** два read-only прохода (Explore) по состоянию `25c47d15`: потребители плоских полей ссылки,
флаги `FW_SHM_*`, глубины очередей, наблюдаемость, потоки OpenCV, плагины с записью во вход.
qex в этот день недоступен (Ollama не запущена), источник истины — grep.

## Что видно в коде (факты для дизайна)

- **Дефект.** Проверка view после обработки (`pipeline_executor.py:222` → `ShmFrameReader.view_valid`)
  сравнивает поколение с тем, что было **в момент чтения** (`_shm_view_generation`), а не с поколением,
  которое записал писатель. Кадр, перезаписанный ещё до чтения, проходит проверку. Поколения в
  сообщении нет вовсе, а при `FW_SHM_SEQLOCK=0` (дефолт) нет и самого заголовка с поколением.
- Мета view (`_frame_is_view`, `_shm_view_*`) пишется в сам словарь ссылки и через `dict(data)` в
  `data_receiver.py:286` едет дальше по цепочке — ссылка чужого хопа доживает до следующего процесса.
- Вторая дыра — окно между проверкой view (`:222`) и копией view в своё кольцо (`_send_results` →
  send-middleware, `:236`): перезапись в этом окне уходит дальше как «целый» кадр с чётным поколением.
- Очереди: все data-очереди процессов — `DEFAULT_QUEUES` data=50 (`process_launch_config.py:14-32`),
  рецепт их не задаёт. Внутри процесса ещё `chain_queue` с отсевом по `chain_max_lag_items`
  (`data_receiver.py:139`). QoS `history_depth` на размер очередей не влияет вовсе.
- Глубина кольца из рецепта (`frame_ring_depth`, `buffer_slots`) читается только под `FW_QOS_PROFILES`.
- Наблюдаемость: CPU процесса не считает никто; байтов SHM нет; ёмкость очередей не видна;
  у `FramePacer` нет счётчиков; время плагина есть только в трассировке под env (по умолчанию выкл.).
- `cv2.setNumThreads` не вызывается нигде.
- Во вход на месте рисует только `blob_detector` (`plugin.py:97-104`, `cv2.drawContours(frame)`). В
  `inspection_full` его спасает порядок цепочки (перед ним `color_mask` подменяет `frame`).

**Отступление, решение лида:** формат ссылки делается вместе с поколением (в 4.4), а не отдельно в
шаге 2. Поколение обязано жить в ссылке; вписать его в оба старых формата (плоские поля `frame` и
`_shm_refs`), а через задачу переписать всех потребителей ещё раз — двойная миграция тех же строк.
Базовая линия «до» уже измерена независимо (пиксельная метка Fable, 0 из 1798), так что честные
счётчики нужны для замера **после** — они и появляются первыми.

**Что не снимается вместе с флагами пути кадра:** `FW_SHM_PREFIX_CLEANUP` — это политика развёртывания
(«один бэкенд на машине»), а не режим пути кадра. `FW_SHM_LOAN_PROTOCOL` — заморожен (см. 4.7).

### Task 4.4 — Ссылка указывает на кадр, а не на ячейку
**Level:** Senior+ · **Assignee:** teamlead · **Layer:** framework + prototype
**Goal:** читатель никогда не отдаёт плагину чужой кадр; каждый отброшенный кадр виден в счётчике.
**Files:** `router_module/middleware/frame_shm_middleware.py`,
`shared_resources_module/memory/{reader/shm_frame_reader.py, format/buffer.py, core/manager.py}`,
`process_module/generic/{pipeline_executor.py, data_receiver.py}`, `router_module/core/router_manager.py`
(`_on_frame_evicted`), `frontend_module/bridge/remote_frame_source.py`, `config_module/feature_flags.py`,
`process_module/io/process_io.py`.

**Дизайн (решено лидом):**
1. **Один формат для всех ключей, включая `frame`:** `data["_shm_refs"][key] = {"owner", "slot", "idx",
   "gen", "name"}` — ровно пять полей. Плоские `owner`/`shm_owner`/`shm_name`/`shm_index`/
   `shm_actual_name`/`shm_seqlock` и `width`/`height` из `on_send` удаляются. Путь `on_send`/`on_receive`
   (wire, GUI) — тот же формат.
2. **`gen`** — чётное поколение, которое поставила **эта** запись (возвращается из пути записи, а не
   перечитывается). Seqlock-заголовок у слотов **всегда**: флаг `FW_SHM_SEQLOCK` удаляется из реестра.
3. **Читатель сверяет с `ref["gen"]`:** поколение слота до чтения ≠ `gen` → stale-drop
   (`frame_stale_drops` +1, `None`); после копии ≠ `gen` → torn-drop (`frame_torn_reads` +1, `None`).
   Проверка view после обработки сравнивает с `ref["gen"]`, а не с поколением момента чтения.
   Сверка — только по имени сегмента из ссылки; попытка «сначала через `mm.read_images`» для чужого
   владельца уходит (в модели «один хоп» процесс свои выходы не читает).
4. **Мета view не пишется в ссылку.** Ссылка на проводе — только пять полей; всё, что читателю нужно
   для проверки, уже в ней (`name`, `gen`).
5. **Один хоп.** Send-middleware кладёт в исходящее сообщение только ссылки с `owner == self`; входные
   ссылки не пересылаются никогда (закрывает 4.2 а, б, г). Повтор fan-out распознаётся по «в
   `_shm_refs` есть ссылка с моим owner», а не по наличию ключа `shm_name` (находка Fable).
6. **Проверка после копии (дверь отправки).** После записи массивов item'а в своё кольцо send-middleware
   сверяет все входные ссылки, прочитанные как view, с их `gen`. Разошлось → сообщение не уходит ни к
   одной цели, `frame_stale_drops` +1 один раз на item (не на цель); повтор fan-out того же item тоже
   дропается. Проверка executor'а после цепочки остаётся (терминальные процессы ничего не шлют, а
   решение по устаревшим пикселям не должно уйти в побочные эффекты) — это один предикат в двух точках.
7. **Loan** (заморожен, выкл.) переводится на новые поля тикета (`slot`/`idx`/`gen`) без изменения
   поведения — его тесты остаются зелёными.

**Acceptance (tester, чёрный ящик, до кода, в worktree на `HEAD` до реализации):**
- [ ] A1. Слот перезаписан после отправки ссылки и до чтения → читатель возвращает `None`,
      `frame_stale_drops` = 1, плагину не приходит массив чужой записи. Для копии и для view, для
      `frame` и для произвольного ключа `foo`.
- [ ] A2. Перезапись во время копии → `None`, `frame_torn_reads` = 1.
- [ ] A3. View прочитан целым, слот перезаписан во время обработки → батч не отправлен,
      `frame_stale_drops` = 1.
- [ ] A4. Перезапись входного слота между концом цепочки и записью в своё кольцо → сообщение не ушло ни
      к одной из двух целей, `frame_stale_drops` = 1.
- [ ] A5. Во всём исходящем data-сообщении нет ни одного ключа из списка: `shm_name`, `shm_index`,
      `shm_actual_name`, `shm_owner`, `shm_seqlock`, `_frame_is_view`, `_shm_view_name`,
      `_shm_view_generation`, `_shm_generation`; у каждой ссылки в `_shm_refs` набор ключей ровно
      `{"owner", "slot", "idx", "gen", "name"}` и `owner` = отправитель.
- [ ] A6. Цепочка из трёх OS-процессов A→B→C: C получает кадр B (пиксели равны записанным B), ссылки A
      до C не доходят.
- [ ] A7. Copy-out (`on_receive`, GUI) восстанавливает `frame` и крупный ключ; stale считается так же.
- [ ] A8. `FW_SHM_SEQLOCK` нет в реестре (`resolve` → `KeyError`); слот без флага имеет поколение.
- [ ] Контракт 4.1 (C1–C8) остаётся в силе в новом формате: tester-файл `test_claim_check_any_key.py`
      переводится на `_shm_refs["frame"]`.
- [ ] **Живьём (лид):** стенд 100 fps 1080p (`if_100_1080`, 30 с) с пиксельной меткой Fable: чужих
      кадров, дошедших до плагина, **0**; отброшенных = `frame_stale_drops + frame_torn_reads` (±1 %).
      Числа до 4.7 будут большими — очередь 50 при кольце 3; это честный счёт, а не цель.

**Out of scope:** глубины кольца и очередей, кэш handles, zero-copy по умолчанию, снятие остальных
флагов (4.7); B-7.

## Открыто и ненадёжно в самой спецификации

- Дефолт `cv_threads` = 2 и глубина 8 — оценки CTO, не замеры этой машины; подтверждаются в 4.6 и 4.7.
- Разбивка «data-очередь 4 + `chain_max_lag_items` 2» — моя; если `chain_queue` на деле не держит view
  дольше одного батча, её доля пересчитывается по замеру, неравенство остаётся.
- CPU по потокам «по запросу» (есть у CTO) отложен: нет потребителя, пока не понадобится.
- POSIX-стенда нет; поведение имён на POSIX проверяется тестом логики имени, не живьём.

## Фаза 2 — Продукт: потеря кадров видима

**Гейт выхода:** оператор видит потерю кадров без чтения счётчиков роутера.

### Task 2.1 — Drop-на-источнике в телеметрию и GUI
**Level:** Middle+ (Sonnet)
**Assignee:** developer
**Goal:** `frame_loan_exhausted` (и `data_evicted` после Фазы 1) публикуются как скорость потери (кадров/с) в штатную телеметрию и отображаются в GUI процесса.
**Files:** publisher-плоскость телеметрии процесса (GATED_METRICS, ADR-PM-018), виджет карточки процесса/пайплайна в `multiprocess_prototype`
**Steps:**
1. Добавить метрику потери кадров в publisher-gate источника (частота — существующим механизмом tick).
2. GUI: индикатор в существующей карточке (число + подсветка при >0 в steady-state); Dict at Boundary.
3. qt-смоук: `QT_MCP_PROBE=1`, проверить наличие и обновление индикатора на webcam_sketch под нагрузкой (человек в кадре — значение растёт, пустая сцена — падает; дозозависимость уже показана эмпирикой §3).
**Acceptance criteria:**
- [ ] на живом прогоне индикатор показывает ~1-5 кадров/с в зависимости от сцены
- [ ] метрика подчиняется publisher-gate (выключаема, cap-aware)
**Out of scope:** новые вкладки/дашборды; алертинг.
**Проверка:** живой прогон + qt-mcp смоук (pytest-qt сборку не доказывает).

## Фаза 3 — backend_ctl: типизированный ноль (минимальный срез)

**Гейт выхода:** вердикт пробы отличает «событий не было» от «путь не подключён» для всех LEAK-ключей.

### Task 3.1 — Провенанс вердиктных счётчиков
**Level:** Middle+ (Sonnet)
**Assignee:** developer (ревью teamlead)
**Goal:** каждый LEAK-ключ в вердикте пробы несёт признак «путь подключён»: счётчик существует у сервера И его инкрементный путь достижим на текущей раскладке. После Фазы 1 признак выводится из **живого реестра каналов**, а не из эвристик по флагам: дескрипторы Task 1.2 уже едут в `introspect_router_stats.channels[*].descriptor` бесплатно.
**Files:** `backend_ctl/probes/g7_soak_probe.py`; `introspect_router_stats` расширять НЕ требуется (дескрипторы и `sent_via_channel_policy` уже в ответе после Task 1.2; при нехватке — точечно `_frame_loan_active` флагом раскладки)
**Steps:**
1. Расширить снимок пробы: рядом с каждым LEAK-ключом — `provenance: {present, path_active}`. Для `queue_data_evicted`/`frame_loans_released_on_evict`: `path_active` = есть ≥1 канал с `descriptor.queue_type == "data"` И (политика ON: `sent_via_channel_policy` присутствует) ИЛИ трафик идёт targets-дверью (`sent_via_targets` > 0). Из живого introspect, не из предположений о конфиге.
2. Ноль с `path_active=false` → вердикт не CLEAN, а `BLIND_SPOT` с перечислением слепых ключей.
**Acceptance criteria:**
- [ ] тест: раскладка «kind ON, политика OFF» (симуляция снимка) даёт `BLIND_SPOT` по `queue_data_evicted` — т.е. сегодняшняя ситуация была бы поймана автоматически
- [ ] тест: раскладка после Фазы 1 (дескрипторы + политика ON) даёт `path_active=true` без специальных флагов
**Out of scope:** полная программа провенанса всех наблюдаемых, слепые плоскости loguru/logger (отдельный план), любые новые MCP-инструменты.
**Проверка:** статика + тесты; живой смоук совместно с прогоном 1.3.

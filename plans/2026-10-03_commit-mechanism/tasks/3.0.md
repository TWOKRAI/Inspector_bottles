DESIGN (decided by the lead — you type it, you do not derive it):
  1. Грамматика id (только ASCII), строка-эталон:
       `[A-Z]{0,3}[0-9]{1,3}[a-z]?(?:\.[0-9]+[a-z]?)*(?:-[a-z0-9]+)*`
     Словами: необязательный префикс трека из 1–3 латинских заглавных; число из 1–3 цифр с необязательной строчной
     буквой; ноль и больше сегментов «точка, число, одна необязательная строчная буква»; ноль и больше суффиксов
     «дефис, строчные и цифры».
     Решения внутри грамматики:
     - одна буква на сегмент (раньше `[a-z]*`): `1.3ab` больше не id. В корпусе таких нет (замер r1: 0);
     - первое число — до трёх цифр: дата `2026-09-25` не id (раньше валидатор её отвергал, расширение без этого
       ограничения стало бы принимать);
     - префикс до трёх букв (`ABC1`) — как у валидатора сейчас.
  2. Трейлер `Task:` = `<slug>#<ID>`, slug — как сейчас (`[a-z0-9][a-z0-9-]*`), `re.ASCII`, fullmatch.
  3. Носители строки-эталона (каждый модуль автономен — сид копируется в чужие репо, строку не импортируют):
     - обе копии `validate_commit.py`: новая константа `TASK_ID_PATTERN`; `TASK_VALUE_RE` строится из неё;
     - `plans_progress.py`: `ID_PATTERN` (имя не меняется);
     - обе копии `plans_ledger.py`: `_TASK_ID` (имя не меняется; атомарная группа — как есть); `_TASK_ID_END` →
       `(?=[\s:~*,;]|\.(?!\w)|$)`, как в п. 4 (иначе ledger читает `T2.K` как `T2`, `5.10.g` как `5.10`). Замер r2:
       `contract_fingerprint` 0 расхождений из 493 файлов, `### Task 1.4. x` → `['1.4']` как прежде.
  4. Конец id в `plans_progress`: `_ID_END = (?=[\s:~*,;]|\.(?!\w)|$)` (было `\.(?!\d)`). Тогда `T2.K` и `5.10.g`
     не усекаются до `T2` и `5.10`, а дают находку `TASK_ID_UNPARSED`; `Task 1.4.` в конце фразы — по-прежнему `1.4`.
     Замер r1: задачи 865/1238 без изменений, находки 101 → 101 (ложная `DUP_HEADING 5.10` в
     `plans/observability-unified-routing.md` уходит, приходит `TASK_ID_UNPARSED 5.10.g`).
  5. Id вне грамматики — `TASK_ID_UNPARSED` в `plans_progress` (уже есть). Планы массово не переписываем; правило
     переименования при касании плана: `2в.2` → `2v.2`, `Т.1` → `T1`, `T2.K` → `T2-k` (прецедент
     `plans/robot-protocol-v2/plan.md`: `T2-k`, `T2-j2`), `5.10.f` → `5.10f`, `D.3` → `D3`. В таблицах-реестрах id не
     переименовываем (`TABLE_ID_RE` — вне задачи).
  6. `(после 1.2.3)` в `plans_progress` теперь читается как зависимость `1.2.3`; файл `tasks/1.2.3.md` — файл задачи.
  7. Тесты — контракт и паритет:
     - контракт: каждая из пяти строк (две копии валидатора, `plans_progress`, две копии `plans_ledger`) равна
       литералу из п. 1, записанному в тесте. Модуль грузится через `importlib` по пути, не регуляркой по исходнику
       (копии отформатированы разными форматтерами);
     - паритет по одной таблице id: валидатор принимает `x#<id>` ⇔ `plans_progress` читает `- Task <id>: t [PENDING]`
       как задачу с этим id ⇔ `plans_ledger.extract_task_ids("### Task <id> — t") == [<id>]`; валидатор отвергает ⇒
       `TASK_ID_UNPARSED` в `plans_progress` и `extract_task_ids(...) == []` в ledger.

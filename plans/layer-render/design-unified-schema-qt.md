## 3. Правило: каждая настройка `imaging` — схема на одной базе

**Одна база `ImagingSchema(SchemaBase)` с `extra="forbid", frozen=True`.** Наследник `SchemaBase` без своей настройки
принимает лишний ключ молча (опыт CTO: `typo_key` принят; с запретом — отвергнут). Поэтому запрет ставит база, а не
каждая схема. Тест обходит все схемы `Services/imaging` и конфиги её плагинов и проверяет запрет на каждом уровне
вложенности. Замер CTO: создание объекта 1,1 мкс против 0,65 у `BaseModel`.

Схемы (с `FieldMeta`: русские подписи, единицы, диапазоны, шаг): пресет v2; слой; эффект — каждый вид своей схемой; фон —
каждый вид своей схемой; тень; место и разброс; секция `train` (вырез, метка, симметрия); каталог; запись набора (сплиты,
формат меток); стили и правила `draw`; конфиг плагина `scene_source` (`PluginConfig`). Через процессы — только словари.
Ручного описания формы рядом нет: форму строит код из `FieldMeta`.

**Одно исключение, названное по имени: `ClassMeta`** (`lr/metadata.py:38`). `meta.yaml` — документ с данными
пользователя, а не настройка: неизвестные ключи наследуются по дереву классов и уходят в `classes.json`
(`dg/core/engine.py:88`). `ClassMeta` не наследует `ImagingSchema`, `extra="allow"` записан явно. Тест-обход держит список
исключений из одного имени с причиной; второе имя — только решением CTO. Чтобы опечатка в известном ключе (`symetry`)
не прошла тихо, загрузчик каталога один раз пишет неизвестные ключи в журнал, паспорт набора их перечисляет; не отвергает.

**Пределы поля объявлены один раз** — в `FieldMeta(min, max)`; схема отвергает значение при создании и при записи.

**Не переводятся:** `GeneratorConfig`, `AugmentConfig` и их части — заморожены вместе с `DatasetEngine`. Конфиги
`ml_train` — потребитель, его план. `SymmetryConfig` лежит в замороженном `dg/core/config.py:222`, а зовёт его живой
генератор (`layer_scene.py:36`): выносится в `imaging` схемой.

### 3.1 Что проверить при переводе класса на `SchemaBase`

| Отличие | Риск | Решение |
|---|---|---|

| min/max из `FieldMeta` проверяются (`schema_base.py:63`) | новые пределы отвергнут старые файлы | пределы переносятся как есть из нынешних `Field(ge/le)`, а сами `Field(ge/le)` убираются: объявление одно |

| `ScenePreset.train` — непрозрачный словарь (`lr/preset.py:57`), ограда путей читает его «осторожно» (`lr/preview.py:172-179`) | костыль | секция `train` — типизированная схема (генератор уже в `imaging/layers`) |
| `SchemaMixin.apply_values` меняет объект | пресет frozen | сессия правки держит замороженный `ScenePreset`; операция возвращает новый; история — список пресетов; словарь появляется только в `preset.commit` |

### 3.2 Порядок эффектов, реестр видов, версии

- **Порядок эффектов — порядок списка в файле.** Так уже работает `apply_effects`. Запуск CTO: `[glare, noise, jpeg]`
  против обратного при одном зерне — разница до 133 уровней; повтор эффекта принят.
- **Схема проверяет только ступени** `scene` → `optics` → `sensor` → `codec`: ступень по списку не убывает, ошибка называет
  пару. Внутри ступени порядок свободный и значимый. Повтор вида запрещён, пока вид сам его не разрешит.
- **Кто пишет файл** (конвертер, миграция, место вставки в форме), берёт канонический порядок — нынешний порядок `EFFECTS`,
  записанный литералом (состав и тесты — [plan-acceptance](plan-acceptance.md)). Реестр видов — словарь, порядок
  регистрации ничего не задаёт; новый вид получает явное место в литерале.
- **Реестр закрыт внутри `imaging`** (ЛР-40): вид регистрирует тот же пакет, что объявляет схему. Иначе один пресет годен
  в одном процессе и негоден в другом. Ошибка перечисляет зарегистрированные виды.
- **Версии** (ЛР-39): поле `schema_version` и упорядоченный список чистых шагов «словарь → словарь» до проверки схемой.
  Файл на диске меняет только явное сохранение. Первый клиент — пресет v1→v2.
- **Конвертер ЛР-30** переводит другой формат (`GeneratorConfig`), а не старую версию той же схемы: разовый инструмент.

## 5. Вес импорта

В процессе показа (замер дизайна): `import Plugins.render.overlay_draw.plugin` уже грузит pydantic и
`data_schema_module` (1266 модулей), `import Services.layer_render` после него — +0,02–0,03 с. Поэтому правило «`draw` не
грузит pydantic» снято; остаётся направление `draw ↛ layers` (уровень и радиус тестов, правило sentrux).

**Но это замер там, где цена уже оплачена.** Чистый процесс — каждый воркер DataLoader на Windows и каждый CLI. Замер
CTO в чистом процессе: `data_schema_module` — 0,78 с и 1113 модулей; `layer_render` сегодня — 0,34–0,42 с и 509; pydantic
— 0,12 с. Приёмка ЛР-38: время импорта `Services.imaging.layers` в чистом процессе до и после; прирост больше 0,3 с —
чинить `data_schema_module` вперёд.

### 6.2 Решение

- Вся логика правки — **модель редактора без UI** `imaging/layers/editing.py` (ЛР-35). Внутри процесса — схемы, не
  словари: сессия держит замороженный `ScenePreset`, операция возвращает новый, история — список пресетов, неверная правка
  падает сразу. Словарь появляется только в `preset.commit`. Тесты — без Qt и без браузера. Модель зовёт клиент Qt в своём
  процессе; авторитетная проверка и запись — `preset.commit` (`scene_source`), превью и раскладка — процесс `layers`.
- Форма — из схемы (ЛР-41). Канва — `QGraphicsView` (такие классы уже есть только у графа пайплайна,
  `multiprocess_prototype/frontend/widgets/tabs/pipeline/graph/`).
- `pult_web`: редактор слоёв **заморожен** — без новых функций; правки только по дефектам; после паритета Qt
  (ЛР-17) — заморожен окончательно, не удаляется.

### 6.3 Блок И3 — не проверено

И3 = gui-constructor 2.1 (оболочка) → 2.2 → gui-service 1.4 → 2.4 (`plans/queue/ORDER.md:228`). Задача Qt-редактора 1.2b
ждёт И3 (`plans/line-sim-layer-editor/phase-1-qt.md:36`): ей нужна оболочка вкладок и второе подключение к бэкенду. Пакет
`sim.*` делает gui-constructor 3.3 — это И5 (`ORDER.md:230`). В нынешнем Qt-фронте вкладки симулятора нет; вкладки есть:
displays, pipeline, plugins, processes, recipes, services, settings.

**«И3 — порядок, а не преграда» не доказано** (CTO). Довод против: в `apps/line_sim/pipeline.yaml` нет процесса Qt.
Сначала проба на полдня.

# C-88 — `outcome` стопа потомка `recog` пуст вместо `exited`

Заведено 2026-11-11 лидом приёмки α по решению владельца: «предел драйвера» как PASS не принимается, чинить (запись 19 `amendments.md`). Владелец кода — полоса Ф (`plans/lifecycle-stop-ownership.md`, ORDER #5; код `multiprocess_framework/modules/process_manager_module`). Лид приёмки код не пишет.

## Проблема
Вход: `system_shutdown` прототипа `letter_robot_sim` после S8. Наблюдение в трёх прогонах из трёх: 9 из 10 детей `exited`, у `recog` — `None`. PM ушёл, порт 8765 свободен, процессов не осталось. `design.md` §2.7 с Task 1.10 требует `exited` у каждого ребёнка. Контракт: `process_manager_module/DECISIONS.md` «Дополнение (Task 1.10)» D2–D4: `ChildProcessStop.outcomes()`, `ProcessRegistry.stop_outcome(name)`.

## Шаг 0 — диагноз (ДО кода; `investigator` или автор, не гадать)
Выяснить, почему для `recog` нет исхода, а для остальных есть. Проверить по порядку, каждый пункт — число или «не вклад»:
1. Есть ли у `recog` запись в `outcomes()` на момент ответа и не затёрта ли она сбросом (`reset_call_stop_outcomes`, `add_process` сбрасывает `stop_outcome`).
2. Отличие `recog` от других детей: самый долгий выход (ML, коллектор 0,25 с), потомок потомка, имя процесса, порядок в плане остановки.
3. Гонка между чтением итога и завершением остановки `recog` (поток стопа ещё не записал итог).
4. Причина в драйвере `backend_ctl` / `system_shutdown` (читает итог раньше времени) или в `ProcessRegistry`.
Диагноз — записью в отчёт с вход → наблюдение; от него зависит, чьё это исправление (PM, реестр, драйвер).

## DESIGN (после диагноза)
- Исход стопа каждого ребёнка = честный `exited | terminated | killed` либо явный, объяснённый признак «не успел» — но НЕ `None` молча. Если итог ещё неизвестен к моменту ответа, ответ ждёт его в пределах окна стопа ребёнка (то же окно, что в Task 1.9, `test_per_child_stop_window_*`), а не отдаёт пусто.
- Не ослаблять §2.7 и не смягчать проверку скрипта `scripts/alpha_sim` («предел драйвера» убрать только когда `recog` отдаёт `exited` — правка скрипта в полосе владельца скрипта).
- Сбой одного ребёнка не валит остальных (принцип 5 проекта).

## REDS (слепой `tester`, критерии без чтения кода)
1. `system_shutdown` дерева из ≥ 10 детей, один из них с долгим выходом (0,5 с): у КАЖДОГО ребёнка `outcome` одно из трёх, `None` нет.
2. Ребёнок, ушедший по SIGTERM после окна, → `terminated`; не ушедший → `killed`; ушедший сам → `exited`.
3. Повторный стоп уже мёртвого — исход прошлого стопа не затирается `None`.
4. Одна проверка с настоящим деревом `ProcessManagerProcess` и реальными дочерними процессами (не двойниками).

Break-injection (предсказания ДО прогона): убрать ожидание итога до окна → RED 1; затирание исхода при повторном стопе → RED 3.

## Приёмка живая
`scripts/alpha_sim` S9 три раза с холодного старта: у всех 10 детей `exited`, включая `recog`; `None` нет. Процессов дерева нет, порт свободен — проверять не по именам, а по `psutil` потомков PM до стопа и после.

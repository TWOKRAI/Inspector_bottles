## DESIGN (decided by the lead)

  1. `recipes/save.py`: приватная `_validate_display_refs(after: dict) -> None` — множество `ids` из `after.get("displays")` (список mapping с ключом `id`;
     не список -> пустое), для каждой привязки из `(after.get("blueprint") or {}).get("displays")` (элемент mapping с `display_id`) — если `display_id`
     не в `ids`: собрать сообщение «blueprint.displays: ссылка на несуществующий display_id '<id>'»; непустой список -> `RecipeValidationError(messages)`.
  2. Вызов в `save_editor_topology_to_recipe` сразу после `validate_recipe_blueprint(...)` (`save.py:254`), до `save_raw` — вне `try/except ValidationError`
     (само бросает `RecipeValidationError`). Больше нигде не вызывать.
  3. Тот же тип и тот же текст, что у валидатора домена («Ссылка на несуществующий display_id»), здесь не воспроизводить дословно; важно имя `display_id` в сообщении.

## ACCEPTANCE (поведение для слепого тестера)

  A. Save, где привязка ссылается на отсутствующий `display_id`: `RecipeValidationError`, в сообщении есть `display_id`; байты файла не изменились; `save_raw` не вызван.
  B. Save с корректными привязками (все `display_id` определены) и Save без привязок — как раньше (байты без правок не меняются на фикстуре A).
  C. Сценарий ревью: база захвачена; `DisplayCatalogFromRecipe.register("probe_disp")`; редактор добавляет несохранённую привязку к `probe_disp`;
     `unregister("probe_disp")` (в файле привязки нет); Save редактора -> `RecipeValidationError`, `store.read(slug)` читается, файл цел.
  D. Save, где привязка есть, а top-level `displays` отсутствует вовсе -> `RecipeValidationError`.

## INJECT (прогнозы до прогона)

  - `_validate_display_refs` не вызывается -> A, C, D
  - проверка идёт по `blueprint.displays` файла `doc`, а не `after` -> C
  - множество `ids` берётся из привязок -> A, C, D
  - вызов перенесён после `save_raw` -> A, C, D (байты изменены)
  - ложный отказ на корректных привязках (инверсия условия) -> B

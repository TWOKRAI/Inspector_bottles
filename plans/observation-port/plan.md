## 1. Контекст: зачем и почему именно так

Плоскость уровней телеметрии (~2 600 строк механизма) завела шесть уникальных машин — каталог
владения, парный ключ, арбитр owner==publisher, поимённое снятие с запасом переутверждений,
голос про самозванца — которых нет ни у одного из 27 модулей. Четыре живых дефекта одного корня
(A1, A2, B, отмена снятия чужой публикацией) — следствие того, что решение «чей это лист»
принимается в трёх местах по трём правилам. Разбор — в досье S-8.

Решение владельца (2026-08-19, дословно): «Тоже самое как сделано для общения — router_manager,
command_manager, channel_routing_module и тп. Использовать готовые модули и инструменты по
максимуму. …сделать один порт наблюдений». Дополнительное требование: «система должна быть легко
масштабируемой и управляемой» — в плане это проверяемые критерии приёмки (§3), не лозунг.

**Главный принцип конструкции: владение = путь.** Каждый писатель публикует только в своё
поддерево — как воркеры уже публикуют в `workers.<w>.*`, а health-репортер подписывает записи
своим контекстом (`process_module/health/state.py:422-431`). Спорить за имя становится
синтаксически невозможно, и вся машина арбитража удаляется, а не чинится.

**Порт — не новый модуль.** Наблюдаемость — ось `channel_routing_module` (база) + три
менеджера-наследника (`LoggerManager`, `ErrorManager` — `error_module/core/error_manager.py:178`,
`StatsManager` — `statistics_module/core/stats_manager.py:110`). Порт — четвёртый брат на той же
базе и четвёртый слот `ObservableMixin` (`base_manager/mixins/observable_mixin.py:46`), живёт на
оси метрик — в `statistics_module` (правило карты ответственности §3: «это уже чья-то ось —
расширяй тот модуль»).

## 2. Целевая конструкция

```
processes.<proc>.state.fps            ← пишет ТОЛЬКО heartbeat (агрегат фреймворка)
processes.<proc>.state.latency_ms     ← пишет ТОЛЬКО heartbeat
processes.<proc>.state.shm.*          ← пишет ТОЛЬКО heartbeat
processes.<proc>.state.plugins.<plugin>.<метрика>   ← пишет ТОЛЬКО этот плагин (через порт)
processes.<proc>.workers.<w>.*        ← как сегодня (уже поддерево на писателя)
```

- Один писатель на поддерево — по построению, без арбитра.
- Публикация — по-прежнему ОДНИМ merge за тик (Р3.5-12 сохраняется).
- Снятие ушедшего писателя — удаление его поддерева дорогой `state.delete`
  (`state_store_module/manager/state_store_manager.py:281, 624`; `TreeStore.delete` —
  `core/tree_store.py:323`), а не поимённые `None`-надгробия.
- Политика (что и как часто едет) — glob-выражением по дереву, движком подписок стора
  (`state_store_module/core/subscription_manager.py:50, 66`).
- **Пульт порта = пульт логирования** (требование владельца, дословно: «управление должно быть
  похоже как с логированием, ручки и контроль»): те же четыре слоя L0–L3 (ключи — в секцию
  `observability:`, `ObservabilityConfig` — `process_module/configs/observability_config.py:318`),
  та же семантика пересборки из источников, та же единственная точка раскладки
  `apply_observability_layers` (`process_module/managers/observability_reload.py:676`), тот же
  словарь команд (`config.reload`, `introspect.observability`, `observability.tail.*`,
  `observability.sink.*` — регистрация в `process_module/commands/builtin_commands.py`), то же
  доказательство применения (`config_reload_verified`, вердикты `:262`). Пятая дверь конфига и
  новый словарь команд не заводятся. Детали — Ф4.
- Читатель GUI один — `telemetry_readmodel_module` (ADR-136), единственная точка миграции путей.

**Целевой узор (решение владельца 2026-08-19, поэтому Ф5 обязательна).** У СТРОК во фреймворке
один писатель: `LoggerCore`; `ErrorManager` — его **наследник**
(`error_module/core/error_manager.py:178`), второй род записи маршрутизируется ДАННЫМИ
(`_level_to_channel`, один `_route()`) и второй машины не заводит; `get_std_logger` — **вид**
поверх единственного писателя (116 вызовов в 112 файлах). У ЧИСЕЛ же `StatsManager` — **брат по
базе, а не наследник писателя** (`statistics_module/core/stats_manager.py:110`) — структурная
причина, почему плоскость чисел разъехалась на две дороги, а плоскость строк — нет. Целевое
состояние плана: **порт для чисел — то же, чем `LoggerCore` является для строк: единственный
писатель; агрегация — вид поверх него, как `get_std_logger`.** «Три пишущих дороги остаются
после Ф4» — неприемлемый исход (Ф5, обязательная).

Что исчезает целиком (полный список с тестами — §9): арбитр owner==publisher, парный ключ,
каталожное владение с `ValueError`, поимённое снятие с запасом, голос про самозванца; в Ф5 —
вторая точка входа записи чисел.

## 3. Правила приёмки для ВСЕХ фаз (уроки S-8 — обязательны, не пожелания)

Каждая задача с кодом проходит конвейер конвенции проекта (`.claude/CLAUDE.md`, «Task launch
convention»), с дополнениями из разбора S-8:

1. **Независимый тестер — всегда, от критериев, до авторских тестов.** Запрещённые пути называются
   поимённо в каждой фазе (см. блок «Тестеру запрещено» в фазе).
2. **Инъекции ДВУХ родов, предсказания до прогона:**
   - род 1 — инверсия каждого заявленного свойства;
   - род 2 — не выводимые из критериев: «механизма нет вовсе» (сборщик/порт возвращает пусто),
     «механизм пропускает всё», «дедуп/частота снята», «харнесс отключён» (fixture без merge).
   Род 2 генерирует НЕ автор критериев (ревьюер или второй агент по докстрингу механизма, вслепую
   от критериев), ДО прогона тестера.
3. **Отрицательный критерий обязан иметь якорь существования в ТОМ ЖЕ тесте** («при X лист ЕСТЬ и
   равен литералу; при Y листа НЕТ»). Тест, у которого все assert — отрицания, не принимается.
4. **Кванторный критерий («ровно один раз», «не чаще») — минимум два тика.**
5. **Тестер сдаёт раздел «недостижимо на стенде»** — какие боевые режимы его харнес не включает
   (гейт, IPC, троттл). Пустой раздел у стенда на фейках — сам по себе находка.
6. Живой стенд — числами через `backend_ctl`, оффскрин; ревью синхронно, с воспроизведениями.

Критерии масштабируемости и управляемости (требование владельца, проверяются в Ф1/Ф3/Ф4):

- **М1.** Добавление нового плагина с метрикой = ноль правок механизма и ноль правок конфига
  (доказательство: `Plugins/sources/capture/plugin.py` в Ф1 не меняется вовсе — см. Task 1.3).
- **М2.** Всё опубликованное обнаруживается обходом одного дерева (`state_get_subtree` по
  `processes.<proc>.state` возвращает все листья, включая только что добавленного писателя).
- **М3.** Любой срез выбирается одним glob-выражением (одно правило
  `processes.*.state.plugins.*.fps` меняет частоту у всех fps всех плагинов — Ф4).
- **М4 (пульт).** Оператор, умеющий управлять логированием, управляет портом теми же движениями
  и теми же командами, без нового словаря. Проверяемо: операторская сессия на живом стенде —
  (а) увидеть действующую политику порта, (б) поменять её, (в) убедиться, что подействовало,
  (г) хвост значений — выполняется командами существующего словаря (`introspect.observability`,
  `config.reload` / `telemetry.reconfigure`, `config_reload_verified`, `observability.tail.*`);
  новых имён команд верхнего уровня — ноль; транскрипт сессии прикладывается к ревью Ф4.
- **М5 (один механизм).** У чисел один писатель: заглуши порт — молчат И уровни в дереве, И
  агрегаты окон (пара-контроль: живой порт даёт оба вида с литералами). Проверяется в Ф5
  поведенчески, не grep'ом.
  **На стенде «агрегаты молчат» меряется по ВСЕМ окнам процесса, не по окну тестового писателя**
  (правка по второму проходу ревью). Иначе критерий зелен при живой третьей дороге: слот миксина
  (`observable_mixin.py:186-190`, 42 боевых вызова) сыплет числа от самого фреймворка, и окно
  тест-писателя о них ничего не знает. Живой съём — `backend_ctl` до/после заглушки, обе половины
  парой чисел.

## §11. Риски и точки невозврата

1. **Merge Ф6 задерживается** → Ф1 не стартует (база — `main`). Митигация: Ф0 минимален (4 точки),
   не тянет пересборку. Если Ф6 застрянет надолго — Ф1 НЕ начинать от ветки: план ждёт.
2. **Неизвестный читатель путей или дельт** (чья-то подписка на `processes.*.state.<имя>`,
   потребитель MISSING-дельты вне названных в Task 2.0) → стоп-условия Task 1.1 / Task 2.0: флип

   (Task 2.1 / 2.3). Точка невозврата — сам флип Ф1+Ф2: атомарен, откат = revert ветки.
3. **`StateProxy.delete` — правка чужого модуля** (state_store). Дорога на приёмной стороне уже
   существует (`:281, :323, :624`), но если хозяин оси потребует иного — named-фолбэк: снятие
   `None`-надгробиями в гранулярности ПИСАТЕЛЯ (класс дефектов всё равно мёртв после Ф1;
   деградация только косметическая — ключи остаются в дереве). План при этом не стоит.
4. **Lifecycle слота в Ф3**: публикация в `configure` раньше `start` менеджеров → lazy-фолбэк
   обязателен и тестируется как равноправная дорога (не «костыль на случай»). Если слот-порядок
   всплывёт шире — Ф3 останавливается на фолбэке, Ф4 от Ф3 не зависит.
5. **Координация с `framework-architecture-rework`** (freeze-окно codemod): порт кладётся в
   текущую плоскую структуру модулей; если codemod-окно случится посреди плана — кодовые фазы
   приостанавливаются (правило того плана), rename-таблица пополняется новыми файлами

   но Ф5 этим НЕ блокируется (её зависимость — Ф3, дорога записей). Порядок предъявления — §11.7.

## §13. Ремкомплект наблюдателя — опрос живого процесса (бэклог, ВНЕ фаз)

Происхождение: идея владельца (2026-08-19) — «опрос памяти Python: записывать адрес переменной,
опрашивать, при пересоздании обновлять контактную книжку». Сырой адрес (`id()`) не живёт:
переиспользуется после GC (ABA — по старому адресу молча лежит чужой объект), бессмыслен между
процессами, а сильная ссылка ради опроса запрещает GC собрать объект (наблюдатель ломает
наблюдаемое). Рабочая форма той же идеи — идентичность ЛОГИЧЕСКАЯ (путь, weakref + поколение),
не физическая (адрес); сам порт наблюдений — её дисциплинированная версия («владение = путь»).

Ниже — потомки идеи, которые работают. Это НЕ задачи фаз: каждый входит по правилу
«минимум → реальная задача → фичи», пакеты ставит владелец.

| Инструмент | Что даёт | Какой живой долг закрывает |
|---|---|---|
| **py-spy** (pip, внешний) | стек-дамп/семплирование ЧУЖОГО процесса без его кооперации (читает память интерпретатора снаружи); Windows поддержан | зависший процесс, который не отвечает `backend_ctl` — graceful-stop 5с-ханг. Самый дешёвый вход: страница в доках «как снять дамп с висящего», ноль кода |
| **faulthandler** (stdlib) | `dump_traceback_later(timeout)` — процесс сам печатает стеки всех потоков, если не дошёл до отмены таймера | сторож в shutdown-пути `ProcessModule`: ханг оставляет улику вместо тишины |
| **`sys._current_frames()`** (stdlib) | стеки всех потоков изнутри процесса | кандидат в команду `introspect.threads` рядом с `introspect.memory` — «где сейчас стоит каждый поток» без отладчика |
| **tracemalloc** (stdlib) | снапшоты аллокаций + diff двух снапшотов, с точками рождения | охота на рост памяти класса «in-flight батчи» (дефект Ф0.3 observability): команда `introspect.tracemalloc` start/snapshot/diff |
| **weakref-реестр с поколением** (stdlib) | «контактная книжка» в честном виде: слабые ссылки (не мешают GC, callback на смерть) + счётчик инкарнаций при перерегистрации — тот же приём, что fencing по per-sender incarnation (Ф4.2) | призраки-дубликаты инстансов (ghost-гонка ADR-SS-019, призрак при резюме агента): команда `introspect.liveness` — кто жив, кто пересоздан, кто умер |
| **objgraph** (pip, мелкий) | `show_backrefs` — цепочка «кто держит объект, который должен был умереть» | следующий шаг после того, как tracemalloc показал, ГДЕ растёт; по требованию при живой охоте, не заранее |
| **pympler.asizeof** (pip) | честный глубокий размер дерева объектов | «сколько на самом деле весит регистр / поддерево стора» — числа вместо прикидок |
| **memray** (pip, Bloomberg) | трассировка аллокаций мощнее tracemalloc (native-стеки, flamegraph) | ТОЛЬКО Linux/macOS — на Windows-стенде не живёт; помнить про macOS-машину, на стенд не планировать |

Порядок входа по цене/пользе: py-spy (доки) → faulthandler в shutdown → `introspect.threads` →
tracemalloc-команда → weakref-реестр. objgraph/pympler — инструменты момента, не поставки.

DESIGN (decided by the lead — you type it, you do not derive it):
  **API сеанса** (`session.py`):
  ```
  class DeviceSession:
    __init__(port, sdk, ident=None, *, timeout_ms=500, watchdog_s=5.0, on_frame,
             on_stall=None, on_state=None, on_timing=None, run=(), rest=())
    start(timeout=5.0) -> bool    # True — захват идёт
    stop(timeout=2.0) -> None
    свойства: state: str, errors: int, last_error: str | None, device: DeviceIdentity | None, device_held: bool
  ```
  `sdk` плагин берёт как `port.sdk` (атрибут сверх `DevicePort`; у фейка он есть, вендорский источник — 4.1). `ident is None` -> первый из `sdk.enum_devices()`; пустой список или нет совпадения `(kind, value)` -> `not_found`, `open` не зовётся. `on_frame(RawFrame)` зовётся из потока владельца; исключение из `on_frame` — не ошибка порта, захват не останавливает. `on_state(old, new)`, `on_timing(name, seconds)` — СЕКУНДЫ (как `record_timing`, `process_module/plugins/base.py:720`); подключает к `ctx` Task 2.3b. `run`/`rest` — `Sequence[Step]` (1.6) для Task 2.2: в 2.1 принимаются и хранятся, методы `_apply_run()` / `_apply_rest()` — пустые точки вставки между `open` и `start_grabbing` и после `stop_grabbing` до `close` (журнал порта не пишут; в ветке `error` `_apply_rest()` не зовётся). Свойства `params`, `params_status`, `param_errors` наполняет Task 2.2; в 2.1 они пустые `{}`. До 2.3a плагин передаёт `ident=None`, `timeout_ms=500`, `watchdog_s=5.0`. `on_timing` вызывается для `"open"`, `"stop_grabbing"`, `"get_frame"` (секунды). Переходы владельца — только compare-and-set под замком состояния (`grabbing` не перезаписывает `stopping`); `on_state`, `on_stall`, `on_timing` зовутся вне замка, `on_state` — из потока, сменившего состояние.
  **Все вызовы порта и `DeviceSdk` (`acquire`, `enum_devices`, `open`, `start_grabbing`, `get_frame`, `stop_grabbing`, `close`, `release`) — только из потока-владельца**: фейковый `DeviceSdk` пишет в тот же журнал (`fake_port.py:174`). Один владелец на цикл `open -> close`; новый `start()` после `closed` — новый поток. Потоки владельца и сторожа — `daemon`.
  **Состояния и переходы.** `idle` — только до первого `start`; `closed` — состояние покоя после остановки (событие `closed -> idle` нет). `start()`/`stop()` по состояниям:
  | из | `start()` | `stop()` |
  |---|---|---|
  | `idle`, `closed` | новый цикл | no-op, журнал порта пуст |
  | `opening` | не ставит команду; ждёт итога текущего старта не дольше СВОЕГО `timeout`, по сроку -> `False`; второго `open` нет | см. «Дедлайн `start`» |
  | `grabbing` | `True`, без второго `open` | `stopping`, затем `closed` |
  | `stopping` | `False` немедленно, не ждёт и не ставится в очередь | no-op (идемпотентен) |
  | `busy`, `not_found`, `error` | новый цикл (автопереподключения нет, ADR-CR-009) | -> `closed`, порт не зовётся |
  `start()` из `busy`/`not_found`/`error`/`closed` — новый цикл только если владелец предыдущего цикла вышел (`device_held == False`); иначе `False` немедленно, без очереди (как в `stopping`). `start()` из потока владельца — `False` немедленно.
  `PortError(kind="busy")` на `open` -> `busy`; `PortError(kind="not_found")` или нет совпадения в `enum_devices` -> `not_found`; прочие `PortError` на `open`/`start_grabbing`/`get_frame` -> `error`. `close` не зовётся, если `open` не удался; после удавшегося `open` — зовётся всегда. `acquire` и `release` — по одному разу на цикл (ветка reopen из 2.2/2.4 их не повторяет); `release` зовётся и при отказе `open`, не зовётся при отказе `acquire`.
  **`stop(timeout)`** — не команда с дедлайном и не отбрасывается; `timeout` — только срок ожидания вызывающего. `stop()` переводит `state` в `stopping` синхронно, в потоке вызывающего, под замком состояния, ДО постановки остановки в очередь (иначе окно «`start()` во время `stopping`» открывается лишь после взятия команды владельцем). Ждёт выхода владельца не дольше `timeout + timeout_ms/1000` (как `Services/code_reader/core/sdk_reader.py:161`); вернулся по сроку -> `state` остаётся `stopping`, `close` довыполняет владелец, `closed` — только после его выхода. `stop()` из потока владельца (из `on_frame`) не ждёт: ставит остановку и возвращается (самосоединения нет, `sdk_reader.py:158-160`). Замок состояния не держится ни при `join`, ни при ожидании ответа владельца.
  **Дедлайн `start`.** `start(timeout)` возвращается по первому из: итог владельца; истечение `timeout` (тогда `False`). Решение «откат или фиксация» принимается под замком команды: по сроку вызывающий ставит `cancelled`, владелец перед `start_grabbing` (после `_apply_run()`) ставит `committed`; кто первый — тот решил, ответ вызывающего равен итогу. Владелец проверяет `cancelled`/`stop` ПОСЛЕ `open` и ПОСЛЕ `_apply_run()`; при отмене — `_apply_rest()` (если run уже писался), `close`, `release`, состояние `closed`, без `start_grabbing`. Проверка дедлайна при взятии из очереди — для `apply` (2.4), у `start` команда в очередь попадает только первой в цикле. Откат, а не «довести и вернуть `True`»: ответ и состояние согласованы (ревью P4 б). Это же закрывает «стоп во время старта».
  **Ошибки кадра.** «Ошибка» — исключение `PortError` из `get_frame`; `None` (таймаут кадра) — не ошибка и сбрасывает счётчик подряд идущих ошибок (прецедент `sdk_reader.py:35-36, 352-362`). 3 ошибки подряд -> `error`, затем `stop_grabbing`, `close`, `release` (порядок `sdk_reader.py:377-402`). `errors` — счётчик за жизнь сеанса (не сбрасывается `start()`), 2.2 растит его же за узлы; `last_error` — `type(exc).__name__` + `kind` + `code` (для `PortError` ещё `str(exc)`), без значений рецепта.
  **Сторож.** «Зависание» = один вызов порта дольше `watchdog_s`; `on_stall(call, seconds)` зовётся один раз на вызов из потока сторожа (`daemon`; колбэк порт не зовёт; `call` — имя из журнала: `"get_frame"`, `"open"`…). Умолчание `watchdog_s=5,0` — запас над GigE `open` 1–3 с и `timeout_ms`=500. Pre: `watchdog_s > timeout_ms/1000`.

Тесты, не проверяющие ожидание кадра, задают `frame_period_s=0.01` (без него цикл горячий и раздувает журнал).

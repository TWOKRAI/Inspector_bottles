## Контекст

Строка L-2 висела с F1 («did not stop in 5.0s»), а память `project_graceful_stop_debt`
держала корень «блокирующий `produce()` источника» (июнь 2026). **На текущем коде этот корень
опровергнут**, сам дефект — жив:

| Факт (2026-09-23, HEAD `277d96e8`) | Число |
|---|---|
| `harness.stop()` на `inspection_full` (7 процессов) | **5.45 с / 5.53 с**, 2 из 2 |
| Строка в журнале | `spawner: ProcessManager did not stop in 5.0s, terminating...` |
| Teardown детей и самого PM по их журналам | **0.6 с** — все `shut down successfully` |
| Остановка воркеров (включая `camera_0`) | 10–50 мс — `produce()` ни при чём |
| Где висит PM (дамп `faulthandler` через 2.5 с после stop) | `util._exit_function → _run_finalizers → queues._finalize_join`; поток feeder в `connection.send_bytes` |
| `cancel_join_thread()` в дереве | **0 вызовов** (framework, Services, Plugins, backend_ctl) |

Механизм: `multiprocessing` на выходе интерпретатора ждёт feeder-поток каждой `mp.Queue`,
в которую процесс писал. Если читатель уже мёртв, а канал полон, `send_bytes` не вернётся
никогда. Ожидание обрывает только внешний `join(5.0)` в `launcher/spawner.py:162-165`, после
чего PM уходит в `terminate()` (код выхода -15).

Цена сегодня: +5 с на **каждый** останов стенда (прототип; closure 4.8 и otel 2.4 записали
«останов шёл через terminate» дважды), грубое завершение PM. На `line_sim` в логах 2026-09-23
останов 0.6–0.8 с — механизм тот же, трафика не хватает переполнить канал. Это зависит от
нагрузки, а не от приложения.

## Task 1.1 — выход процесса ограничен по времени, данные живому читателю доставлены

> **ПЕРЕСМОТР 2026-09-23 (после двух ревью и стенда) — задача сужена до «источник #1 из 2».**
> Итерация 1 (`c7636aa3`, общий отпуск feeder'ов на выходе через `cancel_join_thread` /
> `Finalize.cancel` / приватный `_finalizer_registry`) **отвергнута** ревью: под бюджетом 0.25 с она
> обрывает сообщение медленному ЖИВОМУ читателю посреди записи (15/100 доставлено, читатель висит в
> `os.read` навсегда) — порча, которую раньше давал только `terminate` через 5 с. Итерация 2
> (`03238ad5` + `a2fe8d95` + `3d802091`) лечит **источник #1**: `EventManager._event_queue` была
> `multiprocessing.Queue` без читателя (единственный читатель `wait_for_event` вне тестов не зовётся;
> очередь исключена из pickle, то есть и так процесс-локальная) — стала ограниченной `queue.Queue(1000)`
> с вытеснением старейшего и честным счётчиком `get_stats()["events"]["dropped"]`. Попутно снята
> неограниченная утечка памяти. ADR-SRM-015.
>
> Судьба критериев ниже: **1 — отвергнут** как контракт (писатель по стене времени не отличает мёртвого
> читателя от медленного; отпуск портит медленного), класс тестера A удалён с записью в ADR; **2 — принят**
> (T-B + авторский страж медленного читателя E-d); **3, 5 и «код выхода PM = 0» — перенесены в Task 1.2**
> (стенд после итерации 2 — 5.52 с в 4 из 5 прогонов: второй источник); **4 (`store flush … 0 потеряно`) —
> принят** (0 во всех прогонах ведущего); **6 — выполнено** (матрица `docs/reviews/2026-09-23_task-1.1-injections.md`,
> И1–И8, J1–J5, K1–K2); **7 — выполнено** (ADR-SRM-015). Живой тест тестера `backend_ctl/tests/test_graceful_stop_live.py`
> стоит `skip` до Task 1.2 (красный прогон оставляет сирот — см. L-5). Приёмка: ревью ×2 + `teamlead`
> (3-я итерация) — ACCEPT, `docs/reviews/2026-09-23_task-1.1-teamlead-accept.md`.

**Level:** Senior · **Assignee:** teamlead · **Layer:** framework

**Goal:** процесс, у которого читатель очереди умер, выходит за ограниченное время без
`terminate`; сообщение живому читателю, положенное перед остановом, доставлено.

**Где искать (не предписание):** общий выход всех процессов, включая PM, —
`process_manager_module/runner/process_runner.py` `run_process_function` (блок `finally`,
`:237`); PM тоже запускается им (`launcher/spawner.py:100`). Регистр очередей —
`shared_resources_module/queues/core/manager.py` (`QueueRegistry.shutdown` сейчас пуст).
Место правки выбирает исполнитель: одно, через которое проходят все процессы, а не заплатка
в PM.

**Acceptance criteria:**
- [ ] Изолированно: процесс пишет в `mp.Queue` до переполнения канала, читатель убит, затем
  процесс штатно выходит → выход завершается за < 2 с (сегодня: бесконечно). Тест не
  зависает: вызов в daemon-потоке с дедлайном join.
- [ ] Изолированно, пара к предыдущему: живой читатель, сообщение положено непосредственно
  перед выходом писателя → сообщение получено (досылка ограниченная, а не нулевая).
- [ ] Живьём, `inspection_full` headless, свободный порт: `harness.stop()` < 2.0 с в 5 из 5,
  строк `did not stop in` — 0, код выхода PM = 0.
- [ ] Живьём: `store flush: … M потеряно` — `M == 0` у всех процессов, как в LC4 от 2026-09-08.
- [ ] Живьём: `process_restart_verified` для `renderer`, `camera_0`, `storage` по-прежнему
  проходит (сегодня ~1.3–1.4 с).
- [ ] Break-injection ведущего: без механизма стенд возвращается к ≥ 5.0 с и строке
  `ProcessManager did not stop in 5.0s`; предсказание записано до прогона.
- [ ] Решение записано ADR в `DECISIONS.md` модуля, где живёт механизм (окно досылки —
  число из замера, не с потолка; что теряется и где это видно).

**Out of scope:** прерываемые `cv2.read()` / Hikvision `timeout_ms=1000` (живое железо,
сегодня не воспроизводится — долг ниже); бюджеты spawner/PM.

## Task 1.2 — писатель переживает читателя при останове (источник #2)

**Level:** Senior · **Assignee:** teamlead · **Layer:** framework · **Статус:** PENDING

**Что измерено (investigator, 2026-09-23, 3 зависания из 3 прогонов, стеки faulthandler):** при останове
`system_stop_event` гасит всех параллельно — порядка «сначала источники, потом приёмники» нет. `gui` выходит,
а `renderer` (`pipeline_executor.py:409 _send_results → router_manager.py:770 → queues/core/manager.py:287
put_nowait`) ещё шлёт кадр в `gui/data`. Сообщение крупнее свободного места в канале; EPIPE не придёт —
read-конец держат все процессы, получившие очередь, включая сам `renderer`. Выход `renderer` ждёт feeder
вечно (`queues.py:219 _finalize_join`), PM ждёт `renderer` в `stop_many` (`process_registry.py:332`), спавнер
через 5 с убивает PM, `renderer` остаётся сиротой.

**Направление (решает исполнитель после тестера, не предписание):** метка «читатель ушёл навсегда» на
каждую очередь (межпроцессный флаг рядом с очередью, взводит процесс-владелец при выходе); писатель после
`shutdown()` отпускает feeder ТОЛЬКО у очередей со взведённой меткой — сообщение туда недоставимо по
определению, а медленного живого читателя это не касается (метка не взведена). Гонку «читатель вышел
после проверки» закрыть короткими `join(timeout)` с перепроверкой метки. Альтернатива на рассмотрение —
порядок останова «источники → приёмники».

**Acceptance criteria:**
- [ ] Живьём, `inspection_full`, свободный порт: `harness.stop()` < 2.0 с в **10 из 10** циклов (плавающий
  дефект: 3 цикла мало), строк `did not stop in` — 0, код выхода PM = 0; живой тест тестера снят со `skip`.
- [ ] Медленный живой читатель (страж E-d) — по-прежнему 100/100, читатель не виснет.
- [ ] Сообщение в очередь со взведённой меткой не держит выход писателя дольше короткого окна (число — из замера).
- [ ] Break-injection ведущего: без метки стенд возвращается к ≥ 5.0 с.
- [ ] ADR (дополнение к ADR-SRM-015 или новое), где сказано, что теряется и где это видно.

**Исполнение:** тестер в worktree до кода (новый механизм) → teamlead → инъекции → стенд → ревью.

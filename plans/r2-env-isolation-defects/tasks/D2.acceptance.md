# D2t — слепая приёмка PID-реестра: область checkout, гонка при одновременном старте, имена в логе (ред. 2)

Только критерии. `D2.md` (DESIGN) тестеру не читать. Пишешь до кода, тесты ожидаемо красные там, где указано.

- **Файл:** `multiprocess_framework/modules/process_manager_module/tests/test_pid_registry_checkout_acceptance.py` (новый).
- **Запрещено читать:** `plans/r2-env-isolation-defects/**`, `docs/reviews/**`, `docs/reports/2026-11-15_R2_lane.md`, ветку разработчика. Можно читать: публичные функции `pid_registry`
  (`pid_file_path`, `register_self`, `reap_and_reset`, `clear`), существующие тесты `test_pid_registry*.py` (изоляция temp, «живая жертва»), README модуля.
- **Правила:** ожидаемые значения — литералы; жертва — настоящий `subprocess`, не мок. Второй checkout = ВТОРАЯ НАСТОЯЩАЯ КОПИЯ пакета `multiprocess_framework` (`shutil.copytree`, не симлинк: симлинк-копия через `resolve()` схлопывается в тот же корень),
  запуск через `subprocess` с `PYTHONPATH=<каталог копии>`; в env КАЖДОГО subprocess задать `TMPDIR`, `TEMP`, `TMP` = изолированный каталог теста (подмена `tempfile.gettempdir` в родителе в ребёнка не переходит); `MPF_APP_NAME` — явно;
  `MULTIPROCESS_PID_FILE` / `INSPECTOR_PID_FILE` в дефолт-тестах сняты. Живость жертвы — `Popen.poll() is None`, не `pid_exists`; таймауты реапа ≥ 30 с (копия пакета ~29 МБ, импорт ~0,7 с).
  Имя процесса-жертвы — `psutil.Process(pid).name()`, считанное ДО реапа (литерал не подставлять: на Windows нет `sleep`).

## Критерии

- **C1** (красный до кода). Два checkout одного приложения (`MPF_APP_NAME=AppOne`) → `pid_file_path()` в них — РАЗНЫЕ пути в одном temp; один и тот же checkout — один и тот же путь при повторном вызове и из дочернего процесса с тем же `PYTHONPATH`.
- **C2.** Имя файла начинается с `AppOne` и кончается `_system_pids.jsonl`.
- **C3** (красный до кода). Сосед выживает: жертва записана в реестре checkout A (`register_self` из дочернего процесса A); `reap_and_reset()` из B → жертва ЖИВА, файл A не изменён.
- **C4.** Своё реапится: жертва записана в реестре A; `reap_and_reset()` из A → жертва мертва (≤ 30 с), реестр A пуст, возврат ≥ 1.
- **C5.** Файл прежнего неразделённого имени `AppOne_system_pids.jsonl` с записью живой жертвы: `reap_and_reset()` (любой checkout) → жертва ЖИВА, файл на месте и не пуст. (Зелёный и без части реализации — защиту держит C6.)
- **C6** (красный до кода). То же для приложения `inspector`: файл `inspector_system_pids.jsonl` с живой жертвой → после `reap_and_reset()` жертва жива, файл на месте.
- **C6b** (пин границы, зелёный до и после). Приложение `AppOne` + файл `inspector_system_pids.jsonl` с живой жертвой → жертва УБИТА, файл удалён (легаси до D4 реапается; граница названа в ADR).
- **C7** (красный до кода). Лог: ≥ 2 живые жертвы в реестре, ПОСЛЕДНЯЯ запись реестра — мёртвый pid (например 999999). `reap_and_reset(log=lines.append)` → по ОДНОЙ строке на жертву, содержащей pid именно этой жертвы (`Popen.pid`) и её имя из `psutil` до реапа;
  строки не содержат pid мёртвой записи; плюс итоговая строка со счётчиком «убито 2».
- **C8.** Явная ручка `MULTIPROCESS_PID_FILE=<файл>` сильнее дефолта; `INSPECTOR_PID_FILE` слабее `MULTIPROCESS_PID_FILE`.
- **C9** (гонка при одновременном старте двух запусков, красный до кода). Копии A и B; в каждом реестре по живому «хвосту» своего checkout; оба запуска стартуют по барьеру (общий файл-сигнал или `multiprocessing.Barrier`) и делают `reap_and_reset(); register_self()`; 10 повторов целого сценария.
  Ожидается каждый раз: каждый реап вернул ровно 1 и убил ТОЛЬКО свой хвост; новые записи (`register_self`) живы; в каждом реестре только pid своего checkout; все строки файлов — валидный JSON.
- **C10** (один checkout, два запуска одновременно). Два дочерних процесса ОДНОГО checkout стартуют по барьеру тем же сценарием. Инварианты: нет исключений, все строки реестра парсятся, чужих (из другого checkout) pid нет. НЕ утверждать, что второй запуск не убивает первый, — этого D2 не обещает.

## Зачем — одной фразой

Знание «этот процесс остановлен/убит навсегда» есть только у PM, а пользуются им сейчас сами дети и только на
одном из путей останова. Отсюда три живых дефекта: команда `system.shutdown` возвращает 5.8 с и `terminate`
(1 из 3 прогонов), убитый читатель вешает писателя навсегда, сироты переживают стенд. План переносит власть над
остановкой туда, где знание: в PM.

## Целевое состояние (вердикт CTO, «Как правильно»)

- **Один путь останова.** Любой стоп системы — окно GUI, `harness.stop()`, команда `system.shutdown` (backend_ctl,
  `process_manager_proxy.shutdown_system`, будущий Пульт) — взводит `system_stop_event`. Разных «системных стопов» нет.
- **Метку «читатель ушёл» ставит владелец жизненного цикла.** PM после join/terminate/kill ребёнка, которого не
  собирается перезапускать, взводит метку на его очередях. Самопометка детей на системном стопе остаётся быстрым
  путём. Рестарт — как сейчас: метки нет, очередь переиспользуется.
- **Строка потерь — сигнал, а не шум.** Печатается только при реальной потере (`buffered_dropped > 0`).
- **Сирот нет по построению.** Страховка уничтожения дерева работает на штатном пути; бюджеты вложены
  (внешний > внутреннего); harness знает всё дерево.
- **Оставить:** ADR-SRM-015, `ReaderGoneQueue` как транспорт метки, правило «немаркированную очередь ждать до слива»
  (защищает медленного живого читателя).
- **Не делать сейчас** (CTO): закрывать read-конец у не-читателей (несовместимо с `restart_reuse_queues` — снимается
  только вместе с Task 3.2), порядок «источники → приёмники». Двухфазный стоп CTO считает ненужным после Ф1 и L-6 —
  записан условной Task 3.1, решают числа Ф2.

**Решение стадии 0 (Opus, 2026-10-19, [отчёт](../docs/reviews/2026-10-19_lifecycle-1.8-stage0.md)) — (в): ожидание
вычерпывает свои каналы в буфер, без диспетчеризации.** Пока `join_until` ждёт ребёнка, поток переносит сообщения из pipe
своих каналов (фильтр текущего `receive`: system/state/observability) в FIFO-буфер роутера; разбор и диспетчеризация —
в следующем `receive()`, после возврата обработчика. Ответ команд синхронный, после подтверждённой смерти — как сегодня;
внутри ожидания не исполняется ни одна команда; порядок сохраняется; одна точка закрывает все пути «Факта».
Отвергнуто: (а) с диспетчеризацией — реентерабельность (`topology.apply` внутри `restart_process` между stop и
`create_and_register`); (б) ожидание в другом потоке — теряется неявная сериализация команд PM (`process_monitor.py:1480`);
отпуск feeder по таймауту; метка «ушёл» на очередях PM.

**DESIGN (кратко; полный — отчёт стадии 0, §4):**
- D1 `router_module/core/router_manager.py`: `receive()` запоминает свой фильтр каналов в `_recv_local`; публичный
  `pump_inbound() -> int` — при `depth == 0` возвращает 0, иначе `poll(0.0)` каналов фильтра в `_inbound_stash`
  (FIFO на канал, потолок `POLL_DRAIN_CEILING`, WARNING один раз за эпизод, не бросает); `_poll_all_channels` отдаёт
  буфер канала раньше pipe; пустой буфер — ноль затрат.
- D2 `core/child_process_stop.py`: kwarg `idle` (по умолчанию `time.sleep`), `join_until` зовёт `idle(pause)`; сбой idle —
  один WARNING и `time.sleep`.
- D3 `core/process_registry.py`: `stop_wait_idle`, `_build_child_stop` передаёт его в `ChildProcessStop`.
- D4 `process_manager_process.py`: `_stop_wait_idle(pause_s)` = `pump_inbound()` + сон остатка; ставится в реестр после
  его создания. Обработчики, `stop_process`, `restart_process`, топология — без правок.
- ADR-PMM-037 «Ожидание стопа вычерпывает свои каналы» + ADR в `router_module/DECISIONS.md` (контракт `pump_inbound`) +
  `python -m scripts.sync`.

### Task 3.1 — Остановка как протокол: «прекратите слать» → «перестал» → «выходите» (межпроцессная половина)

**Level:** Senior+ · **Assignee:** teamlead · **Цена:** S–M (была M до сужения 2026-10-03)
**Сужена 2026-10-03 (П3 вердикта CTO по `lifecycle-owner-scope`).** Внутрипроцессная половина — именованные фазы
`stop()`, порядок «работа → транспорт → наблюдаемость», удаление хука `_before_observability_teardown`, вложенность
срока внутри ребёнка — делается в [`lifecycle-owner-scope`](2026-10-03_lifecycle-owner-scope/plan.md) Ф1 (Task 1.1
`stop_budget`, Task 1.2 корень с барьерами). Ребёнок там получает `cancel()` = «прекратите» и `close()` = «выходите».
Здесь остаётся только протокол между PM и детьми: рассылка quiesce, сбор ack, затем exit — поверх их `cancel()`/`close()`.
**Идея:** PM рассылает quiesce, каждый процесс перестаёт производить и отправлять, отвечает ack, затем PM рассылает
exit; сроки вложены явно (ребёнок < PM < спавнер; число ребёнка — из `stop_budget.py`). Один путь для окна GUI,
`harness.stop()`, `system.shutdown`, Пульта.
**Триггер:** после Ф1 + L-6 хотя бы одно из: `buffered_dropped > 0` на штатном стопе; потеря последних сообщений детей в
PM (`store flush` M > 0); отпуск по метке срабатывает на ≥ 1 из 20 стопов.
**Разногласие, записанное честно:** CTO (приёмка 2026-09-24) считает двухфазный стоп после Ф1 и L-6 ненужным; ведущий
считал его частью целевой архитектуры. Решают числа триггера.

### Task 3.2 — Перезапуск получает новые очереди, а не старые

**Level:** Senior+ · **Assignee:** teamlead · **Цена:** M
**Идея:** `restart_process` выдаёт новому воплощению новые очереди, соседи узнают адрес через эпоху маршрутизации
(`routing_meta.epoch`/incarnation уже есть, Ф3.1 routing-epoch). Снимает главное ограничение ADR-SRM-016: при рестарте
нельзя закрыть/пометить очередь, потому что её переиспользуют; открывает путь «закрыть read-конец у не-читателей → EPIPE
сам» (отвергнутый CTO только из-за `restart_reuse_queues`).

### Task 3.3 — Транспорт без скрытого потока-отправителя

**Level:** Senior+ · **Assignee:** teamlead (+ CTO на вердикт) · **Цена:** L — трогает весь IPC
**Идея:** `mp.Queue` отправляет через фоновый feeder-поток, которого Python ждёт на выходе, — это источник обоих
зависаний L-2. Целевой транспорт: отправка не блокирует никогда — «ушло» или «переполнено → политика QoS со счётом»;
кандидаты — неблокирующий pipe/socket со своей рамкой, SHM-кольцо с seqlock (в проекте уже есть), `multiprocessing.connection`
без feeder. Политики переполнения уже есть (QoS, drop-oldest, never-drop) — нужен транспорт, который их честно исполняет.
**Триггер:** после L-6 и Ф1 отпуск по метке всё ещё срабатывает, ИЛИ профиль показывает, что feeder-потоки/pickle — узкое
место, ИЛИ Task 3.2 делается и транспорт всё равно переписывается. Без триггера — не делать: ReaderGoneQueue остаётся страховкой.
**Предусловие:** отдельный план с ревью CTO до кода; окно codemod `framework-architecture-rework` (Р-9) — сверить.

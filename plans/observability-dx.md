## Трек А — Разъём наблюдаемости для авторов Services

**Факт.** `IService` (`service_module/interfaces.py`) — 4 метода (`name/start/stop/get_status`),
наблюдаемости нет. В `Services/` два несогласованных лагеря: 7 файлов вручную наследуют
`BaseManager + ObservableMixin`, 18 — на `get_std_logger(__name__)`. Автору модуля фреймворка —
богатый контрактный разъём; автору плагина — фасад; автору сервиса — конвенция на выбор.
Для конструктора это самая заметная неравномерность поверхности: первый же внешний встройщик
сервиса спросит «а как мне логировать?» и получит два разных ответа.

**Развилка владельца Р-А1 — форма разъёма:**

| Вариант | Суть | Цена |
|---|---|---|
| (а) **`ServiceContext`** — фасад-зеркало `PluginContext` (пять `log_*`, `health.report_error`, `write_document`, после 6.2 — `record_metric`), вручается вызывающим; переходники `from_plugin(ctx)` / `from_manager(mixin)` | один инжектируемый объект, никакой ломки `IService` (параметр опциональный / отдельным сеттером); оба лагеря получают мост, а не третий лагерь | новый класс (~150 строк + тесты) → **рекомендация** |
| (б) расширить `IService` абстрактными методами | контракт железный | ломает все существующие сервисы — отвергнуть |
| (в) узаконить конвенцию «сервис = BaseManager» | нулевой код | BaseManager тяжёл для SDK-сервисов (sql, hikvision); лагерь `get_std_logger` останется — не решает |

| # | Задача | Приёмка |
|---|---|---|
| А.1 | Спека разъёма (страница в `service_module/README.md` + решение Р-А1) — какие методы, кто вручает контекст (плагин? процесс? композиционный корень?), что остаётся законным для `get_std_logger` (SDK-код import-time) | ревью спеки независимым агентом; граница «когда std_logger законен» названа |
| А.2 | `ServiceContext` + переходники + контракт-тест «пятёрка `log_*` идентична PluginContext» (оракул читает оба протокола — дрейф краснеет) | контракт-тест; break-injection: снять метод у фасада → красный поимённо; запись сервиса доезжает до плоскости под именем сервиса (live, по образцу приёмки Ф5) |
| А.3 | Миграция двух показательных сервисов (`device_hub` — самый живой, `documents` — уже в плоскости) на `ServiceContext`; остальные — по мере касания, реестром | оба сервиса пишут через фасад; `manager_call_failures` = 0 на стенде; список немигрированных — в README трека с причиной |
| А.4 | Слепая приёмка (метод S2, вход С-9 этапа 8): агент, не видевший исходников, подключает наблюдаемость к новому сервису только по README | агент прошёл без догадок; каждая заминка — правка README, не устный ответ |

**Out of scope:** переписывание всех 18 `get_std_logger`-точек (мост и так доставляет в плоскость);
разъём для `Utils/`.

## Трек Б — Двери конфига: меньше, а не больше

**Факт.** Для одной подсистемы: 4 слоя × 2 секции (`observability` + отдельная `telemetry`),
6 env-пар = 12 имён (и каждый читатель дублирует чтение пары сам — `env.py` называет это
намеренным), 14 рантайм-команд + 3 команды-алиаса (`logger.sink.*`, имена до 5.10), плюс два
**противоположных** правила приоритета env↔конфиг в одном репозитории (П-11, назван в ADR-138).

| # | Задача | Приёмка |
|---|---|---|
| Б.1 | **Требование к спеке 6.1 (сейчас):** телеметрия НЕ заводит пятую дверь — её ручки живут в существующих слоях L0–L3 и существующих командах; если спека решает иначе — решение владельца с записью цены | строка в спеке 6.1 «двери: без новых» либо явная развилка владельцу |
| Б.2 | **Одна функция чтения env-пары.** `read_env_pair(canonical)` в `app_module/env.py`; все читатели наблюдаемости (log_paths, observability_store, process_launch_config, observability_reload, managers_config, frame_trace, health/state — 7 точек по карте разведки) переходят на неё | grep «прямое чтение `INSPECTOR_*`/`MULTIPROCESS_*` мимо helper'а в модулях наблюдаемости» = 0 (страж-тест по AST, как страж писателей); поведение пар не изменилось (пара-тесты 5.2 зелёные) |
| Б.3 | **П-11 — одно правило приоритета.** ADR: выбрать направление (рекомендация — «явный конфиг выше env», как у `log_paths`) и выровнять `launch.resolve_log_dir_root`; разворот поведения — named-решение владельца, не тихая правка | ADR принят; пара тестов на оба слоя читает ОДНО правило; `CONTROL_PANEL.md` называет его одной строкой |
| Б.4 | **Карта дверей — одна страница.** Раздел в `CONTROL_PANEL.md`: все входы конфига наблюдаемости (слои, env-пары, команды, алиасы) одной таблицей с приоритетами — оператор перестаёт собирать её по четырём файлам | сверщик документов расширен проверкой «каждая env-пара из `ENV_ALIAS_PAIRS` упомянута в карте» (показан красным на снятой строке) |
| Б.5 | Команды-алиасы `logger.sink.*` — решение: оставить (записаны в сохранённых сессиях драйвера) или deprecation-строк в ответе | решение записано; если остаются — ответ алиаса несёт указание на каноничное имя |

**Out of scope:** трогать сами слои L0–L3 (форма проверена тремя раундами приёмки — не улучшать
работающее); переименование env-имён.

## Трек В — Readback по протоколу, а не duck-typing

**Факт.** `observability_reload.py` собирает readback трёх плоскостей на 31 `getattr` + 12
`callable` — «есть ли у объекта метод» вместо «обязан ли». Эта форма уже прятала дефект годы:
ветка readback'а stats сторожилась `getattr(stats, "config", None)` и не исполнялась ни разу (B1).
`StatsManager.observability_readback()` уже существует — протокола, который ТРЕБУЕТ его от
остальных, нет.

| # | Задача | Приёмка |
|---|---|---|
| В.1 | Протокол `ObservabilityReadback` (в `channel_routing_module/interfaces.py`, рядом с базой менеджеров): `observability_readback() -> dict` (+ уже общие `_sink_readback`/`idle_sinks` остаются в CRM); `LoggerCore`/`ErrorManager` реализуют; `observability_reload` переходит на протокол | duck-typing остаётся только на границе «слот пуст/None»; **молчащий readback невозможен молча**: зарегистрированный менеджер без протокола → в ответе `unverifiable` с причиной, не пустой dict |
| В.2 | Break-injection обеих сторон | снять метод у одного менеджера → оракул протокола красный поимённо (а не тихо худой readback); снять переход на протокол в reload → красный; количество `getattr` в файле — числом в приёмке (31 → ≤ границы с None-слотами) |

**Out of scope:** менять СОСТАВ readback'а (9/3/3 источника — как есть); трогать `introspect.observability` контракт.

Ответ на вопрос владельца «улучшится ли потребление после плана телеметрии»: **да, основное — этап 6**.

## Трек Д — Дисциплина процесса

**Факт.** Механика ремонта отличная (break-injection 3/3 подтверждён), но: хвост раунда 2 сутки
жил с 21 красным (гейт не запускали), `QUEUE.md` отставал на два этапа, флейк без карантина,
qex-индекс был на 6 дней старше «свежего». Правило «подпись гейта живёт на HEAD» уже внесено в
roadmap — здесь его исполняемая часть.

| # | Задача | Приёмка |
|---|---|---|
| Д.1 | **Одна команда — все гейты.** `scripts/run_all_gates.py`: корневой pytest + `run_framework_tests.py` + `validate.py`, один сводный вердикт одной строкой (числа passed/failed по каждому). Именно её зовёт приёмка этапа и исполнитель перед `docs(plans)`-коммитом закрытия | скрипт существует, зовётся из `make gate`; вердикт-строка содержит HEAD-хеш — подпись привязана к дереву |
| Д.2 | **Карантин флейков — механизмом, не словом.** pytest-маркер `quarantine(reason, until)` + реестр; красный без маркера = красный гейт; маркер без причины/срока = красный страж (пустеющий реестр — зелёный) | `test_hot_reload_reconfigures_logger` (Т-3 ремонта) проходит через этот механизм первым; страж показан красным на маркере без причины |
| Д.3 | **Свежесть qex — привычкой инструмента.** Включить post-commit hook (`/mcp-qex:install-reindex-hook` уже существует); правило «qex-first» дополняется строкой «сверь `last_indexed` ≥ HEAD-даты, иначе Grep» | hook стоит; строка в CLAUDE.md/правилах qex |
| Д.4 | **Документы-спутники в гейте закрытия.** Чек закрытия этапа: `QUEUE.md`, `MODULES_STATUS.md`, real-state-map — либо обновлены, либо названы «не трогал, потому что…» в docs(plans)-коммите | пункт в шаблоне закрытия этапа в roadmap |

**Out of scope:** CI-сервер/ночные прогоны (нет инфраструктуры — не выдумывать); авто-коммиты.

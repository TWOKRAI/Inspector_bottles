# gui-service — архитектура: сборка из сервисов

Часть плана [`plan.md`](plan.md). Правится вместе с ним. Решения владельца 2026-09-23 и то, что из
них следует для раскладки кода. Факты сверены грепом 2026-09-23.

## Сборка из сервисов

Слова владельца: «рецепт — бэкенд. Фронтенд лишь помогает редактировать его. Пульт — отдельный
сервис. Нужно разбивать на сервисы и из них собирать».

**Сервис — вертикальный срез, а не папка.** У каждого сервиса до трёх частей, и каждая лежит в своём
слое:

| Часть | Что это | Слой | Правило |
|---|---|---|---|
| Бэкенд-часть | обработчики команд, владелец данных | процесс/плагин дерева | dict на границе, Qt-free |
| Клиентская часть | реализация порта (`Protocol` из `domain/protocols`) поверх команд | Qt-free | одна на обе сборки GUI |
| GUI-вклад | `TabSpec` + сборка портов = **`GuiAppSpec`** (frontend-constructor T4.1) | Qt | не импортирует бэкенд-часть |

**Приложение — это сборка.** Бэкенд — дерево процессов из сервисов (как сегодня `app_module`).
Интерфейс — хост, в который вставлены GUI-вклады:

```
apps/pult/                    хост: CLI, конфиг подключений, ~сотня строк
  = GuiBootstrap (fw) + RemoteGuiRuntime (fw) + N × GuiAppSpec, загруженных ПО ИМЕНИ из конфига

встроенный GUI (слот D8)      = GuiBootstrap (fw) + InProcessRuntime (fw) + 1 × GuiAppSpec
```

- Пульт **не импортирует** прототип. Правило `apps/* ↛ multiprocess_prototype/*` уже стоит в
  `.sentrux/rules.toml:128`, и оно остаётся без исключения. Пакет вкладок инспектора подключается
  строкой в конфиге Пульта (`gui_packs: {inspector: "<модуль>:APP_SPEC", line_sim: "…"}`) тем же
  способом, каким `launch.py:216` подключает класс процесса `gui`. Хост знает только контракт
  `GuiAppSpec`. Механизм обнаружения (entry points) не заводим: явный список, пока приложений два.
- Пакет, который загружается, выбирается по `capabilities` бэкенда (идентификатор приложения +
  версия протокола). При несовпадении версии Пульт показывает причину и не рисует вкладки.
- Пакет вкладок приложения живёт **при приложении** (инспектор — в прототипе, симулятор — в
  `Services/line_sim` или `apps/line_sim`) и импортирует только кит фреймворка и Qt-free контракт
  своего приложения. Запрет «фронт ↛ бэкенд прототипа» ставит Task 1b.3.

**Что сегодня «толстый клиент» и куда уходит** (разъём S9 аудита 1.1 + `AppServices`):

| Сейчас в процессе GUI | Владелец после | Задача |
|---|---|---|
| `RecipeManager`, `recipes/`, запись `app.yaml` | сервис рецептов на бэкенде, ревизия на сохранение | 1b.1 |
| `PluginRegistry.discover` (код `Plugins/` в GUI), каталоги дисплеев/сервисов | каталог от бэкенда | 1b.2 |
| `ProjectHolder`, undo, `CommandDispatcherOrchestrator` | **остаётся в GUI** — черновик редактора; сохраняется командой | 1b.3 |
| кадры | мост + SHM по имени / поток | 1.3, 2.1 |
| `Services.auth`, `users.yaml` (32 импорта, все во фронте) | сервис auth на бэкенде; сессия оператора, проверка команд у владельца | 1b.4 |

**Что это меняет в фазах:** Task 1.4 кладёт хост в `apps/pult/`, а не в
`multiprocess_prototype/frontend/pult/`. Исключение из правила QUEUE §5 («универсальный код в
прототипе по записи») **снимается**: универсальный хост в прототип не попадает. Прототип отдаёт
только свой `GuiAppSpec`. Добавлена фаза 1b. Ф2 без неё не стартует. Добавлена Task 3.3 «один режим GUI».

## Где что лежит после плана

| Что | Путь | Qt | Кто импортирует |
|---|---|---|---|
| Клиент двери | `multiprocess_framework/modules/router_module/channels/socket_client.py` | нет | `RemoteGuiRuntime`, `backend_ctl` (реэкспорт) |
| `Remote*`-реализации (`CommandSender`, `StateProxy`, `FrameSource`) | `frontend_module/bridge/remote_*.py` | нет | `RemoteGuiRuntime` |
| `GuiHostRuntime` (Protocol) + `InProcessRuntime` + `RemoteGuiRuntime` | `frontend_module/bootstrap/runtime*.py` | нет | `GuiBootstrap` |
| `GuiBootstrap`, `GuiAppSpec` (контракт пакета) | `frontend_module/bootstrap/` | да | хосты: `apps/pult`, встроенный `GuiProcess` |
| Хост Пульта | `apps/pult/` (`__main__.py`, `config.yaml`, README/STATUS/DECISIONS, tests) | да | никто — composition root |
| Пакет вкладок инспектора | `multiprocess_prototype/frontend/app_spec.py` (`APP_SPEC`) | да | по имени из конфига хоста |
| Пакет вкладок симулятора | `apps/line_sim/gui_spec.py` (появится в 3.2) | да | по имени из конфига хоста |
| Сервис рецептов (бэкенд) | `multiprocess_framework/modules/recipe/service*` + хук формата в `multiprocess_prototype/backend/` | нет | дерево инспектора |

Всё, что помечено «фреймворк», добавляется **новыми файлами**, не переносом. Окно codemod rework их
переложит по доменам Р-4 (ядро без Qt → `framework`, `bootstrap/` → Qt-пакет `frontend`) вместе с
остальным. Колонку «Qt» проверяет `grep PySide6` в приёмке каждой задачи.

## Контракт двери — публичный API

Провод «GUI ↔ бэкенд» после этого плана — публичный интерфейс между двумя сервисами, а не
внутренность одного процесса. Значит:
- `capabilities` отдаёт `app_id` и `protocol_version`. Хост выбирает пакет по `app_id` и отказывается
  рисовать при несовместимой версии, называя обе версии;
- ломающее изменение формы команды или ответа = новая `protocol_version` + запись в DECISIONS модуля
  `router_module`;
- Dict at Boundary — как везде: схемы на проводе — `to_dict`/`from_dict`, Pydantic внутри.

## Auth — на бэкенде (решение 2026-09-23)

Следует из того же принципа, что рецепт: пользователи и роли — это данные приложения, а владелец
данных — бэкенд. Сегодня `Services.auth` и `users.yaml` живут только в GUI (32 импорта, все в
`multiprocess_prototype/frontend`), то есть права проверяет клиент. Для Пульта на другой машине это
означает, что права проверяет тот, кого проверяют. PSK-токен (2.2) удостоверяет машину, а не
оператора. Правильно: сессия оператора открывается командой на бэкенде (`auth.login` → токен сессии),
каждая команда несёт токен сессии, проверка идёт на стороне владельца. Сервис `Services/auth` уже
есть — меняется хост, не код.

**`Services/auth` остаётся сервисом** (уточнение владельцу 2026-09-23): пакет, слой `Services/` и
код не меняются. Меняется только хост. Сейчас его поднимает процесс GUI, станет — процесс в дереве
бэкенда. В разложении по трём частям это выглядит так:
- бэкенд-часть — сам `Services/auth` (manager, session_tracker, storage, audit) плюс командная
  поверхность `auth.*` и мидлварь проверки;
- клиентская часть — удалённый `AuthFacade` (порт уже есть в `domain/protocols`);
- GUI-вклад — вкладка «Администрирование» и скрытие контролов по ролям.

Так же разложится любой будущий сервис: `Services/<имя>` — бэкенд, клиент и GUI-вклад рядом, а не
внутри прототипа. Задача — 1b.4. На одной машине (Ф1, Ф3) не блокирует, **Ф2 без неё не
стартует**.

## Целевое состояние: один режим GUI

Пока паритет не доказан, живут две сборки: встроенная (`InProcessRuntime`, слот D8) и Пульт
(`RemoteGuiRuntime`). Это нужно ради приёмки 1.4 и чтобы у `GuiHostRuntime` было две реализации. Но
два боевых пути навсегда — это двойная поверхность дефектов и тестов. Цель: **GUI никогда не живёт в
дереве процессов.** После приёмки 1.4 (числа fps/паритета зелёные):
- слот `gui` в дереве = только мост (`BridgeGuiProcess`) или headless;
- `frontend/run.py` = «поднять бэкенд + Пульт на localhost» одной командой;
- Qt-воплощение `GuiProcess` уходит в LEGACY по правилу владельца «freeze, не kill» (как Gen-1).

Решение принимается **по числам 1.4**, не заранее: если Пульт на localhost хуже встроенного GUI по
fps больше допуска, встроенный режим остаётся, а причина записывается. Задача — 3.3 (после Ф3, когда
Пульт обкатан на двух бэкендах).

## Что тянется из frontend-constructor раньше Блока В

Хост без composition root не собрать, а `run_gui` сегодня — 749 строк с инъекцией `process._*`.
Поэтому **T4.1 (дизайн-док `GuiAppSpec`/стадий), T4.2 (разборка на стадии с характеризацией
boot-порядка), T4.3 (`GuiBootstrap` новым файлом во фреймворке), T4.4 (`GuiHostRuntime` вместо
`process._*`)** выполняются до Task 1.4 как её предпосылка. Все четыре — новые файлы или правки на
месте, окно codemod им не нужно. Ф3 (промоушен кита), T4.5–T4.6 и Ф5–Ф6 остаются в Блоке В.
Владелец этих задач — frontend-constructor, статусы ведутся там.

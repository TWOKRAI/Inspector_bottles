# Phase 3 — Несколько бэкендов: вкладка или окно на каждый

Часть плана [`plan.md`](plan.md). Цель фазы: Пульт держит N подключений одновременно — инспектор и
симулятор рядом, вкладками или отдельными окнами по выбору оператора. Это точка посадки для
line-sim Ф6 (пульт симулятора) и Ф7.3 (Qt-редактор объектов).

---

### Task 3.1 — Модель подключений: `BackendConnection`, вкладка/окно на бэкенд, отстыковка

**Level:** Middle+ (Sonnet, extended thinking)
**Assignee:** developer
**Goal:** Пульт хранит список подключений (`pult.yaml`: имя, host, port, токен-ссылка, предпочтение
транспорта кадров), поднимает по одному набору вкладок на подключение, показывает их верхнеуровневыми
вкладками; любую можно **отстыковать в отдельное окно** и пристыковать обратно. Отвал одного
бэкенда не трогает другие.

**Контекст:** «вкладка на бэкенд или окно на бэкенд — раскладка одних и тех же виджетов, не
архитектура» (plan.md). Qt даёт это нативно: `QDockWidget.setFloating(True)` либо reparent виджета
в новый `QMainWindow`. Выбрать одно (рекомендация — `QDockWidget`: floating/attach из коробки,
запоминание раскладки через `saveState/restoreState`), обосновать в DECISIONS Пульта. Ничего своего
для drag-and-drop окон не писать. Шелл на бэкенд — `GuiHostWindow` frontend-constructor T4.6 (генерик
меню/доки/статусбар/tab-host из `main_window.py`), если он уже выделен; если нет — Пульт использует
`main_window.py` прототипа как есть и **не** выделяет шелл сам (это работа T4.6, её нельзя сделать дважды).

**Files:**
- `multiprocess_prototype/frontend/pult/connections.py` — `BackendConnection` (Pydantic), `ConnectionStore`
  (YAML через `ruamel.yaml`, путь по умолчанию `INSPECTOR_CONFIG_DIR/pult.yaml`)
- `multiprocess_prototype/frontend/pult/bootstrap.py` — N сессий: на каждое подключение свой
  `SocketClient` + `Remote*` + `AppServices`; ошибки одной сессии не выбрасываются в другие
- `multiprocess_prototype/frontend/pult/workspace.py` — верхнеуровневый `QMainWindow` с
  `QDockWidget` на бэкенд; меню «Подключения» (добавить/удалить/подключить/отключить); индикатор
  состояния на каждой вкладке
- `multiprocess_prototype/frontend/pult/tests/test_connections.py`, `test_workspace.py` (pytest-qt на
  двух in-process `SocketChannel(port=0)`)

**Steps:**
1. `ConnectionStore`: load/save round-trip с комментариями; валидация `host:port`; токен в файле
   **не хранится** — ссылка на env-переменную (`token_env: PULT_TOKEN_INSPECTOR`) либо ввод при
   подключении.
2. Сессия на подключение — отдельный объект с собственным жизненным циклом (connect/disconnect/
   reconnect), никаких глобальных синглтонов `AppServices` (проверить по коду, что `AppServices` не
   синглтон; если синглтон — это находка: адаптер, не правка виджетов).
3. Раскладка: `QDockWidget` на бэкенд; двойной клик по заголовку — floating; `saveState` в
   `pult.yaml`-соседний файл при закрытии, `restoreState` при старте.
4. Автор пишет hazard-тесты: (а) два подключения к **одному** бэкенду (оператор ошибся) — работают
   оба, подписки не смешиваются (у каждого свой `SocketClient`/сессия); (б) удаление подключения при
   живой сессии — сессия закрыта, виджеты уничтожены, потоков клиента не осталось (счётчик
   `threading.active_count()` до/после).

**Acceptance criteria:**
- [ ] Два бэкенда (два in-process `SocketChannel` на `port=0` с разными процессами-стабами):
      `Workspace` показывает две верхнеуровневые вкладки с именами из `pult.yaml`; в каждой — свой
      набор внутренних вкладок.
- [ ] Команда из вкладки A приходит **только** на бэкенд A (спай на стабе B — 0 вызовов); стейт
      бэкенда B меняется — виджеты A не получают колбэк.
- [ ] Остановка бэкенда A: вкладка A показывает «отключён», вкладка B продолжает получать кадры
      (счётчик кадров B за 10 с ≥ 0.8 × прежнего).
- [ ] Отстыковка вкладки A (программно `setFloating(True)`) → отдельное окно верхнего уровня
      (`isWindow()`), содержимое то же (тот же объект виджета); пристыковка обратно — окно исчезает.
- [ ] `pult.yaml` round-trip: load → save без изменений байт-в-байт для файла с комментариями;
      файл с `port: "abc"` → понятная ошибка валидации с именем поля.
- [ ] В `pult.yaml` после сохранения нет значения токена (`grep` по значению → 0).

**Out of scope:** обнаружение бэкендов в сети (mDNS и т.п.); единая «сводная» вкладка по всем
бэкендам; права доступа.
**Edge cases:** ноль подключений — Пульт открывается с пустым рабочим пространством и меню
«Подключения», не падает; подключение с тем же именем дважды — валидация.
**Dependencies:** Task 1.4.
**Module contract:** impl-only (`frontend/pult` уже new-full из 1.4; здесь наполняется).

### Task 3.2 — Вкладка «Симулятор»: Пульт подключён к дереву line-sim

**Level:** Middle (Sonnet)
**Assignee:** developer
**Goal:** второе подключение Пульта — бэкенд симулятора (`apps/line_sim`, **уже есть** на ветке
`feat/line-sim`: процессы `robot`/`camera`/`pult`, `BACKEND_CTL` 8766, стенд двух приложений снят
2026-09-21). Штатные вкладки (процессы, дисплеи, настройки, наблюдаемость) работают против
симулятора **без sim-специфичного кода** — дисплей сцены виден рядом с дисплеем инспектора. Это
точка посадки line-sim Ф6 (Qt-вкладка поверх готовых команд `belt.*` 2.3a; веб-пульт 2.3b на 8092
уже есть и остаётся) и Ф7.3 (Qt-редактор объектов) — они добавляют вкладки внутрь этого подключения,
не меняя Пульт.

**Контекст:** если штатные вкладки требуют правок под «второе приложение» — это находка для
конструктора (`QUEUE` P-2: «второе приложение чужими руками»), не для этого плана: записать, не
чинить здесь, кроме тривиального.

**Files:**
- `multiprocess_prototype/frontend/pult/README.md` — раздел «Два бэкенда: инспектор + симулятор»,
  пример `pult.yaml`
- Правки кода — только по находкам (каждая названа в PR); ожидаемый объём — 0
- НОВЫЙ `docs/reviews/2026-XX-XX_pult-two-backends.md` — отчёт приёмки с скриншотом/числами

**Steps:**
1. Поднять инспектор (`BACKEND_CTL_PORT=8765`) и симулятор (`8766`) на одной машине; Пульт с
   `pult.yaml` из двух записей.
2. Пройти по каждой штатной вкладке в подключении «Симулятор»: что показывает, что не работает
   (например, вкладка рецептов ждёт структуру рецепта прототипа) — таблица «вкладка / работает /
   почему нет».
3. Дисплей сцены симулятора (процесс `camera`, плагин `scene_source` — line-sim 2.2: спрайт едет по
   энкодеру; после Ф3 — диски с буквами) виден и обновляется; дисплей `main` инспектора рядом показывает
   те же кадры, пришедшие через поток (`mjpeg_sink` → бэкенд `stream`, line-sim 1.2) — два дисплея одного
   источника через разные дороги.
4. Отстыковать «Симулятор» в отдельное окно — работает (3.1).

**Acceptance criteria:**
- [ ] Пульт с двумя записями подключается к обоим; `capabilities` каждого показаны во вкладке
      процессов (список процессов симулятора содержит `robot`, `camera` и `pult` — как в
      `apps/line_sim/pipeline.yaml` на момент задачи, инспектора — `camera_0`, `vision`, …).
- [ ] Дисплей сцены симулятора обновляется в Пульте ≥ 0.8 × fps сцены (fps — из
      `introspect_router_stats` симулятора).
- [ ] Таблица вкладок для подключения «Симулятор» заполнена для ВСЕХ штатных вкладок; у каждой
      неработающей названа причина и заведена строка находки (в отчёт), а не «TODO».
- [ ] Ни одного файла с условием вида `if backend_name == "line_sim"` в `frontend/pult` (grep → 0):
      Пульт не знает, что второе подключение — симулятор.
- [ ] `docs/reviews/…_pult-two-backends.md` с числами и разделом «что не проверено».

**Out of scope:** контролы симулятора (line-sim Ф6), редактор (line-sim Ф7.3), правда/счётчики
(line-sim Ф5).
**Edge cases:** симулятор поднят, инспектор нет — вкладка симулятора полностью функциональна,
инспектор в «отключён»; оба на одном порту по ошибке конфига — валидация `ConnectionStore`
(дубликат `host:port`) с понятным текстом.
**Dependencies:** Task 3.1; `apps/line_sim` в `main` (merge `feat/line-sim` — line-sim 1.1/1.3 уже закрыты).
**Module contract:** impl-only.

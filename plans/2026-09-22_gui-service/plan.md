## Контекст — решение владельца 2026-09-22

Три формулировки владельца в одном разговоре, приведены близко к тексту:

1. «Прототип не знает о симуляторе, но графический интерфейс было бы правильно сделать как
   **отдельный сервис, который даёт управление прототипом, и в него же можно сделать вкладку
   симулятора**. Также можно сделать **два графических окна отдельно**, чтобы их разделить.
   Основная философия: графический интерфейс, который находится в прототипе, — это тоже своего рода
   сервис, который помогает **объединить всё для человека и отобразить**».
2. «Чтобы можно было **симулятор запустить на другой машине** и по локальной сети передавать
   **кадры и управление**».
3. Редактор объектов (слои): мышью двигать/вращать/масштабировать **и значениями**, интерфейс
   дублируется **в HTML и в Qt** (это уходит в `line-sim` Ф7, здесь — только место для Qt-клиента).

**Что это значит архитектурно — три сервиса, не два:**

```
                 ┌──────────── Пульт (этот план) ─────────────┐
                 │ вкладка/окно «Инспектор»  вкладка/окно «Симулятор» │
                 └───────┬─────────────────────────────┬───────┘
     SocketChannel: команды/стейт/логи   SocketChannel: те же
     кадры: SHM по имени | поток по сети  кадры: SHM по имени | поток по сети
                 ▼                                     ▼
        ┌─ дерево Инспектора ─┐              ┌─ дерево Симулятора ─┐
        │ camera → vision →   │ ◄─ Modbus ──►│ лента · ПЧ · робот   │  (line-sim)
        │ recog → robot       │ ◄─ кадры ────│ сцена · правда       │
        └─────────────────────┘              └──────────────────────┘
```

- Бэкенды остаются headless-деревьями фреймворка (`SystemLauncher → ProcessManager`), друг о друге не знают.
- Пульт — **не процесс ни одного дерева**. Он подключается снаружи к N бэкендам и рисует их.
  Вкладка на бэкенд или окно на бэкенд — раскладка одних и тех же виджетов, не архитектура.
- Симулятор становится сервисом **без Qt вообще**: его пульт и редактор живут в Пульте.

## Сборка из сервисов (ред. 2, 2026-09-23)

Вынесено в [`architecture.md`](architecture.md): сервис как вертикальный срез, Пульт как хост
`GuiAppSpec`-пакетов, кто что владеет после плана, auth на бэкенде, целевое состояние «один режим GUI».
Читать до approve — это несущая часть ред. 2.

**Что становится дешевле после этого плана:** line-sim Ф6 (пульт симулятора) больше не тянет Qt в
дерево симулятора; редактор Ф7.3 — ещё одна вкладка Пульта; наблюдаемость Пульта как клиента
одинакова для всех бэкендов.

## Цели

- `python -m apps.pult --connect 127.0.0.1:8765` поднимает тот же набор вкладок, что
  `frontend/run.py`, **без** `SystemLauncher` в этом процессе и без импорта `multiprocess_prototype`
  хостом; дисплеи идут с той же частотой (baseline и допуск — Task 1.4).
- Ни одна сборка GUI не читает и не пишет `recipes/`/`app.yaml` с диска: рецепт принадлежит
  бэкенду, GUI редактирует черновик и сохраняет командой (фаза 1b).
- Убийство Пульта не меняет счётчики бэкенда; убийство бэкенда переводит Пульт в «отключён» и
  он сам восстанавливается при возврате бэкенда.
- Пульт на машине B видит дисплеи и управляет бэкендом на машине A; без токена соединение
  отвергается; `bind 0.0.0.0` без токена — бэкенд **не поднимает** endpoint (fail-closed).
- Инспектор и симулятор — рядом, вкладками или окнами; отвал одного не трогает другой.
- Регрессия: встроенный путь `frontend/run.py` работает как прежде, pytest-qt сьюта зелёная
  (число baseline фиксируется в Task 1.1).

## Out of scope

- Перенос файлов `frontend_module` во фреймворк/свой пакет (rework Р-4, frontend-constructor Блок В).
  Этот план **добавляет** файлы в существующие места, переносить будет codemod.
- Наблюдаемость самого Пульта как процесса фреймворка (он вне дерева; логи — `get_std_logger` в файл;
  порт наблюдений Пульта — после v1, см. «Открытые вопросы»).
- Пульт через интернет / TLS как обязательный / многопользовательские права. v1 — доверенная LAN,
  PSK-токен обязателен вне localhost, TLS — опция.
- Веб-версия Пульта. HTML в v1 — только редактор объектов (line-sim Ф7.2).
- Мобильный клиент, удалённый доступ через VPN-специфику.

## Риски и ограничения

- **Неизмеренные in-tree допущения** — главный риск сроков; снимается Task 1.1 до кода.
- **Окно codemod rework** — этот план добавляет файлы в `router_module/channels/`,
  `frontend_module/bridge/`, `multiprocess_prototype/frontend/`; если окно откроется во время Ф1–Ф3 —
  план ставится на паузу (правило «один активный план на полосу»), не сливается поверх codemod.
- **Один стенд.** Live-задачи (1.4, 2.x, 3.x) и live-задачи line-sim не идут одновременно на одном
  бэкенде; с двумя бэкендами — по порту.
- **Зависимость от чужих планов, не стартовавших:** frontend-constructor T4.2 (перед 1.4) — в прототипе/
  фреймворке без переноса файлов, окна не требует; если владелец её не запускает — её объём добавляется к
  1.4 явно, а не «само получится». Транспорт двери (бывшая remediation 3.1/3.3) — уже свой, Task 1.3a.
- **План писался против устаревшего `main` (найдено 2026-09-22):** ветка `feat/line-sim` на 112 коммитов
  впереди, и то, от чего этот план «зависел» (дверь кадров, дерево симулятора), там уже сделано иначе,
  чем здесь предполагалось. Ссылки исправлены; **до approve — merge `feat/line-sim` в `main`**, иначе
  Task 1.1 снимет baseline на дереве без `apps/line_sim` и `stream`-бэкенда, и числа придётся переснимать.
- **SHM вне леджера** — торн-кадры измеряются, не отрицаются (см. «Открытые вопросы»).
- **PSK без TLS** — перехватываем в LAN; принято для v1 явно, см. decisions log.
- **Тестовый канон (STRICT, `.claude/CLAUDE.md`):** независимый `tester` на КАЖДОЙ задаче, синхронно,
  в worktree на пред-коммите, только по acceptance criteria; break-injection по каждому свойству;
  `reviewer` синхронно после каждой задачи; на 2.2 — `reviewer` в режиме security обязателен.

## Замечания
- [major/dryrun] Свойство «путь стопа не бросает на плохом `timeout`» (DESIGN 7) не защищено тестом. Если убрать вызов `_stop_timeout_s` из `_stop_many`, все тесты автора остаются зелёными.
  Инъекция в памяти (scratchpad `cr1/inj_coerce.py`): `timeout_s = self._stop_timeout_s(timeout)` → `timeout_s = timeout`. Результат: `test_stop_many_with_bad_timeout_does_not_raise` → GREEN; `test_registry_timeout_coercion[inf|nan|None]` → GREEN. При этом живой вызов `stop_many(["Q"], math.nan)` на дублёре → `ValueError budget_s: ожидается конечное число, получено nan`.
  Причина: первый тест берёт только `ghost`, а для него `_stop_many` возвращается до `open_scope` (`process_registry.py`, `if stop is None: return result`). Второй тест зовёт приватный метод напрямую. В матрице лида inj-18 правит само тело `_stop_timeout_s`, вызов из `_stop_many` она не трогает.
  Исправить: тест на наблюдаемый эффект — живой дублёр, `stop_many([...], timeout=nan | None | "x")` → без исключения, `{name: True}` после эскалации. Добавить инъекцию «сырой timeout в `open_scope`» с прогнозом «красен этот тест».
- [minor/design] Если `is_alive()` бросает, предупреждение пишется на каждом проходе опроса. `ChildProcessStop._alive` (`child_process_stop.py:104-109`) зовёт `_emit("warning", …)` при каждом исключении. Проверка (`cr1/races.py`, сценарий d): дублёр с падающим `is_alive()`, `join_until(now + 1.0)` → `warnings_in_1s=21`. При graceful 5,0 с и эскалации 2,0 с это около 140 строк на один процесс в логе PM. Классификация «жив» и выживший без метки при этом верны (`survivors=('D',)`).
  Исправить: писать одну строку на имя, как уже сделано для «нет stop_event» (`_missing_event_logged`). Добавить тест «одно предупреждение за `join_until`».
- [nit/context] Для 1.2 не записано: типизированный конфиг ребёнка молча отбрасывает ключ `stop_budget`. Проверка (`cr1/races.py`, пункт 6): `GenericProcessConfig.model_validate({"name": "R", "class": "x.Y", "stop_budget": stop_budget(5.0)})` → ошибки нет, `__pydantic_extra__=None`, атрибута `stop_budget` нет. До раннера словарь доезжает: `cr1/child_cfg.py` → `runner reads from custom.process_config: stop_budget in child cfg = True`, с SRM и без него. Читатель в 1.2 должен брать словарь из сырого конфига или завести поле.
  Исправить: строка «для 1.2 (г)» в ADR-PMM-035 и в `1.1.result.md`.
- [nit/process] В `tasks/1.1.result.md` нет строки с токенами задачи. DESIGN 10 требует: «токены задачи — строкой в нём». `grep -n -i -E "токен|token"` по файлу → 0 совпадений. Исправить: дописать строку.

## Что я оставил открытым / ненадёжным
- «Упрямый» процесс — дублёр, а не настоящий процесс: на Windows `terminate()` убивает сразу. POSIX и Linux не гонял, в том числе сбор зомби в `is_alive()` из двух потоков (`request_stop` из чужого потока в 1.2).
- Живой стенд и `1.1.probe.md` не трогал — их меряет другой агент.
- Инъекции из замечания 1 и проверку inj-6 делал подменой в памяти (`exec` и monkeypatch), не правкой файла. Повторного прогона полной матрицы лида не было.
- Строгий `stop_budget` в `_create_components` PM: невалидный `shutdown_timeout` в конфиге (строка, отрицательное) теперь не даст PM стартовать. Раньше PM стартовал и падал только на стопе. Сознательный fail-fast по DESIGN 2; есть ли такие конфиги у прототипа, не проверял.
- Как ведёт себя ProcessModule с неизвестным верхним ключом вне `GenericProcessConfig` (другие классы процессов), не смотрел.
- qex недоступен, sentrux не запускал; поиск — `git grep` по путям. Промежуточные находки — в scratchpad `cr1/findings.txt`.

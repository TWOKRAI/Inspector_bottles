Суть. Сегодня `BaseManager.shutdown()` абстрактный (`base_manager/core/base_manager.py:66-67`), у менеджера нет области. У `BaseManager.scope` поэтому нет живого вызывающего в проде — это контракт (принцип владельца 3), и G-6 обязателен. Долги — в ADR-BM-009, раздел «Отложенное»: `WorkerManager._on_shutdown` зовёт `stop_all_workers()` без срока; внутренний порядок `StateStoreManager` не меняется.

## Гарантии для инъекций (предсказания пишет лид)

- G-1. `shutdown()` зовёт `_on_shutdown()` ровно один раз за жизнь объекта при любом числе вызовов.
- G-2a. Через корень: область менеджера (`proc/p/planes/stats_manager-scope`) закрыта раньше вызова `shutdown()` этого менеджера.
- G-2b. Прямой `shutdown()` у класса без своего `shutdown` (тестовый подкласс): область закрыта раньше `_on_shutdown()`.
- G-3. `shutdown()` возвращает `bool(_on_shutdown())`; исключение в `_on_shutdown()` → `False` и строка лога `shutdown <manager_name>: _on_shutdown упал: <ExcType>: <текст>`; область закрыта.
- G-4. Без привязки: `scope is None`, `shutdown()` работает; `G3 unclosed roots` — ровно 105, все `t02…`/`t-…` (`test_lifetime_scope_acceptance.py:65`, `test_lifetime_scope.py:54`); путей `proc/` — 0.
- G-5. pickle с привязанной областью проходит; после распаковки `scope is None`.
- G-6. После `initialize()`: `proc.stats_manager.scope.spawn(t, name="t")`; шпион на экземпляре `proc.stats_manager.shutdown`; `proc.shutdown()` → поток `t` вышел раньше вызова шпиона.
- G-7. Порядок корня 1.2a (G7) не меняется.
- G-8. (1.2b-3) подкласс, определяющий `shutdown`, — `TypeError` при определении класса.
- G-9. (1.2b-2) производственных подклассов со своим `shutdown` после кодмода — `0`.
- G-10. Второй `shutdown()` из другого потока возвращает результат первого.
- G-11. Реентрантный `shutdown()` из `_on_shutdown` → `False` сразу, без ожидания (тест под сроком). Вызов из потока поддерева области менеджера — первый или нет — сразу `False`; останов не начинает, флаг «идёт» не ставит, `_on_shutdown` не зовёт.
- G-11b. Корень: поток области менеджера зовёт `shutdown()` → `False`; `_on_shutdown` идёт на главном потоке (не на потоке области), область к этому моменту закрыта.
- G-14. К менеджеру привязана подделка `IScope` (не `Scope`): `shutdown()` работает, `AttributeError` нет; срок второго вызова — `_DEFAULT_SECOND_CALL_WAIT_S` (5,0 с).
- G-12. Повторный `attach_scope` → `RuntimeError`.
- G-13. Области получают ровно атрибуты корня из DESIGN 4.

### Решения (DESIGN)

DESIGN (decided by the lead — you type it, you do not derive it):
  Module contract: public-api-change (`base_manager`: `BaseManager.shutdown` конкретный, новые `_on_shutdown`, `scope`, `attach_scope`).
  1. Шаблон (`base_manager/core/base_manager.py`). `shutdown() -> bool`:
     - первый вызов: под локом объекта ставит «идёт», запоминает поток; закрывает привязанную область (`scope.close()`), затем `result = bool(self._on_shutdown())`; исключение → `False` и строка лога `shutdown <manager_name>: _on_shutdown упал: <ExcType>: <текст>` (`self._log_error`, если есть, иначе `emergency_log`); результат кэшируется, событие «готово» взводится;
     - вызов из потока, который выполняет этот `shutdown()` (реентрантный из `_on_shutdown`) → `False` сразу, без ожидания;
     - вызов из потока поддерева области менеджера — первый или нет — сразу `False`; останов не начинает, флаг «идёт» не ставит, `_on_shutdown` не зовёт. Правило то же, что у `Scope._close` (`lifetime.py:690-692`);
     - поддерево и срок даёт внутренняя функция `_manager_scope_view(scope) -> tuple[bool, float]` в `base_manager/core/lifetime.py` (`in_subtree`, `wait_s`): для `Scope` — `(scope._is_subtree_thread(), scope.budget_s + scope.kill_reserve_s)` (`lifetime.py:673-681`); для не-`Scope` (подделка `IScope`) — `(False, _DEFAULT_SECOND_CALL_WAIT_S)`; без области — тот же `_DEFAULT_SECOND_CALL_WAIT_S`. Константа `_DEFAULT_SECOND_CALL_WAIT_S = 5.0` — там же. Тот же пакет `base_manager/core`, новой публичной API нет;
     - вызов из любого другого потока ждёт «готово» не дольше `wait_s`; на сроке → `False` и одна строка лога `shutdown <manager_name>: первый вызов не завершился за <N> с — второй вызов вернул False`;
     - после завершения первого — его кэшированный результат.
     `_on_shutdown()` по умолчанию `return True` (мягкий режим: абстрактным не делать, иначе 29 классов сломаются до 1.2b-2). Флаг «идёт» ставится ДО `_on_shutdown`.
  2. Область. `scope` — свойство только для чтения, `None` до `attach_scope(scope: IScope)`; повтор `attach_scope` → `RuntimeError`. Хранение — модульный `weakref.WeakKeyDictionary` менеджер → область, запись под модульным локом; в `__dict__` области нет (Р7 (б)), pickle её не видит. Ленивого корня нет (G3, `task-0.2.md:31-34`). `IBaseManager` (`base_manager/interfaces.py:43-44`): docstring `shutdown` получает Post-строки — «один раз за жизнь; сначала закрывается `scope`; исключение `_on_shutdown` → `False`; реентрантный вызов → `False`»; добавляется абстрактное свойство `scope -> IScope | None` только для чтения. `attach_scope` в интерфейс не идёт: это деталь проводки корня, как `lifetime_segments` (вызывает только `ProcessModule`).
  3. Р4 (`IProcessModule`, раннер) — не в 1.2b-1: перенесён в 1.2b-2 (бюджет teamlead).
  4. Области менеджеров корня (`process_module.py`). Сразу после каждой регистрации `_attr_call(attr, "shutdown", …)` (:517-528, :795-798): если `getattr(self, attr)` — `BaseManager` без области, то `child = segment.child(f"{attr}-scope")` и `manager.attach_scope(child)`. LIFO закрывает область раньше записи `_attr_call`. Атрибуты при `ProcessModule("p", config={})`:
     - получают область (`BaseManager`): `stats_manager` → `proc/p/planes/stats_manager-scope`; `observation_manager` → `proc/p/planes/observation_manager-scope`; `router_manager` → `proc/p/transport/router_manager-scope`; `command_manager` → `proc/p/transport/command_manager-scope`; `console_manager` → `proc/p/transport/console_manager-scope`;
     - `None` при `config={}`, области нет: `error_manager`, `shared_resources`; при наличии — `proc/p/planes/error_manager-scope`, `proc/p/transport/shared_resources-scope`;
     - `_orchestrator` — не `BaseManager` (`plugin_orchestrator.py:24`), области нет;
     - `logger_manager` и `worker_manager` — не через `_attr_call` (`_stop_logger_entry` :408/:522, `_WorkersStop` :278), области не получают; логгер гасится последним по своему пути, воркеры — адаптером.
     Подмена менеджера после `initialize()` области не получает — её закроет `_attr_call` через `shutdown()`. `ProcessModule.shutdown` (:341) в 1.2b-1 не трогать.
  5. Импорт `IScope` — из `base_manager.interfaces`; `core.lifetime` вне пакета не импортировать (G6 R7).
  6. Документы: ADR-BM-009 в `base_manager/DECISIONS.md` (шаблон, мягкий режим, Р1/Р7/Р8, правило реентрантности, отвергнутое, раздел «Отложенное»: FREEZE-долги и риск Р1 (а) для внешних подклассов); `python -m scripts.sync`; README/STATUS `base_manager` и `process_module` — по строке.

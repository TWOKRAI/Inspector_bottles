  1. `ProcessModule` (`multiprocess_framework.modules.process_module`): `attach_stop_budget(budget: dict)` до `initialize()`; без него процесс берёт `{"work_s": 3.0, "infra_s": 1.0}`. После `initialize()` свойство `lifetime_segments` — dict ровно с ключами `"planes"`, `"transport"`, `"work"`; значения — области (`own`, `cancel`, `close` по контракту `IScope` из `multiprocess_framework.modules.base_manager.interfaces`). До `initialize()` — пустой dict. Наследник может переопределить `_own_work(self, work)` — регистрировать свои ресурсы в `work` (вызывается внутри `initialize()`); для своих записей используйте его или `lifetime_segments[...]`.
  2. `stop()` не блокирует: возвращается за ≤ 0,2 с, даже если запись в `work` держит выход 2 с; после `stop()` ресурс-Stoppable в `work` получил `request_stop()`, а ни один менеджер ещё не погашен. Гасит `shutdown()`: возвращает `bool`; второй вызов ничего не гасит повторно. `close_root()` возвращает отчёт корня (`CloseReport`: `survivors`, `errors`, `ok`), повтор — тот же объект.
  3. Порядок закрытия (golden G7) у процесса, собранного `ProcessModule("p", config={})` + `initialize()`: замените атрибуты процесса записывающими дублёрами ПОСЛЕ `initialize()` — `worker_manager` (объект с `stop_all_workers(timeout=...)`, `list_workers()` → `[]`, `is_worker_running(name)` → `False`), `_orchestrator` (`shutdown()`), `shared_resources` (`shutdown()`), `router_manager`, `command_manager`, `console_manager`, `error_manager`, `stats_manager`, `observation_manager`, `logger_manager` (каждый — `shutdown()`), а также методы экземпляра `_uninstall_process_hooks` и `_flush_observability` (присвоение атрибута экземпляру); регистрация читает атрибут в момент закрытия. Литерал последовательности после `shutdown()`: `["workers", "plugins", "hooks", "flush", "console", "command", "router", "srm", "observation", "stats", "error", "logger"]`. Статус STOPPED пишется между `error` и `logger` (наблюдать через подмену `update_process_state` записывающим дублёром — запись `"status:stopped"` стоит после `"error"` и до `"logger"`).
  4. Барьеры: Stoppable-дублёр в `planes` получает `request_stop()` только после того, как закрылось всё в `work` (метки `time.monotonic()` или журнал событий: `request_stop` стока позже конца `join_until` записи в `work`, которая держит выход 0,3 с).
  5. Бюджет: процесс с `attach_stop_budget({"work_s": 0.6, "infra_s": 0.2, "pm_graceful_s": 1.0, "pm_total_s": 3.0, "outer_s": 4.5})` и Stoppable в `work`, который не останавливается никогда (`join_until` ждёт до срока и возвращает `False`, `kill` нет): `close_root()` возвращается не раньше 0,55 с и не позже 0,95 с; имя записи — в `survivors`.
  6. Раннер `multiprocess_framework.modules.process_manager_module.runner.process_runner`: константа `EXIT_SURVIVORS == 76`; модульная `_hard_exit(code)` — подменяйте её `monkeypatch` (настоящий `os._exit` убьёт pytest). `run_process_function(class_path, name, stop_event=<уже взведённое Event>, shared_resources_or_bundle=<SharedResourcesManager>, exit_report=[0, 0, 0])` в процессе pytest (образец — `process_manager_module/tests/test_process_runner.py`). Класс процесса — функция-уровня-модуля класс в вашем файле, наследник `ProcessModule`, с `_own_work`. Выжившие в отчёте корня → `_hard_exit` вызвана ровно один раз с `76`, и к моменту вызова слот `exit_report[0] == 1`. Нет выживших → не вызвана. Единственный выживший с суффиксом ` (self)` в имени пути → не вызвана. Короткий бюджет ребёнку в SRM-режиме: положите `{"shutdown_timeout": 0.5}` или словарь `stop_budget` в `process_config` процесса через `custom` его `process_data` (как раннер читает конфиг — `process_runner.py:338-343`); раннер берёт `stop_budget` из конфига, иначе считает его из `shutdown_timeout`.

PM (`ProcessManagerProcess`): запись «stop summary:» (сводка стопа) публикуется раньше `_flush_observability`; при `shutdown()` дважды подряд БЕЗ `stop()` дети останавливаются один раз (событие стопа каждого ребёнка взведено один раз, сводка — одна запись).

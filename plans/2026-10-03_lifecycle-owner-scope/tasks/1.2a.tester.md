DESIGN (decided by the lead — you type it, you do not derive it):
  1. `ProcessModule` (`multiprocess_framework.modules.process_module`): `attach_stop_budget(budget: dict)` до `initialize()`; без него процесс берёт `{"work_s": 3.0, "infra_s": 1.0}`. После `initialize()` свойство `lifetime_segments` — dict ровно с ключами `"planes"`, `"transport"`, `"work"`; значения — области (`own`, `cancel`, `close` по контракту `IScope` из `multiprocess_framework.modules.base_manager.interfaces`). До `initialize()` — пустой dict. Наследник может переопределить `_own_work(self, work)` — регистрировать свои ресурсы в `work` (вызывается внутри `initialize()`); для своих записей используйте его или `lifetime_segments[...]`.
  2. `stop()` не блокирует: возвращается за ≤ 0,2 с, даже если запись в `work` держит выход 2 с; после `stop()` ресурс-Stoppable в `work` получил `request_stop()`, а ни один менеджер ещё не погашен. Гасит `shutdown()`: возвращает `bool`; второй вызов ничего не гасит повторно. `close_root()` возвращает отчёт корня (`CloseReport`: `survivors`, `errors`, `ok`), повтор — тот же объект. Без `initialize()` `shutdown()` возвращает `True` и ничего не гасит.
  3. Порядок закрытия (golden G7) у процесса, собранного `ProcessModule("p", config={})` + `initialize()`: замените атрибуты процесса записывающими дублёрами ПОСЛЕ `initialize()` — `worker_manager` (объект с `stop_all_workers(timeout=...)`, `list_workers()` → `[]`, `get_worker_status(name)` → `{"is_alive": False}`), `_orchestrator` (`shutdown()`), `shared_resources` (`shutdown()`), `router_manager`, `command_manager`, `console_manager`, `error_manager`, `stats_manager`, `observation_manager`, `logger_manager` (каждый — `shutdown()`), а также методы экземпляра `_uninstall_process_hooks` и `_flush_observability` (присвоение атрибута экземпляру); регистрация читает атрибут или метод в момент закрытия. Литерал последовательности после `shutdown()`: `["workers", "plugins", "hooks", "flush", "console", "command", "router", "srm", "observation", "stats", "error", "logger"]`. Статус STOPPED пишется между `error` и `logger` (наблюдать подменой `update_process_state` записывающим дублёром — запись `"status:stopped"` стоит после `"error"` и до `"logger"`).
  4. Барьеры: Stoppable-дублёр в `planes` получает `request_stop()` только после того, как закрылось всё в `work` (журнал событий: `request_stop` стока позже конца `join_until` записи в `work`, которая держит выход 0,3 с).
  5. Бюджет: процесс с `attach_stop_budget({"work_s": 0.6, "infra_s": 0.2, "pm_graceful_s": 1.0, "pm_total_s": 3.0, "outer_s": 4.5})`, менеджеры которого после `initialize()` заменены дублёрами без задержки (как в п.3), и Stoppable в `work`, который не останавливается никогда (`join_until` ждёт до срока и возвращает `False`, `kill` нет): `close_root()` возвращается не раньше 0,5 с и не позже 0,95 с; путь записи — в `survivors`.
  6. Раннер `multiprocess_framework.modules.process_manager_module.runner.process_runner`: модульная `_hard_exit(code)` — подменяйте её `monkeypatch` (настоящий `os._exit` убьёт pytest); код выживших — `EXIT_SURVIVORS == 76` из `multiprocess_framework.modules.process_manager_module.core.stop_budget`. Вызов в процессе pytest: `run_process_function(class_path, name, stop_event=<уже взведённое multiprocessing.Event>, shared_resources_or_bundle=srm, exit_report=[0, 0, 0])` (образец — `process_manager_module/tests/test_process_runner.py`). Класс процесса — класс уровня модуля в вашем файле, наследник `ProcessModule`, с `_own_work`. Конфиг ребёнка в SRM-режиме (проверено лидом): `srm = SharedResourcesManager()`; `srm.process_state_registry.register_process(name)`; `srm.get_process_data(name).custom["process_config"] = {...}` — раннер берёт этот словарь как конфиг процесса. Наблюдения:
     - выжившие в отчёте корня → `_hard_exit` вызвана ровно один раз с `76`, и к моменту вызова `exit_report[0] == 1`;
     - нет выживших → не вызвана; единственный выживший — поток, закрывающий свою же область (путь с суффиксом ` (self)`) → не вызвана;
     - `stop_budget` из конфига доходит до процесса: в `custom["process_config"]` положите `{"stop_budget": {"work_s": 0.6, "infra_s": 0.2, "pm_graceful_s": 1.0, "pm_total_s": 3.0, "outer_s": 4.5}}`; класс процесса переопределяет `attach_stop_budget`, запоминает аргумент и зовёт `super()`; после раннера запомненный словарь равен этому литералу. Без ключа `stop_budget`, с `{"shutdown_timeout": 1.0}` — запомненный словарь равен `{"work_s": 0.6, "infra_s": 0.2, "pm_graceful_s": 1.0, "pm_total_s": 3.0, "outer_s": 4.5}` (сравнение `pytest.approx`).
  7. PM (`multiprocess_framework.modules.process_manager_module.process.process_manager_process.ProcessManagerProcess`) — рецепт сборки, проверен лидом на текущем коде (сборка без детей: `initialize()` → `True` за 0,11 с, `shutdown()` → `True` за 0,52 с, после — только `MainThread`):

     - ПОСЛЕ `initialize()` на экземпляре: `pm._publish_stop_summary = рекордер(stop_results)`; `pm._flush_observability = рекордер()`; `pm._process_registry = FakeRegistry()` — реестр читается в момент остановки, не при сборке. `FakeRegistry` даёт `children_stop(*, mark_reader_gone)` → объект-группа с `request_stop()`, `join_until(deadline) -> True`, `kill()`, `close()`, `result() -> {"child": True}` (каждый вызов в журнал), и `exit_report(name) -> {"released": 0, "buffered_dropped": 0, "reported": True}`;
     - наблюдения: после `shutdown()` в журнале `request_stop` группы раньше записи сводки, сводка (`_publish_stop_summary` с `{"child": True}`) раньше `flush` (тест 9); `shutdown()` дважды подряд БЕЗ `stop()` → `children_stop` вызван один раз, `request_stop` группы — один раз, сводка — одна (тест 10);

## What I interpreted rather than followed

- G-24 для `ProcessModule`: срок = `work_s + 0.2` (0.6 + 0.2 = 0.8; в замере 0.3 + 0.2 = 0.5), не `work_s + infra_s`. Так понял литерал «0.6 + 0.2» (`0.2` — добавка, не `infra_s`). Для PM — `pm_total_s + 0.2`.
- Формула второго вызова: `(budget + kill_reserve области, иначе 5.0) + _ON_SHUTDOWN_WAIT_S`. Из G-15 (0.9 = 0.3 + 0.2 + 0.4; 5.4 = 5.0 + 0.4) и G-24 (5.5: корень `ProcessModule` к `scope` менеджера не привязан, значит 5.0 + 0.5).
- G-24 замер: подкласс `ProcessModule._on_shutdown` после события зовёт `super()._on_shutdown()` (для уборки реальных менеджеров). Предположил, что `ProcessModule._on_shutdown` существует (G-9a это требует) и что вызов после отпускания события безопасен.
- G-22б: `shutdown_nowait()` не возвращается, пока бегущая задача не закончит (иначе «длина 1» гоняла бы). Если вернётся раньше — тест краснеет по длине 0, это вопрос к лиду.
- G-19 «ровно один вызов `attach_stop_budget` с этим словарём»: сравнение `pytest.approx` со словарём; `close_root` считается обёрткой подкласса; `shutdown` 0.
- G-20 duck и mock: раннер получает класс по `class_path` и вызывает конструктор любым набором аргументов (`*args, **kwargs`); для `MagicMock` путь — функция-фабрика на уровне модуля. Раннер принял оба варианта (зелёный mock-тест).
- G-9 в статике: «производственный» = не в каталоге `tests`, не `test_*.py`, не `conftest.py`; потомок `BaseManager` — по простым именам баз, транзитивно по всем файлам шести корней.
- Имя менеджера в строке G-24 (`…`): сравниваю хвост строки без префикса `shutdown <имя>:`.

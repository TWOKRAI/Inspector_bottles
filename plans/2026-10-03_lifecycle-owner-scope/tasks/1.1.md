  1. Новый файл `multiprocess_framework/modules/process_manager_module/core/stop_budget.py`, только stdlib, без импорта PM.   2. Функция `stop_budget(shutdown_timeout) -> dict[str, float]`, ключи строго в этом порядке: `work_s`, `infra_s`, `pm_graceful_s`, `pm_total_s`, `outer_s`. `pm_graceful_s = float(shutdown_timeout or DEFAULT_SHUTDOWN_TIMEOUT_S)` (`None`, `0`, `0.0` дают 5,0, как прежнее `get_config(...) or 5.0`); `pm_total_s = pm_graceful_s + TERMINATE_GRACE_S + KILL_CONFIRM_S`; `outer_s = pm_total_s + PM_TEARDOWN_MARGIN_S`; `child_total = CHILD_STOP_FRACTION * pm_graceful_s`; `infra_s = min(INFRA_STOP_S, child_total / 4)`; `work_s = child_total - infra_s`. Литералы: 5,0 → work 3,0, infra 1,0, pm_graceful 5,0, pm_total 7,0, outer 8,5; 1,0 → work 0,6, infra 0,2, pm_graceful 1,0, pm_total 3,0, outer 4,5 (сравнение через `pytest.approx`); `None` и `0` → как 5,0. NaN, ±inf и отрицательное — `ValueError`, `bool` и нечисловое — `TypeError`; текст называет параметр `shutdown_timeout` и тип, значения не несёт. Причина строгости: иначе ошибка всплыла бы позже, на открытии области (`_seconds` в `lifetime.py:49` отвергает те же значения), то есть посреди стопа; прежний код молча принимал отрицательное и NaN. Пин в тесте.
  3. Новый файл `core/child_process_stop.py` — класс `ChildProcessStop`, один на ГРУППУ процессов (О2). Конструктор: `ChildProcessStop(processes: Mapping[str, Process], stop_events: Mapping[str, Event], *, on_confirmed_dead: Callable[[str, Process], None] | None = None, logger=None, terminate_grace_s: float = TERMINATE_GRACE_S, kill_confirm_s: float = KILL_CONFIRM_S, poll_s: float = STOP_POLL_S)`. Процесс — любой объект с `is_alive()`, `terminate()`, `kill()`; событие — любой объект с `set()`; тестер подставляет дублёры. Имя без события в `stop_events` — запись в лог, сигнал не шлётся, остановка этого процесса идёт эскалацией.
  4. `request_stop()` — `set()` события каждому живому процессу; не блокирует, идемпотентно, из любого потока. `join_until(deadline) -> bool` — `deadline` абсолютный `time.monotonic()`; опрос каждые `poll_s` ВСЕХ ещё живых за один проход (не последовательный `join`); каждый ставший мёртвым один раз получает `on_confirmed_dead(name, process)` в момент наблюдения смерти и выходит из ожидания; `True`, когда ждать некого (пустая группа — `True`); на сроке `False`, не бросает; срок в прошлом — ровно один проход опроса. Исключения из `terminate`, `kill`, `on_confirmed_dead` логируются, цикл не прерывают. Блокирующий `Process.join` и числовые литералы в `.join(` в файле не используются (G6 R3).
  5. `kill()` НЕ блокирует (О3): каждому живому — `terminate()`; запомнить `time.monotonic()` как начало эскалации; вернуться. Повтор — no-op. Пока `kill()` не вызван, `join_until` не шлёт никаких сигналов. После `kill()` `join_until` один раз шлёт настоящий `kill()` каждому ещё живому на первом проходе, где `time.monotonic() >= min(начало + terminate_grace_s, deadline - kill_confirm_s)` (параметр конструктора `kill_confirm_s`, DESIGN 3), и продолжает опрос до срока. Причина границы `deadline - kill_confirm_s`: срок области абсолютный (`lifetime.py:642`, `deadline + KILL_RESERVE_S`), а метка соседа может быть медленной — без границы настоящий `kill()` при опоздании от 1,0 с не уходит вовсе (воспроизведено ревью р.1). Тексты лога: на `terminate` — `Process '<имя>' did not stop in <N>s, terminating...` (`N` — секунды с `request_stop()`, а без него с создания), на настоящий kill — `Force killing process '<имя>'`: подстроки `did not stop in` и `Force killing` ловят живые тесты `backend_ctl/tests/test_graceful_stop_live.py:64` и `test_system_shutdown_live.py:97`. `survivors() -> tuple[str, ...]` — делает один проход наблюдения (метит `on_confirmed_dead` каждого умершего с прошлого прохода) и возвращает имена без подтверждённой смерти ПОСЛЕ этого прохода, в порядке `processes`: результат строится по набору подтверждённых, а не по повторному `is_alive()` после метки; без метки остаётся только умерший позже прохода самого `survivors()`, он и есть выживший. Так `True` всегда с меткой (правило ADR-PMM-030 «True ⇒ метка», воспроизведено ревью р.1; процесс, умерший после срока области, но до прохода `survivors()`, получает и метку, и `True`). Реестр зовёт `survivors()` один раз; лог и результат строит из одного кортежа.
  6. `close()` — сам делает проход наблюдения (как `survivors()`, решение лида после слепого тестера: тестер оставил это непривязанным) и для каждого имени, чья смерть подтверждена (`not is_alive()`) и кому метка ещё не ставилась, зовёт `on_confirmed_dead`; выжившим метку не ставит; идемпотентно; не бросает. «Одна метка на имя за жизнь объекта» держится набором уже помеченных. Причина `close()`: в пути области (`lifetime.py:585-586, 649-652`) метки уже поставлены `join_until`, и `close()` никого не метит; метод нужен как страховка контракта `Stoppable` при прямом использовании и для 1.2, где `close()` может прийти без предшествующего прохода. `ChildProcessStop` соответствует `Stoppable` из `base_manager/interfaces.py` (`request_stop`, `join_until`, необязательные `kill`, `close`).
  7. `ProcessRegistry` (клиент): `stop_one` и `stop_many`/`_stop_many` остаются публичными с прежними сигнатурами и результатом `{name: bool}`; обе дороги идут через один приватный метод. Шаг (а) `_stop_many` (имя не в реестре или процесс уже мёртв → сразу `True` и метка) не меняется. Для живых: `ChildProcessStop(procs, self._stop_events, on_confirmed_dead=<_mark_confirmed_dead, если mark_reader_gone, иначе None>, logger=self.logger)`; `scope = open_scope("pm/stop", budget_s=<timeout, приведённый как ниже>, kill_reserve_s=KILL_RESERVE_S)` из пакета `base_manager` (не из `core.lifetime`, G6 R7); `scope.own(stop, name="children", kind="process")`; `scope.close()` в `try/finally` (причина временной области вместо трёх прямых вызовов: порядок фаз живёт один раз, в `Scope`, и тот же код исполнит область `children` в 1.2, без ручной копии); результат: имя в `stop.survivors()` → `False`, иначе `True`. Ошибки из отчёта области и выжившие — в лог прежними сообщениями («остановка НЕ подтверждена»). Окна прежние: graceful `timeout`, затем `TERMINATE_GRACE_S`, затем `KILL_CONFIRM_S`. `_stop_one` как отдельная цепочка удаляется; `.terminate()`, `.kill()` и числовые `.join(` в `process_registry.py` не остаются. Значения по умолчанию `timeout: float = 5.0` в трёх сигнатурах заменяются на `DEFAULT_SHUTDOWN_TIMEOUT_S`. Приватный метод принимает `timeout` как есть и сам приводит: конечное и > 0 — как есть; ≤ 0 — `0.0`, то есть сразу эскалация, как раньше с отрицательным; NaN, ±inf, `bool`, `None` и нечисловое — `DEFAULT_SHUTDOWN_TIMEOUT_S` с предупреждением в лог, как у `spawner.stop` (DESIGN 8; `inf` не превращается в немедленный terminate, который оборвал бы graceful-выход); новых исключений на пути стопа нет (`timeout` из `stop_process_timeout` идёт мимо `stop_budget`, `process_manager_process.py:1831, 3665, 4221`).

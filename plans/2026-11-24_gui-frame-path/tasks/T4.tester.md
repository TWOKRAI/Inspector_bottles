DESIGN (decided by the lead — you type it, you do not derive it):
  1. Tests use real objects where the contract names them (the real `FrameIntake`, the real `DataReceiverBridge` and `LatestMailbox`, the real `WorkerManager`, the real `MainWindow`); expected values are literals taken from the ACCEPTANCE block, never derived from the code under test.

CONTRACT (final; the code files are closed to you): `multiprocess_prototype.frontend.frame_intake.FrameIntake(receive, put, log_info, log_critical, track_error, record_metric, sleep=...)`; `run_loop(stop_event, pause_event)`; `get_cycle_metrics() -> dict` with exactly 10 keys `frames_in`, `batches`, `superseded`, `pending`, `bytes_held`, `max_bytes_held`, `shown`, `max_frame_age_ms`, `pump_busy_share`, `qt_pending`. Three sources are attached after construction, each by a callable that `FrameIntake` calls WITHOUT arguments: `attach_pump_stats(provider)` with `provider() -> dict[key, dict]` (the pump counters per key: `shown`, `max_age_ms`, `busy_ms_total`, `errors`, `window_max_age_ms`; your fake is `lambda: {...}`); `attach_mailbox_stats(provider)` with `provider() -> dict` of the mailbox (`LatestMailbox.stats`); `attach_qt_pending(provider)` with `provider() -> int` (the bridge counter `bridge.qt_pending`). Module-level functions of `frame_intake`: `latency_sample(item, now) -> float | None` and `fps_text(shown_per_s, superseded_per_s, per_slot) -> str`. `MainWindow.update_status(fps, latency_ms=None, *, shown=None, superseded=None, per_slot=None)`. The module `frame_intake` imports `time` at module level and calls `time.perf_counter()` and `time.sleep()` through it, so `multiprocess_prototype.frontend.frame_intake.time` can be patched.
  3. Roles of the callbacks: `receive` is called as `receive(timeout=0.1, channel_types=["data"], return_messages=False)` and returns a list of message dicts (a frame message has a `frame` key; a non-frame message is for example `{"data_type": "status"}`); `put` is the bridge `dispatch` and receives every message; `frames_in` counts frame messages only, `batches` counts only non-empty `receive` results.
  4. Definitions, as literals: `shown` is the sum over pump keys; `max_frame_age_ms` is the maximum (not the sum) of `window_max_age_ms` over keys; before `attach_pump_stats` the three pump metrics `shown`, `pump_busy_share`, `max_frame_age_ms` are 0; `pump_busy_share` is the delta of the summed `busy_ms_total` between two `get_cycle_metrics` calls divided by the interval in ms (clock `time.perf_counter` of the module `frame_intake`, patch it for the interval), clamped to [0, 1], a negative per-key delta counts as 0 for that key, the first call gives 0.0; the base is taken at the first call that sees a provider and when a key first appears, the delta of a new key in that same call is 0.0 (calls before the attach take no base); `qt_pending` is the number of messages passed to Qt and not yet handled, and returns to 0 after handling.
  5. Imports of `FrameIntake`, `latency_sample`, `fps_text` are INSIDE each test (not at module level): otherwise every RED fails by `ImportError` at collection instead of by behaviour. Each new `.py` has `__all__` and a `Purpose:` line in its docstring; a test that can block runs the call in a daemon thread with a join deadline.
  6. Scenarios. `test_superseded_grows_when_qt_blocked` builds a `FrameIntake` from the real `DataReceiverBridge` and a real `LatestMailbox` and calls `attach_mailbox_stats(bridge.frame_mailbox.stats)`. `test_worker_status_contains_intake_metrics` builds a real `WorkerManager`, creates a worker on the bound method `FrameIntake.run_loop` and reads the 10 keys from the worker status (`get_worker_status`). `test_qt_pending_returns_to_zero` needs a `QApplication`: use the `qapp` / `qtbot` fixture of pytest-qt; 50 state deltas (`data_type` `state_delta`) are dispatched from a daemon thread while the Qt events are not processed, `qt_pending` is 50; after processing the events it is 0.

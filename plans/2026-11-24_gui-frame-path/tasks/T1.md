DESIGN (decided by the lead — you type it, you do not derive it):
  1. Класс `LatestMailbox` без Qt, без IPC, один `threading.Lock`. Ключ — непрозрачная строка (ни в одном методе ключ не разбирается и не сравнивается с форматом `sender`). Модуль не импортирует Qt-пакеты.
  2. Сигнатуры и семантика:
     - `LatestMailbox(max_keys: int = 64, clock: Callable[[], float] = time.perf_counter)`.
     - `put(key, item, nbytes=0) -> bool`: `True` — принят, `False` — отвергнут по `max_keys`. Замена элемента существующего ключа принимается (`True`) даже при заполненном `max_keys`; считается `superseded`. Отвергнутый вызов считается только в `rejected` и в `put` не входит (всего вызовов = `put` + `rejected`).
     - `take(key) -> (item, age_s) | None`: снимает запись (`taken`, освобождает слот `max_keys`); `age_s` = `clock()` при `take` минус `clock()` при `put` ВОЗВРАЩЁННОГО элемента (после замены отсчёт от последнего `put`).
     - `pending_keys() -> list[str]`: ключи с ожидающим элементом, снимок под замком; порядок — порядок первого `put` ключа (замена порядка не меняет; после `take` и нового `put` ключ идёт как новый).
     - `clear()`: не обнуляет накопительные счётчики и `max_bytes_held`; обнуляет `bytes_held` и `pending`; выброшенное считает в `superseded`.
     - `stats() -> dict[str, int]` ровно 7 ключей: `put, taken, superseded, rejected, pending, bytes_held, max_bytes_held`.
     - определения: `put` = принятые вызовы; `superseded` = замены + выброшенное `clear()`; `pending` = число ключей с элементом; `bytes_held` = сумма `nbytes` ожидающих; инвариант `put == taken + superseded + pending` при любом чередовании вызовов.
     - `max_keys` — предел на число ключей С ОЖИДАЮЩИМ элементом. Причина «отвергнуть новый ключ, а не вытеснять старый»: ключ = sender, число sender-ов ограничено рецептом; отказ сохраняет предел памяти и не отнимает кадр у уже показываемого sender-а.
     - при замене: вычесть байты старого, добавить байты нового, `max_bytes_held` обновить ОДИН раз за `put` после обмена (иначе пик 23328000 вместо 18662400).
  3. `pending_keys()` нужен потому, что кадр неизвестного sender-а в gui идёт в слот «main» (`recipe_displays.py:124-143`, `app.py:1157`); без перечислителя `FramePump` (T2) не найдёт такой ключ и кадр навсегда останется в ящике.
  4. Запись о решении — `### ADR-PM-064 — ...` в `multiprocess_framework/modules/process_module/DECISIONS.md` (номер 045 занят: строка 3433; 064 свободен; заголовок СТРОГО формы `###`, невидимой индексу `sync`, чтобы `sync` не писал вне FILES). Содержание: почему «последний на ключ», почему не `DataReceiver._bound_lag`, почему нейтральное место (нужен и процессу буфера T10), почему отказ новому ключу. Класс экспортируется из `generic/__init__.py` (`__all__`). `python -m scripts.sync` developer не запускает (сливает лид).
  5. Требования contract-lite: docstring модуля с `Purpose:`, `Public API:`, `Stability:`; `__all__`; у публичных методов строки `Pre:` / `Post:` в docstring; исключения не бросать (предусловия только в docstring); при добавлении `ValueError` (`nbytes < 0`, `max_keys < 1`) текст сообщения константный.

DESIGN (decided by the lead — you type it, you do not derive it):
  1. Tests use real objects (the real `DataReceiverBridge`, the real `FramePump` over a real `LatestMailbox`, a real `ImagePanelWidget` with display slots); expected values are literals taken from the ACCEPTANCE block of `tasks/T3.md`, never derived from the code under test.

CONTRACT (public names; the code files `bridge_impl.py` and `app.py` are closed to you, so these names are the whole interface): `bridge.frame_mailbox` is a `LatestMailbox` instance created by `DataReceiverBridge()` (import path of the bridge: `multiprocess_prototype.frontend.bridge`); `LatestMailbox` is `multiprocess_framework.modules.process_module.generic.latest_mailbox.LatestMailbox`, `stats()` returns exactly 7 keys: `put`, `taken`, `superseded`, `rejected`, `pending`, `bytes_held`, `max_bytes_held`; `FramePump` is `multiprocess_framework.modules.frontend_module.bridge.frame_pump.FramePump`, constructor kwargs `mailbox=` and `sink=` (`sink(key, item)`), methods `set_keys({key: fps_limit})`, `stop()`, `stats(reset_window=False) -> dict[key, dict]`; the slot key `fps_limit` in the dicts returned by `build_panel_displays` (`multiprocess_prototype.frontend.widgets.image_panel.recipe_displays`); the pump created by the app wiring is `process._frame_pump`, created inside `multiprocess_prototype.frontend.app._setup_bridge_callbacks`. «Shown» is counted by the key `shown` in `process._frame_pump.stats()` (per key), not by counting `display_frame` calls. The `recipe_manager` stub has two methods: `get_active()` returns a slug, `read_recipe(slug)` returns the recipe dict. Recipe format: `displays` is a list of `{"id", "name", "enabled", "position": {"x", "y"}, "fps_limit"}`; `blueprint.displays` is a list of `{"node_id": "<sender>.<plugin>.<port>", "display_id"}` (the sender is the first segment of `node_id`). The `process_stub` has the attributes `_bridge` (a real `DataReceiverBridge`), `_log_info` and `_log_warning`; the wiring sets `_frame_pump` on it; `window_mock` is a mock of the main window; `image_panel` is a real `ImagePanelWidget`.
  5. Wiring is covered by the real function (rule: a fake-harness suite needs one test that wires the real objects): `test_no_aliasing_22hz_source_limit_20`, `test_overload_last_frame_reaches_screen` and `test_state_delta_delivered_under_frame_flood` (it is red only with the real drawing callback connected) call the real `_setup_bridge_callbacks(process_stub, image_panel, window_mock, recipe_manager=stub)` with a real `ImagePanelWidget`; the limit 20 comes from the recipe through `build_panel_displays` (a recipe dict with a display `fps_limit: 20`), the test does not set it by hand.
  6. Machine safety: the 500 MB private-bytes ceiling lives in ONE shared producers helper (a fixture) that is mandatory for EVERY test flooding at 300 frames/s or more (`test_overload_memory_stays_bounded`, `test_qt_timer_ticks_under_overload`, `test_state_delta_delivered_under_frame_flood`, `test_overload_last_frame_reaches_screen`, `test_slow_sender_shown_while_fast_floods`): the producers stop as soon as the private bytes of the process have grown by more than 500 MB, polled at least 20 Hz (every 50 ms or less) (the acceptance bound stays 100 MB); the base is taken after every slot has shown at least 1 frame, the metric is the peak over 5 s, the way is `GetProcessMemoryInfo` through `ctypes` (psutil is forbidden by the project rules). The gate class of the file is `medium`, stated explicitly in the run command.
  7. Existing test `test_recipe_displays.py::test_extracts_id_label_enabled_position` (:38-41, a literal of five keys per slot) is updated by you: each slot literal gets `"fps_limit": 30.0` (a recipe without `fps_limit` gives 30.0). This is an explicit item of your work: the test is red before the code and goes green with it.
  8. `test_fps_limit_read_from_recipe` takes parameters: 20.0 from the recipe gives 20.0; no key gives 30.0; `0` gives 0.0 (it means the 60 Hz ceiling by the owner decision). `test_fps_limit_garbage_falls_back_to_30` has parameters None, the string "abc" and NaN: each gives 30.0 and the build does not raise.
  9. «Callback» in `test_frame_before_callback_shown_after` means: the creation of the pump and its first `set_keys`. A frame that reaches `dispatch` before that lands in the sink on the first tick.
  10. Guards (not in REDS): `test_state_delta_delivery_unchanged` is green before and after the developer code (it goes through `state_updated`); `test_frame_with_older_capture_ns_is_shown` and `test_item_meta_reaches_sink` go through the real `dispatch` / `_setup_bridge_callbacks`, so before the code they are red by the missing API (`frame_mailbox`, `_frame_pump`) and green after it. Their literals: `test_frame_with_older_capture_ns_is_shown` (`capture_ns` 2_000_000_000, then 1_000_000_000; the second frame is shown, not dropped); `test_item_meta_reaches_sink` checks that `capture_ns` and `capture_ts` reach the sink literally. One extra RED scenario for the state branch under overload: `test_state_delta_delivered_under_frame_flood` — a state delta is delivered within 1 s while each of 4 senders floods at 400 frames/s (the 1 s bound is a hypothesis, the final one is set at the stand).
  11. Parameters of ALL overload tests: the `fps_limit` of all four displays is 20; the «Qt timer» of a test is a `QTimer` with an interval of 100 ms; precondition: the `put` count of every sender equals 2000 (for the memory test at least 90% of 2000, otherwise the flood was not reached and the test does not count). Windows and deadlines: after the producers stop the last accepted frame number on each slot is 2000, not later than 1 s after the stop; «not less than 4 ticks per second» is the average over the whole 5 s run; the overload input is 400 frames/s on EACH sender, 5 s, number 2000 (total input 1600/s).

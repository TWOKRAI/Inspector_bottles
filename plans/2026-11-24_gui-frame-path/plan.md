## Цель

1. **Ряд А (дисплей).** Тракт кадров gui не накапливает кадры: память структурно ограничена «ключи × 1 кадр» при любой частоте входа, экран не замирает, `fps_limit` дисплея становится настоящим, счётчики говорят правду. Причина: очередь событий Qt без предела держит полные копии кадров (+457 МБ/с при 220 кадр/с, отрисовка 0-1 в секунду; воспроизведено cto offscreen).
2. **Ряд Б (запись).** Штамп времени кадра на общей шкале (`capture_ns`), независимый от gui буфер последних 60-120 с на камеру (JPEG-сегменты, индекс по времени), закрепление диапазона по событию брака, основа для записи на диск и ползунка перемотки. Запись не зависит от gui и Qt; «без потерь» = потерь нет в пределах заявленного запаса, каждая потеря сверх него считается и пишется разрывом (У3).

## Решения владельца (2026-11-24)

Владелец согласился с рекомендациями лида:

1. `fps_limit: 0` = страховочный потолок 60 Гц.
2. Строка FPS = «показано» по слотам плюс «вытеснено».
3. Имя пакета `Services/frame_buffer` подтверждено (решение 12 приложения 2): плагин `Plugins/io/frame_saver` остаётся для одиночных снимков; плагин буфера — `Plugins/io/frame_buffer`.
4. Запись видео — по событию с предзаписью из буфера 1-2 минуты, не непрерывно.
5. Диск D: (не C:); архив mp4v через `cv2` без новых зависимостей; q85 с окончательной фиксацией после замера на 100 настоящих кадров камеры.
6. Redis и подобные серверы хранения для T12 и T16 не используются (2026-11-24, владелец согласился с лидом). Причины: предзапись уже держит `TimeRing` в плагине T10; кадр через сервер — лишняя копия и сериализация; под Windows нет штатной сборки (Memurai/WSL — отдельный процесс со своими сбоями); данные в RAM, а запись идёт на диск D:; новая зависимость. Первичная запись — независимые JPEG в дозаписываемом сегменте с индексом (У4); малые данные (журнал событий, квоты, срок хранения) — SQLite через `Services/sql`. Пересмотр — только если появится требование делиться кадрами между машинами или замер покажет, что диск не тянет две камеры.

Открыто по T12 и T16: квота на камеру и на события; порядок действий при нехватке места; окно события «до/после»; срок хранения; сеть при > 2 камер.

Остальное из вердикта: бюджет памяти процесса и реакция супервизора — отдельный план (решение 3 вердикта); поля `displays[]` `ring_buffer_blocks` / `width` / `height` / `format` остаются с пометкой «только SHM-привязка» (решение 4); `RemoteFrameSource` отложен (решение 6); штамп `capture_ts` вместо снятия надписи Latency (решение 5 снято).

Снятые блокировки: T3 и T4 (решения 1, 2), T10 (имя подтверждено). T12 и T16 по-прежнему ждут квот и порядка при нехватке места.

## Условия приёмки (приложение 2)

- **У1.** Процесс записи всегда copy-out потребитель камеры (`copy_out_targets`), со сторожевым тестом по рецептам. Иначе при `FW_SHM_LOAN_PROTOCOL=1` застрявшая запись отнимает кадры у дисплея (воспроизведено). -> T14.
- **У2.** Слот камеры «последний кадр» заменяется очередью со счётчиком (T13) до любой приёмки со словами «запись без потерь».
- **У3.** «Без потерь» = потерь нет в пределах заявленного запаса на задержку; каждая потеря сверх него — запись о разрыве и счётчик. Приёмка по непрерывности `seq_id`. -> T10, T14.
- **У4.** Первичный формат записи — независимые кадры в дозаписываемом сегменте с индексом. MP4/H.264 только производный архив. -> T9a, T9b, T12, T16.
- **У5.** Умолчания размеров и квот фиксировать после замера 100 настоящих кадров камеры. -> T10, T11; конструктор `TimeRing` без значений по умолчанию.

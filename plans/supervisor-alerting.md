# supervisor-alerting (В5 · NEW-7)

**Ветка:** `feat/supervisor-alerting`
**Refs:** `plans/current-path/plan.md` (В5 NEW-7, E-5), `plans/supervisor-strategies.md` (NEW-6b)
**Слой:** framework
**Статус:** реализовано

## Цель

Правила «`gave_up` / `unresponsive` / дропы растут → **громкая нотификация**» поверх уже
существующего потока supervisor-событий. До NEW-7 терминальные состояния были обычными
лог-строками и терялись в потоке; счётчик потерь данных не поднимал тревогу вовсе.

## Дизайн

- **`core/alert_rules.py` — чистый модуль** (без I/O, StateStore и времени «изнутри»):
  `AlertRule` (событийное ИЛИ счётчиковое), `DEFAULT_RULES`, `rules_for_event`,
  `counter_rules`, `should_fire` (антидребезг), `counter_growth`. Всё юнит-тестируемо
  в изоляции; побочные эффекты остаются в мониторе.
- **Правила по умолчанию:** `gave_up` → **critical** (cooldown 300с — одно громкое
  событие вместо потока), `unresponsive` → warning (60с), рост дропов → warning (60с).
  Путь счётчика — список кандидатов, первый резолвящийся выигрывает:
  `processes.{process}.state.drops` (реальный публикатор — capture-плагин), затем
  `processes.{process}.state.drops_count`. Единственный «правильный» путь оказался
  мёртвым (находка ревью) — имя поля есть конвенция публикующей стороны.
- **Публикация:** `system.alerts.<process>.<rule>.{severity,reason,at}` — supervisor-owned
  плоскость (как `processes.<name>.supervisor.*`), не конкурирует с health-поддеревом
  процесса, которое тот публикует полным снапшотом (урок HIGH-2 ревью NEW-6b).
- **Хуки:** событийные — прямо в `_emit_supervisor_event` (единый поток); счётчиковые —
  `_check_counter_alerts()` в цикле мониторинга.
- **Флаг** `FW_SUPERVISOR_ALERTS` (default **ON** — терминальные состояния не должны
  теряться; откат env `=0`).

## Ключевые решения

1. **Первый замер счётчика — только база**, алерта нет: иначе счётчик, накопленный до
   старта монитора, дал бы ложную тревогу на пустом месте.
2. **Сброс счётчика приростом не считается** (`current < baseline` → 0): рестарт
   процесса не должен выглядеть как всплеск потерь.
3. **Антидребезг per (правило, процесс)** — crash-loop даёт один алерт, а не поток.
4. **Словарь supervisor-событий не расширен** — алертинг читает существующий поток,
   а не вводит новые виды событий (контракт GUI сохранён).

## Acceptance

- [x] `gave_up` → critical-алерт + ERROR-лог; `unresponsive` → warning; `recovered` → ничего.
- [x] Антидребезг: повтор в окне cooldown не поднимает второй алерт; алерты per-процесс.
- [x] Рост `drops_count` → warning с величиной прироста в reason.
- [x] Первый замер только базирует; отсутствие пути/StateStore/не-int (в т.ч. bool) — тихо.
- [x] `FW_SUPERVISOR_ALERTS=0` → алертов нет.
- [x] Тесты: `test_alerting.py` (26) + регресс 1648 passed.
- [x] Полный framework-suite (5353 passed).
- [x] Fable-ревью (graphify отработал — подтвердил отсутствие рекурсии по графу вызовов):
  1 HIGH + 2 MED + 3 LOW закрыты — мёртвый дефолтный путь счётчика (реальное поле `drops`
  + мульти-кандидат + регресс-страж), сброс алерт-состояния и удаление `system.alerts.<name>`
  в `forget_process`, bool-фильтр, документирование эрозии cooldown. Тесты: 34 (+8).

## Out of scope

- GUI-панель алертов (данные в `system.alerts.*` уже готовы к подписке).
- Внешние каналы нотификаций (почта/мессенджер) — это прикладной sink поверх state.
- Пользовательская настройка правил из рецепта (сейчас `DEFAULT_RULES`; поле для
  переопределения — следующий шаг, если понадобится).
- **Резидуал:** снятие алерта по `recovered`/TTL (сейчас снимается только при уходе
  процесса из топологии) — вместе с GUI-панелью алертов.

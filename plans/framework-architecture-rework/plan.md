## Зачем

Цель владельца: **универсальный конструктор многопроцессных приложений**, который можно развивать
годами, переживая смену версий Python и библиотек. Прототип-инспектор — первое приложение на нём,
не самоцель.

Инвентаризация показала: **архитектура уже зрелая** — ноль циклов при импорте, 27/27 модулей с
полным комплектом README/STATUS/DECISIONS/tests/interfaces, порты-у-потребителя применены в четырёх
местах самостоятельно. Чинить нечего. Не хватает трёх вещей, и все три — про **проверяемость**, а
не про структуру:

1. **Конструктор не устанавливается.** `pip install` фреймворка сегодня тянет Qt (`pyproject.toml:16`),
   а импорт одного модуля загружает **23 корня** (доказано запуском). «Фреймворк независим» —
   утверждение, а не свойство.
2. **Разъём наблюдаемости неоднозначен.** `record_metric` означает counter или gauge в зависимости
   от того, чем сшит слот. Семь форм доставки. Два узла у железа — `robot_comm/core/client.py`,
   `vfd_comm/core/client.py` — без канала диагностики вообще.
3. **Документы расходятся с кодом.** Двенадцать случаев за одну сессию, включая неверную диаграмму
   наследования в README **двух** модулей сразу. Это и есть сила, убивающая архитектуру на
   дистанции — не сложность, а неверность описания.

## Ф0 — Решения владельца (кода нет)

### Р-1. Принцип группировки — несущее решение, от него зависят все остальные

**Рекомендация: три оси, три механизма. Не смешивать.**

| Ось | Механизм | Почему так |
|---|---|---|
| **Смысл** → папки | домены: `observability`, `ipc`, `schema`, `execution`, `state`, `catalogs`, `messaging`, `runtime` | стабильны при рефакторинге, совпадают с тем, как задают вопросы («где логирование?») |
| **Дистрибутив** → пакеты | workspace: `framework` / `frontend` / `services` / `plugins` | делает независимость **физическим свойством**, а не правилом |
| **Ярусы** → контракт линтера | `import-linter`/`tach` в CI, папками НЕ выражаются | ярус меняется при добавлении импорта; папка от этого меняться не должна |

**Почему не папки-слои, как в замещаемом плане.** Он предлагал девять папок-слоёв. Измерение
подрывает эту форму дважды: (а) граф **широкий и мелкий**, большинство модулей — листья, то есть
слои описывали бы глубину, которой нет; (б) тир — артефакт графа импортов, а не смысла: в тире 4
рядом оказались `recipe`, `shared_resources`, `console`, `actions` — у них нет ничего общего.
Папка по тиру = навигация по случайности, и она разъезжается при каждой правке импортов.

**Раскладка, ред. 2** (27 модулей → 8 доменов + ядро). Ред. 1 забраковано ревью по двум дефектам,
оба записаны, чтобы не вернулись:

> **Дефект 1 — потерян модуль.** Ред. 1 размещала 25 каталогов из 27: `base_manager` (fan-in **16**,
> дом `ObservableMixin`, объект решения Р-7) не попал ни в одну клетку. Это не описка — ему **не
> было естественного места**, и раскладку этому тесту не подвергли.
>
> **Дефект 2 — домены циклились, хотя модули ацикличны.** `config`(schema) → `logger`(obs) →
> `data_schema`(schema); `statistics`(obs) → `channel_routing`(msg) → `_fallback`(obs). Раскладка,
> обещающая стабильность, давала клубок из трёх папок.
>
> **Дефект 3 — ред. 2 создала НОВЫЙ цикл, убивая старый** (найдено ревью №2 ред. 2). Перенос
> `config` в `runtime` замкнул пару **ipc↔runtime**: `router_module/core/router_manager.py:16` —
> жёсткий `from ...config_module.feature_flags import is_enabled`, а обратно runtime→ipc идёт
> шестью жёсткими рёбрами (`spawner.py:16`, `process_manager_process.py:27`,
> `process_runner.py:13`, `backend_ctl_endpoint.py:21-22`, `process_data.py:10`,
> `generic/__init__.py:19`). **Ф2.2 его НЕ снимает — ребро не логгерное.**
> Починка: `feature_flags.py` (393 строки, зависимости — только stdlib + `tools/env.py`) переезжает
> в `kernel`. Альтернатива — ленивый импорт в роутере, прецедент в том же модуле есть
> (`frame_shm_middleware.py:314`); выбран перенос, потому что ленивость прячет зависимость,
> а не убирает.

```
framework/
├── kernel/         data_schema · base_manager · _fallback · observability_declarations
│                   + feature_flags (из config)   ← см. дефект 3
├── messaging/      message · dispatch · event · command · channel_routing
├── observability/  logger · error · statistics · telemetry_readmodel
│                   + подпакет observability/ из channel_routing (hub, store)   ← см. 3.8
├── ipc/            shared_resources · router · display
├── execution/      worker · chain
├── state/          state_store · recipe · actions · registers
├── runtime/        console · config · process · process_manager · app · service
└── plugin_api/     контракт плагинов, вынесенный из process (Р-5)
```

Что изменилось и почему:

| Правка | Причина |
|---|---|
| **+`kernel`** | `base_manager` получил дом; вместе с ним туда ушло всё, что не имеет жёстких исходящих рёбер вовсе. Признаём честно: `kernel` — ярусное имя, а не смысловое, это единственное отступление от принципа «папки = смысл», и оно куплено ацикличностью |
| `config` → `runtime` | README сам о себе: «это NOT валидация… **только runtime доступ и подписки**». В «схемах» он был по имени, не по существу |
| `registers` → `state` | README: «**Runtime-слой**… pub/sub… отправка через роутер». Тоже не схема |
| **`catalogs` растворён** | был свалкой по форме данных, а не доменом: никто не спрашивает «где каталоги?». `display` → `ipc` (реестр SHM-каналов, сосед `shared_resources`); `telemetry_readmodel` → `observability` (на вопрос «где телеметрия?»); `service` → `runtime` (розетка слоя `Services`) |
| `channel_routing/observability/` → `observability/` | хаб и стор — **транспорт наблюдаемости**; оставить их в `messaging` значит провалить собственный тест Р-1: вопрос «где логирование?» вёл бы не туда |

Суффикс `_module` снимается, контейнер `modules/` исчезает: `multiprocess_framework.state.state_store`.

### Р-1а. Почему Ф2 стала ПРЕДУСЛОВИЕМ Ф3, а не параллельной фазой

Разбирая дефект 2, выяснилось главное открытие пересмотра: **бо́льшая часть связности фреймворка
создана не логикой, а разъёмом наблюдаемости.** `config`, `console`, `event`, `recipe`,
`shared_resources`, `state_store`, `actions`, `router` тянут `logger` **ради одного
`get_std_logger`** — то есть ради разъёма, а не ради дела. Отсюда и fan-in 13 у `logger`, и
межпапочные циклы.

Замена импорта на инъекцию порта (Task 2.2) снимает эти рёбра. Значит раскладывать по папкам
**до** Ф2 — значит зацементировать в дереве связность, которая должна исчезнуть.

Список сверен пофайлово (ревью №2 поправило две позиции из восьми):

| Модуль | Ребро в `logger` | Снимается 2.2? |
|---|---|---|
| `config`, `event`, `recipe`, `actions`, `state_store`, `router` | только `get_std_logger` | **да** |
| `console` | `logger_module.interfaces.ILogChannel` — **контракт**, не разъём | нет |
| `shared_resources` | три ребра: два разъёмных + **структурное** `memory/platform/shm.py:19` (класс `FallbackLogger`) | частично |

Отсюда правило приёмки: считать **рёбра-файлы**, а не модули, и каждое помечать
«разъёмное / структурное» письменно. Иначе критерий «рёбер ради разъёма = 0» спорен.

**Ф2 → Ф3. Не параллельно.** Приёмка Ф2 включает пересъём **полного графа доменов** — не только
рёбер `→ logger`. Ред. 2 заужала приёмку до логгерных рёбер, из-за чего цикл ipc↔runtime доехал
бы незамеченным до финальной приёмки Ф6. Раскладка Р-1 проверяется на **новом** графе перед
стартом окна; критерий — **ноль циклов между доменами**, а не «стало меньше».

### Task 2.2 — Половина доставки: сначала `BaseManager`, порт — только остатку
**Решение владельца 2026-08-17 (Р-7):** правило «все компоненты через `BaseManager`» остаётся,
и оно же закрывает бо́льшую часть задачи. Порядок обратный тому, что предлагала ред. 2.

**Шаг 1 — перевести на `BaseManager` тех, у кого есть жизненный цикл и состояние.** Механика
проверена: `base_manager` не импортирует `logger_module`, `ObservableMixin` берёт менеджеры
инъекцией — ребро `→ logger` **исчезает**, а не переезжает.

| Кандидат | Основание |
|---|---|
| `event.EventBus` | подписки, живёт весь процесс |
| `actions.ActionBus` | стек undo, живёт долго |
| `state_store.PersistenceManager` | уже назван менеджером, цикл есть |
| `recipe.RecipeEngine` | пограничный — решить при исполнении, стор есть, но по сути dict→dict |

**Шаг 2 — остаток, которому `BaseManager` не подходит, и это уже решено в коде дважды:**
`config.Config` — намеренно лёгкий (`ConfigManager` существует как менеджерская версия, в коде
стоит комментарий о сознательности), `router.frame_shm_middleware` — функция конвейера, не объект
с циклом. Сюда же `BaseDispatcher`/`BaseCommandManager` — облегчённые варианты **по замыслу**.
Для них вопрос ставится сначала так: **нужен ли им разъём вообще** (`Message` сегодня без разъёма
и это правильно). Порт — только если ответ «нужен».

**Приёмка:** рёбра `→ logger` разъёмного класса = 0 (считать **рёбра-файлы**, каждое помечено
«разъёмное / структурное»); ни один переведённый объект не приобрёл лишнего в конструкторе на
боевых сайтах; для остатка — работа **без** разъёма названным поведением (no-op, не

## Ф5 — Дистрибутив, совместимость, долголетие

- **5.1 Workspace:** `framework` / `frontend` / `services` / `plugins`, каждый со своим `pyproject`.
- **5.2 Qt уходит из зависимостей ядра.** Заодно — пин git-форка `NodeGraphQt` (`pyproject.toml:19`

- **5.3 numpy/vision уходят из ядра или в extras.** Зеркальное Qt мерило универсальности: сегодня
  `shared_resources` (IPC!) жёстко тянет numpy, `chain` знает про маски и контуры. Посторонний,
  строящий НЕ-vision приложение, получает кадровую семантику в «чистых» доменах.

  работает; путь описан в quickstart 6.0; существующая discovery по путям не сломана.
- **5.5 Релизная политика самого фреймворка.** Ред. 1 давала semver только `plugin_api`. Нужны:

  **Приёмка:** написан документ политики; один цикл проверен на живом примере — снятие одного
  публичного имени проходит объявленный путь (deprecation → предупреждение → удаление), а не
  исчезает молча; CHANGELOG собирается из Conventional Commits.
- **5.6 Долголетие проверяется, а не обещается.** Сегодня `pyproject.toml:5` пинит
  `>=3.12,<3.13` — то есть «переживёт пять лет» ничем не обеспечено. Нужны: CI-матрица версий,
  расширение диапазона, прогон под free-threaded сборкой. Ред. 1 предлагала на потокобезопасность

- **Приёмка:** `pip install` фреймворка **без Qt и без numpy** — проверяется **запуском** в чистом
  окружении. Сегодня такой проверки не существует, и это само по себе ответ.

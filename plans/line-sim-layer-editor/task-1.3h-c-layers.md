## Устройство бэкенда (c1)

Решение лида, не жёсткий контракт.

- **Канал файлов — пока только чтение.** Команда `preset.sprites` в плагине `layer_preview` (процесс
  `layers`, поток команд сцены не занимает; ограда путей уже там) перечисляет PNG одного каталога. Постоянный
  канал «файлы по id» (Д 1.3, `dataset-annotation`) и загрузка из браузера — не здесь: новый PNG оператор
  кладёт в каталог руками, потом жмёт «Обновить список».
- **Каталог** — ключ конфига `layer_preview.sprites_dir`, по умолчанию `data/line_sim` (от корня репозитория,
  `resolve_repo_path`). Это **единственный** каталог и для списка, и для будущей записи. `data/` в `.gitignore`:
  на свежем клоне каталога нет, и это отказ с текстом, а не пустой список.
- **Путь для `sprite_source` считает бэкенд, не JS.** Относительно каталога файла пресета хоста (у пресета без
  файла — от корня репозитория), прямыми слэшами, по правилу Task 1.0. Считает **одна** функция —
  «файл в `sprites_dir` → запись списка»; её же позовёт запись 1.3h-d. Страница вставляет строку как есть.
- **Ответ:** `{status: ok, dir, files: [{path, sprite_source}], truncated, layer_template}`. `path` — от `sprites_dir`
  (прямые слэши), это подпись в списке; `dir` — сам каталог от корня репозитория, если он внутри репо, иначе абсолютный. Поиск рекурсивный, по `*.png` без учёта регистра; порядок — по `path`; не
  больше 500 записей, лишние отрезаются с `truncated: true`. Файл, чей `resolve()` уходит за пределы
  `confine_preset_paths` (симлинк наружу), в список не попадает: `commit` его всё равно отверг бы.
- **`layer_template`** — `LayerSpec(name="_", mode="static", sprite_source="_").model_dump(mode="json")`: полный
  набор ключей слоя с дефолтами. Форма 1.2h строится из ключей словаря; без шаблона у нового слоя не будет полей
  `offset_px`/`angle_deg`/`scale`. Новое поле `LayerSpec` попадает в шаблон само.
- **Отказы:** каталога нет или он не читается → `io_error` (HTTP 500) с путём в тексте. Каталог вне ограды →
  `bad_request`. RGBA при перечислении **не** проверяется: не-RGBA картинку отвергнет следующий `preset.layout`
  (`invalid`, текст фабрики «нужен альфа-канал»), а отказ раскладки страница уже показывает (1.3h-b).
- **Маршрут** `POST /api/preset/sprites` (тело `{}`) → `layers_process`: строка в `_PRESET_ROUTES`, таймаут как у
  layout. Нового кода диспетчеризации нет.

## Устройство страницы (c2)

- Список `<select>` с файлами и отдельной строкой «спрайт класса (`class://`)». Кнопки: «Добавить слой»,
  «Заменить картинку», «Удалить», «Выше», «Ниже», «Обновить список».
- Каждая операция — одна правка `presetState`, одна запись undo (тот же стек) и перезапрос раскладки, через тот же
  путь, что жесты: снимок `collectPresetFromFields()` → изменение → `renderPresetLayers()` →
  `requestPresetLayout()`. Если операция ничего не изменила («Выше» у верхнего слоя, ничего не выбрано), записи
  undo и запроса нет.
- **Добавить** — функция, принимающая **запись списка** `{path, sprite_source}`, а не читающая `<select>` сама:
  1.3h-d отдаст ей ответ записи той же формы. Копия `layer_template`, `name` — основа имени файла (`class` для
  `class://`), занято — `_2`, `_3` и дальше. Слой встаёт **наверх** (в конец списка) и становится выбранным.
- **Удалить** и **Заменить** — над выбранным слоем. Заменить меняет только `sprite_source`.
- **Выше** — к концу списка (рисуется поверх), **Ниже** — к началу. Выбор идёт за слоем (по имени, как в 1.3h-b).
- Авто-слой `base` не входит в `presetState`, его не касается ни одна кнопка.
- **Имена в разметке — литералы:** `id="presetSpriteSelect"`, `btnLayerAdd`, `btnLayerSprite` (заменить картинку),
  `btnLayerDelete`, `btnLayerUp`, `btnLayerDown`, `btnSpritesRefresh`, `presetSpritesError` (текст отказа списка).
  Значение `<option>` — `sprite_source`, текст — `path`.

## Заготовка под канал записи — Task 1.3h-d

**Статус:** PENDING, не в работе. Постановка — после приёмки 1.3h-c. Кода под неё в 1.3h-c нет, есть три
закладки в контракте: один каталог `sprites_dir`, одна функция «файл → запись списка», «Добавить» принимает запись.

**Goal:** оператор выбирает PNG на своём диске в браузере, файл ложится в `sprites_dir`, и слой из него
добавляется тем же путём, что из списка.

Эскиз (уточняется при постановке):
- Команда `preset.sprite_put {name, png_b64}` в том же `layer_preview` → ответ `{status: ok, file: {path,
  sprite_source}}` — **та же форма**, что элемент `files` у `preset.sprites`; страница отдаёт её функции «Добавить».
- Маршрут `POST /api/preset/sprite_put` — строка `_PRESET_ROUTES` со своим потолком тела (порядка 8 МБ, отказ 413
  до чтения, как в 1.2h). На странице — `<input type="file" accept="image/png">`, чтение `FileReader` в base64.
- Граница доверия — здесь запись на диск из сети: `name` → только базовое имя, символы вне `[\w.-]` → `_`,
  расширение `.png` обязательно, `..` и абсолютные пути отвергаются. Существующий файл **не перезаписывается** →
  `conflict`. Не-RGBA отвергается **до** записи (`load_image_rgba` из `Services.line_sim.core.catalog_bridge` на
  декодированных байтах) — `invalid`. Запись атомарная (временный файл того же каталога → `os.replace`, как
  `commit` в 1.2a).
- Пульт слушает `127.0.0.1` и проверяет `Host` (ревью 5.3a) — поверх этого новых мер не нужно, пока `host` не
  открыт наружу; открытие наружу пересматривает 1.3h-d целиком.
- **Когда придёт Д 1.3** («файлы по id», `dataset-annotation`): решить, заменяет ли он 1.3h-d или живёт рядом.
  До тех пор `sprite_source` — путь, не id.

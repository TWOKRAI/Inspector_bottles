## Контекст

Слова владельца (2026-09-21): «должен быть редактор, похожий как в paint или фотошопе».
Движок `Services/line_sim` собирает объект из слоёв (`LayeredObject` ← `ScenePreset`), но
создать пресет можно только одним способом — написать YAML руками. Для диска (один
вырезанный спрайт) это терпимо. Для бутылки — тара, наполнение, этикетка, крышка, кольцо,
у каждого слоя смещение, масштаб, угол и диапазоны вариации — подбирать числа вслепую
нельзя: результат не виден, пока не запущен стенд.

Прецедент в истории git: `6116adf3:Create_bottles/generate_pyqt.py` (641 строка) — окно с
живым превью, у бутылки/крышки/кольца/этикетки видимость, смещение, масштаб, угол.
Перенимается идея, не код: набор слоёв там зашит в класс окна (новый продукт = правка
кода), мыши нет, рендер свой. Здесь слои — данные пресета, рендер — движка.

**Это не Photoshop.** Рисования, кистей, выделения, фильтров нет: спрайты приходят
готовыми (`Services/dataset_gen/tools/cut_real_disks` или любой внешний редактор).
Редактор делает одно — компонует готовые RGBA-слои в объект и пишет пресет.

## Цели

- Новый продукт заводится без правки кода и без ручного YAML: открыл редактор → добавил
  PNG-слои → расставил мышью → задал диапазоны → сохранил пресет → лента едет с ним.
- Что видно в редакторе, то и поедет по ленте: превью рендерит **тот же**
  `LayeredObject`, своего рендера у редактора нет.
- Эффект аугментации виден до запуска стенда: сетка случайных образцов по кнопке.

## Out of scope

- Рисование и ретушь спрайтов, вырезание из фото (это `cut_real_disks`).
- Редактирование сцены: лента, фон, камера, ROI, поток — это пульт (`line-sim` Ф6).
- Фотометрия (блик, размытие, гамма) — свойство сцены, Ф4.3, не слоя.
- Встраивание во вкладку **прототипа** (пакет `inspector.*`): редактор — вкладка пакета `sim.*`, прототип о нём не знает (см. решения).
- Визуальные «призраки» границ диапазона на канве — сетка образцов закрывает ту же
  потребность дешевле; добавлять, если сетки окажется мало.

## Решения

- ~~**Автономное окно, не вкладка прототипа.**~~ **Пересмотрено владельцем 2026-09-26:** редактор — **вкладка
  пакета `sim.*`** конструктора интерфейса (виджеты `sim.layers` — список, `sim.layer_props` — свойства,
  `sim.layer_canvas` — канва), работает на подключении к бэкенду `line_sim` одинаково во встроенном GUI и в
  `apps/gui_client` ([`gui-constructor`](../gui-constructor/plan.md) Task 3.3–3.4). Прототип о симуляторе по-прежнему не
  знает: пакет `sim.*` не входит в пакет инспектора. Отсюда зависимость: редактор **ждёт** оболочку и второе
  подключение (gui-constructor Ф2, 3.1), а не стартует раньше GUI-загрузки. Исторический прецедент автономного окна —
  `Services/robot_comm/server/sim_monitor.py`.
- **Слои хранит бэкенд симулятора, редактор правит их командами.** Бэкенд-часть (процесс дерева `apps/line_sim`)
  отдаёт пресет (`ScenePreset.to_dict()`) с ревизией и принимает `commit{preset, base_rev}` → `{ok, rev}` /
  `conflict` — шаблон `recipe.*` (gui-service 1b.1) и помощник gui-constructor Task 3.4. Превью рендерит бэкенд тем
  же `LayeredObject` и отдаёт кадром/ответом команды — «что видно, то поедет» сохраняется. Добавление нового PNG
  требует канала файлов по id — он зарезервирован в контракте контекста; кто реализует первым (разметка или этот
  редактор) — решается при постановке Task 1.2. Имена команд — при постановке, по соседству с `belt.*`.
- **PySide6 только внутри `Services/line_sim/gui/`.** Критерий Task 3.1 «`from
  Services.line_sim import …` без PySide6» остаётся в силе: подпакет `gui` не
  реэкспортируется из `Services/line_sim/__init__.py` (контракт-тест gui-constructor Task 1.0).
- **Канва своя, не из прототипа.** Единственная `QGraphicsView`-канва проекта —
  `multiprocess_prototype/frontend/widgets/tabs/pipeline/graph/graph_view.py`; импорт
  `Services → prototype` запрещён правилом слоёв (`.sentrux/rules.toml`). Вынос канвы во
  `frontend_module` ради одного потребителя не оправдан. Приёмы drag смотреть там, код не
  импортировать.
- **Модель редактора — сам `ScenePreset`.** Отдельного «документа» нет: правка = новая
  копия Pydantic-модели, undo = стек словарей `to_dict()`. Вторая модель рядом с
  `ScenePreset` разошлась бы с ним на первом же новом поле.
- **Тестовый контент — демо-бутылка из истории git.** `6116adf3:Create_bottles/Images/`:
  `bottle.png` 656×850, `cap.png`, `ring.png`, `eticet.png` — все четыре проверены
  чтением, 4 канала (RGBA). На однослойном диске редактор проверить не на чем.

## Решения 2026-09-27 (владелец)

- **О-2 — план одобрен, цель шире демо.** Владелец заводит объекты разной сложности. У каждого слоя —
  стандартные операции: сдвиг, масштаб, поворот, цвет; аугментация — на выбранные слои по своим правилам,
  для последующего использования на линии. Контракт 3.1a это покрывает, **кроме цвета** (ниже).
- **О-3 — от класса зависит отмеченный слой; сейчас это буква.** Для диска владелец хочет варьировать
  отдельно: размер диска, размер буквы, поворот буквы, цвет диска, цвет буквы, шрифт. Факт кода:
  `ObjectFactory.make` кладёт спрайт класса целиком (диск и буква слиты в одну картинку) слоем `base`
  **первым**, слои пресета — поверх. Раздельные размер и цвет диска и буквы так невозможны: нужны два слоя —
  диск снизу, буква сверху — и отметка «этот слой берёт спрайт класса» в пресете, в любой позиции.
  Без отметки — прежнее поведение (`base` первым), пресет `letters_disk` не меняется. → Task 1.1b.
- **Цвет — новая операция слоя.** `hue_shift_deg` на ахроматичных пикселях ничего не делает — замер
  2026-09-27, `_hue_shift(…, 120)`: `(255,255,255)`, `(0,0,0)`, `(128,128,128)` остаются как были,
  `(200,40,40)` → `(40,200,40)`. Белый диск и чёрная буква так не перекрашиваются. → Task 1.1b.
- **Шрифт — это набор спрайтов класса, не трансформ.** `SpriteCatalog.get_sprite` уже берёт случайный
  файл из папки класса; шрифты = несколько файлов на букву. Нужен генератор букв по TTF (Pillow 12.2
  в окружении). → Task 1.1b.
- **На реальной линии диски готовые и не меняются.** Все вариации — по умолчанию выключены (вырожденные
  диапазоны); они для испытаний устойчивости и датасета, не для имитации линии.
- **О-5 — HTML и Qt оба, над одним бэкендом.** Команды пресета (1.2a) — единственная поверхность; HTML на
  `pult_web` (1.2h) и вкладка `sim.*` (1.2b) — два тонких клиента одних и тех же команд, без своей логики и
  своего рендера. HTML идёт первым (не ждёт И2–И5), Qt — когда готова И3. Паритет проверяется одним
  набором сценариев против обоих клиентов.

## Открытые вопросы

1. **Эффект налива** (`fill_level` — маска заливки по уровню, был в историческом
   `LayerImage`) — нужен ли в первой версии редактора или вместе с настоящим пресетом
   бутылок? Сейчас вынесен в Task 2.1 и помечен как необязательный.
2. **Один пресет — один класс объекта или каталог классов?** `ScenePreset` Task 3.1 несёт
   каталог классов (буквы). Для диска класс меняет один слой (букву), остальные общие.
   Редактору нужно правило «какой слой зависит от класса» — уточняется по факту контракта
   3.1, до старта Task 1.2.
   **Закрыт 2026-09-27 (О-3):** каталог классов, от класса зависит отмеченный слой — Task 1.1b.

## Порядок запуска задач

По стоящему правилу проекта: независимый `tester` до реализации (один раз на механизм:
1.1 — пресет, 1.2 — модель и окно, 1.3 — канва), break-injection по каждому заявленному
свойству, `reviewer` синхронно после каждой задачи. GUI-тесты, способные зависнуть
(`QTest`-жесты), идут с дедлайном, а не до таймаута сьюты.

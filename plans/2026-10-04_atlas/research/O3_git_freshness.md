## 2. «Одна git-ветка на модуль, сливать потом» — оценка по числам

### 2.1 Что даст идея и что она ломает

Что владелец, по-видимому, хочет: чтобы знание о модуле лежало в одном месте и менялось в одном месте; чтобы агенты, работающие над разными модулями, не мешали друг другу.

| Проверка | Число | Что предсказывает для «ветка на модуль» |
|---|---|---|
| Коммит с кодом трогает 2+ модуля | 44% (код-модули) / 87% (с docs, plans) | Почти половина коммитов не лезет ни в одну ветку: надо делить по модулям или выбирать «хозяина» |
| Слияние трогает 3+ модулей кода | 43%; 5+ — 26% | Задача плана = слияние 3–5 веток модулей. Порядок слияния и зависимости между ветками станут отдельной работой |
| План трогает модулей | медиана 5, среднее 8.6 | Один план = 5–9 веток, которые обязаны попасть в main вместе. Иначе main сломан (изменили IPC-контракт в `router_module`, а потребитель в `process_module` ещё на своей ветке) |
| Горячие модули | `process_module` 240 коммитов, `router_module` 90 | Именно в них 3–4 агента правят одновременно. Ветка на модуль не убирает гонку, а переносит её на слияние |
| Время жизни ветки сегодня | медиана ~1 час, 91% ≤1 дня | Долгая ветка модуля сделает «дрейф от main» нормой: `feat/lifecycle-owner-scope` за ~несколько дней уже в 118 коммитах позади main |
| Документы и граф | один источник правды = main | У каждой долгой ветки свои `README/STATUS`, свой `graph.json` (post-commit хук `graphify update .` пересобирает граф на каждом коммите той ветки), свои `docs/maps`. Правды «как сейчас» нет нигде, пока ветки не влиты |
| Слияния уже дороже коммитов | слияние: медиана 14 файлов, 4 области; 38 из 191 без `Why/Layer` | Больше слияний = больше мест, где трейлеры не проверяются (валидатор пропускает `Merge …`) |

Известные ловушки именно этого репозитория, которые ветка на модуль усилит: (а) один файл — два писателя (`docs/sessions/<дата>.md`, `ORDER.md`, `MEMORY.md`, `MODULE_TIERS.md`); (б) `plans/queue/ORDER.md` и сводные таблицы — общие по определению; (в) `pre-commit` с откатом stash при pathspec.

**Вывод: не брать.** Идея решает «агенты мешают друг другу» ценой «ни одна ветка не знает, что в main». Первое уже решено worktree на задачу (80 worktree, 91% веток живут ≤1 дня). Второе — главная цель владельца («один источник правды, не дубли»), и ветки на модуль бьют по ней прямо.

### 2.2 Сравнение четырёх альтернатив

| Вариант | Что это | Плюсы по числам | Минусы | Оценка |
|---|---|---|---|---|
| (a) trunk-based, короткие ветки на задачу плана (**сегодня**) | `<type>/<slug>`, worktree, слияние в main | 91% веток ≤1 дня; Refs 96%; один main — одна правда | Не знает модулей; 109 разных областей в заголовках | База. Оставить |
| (b) модуль в заголовке `type(module)` + `Refs` | область заголовка = id модуля из реестра | Даёт связь «коммит → модуль» без веток; 120 коммитов уже без области, 109 значений — одна нормализация | Коммит на 2+ модуля: нужно правило (главный модуль или список через запятую — регэксп уже допускает запятую) | Брать. Дешево, но **выводить автоматически из путей**, а не просить агента угадывать |
| (c) файл владения `path → модуль` (как CODEOWNERS), на нём хуки обязательств по документам | один `modules.yaml` / `.claude/modules.toml` | Единственный способ вычислить «тронут модуль X» без угадывания; `.sentrux/rules.toml` уже содержит часть карты слоёв | Его нужно поддерживать при добавлении модуля (раз в неделю, не в день); `other` 209 коммитов (корневой `backend_ctl/`, `apps/`, `tools/`) сегодня не принадлежат никому | Брать. Это ядро всей системы |
| (d) пост-слияние регенерация (реестр, граф, HTML) только на main | CI/пост-хук после слияния | Одна точка записи → ноль конфликтов писателей; работает в облаке | Задержка на цикл CI; сгенерированное не должно коммититься обратно в конкурентном режиме | Брать для **производных** артефактов (карта модулей, граф, HTML-учебник); не для рукописных документов |

### 2.3 Рекомендация: (a) + (b) + (c) + (d), ветки на модуль — нет

Причины:
1. (a) уже измерен как рабочий. Менять его — риск без выигрыша.
2. (c) — один источник «что такое модуль». От него питаются (b), обязательства по документам, реестр, граф, HTML и карта зависимостей. Без него каждая система заводит свой список модулей — это и есть дубликаты, от которых хочет уйти владелец.
3. (b) выводится из (c): хук подставляет/проверяет область по застейдженным путям. Сегодня 109 значений области — это просто шум для любой автоматики.
4. (d) закрывает «правда одна»: производное собирается только из main, и никто не держит пер-веточных копий.
5. Параллельным писателям ничего нового писать в общие файлы не надо (см. §3): это снимает ловушку из `feedback_a_hook_that_writes_a_shared_file_deadlocks_two_writers`.

Что взять от идеи владельца: **владельца модуля как поле** в `modules.yaml` (кто агент-эксперт/карта `docs/maps/<m>.md`), а не ветку. И то, что «слияние потом» полезно для опасных долгих работ — это уже есть: `feat/line-sim`, `feat/lifecycle-owner-scope`; правило «не жить дольше N дней без слияния main внутрь» можно добавить как предупреждение (замер: 3% веток >7 дней).

## 3. Механизм свежести при многих параллельных агентах

Базовые числа для оценки ложных срабатываний: документ модуля сопровождает код в 50% правок (§1.6). Значит жёсткая блокировка «код → документ» на каждом коммите отклонила бы **около половины** коммитов с кодом. Блокировать так нельзя.

Стоимость «за коммит» ниже — **оценки по устройству, не замеры** (валидатор уже зовёт `git diff --cached` и читает файл конфигурации; добавочно — сопоставление путей с глобами). Замерить до внедрения.

### Вариант A. Обязательство по документу на коммите

Правило: коммит трогает исходник модуля X (по `modules.yaml`) → должен трогать документ X (`STATUS.md`/`README.md`/`DECISIONS.md`) **или** иметь трейлер `Docs: n/a (<причина>)`. Каркас готов: в `validate_commit.py` шаг 7 «tests-gate» делает ровно это для `tests/` (`staged_files`, `_glob_to_regex`, `Tested: skip (<reason>)`). Переиспользовать.

| Параметр | Оценка |
|---|---|
| Цена за коммит | миллисекунды (уже есть список застейдженных путей) |
| Ложные срабатывания | **высокие при слепом правиле** (50% кода без документа). Снизить: срабатывать только на изменение публичной поверхности — `interfaces.py`, `__init__.py` с экспортами, схемы `SchemaBase`, `DECISIONS`-связанные пути; `fix` и `test` — только предупреждение. Долю нужно замерить на 517 коммитах: сколько из них трогают публичную поверхность |
| Конфликты писателей | **нет** (хук читает, не пишет). Но заставляет **каждого** писателя править `STATUS.md` модуля → сам по себе рождает конфликт слияния в горячих модулях (`process_module` 240 коммитов за 60 дней, 3–4 агента параллельно). Смягчение: обязательство — «добавить строку в журнал изменений модуля», файл `docs/…/<m>.changes.md` с appended-only строками и `merge=union` (как уже сделано для `docs/sessions/*.md` через `.gitattributes`) |
| В облаке | локальный `.git/hooks` в облачный clone **не попадает** (хуки не версионируются; `install_hook.sh` надо запускать). Поэтому правило дублируется в CI (`.github/workflows/ci.yml` уже есть) как проверка диапазона `main..HEAD`: тот же код, `python scripts/validate_commit/validate_commit.py` по каждому коммиту |
| Обход | `--no-verify` — оставить, но CI ловит |

### Вариант B. Штампы `verified_at` + ворота устаревания

Каждый документ несёт `verified_at: <дата, хеш>`; ворота краснеют, если код модуля новее штампа более чем на N дней.

| Параметр | Оценка |
|---|---|
| Цена за коммит | 0 при коммите; ворота на CI — чтение дат |
| Ложные срабатывания | средние: «проверено» — это обещание человека/агента, а не факт; штамп можно поставить, ничего не проверив. Замер проекта: `docs_verify` (19 проверок) держится только потому, что **исполняет** утверждения, а не ставит штамп |
| Конфликты писателей | **плохо**: штамп — запись в документ модуля при каждой проверке; два писателя в одном файле. Это ровно ловушка из памяти (общий файл, который меняется при коммите любого автора) |
| В облаке | да (чисто файловая проверка) |
| Вывод | **штамп не писать вручную.** Возраст вывести из git: `git log -1 --format=%cs -- <код модуля>` против `git log -1 --format=%cs -- <документ модуля>`. Это то, что я посчитал в §1.6 (18 модулей >30 дней). Ноль записей, ноль конфликтов, ноль возможности соврать. Штамп допустим только как **результат исполняемой проверки** (`docs_verify`-подобной), и тогда его пишет один писатель на main |

### Вариант C. Сгенерированные разделы между маркерами (как `scripts/sync`)

Каркас есть: `scripts/sync` пересобирает таблицы между `<!-- … -->` в `multiprocess_framework/DECISIONS.md` и `docs/ADR_REGISTRY.md`; `--check` падает при дрифте. Плюс `scripts/plans_progress --sync-order` пишет блок в `ORDER.md`.

| Параметр | Оценка |
|---|---|
| Цена за коммит | если запускать на каждый коммит — секунды (парсинг ~100 модулей) и **запись в общие файлы** |
| Ложные срабатывания | низкие: генератор детерминирован, `--check` показывает diff |
| Конфликты писателей | **высокие, если генерировать в ветках**: общий сводный файл меняется у каждой ветки, добавившей модуль или ADR → конфликт слияния на каждой второй ветке. В `ORDER.md` это уже решено правилом «писатель блока — лид в main, в точке слияния» (`plans_progress` README). Обобщить это правило |
| В облаке | да, и это лучшее место: единственная точка записи |
| Вывод | **Сводное — только на main.** В ветках — только `--check` (чтение, красный/зелёный, без записи). Запись — в CI после слияния или командой лида |

### Вариант D. Ночной / облачный проход по самым устаревшим картам

Рутина (schedule/cloud agent) берёт K самых устаревших по §1.6 модулей (разница дат «код − документ»), читает код, сверяет утверждения карты `docs/maps/<m>.md`/`README`/`STATUS`, открывает PR с правками и списком «не смог проверить».

| Параметр | Оценка |
|---|---|
| Цена | токены облачной сессии: **полная сессия ≈ 107–228k токенов на вход агента** (замер пилота «Компания v2» в `.claude/CLAUDE.md`); K модулей × ~150k. 18 модулей >30 дней ≈ 2,7M токенов на разовую раскачку — прикинуть против кредита $250 до 4 ноября |
| Ложные срабатывания | нет блокировок; риск — агент «подтвердит» неверное. Нужны правила проекта: вердикт без вход → выход — совет; честный список «что не проверил» |
| Конфликты писателей | один писатель (рутина), результат — PR, ничего не пишется в main само |
| В облаке | **да**, это целевая среда (Linux, GitHub clone, нет Ollama: qex недоступен, использовать `git grep`/graphify) |
| Вывод | Брать как **страховку**, не как основу: ловит то, что A не видит (правки без `fix`-документа, протухание без правок кода) |

### Сводная таблица

| Вариант | Стоимость за коммит | Ложные срабатывания | Конфликт писателей | Облако |
|---|---|---|---|---|
| A. Обязательство (`Docs: n/a`) | мс | высокие при слепом правиле → нужны уровни | нет (читает) + горячие файлы → журнал `merge=union` | через CI-копию правила |
| B. Штампы `verified_at` | 0 | средние (штамп ≠ проверка) | **есть** (запись в общий документ) | да |
| B′. Возраст из git (без штампа) | 0 | низкие | **нет** | да |
| C. Генерируемые разделы | секунды, если на каждый коммит | низкие | **есть**, если в ветках | да, на main |
| D. Ночной проход | токены (облако) | нет блокировок | один писатель, PR | да |

### Рекомендуемая комбинация

1. **B′** (возраст из git) — базовая метрика для всех. Нулевая запись.
2. **A** в два уровня: в локальном хуке — предупреждение; в CI на диапазоне `main..HEAD` — блокировка только для публичной поверхности (`interfaces.py`, экспорты, схемы). Остальное — отчёт. Обязательство выполняется строкой в append-only журнале изменений модуля, а не правкой общего `STATUS.md`.
3. **C** только на main, одним писателем (CI после слияния или лид). В ветках — `--check`.
4. **D** раз в ночь/неделю по списку B′; результат — PR.
5. Жёсткое правило против общих файлов: хук **никогда не пишет** в файл, который может править второй писатель. Проверка и генерация — раздельные шаги; запись только в точке слияния.

## 4. Валидатор коммитов и связка коммит → задача → модуль → документ

### 4.1 Что есть

`scripts/validate_commit/validate_commit.py` (1102 строки), хук `.git/hooks/commit-msg`:
- заголовок `type(scope): …` по регэкспу; тип из списка; пустая строка; `Why:` и `Layer:` обязательны; значения `Layer` — из `.claude/commit-layers.txt`; `Risk`, `Reversible` — предупреждения;
- **Refs по ветке**: ветка `<type>/<slug>` → ищется план (три маршрута: поле «Ветка:» в шапке плана, glob `plans/YYYY-MM-DD_<slug>…`, ранее написанные `Refs:` в ветке) → если план найден, коммит **обязан** содержать `Refs: plans/<slug>…`;
- шаг 7 «tests-gate» (`tests_gate`, из `.claude/modes/_stack.md`, блок ```ini): при застейдженном коде без `tests/**` нужен `Tested: tests/<существующий путь>` или `skip (<reason>)`;
- пропускает `Merge `, `merge: `, `Revert `, `fixup!`, `squash!`, `amend!` (поэтому 38 слияний без `Layer`, 51 без `Refs`).
- `check_injections.py` — отдельная проверка инъекций по плану.

`scripts/plans_progress/plans_progress.py` (2150 строк): читает `Refs:` **только** чтобы связать ветку с планом (`_step_refs`: самый новый коммит `main..<ветка>` с токеном `plans/…`) для режима `--who` (какие worktree активны). **Связи «коммит → конкретная задача» нет.** Статус задачи в плане ставит человек/агент вручную (`[DONE <hash>]`).

### 4.2 Замеры связности

| Вопрос | Значение |
|---|---|
| Обычные коммиты с `Refs:` | 1777 / 1860 = 96% |
| В строке `Refs:` есть идентификатор задачи/фазы | 374 / 1777 = **21%** |
| В сообщении есть `Task X.Y` где угодно | 662 / 1777 = **37%** |
| `Task <id>` в заголовке | 461 |
| Токены `plans/…` из Refs, которые не указывают на существующий файл (включая `_archive/`) | **121 из 1955 = 6%** (напр. `plans/2026-10-02_plans-progress-dashboard.md` после переноса в папку) |
| `Docs:` трейлер | 0 |
| Область заголовка = id модуля | нет (109 значений, свободный текст) |

То есть: коммит → **план** связан хорошо (96%). Коммит → **задача** — нет (21–37%, свободный текст). Коммит → **модуль** — нет вообще (только `Layer` из 6 значений). Модуль → **документ** — нет карты (README/STATUS/DECISIONS лежат по соглашению рядом, но `CONTEXT.md` нигде нет, а `scripts/aggregate_context` его ждёт).

### 4.3 Чего не хватает для автосвязи «коммит → задача → модуль → документ»

| № | Чего нет | Что добавить | Где |
|---|---|---|---|
| 1 | Файл владения `path → модуль` (id, слой, документы, владелец) | `modules.yaml`: `id`, `paths` (глобы), `docs` (README/STATUS/DECISIONS/map), `layer`, `tier`. ## Что я оставил открытым / что в моей работе ненадёжно

1. **Агенты не отличимы от человека в git.** Автор — 2 имени; доля «коммитов агентов» не измерена. Скорость (44 коммита/день, пик 204) включает коммиты агентов под именем владельца.
2. **Метрика «документ тронут» грубая.** Я считал только `README/STATUS/DECISIONS` внутри каталога модуля. Карты в `docs/maps`, ADR в `docs/claude/DECISIONS/`, `docs/reviews` не считал документом модуля. 50% — нижняя оценка «документ обновлён»; верхняя — 90% (любой `.md` из `docs/`/`plans/`). Метрика «в течение 7 дней» (93%) завышена и не используется.
3. **Верность документов не проверена вообще.** «Тронут» ≠ «верен». Для верности есть только `scripts/docs_verify` (19 проверок, только наблюдаемость). Возраст из git — прокси.
4. **Определение модуля** — по пути. `fw/_other` (126 коммитов) и `other` (209; корневой `backend_ctl/`, `apps/`, `tools/`) — не модули по моему определению; доля «2+ модулей» зависит от того, как их считать. Для кодовых модулей я их исключал; в строках «все области» — включал.
5. **Время жизни ветки** считалось по `committer date` первого коммита: при rebase/cherry-pick сдвигается. Слияния без второго родителя-ветки (fast-forward) не попали (105 из 191 слияний — первый родитель main; остальные — `main` влит в ветку).
6. **Стоимость хуков — оценка по коду, не замер.** Время работы валидатора на коммите не измерял.
7. **Доля публичной поверхности** среди 517 коммитов не посчитана — от неё зависит, сколько реально заблокирует вариант A. Это первое, что надо замерить.
8. **Облако не проверено:** не знаю, какие хуки, Python-версия и права доступны в облачном clone; полагаюсь на то, что `.github/workflows/ci.yml` работает (содержимое не читал).
9. **graphify MCP и qex не использовались** (qex недоступен по брифу; граф не нужен для этих замеров).
10. Цена облачного прохода (~150k токенов на модуль) взята из замера пилота в `.claude/CLAUDE.md`, на этой задаче не перемеряна.
11. Подсчёт «конфликтов слияния» не делал: слово «conflict/конфликт» встречается в 78 сообщениях, но это обсуждения, а не события.

## Вопросы владельцу (до 5)

1. **Ветки на модуль не делаем, оставляем короткие ветки на задачу плана + карту модулей `modules.yaml`?** Рекомендация: да. Основание: 43% слияний трогают 3+ модуля, план — медиана 5 модулей, 91% веток живут ≤1 дня.
2. **Блокировать ли коммит без обновления документа модуля?** Рекомендация: нет на каждом коммите (отклонил бы ~50% коммитов с кодом). Блокировать в CI только при изменении публичной поверхности (`interfaces.py`, экспорты, схемы); остальное — отчёт о возрасте. Выход — `Docs: n/a (<причина>)`.
3. **Добавить трейлер `Task: <slug>#<id>` и перевести область заголовка на id модуля из `modules.yaml`?** Рекомендация: да; сейчас 109 областей и связь «коммит → задача» есть лишь в 21–37% коммитов.
4. **Свежесть — из git (возраст «код новее документа»), без штампов `verified_at`, сводное — только на main одним писателем?** Рекомендация: да (штамп = запись в общий файл = ловушка двух писателей).
5. **Разовая раскачка облачным проходом по 18 модулям с документом старше кода на 30+ дней (оценка ~2,7M токенов) — тратить на это часть кредита $250?** Рекомендация: сначала дёшево — `modules.yaml` + отчёт возраста (без LLM); облачный проход — только на 5–6 самых «горячих и устаревших» (`config_module`, `command_module`, `data_schema_module`, `router_module`).

## 1. Скорость `card`/`ref` — расследование (investigator, 2026-10-09) → Task 1.6g

**Симптом.** Пин-тест `test_card_on_origin_main_pin` идёт 723–928 с на Windows (в CI на ubuntu весь набор Атласа — 323 с).

**Что оказалось.**
- 13 минут — не один вызов: тест зовёт `card` для всех 87 модулей пина (`test_views_pinned.py:102`); один вызов — ~20 с
  холодный, повтор того же модуля — 0,23 с.
- Каждый первый `card`/`ref` модуля на ревизии стоит на Windows **12–14 с**, даже когда build уже в кэше: выгрузка
  `.py` всех 11 корней `modules.yaml` (`codemap.checkout`, 3821 файл, ~40 МБ) и граф grimp строятся заново на каждый
  вызов — они не зависят от модуля, но живут один процесс. Разбивка одного вызова: `git archive` 0,45 с, распаковка
  4,0 с, граф 3,0 с, «Кто использует» 2,1 с (холодное чтение файлов), Scan 0,34 с, удаление 0,37 с.
- Агент, смотрящий 5 модулей после коммита, ждёт около минуты; кэш вида 1.6e помогает только повтору того же
  модуля на том же sha.
- **`tar` на Windows всегда падает, откат молчит.** `codemap.checkout` зовёт `[tar, "-x", "-C", dir]` без `-f -`:
  bsdtar из System32 открывает ленту `\\.\tape0` (rc=1), GNU tar из Git не открывает `C:\…` в `-C` (rc=2) — и с
  `-f -` тоже (проверено лидом). Откат на `tarfile` — 4,0 с вместо ~1 с. Рабочая форма для обоих:
  `[tar, "-x", "-f", "-"]` с `cwd=<каталог>` (проверено лидом: rc=0 у GNU tar и у bsdtar).

**Решение (Task 1.6g).** (1) `tar -x -f -` в `cwd`, откат на `tarfile` — с предупреждением в stderr; (2) выгрузка
ревизии сохраняется на диске (`data/atlas/checkout/<ключ>`, атомарно: распаковка во временный каталог и
переименование; хранятся последние 3) и переиспользуется следующими процессами; (3) кэш grimp рядом с выгрузкой
(файлы неизменны); (4) в одном процессе `Code` ревизии переиспользуется (цикл теста по 87 модулям). Отвергнуто:
кэш только в памяти процесса (агенты зовут CLI — каждый вызов новый процесс); расчёт всех 87 модулей при первом
промахе (первый вызов ~50 с вместо 12 с).

**Урок для памяти** (записать в канон с 1.6g): `tar` на Windows без `-f -` читает ленту, GNU tar из Git не берёт
`C:\` в `-C`; молчаливый откат на `tarfile` скрывал это — всегда `-f -` + `cwd`, откат логировать.

## 2. Сервер Атласа — один процесс на сессию (идея владельца 2026-10-09) → Task 1.10e

Постоянный процесс держит граф, разбор файлов и базу в памяти; каждый следующий запрос — доли секунды. Для агентов —
**MCP-сервер Атласа** (как `qex`, `sentrux`): Claude Code запускает его один раз на сессию, агенты зовут инструменты
`atlas_card`, `atlas_ref`, `atlas_brief`, а не CLI.

| | Кэш на диске (1.6g) | Сервер / MCP (1.10e) |
|---|---|---|
| Повторный модуль той же ревизии | ~2–4 с (оценка до замера 1.6g) | < 0,5 с |
| Кому помогает | всем: CLI, хукам, CI, тестам, другим сессиям и worktree | тем, кто ходит через сервер |
| Процесс не запущен или упал | ломаться нечему | нужен откат на CLI |
| Новый коммит | новая выгрузка, старая в кэше | сервер следит за ревизией и корнем |
| Сложность | ~50 строк в `codemap.py` | жизненный цикл, конфиг MCP, права ролей |

Порядок: сначала 1.6g (холодный старт сервера берёт выгрузку из того же кэша), затем библиотека 1.10a (сервер —
тонкая обёртка над ней), затем 1.10e. Решение «делать ли» — по числам: повторный `card` после 1.6g ≥ 2 с или журнал
1.10b (U1) показывает много вызовов `atlas` на задачу. Вопросы дизайна: один сервер на корень или на сессию
(worktree — разные корни); смена ревизии (HEAD двигается — кэш по sha); доступ субагентов к MCP-инструментам
(`tools:` в определениях ролей); Windows — запуск через `.mcp.json`, как `qex`.

## 3. Мелочи из ревью 1.7a и 1.9a (задач нет; брать попутно)

- **1.7a, тест A6 стережёт текст `ci.yml`, а не исполнение:** мутации ревью `= push` → `!= push`, `if: false` у job,
  `if:` у шага pytest, `|| true` после `check` — тесты зелёные. Поведенческий тест: исполнить `run` шага `check` под
  `bash` с заглушкой `uv` для `EVENT=push` и `EVENT=pull_request` и сверить argv; плюс «нет `if:` и `|| true`».
- **1.7a, хук пропуска `slow` действует на любой каталог корневого прогона:** будущий `@pytest.mark.slow` в
  Services/Plugins молча уйдёт в skip с причиной «atlas». Сегодня маркер только у Атласа. Выход: ограничить хук
  каталогом `scripts/atlas/tests` (тогда A1–A4 tester'а — на синтетике вне дерева — надо переписать) или маркер
  `atlas_slow`.
- **1.7a, `index --check` на PR сверяет синтетическое слияние:** если `main` ушёл вперёд и задел индексируемые
  модули, INDEX.md в слиянии может отстать при свежих обеих сторонах — красный, нужен rebase. Не воспроизведено.
- **1.7a, push в `main` проверяется по `--base <event.before>`:** статус success, но какая ветка шага взялась, по
  логу без авторизации не видно — подтвердить скриншотом шага при случае.
- **1.9a, хук `lint-result.sh` молчит, если путь интерпретатора с пробелом** (`$PY` без кавычек — идиома
  `autofix-text.sh`).
- **1.9a, архивный план с тем же slug** даёт второй `RESULT_FORM` на тот же узел `result:<slug>#<id>`.
- **1.9a, `views._text` читает `utf-8`, не `utf-8-sig`:** раздел в первой строке файла с BOM `pack` не видит.
- **1.7a/1.9d, `plans_ledger.py brief` отвергает брифы Атласа:** метки ролей лежат в fenced-блоках — входные
  данные 1.9d (формат брифа совместим с `brief`).

## 4. Процесс (локальная схема с 1.6e)

- **Push в `main` идёт в обход правила GitHub «только через PR»** («Bypassed rule violations» — у учётной записи
  владельца есть обход). Локальные слияния лида держатся на этом обходе; альтернатива — PR на каждое слияние
  (владелец открывает, как с 1.7a). Решение за владельцем.
- **CI до слияния — только через PR владельца:** `gh` не авторизован, push в ветку CI не запускает. Статус прогонов
  лид видит через открытый API GitHub (`/actions/runs`), логи — нет (403 без токена).
- **Ревьюер случайно запустил `uv run` в worktree** (подмена PATH не сработала) — `uv.lock` переписан, создан `.venv`.
  В промпт ревьюера: «никаких `uv`; проверку шага CI — исполнением `run` с заглушкой через функцию bash, не PATH».

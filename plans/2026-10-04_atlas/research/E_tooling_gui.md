### 3. Формат строки задачи (`plans/README.md`, «Формат задачи и прогресс»)

В `plan.md`, раздел с заголовком «Порядок выполнения» (или `Execution order`, `Порядок`):

```
- Task <id>: название [PENDING] (после <id>)
- Task <id>: название [DONE 2026-10-02 — `хеш`; числа приёмки]
```

Закрытый набор статусов: `PENDING`, `IN PROGRESS`, `DONE`, `BLOCKED`, `DEFERRED`, `SUPERSEDED`. Процент = `DONE / (всего − DEFERRED − SUPERSEDED)`, всегда рядом `N из M`.
Статус пишется **один раз** (в плане); при расхождении побеждает строка списка. Id: `[A-Z]{0,2}[0-9]+[a-z]?(\.[0-9]+[a-z]*)?(-[a-z0-9]+)*` (`1.3`, `1b.2b-pre`, `T1`).
Первая группа `[...]` со словом набора; код-спаны не считаются; хвост после статуса свободный. Старые форматы читаются терпимо (заголовок `#### Task X.Y` + `**Статус:**`, таблица с `✓`, `tasks/<id>.md`) и порядок источников задан: пункты раздела → заголовки `Task` → таблица `✓` → файлы `tasks/`.
Layout v2 каталога плана: `plan.md` (контракт + задачи одной строкой), `design.md`, `tasks/<id>.md`, `tasks/<id>.result.md` (≤ 2 КБ), `amendments.md` (только дописывание), `contract.lock` (заморожен `approve`), `SUMMARY.md` (пишет `close`).

### 6. Что механизм показывает и чего не может

**Показывает:** N из M и ячейки по всем планам (включая архив); приоритет и полосу; «можно начинать» по цепочке `После:`; какие worktree живы сейчас (сессии, агенты, последний сигнал) и к какому плану привязаны; находки формата.

**Не может (измерено чтением кода):**
- **Не проверяет отметку по git.** Хеш из `[DONE … \`hash\`]` сохраняется в `Task.ref` как текст; в `plans_progress.py` нет ни `cat-file`, ни `merge-base --is-ancestor`. План может объявить DONE с несуществующим хешем, страница покажет зелёную ячейку. (Шапки планов уже врали минимум в пяти; задача 5.5 сравнивает ветку с `main` по тексту планов, не по коммитам.)
- **Нет времени.** Страница — снимок на момент сборки: ни истории, ни тренда, ни даты закрытия задачи, ни скорости. В `Task` только `ref` (первый хеш) — число коммитов на задачу, авторы, затронутые файлы не собираются.
- **Нет связи с модулями, ADR, дефектами, решениями.** Коды `L-*`/`K-*`/`PC-*` из `plans/queue/defects.md`, `О-*` из `decisions.md`, `ADR-*` из `DECISIONS.md`, поле `Layer:` коммита — не разбираются. Граф связей — только план→план, задача→задача, worktree→план.
- **Нет «живости» без локального журнала.** `data/agent-journal.jsonl` лежит в gitignored `data/` каждого worktree; в облачной сессии (чистый клон) его нет — `active` пуст.
  Работает ли `plans_progress` на Linux, не проверено (тесты гонялись на Windows; код использует `git`, `pathlib`, `subprocess` — переносимо по виду, не по прогону).
- **Не обновляется сам.** Нет хука: страница и блок `ORDER.md` строятся вручную (`--html`, `--sync-order`); post-commit-хук обновляет только graphify.
- **Одна страница = один жёстко заданный набор секций** (`to_html`, склейка строк, стр. 1970–2046): расширить набор нельзя без правки функции; CSS — строка-константа.

### 7. Чем это может стать: общий реестр или только планы

**Ответ: реестром стать может, но не расширением этого файла.** Годится образец, не код парсера.

**Модель данных сегодня** (`plans_progress.py`, стр. 116–200):

| Сущность | Ключ | Поля |
|---|---|---|
| `Plan` | basename (уникален по `plans/` + `_archive/`; при дубле побеждает архив) | `name, rel, archived, tasks[], lane, tier, header_status, info[], after[], after_reason, waiting_on[], header_branch, active[], priority, ready, dep_unknown, dep_cycle, …` |
| `Task` | `(plan, id)` | `id, title, status, ref, unmarked, after[], ready` |
| `Finding` | `plan:КОД[:id]` | `code, plan, task_id, blocking, text`; `key` — ключ базы-храповика |
| `OrderRow` / `SnapRow` | basename плана | `tier, lane, info[]` / `n, lane, plan, next, waits` |
| `Active` | worktree | `branch, worktree, via, sessions, agents, last_signal` |
| Рёбра | — | `plan→plan` (`after`), `plan→условие` (`waiting_on`), `task→task` (`after`), `worktree→plan` (шаг `via`) |

**Обобщённая модель (предложение для дизайнера).** Узел: `Node{kind, id, path, status ∈ закрытый набор вида, stamp{verified_at: sha, covers: [пути]}, edges[{type, to}], findings[]}`.
Виды: `plan`, `task`, `module`, `doc`, `adr`, `defect`, `decision`, `diagram`, `memory`. Типы рёбер: `after` (план/задача ждёт), `refs` (коммит → план, из `Refs:`), `implements` (задача → коммит, из хеша
в статусе — **после** проверки по git), `covers` (документ → пути, из штампа), `decides` (ADR → модуль), `tracks` (дефект → план/задача), `works_on` (worktree → план). Вид `plan` — первый адаптер; текущий `Plan`/`Task` ложатся в `Node` без потерь.

**Точки расширения, которые уже есть в коде (то, на что можно опереться):**

| Точка | Где | Чем полезна |
|---|---|---|
| Находки + база-храповик | `Finding`, `build_findings`, `load_baseline`, `run_check` | **лучшая часть**: новая проверка включается без починки мира (сегодня 0 блокирующих, 102 информационных на 61 плане); годится для проверки штампов свежести документов |

**Чего нет и нужно построить для реестра:** (1) регистрация источника/адаптера (сегодня источник один и зашит в `main`); (2) расширяемый набор секций страницы (сегодня `to_html` — монолит); (3) словарь статусов на вид узла (сегодня один — для задач);

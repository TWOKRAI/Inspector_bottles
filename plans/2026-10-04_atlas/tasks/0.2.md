**Level:** Middle. **Assignee:** лид solo (один файл, ~30 строк YAML; стадии 0, 3, 5 — не solo). **Дерево:** worktree
`.claude/worktrees/atlas`, ветка `feat/atlas`; до правки — `main` влит в ветку (валидатор 3.0 из `main`).
**Goal:** каждый PR в `origin` проверяет все свои коммиты валидатором из **базы** PR; красный job — при отказе

нет (см. Out of scope).
**Зачем:** облачные сессии Атласа сдают работу только PR, git-хуков в облаке нет — гейт там только CI (plan.md,
«Правила исполнения»). 0.2 — предусловие пилота P1.1.
**Handoff:** reviewer (спека; ред. 1 — агент `abd83d1810cbc13ba`, CHANGES REQUESTED, 10 пунктов учтены) → лид (правка
`ci.yml`, A1, A4) → push `main` и тестовых веток по правилу владельца (договорённость с сессиями) → A2, A3, A5 → reviewer.
**Тестер не запускается:** механизм — job CI; его приёмочный тест — пара PR «красный/зелёный» и эмуляция шага на
истории (plan.md: «для гейтов CI инъекция = PR с нарушением»). Пропуск пишется в коммит.
**Изменение приёмки плана** (plan.md, строка Task 0.2): было «`origin/main..HEAD`; без `Layer:` → красный, с
`Layer: framework` → зелёный». При `STRICT = False` без `Layer:` — предупреждение, rc 0, такой PR зелёный. Стало:
диапазон `base.sha..head.sha`, «без `Why:` → красный»; отказ без `Layer:` придёт сам с commit-mechanism 3.1 (job не
меняется). Строку плана правит этот же коммит.

## DESIGN
1. В `.github/workflows/ci.yml` новый job `commits` (имя `commits (validate_commit, PR)`), только для
   `pull_request`: `if: github.event_name == 'pull_request'`.
2. `actions/checkout@v4` с `fetch-depth: 0` (без него `base.sha` нет в клоне, диапазон не строится);
   `actions/setup-python@v5` с `${{ env.PYTHON_VERSION }}`; без `uv sync` (валидатор — stdlib).
3. SHA — через `env:` шага (`BASE: ${{ github.event.pull_request.base.sha }}`, `HEADSHA: ${{ github.event.pull_request.head.sha }}`),
   не подстановкой `${{ }}` внутри `run:`. Диапазон `$BASE..$HEADSHA`, **не** `HEAD`: при `pull_request` HEAD —
   синтетический merge GitHub.
4. **Валидатор и слои — из базы PR:** первой строкой `run` шага (п. 5) — `git checkout "$BASE" -- scripts/validate_commit/validate_commit.py .claude/commit-layers.txt`.
   Иначе PR ослабляет собственный гейт правкой валидатора или списка слоёв (в облаке CI — единственный гейт). PR,
   который законно меняет валидатор, проверяется старым — безопасная сторона; после слияния хук и job снова одинаковы.
   Шаг пишет в дерево и индекс; в CI это безвредно, локально — только в scratch-клоне.
5. Шаг (текст из ревью, замерен ревьюером):
   ```bash
   git checkout "$BASE" -- scripts/validate_commit/validate_commit.py .claude/commit-layers.txt
   shas=$(git rev-list --reverse "$BASE..$HEADSHA")
   if [ -z "$shas" ]; then echo "ERROR: пустой диапазон $BASE..$HEADSHA"; exit 1; fi
   echo "commits to check: $(printf '%s\n' "$shas" | wc -l)"
   fail=0
   for sha in $shas; do
     git log -1 --format='%h %s' "$sha"
     if ! git log -1 --format=%B "$sha" | python -I -X utf8 scripts/validate_commit/validate_commit.py -; then fail=1; fi
   done
   if [ "$fail" -ne 0 ]; then exit 1; fi
   ```
   Подстановка `$(git rev-list …)` в переменную, не в `for`: в `for` ошибка `rev-list` теряется и job зеленеет, не
   проверив ни одного коммита (ревьюер: rc 0 и при `bash -e`, и при `pipefail`). Слияния не исключать. Тело сообщения
   в лог не печатать (строка `::…` стала бы командой раннера) — только `%h %s`. `python -I` не кладёт каталог
   скрипта в `sys.path`: иначе файл PR `scripts/validate_commit/dataclasses.py` подменит модуль stdlib и гейт
   зеленеет (ревьюер: rc 0 без `-I`, rc 1 с `-I`); `-X utf8` — потому что `PYTHONUTF8` под `-I` игнорируется.
6. Шапка-комментарий `ci.yml` («Что гоняется») — одна строка про `commits`. Остальное в `ci.yml` не трогать.

## Out of scope и риски

**Out of scope:** флаг строгости, env-переменные строгости, склейка трейлеров (commit-mechanism 3.1); проверка на
`push` в `main`; правка `validate_commit.py`; required status checks в настройках репозитория (решение владельца).
**`Refs:` в CI не проверяется:** HEAD отсоединён, план ветки не определяется (`resolve_plan` → `detached-head`).
Закрыть — флагом ветки или базы у валидатора (кандидат f7: при отсоединённом HEAD брать ветку из `GITHUB_HEAD_REF`), отдельной задачей commit-mechanism или Атласа; строка в
`docs/claude/OPEN_QUESTIONS.md`.

**Риски.**
- Слои берутся из базы PR: PR, который добавляет слой в `.claude/commit-layers.txt`, свои коммиты с этим слоем проверит старым списком (до 3.1 — предупреждение, после — отказ «Layer not in list»). Новый слой вводится отдельным PR раньше (согласовано с f7 2026-10-05, строка в их `amendments.md`).
- После 3.1 `Merge branch 'main' into …` с текстом по умолчанию станет отказом — и в CI, и в уже открытых PR. Брифы
  облачных сессий обязаны требовать `git merge -F` с `merge: …` + Why/Layer/Refs (облачная сессия может не попасть в
  `ListAgents` и не получить рассылку f7).
- Устаревает ли `pull_request.base.sha` при `synchronize`, если ветка влила свежий `main`, — не проверено; тогда в
  диапазон попадут чужие коммиты `main`. Запасной вариант — `HEAD^1..HEAD^2` (родители merge-ref). Проверить в A3:
  N из лога = N, записанному до push.
- PR в ветку, у базы которой нет `validate_commit.py` или `.claude/commit-layers.txt` (в origin есть старые ветки,
  например `clean_v3`, `experiment_v3`), будет красным всегда: ошибка pathspec у `git checkout "$BASE" -- …`.

## Инъекции

**Проверка лидом — инъекции (предсказание до прогона, на копии `step.sh` в эмуляции A1):**
- убрать `fetch-depth: 0` (эмуляция — клон `--depth 1`) → `fatal: unable to read tree (…)` у checkout, rc 128, красный;
- вернуть `for sha in $(git rev-list …)` при `HEADSHA`, которого нет в клоне (BASE существует) → `fatal: Invalid revision
  range`, rc 0, зелёный — **показывает, зачем пункт 5**;
- `break` после первого отказа → первый диапазон A1 печатает 1 тему вместо 2;
- убрать `exit 1` в конце → первый диапазон A1 rc 0;
- `scripts/validate_commit/dataclasses.py` с `sys.exit(0)` в дереве → без `-I` зелёный, с `-I` красный;
- диапазон `HEAD^!` (только синтетический merge) → предупреждение, rc 0 — **не ловится до 3.1**, записать как непокрытую;
  `git rev-list HEAD` (вся история) → красный на зелёном PR;
- убрать `git checkout "$BASE" -- …` и ослабить валидатор в ветке PR → эмуляция с изменённым валидатором в дереве
  зеленеет; с командой — красная.

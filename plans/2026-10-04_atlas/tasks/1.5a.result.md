Atlas 1.5a review (2026-10-07): `store.connect` read `PRAGMA user_version`; on a mismatch it closed the
connection, unlinked the file and created a new one. Four `atlas build` processes started together on a
missing database: 11 of 40 exited 2 (`sqlite3.OperationalError: disk I/O error` or `attempt to write a
readonly database` inside `executescript`), 5 of 20 cache rows were lost. The same harness on the previous
code (no unlink): 0 of 40. A process that already held the old file got `attempt to write a readonly
database` on its next write, because the inode was replaced under it.

**Why:** the version read and the unlink are two steps with no lock between them. A second process sees
the half-created file (tables made, version not yet set) as "old" and unlinks it under the first one.
SQLite makes a connection whose file was unlinked read-only. The brief listed the race as an accepted
"not tested" hole; in fact it was a regression against main.

**How to apply:** recreate a derived SQLite cache inside the file, never by replacing the file: an
autocommit connection, one `BEGIN IMMEDIATE` transaction that reads `user_version`, drops the tables, runs
the DDL statement by statement and sets the version. The lock serialises creators and the inode stays.
Prove it with N processes started together on a missing file, and run the same harness on the previous code.

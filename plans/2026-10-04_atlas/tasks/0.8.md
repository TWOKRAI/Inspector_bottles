## 0.8b — метод запуска: замер → решение владельца → `spawn` везде

**Замер.** `scripts/start_method_probe.py` (stdlib + `psutil`): для каждого доступного метода из `fork`, `forkserver`,
`spawn`, 5 повторов:
- (1) **лёгкая строка:** родитель ДО `start()` импортирует тот же набор, что дети (`multiprocess_framework.modules.process_manager_module`,
  `numpy`, `cv2`), иначе fork-дети тоже платят за импорт и разница занижена; N = 4 ребёнка импортируют набор и
  сигналят `Event`; время «старт → все готовы» (медиана, min–max), медиана USS ребёнка (`memory_full_info().uss`) сразу
  после готовности;
- (2) **реальная строка:** время загрузки `examples/minimal_app` (как в `examples-smoke`) при каждом методе — от
  запуска до доказанного IPC, медиана и разброс; число процессов приложения.
- Печать: ОС, Python, CPU, таблица. На Windows `fork`/`forkserver` — «недоступен», не ошибка. Скрипт остаётся в репо
  (повтор на Orin). В PR — временный шаг CI, удаляется последним коммитом.

**Что одинаково, а что нет (записано до замера).** После старта код и разделяемая память (`SharedMemory`, очереди) у
методов одинаковы. Различаются: (а) старт — у `spawn` ребёнок импортирует модули заново; каждый **рестарт** ребёнка
супервизором снова платит эту цену (ADR-PMM-032: ~0,4 с загрузки под spawn); (б) память — у `fork` USS ребёнка сразу
мал, но растёт по мере записи в унаследованные страницы (copy-on-write), у `spawn` своя копия импортов сразу. (в)
Надёжность — не число: `fork` при живых потоках родителя (логгер, Qt) копирует замки в произвольном состоянии; Python
3.14 меняет метод Linux по умолчанию с `fork` на `forkserver` по этой причине.
**Решение — владельца, по числам.** Лид приносит: разница старта на ребёнка и на приложение `minimal_app`, разница USS
на ребёнка × число процессов `inspection_full` = добавка памяти на Orin, рекомендация. Порогов лид не назначает: бюджета
старта и памяти Orin в проекте нет (если появится — правило станет механическим).

**Код при решении «spawn»:**
1. `platforms/base.py` `setup_multiprocessing` — по контракту выше на всех ОС; `freeze_support()` — только win32, как
   сейчас; молчаливое `except RuntimeError: pass` убрать.
2. `system_launcher.py`: `setup_multiprocessing()` — первой строкой `SystemLauncher.__init__`, до `_MpEvent()`
   (`:107`, `:111`): `multiprocessing.Event()` фиксирует контекст по умолчанию (на Linux `fork`) раньше `spawner.py:85`
   (стадия 0: `before None / after Event(): spawn / set again → RuntimeError('context has already been set')`). Вызов в
   `spawner.py:85` остаётся — идемпотентен. Прод-входы прототипа, создающие примитивы `multiprocessing` до
   `SystemLauncher`, developer ищет `git grep` и перечисляет в отчёте; вызов ставится раньше них.
3. `modules/conftest.py`: добавить `pytest_configure` с вызовом `StubPlatformAdapter().setup_multiprocessing()`
   (тесты строят процессы, не проходя через `spawner.py`). Группа A (21 тест) уходит этим.
4. Документы: `.rules/module-state.md:13` (сверить); `process_manager_module/DECISIONS.md` ADR-PMM-032 (`:1425`,
   `:1439-1444` — «Linux — fork» как причина отвергнуть варианты 2–3) — дописать «с 0.8b Linux на spawn», пересмотр
   отвергнутых вариантов — строкой в `docs/claude/OPEN_QUESTIONS.md`; `docs/DESIGN_RULES.md:170`; запись Task 1.5 в
   `OPEN_QUESTIONS.md` (`:1238/:1241`) — «закрыто 0.8b» с SHA.

**Тестер (до кода, слепой, worktree на коммите спеки ред. 2):** ожидания — литералы, проверка
`get_start_method(allow_none=True)` (без `allow_none` вызов сам фиксирует метод и тест зелёный до кода).
- В свежем процессе (`subprocess`) с подменой `sys.platform` на `"linux"` и `"darwin"`: после
  `StubPlatformAdapter().setup_multiprocessing()` → `"spawn"`; повторный вызов — без исключения.
- В свежем процессе: `multiprocessing.set_start_method("fork")` (только где `fork` доступен — Linux/CI), затем
  `setup_multiprocessing()` → `RuntimeError` с текстом из контракта.
- В свежем процессе: `SystemLauncher(...)` без запуска → `"spawn"`, исключения нет (Linux/CI).

- Красные до кода: подмена `"linux"`/`"darwin"` — локально; `fork`→RuntimeError, `SystemLauncher`, сессия pytest —

## Out of scope и риски

**Out of scope:** перевод CI на корневой `testpaths`; branch protection; guard-job под `pull_request_target` (вердикт
Fable — `tasks/0.2.result.md`); `fork`-оптимизации; пересмотр отвергнутых вариантов ADR-PMM-032 (только строка в
OPEN_QUESTIONS).
**Риски.**
- `spawn` на Linux меняет прод Orin: ребёнок не наследует память родителя; всё, что молча работало через наследование
  при `fork`, сломается так же, как сломалось бы на Windows (там класс ошибок уже закрыт). Живой прогон на Orin — после
  0.8, владелец.
- POSIX-only тесты (`parent_death`, R2-контроль) ни разу не были зелёными в CI — могут проявить настоящие ошибки;
  каждая — строкой в отчёт, не `skip`.
- ubuntu-latest (2 vCPU) ≠ Orin — повтор скриптом на Orin.
- Каждый PR открывает владелец по ссылке; промежуточные прогоны — новые push в ветку PR.

## Решения лида (DESIGN; источник — `scripts/atlas/DECISIONS.md`, ADR-ATL-001 §1, §2, §5)

Замеры лида 2026-10-06 (Windows, `main` = `d08ecd308`): `plans_progress --json` — 148 планов, 1240 задач, ~2 с;
два живых вызова подряд байт-в-байт равны; `--root <распакованный plans/ ревизии>` даёт те же 148 планов и
отличается от живого вызова только полями `active` (2 плана) и `branches` (3) — это живое состояние git, у
распакованного каталога git нет. Коллизий slug — 0; планов без даты в имени — есть (`plans/<slug>.md` и
`plans/<slug>/plan.md`). `modules.yaml` — 87 строк, `git ls-files` — 6899 путей.

1. **Узлы `plan`/`task` — из дерева сборки, не из рабочего дерева.** Адаптер `plans` распаковывает только `plans/`
   ревизии (`Tree.materialize("plans")`) и запускает `plans_progress --json --root <каталог>`. Причина: реестр —
   производная дерева сборки (ADR-ATL-001, контекст); `check` строит и `<ref>`, и `HEAD` — узлы обязаны отвечать своей
   ревизии. Распаковка одного `plans/`, а не всего дерева — 6,9 тыс. файлов на каждую сборку не нужны. Нет файла под `plans/` в дереве сборки → пустой выход адаптера, `plans_progress` не вызывается.
2. **Скрипт `plans_progress` — из checkout, где лежит сам atlas**, а не из анализируемого дерева:
   `PLANS_PROGRESS = Path(__file__).resolve().parents[2] / "plans_progress" / "plans_progress.py"`, запуск
   `sys.executable`. Причина: инструмент и данные разделены — у старой ревизии (`<ref>` в `check`) скрипта может не
   быть или он старый; правило «корень — не `__file__`» (1.2) касается данных, не инструмента. Тесты подменяют
   константу через `monkeypatch`. **Принятый предел:** отпечаток кэша (`CORE_VERSION` + `name:version`) не включает содержимое
   `plans_progress.py`; смена его парсера → поднять `PlansAdapter.version` (иначе кэш `<ref>` хранит старый разбор). Хеш скрипта в
   отпечатке — не в 1.3a (правка `build.py` сверх DESIGN, запас бюджета 25 строк).
3. **Значение `plans` в `--json` — живой вызов** `plans_progress --json --root <корень checkout>`, вставленный без
   изменений (`json.loads` его stdout); сверка — байтовая: `json.dumps(plans, ensure_ascii=False, indent=2)` равно stdout
   `plans_progress --json` без завершающего перевода строки (ревью стадии 0: на реальных данных `True`). Причина: ADR-ATL-001 §5 выводит `plans` из гарантии детерминизма и оставляет
   выбор 1.3a; живой вызов — ровно то, что видит владелец, без новой таблицы SQLite и без поля в `AdapterOutput`
   (меньше слоёв). `plans` = `null`, если `--ref` разрешился не в SHA `HEAD` (живое значение описывает checkout, а не
   ревизию) или в корне checkout нет каталога `plans/` (так остаётся зелёным тест 1.2 `data["plans"] is None`).
   `build` и `check` живой вызов не делают.
4. **Узлы и рёбра** (ADR-ATL-001 §1–2; только статичные поля вывода `plans_progress`):
   - `plan:<slug>` — slug = поле `plan` без префикса `^\d{4}-\d{2}-\d{2}_`; `path` = поле `path`; `status` = поле
     `header_status` как есть (обычно `null`); архивные планы входят (на них сошлются `REF_MOVED` и 1.3b);
   - `task:<slug>#<id>` — `path` = путь плана, `status` = поле `status` задачи как есть (`done`, `pending`, …);
   - ребро `in_plan`: `task:<slug>#<id>` → `plan:<slug>`, `via` = `plan-line`;
   - `time` = `null` у всех. Находок адаптер `plans` в 1.3a не даёт.
5. **Ребро `done_by` и находки `DONE_*` — не здесь, а в 1.3b.** Причина: `done_by` ведёт в узел `commit:<полный SHA>`,
   а строка DONE несёт короткий хеш (332 строки, 8–9 знаков) — разрешение хешей и узлы коммитов делает адаптер
   `commits`; `COMMIT_WITHOUT_DONE` без коммитов не посчитать.
6. **Адаптер `modules` читает `modules.yaml` из дерева сборки** (`ctx.tree.read`), не с диска. Для этого
   `scripts/atlas/modules.py` получает `parse_modules(text: str, name: str = "modules.yaml") -> list[dict]` с той же
   проверкой и теми же текстами, что сейчас в `load_modules` (`name` — префикс сообщения вместо `file.name`);
   `load_modules` зовёт её (поведение и 30 тестов 0.3 — без изменений). Публичная функция адаптера
   `modules_for(tree) -> list[dict]` — для 1.3b (`touches`) и 1.4 (`covers`). Узел `module:<id>`, `path` =
   `modules.yaml`, `status` = `null`, `time` = `null`; рёбер и находок нет (`depends_on` — AST, не 1.3a).
   Нет `modules.yaml` в дереве — пустой выход (старые ревизии в `check`). Невалидный файл — exit 2, текст
   `ValueError` из `parse_modules` (в нём ключ и индекс строки, значения нет).
7. **Пути вне модулей остаются `other`.** Решение по 2443 путям из итога 0.3: новых строк в `modules.yaml` не
   заводим, пока нет потребителя, которому `other` мешает (первый кандидат — `touches` в 1.3b, число там).
8. **Ошибки — exit 2 через `AtlasError`, без входных значений в тексте:**
   `atlas: plans_progress --json failed (exit <N>)` (N — код процесса); невалидный JSON на stdout — тот же текст с
   `exit 0`; два плана с одним slug — `atlas: two plans share one slug — rename one plan`; два одинаковых id задачи
   в плане — `atlas: duplicate task id in one plan`.
9. **Регистрация:** `ADAPTERS = (ModulesAdapter(), PlansAdapter())`, у обоих `version = 1`, имена `modules`,
   `plans`. Тесты ядра 1.2 подменяют `ADAPTERS` и не меняются.

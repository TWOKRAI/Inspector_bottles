# Ф5 — Дробление `inspector.classic` и перенос срезов в `Services` (по нужде)

Часть плана [`plan.md`](plan.md). Ветка `feat/gui-constructor-f5-<срез>` — по ветке на срез. **Фаза не
исполняется целиком**: каждая задача стартует, когда её тянет конкретная потребность (роль оператора/наладчика,
третий потребитель, инвентарь). Порядок из решения владельца: «по инвентарю T3.0, не по оценке».

**Вход:** инвентарь T3.0 frontend-constructor (`plans/frontend-constructor/promotion-inventory.md`, владелец —
frontend-constructor; числа до него не называть: `multiprocess_prototype/frontend` — 46 594 строки без тестов,
сверено CTO, сколько из них общее — неизвестно).

**Два правила, которые здесь сталкиваются (находка CTO f):**
- **Строить — по двум потребителям.** Механизм уходит во фреймворк, когда он нужен двум (инспекция и `sim.*`, или
  инспекция и `examples/*`). Нужное одной инспекции остаётся в прототипе.
- **Не резать — по нулю.** «Не используется ≠ не нужно» (память владельца `feedback_unused_paths_are_contracts`,
  07-13; rework 4.5). Правило двух потребителей **не даёт права** удалять существующий путь, у которого сегодня ноль
  вызывающих: Gen-1 `frontend_module` заморожен как LEGACY (`STATUS.md`), а не удалён этим планом. Удаление Gen-1 —
  отдельное решение rework (ступень 3.0, Р-6, с записью исключения), не следствие этого плана.

Канон запуска каждой задачи — шапка [`phase-1-boot-split.md`](phase-1-boot-split.md).

### Task 5.1 — Дробление `inspector.classic`: камера, результаты, управление

- **Статус:** [PENDING — по нужде] · **Level:** Senior · **Assignee:** teamlead
- **Handoff:** tester (RED, worktree) → teamlead → reviewer
- **Условие старта:** нужна раскладка, в которой части `classic` стоят в разных доках/окнах (например, наладчику —
  камера в отдельном окне, оператору — запертая камера + результаты). Без такой раскладки не начинать.
- **Goal:** из `classic` выделяются `inspector.camera`, `inspector.results`, `inspector.control` на чистом контексте
  (без `legacy_deps`); раскладки по ролям используют их.
- **Acceptance (черновик, уточняется при постановке):** sunset-тест `legacy_deps` меняет литерал 1 → 0 отдельным
  коммитом **или** остаётся 1 с записью, какие вкладки ещё держат легаси-дверь; раскладка оператора по умолчанию —
  камера заперта (тест замка 2.1 на этом доке); набор вкладок/функций — не меньше, чем до задачи.
- **Module contract:** impl-only. **Dependencies:** Ф2; T3.0 — для списка вкладок.

### Task 5.2 — Перенос прикладных срезов прототипа в `Services/<svc>/gui/` (по срезу на PR)

- **Статус:** [PENDING — по нужде] · **Level:** Senior · **Assignee:** teamlead
- **Условие старта:** срез нужен второму приложению (симулятор, `minimal_gui`, будущий потребитель из другой сферы)
  **или** инвентарь T3.0 классифицировал его как сервисный. Кандидаты по записи владельца: `recipe`, `auth`,
  устройства. Каждый — свой PR, свой tester.
- **Goal:** срез = бэкенд-часть (уже в `Services/<svc>` или на хабе) + клиентский порт + пакет виджетов
  `Services/<svc>/gui/`; пакет инспектора перестаёт держать его вкладку.
- **Acceptance (черновик):** контракт-тест 1.0 зелёный (Qt только в `gui/`); `sentrux check .` зелёный; вкладка
  доступна и в `apps/gui_client`, и во встроенном GUI; hot-reload пакета — префикс `Services.<svc>.gui.` в зоне чистки.
- **Module contract:** new-full на каждый новый `gui/`. **Dependencies:** Ф2, Ф3 (3.2 — шина, если срез публикует
  события); T3.0.

### Task 5.3 — Qt Advanced Docking System — только если понадобится

- **Статус:** [DEFERRED] · **Level:** Senior · **Assignee:** teamlead
- **Условие старта:** доказанная потребность перетаскивать доки **мышью между** главными окнами (пункт «Переместить
  в окно…» из 2.1 не устраивает владельца).
- **Goal:** проверка лицензии, колёс `PySide6QtAds` под PySide6 6.10 / aarch64 (Orin NX), замены `QDockWidget` за
  интерфейсом оболочки без правки виджетов.
- **Module contract:** impl-only. **Dependencies:** 2.1.

### Связь с frontend-constructor Ф3 (промоушен кита)

Промоушен генерик-кода (`GuiStateBindings`, `RequestRunner`, `QtEventBus`, `TabFactory`, forms, примитивы) остаётся
в frontend-constructor Ф3 (Блок В, после окна codemod). По мере промоушена хуки `multiprocess_prototype/frontend/boot/*`
тоньшают (`design-boot.md` §2) — это не задачи этого плана, но их эффект мерится здесь: `wc -l` хуков пакета
инспектора до/после каждого промоушен-PR.

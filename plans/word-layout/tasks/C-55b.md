**Что может нести health API.** `HealthState` — один на процесс (`health/state.py:148`): `status` ∈
`ok | degraded | failed` (`HealthStatus(str, Enum)`, `schema.py:37-42`) и одна строка `degraded_reason`; при записи
побеждает последний (`state.py:404-422`); `report_error` пишет запись в плоскость ошибок и растит счётчики. Уровней
error / warning / info и сообщения на каждую находку health не несёт. Поэтому: error → `report_error` +
`degraded(reason)` + регистр `last_error`; warning / info → `ctx.log_warning` / `ctx.log_info`
(`plugins/interfaces.py:277-285`).

**Где видно оператору.** Регистр `last_error` — в инспекторе плагина GUI. `health.status` GUI сейчас не показывает:
панель «Здоровье системы» выводит total / active / broken_wires / avg_fps (`processes/presenter.py:191-207`).

## DESIGN

### Б-реестр — `Services/ml_inference/core/registry.py`

1. **Типы.** `ModelDiagnosis` — `@dataclass(frozen=True)`: `severity: Literal["error", "warning", "info"]`,
   `message: str`, `path: Path | None`, `spec: ModelSpec | None = None`. `ModelAssetError(RuntimeError)` — тип
   инцидента для `report_error` (Б4).
2. **Общий выбор весов и разбор.** `_weight_files(self) -> dict[str, Path]` — один проход
   `sorted(self._dir.iterdir())` с тем же фильтром, что сейчас в `scan()` (`registry.py:56-58`: файл,
   `suffix.lower() in _WEIGHT_SUFFIXES`), по стему побеждает **последний** в порядке `sorted` — ровно нынешнее
   поведение `scan()` (r2: при `m1.onnx` + `m1.pth` выбирается `m1.pth`). `_load_one(self, weights: Path) ->
   ModelSpec`: sidecar `weights.with_suffix(".yaml")` (нет → `FileNotFoundError`), затем `_load_spec` (`:88`).
   `scan()` переписать на `_weight_files()` + `_load_one` без смены поведения (битые записи — тот же warning и пропуск).
3. **`diagnose(self, model_id: str) -> ModelDiagnosis`** — один id, без кэша `_specs`, без побочных эффектов.
   Порядок проверок (`D` = `self._dir`):
   1. `model_id == ""` → warning «модель не выбрана — pass-through до выбора в GUI», `path = D`.
   2. `model_id` не проходит `re.fullmatch(r"\w(?:[\w.\- ]*\w)?", model_id)` или содержит `..` → error «недопустимый id
      модели: разрешены буквы, цифры, `_`, `.`, `-`, пробел; без `..`», `path = None`. **Сырое значение в текст не
      идёт** (оно уходит в `last_error` и `degraded_reason`). Шаблон — тот же, что `_NAME_RE` для имён рецептов
      (`multiprocess_framework/modules/recipe/service.py:142`; докстринг `:24` пишет короче — `\w[\w.\- ]*`, исполняется
      `:142`). Копия литерала с комментарием-ссылкой: `modules/recipe` — запретный путь, его приватное имя не
      импортировать. Отсекает `../m1`, `a/b`, `a\b`, `C:m1` (на Windows `Path("C:m1")` уходит из песочницы),
      `m\n1`. Все id в рецептах (`mobilenet_v3_large_20260616_050828`, `…_20260615_112355`) и в `data/models`
      (`smoke_manual12`) шаблон проходят.
   3. `D` не каталог → error «каталог моделей не найден: <D>», `path = D`.
   4. `w = self._weight_files().get(model_id)`; `None` → error «нет весов модели (<id> + один из .onnx|.pt|.pth) в
      <D>», `path = D / model_id`. Суффиксы в тексте — из `_WEIGHT_SUFFIXES`, кортеж нигде не копируется.
   5. Sidecar `w.with_suffix(".yaml")` нет → error «нет sidecar», `path` — этот файл.
   6. `_load_one(w)` бросил → error «sidecar не читается: <ИмяТипаИсключения>», `path` — sidecar. **`str(exc)` в
      текст не идёт** (у pydantic это многострочный текст с вводом).
   7. `spec.weights_path` не файл (`weights:` в sidecar перенаправил) → error «файл весов из sidecar не найден»,
      `path = spec.weights_path`.
   8. `spec.labels_path` задан и `spec.load_labels() is None` (файла нет, он пуст или только пробелы —
      `model_spec.py:74-80`) → error «файл меток из sidecar отсутствует или пуст», `path = spec.labels_path`.
      **Это сознательное сужение:** сегодня такая модель грузится и подписывает классы `class_<id>`; после C-55b —
      error, health `degraded`, pass-through. Причина: в тракте робота метка `class_3` вместо буквы кладёт диск не в
      ту ячейку молча. Записать в README (п. 7).
   9. Иначе → info «модель '<id>': <spec.weights_path.name>, backend <spec.backend>», `path = spec.weights_path`,
      `spec = spec`.

### Б-плагин — `Services/ml_inference/plugin/plugin.py`

4. **`_load_selected_model` (`:264-286`).** Сначала `d = self._engine.registry.diagnose(self._reg.model)` (публичное
   свойство `engine.py:54`), под тем же `_engine_lock`. Сброс телеметрии в начале метода — как сейчас.
   - **warning** (модель пуста): `unload()`, `loaded_model = ""`, `ctx.log_warning(d.message)`, снять свою
     деградацию (Б5). Деградацию не ставит.
   - **error**: `unload()` (pass-through), `loaded_model = ""`, `last_error = d.message`,
     `self._asset_reason = f"ml_inference: {d.message}"`, `ctx.health.report_error(ModelAssetError(d.message),
     context="ml_inference.model")`, `ctx.health.degraded(self._asset_reason)`, `self._asset_degraded = True`.
     Исключение наружу не уходит: `configure` и команды не падают, старт не блокируется.
   - **info**: `load_model(...)`, как сейчас. Успех → `ctx.log_info(d.message)`, снять свою деградацию. Исключение
     загрузки → ветка error с текстом «не удалось загрузить '<id>': <ИмяТипа>»; в регистр `last_error` — `str(exc)`,
     как сейчас (это не pydantic, текст onnxruntime оператору полезен).
   - **Один коннектор на точку** (`modules/tests/test_one_connector_per_point.py`, корни сканирования включают
     `Services`): нынешний `self._ctx.log_error(...)` в `except` (`:286`) заменяется на `report_error`; `log_error`
     и `report_error` в одной ветке не стоят.
5. **Снять свою деградацию.** `self._asset_degraded = False`, `self._asset_reason = ""` — в `configure` до
   `_load_selected_model`. Снятие: если `self._asset_degraded` и `ctx.health.status == "degraded"` (сравнение
   строкой: `HealthStatus` — `str`-Enum) → `ctx.health.set_status("ok")`; флаг `False`. `HealthStatus` в плагин не
   импортировать: `set_status` есть в протоколе `IHealthReporter` (`state.py:135`), Enum мимо фасада не нужен.
   Чужую деградацию плагин не снимает, пока сам её не ставил (ограничение — «Открыто», п. 1).
5а. **Повторная постановка деградации — временный обход C-66** (полоса Ф, связан с планом 14а: breaker забирает
   владение `DEGRADED`, `state.py:396-402`). Стадия 0 r2 воспроизвела: 5-й `report_error` открывает breaker, он
   становится владельцем `DEGRADED`; закрытие через ~60 с → `ok(None)`; `record_success` в `recog` не зовётся, и
   деградация из-за ассетов снимается сама. Правка: в начале `_publish_state` (`:316`; зовётся из `process` не чаще
   раза в секунду, `:152-157`) — если `self._asset_degraded` и `ctx.health.status == "ok"` (не понижать `failed`; ревью стадии 5) →
   `ctx.health.degraded(self._asset_reason)`. Над строкой — комментарий
   `# Обход C-66: breaker снимает чужую деградацию при закрытии; снять после исправления владения degraded в health`.
6. Порядок `configure` (`:111-134`) и итоговая строка `log_info` — без изменений.

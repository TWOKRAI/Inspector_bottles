**Что может нести health API (ответ на вопрос лида).** `HealthState` — **один на процесс**
(`health/state.py:148`, `get_or_create_health_state`): `status` ∈ `ok | degraded | failed` (`schema.py:37-42`) и
одна строка `degraded_reason`; `set_status` — «последний пишущий выигрывает» (`state.py:404-422`); счётчик `errors`
и `last_error` (тип, сообщение, контекст, время) растут от `report_error`, она же пишет запись в плоскость ошибок
(`errors.log`). **Уровней error / warning / info и сообщения на каждую находку health не несёт.** Поэтому:
error → `report_error` + `degraded(reason)` + регистр `last_error`; warning / info → `ctx.log_warning` /

`presenter.py:191-207`) выводит total / active / broken_wires / avg_fps. Показ статуса — забота задачи готовности,
не C-55b (см. «Открыто»).

## Решение (DESIGN)

### Б-реестр — `Services/ml_inference/core/registry.py`

1. **`ModelDiagnosis`** — `@dataclass(frozen=True)`: `severity: Literal["error", "warning", "info"]`, `message: str`,
   `path: Path | None`, `spec: ModelSpec | None = None`. **`ModelAssetError(RuntimeError)`** — тип инцидента для
   `report_error` (п. Б3).
2. **`_load_one(self, weights: Path) -> ModelSpec`** — общий шаг для `scan()` и `diagnose()`: sidecar
   `weights.with_suffix(".yaml")` (нет → `FileNotFoundError`), затем `_load_spec(weights, sidecar)` (`registry.py:88`).
   `scan()` (`:45-70`) переписать на `_load_one` без смены поведения: битые записи пропускаются с тем же warning.
3. **`diagnose(self, model_id: str) -> ModelDiagnosis`** — один id, без кэша `_specs`, без побочных эффектов.
   Порядок проверок и ответ (`D` = `self._dir`):
   1. `model_id == ""` → warning «модель не выбрана — pass-through до выбора в GUI», `path = D`.
   2. В `model_id` есть `/`, `\` или `..`, либо `Path(model_id).is_absolute()` → error «недопустимый id модели:
      '<id>'», `path = None`.
   3. `D` не каталог → error «каталог моделей не найден: <D>», `path = D`.
   4. Веса — первый существующий `D / f"{model_id}{s}"` для `s` из `_WEIGHT_SUFFIXES` (`registry.py:22`, порядок
      `.onnx`, `.pt`, `.pth`); нет ни одного → error «нет весов модели '<id>' (<id> + один из .onnx|.pt|.pth) в <D>»,
      `path = D / model_id`. Суффиксы в тексте собираются из `_WEIGHT_SUFFIXES`, кортеж нигде не копируется.
   5. Sidecar `D / f"{model_id}.yaml"` нет → error «нет sidecar <id>.yaml», `path` — этот файл.
   6. `_load_one` бросил → error «sidecar <id>.yaml не читается: <ИмяТипаИсключения>», `path` — sidecar.
      **`str(exc)` в текст не идёт** (у pydantic это многострочная простыня с вводом).
   7. `spec.weights_path` не файл (ключ `weights:` в sidecar перенаправил) → error «файл весов из sidecar не найден:
      <путь>», `path = spec.weights_path`.
   8. `spec.labels_path` задан и не файл → error «файл меток из sidecar не найден: <путь>», `path = spec.labels_path`.
   9. Иначе → info «модель '<id>': <spec.weights_path.name>, backend <spec.backend>», `path = spec.weights_path`,
      `spec = spec`.

### Б-плагин — `Services/ml_inference/plugin/plugin.py`, `_load_selected_model` (`:264-286`)

4. Сначала `d = self._engine.registry.diagnose(self._reg.model)` (публичное свойство `engine.py:54`), под тем же
   `_engine_lock`. Сброс телеметрии в начале метода — как сейчас.
   - **warning** (модель пуста): `unload()`, `loaded_model = ""`, `ctx.log_warning(d.message)`, снять свою деградацию
     (ниже).
   - **error**: `unload()` (pass-through, как сейчас при отказе), `loaded_model = ""`, `last_error = d.message`,
     `ctx.health.report_error(ModelAssetError(d.message), context="ml_inference.model")`,
     `ctx.health.degraded(f"ml_inference: {d.message}")`, `self._asset_degraded = True`. Без исключения наружу:
     `configure` и команды не падают — старт не блокируется.
   - **info**: `load_model(...)`, как сейчас. Успех → `ctx.log_info(d.message)` и снять свою деградацию. Исключение
     загрузки → та же ветка error, текст «не удалось загрузить '<id>': <ИмяТипа>»; в регистр `last_error` —
     `str(exc)`, как сейчас (это не pydantic, текст onnxruntime оператору полезен).
   - **Один коннектор на точку** (`modules/tests/test_one_connector_per_point.py`, корни сканирования включают
     `Services`): нынешний `self._ctx.log_error(...)` в `except` (`:286`) заменяется на `report_error`; `log_error`
     и `report_error` в одной ветке не стоят.
5. **Снять свою деградацию:** `self._asset_degraded` ставится только веткой error (атрибут создаётся в `configure`,
   `False`). Снятие — если `self._asset_degraded` и `ctx.health.status == HealthStatus.DEGRADED` →
   `ctx.health.ok()`, флаг `False`. Чужую деградацию плагин не снимает, пока сам её не ставил. Ограничение
   API — в «Открыто», п. 1.
6. Порядок `configure` (`:111-134`) и итоговая строка `log_info` — без изменений.

## Открыто

1. **Health — на процесс, не на плагин.** Причина одна, «последний пишущий выигрывает»; два плагина одного процесса
   затирают причины друг друга; `HealthReporter` не отдаёт текущую причину, поэтому п. Б5 сверяет только `status`:
   если после нашей деградации сосед выставил свою, наше восстановление снимет и её. Будущему гейту готовности,
   вероятно, нужен источник по плагину — вопрос той задачи.
2. Строка для `plans/queue/defects.md` (opus №7, полоса Ф): «**Провода остаются `broken` после отказанного

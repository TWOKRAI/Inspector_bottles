## Что было (стенд 2026-10-27, отчёт `docs/reports/2026-10-27_word-layout_C-5x.md` → «Живой стенд»)

`venv_guard` (`run.py:120-161`) при чужом интерпретаторе вызывает `os.execv` (`run.py:159`). На POSIX `execv`
подменяет процесс: PID, код выхода и сигналы остаются за приложением. На Windows CPython эмулирует `execv`:
запускает новый процесс и **сразу завершает текущий с кодом 0**. Наблюдение: `machine_gate.sh heavy … run.py
letter_robot_sim --headless` из worktree завершился с exit 0 через ~2 с; бэкенд жил ещё 96 с, пока его не
погасил `system_shutdown`. Гейт, TaskStop и любой скрипт, который ждёт код выхода, теряют процесс.

Решение владельца (2026-10-27): C-55a влита как есть, C-70 чинится отдельной задачей полосы С.

## DESIGN

1. Шов `execv` в `venv_guard`, `run.launch`, `frontend/run.launch` заменяется швом
   `relaunch: Callable[[str, list[str]], int]` (тип — в сигнатуре; синтаксис `type X = …` шапка `run.py`
   запрещает). Смысл: «перезапусти `argv` интерпретатором `exe`, верни код выхода приложения». Имя `execv`
   уходит целиком, без псевдонима: тип возврата меняется с «не возвращается» на `int`, `TypeError` заставит
   мигрировать явно. Внешних вызывающих `venv_guard` нет.
2. Значение по умолчанию — публичная `run.default_relaunch(exe: str, argv: list[str]) -> int`:
   - `os.name != "nt"`: `os.execv(exe, argv)` — как сейчас, не возвращается (`# nosec B606` переезжает сюда).
   - `os.name == "nt"`: `proc = subprocess.Popen(argv, executable=exe)` (через атрибут модуля
     `subprocess.Popen`, чтобы тест мог подменить; `executable=exe` — иначе при `argv[0] != exe` Windows даёт
     `FileNotFoundError`; `# nosec B603`). stdin/stdout/stderr и окружение наследуются. `OSError` не ловить.
   - Ожидание: `while True: try: rc = proc.wait(); break / except KeyboardInterrupt: continue`. Причина (замер
     стадии 0): на Windows `Popen.wait()` сигналом не прерывается, `KeyboardInterrupt` от Ctrl+C приходит
     **после** выхода ребёнка (оба процесса одной консоли получают Ctrl+C, приложение гасит себя само). Без
     цикла вместо кода ребёнка вылетел бы traceback. Ребёнка родитель не убивает и не трогает.
   - Код выхода: `Popen.returncode` на Windows беззнаковый (`0xC0000005` → `3221225477`), а `sys.exit` с
     таким числом на 3.11/3.12 даёт `4294967295`. Вернуть знаковое:
     `rc - (1 << 32) if rc >= (1 << 31) else rc`.
   - Почему не `subprocess.run`: при `KeyboardInterrupt` он делает `process.kill()`. Почему не `SystemExit`
     внутри `default_relaunch`: в потоке он молча завершает поток, значение до вызывающего не доходит.
3. `venv_guard` при перезапуске возвращает `relaunch(...)` как есть. Контракт: `None` — интерпретатор уже
   нужный, продолжать запуск; любое `int`, в том числе `0`, — завершить вход с этим кодом. Обновить докстринг
   `venv_guard`, шапку модуля (п.3 «re-exec», п.4 «без subprocess») и комментарий `# nosec B404`.
4. `frontend/run.py` берёт `default_relaunch` из `run.py` (одна реализация, как guard в C-55a).
5. Сообщения C-55a («переключаюсь на …», ошибки venv) не меняются.
6. Видимое поведение: запуск чужим python на Windows теперь держит консоль до выхода приложения (раньше
   отпускал через ~2 с). Так ведёт себя POSIX; это и есть цель.

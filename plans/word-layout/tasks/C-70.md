## Что было (стенд 2026-10-27, отчёт `docs/reports/2026-10-27_word-layout_C-5x.md` → «Живой стенд»)

`venv_guard` (`run.py:120-161`) при чужом интерпретаторе вызывает `os.execv` (`run.py:159`). На POSIX `execv`
подменяет процесс: PID, код выхода и сигналы остаются за приложением. На Windows CPython эмулирует `execv`:
запускает новый процесс и **сразу завершает текущий с кодом 0**. Наблюдение: `machine_gate.sh heavy … run.py
letter_robot_sim --headless` из worktree завершился с exit 0 через ~2 с; бэкенд жил ещё 96 с, пока его не
погасил `system_shutdown`. Последствия: гейт, TaskStop и любой скрипт, который ждёт код выхода, теряют процесс;
настоящий код выхода приложения не доходит до вызывающего.

Решение владельца (2026-10-27): C-55a влита как есть, C-70 чинится отдельной задачей полосы С.

## DESIGN

1. Шов `execv` в `venv_guard`, `run.launch`, `frontend/run.launch` заменяется швом
   `relaunch: Callable[[str, list[str]], int]` — «перезапусти `argv` интерпретатором `exe` и верни код выхода
   приложения». Имя `execv` больше не описывает поведение, поэтому оно уходит целиком (без псевдонима).
2. Значение по умолчанию — новая публичная функция `run.default_relaunch(exe: str, argv: list[str]) -> int`:
   - `os.name != "nt"`: `os.execv(exe, argv)` — как сейчас, не возвращается;
   - `os.name == "nt"`: `subprocess.Popen(argv)` с унаследованными stdin/stdout/stderr и окружением;
     ждать `proc.wait()`; вернуть `proc.returncode`.
   - Ctrl+C на Windows получают оба процесса одной консоли. `KeyboardInterrupt` во время ожидания родитель
     **не** превращает в выход: продолжает `wait()`, пока ребёнок не закончит сам, и возвращает его код.
     Ребёнка родитель не убивает — остановка остаётся за приложением.
3. `venv_guard` при перезапуске возвращает `int(relaunch(...))`. Контракт возврата: `None` — интерпретатор уже
   нужный, продолжать запуск; любое `int` (в том числе `0`) — завершить вход с этим кодом. Докстринг обновить.
4. `frontend/run.py` берёт `default_relaunch` из `run.py` (одна реализация, как guard в C-55a).
5. Сообщение «переключаюсь на …» и все сообщения C-55a не меняются.

## ACCEPTANCE

- **A1.** Worktree без своего `.venv`, `.venv` основной копии есть, интерпретатор чужой.
  `run.launch(project_root=…, common_dir_of=…, relaunch=fake)`; `fake` возвращает `7`.
  → `fake` вызван ровно 1 раз с `(venv_py, [venv_py, <абсолютный путь run.py>, *sys.argv[1:]])`;
  `launch` вернул ровно `7`.
- **A2.** То же, `fake` возвращает `0` → `launch` вернул `0`, а **не** продолжил запуск: приложение не
  стартовало (`multiprocess_prototype.main` не импортирован этим вызовом).
- **A3.** `frontend/run.launch(..., relaunch=fake)`, `fake` возвращает `5` → вернул `5`; в `os.environ` нет
  `INSPECTOR_PRESENTATION`, выставленного этим вызовом.
- **A4 (только Windows, настоящий процесс).** `run.default_relaunch(sys.executable, [sys.executable, script])`,
  где `script` спит 0.5 с, пишет файл-метку и выходит с кодом `3`. → вернул `3`; к моменту возврата метка
  существует (вызывающий дождался ребёнка). Вызов — в daemon-потоке с дедлайном join 20 с.
  На POSIX тест не собирается (платформенный), это записать в отчёт: POSIX-ветка `execv` стендом не
  проверяется, на этой машине её нет.
- **A5.** Сообщения C-55a не изменились: тесты `test_run_launcher_c55.py` после переименования зелёные.

Хазард автора (стадия 2): **H1** — `KeyboardInterrupt` во время ожидания не обрывает ожидание: функция
возвращает код ребёнка, ребёнок не убит. Ребёнок настоящий, `KeyboardInterrupt` подаётся в `wait()` через шов
или через `_thread.interrupt_main` — на выбор автора, вызов в daemon-потоке с дедлайном.

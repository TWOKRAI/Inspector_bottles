## Допущения (в ACCEPTANCE нет)

1. Интерпретатор лаунчера и цепочки — один и тот же `PY` (переходник `.venv` основной копии); лаунчер не «системный python».
   Если лаунчер на настоящем стенде идёт под другим python, поведение переходников то же, но путь не идентичен.
   Если `PY` нет на диске — `pytest.skip`.
2. Режимы `child.py`: `sleep` (J1/J2), `first` (J1b: `Popen` grandchild первым действием после импортов), `exit3` (J3).
3. «Потомок» в J1b и J3 = и `grandchild`, и его переходник (`redir_gc`): оба в одном job, строже спеки (только grandchild); J2b — оба по спеке.
4. J3: «жив до события» не утверждается (child выходит сразу после `gc.json`, после правки потомок может умереть раньше,
   чем тест откроет handle). Дедлайн метки `rc` в J3 — 15 с (старт лаунчера в уже поднятой цепочке), потомки мертвы ≤5 с после метки.
5. Подъём цепочки — дедлайн 30 с; метка `rc` в J2a — 5 с.
6. `taskkill` проверяется только по `returncode == 0`; текст вывода не разбирается.
7. Живость: handle открыт с `SYNCHRONIZE | QUERY_LIMITED | TERMINATE` (TERMINATE — для зачистки).
8. Потоков с join-дедлайном нет: все ожидания — ограниченный опрос, `taskkill` с `timeout=20`, stdout лаунчера в файл (не pipe).

## Что я оставил открытым / ненадёжным

- **Гонка открытия handle (J3).** handle процесса, умершего до открытия, не открыть -> он считается мёртвым.
  Если бы PID освободился и был занят чужим процессом, J3 мог бы дать ложный «мёртв»/«жив». Практически мала
  (Windows не переиспользует PID мгновенно), но защиты по времени создания в тесте нет.
- **Зачистка по меткам при раннем падении.** Если тест упал до `open_handles`, `cleanup` открывает handles по PID из меток
  уже в teardown: для уже умершего и переиспользованного PID может задеть чужой процесс. Время создания не сверяется.
- **Время.** Тесты берут 4–8 с каждый (три запуска python на цепочку); на загруженной машине подъём цепочки (30 с) может не уложиться -> падение «цепочка не поднялась», а не ложный зелёный.
- **Переходник на других машинах.** Предполагается, что `.venv\Scripts\python.exe` — настоящий переходник (родитель ребёнка).
  Если переходника нет (`ppid` ребёнка = лаунчер), проверка «пять PID различны» упадёт с ясным сообщением (не проверено: на этой машине переходник есть).
- **Зелёное состояние не наблюдалось** (кода правки нет): доказательство достижимости — только копия с `/T`
  (убивает дерево штатно, а не через Job Object); J2b/J3 зелёными не прогонялись.
- **J1b** по исходу совпадает с J1 (как сказано в брифе); порядок «до старта» отличает только HR5 автора.
- Каталог `scratchpad` содержит мои разовые скрипты (`leftovers_c76t.py`, `kill_c76t.py`, `sanity/test_sanity_c76.py`); в проект не входят.
- Проверка «после прогона живых нет» сделана по меткам последнего прогона, не по всему списку процессов (общий список процессов командой не смотрел: PowerShell/CIM был отклонён классификатором).

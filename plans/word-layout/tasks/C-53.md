## Решение (DESIGN)

### Часть А — C-53 (`process_module/__init__.py`)

- **А1.** Строки 118, 122, 126: `from ...process_manager_module.topology.blueprint import …` →
  `from ..process_manager_module.topology.blueprint import …`. Ленивость сохранить (импорт внутри
  `__getattr__`): `process_module` — ярус ниже `process_manager_module`
  (`process_module/configs/observability_layers.py:100`: «`process_module` ниже `process_manager_module`»),
  на уровне модуля такой импорт дал бы цикл импорта.
- **А2.** Над тремя ветками — одна строка комментария: реэкспорт вверх по ярусу, оставлен ради контракта
  `__all__` (C-53, FREEZE); канонический дом — `process_manager_module.topology.blueprint`.
- **А3.** Остальные 19 ленивых веток и 13 eager-импортов не трогать. `__all__` не менять.
- **А4** (решение владельца 2026-10-27: «везде одинаково во всех модулях, правильно, без костылей»).
  `router_module/interfaces.py:16`: `from ...message_module import Message` → `from ..message_module import Message`.
  Строка под `TYPE_CHECKING`, в рантайме не исполняется; для pyright путь сейчас ведёт в несуществующий пакет.
  Правка — одна точка, тот же класс дефекта.
- **А5** (то же решение владельца). Страж `multiprocess_framework/modules/tests/test_relative_imports_c53.py`:
  обходит **все** `multiprocess_framework/modules/**/*.py`, включая `tests/` и `TYPE_CHECKING`-блоки, через `ast`
  (без импорта модулей). Для каждого `ImportFrom` с `level > 0` вычисляет пакет-цель (пакет файла; для
  `__init__.py` — сам пакет; подняться на `level - 1`; дописать `module`, если он есть) и требует, чтобы цель
  начиналась с `multiprocess_framework.modules`. **Без allowlist и исключений** — ни по файлу, ни по строке.
  Файл, который `ast` не разбирает, — тоже падение (страж не пропускает молча). Сообщение падения — список
  `путь:строка -> цель`. Сейчас ловит ровно 5 строк в 3 файлах (замер менеджера, 2296 относительных импортов):
  `process_module/__init__.py:118, 122, 126`, `router_module/interfaces.py:16`,
  `shared_resources_module/adapters/data_schema_adapter.py:29`. `from .. import X` в
  `frontend_module/schema_adapter.py:23` — цель `multiprocess_framework.modules`, законно, правилу удовлетворяет.
  Корень обхода — от `Path(__file__)` стража (`parents[1]` = `modules/`), не от cwd.
- **А6. `Services/` и `Plugins/` — замер, не правка.** Тот же скан (2026-10-27): `Services/` — 122 относительных
  импорта, `Plugins/` — 170 (сверено `git grep -c "^\s*from \.+"`: 292 в 166 файлах); выход за свой верхний пакет
  (`Services`, `Plugins`) — **0**. Расширять страж на эти слои или нет, решает лид; в этой задаче страж покрывает
  только `multiprocess_framework/modules/**`.

### Часть Б — C-54 (`shared_resources_module/adapters/data_schema_adapter.py`)

- **Б1.** Строка 29: `from ....data_schema_module.storage.storage_manager import StorageManager` →
  `from ...data_schema_module.storage.storage_manager import StorageManager`. Импорт оставить внутри метода
  (ленивым): `data_schema_module/storage/storage_manager.py:22` под `TYPE_CHECKING` импортирует
  `shared_resources_module.core.shared_resources_manager`; импорт на уровне модуля адаптера связал бы
  `shared_resources_module/__init__` (он импортирует адаптер на `:30`) с `data_schema_module` в момент загрузки —
  лишний риск цикла без выгоды (урок `feedback_lazy_import_for_layer0_data_schema_files.md`).
- **Б2. `ImportError` не глотать — убрать `try` / `except ImportError: return None` целиком, без лога.**
  Причины:
  - `data_schema_module` — ярус `core` (`multiprocess_framework/docs/MODULE_TIERS.md:33`), он есть в каждой
    установке. `ImportError` здесь значит одно: сломан путь или установка. Ровно эта ошибка пролежала полгода
    молча.
  - Лог + повторный `raise` даёт ту же трассировку дважды: вызывающих нет, читать вторую строку некому.
    Исключение само несёт путь импорта.
  - Исключения конструктора `StorageManager` уже сейчас проходят наружу — поведение становится единым.
- **Б3.** Ребро `shared_resources_module → data_schema_module` разрешено: оба `multiprocess_framework/*`,
  в `.sentrux/rules.toml` между модулями framework `[[boundaries]]` нет (есть только framework → app_module /
  prototype / Services / Plugins / backend_ctl). Ребро уже есть в карте (`docs/maps/framework-core.md:228`,
  1 импорт) и задумано: ленивый импорт стоял с 2026-03. Обратное ребро (`:204`) — `storage_manager.py:22` под
  `TYPE_CHECKING`; правка его не добавляет.
- **Б4. Докстринги** — убрать обещание graceful degradation:
  - модуля (`:6`): «Ленивый импорт: data_schema_module опционален (graceful degradation)» → «Импорт
    `StorageManager` ленивый (при первом вызове); `data_schema_module` — core, ошибка импорта не глотается (C-54)»;
  - класса (`:18`): «Graceful degradation: возвращает None …» → «Ошибка импорта `StorageManager` уходит
    вызывающему как `ImportError`»;
  - `is_available()` — докстринг: «True, если `StorageManager` создан; ошибку импорта не прячет — бросает».
  Аннотации `Optional[Any]` на строках, которые не меняются по смыслу, не трогать (§11: без попутной
  переделки). Сигнатуры не меняются.
- **Б5. README.** `shared_resources_module/README.md:188`: «тонкий мост: `srm.data_manager` → …» неверно —
  `data_manager` у SRM удалён (`DECISIONS.md:11`). Заменить на: «тонкий мост: `DataSchemaAdapter(srm).data_manager`
  → `StorageManager(shared_resources=srm)` из data_schema_module; вызывающих в коде нет (FREEZE, C-54)».
- **Б6.** Адаптер и `StorageManager` не удалять: адаптер — публичный экспорт; `storage_manager` — FREEZE G4
  (`MODULE_TIERS.md:88`).

## DESIGN

1. Только ветка `os.name == "nt"` внутри `default_relaunch`. POSIX-ветка (`os.execv`) и всё после `Popen` — ожидание,
   цикл `KeyboardInterrupt`, знаковый код выхода — **не меняются** (M2, M3, Ctrl+C из C-70).
2. Порядок на `nt` (ctypes импортируется внутри функции — шапка `run.py` разрешает только stdlib на уровне модуля):
   1. `CreateJobObjectW(None, None)`; `SetInformationJobObject(job, JobObjectExtendedLimitInformation=9, …)` с
      `BasicLimitInformation.LimitFlags = JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE (0x2000)`.
   2. `subprocess.Popen(argv, executable=exe, creationflags=CREATE_SUSPENDED (0x4))` — ребёнок создан, но не выполнил
      ни одной инструкции. Именно `subprocess.Popen` через атрибут модуля (тесты C-70 его подменяют).
   3. `AssignProcessToJobObject(job, <handle ребёнка>)`. Handle — `OpenProcess(PROCESS_SET_QUOTA | PROCESS_TERMINATE |
      PROCESS_SUSPEND_RESUME, proc.pid)`, не приватный `proc._handle`.
   4. `NtResumeProcess(handle)` (ntdll) — ребёнок стартует уже внутри job: его потомки (переходник → приложение →
      воркеры) наследуют job с рождения, окна «создал потомка раньше, чем лаунчер положил его в job» нет.
   5. Handle job живёт локальной переменной до выхода из функции и **не наследуется** ребёнком (`close_fds=True`
      по умолчанию — не менять). Смерть лаунчера закрывает handle → ядро убивает всех членов job.
3. Нормальный выход: после `wait()` handle job закрывается явно (`try/finally`) — это убивает **оставшихся** членов job
   (потомков, пережившие главный процесс приложения). Это решение, не побочный эффект: цель — «сирот нет»; после выхода
   приложения живой потомок держал бы порты и камеру. Выносим на проверку стадии 0 и в список решений владельца.
4. Отказ API (политика): сбой на п.2.1 или п.2.3 — предупреждение в stderr (текст со словами «job object» и причиной),
   приложение запускается без защиты (сироты возможны, как до C-76); если ребёнок уже создан приостановленным — его
   **обязательно** возобновляют. Сбой `NtResumeProcess` — ребёнка убить (`proc.kill()`) и пробросить `OSError`:
   вечно приостановленный процесс хуже сироты. Тихо проглатывать нельзя.
5. Размер: ~40 строк в `run.py`. Обновить шапку модуля (п.3 — добавить «Windows: приложение в Job Object») и
   комментарий `# nosec B404`/`B603` при необходимости. `frontend/run.py` берёт `default_relaunch` из `run.py` — не трогаем.
6. Отвергнуто: **самоназначение лаунчера в job** (`AssignProcessToJobObject(job, GetCurrentProcess())` до `Popen`) —
   в тесте лаунчером служит процесс pytest, закрытие handle убило бы сам pytest. **Назначение после `Popen` без
   `CREATE_SUSPENDED`** — остаётся окно, в котором переходник успевает породить потомка вне job.
   **Правка `spawner.py stop()`** — чужая полоса (Ф, T1.11), лечит другой случай (штатная остановка).

## Заглушка замера (для тестера; пишется в `tmp_path` теста)

- `launcher.py`: `sys.path.insert(0, <корень worktree>)`; `import multiprocess_prototype.run as run`;
  пишет в файл-метку свой PID; `rc = run.default_relaunch(PY, [PY, "child.py"])`; пишет `rc` в другой файл-метку.
  `PY` — интерпретатор **`.venv` основной копии** (`…\Inspector_bottles\.venv\Scripts\python.exe`, переходник): без него
  цепочка из трёх процессов не воспроизводится.
- `child.py`: пишет в файл `os.getpid()` и `os.getppid()` (PID переходника), порождает потомка `grandchild.py`
  (спит 120 с, пишет свой PID), сам спит 120 с.
- Тест запускает `launcher.py` как **отдельный процесс** (`subprocess.Popen`), не как поток pytest.
- Живость — `OpenProcess(SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION, False, pid)` + `GetExitCodeProcess == 259`
  (`STILL_ACTIVE`); handle открывается, пока процесс жив (защита от повторного использования PID). `os.kill(pid, 0)`
  не использовать: на Windows он убивает.
- Убийство — `subprocess.run(["taskkill", "/PID", str(pid), "/F"])` **без `/T`** либо `TerminateProcess`.
- Зачистка в `finally`/фикстуре: убить всех известных PID, чтобы упавший тест не оставил сирот. Любое ожидание —
  с дедлайном; тест, который может блокироваться, идёт в daemon-потоке с `join(deadline)`.

## ACCEPTANCE

Все Windows-тесты — с настоящими процессами, помечены `skipif(os.name != "nt")`.

- **J1 (M1, главный).** Цепочка `launcher → переходник → child → grandchild` поднята, все четыре PID записаны и живы.
  Убить лаунчер (`taskkill /PID <launcher> /F`, без `/T`). → в пределах 5 с живых из `{переходник, child, grandchild}`
  ровно **0**, лаунчер мёртв; проверка идёт, пока pytest жив.
- **J1b (потомок с рождения).** `child.py` порождает `grandchild.py` первой строкой. После убийства лаунчера
  `grandchild` мёртв за ≤5 с.
- **J2 (M2, неизменность).** Та же цепочка. Убить **переходник** (`taskkill /PID <переходник> /F`). → child и grandchild
  мертвы ≤5 с (по замеру M2 — ≤2 с); лаунчер жив до этого момента; `launcher.py` записал `rc == 1`.
- **J3 (нормальный выход).** `child.py` порождает `grandchild.py` (спит 120 с) и выходит с кодом `3`. →
  `default_relaunch` вернул ровно `3` (метка `rc`), а `grandchild` мёртв ≤5 с после возврата.
- **J4 (код выхода через job).** Сценарии A4 и A4b из C-70 (`3` и `-1073741819`) проходят без изменений — тесты
  `test_run_relaunch_c70.py` зелёные.
- **J5 (POSIX-ветка).** A7 из C-70 зелёный: при `os.name = "posix"` вызван `os.execv`, `subprocess.Popen` и ctypes
  не трогались.

Хазарды автора (стадия 2; фейки допустимы, seam выбирает автор):
- **HR1.** Сбой создания job → приложение запущено, `rc` дошёл, в stderr предупреждение со словами «job object».
- **HR2.** Сбой `NtResumeProcess` → ребёнок убит (`poll() is not None`), `OSError` проброшен, приостановленных
  процессов нет.
- **HR3.** Сбой назначения в job → ребёнок возобновлён и работает, предупреждение в stderr.
- **HR4.** Handle job не попадает в ребёнка: ребёнок не видит наследуемых handle'ов типа Job (перебор своих handle
  через `NtQueryObject`/`DuplicateHandle` не нужен — достаточно J1: наследование дало бы живых сирот).

Известный пробел (не скрывать): порядок «назначить ДО старта» (`CREATE_SUSPENDED`) исходом не отличим от «назначить сразу
после `Popen`» — переходник стартует за миллисекунды, а назначение занимает микросекунды. J1b красным не станет. Закрыть
детерминированно можно фейком шва в хазарде (проверка, что `Resume` вызван после `Assign`); решение — стадия 0.

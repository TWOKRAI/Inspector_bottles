## Решение о конкурентности

Пишет teamlead (Opus) до разработчика. Раздел не содержит механизма до его записи; разработчик не начинает, пока строка «Решение:» не заполнена.

Требования к решению (пишет teamlead):
  1. **Окно 3,0 с (О8, Ф9).** `plugin.shutdown(ctx)` с двумя роботами в движении (программа у одного, jog у другого) возвращается ≤ 3,0 с; в закрытии корня `device_hub` `survivors == []`. Бюджет корня — 2,5 с. Порядок: (1) стоп-запрос всем драйверам сразу, без ожидания (стоп робота уходит до любых ожиданий); (2) ожидание и закрытие; (3) `self._scope.close(budget_s=2.5)`. Решение называет, где живут фазы (1) и (2) (`DeviceManager.shutdown`, `disconnect`, `_PROGRAM_JOIN_S`) и какие сроки они получают; сроки в сумме с 2,5 с не выходят за 3,0 с.
  2. **Выжившие видны.** Поток, переживший срок, виден в `last_error = "поток драйвера не вышел за срок"`, `tx_err` +1 и `health.report_error(context="device_hub.scope")`. Решение объясняет, как выживший попадает в `health`, если `IHandle.close` уже отцепил его от владельца (`interfaces.py:606-616`) и в отчёт `scope.close()` он не входит.
  3. **Порядок старта поводка (п. 5 вердикта).** `self._jog = run` и `self._last_hold = now` — под `_flags_lock` ДО `spawn`; `run.handle = self._spawn(...)` — под `_jog_tx_lock`. Решение называет шов, в котором тест может остановить поток между `spawn` и записью `handle`.
  4. **`handle is None`.** `jog_release`/`disconnect` при `run.handle is None` идут без `close`, стоп — через `_stop_jog` (ждёт `_jog_tx_lock`).
  5. **`spawn` после ACK (п. 6).** `_stop_jog_locked(run)` под взятым `_jog_tx_lock`; seq стопа — в `_own_stops`; откат `run.active = False`, `self._jog = prev`. Порядок замков: `_jog_tx_lock` не держится на `handle.close` (DESIGN 6).
  6. **Имена потоков (п. 1).** Счётчик `k` один на модуль; безопасен при вызове из двух потоков одновременно; `ValueError` от `spawn` не маскируется под `TEXT_SCOPE_CLOSED`.
  7. **Двойной и аварийный shutdown (п. 7).** Повторный `shutdown()` и `shutdown()` после упавшего `configure()` — без действия, без второго `health.report_error`; `configure()` закрывает корень сам при исключении.
  8. **Шов для теста гонки.** Тестер и автор сторожей не используют барьер на входе метода (он гонку не воспроизводит): решение называет шов транспорта или обёртку `spawn`, через которые строятся рандеву сторожей S1, S6, S7, S8 ниже.

**К1. Фазы остановки и сроки (треб. 1, О8, Ф9).**

Новое в драйвере (`robot_driver_v2.py`, добавления):

- `def _request_stop(self, program_level: int) -> None` — общий код для `request_stop` и `disconnect`:
  1. `with self._jog_tx_lock:` и внутри `with self._flags_lock:` — `self._stopping = True`; `self._stop_level = max(self._stop_level, program_level)`; `run = self._jog`; `stop_jog = run is not None and not run.stop_sent`; при `stop_jog`: `run.released = True`, `run.stop_requested = True`, `run.wake.set()`; `prog_alive = self._prog_alive`; `job_active = self._job_active`. Затем оба замка отпускаются (V1, DESIGN 6: `JOG_CONT` в полёте дописывает `self._jog` до входа; `_stop_jog` снова берёт `_jog_tx_lock`, замок не реентерабельный).
  2. `client = self._client`; `client is None` → выход.
  3. Без замков, по порядку, каждый вызов в своём `try` / `except Exception as exc:` → `self._record_err()` + `logger.warning(f"робот {self.entry.id!r}: стоп <задания|jog|программы> не доставлен: {type(exc).__name__}: {exc}")`, затем следующий вызов: `job_active` → `client.stop(STOP_LEVEL["HARD"])`; `stop_jog` → `self._stop_jog(run)`; `prog_alive` → `client.stop(program_level)`.
- Проверка `self._stopping` — первым условием в существующих секциях `_flags_lock`:
  - `_op_jog_hold`, обе секции → `return {"status": "error", "message": TEXT_STOPPING}`;
  - `_launch`, первая секция → тот же ответ;
  - `_dispatch` (`robot_driver_v2.py:545-552`) → `or self._stopping` в условии выхода (задание не берётся);
  - `_program_loop` — после первой публикации `running`, ДО `run_chunks`: `with self._flags_lock: stopping = self._stopping`; `stopping` → `state["state"] = "aborted"`, `run_chunks` не вызывается, дальше тот же `finally`.
- Микроокно `_program_loop` (р.2 п. 8). `_run_chunks` берёт поколение стопа один раз в начале: `g0 = self._stop_generation` (`client_v2.py:998`), и обрывает прогон по `by_generation()` — `self._stop_generation != g0` (`client_v2.py:1001-1002`, проверки `marked()` перед `SC_RUN` и после ACK, `:1018, :1027`). Стоп, записанный между проверкой `_stopping` в `_program_loop` и строкой `:998`, входит в `g0`, и прогон его не видит: HARD уходит на свободного робота, сценарий стартует. Стоп после `:998` прогон видит сам. `on_progress` зовётся из `on_poll` первого `wait_done` при первом же опросе: `progress["done"]` стартует с `-1` (`client_v2.py:1013, 1033-1040`). Фикс — повтор стопа в `on_progress` `_program_loop` (`robot_driver_v2.py:912-914`), один раз на прогон: локальный `resent = [False]`; в `on_progress` после публикации — `with self._flags_lock: level = self._stop_level if (self._stopping and not resent[0]) else 0; if level: resent[0] = True`; при `level` → `try: self._client.stop(level)` / `except Exception as exc:` → `self._record_err()` + `logger.warning(...)`. Остаток окна — ход от ACK первого `SC_RUN` до первого опроса `wait_done`: загрузка второго куска плюс один `poll_interval_s` (оценка ≤ 0.1 с, не измерено). Уровень берётся из `_stop_level`: обычный `disconnect` повторяет SOFT, фаза 1 — HARD; поведение отключения не меняется.
- `connect()`, начало (вместо прежней секции `job_active`): `with self._flags_lock: shutdown = self._shutdown; job_active = self._job_active`; `shutdown` → `return False` без ввода-вывода. После проверки `job_active or self._activity_alive()` (перед `was_ready = self._ready`): `with self._flags_lock: self._stopping = False; self._stop_level = 0`. Перед `self._ready = True` в конце: `with self._flags_lock: shutdown = self._shutdown`; `shutdown` → `return False` (подключение, начатое до фазы 1, не делает драйвер готовым). Причина снятия `_stopping`: после обычного `disconnect` ручное «Подключить» снова разрешает jog и программы; после `request_stop()` — нет.
- Гонка с supervisor (р.2 п. 7), решающая строка: `_WorkersStop.request_stop` — `return None` (`multiprocess_framework/modules/process_module/lifecycle/process_lifecycle.py:189-190`; докстрока `:179-180`: «`request_stop` — ничего: у `WorkerManager` нет неблокирующего „стоп всем“»). Без (а) supervisor заново создаёт `dev_<id>` после шага 2 (`plugin.py:329-399`), а у v1 и прочих kind защёлки нет — тик переподключил бы их после `shutdown`. - Почему у программы в фазе 1 HARD, а не SOFT. SOFT посреди хода sim откладывает до цели или до ближайшей EXACT-точки (`sim_core_v2.py:783-788`), а `client.stop(SOFT)` ждёт эха до `soft_echo_timeout_s` = 2.0 с (`client_v2.py:170, 746`): одна программа с длинным ходом заняла бы окно 3,0 с целиком. HARD обрывает ход сразу (`sim_core_v2.py:790-791`), эхо ждётся до `stop_echo_timeout_s` = 1.0 с (`client_v2.py:169`). Jog — SOFT (SOFT у jog обрывает сразу, `sim_core_v2.py:783-785`); задание — HARD (как `robot_driver_v2.py:426`). Обычный `disconnect` оставляет программе SOFT.

**К2. Выживший виден (треб. 2, п. 8).** Путь в health один — reporter корня плагина.
- `configure`: `open_scope("device_hub", budget_s=_SCOPE_BUDGET_S, reporter=self._on_scope_report)`. Reporter вызывается на КАЖДОЕ закрытие: на `scope.close()` (отчёт корня) и на каждый `IHandle.close` записи (`lifetime.py` `_close_entry_early` → `_call_reporter`; проба Т6, Т9). Поток, который отцепил `handle.close` обычного `disconnect`, в отчёт `scope.close()` уже не попадёт (проба Т8: `root close survivors: ()`), но в reporter он пришёл со своим отчётом `survivors=(путь,)` (проба Т9).
- `def _on_scope_report(self, report) -> None`: тело в `try` / `except Exception as exc: self._ctx.log_error(...)` (reporter не бросает). Под `self._scope_seen_lock`: `new = [p for p in report.survivors if p not in self._scope_seen]`, затем `self._scope_seen.update(new)`. `errors = list(report.errors)`. `not new and not errors` → выход. Иначе `ctx.log_warning(f"device_hub.scope: выжившие {new}, ошибки {errors}")` и `ctx.health.report_error(ScopeThreadSurvived(TEXT_SCOPE_SURVIVED), context="device_hub.scope", survivors=new, errors=[f"{p}: {e}" for p, e in errors])`.
- В `plugin.py`: `TEXT_SCOPE_SURVIVED = "поток области хаба не вышел за срок"`, `class ScopeThreadSurvived(RuntimeError)`. Поля `self._scope_seen: set[str]` и `self._scope_seen_lock = threading.Lock()` создаются в `configure` ДО `open_scope`.
- Почему замок: reporter зовут потоки supervisor (обычный `disconnect`), команд (`jog_release`) и `shutdown`. Почему отбор по пути: фаза 3 зовёт `handle.close` записи, которая уже выжила в закрытии корня, и reporter получает второй отчёт с тем же путём (проба Т6: `('close', 'probe/deaf', ('probe/deaf',))` после отчёта корня).

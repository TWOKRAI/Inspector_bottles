## Факты (чтение, `d77235841`)

1. **Почему пуши `.status` не доходят.** Плагин хаба публикует статус через `state_proxy.merge` (`Plugins/hub/device_hub/plugin.py:532`,
   `:624-628`): дельты идут листьями (`….status.ts`, `….status.telemetry.x_mm`, …), и только изменившимися. Вкладка
   подписана на точный путь `….status` (`controller.py:153-157`) — листья паттерн не матчат. `ts` меняется каждый тик
   (`drivers/base.py:214`), поэтому лист `status.ts` приходит каждую публикацию.
2. **Состав снимка v2** (`base.py:212-219`, `robot_driver_v2/driver.py:704-718`, `:577`): `quality`, `ts`, `stats{…}`,
   `queue_len`, `jobs_*`, `returns_*`, `return_queued`, `pick_lead_mm`, `telemetry{x_mm, y_mm, z_mm, rz_deg, servo, …}`,
   `free`, `encoder`. Порядок листьев — порядок ключей словаря; вкладка не должна от него зависеть (как у `.park`, README хаба).
3. **Утечка подписок (найдено при чтении, до этой задачи).** `_bind_state` не сохраняет хэндлы `bind_fanout`
   (`controller.py:153-163`), а `_unbind_state` (`:137-144`) снимает только пустой `_status_handles` и через `unbind`
   (метод для `bind`, не для `bind_fanout`). Подтверждено ревьюером стадии 0 на уровне API: после чередования
   `set_device` — 8 подписок и 0 `release`; `unbind()` и `set_device(None)` не снимают ничего. В живом приложении
   `set_device` зовут один раз на контроллер (`section.py:147`), поэтому реальная утечка другая: `unbind()` не освобождает
   подписки до `destroyed` виджета. От чужих дельт `.park` спасает только фильтр префикса (`:322-323`). Чиним здесь.
4. **`_check_stale` оживёт.** Сейчас `_last_status_ts` всегда `None` — проверка молчит (`:128`). После починки п.1 пуши
   пойдут: пропали на > 3 с — текст «Нет связи с hub…» (`:132`) затирает любой статус, в том числе итог park; пуши

DESIGN (decided by the lead — you type it, you do not derive it):
  1. **Помощник сборки вида** — модульная функция `_apply_leaf(view: dict, rel: str, value: Any) -> None` в

  2. **Подписка `.status.**`.** `_bind_state` (`:146-163`): `bind_fanout(f"{base}.status.**", self._on_telemetry_push,

     `self._bindings.unbind_fanout(h)` (исключение — `except Exception: pass`, как соседний цикл) и чистит список.
     Альтернатива, отвергнутая: хаб публикует `.status` атомарным `set` (`plugin.py:625`, как `.conn`) — правка чужого

     порядка листьев (`ts` приходит раньше `telemetry`, вид отстал бы на тик).
  3. **`_on_telemetry_push(path, value)`** (`:165-170`) — переписать: `prefix = f"devices.state.{self._device_id}.status"`;
     `path == prefix` → `rel = ""`; `path.startswith(prefix + ".")` → `rel` — остаток; иначе `return` (чужое устройство).
     `value is DELETED` (импорт `DELETED` из `multiprocess_prototype.frontend.state.bindings`): `rel == ""` →
     `self._status_view = {}`, иначе удалить лист из вида, если он есть; в обоих случаях — `return` без отрисовки.

     вида). Держит её сторож `status_deleted_drops_leaf` и инъекция J12.

     Иначе `_apply_leaf(self._status_view, rel, value)`. Затем `self._last_status_ts = time.time()` и

#### DESIGN п.5–6 — срок итога park и жизнь таймеров

  5. **Срок ожидания итога park — без второго `QTimer()` (решение лида, вариант (а) по блокеру стадии 0).** Второй
     `QTimer()` без родителя нарушил бы страж G6 R2: в allowlist для `robot/controller.py` ровно 1 вызов
     (`plans/2026-10-03_lifecycle-owner-scope/tasks/0.5a.allowlist.tsv:20`, это `_stale_timer`); новая запись — решение
     владельца. Поэтому — `QTimer.singleShot(ms, callable)` с токеном поколения (R2 матчит только конструктор `QTimer(...)`).
     Константы модуля: `_PARK_RESULT_GRACE_S = 3.0` (1,5 с — запас хаба на тик после срока, ещё 1,5 с — путь хаб → PM →
     GUI и таймер Qt; таймер вкладки к тому же стартует позже `t0` хаба) и `_PARK_TIMEOUT_FALLBACK_S = 60.0` (потолок
     хаба, `texts.py:184`). Поля `__init__`: `self._park_gen: int = 0`, `self._park_wait_s: float = 0.0`.
     - `_on_park_result`, ветка `accepted` (`:289-294`): `t = data.get("timeout_s")`; число (`int`/`float`, не `bool`) и
       `0 < t <= 60` → берём, иначе `_PARK_TIMEOUT_FALLBACK_S`; `self._park_wait_s = t + _PARK_RESULT_GRACE_S`;
       `self._park_gen += 1`; `gen = self._park_gen`; `QTimer.singleShot(int(self._park_wait_s * 1000), lambda:
       self._on_park_deadline(gen))` — до `self._render_park()` (терминал мог прийти раньше ответа). Ответ-отказ поколение
       не трогает (идущий park живёт со своим сроком).
     - Аннулирование = `self._park_gen += 1` (вместо `stop()`): в `_render_park` (`:347-362`) в ветках `done` и `failed`
       перед `set_status`; в `unbind` (`:117-120`); в `_reset_park` (`:264-269`); в `_on_widget_destroyed` (п.6).
     - `_on_park_deadline(self, gen: int) -> None`: `gen != self._park_gen` или `self._widget_gone` или `self._park_seq is
       None` → `return`; иначе `self._park_text = f"Основная остановка: итог не получен за {math.ceil(self._park_wait_s)}
       с. Проверьте робота."` и `set_status`. Округление вверх (`math.ceil`, импорт `math`): 4,0 → «4 с», 4,5 → «5 с»;
       не `:.0f` (банковское округление). `_park_seq` НЕ сбрасывать: опоздавший терминал того же `seq` покажется поверх.
     - Решение лида по замечанию 8 — нажатие любой кнопки робота во время ожидания срок НЕ отменяет (`_clear_park_text`
       поколение не трогает). Текст срока может заменить текст кнопки; позднему итогу park он уступает.
     - Старый J9 (`_reset_park` не аннулирует срок) — эквивалентный мутант по замыслу: `_reset_park` ставит
       `_park_seq = None`, слот выходит по нему; новое ожидание всегда идёт через `accepted`, а там `_park_gen += 1`.
       `+= 1` в `_reset_park` оставляем как явную запись намерения; инъекцией его не проверяем.

     `_STALE_THRESHOLD_S`. Параметр конфигурации не вводим: у вкладки нет пути конфигурации на устройство, слой ради

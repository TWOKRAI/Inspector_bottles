## Факты проб (вход → наблюдение)

1. `state.get {"path": "devices.state.r1.conn"}` → лист `{"status": "ok", "request_id": "", "value": {"conn": "connected", "ts": N}}`
   — словарь, не строка; до первой публикации — `success: false`, `"Путь не существует: 'devices.state.r1.conn'"`.
   `devices.state.r1.program` — словарь `{"name", "state", "done", "total", "error"}`; путь появляется с первым `program_run`.
2. Журнал обмена: содержательный файл только `<log_dir>/devices/robot_exchange.log` (в каталогах других процессов
   файл есть, 0 байт). Строки `STOP_REQ`, записанные на `plugin.shutdown`, на диске к возврату `process.stop` — 21/21.
3. Получив `process.stop`, процесс `devices` перестаёт обслуживать команды («Stop signal received» в
   `devices/messages.log`); плагин закрывается через 150–190 мс («All workers stopped»). `robot_jog_hold`, отправленный
   после этого, отвечает `timeout`.
4. Поэтому окно удержания (`_HOLD_WINDOW_S = 0.2`) может истечь ДО `request_stop`: поводок пишет свой SOFT, затем
   выключение пишет SOFT стоящему роботу. Держатель жив до отправки `process.stop`: r1 = 2 в 9 из 16; держатель шлёт и
   во время `process.stop`: 5 из 16; держатель замолк за 0,6 с до стопа: 4 из 4. Простой r2 — 1 во всех 41 прогоне;
   уровень SOFT везде. Буквальный шаг 5 (один `jog_hold`): 5/5 по 1, но `JOG_CONT → STOP_REQ` 0,146–0,205 с против
   окна 0,2 с — гонка, тест мигал бы.

## Решение лида 2026-10-20 (владелец передал выбор лиду)

Стоп поводка — конец jog (защита: удержание пропало), не стоп выключения. Выключение даёт каждому подключённому
роботу ровно один стоп в своём поколении, стоящему — SOFT (решение владельца 2026-10-19, п. 1). Две записи у робота,
чей jog закрыл поводок до `request_stop`, — норма. Частный случай (стадия 0 р.1, п. 5): запись поводка легла после
сброса защёлки первым `request_stop` (`robot_driver_v2.py:704-709`) — защёлка T5.3a засчитывает её и гасит SOFT
выключения (`:761-765`); робот получает один SOFT в поколении выключения, выключение само не пишет. Лид считает это
исполнением правила владельца (робот остановлен одним стопом), не сужением; механизм защёлки не меняется.
Продукт пути стопа НЕ меняется: «пропуск» стопа выключения после поводка вносит в путь стопа условие, которое может
пропустить нужный стоп. Причина стопа поводка становится видна в логе (DESIGN ниже).
Корень — зазор «процесс не берёт команды → закрытие плагина» ~170 мс — в T5.3e (штатное выключение пересматривает
порядок остановки). Отвергнуто: окно удержания из конфига (правка конкурентности драйвера; зазор зависит от нагрузки,
окно его не закрывает).

## Решения владельца 2026-10-20 (вопросы передачи `docs/handoffs/2026-10-20_task-T5.3cd-lead.md`)

## DESIGN (developer)

D-L1. `robot_driver_v2.py`, `_lease_loop`: в секции `_flags_lock`, где решается `stop`, запомнить
`reason = "область закрывается" if ev.is_set() else "окно удержания истекло"` (приоритет `ev` — порядок прежнего `or`,
`:1550`) и `late = self._stopping`. Вызов `self._stop_jog(run)` заменить телом с тем же замком:
`with self._jog_tx_lock:` → `wrote = not run.stop_sent`; `if wrote: self._stop_jog_locked(run)`. После выхода из `with`
(не держа `_flags_lock` и `_jog_tx_lock`), если `wrote`, — одна строка `logger.info`:
- при `late` False — `f"робот {self.entry.id!r}: jog остановлен поводком: {reason}"`;
- при `late` True — `f"робот {self.entry.id!r}: jog остановлен поводком после начала остановки: {reason}"`.

`run.released`, `wrote` False или исключение — строки нет (исключение — прежний warning «поводок jog прерван», `:1560`).
Строка уходит в `<log_dir>/devices/messages.log` (INFO → BUSINESS → `messages_file`,
`logger_manager_config.py:447-455, 498-511`), не в `system.log`. На верном коде `late` недостижим: `_stopping` ставят
только `_process_stop` (`:742`) и `_request_stop` (`:881`), в той же секции, что `released` (`:745-749`, `:884-888`);
поток читает `released` первым (`:1548`). Хунк только в `_lease_loop`; замок, условие и вызов — те же, что в `_stop_jog`.

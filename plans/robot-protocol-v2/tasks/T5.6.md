## Module contract

lite. `exchange_log.py`: docstring с разделами Purpose / Public API / Stability: lite. `__all__ = ["ExchangeLog", "ExchangeLogTransport"]`. Pre/Post у `get` и `set`.

Публичный API:
- `ExchangeLog(device_id: str, *, maxlen: int = 2000, clock=time.perf_counter, enabled: bool = True, periodic: bool = False)`.
- `.get(since_seq: int = 0, limit: int = 200) -> dict` возвращает `{"enabled", "periodic", "lines", "last_seq", "dropped", "counters", "log_errors"}`.
- `.set(enabled: bool | None = None, periodic: bool | None = None, clear: bool | None = None) -> dict` возвращает состояние в том же виде, что `get`, но без `lines`.
- `ExchangeLogTransport(inner, log: ExchangeLog)`.

Начальные значения ручек берутся из `entry.params.get("exchange_log", {})`: ключи `enabled` (по умолчанию `True`) и `periodic` (по умолчанию `False`).

## DESIGN

### Перехват

1. **Где перехват.** Журнал создаётся в `RobotDriverV2.__init__` (после `:274`) и живёт столько же, сколько драйвер. Нового параметра конструктора нет: иначе конфликт со `spawn` T5.3.
   - Обёртка ставится в двух местах. В конце `__init__`, после создания журнала: если `self._transport` не `None` (транспорт внедрён параметром `transport=`, `:241`) — обернуть. В `connect()` — одной строкой сразу после `build_transport` (`:360`), до создания клиента (`:362`).
   - При переподключении транспорт не пересоздаётся: `connect()` зовёт `.connect()` на том же объекте (`:364`).
   - Мост ПЧ получает обёртку через `carrier.transport` (`transports.py:134-137`, `vfd_driver.py:309`). Это желательно, но в строке журнала не различается. Записать в README.
2. **Обёртка `ExchangeLogTransport`.** Явно реализованы:
   - `is_connected` (property);
   - `read_registers`;
   - `transaction`;
   - `connect()` — пишет строку `tag="link"` с текстом `connect ok` или `connect fail`;
   - `disconnect()` — пишет строку `tag="link"` с текстом `disconnect`.

   `__getattr__` отдаёт только чтение прочих атрибутов (`get_status`, `state`, `config`). Для имён на `_` и до установки `_inner` он бросает `AttributeError`. `__slots__` и `__setattr__` запрещены: тесты `test_robot_driver_v2.py:764-775` и `test_robot_driver_v2_jobs_acceptance.py:344-355` подменяют `drv.transport.transaction` атрибутом экземпляра.

   `write_register(s)` и `read_holding` прошли бы мимо журнала. Сегодня на транспорте робота их никто не вызывает — записать это в README.
### Строка, ручки, счётчики

3. **Строка журнала.** Поля: `seq` (сквозной номер), `t` (`perf_counter`; `monotonic` не брать — на Windows у него шаг 15,6 мс, `sim_journal.py:180-182`), `side`, `text`, `tag`, `n`, `ms` (длительность вызова транспорта).
   - Стороны — с точки зрения робота, как у симулятора: `in` — ПК → робот (запись), `out` — робот → ПК (ответ на чтение).
   - Имена берутся из сгенерированной карты v2 `Services/robot_comm/core/protocol_v2.py`: `REG`; `REG_COUNT` — для блоков (`CMD_ARGS[2]`). Адрес вне карты пишется как `0x1234`.
   - Значение — сырое слово десятичным числом: шкал и знаков в карте v2 нет. `CMD_OPCODE` дополнительно подписывается именем из `OP`: `W* CMD_OPCODE = 16 (PTP_MOVE)`.
   - Запись `("w", a, v)` даёт строку `W <ИМЯ> = v`. Запись `("wm", a, [..])` даёт строку `W* <ИМЯ> = v` на каждое слово (как `_FC_NAMES` FC6/FC16).
   - Исключение: блоки `SC_BUF` и `PMIR` дают одну строку на вызов: `W* SC_BUF[0..29] (30 слов)`.
   - Чтение даёт одну строку на вызов: `R <ИМЯ_первого>..+<count>`. Значения не пишутся, `ms` — только в поле, не в тексте.
   - Чтение, покрывающее `0x1010..0x1012` целиком, даёт строку `tag="res"`: `R RES_SEQ..+4 RES_SEQ = 5, RES_STATUS = 0, RES_ERRNO = 0 (ОК)` (у `RES_ERRNO` — текст из `ERR_TEXT`). Такая строка пишется, только если тройка изменилась против последней записанной строки `res`, независимо от `periodic`; первое чтение `RES` всегда даёт строку. Частичное чтение (`_rd(RES_SEQ, 1)`, `client_v2.py:588`) — обычное чтение.
   - Строки `err` и `link` при `enabled` пишутся всегда, независимо от `periodic`.
   - Ошибка транспорта (исключение или `transaction` вернул `False`) даёт строку `tag="err"` с типом и сообщением. Исходное исключение пробрасывается дальше тем же объектом.
   - Теги: `""` | `"cmd"` (запись `CMD_FLAG`) | `"res"` | `"err"` | `"stop"` (запись `STOP_REQ`) | `"hb"` (запись `HB_PC` / `JOG_LEASE`) | `"link"`.
   - Склейка: подряд идущие строки с тем же `side`+`text` дают `n += 1`; `t` и `ms` берутся от последнего вызова (как `plugin.py:802`), `seq` не меняется.
4. **Ручка `periodic`.** При `False` строк нет для периодического трафика: чтений без нового ответа `RES` и записей `HB_PC` / `JOG_LEASE`. Счётчики при этом считаются.
   - Без этой ручки шум задавит журнал. `HB_PC` растёт на +1 каждый пульс (`client_v2.py:461`), строки тика чередуются, ожидание опрашивает раз в 0,02 с (`client_v2.py:164`). Это ~100 строк/с: кольцо на 2000 строк заполнится за ~20 с.
   - При `True` — все строки.
5. **Счётчики.** Один вызов транспорта — одна операция:
   - чтение — `read <имя первого адреса>`;
   - транзакция со словом `CMD_OPCODE` — `cmd <OP>`;
   - прочие записи — `write <имя первого адреса>`.

   По каждой операции: `count`, `errors`, `ms_last`, `ms_max`, `ms_avg`. Отдельно: `log_errors` (сбои самого журнала).
6. **Ручка `enabled`.** Наблюдаемость включается на ходу и при выключении ничего не стоит (правило владельца, `project-rules` §5).
   - При `False` обёртка проверяет один флаг и зовёт транспорт напрямую: ни часов, ни форматирования, ни счётчиков, ни записи в логгер.
   - Включение и выключение — без переподключения.
### Потоки, файл, операции, команды

7. **Потоки и порядок.** Транспорт зовут: тик хаба, поток поводка, исполнитель программ, команды плагина (`plugin.py:690`, `:719`), `disconnect` / `request_stop` (T5.3), поток моста ПЧ.
   - Замок журнала (`threading.Lock`) НЕ держится во время вызова транспорта. Иначе журнал сериализует обмен и меняет тайминг.
   - Под замком: `seq`, склейка, счётчики, копия текста.
   - Конец вызова читается часами сразу после возврата, `ms` = конец − начало. `t` — второе чтение часов ПОД замком журнала, вместе с выдачей `seq`. Только так `t` монотонен по `seq`.
   - `ms` включает ожидание `RLock` у `ModbusDevice` (`device.py:61`, `:176`). Это не задержка робота — записать в README.
   - Логгер вызывается ПОСЛЕ выхода из замка. Запись в логгер синхронная, медленный приёмник блокирует пишущего (`logger_module/README.md:420-430`). Внутри замка все потоки обмена встали бы на файловом вводе-выводе.
8. **Файл сессии — через единственный писатель `logger_module`.** Своего `open()` нет (правило владельца «один пишущий логгер»).
   - Источник: `get_std_logger(f"{__name__}.{entry.id}")` (конвенция `__name__`, `logger_module/README.md:206-222`).
   - Отдельный файл задаётся правилом конфига без нового писателя (`README:370-405`). В `multiprocess_prototype/backend/config/system.yaml` (`:76-127`) добавить канал `robot_exchange_file: {type: file, name_max_len: 20, file_path: robot_exchange.log}` и правило `Services.device_hub.drivers.exchange_log: {level: INFO, channels: [robot_exchange_file]}`.
   - В логгер идёт одна запись на новую строку: `#<seq> <side> <text>`. Когда закрывается склейка с `n > 1`, идёт запись `#<seq> … ×<n>`.
   - Файл переключается на ходу через `backend_ctl` `logger_sink_disable` / `logger_sink_enable`.
9. **Операции драйвера** — 2 штуки, отдельным блоком в конце файла: `_EXCHANGE_OPS = {...}` и `RobotDriverV2._OPS.update(_EXCHANGE_OPS)` после литерала (`:954-960`). Сам литерал и `call()` не трогать.
   - `exchange_log_get` — args `{since_seq=0, limit=200}`. Возвращает строки с `seq >= since_seq`, первые `limit` по возрастанию; `last_seq` — `seq` последней ОТДАННОЙ строки. Читатель заменяет строку по `seq` (у строки `since_seq` мог вырасти `n`). `dropped` — сколько строк с `seq >= since_seq` уже вытеснено из кольца.
   - `exchange_log_set` — args `{enabled?, periodic?, clear?}`.
10. **Команды плагина** — 2 штуки, `cmd_robot_exchange_log_get` и `cmd_robot_exchange_log_set`, в двух местах:
    - таблица `commands` (`plugin.py:86-130`, после `:117`);
    - методы после `:773-775`.

    `manager.call` при неподключённом роботе отвечает «не подключено» (`manager.py:357-360`), а журнал нужен как раз при сбое связи. Поэтому команда работает так:
    - kind проверяется как в `_kind_call` (`:489-503`);
    - затем `self._manager.get_driver(dev_id)` и `driver.call(op, args)` через `_safe_call`;
    - если драйвера нет — `{"status": "error", "message": "журнала нет: драйвер не создан"}`.

## Hazard-тесты автора (обязательны)

- H1. Фейк блокирует `read_registers` на событии. Второй поток в это время делает `transaction` и завершается до освобождения (join с дедлайном). Это доказывает, что замок не держится во время вызова транспорта.
- H2. При выключенном журнале: часы — 0 вызовов, форматтер — 0, записей в логгер — 0, счётчики не меняются.
- H3. Форматтер бросает исключение. Обмен при этом не ломается: вызов возвращает результат, `log_errors += 1`, `logger.warning` — один раз за жизнь журнала.
- H4. Логгер вызывается вне замка: обработчик логгера блокируется на событии; второй поток делает `read_registers(0x1040, 32)` при `periodic=False` (строки нет, записи в логгер нет) и завершается до освобождения; `read TLM_PROTO_VER.count` вырос на 1.

## Цена (замер, а не утверждение)

- `timeit`, 100 000 вызовов `read_registers` на пустом фейке, три варианта: голый транспорт / журнал выключен / журнал включён. Результат — нс на вызов, 3 повтора с разбросом.
- На стенде: `ms` чтения TLM при включённом и выключенном журнале. Период тика (сон 0,5 с, `:70`) цену не покажет.

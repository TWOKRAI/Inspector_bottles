## Почему так

- **Точка линеаризации K** — `disconnect_request` под замком состояния, внутри `_workers_lock`. Против C0 — тот же
  замок состояния: K раньше C0 → `"cancelled"` (O3, O11); позже → снимок и `_stopping`, следующий шаг `connect`
  отказывает (O4–O7, O10, O12). Направление владельца «connect проверяет desired_connected между шагами» выполнено
  через `_stopping` и счётчик: их ставит тот же вызов K, что и `desired_connected = False` (стадия 0 п.7).
- **Против супервизора** — `_workers_lock`: K и (б) взаимно исключены. Либо K раньше чтения в (б) (stop, desired
  True не ставится), либо позже (K пишет False после True). O13 закрыт (стадия 0 п.5).
- **Снимок переживает выход `connect`.** K пишет `_stop_linked` и `_stopping`; `connect_end` снимает только
  `_connecting` и `_connect_linked`; D2 монотонен; D3: `_stop_linked and link_up()` — сокет после отказа открыт до
  D6 → 1 SOFT. До A3 снимок False → 0.
- **Один владелец закрытия** — D6. Тик: `disconnect_owns_close()` истинно после K со снимком True — тик не
  закрывает; при снимке False и при `"cancelled"` тик закрывает свой сокет сам, D6 — повторно, идемпотентно.
- **ABA.** `[connect₁ (идёт), disconnect, connect₂]`: K прерывает `connect₁`; в (б) `disconnect_pending` True →
  desired True не ставится (бывший остаток О4 закрыт), `conn` = `disconnecting`; `disconnect` — 1 SOFT, счётчик 0;
  `connect₂` целиком. Два K подряд — счётчик 2, два `disconnect` в очереди — 0 (стадия 0 п.6, R8).
- **Счётчик 1:1 с очередью.** Каждый K, нашедший драйвер, — +1 и ровно один элемент `disconnect`; этот элемент
  зовёт `driver.disconnect()` → `disconnect_end` −1. Пути без `disconnect_end` (чтение):
  (1) остановка плагина: супервизор очередь не разбирает (`_shutting_down`), `manager._on_shutdown` зовёт
  `disconnect()` один раз на драйвер — при двух K счётчик останется 1. Не вредно: `_shutdown` уже стоит,
  C0 отвечает `"shutdown"` раньше счётчика;
  (2) `remove` / `DeviceNotFoundError` в `manager.disconnect`: драйвер выбрасывается, новый — со счётчиком 0;
  (3) `disconnect()` без K (`_on_shutdown`, `remove`, тесты) снимает 1 раньше элемента очереди. Источники
  конечные (драйвер выключается или выбрасывается); пол 0 защищает тесты.
  Пути, где счётчик залипает на живом драйвере, чтением не нашёл. Если стадия 0 найдёт такой путь, правка —
  снять счётчик на этом пути явным переходом, а не угадывать общий сброс.
- **Без опоры на общую очередь (В2, C-31).** От очереди не зависит: точка линеаризации (замок состояния), закрытие
  окна (б) (`_workers_lock`), снимок, счётчик и отказы В4 — всё на драйвере и словаре плагина. Опора только одна:
  элементы одного устройства идут по порядку (`disconnect` раньше `connect₂`) и каждый K даёт ровно один
  `disconnect`. Очередь на устройство (C-31) это сохраняет — переделки C-29 не нужно.
- **В3.** `conn` пишут и плагин, и `publish_cb` менеджера в `ctx.state_proxy.set` (`plugin.py:248`, `:613-615`).
  Менеджер при `disconnect_pending` публикует `disconnecting`, плагин тоже → после схлопывания повторов
  `connecting`, `disconnecting`, `disconnected` (C11-a). Без K — `connecting`, `connected` (C11-b).
- **В4.** Отказ в той же секции, где jog допускается (`jog_hold_admit` под `_jog_tx_lock`): K раньше — отказ, позже —
  jog допущен, его останавливает D2. Задание: отказ в команде; задание, ставшее в очередь до K, тик не берёт, пока
  счётчик > 0.

## Что меняется в ADR-DH-011

Новый пункт «Решения» после T5.3h: «**«Отключить» прерывает `connect` (C-29, решения владельца 2026-10-25,
В1–В4).**» — `request_disconnect` (getattr, без базы) из команды под `_workers_lock`; переход `disconnect_request` —

disconnect» — отклонено» заменить ссылкой на C-29 (В1); остатки О1–О9 ниже; пункт T5.3g «окно «проверка → запись»
остаётся» — без изменений (О1).

## Приёмка (слепой тестер; только публичное поведение)

Обвязка — как в пробе: настоящий `DeviceHubPlugin` (`make_ctx`), драйвер v2 на фейках (фабрика менеджера).
Счётчики — на фейке: STOP_REQ по уровням, SERVO, DO, `probe`, JOG_CONT. Статусы — канал `ctx.state_proxy.set` с
путём `devices.state.<id>.conn` (плагин и `publish_cb` менеджера), повторы подряд схлопнуты. Паузы — только в
потоке супервизора или тика; блокирующие вызовы — daemon-поток с join-дедлайном.
- A1. Команда посреди `connect` — `{"status": "ok", ...}` за 1,0 с, пока `connect` стоит.
- A2. После подъёма связи (`probe`; `sync_params`; перед SERVO; перед DO): после команды SERVO 0, DO 0;
  `connect()` False; SOFT ровно 1; в конце транспорт закрыт.
- A3. До подъёма связи (внутри `transport.connect()`): `probe` 0, SERVO 0, STOP_REQ 0, `connect()` False.
- A4. Долгая синхронизация 2,0 с и ожидание TLM после неподтверждённого SERVO: от команды до входа в `disconnect`
  драйвера < 0,5 с; SOFT 1.
- A5. Статусы прерванного `connect`: ровно `connecting`, `disconnecting`, `disconnected` (нет `connected`, нет
  `error`). Парная: `connect` без команды — `connecting`, `connected`. `desired_connected` False до конца очереди.
- A6. «Подключить» → команда → «Подключить»: `connect()` `[False, True]`; SERVO только после `disconnect`; SOFT 1;
  в конце подключён, `desired_connected` True.
- A7. Тик переподключает (связь упала), команда в `probe` тика: SERVO 0, тик не подключил, SOFT 1, закрыт.
- A8. Первый `connect` после старта, команда до того, как супервизор взял `connect` (драйвер ещё не создан):
  `probe` 0, SERVO 0, STOP_REQ 0.
- A9. Ручной `connect` ждёт замок за переподключающимся тиком, затем команда: после команды `probe` 0, SERVO 0;
  SOFT 1.
- A10. Робот подключён, команда, очередь ещё не разобрана: `jog_hold` → `{"status": "error", "message":
  "идёт отключение робота"}`, JOG_CONT 0; `jog_step` → тот же текст, кадров jog 0. Парная: без команды
  `jog_hold` → JOG_CONT 1.
- A11. То же окно: `enqueue_job` → `status` error, `message` «идёт отключение робота». Парная: без команды —
  `{"status": "ok", "queue_len": 1}`.
- A12. Регресс: команда на подключённом простом роботе — SOFT 1, `disconnect` за 1,0 с; затем «Подключить» →

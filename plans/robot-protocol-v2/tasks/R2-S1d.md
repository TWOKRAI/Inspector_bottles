### Task R2-S1d — СТОП оператора не запирается готовностью драйвера

**Level:** Senior+ (Opus)
**Assignee:** teamlead
**Goal:** `stop` и `abort` уходят на робота, даже когда драйвер «не подключён» после обрыва или неудачного повторного
connect; молчаливой потери СТОПа нет.
**Module contract:** `OpSpec.needs_link` (существует). **Dependencies:** R2-S1a (ветка `fix/modbus-link-drop`).

**Правило (cto 2026-11-27, `docs/reviews/2026-11-27_task-R2-S1a-cto.md`).** СТОП оператора пишется всегда, когда у
драйвера есть клиент, подтвердивший прошивку v2 по этому адресу (`client.probed`), и связь не закрыта законченным
намеренным `disconnect()`. `_ready`, `is_connected`, идущий или неудачный connect, лимит переподключений его не
запирают. Это ровно условие `_stop_reachable` (`stop.py:91-99`).

#### Что сейчас не так (воспроизведено)
- `manager.py:742` отклоняет любую операцию при `not is_connected`: при повторном connect во время движения с
  `on_connect.servo: false` или после обрыва `stop`/`abort` отвечают «не подключено», робот едет до своего сторожа.
- После обрыва во время задания тик зовёт `_link_lost()` → `transport.disconnect()` (клиент SDK = None) раньше ждущего
  СТОПа: на провод ничего.

#### Дизайн
1. `spi.py`: `needs_link=False` у `_ABORT` и у `stop` v2. `manager.py` не менять.
2. `ops.py::_operator_stop`: отказ `_NOT_CONNECTED`, когда не `_stop_reachable` (вместо одной проверки `client is None`);
   запись — с одним повтором и «стоп не подтверждён роботом» при двух неудачах (переиспользовать
   `_write_stop_twice`; гонка с закрытием и открытием транспорта в `driver.py:364-365` закрывается этим повтором).
3. `driver.py::_link_lost`: не звать `transport.disconnect()`, когда транспорт уже не подключён. Явный reconnect в путь
   СТОП не добавлять.
4. `robot_driver.py` (v1): `_op_abort` без связи — прежний отказ «не подключено», 0 записей (`_ABORT` общий с v2).
5. `plugin.py::_driver_call`: текст «журнала нет: драйвер не создан» остаётся только у операций журнала, у остальных
   нейтральный.
6. `Services/device_hub/DECISIONS.md`: ADR-DH-016 — правило выше и инвариант «обёртку SDK обнуляет только намеренное
   отключение»; отмена `R2-S1a.md:35` для следующих задач.
7. `test_r2s1a_hazards.py`: у `test_stop_during_job_after_drop` в порядке tick_first ожидание меняется на «STOP на
   проводе» (это авторский тест R2-S1a, менять разрешено лидом). Если после пункта 3 порядок tick_first этого не даёт —
   сообщить, не гнуть ассерт.

#### Приёмка
Команды подаются как из приложения — через хаб устройств (`robot_stop`, `robot_abort`), робот — сим v2 по TCP.
- [ ] A1. Робот движется; повторный connect уже подключённого устройства не удался (сим занят / сбой после пробы):
  `robot_stop` HARD отвечает ok, `STOP_REQ` на проводе, робот встал. То же для `robot_abort`.
- [ ] A2. Робот движется; обрыв и возврат связи; СТОП до удачного переподключения тиком: записан, робот встал.
- [ ] A3. После законченного намеренного отключения: `stop`/`abort` — ответ-ошибка, 0 кадров, нового TCP нет.
- [ ] A4. Прошивка не подтверждена (проба не прошла): 0 кадров STOP, ответ-ошибка.
- [ ] A5. Связь мертва: ответ приходит за ограниченное время (< 5 с на loopback), «стоп не подтверждён роботом» в
  `last_error` ровно один раз на нажатие, `stop_unconfirmed` True.
- [ ] A6. v1 без связи: `robot_abort` — ответ-ошибка, 0 записей.
- [ ] A7. Порядок «тик первым» при задании после обрыва: STOP на проводе (и `disconnect`, и `request_stop`).
- [ ] A8. Прочие операции (`robot_servo`, `robot_jog_step`) в неготовности по-прежнему отклоняются, 0 кадров.
- [ ] A9. СТОП, навязанный в окно между закрытием и открытием транспорта в connect: записан.

**Out of scope:** `manager.py`; явный reconnect; `_run_on_connect` и серво (R2-S1); R2-S1c; прошивка; GUI.
**Прогоны:** только через `scripts/machine_gate.sh`; в worktree `PYTHONPATH=<корень>`, `uv sync` не делать.

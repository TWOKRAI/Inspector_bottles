## Точка линеаризации (решение лида, вариант (а), стадия 0 п. 1)

Окно W1′. `request_stop` состоит из двух секций: `request_stop_begin` (`state.py:270-277`), затем `_jog_tx_lock`
(`stop.py:51`), затем `process_stop_plan` (`state.py:287-316`). Между ними T1 успевает выйти из `connect` через
отказ и `finally connect_end`. Тогда план видит `connected()` False и «подключения нет», получается 0 SOFT и
`connect()` False. Ни один последовательный порядок так не даёт.

Решение: одна точка линеаризации — секция `request_stop_begin`, где ставится `_shutdown = True`. В ней при первом
вызове (ветка `if not self._shutdown`) запоминается `self._stop_linked = self._connecting and self._connect_linked`.
`process_stop_plan` берёт этот снимок, а не живые флаги подключения. `connect_link_up` при `_shutdown` (и при
`_stopping`) связь не поднимает и отказывает. Итог:
- стоп раньше поднятия связи — `_stop_linked` False, записи нет (A3), `connect_link_up` отказывает;
- стоп после поднятия связи и до `connect_finish` — `_stop_linked` True, 1 SOFT при любом времени выхода T1 (A1);
- стоп после `connect_finish` — `connected()` True, 1 SOFT, `connect()` → True (A4).

## Q1 (W4)

Один переход `RobotState.connect_begin() -> tuple[str, bool]` заменяет в `_connect_locked` три вызова:
`connect_check` (`driver.py:293`), `_activity_alive` (`driver.py:296` → `state.py:228-232`) и `connect_reset`
(`driver.py:298`). Одна секция под замком:
- `_shutdown` → `("shutdown", False)`, `_ready` не трогается;
- `_job_active`, `run.active` или `_program_active` → `("busy", False)`;
- иначе: `_connect_reset_locked()` (тело `connect_reset`, `state.py:244-247`), `was_ready = self._ready`,
  `self._ready = False`, `self._connecting = True`, `self._connect_linked = was_ready` → `("go", was_ready)`.

Окно W4 (`driver.py:293` → `:298`) исчезает. `connect_check`, `connect_reset` и `is_shutdown` остаются:
их держат контрактные тесты (`test_robot_v2_state_acceptance.py:434-446, 728-746`), принцип 3.
Следствие (стадия 0 п. 2): `request_stop` ДО `connect` у готового робота — 1 SOFT по `is_connected`, `connect()` →
False, `is_connected` остаётся True до `disconnect`, как в A4.

## Q2 (W1)

`_ready` переносится в `RobotState` (поле `_ready`).

Подсчёт по коду:
- записи на драйвере: `driver.py:162` (инициализация) и рабочие `:300`, `:318`, `:342`, `:389`, `:519`, `:530`;
- чтения: `:257` (`is_connected`) и `:299`;
- швы тестов: `test_robot_v2_ops.py:546, 642, 780`, сторож `test_no_private_driver_state.py:86` (`"_ready": 3`).

Одной условной установки мало. Между проверкой в переходе и `self._ready = True` вне замка снова проходит
`request_stop`. То же касается `:318` после `:316`.

Выбрано: на драйвере `_ready` становится свойством. Геттер читает `self._state.ready` без замка, сеттер зовёт
`self._state.set_ready(v)` под замком. Записи `:300`, `:318`, `:342` уходят в переходы. Записи `False` на `:389`,
`:519`, `:530` и швы тестов идут через сеттер, их текст не меняется. Заодно закрывается W2.

Отклонено: обратный вызов из перехода, который ставит `_ready` драйвера. Тогда код драйвера выполняется под
листовым замком, а W2 остаётся открытым.

Реентерабельность. Замок — `threading.Lock` (`state.py:125`), а `connected()` вызывается под ним (`stop.py:81`,
`programs.py:45`). Поэтому геттер и `is_connected` замок не берут. Чтение bool без замка атомарно. Все, кто пишет
это поле, держат тот же замок. Прецедент — `returns_done` (`driver.py:264-267`). `transport.is_connected` тоже не
берёт замок: `Services/modbus/core/device.py:79-81`, `exchange_log.py:423-425`.

## Q3 (WW)

`process_stop_plan(connected, link_up=None)`. Ветка простого робота (`state.py:304`) теперь такая:
`elif connected() or (self._stop_linked and link_up is not None and link_up())`. Контрактные вызовы без
`link_up` не меняются. Драйвер (`stop.py:81`) передаёт
`link_up=lambda: self._transport is not None and bool(self._transport.is_connected)`.

Клиент создаётся на `driver.py:309-310`, раньше `connect_link_up` (после `:312-313`). Для `was_ready` клиент
остался с прошлого `connect`, а `_client = None` в пакете нигде не пишется. Значит, когда `_stop_linked` True,
клиент всегда есть. Проверка на `stop.py:82` остаётся защитной. SOFT пишет сам `request_stop` (T2).

Сериализация:
- транспорт: каждая операция `ModbusDevice` идёт под RLock (`device.py:61, 176, 200, 213`);
- клиент: `issue_stop` берёт только `_stop_lock` (`client_v2.py:733-734`), а `_mailbox_lock` — только в `cmd()`
  (`client_v2.py:16-17, 314`);
- пока T1 внутри `probe`, T2 сам делает `_ensure_probed` (`client_v2.py:731-732, 432-442`). Это одни чтения, и
  базы обновляются по поколениям (`client_v2.py:385-386`).

Настоящий транспорт внутри `connect()` находится в CONNECTING: `is_connected` False до `device.py:103`
(`status.py:63-65`). Поэтому граница A3 — `connect_link_up`, а не флаг транспорта.

## Q4

После SOFT посреди `connect` флаги стопа никто не сбрасывает: это делает только `connect_begin`. `connect` выходит
с False в первой же проверке отмены:
- `connect_link_up()` → False;
- `begin_sync` отказывает (`state.py:452-453`) или срабатывает `cancelled=` в `sync_params`
  (`client_v2.py:822-827`); затем `if not self._state.connect_restore(was_ready): return False` (решение лида, стадия
  0 п. 5в). Слой `_sync_cancelled()` (`driver.py:316-317`) сливается с переходом. `connect_restore` под замком при
  `_stopping`/`_shutdown` возвращает False, иначе `self._ready = was_ready` и True; затем `return self.is_connected`;
- `_run_on_connect` возвращает bool. Перед каждым `client.servo` и `client.do_set` стоит
  `if self._sync_cancelled(): return False`;
- `connect_finish()` под замком при `_stopping`/`_shutdown` возвращает False, иначе `self._ready = True` и True;
- исключение при отмене обрабатывается как сейчас (`driver.py:326-330`);
- `finally: self._state.connect_end()` снимает `_connecting` и `_connect_linked` на любом выходе после
  `connect_begin`.

Уточнение 1 (обычный `disconnect` посреди `connect` → `connect()` False) принято в рамках T5.3g. Обязательны тест
`test_disconnect_during_on_connect_connect_false` и запись в ADR-DH-011. Побочный эффект: если в пути тика
`desired_connected` остался True, отказ считается неудачным переподключением, `_note_reconnect_failed()`
(`driver.py:453`).

## Q5

Имя `_connect_locked` не меняется: его держит `sys._getframe(2)` пробы. Исполнитель правит
`test_robot_v2_t53g_windows.py` вместе с кодом. Литералы W1-a … WW-b не меняются:
- W1: обёртка на `RobotState.connect_finish`, пауза ДО исходного вызова;
- W4: обёртка на `RobotState.connect_begin`, пауза ПОСЛЕ возврата `("go", True)`;
- WW: без изменений.

Новые тесты автора:
- `test_w1p_soft_when_connect_exits_between_stop_sections` (W1′). T1 стоит в `probe`. В T2 обёртка на
  `RobotState.process_stop_plan`: отпустить барьер T1, дождаться `join` T1 с дедлайном, затем вызвать исходный.
  Ждём 1 SOFT и `connect()` False;
- `test_ww_c_ready_robot_connect_false`. Барьер WW, робот подключён до T1. Ждём `connect()` False и
  `is_connected` False. Ловит инъекцию 5 (`connect_restore`); W4-a её не ловит, потому что `connect_link_up`
  отказывает раньше (см. `T5.3g.injections.md`);
- `test_a3_no_write_inside_transport_connect`. Транспорт не подключён; в фейковом `connect()` сначала
  `is_connected = True` (как `device.py:103`), затем пауза. Ждём 0 записей, `stop_unconfirmed` False, `connect()`
  False;
- `test_a3_no_write_while_closing_stale_socket`. Робот не готов, транспорт «подключён». Пауза в фейковом
  `disconnect()` до сброса флага (`driver.py:302-303`). Ждём 0 записей и `connect()` False;
- `test_a4_stop_after_connect_finish_one_soft`. Пауза ПОСЛЕ возврата True из `connect_finish`. Ждём `connect()`
  True и 1 SOFT. Это страж регресса, в инъекциях не участвует;
- `test_q4_no_servo_after_stop_in_on_connect`. В TLM фейка `TLM_SERVO = 0`, фейковый `servo` ставит бит.
  Пауза в `transport.read_registers` из T1 во время `_run_on_connect`. Ждём 0 вызовов `servo` и `connect()` False;
- `test_disconnect_during_on_connect_connect_false`. Та же пауза, T2 зовёт `drv.disconnect()`. Ждём `connect()`
  False и `is_connected` False.

Проверка достижимости в каждом тесте: `entered` дождались, T1 жив, `release` не поставлен.

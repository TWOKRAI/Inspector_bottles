## Замечания

- [major/dryrun] Две строки плана инъекций по метке стопа проверяют не то свойство.
  (1) «нет проверки метки до загрузки → приёмка "после стопа ни одной записи в буфер"». Приёмка b ставит стоп в `on_progress` внутри `wait_done` третьего куска. К этому моменту четвёртый кусок уже загружен, а `RobotAborted` из `wait_done` уходит наружу при любых проверках метки. Прогон эталона: `RobotAborted errno 13 … after [] bad [] runs 3` — проверка метки в нём вообще не участвует, поэтому без проверки до загрузки b останется зелёной.
  (2) «нет проверки после ACK → тест автора: стоп в простое между кусками». Прогон, 60 точек, свой HARD в `on_progress` при done == 25:
  `idle stop, full design -> RobotAborted(between) sc_run_after_stop=0`
  `idle stop, NO after-ACK check -> RobotAborted(between) sc_run_after_stop=0`
  Стоп ловит проверка до SC_RUN, и тест зелёный при инъекции. Проверку после ACK отделяет от других только чужой стоп: `STOP_REQ` записан прямо в ядро перед транзакцией SC_RUN.
  `external stop before SC_RUN, full -> RobotAborted(after ack)`
  `…, NO after -> RobotAborted(before upload) sc_run_after_stop=1` — кусок k+1 запущен.
  Как исправить:
  - В п.9 описать тест автора с `HookTransport.before_tx` на CMD-транзакции SC_RUN куска k+1: `core.write(REG["STOP_REQ"], чужое значение)`. Ожидание: после ACK в журнале STOP_REQ HARD, затем `RobotAborted`. Под инъекцию (2) этот тест красный.
  - Проверку до загрузки изолирует только `read_filter` на чтении `TLM_STOP_ACK` сразу после проверки после ACK. Либо так, либо убрать строку (1) из плана и написать, что проверка до загрузки — второй рубеж.
  - Добавить в план две инъекции на тесты автора, которые уже есть в п.9: «метка после ACK → `RobotAborted` без `stop(HARD)`» и «`RobotTimeout("response")` без `stop`».
- [major/design] Правило владельца «после стопа ничего не загружается» не выполняется для стопа из другого потока. DESIGN 6d проверяет метку один раз перед загрузкой куска, а не перед каждым блоком FC16. Прогон, `stop(HARD)` на втором блоке из пяти: `stop mid-upload (2nd block), full -> RobotAborted buf_writes_after_stop=3`. Приёмка b это не видит, потому что её стоп идёт из того же потока.
  Кроме того, не сказано, что делать, если метка взведена перед загрузкой. Прочтение «сразу `RobotAborted`» (как перед SC_RUN) возвращает управление, пока робот ещё едет: SOFT доводит до EXACT. Прогон без проверки после ACK: `RobotAborted(before upload)`, а кусок k+1 исполняется.
  Как исправить:
  - В цикле загрузки внутри `run_chunks` перед каждым блоком FC16 проверять `stop_generation != g0` — это чтение из памяти, без ввода-вывода.
  - При метке до загрузки или во время неё: дальше не грузить, SC_RUN не слать, дождаться `wait_done(seq)` текущего куска (он кончится `E_ABORTED` → `RobotAborted`) и в любом случае поднять `RobotAborted`.
  - Тест автора: `before_tx` на втором блоке зовёт `stop(HARD)` → после стопа 0 записей в `SC_BASE..+330`.

## Major

**M1. T5.3e.1 — окно SOFT поводка между `park_begin` и отпусканием jog в потоке park (п.2 брифа лида).**
DESIGN п.2: отказы `_parking` в `jog_hold_check` / `jog_hold_admit` стоят «сразу после проверки `_disconnect_requests`»,
то есть ДО `_holding_locked()` -> `"hold"` (`state.py:660-668`). Значит, с `park_begin` продление окна прекращается, а
`released` поток park ставит позже (`jog_release_begin`, `state.py:720-732`). Поводок пишет SOFT, если
`clock - last_hold > 0,2` (`state.py:744`, `_HOLD_WINDOW_S`, `texts.py:74`). Прецедент C-29 (`state.py:661`) сознательно
даёт поводку истечь — для park это прямо противоречит приёмке владельца.
Чередование: t=0,000 `jog_hold` ok (`last_hold=0`); t=0,095 `robot_park` -> `_parking=True`, публикация, `spawn`;
t=0,100 `jog_hold` -> `TEXT_PARKING` (без продления); поток park запущен, но до `jog_release_begin` не дошёл к t=0,2
(GIL, тик, IPC); t≈0,2 `lease_check` -> `stop_requested`, поток поводка пишет SOFT и строку «jog остановлен поводком:
окно удержания истекло» -> L1 = 1, А3 красный; `jog_release_begin` возвращает None (`state.py:724`). Запас — около
0,1 с минус задержка потока; под нагрузкой это окно реально. P-I2 от этой гонки не отличим.
Исправление: в `park_begin` той же секцией замка, если `_holding_locked()`, ставить пометки release (`released`,
`stop_requested`, `wake.set()`, `_jog_stopping = True`) и вернуть `run` потоку park. Поток park пишет SOFT
(`_close_thread` + `_stop_jog` + `jog_release_done`, как `jog.py:117-122`). Поводок выходит по `"released"`
(`state.py:742`) без своего стопа. Сторож автора: удержание с периодом 0,19 с, `robot_park` в конце периода, задержка
старта потока park 0,15 с (шов `spawn`) -> строк «поводком» 0.

**M2. T5.3e.1 — итог seq k может лечь в стор ПОСЛЕ публикаций seq k+1; ждущий k+1 висит до своего срока.**
Порядок «`park_end` -> публикация итога» (DESIGN п.4) снимает `_parking` до публикации. Чередование: T1 `park_end(True)`;
поток команды: второй `robot_park` -> `park_begin` (`_parking` уже False, `_parked` не отказывает — А12) -> seq 2 ->
публикация `{seq: 2, parking}` -> `spawn` T2; T2 (робот уже дома): шаги 1–4 за миллисекунды -> `park_end` ->
публикация `{seq: 2, done}`; T1 продолжает -> публикация `{seq: 1, done}`. В сторе остаётся seq 1; ждущий seq 2
(шаг `pre_stop` 1.4, контроллер T5.3e.4) не видит итога до срока (40 с / `timeout_s`). В чтении Б стор — единственный
носитель итога.
Исправление: отдельный замок драйвера `_park_pub_lock` (не замок `RobotState`). Поток park держит его на
`park_end` + публикации итога. Поток команды держит его на `park_begin` + первой публикации + `spawn`. Секции короткие,
без ожиданий. Порядок замков: `_park_pub_lock` -> замок состояния; `_jog_tx_lock` под ним не берётся. Сторож: шов
публикации задерживает итог T1 на 0,2 с, второй park на роботе дома -> последнее значение `.park` имеет `seq == 2`.

Основание: `T5.3e.analysis.md` §«Варианты без костылей», §«Свод лида» (HEAD `5544cf1e7`). Только чтение кода, без прогона.

### 1. Мои находки по Б при В2

- **M1 — хуже, если отпускание jog отдать тику.** Задержка до 0,5 с больше окна `_HOLD_WINDOW_S` = 0,2
  (`texts.py:74`): SOFT поводка будет почти всегда, L1 = 1. Один поток тика гонку не убирает: поводок и держатель —
  другие потоки. Исправление при В2: шаг 1 «jog» остаётся в потоке команды. `_op_park` ставит пометки release в
  секции `park_begin` и до ответа исполняет тело `_op_jog_release` (`jog.py:110-122`), там же, где сегодня идёт
  `robot_jog_release` оператора. Удержания и park — в одном потоке команды, поводок выходит по `"released"`
  (`state.py:742`). Гонки нет. SOFT программы (тело `_op_program_abort`, `programs.py:146-150`) — туда же. Цена: при
  живом jog ответ park приходит после release (join ≤ `_LEASE_JOIN_S` 1,0 с + эхо SOFT); А1 «≤ 0,1 с» верно только без
  jog, А3 нужен свой литерал.
- **M2 — меняет форму.** Итоги всех seq пишет один поток (тик), итог k всегда раньше итога k+1: зависание из Б уходит.
  Остаётся другое чередование. Поток команды: `park_begin` (seq 2), вытеснен до публикации `{seq: 2, parking}`. Тик
  (робот дома) за один тик проходит seq 2 и публикует `{seq: 2, done}`. Поток команды публикует `{seq: 2, parking}`.
  В сторе остаётся `parking`, ждущий висит. Исправление: один писатель — все публикации `.park` только из тика
  (первый шаг публикует `parking`), поток команды в `.park` не пишет. Ждущие фильтруют по `seq`; А10, А13 не меняются.
- **M3 остаётся:** тику нужен исход `park_home` от `program_finished` (то же исправление).
- **M4 остаётся, плюс деталь В2.** Если проверку срока поставить в `_dispatch` после условия `free`, срок во время хода
  домой заметят только после прибытия. Park отчитается `done` вместо «срок вышел»: А7 ложный.
- **M5 остаётся.** `_operator_stop` (`ops.py:80-100`) -> `park_cancel()`, тик проверяет признак на каждом шаге.
  Окно: отмена между проверкой тика и `_launch` — дом запущен после HARD. Закрыть: `admit_launch(kind="park")`
  отказывает при признаке отмены, в той же секции замка.
- **M6, M7 остаются** (от носителя не зависят).
- **m1 уходит** (нет `spawn`), но появляется N1 ниже. **m5 уходит**, если jog отпускает поток команды.
- **m2 меняет форму.** `_resync_maybe` и park — в одном тике (`driver.py:555-568`), гонки `TEXT_SYNCING` нет. Но
  ресинхронизация посреди park может переписать `P_HOME_*`, а шаг 3 берёт `_home_point()` из `_values`
  (`driver.py:239-248`). `_parking` в `begin_sync` оставить.
- **m3 остаётся:** `park_begin` в потоке команды против `take_next_action` в тике — та же гонка.
- **m7 остаётся:** тик может записать серво после `_shutdown`, не больше одной записи.
- **m11 меняет форму.** «≤ 0,2 с» в А6 при В2 недостижимо: `failed` публикует следующий тик (≤ `poll_interval_s`).
  Литерал — `≤ poll_interval_s + 0,1` с `poll_interval_s: 0.05` в тесте. Альтернатива — итог park в `request_stop`,
  но это правка `stop.py`, которую бриф запрещает (п.7).
- **m4, m6, m9, m10, m12–m17** остаются; **m8** снимается вместе со ссылкой.

### 2. Новые дыры В2

- **N1 (major) — обрыв связи посреди park даёт вечный `_parking` и запрет переподключения**, если `_parking` входит
  в `_activity_alive_locked` (бриф п.2). Вход: связь пропала. Тик: `_ensure_connected` -> `is_connected` False ->
  `_activity_alive()` True (`driver.py:493`) -> False -> snapshot `bad` (`:530-531`). `_dispatch` не зовётся, park не
  видит ни связи, ни срока, `_parking` не снимается, переподключения нет никогда. Исправление: при В2 `_parking` НЕ
  входит в `_activity_alive_locked` (у park нет потока). Проверка park (срок, связь, `_shutdown`, отмена) — первой
  строкой `tick`, до `_ensure_connected` (`:530`) и до раннего выхода по TLM (`:547-551`). `connect_begin` отказывает
  «busy» при `_parking` отдельной проверкой: иначе ручное «Подключить» снимет `_parking` через `_connect_reset_locked`
  посреди хода.
- **N2 (major) — место шага относительно `free`.** Ожидания (конец программы, срок, отмена, связь) должны идти каждый
  тик, независимо от `free` (`jobs.py:52-53`). Условие `free` нужно только запуску дома (шаг 3) и проверке простоя
  (шаг 2). Шаг `_park_step(tlm, free)` поставить в `tick` после чтения TLM, до `_dispatch`. `take_next_action` при
  `_parking` возвратов и заданий не выдаёт (как в брифе).
- **N3 — задержка.** Каждый переход ждёт тика: первый тик после `park_begin` ≤ 0,5 с; конец программы дома замечен
  ≤ 0,5 с; подтверждение серво по TLM, если нужно, ещё ≤ 0,5 с. Итого +1,0…1,5 с. А2 `elapsed_s < 1.0` держится, только
  если «уже дома» проходит шаги 3–5 за один тик без подтверждения серво; иначе литерал < 1,5 с. Срок меряется с шагом
  тика: А7 (0,3 с) замечен на ≤ 0,5 с. L1 после правки M1 не задет. Умолчание 30 с не задето.
- **N4 — блокировка тика.** Ни один шаг блокировать не обязан: задание и сегодня держит тик, пульс шлёт `on_poll`.
  Ловушка: цикл ожидания внутри тика (конец программы, TLM серво) снимает пульс (`driver.py:536`) — сторож робота
  (`TEXT_WDG_INTERVAL`, `driver.py:376-378`). В спеку: один неблокирующий переход за тик. Сторож автора: длительность
  тика во время park ≤ 0,1 с (сим).
- **N5 — выключение.** `request_stop` режет движение без тика: HARD программе и заданию (`state.py:441-443`) из потока
  `request_stop`; `wait_done` задания в тике выходит по `RobotAborted`. Учёт park ждёт тика, а после
  `request_stop_all` плагин удаляет воркеры тика (`plugin.py:298-308`): `failed` может не опубликоваться, в сторе
  останется `parking`. Тик между `_shutdown` и удалением дом не запускает (`admit_launch(park)` отказывает при
  `_shutdown`); серво — m7.

### 3. Архитектура: Б, В1, В2, В3

| критерий | Б | В1 | В2 | В3 |
|---|---|---|---|---|
| механизмы исполнения | +1 вид потока драйвера (`-park-`) | исполнитель + поток программы (поток исполнителя ждёт поток `spawn`, `programs.py:56`) | 0 новых: тик + поток программы | как В1 + ранний ответ |
| слои / файлы | Services | фреймворк (полоса Ф) + Services + prototype | Services | фреймворк ×2 + Services |
| C-60 (принцип 2) | обход | чинит | не задет; чинит полоса Ф по существу | чинит |
| универсальность | только робот | любая долгая операция любого процесса | шаблон для любого драйвера хаба (у всех есть `tick`, `plugin.py:496`), пока — код робота | самая широкая |
| проверяемость (принцип 5) | гонки потоков (M1, M2) | нужен жизненный цикл процесса | лучшая: тест зовёт `tick()` сам, шаги детерминированы; гонки — только «команда против тика», уже существующие | как В1 |
| остаточные риски | M1, M2, выживший | порядок фаз всех процессов, ответ 30 с GUI (`command_sender.py:31`), ключ `device_id` | N1–N5, m3, m7 | всё В1 + две формы ответа |

Самый правильный и надёжный для этой задачи — **В2**: наименьшее число механизмов, детерминированные шаги, движение
режется стопом без тика. Самый универсальный — В3, но широкая возможность с одним потребителем противоречит принципу 4.
Для хаба универсальность даёт В2, если поднять форму на уровень SPI: контракт «долгая операция устройства — ответ
`{accepted, seq}`, итог в `devices.state.<id>.<op>`: `{seq, state: parking|done|failed, step, reason}`, шаги — в тике
драйвера». Помощник в базовом драйвере — когда появится второе устройство (vfd: торможение до 0 Гц, generic_modbus:
последовательность).
Остаточные риски В2 по механизму: задержка ≤ интервала тика на переход (N3); гонки «команда против тика» (M2-форма,
m3); ранние выходы тика (N1); блокировка тика ошибкой реализации (N4); итог при выключении теряется (N5); запись серво
после `_shutdown` (m7).

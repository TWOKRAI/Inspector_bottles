## Вопросы по API

1. Соседние тесты `bindings` не передают и образца `_on_telemetry_push` в них нет. Форму `bindings=MagicMock()` и вызов `bind_fanout(pattern, handler, owner=widget)` я взял из брифа; прогон существующего контроллера показал, что вызов уже имеет эту форму (`bind_fanout('devices.state.robot_main.status', handler, owner=widget)`).
2. Значение для `_on_telemetry_push(".status", …)` я взял в виде словаря `_apply_telemetry` (`{"telemetry": {...}, "free": True, ...}`). Проверено прогоном: текущий контроллер пишет «Связь с роботом активна.».
3. Тексты новых кнопок взяты из брифа дословно: «Остановить» и «Остановить принудительно» (поиск по точному совпадению `text().strip()`). Если реализация добавит иконку, эмодзи или другой текст, тесты К12 и клика покраснеют ложно — нужно подтверждение текстов.
4. Атрибуты новых кнопок неизвестны, поэтому я ищу их по тексту. Есть ли у них имена вида `_btn_park` / `_btn_force_stop`, не знаю.
5. Старые кнопки «Стоп: домой / домой+выход / на месте» — `_btn_stop1/2/3` (проверено прогоном, `stop_requested` шлёт 1/2/3). «Серво ON» как кнопки в виджете нет, поэтому К6 («любая другая кнопка») проверена только на «Стоп: домой».
6. Как `reason` приходит при failed: отдельным листом `.park.reason` до `.park.state` или после — не указано. Я пушу reason раньше state (и вариант целым узлом).

## Что оставил открытым / ненадёжно

- Реализации нет: тесты ни разу не выполнялись против рабочего кода. Красные по К2–К10 падают на самом первом обращении (`park_requested` / `_on_park_push`), поэтому их финальные assert-строки не исполнялись. Корректность моделей ожидаемого (последовательности дельт, тексты) подтверждена только чтением, не прогоном. После реализации возможны ложные красные из-за моей модели, и вызывать их разбирать надо по assert, а не по типу ошибки.
- Over-spec, который я допустил: К12 требует, чтобы новые кнопки имели того же `parentWidget()`, что и `_btn_stop1` («в ряду стопов»). Если реализация положит их в другой контейнер, тест красный при верном поведении.
- К9: помимо `seq=3` и `state=done` я добавил лист `home=moved` (в брифе его нет), чтобы итог был однозначным. Без `home` ожидаемый текст по брифу тот же, но эта ветка не проверена.
- К5: проверен только сценарий «seq=0 + home + state=done после запомненного seq=1». Сценарий «state=done без seq-листа вообще» не покрыт: бриф его не определяет.
- К3: промежуточный статус после `seq`/`home` до `state=done` не проверяю (не следует из критериев).
- Порядок «state=failed раньше reason» не покрыт.
- on_result вызывается в тестах прямо в потоке теста; если реализация маршалит ответ через очередь Qt, ждём `qtbot.waitUntil` (1 с) — для позитивных проверок. Негативные («статус не меняется») проверяются после `processEvents()`, их слабость: сигнал из другого потока с задержкой они бы не поймали.
- Break-injection не выполнялся (нет реализации); зелёное без инъекций ничего не доказывает — это для стадии после реализации.
- Таймаут-ветки, смена устройства (`set_device` на другое при висящем park), ответ force_stop с ошибкой, гонка двух park подряд — вне критериев, не покрыты.
- Прогон-проба (не чтение исходников): я запускал текущие виджет/контроллер, чтобы увидеть тексты кнопок и вид `bind_fanout`; исходные файлы запрещённых путей не открывались.

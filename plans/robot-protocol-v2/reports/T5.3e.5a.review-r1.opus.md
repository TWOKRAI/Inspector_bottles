### M1 — [T5.3e.5a.md:53] [architecture] (ii) — проверка `not_v2` через `getattr` на драйвере ломает сторож SPI.b2

**Вход:** DESIGN 5a1 п.3 набран как написан: в `manager.py` `drv = self.get_driver(id)`, затем
`not callable(getattr(drv, "park_wait", None))`.
**Вывод по чтению:** `Services/device_hub/tests/test_spi_contract.py:649-653` `test_no_duck_typing_on_drivers` —
красный: `_DUCK_FILES` (`:530`) содержит `manager.py`, `_DUCK_FUNCS = {getattr, hasattr}` (`:529`), а имя,
связанное с вызовом `get_driver`, — получатель (`:522-526`). Ожидание: `found == {rel: []}`, факт — один сайт в
`robot_park_all`. Это и инвариант модуля: ADR-DH-012 (`Services/device_hub/DECISIONS.md:137`) — менеджер зовёт
контракт драйвера напрямую (способность — флагом SPI, как `stop_aware`, `spi.py:112, 145`), без duck typing.
**Почему не видно сразу:** TESTS 5a1 (`T5.3e.5a.md:103-105`) — `light` по 4 файлам, `test_spi_contract.py` в нём
нет; радиус `medium` по `Services/device_hub/tests` стоит только у 5a2. 5a1 придёт зелёным, красный всплывёт в 5a2
на чужом файле.
**Исправить:** решение лида, одно из двух: (а) признак v2 — из записи реестра, не из драйвера:
`entry.protocol != "delta_v2"` → `skipped/not_v2` (`entry` уже есть в обходе `snapshot_registry()`, `spi.py` не
меняется); (б) флаг SPI по образцу `stop_aware` (`ClassVar[bool]` в `DeviceDriver`, умолчание в `BaseDeviceDriver`)
— тогда снять запрет «`spi.py` не менять» (п.4) и проверить счёт SPI в 5l. В TESTS 5a1 добавить
`Services/device_hub/tests/test_spi_contract.py`.

### M2 — [T5.3e.5a.md:54-56, 107-108] [spec] Senior+ сроки — фаза отправки `robot_park` не ограничена сроком и не смотрит `should_stop`

**Факт кода:** `_op_park` при держащемся jog (`ops.py:151-157`) делает `_close_thread(handle, _LEASE_JOIN_S)`
(`texts.py:96`: 1,0 с), затем `_stop_jog(run)` → `_stop_and_wait(SOFT)` (`jog.py:133`) с ожиданием эха до
`soft_echo_timeout_s` (`client_v2.py:172`: 2,0 с). Итого до ~3,0 с на одного робота. Утверждение OUT OF SCOPE
«отправка последовательна, каждая ≤ 1,0 с» (`:108`) этим кодом не подтверждается.
**Вход → вывод (по чтению):**
1. Два робота, у первого держится jog без эха; `timeout_s 30`. Отправка ≈ 3 с; `accept` второго — в `t0 + 3`; его
   срок park кончается в `t0 + 33` (+ тик), а ожидание — в `t0 + 31,5` (`:60`) → у второго `timeout` вместо
   `failed/срок вышел`, хотя его park сам закрылся бы через 1,5 с.
2. Хук `request_stop` приходит, пока первый робот в `_stop_and_wait`: цикл отправки `should_stop()` не читает
   (проверка есть только при входе, `:49`, и в цикле ожидания, `:62`). Ответ ≈ остаток отправки + ожидание → больше
   1,0 с после хука — нарушен Goal (`:13-14`) и ACCEPTANCE (`:125`). Плюс поток стопа того же робота ждёт
   `_jog_tx_lock` (`stop.py:52`), пока `_stop_jog` его держит.
**Исправить:** (1) в цикле отправки перед каждым `robot_park` — `should_stop()` истинно → оставшимся роботам `R`
без вызова (например, `{"result": "skipped", "reason": "stopping"}` — литерал в форме ответа) и сразу к ожиданию с
`deadline = now + 0.5`; (2) в OUT OF SCOPE заменить «≤ 1,0 с» на верхнюю оценку по коду (`_LEASE_JOIN_S +
soft_echo_timeout_s` ≈ 3,0 с при держащемся jog) и записать следствие (1) в «Открыто» или считать срок ожидания
робота от момента его допуска (`max(t0 + t + 1.5, t_accept_k + t + 1.5)` с общим потолком `t0 + 33.5`) — решение
лида. Хазард-тест автора: поддельный `call("park")`, который держит 1,5 с, и `should_stop` истинно через 0,3 с →
ответ ≤ 1,0 с после `should_stop` (без этой правки — около 1,5 с + 0,5 с).

### M3 — [T5.3e.5a.md:95-96, 147-148] [tests] два REDS зелёные при своих инъекциях (A-5, A-6)

**Механизм:** `Condition.wait_for(pred, timeout)` по истечении срока возвращает `pred()`; а `wait(timeout)` с
последующим `self._terminals.get(seq)` находит уже записанный итог. Итог в словаре есть — ответ верный, только
поздний.
**Вход → вывод (по чтению):**
- A-6 «`wait_terminal` без проверки уже записанного (только `wait`)»: реализация `self._done.wait(t); return
  copy(self._terminals.get(seq))`. Терминал `seq 1` записан до вызова → `wait` спит весь срок среза 0,2 с
  (`:60-61`) → возвращает итог → `R == done`. `test_terminal_before_wait_not_lost` («→ `done`», `:95`) зелёный.
- A-5, вариант «`notify_all` после `publish`» (запись итога — до): `publish` бросает → `notify_all` не позван →
  `wait_for` просыпается по сроку среза → предикат истинен → итог отдан. `test_terminal_kept_when_publish_raises`
  (`:96`) зелёный. Красный только у варианта «запись после `publish`».
**Исправить:** в обоих REDS звать `park_wait(seq, 5.0)` прямо (не через срез 0,2 менеджера) в daemon-потоке и
проверять время возврата литералом: `≤ 0,1 с`. В A-5 развести два мутанта: «запись после `publish`» и
«`notify_all` после `publish`» — оба должны дать красный этих тестов.

### M4 — [T5.3e.5a.md:6-8, 115-128] [spec] (a), (d) — у слепого тестера нет поверхности вызова

### m1 — [T5.3e.5a.md:60-63] [spec] место проверки `should_stop` в цикле ожидания не задано

**Вход → вывод (по чтению):** если `should_stop()` проверяется раз за проход по всем ждущим, проход длится до
`N × 0,2` с. Три робота без терминала, хук в момент `T` → обнаружение до `T + 0,6`, срок `T + 1,1` → ответ позже
1,0 с после хука (Goal `:13-14`). При проверке перед каждым `park_wait` — ≤ `T + 0,2 + 0,5`. REDS
`test_should_stop_ends_wait_quickly` (`:93-94`) с одним роботом этого не различает.
**Исправить:** в DESIGN — «`should_stop()` — перед каждым `park_wait`»; в REDS — вариант с тремя поддельными
роботами, ответ ≤ 0,3 + 0,5 + 0,2 с.

### m2 — [T5.3e.5a.md:62-63, 125-126] [spec] (a) — `failed` после хука гарантирован только при быстрой записи стопа

**Факт:** терминал `failed` ставит `abort(TEXT_STOPPING, stop=True)` после `_process_stop` (`stop.py:52-65`):
сначала `_jog_tx_lock.acquire(timeout=остаток)`, затем запись с бюджетом `timeout_sec * (retries + 1)`
(`stop.py:113-116`, умолчание 2,0 с). Окно менеджера после `should_stop` — 0,5 с.
**Вход → вывод:** связь медленная (запись стопа 1,0 с) → к `T + 0,5` терминала нет → `R == timeout`, а
ACCEPTANCE требует `failed`. На sim запись — миллисекунды, поэтому стенд P5 это не покажет.
**Исправить:** в строке ACCEPTANCE — предусловие «стоп записан роботу за ≤ 0,5 с (связь жива)», иначе
`timeout`; число 0,5 обосновать (см. m5).

### m3 — [T5.3e.5a.md:52-54, 112] [quality] гонка: ожидание на `drv`, а `park` уходит через `self.call(id, …)`

**Факт:** `DeviceManager.call` (`manager.py:510-528`) заново берёт драйвер `get_driver(dev_id)`.
**Вход → вывод:** `device_upsert` того же id между `drv = self.get_driver(id)` и `self.call(...)` → `park` и `seq`
— у нового драйвера, `park_wait` — у старого `ParkMachine` → `R == timeout` при выполненном park. Кроме того, TRAPS
(`:112`) пишет «`drv.call` не держать под замком», а DESIGN — `self.call`: два чтения.
**Исправить:** `drv.call("park", {"timeout_s": float(t)})` на том же объекте (проверка подключения уже сделана
выше); TRAPS и DESIGN привести к одному имени.

### m4 — [T5.3e.5a.md:53, 123] [spec] (a) — порядок причин `skipped` не в ACCEPTANCE

**Вход → вывод:** DESIGN проверяет `not_connected` раньше `not_v2`. Слепой тестер берёт неподключённый робот v1 и
ждёт `not_v2` (строка `:123` не говорит, что v1 подключён) → `not_connected`, красный по неверной причине.
**Исправить:** в ACCEPTANCE: «робот v1 подключён → `not_v2`; любой неподключённый → `not_connected` (раньше
`not_v2`)».

### M-2. T5.3e.1, D4/D5: порядок `accept` / release / SOFT и `_finish` без `seq` — три гонки
`_finish(ok, reason)` и `abort(reason)` (D5) не получают `seq`, сравнивают с `self._seq`, которое пишет `accept()`.
1. **Тик стартует ход домой раньше SOFT.** D4: `park_begin` → `accept` → release → `prog_soft` SOFT. После `accept` автомат активен.
   Чередование: поток команды между `park_begin` и записью SOFT программе (`prog_soft = True`, последний ход пользовательской
   программы). Программа кончается сама (`program_finished`), тик: `activity` пуст → `idle` → `home` → `launch_home(seq)`;
   `admit_launch(kind="park")` пропускает. Поток команды дописывает SOFT уже в `park_home`. Что именно сделает SOFT на последней записи
   одного хода — спека утверждает «ничего не меняет» (D5, последний абзац), но чтением `run_chunks` это не показано.
   Худший исход — `park_home` `aborted` → park `failed` («ход домой прерван»), серво ON.
2. **Устаревший финишер закрывает чужой seq.** Тик в `servo_off()` (ввод-вывод вне `_lock`, D5 «Ловушки») для seq=1. Параллельно
   `abort` (сбой `disconnect`/команды) → `failed` seq=1, оператор тут же шлёт `robot_park` → `park_begin` (seq=2) → `accept(2)`.
   Тик возвращается из `servo_off()` → `_finish(True, None)` читает `self._seq == 2` → `park_end(2, True)` выигрывает → seq=2 закрыт как `done`,
   очереди сняты, `_parked = True`, а робот ещё не едет домой. Окно — длительность записи Modbus (до `res_timeout_s`).
3. **`abort` до `accept` ничего не закрывает.** Если исправить п. 1 порядком «release/SOFT → `accept`», то исключение в release вызывает
   `abort` при `_seq` от прошлого park → `park_end` не совпал → `_parking` остаётся True (тот же вечный отказ, что в M-1).
- **Фикс.** `step()` фиксирует `seq` на входе и зовёт `_finish(seq, ok, reason)`; `abort(seq, reason)`; `_op_park` вызывает
  `accept` после release/SOFT, а исключение до `accept` закрывает путь `ParkMachine.fail_unaccepted(seq, reason)` (`park_end` + одна
  публикация `failed`). Добавить hazard-тест автора `test_stale_finisher_does_not_close_new_park` (шов: `servo_off` ждёт `Event`,
  пока тест не выполнит `abort` + новый park).

### 2. Вопросы менеджера
- **а) Одна запись серво после `_shutdown` — совместима ли с D3?** Да, при двух условиях. Сценарий: тик прошёл `guard` до `_shutdown`, ушёл в `servo_off()` (`client.servo(False)`),
  `request_stop` параллельно пишет SOFT. Запись `STOP_REQ` идёт мимо замка mailbox клиента (докстрока `driver.py` «Потоки»: `stop` / `kick_heartbeat` / `jog_lease` нарочно минуют замок), а серво — через mailbox;
  значит аварийный стоп серво не ждёт. Серво OFF после SOFT безопасно (робот стоит). Условия: (1) `request_stop` не ждёт поток тика и не берёт `ParkMachine._lock` на ввод-вывод (m-2);
  (2) эхо SOFT при серво OFF не даёт ложного health — спека сама держит это открытым (`T5.3e.md:247`), L1–L3 проверят. В D7 оговорить: «≤ 1 записи» относится к регистру `SERVO`, не к `STOP_REQ`.
- **б) Обычный `disconnect` ждёт ход домой до 5 с; длиннее — выживший.** Приемлемо как поведение, дыры нет, но не бесплатно. Путь: `abort` → `_request_stop(SOFT)`; программа `park_home` жива → `_stop_and_wait(SOFT)`
  ждёт эхо (SOFT посреди хода — до прибытия, `server/README.md:12`) до `soft_echo_timeout_s`; затем `_close_thread(prog, _PROGRAM_JOIN_S = 5.0)` (`driver.py:441`); дальше транспорт закрывается под живым
  потоком программы — её следующая запись падает, `.program` получает `failed`, `TEXT_THREAD_SURVIVED` идёт в `last_error`. Робот доезжает до дома сам (ход уже в регистрах), SOFT останавливает его там,
  сторож HB_PC — при тишине. Итог: физически безопасно, но `.park` = `failed` («идёт отключение робота») при реально дошедшем роботе. Фикс: записать в «Открытое» (m-13), кода не добавлять; нужен замер хода домой
  из дальней точки сима (ноги ≈ 3,1 с, `test_robot_v2_scope.py:547`) — если ход длиннее ~5 с, выживший будет стабильным, а не редким.
- **в) План тестов осуществим?** Да, с поправкой M-4: `FakeClock` есть в `Services/device_hub/tests/conftest.py`, рекордер — свой `_Rec`; нужен реальный `_until` на ход домой; А13 и А15 требуют швов (m-10).

### 3. Приёмка владельца: на стенде v2 выключение идёт без SOFT поводка
- **Механизм есть.** `park_begin` помечает release в секции замка до ответа; поток поводка выходит по `"released"` (`state.py:742–743`), SOFT release пишет `_op_park`; `jog_hold` после этого получает
  `_PARKING` / `_PARKED` и окно не продлевает; `process.stop` застаёт простой робот: `_process_stop` пишет один SOFT простому подключённому (`state.py:446–447`; защёлка сброшена первым `request_stop_begin`,
  `:405–407`) → `d1 == 2`, `L1 == A1 == E1 == 0`.
- **Условие.** Park должен быть `done` до `process.stop`; иначе путь аварийного стопа прежний (спека это говорит). Окно, где SOFT поводка остаётся, — m-3.
- **Литералы L1–L3.** `d1 == 2`, `L1 == 0`, `A1 == 0`, `E1 == 0`, `& 3 == 1`, `jog_hold` после ответа ≥ 3 и `ok` — 0, `home == "moved"` ≤ 30 с, `home == "already"` ≤ 1,5 с (0,5 с тик + длительность тика + запас —
  записано числом), дедлайны 20 с / 40 с, шаг 0,05 с — числа. Замечания: «ответ ≤ 0,5 с» — m-6; определение счёта `L1` / `A1` / `E1` / `d1` лежит в `test_robot_v2_live_backend.py:448–522` (RED 16), не в amend (m-14);
  `d1 == 2` верно, только если SOFT release и SOFT выключения — две разные записи; чтение `process_stop_plan` это подтверждает (защёлка сброшена), пусть L1 проверит первой красной.

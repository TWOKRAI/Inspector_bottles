## DESIGN

Сейчас единственный вызывающий `push_if_paused_changed` — воркер `readiness_snapshot` (`process_module.py:1130-1142`, период 0,5 с); сообщение строит тот же `_send_heartbeat_locked`, что и регулярный (`status`, `pid`, `workers_status` без `metrics`, `readiness` — `deepcopy` снимка `ready`/`reasons`/`paused`/`at`).

1. Переименовать `push_if_paused_changed` → `push_if_changed`; вызывающий и лог («при смене paused» → «при смене готовности») — по новому имени. Подпись «ушедшего» `(paused, ready, frozenset((r["node"], r["severity"]) for r in reasons if r["severity"] in READINESS_BLOCKING_SEVERITIES))`; push шлётся, когда подпись текущего снимка ≠ подпись реально ушедшего.
2. Подпись «ушедшего» берётся из КОПИИ, реально ушедшей, внутри `_send_heartbeat_locked` в существующем `try` (`process_heartbeat.py:445-456`), а не из снимка, сравнённого до замка (`:383`) — иначе гонка между сравнением и отправкой. Её обновляют и регулярный, и внеочередной heartbeat (`_last_sent_sig`), иначе после регулярного уйдёт дубль. Подпись пишется ТОЛЬКО после успешной отправки (`_last_sent_paused` сегодня тоже пишется после `send_message`, `process_heartbeat.py:454-456`): запись до отправки пометит неудавшийся heartbeat «ушедшим», и смена потеряется.
3. Расчёт подписи — ВНУТРИ `try`: битая причина (нет ключей) не должна съесть регулярный liveness-heartbeat (PM объявит процесс `unresponsive`). Доступ — `.get("node")`/`.get("severity")`, не `[...]`.
4. `at` и `stale_after_s` в подпись НЕ входят (иначе постоянный поток ~2 сообщения/с: антидребезг его не гасит). Тексты причин и `out_of_spec`/`maintenance` не входят: в листе PM они отстают до ~5,5 с — это решение, фиксируется в ADR.
5. `ready` в подписи нужен отдельно от причин: защёлка boot даёт `False -> True` без причин (`process_module.py:1163-1167`).
6. Константа `READINESS_BLOCKING_SEVERITIES` — из `process_module/health/schema.py:128` (тот же пакет). Копия в `process_manager_module/process/run_state.py:44` — PM; импорт оттуда — обратная зависимость слоя. Импорт на уровне модуля; проверить отсутствие цикла (открытый дефект очереди `2026-11-16_run-state-stand110_1`: `_DeadlockError` на ленивых импортах heartbeat).
7. Первый снимок (`None` до него) сменой не считается. Решение и причина: boot-смена `ready False -> True` доезжает best-effort — если первый регулярный heartbeat ушёл без `readiness` (порядок не гарантирован, `reports/1.2.developer.md:200`), push по `None` не шлёт, смену донесёт следующий регулярный (≤ ~5 с). Принято, чтобы не плодить push на старте.
8. Антидребезг прежний: `_PUSH_MIN_INTERVAL_SEC = 0.5` под `_send_lock`, подавленная смена не теряется. Регулярный heartbeat расписание не меняет; push `_last_heartbeat_sent` НЕ двигает.
9. Лог: сбой расчёта подписи вне замка — ERROR ОДИН РАЗ на тип исключения (серия); в логе только тип исключения, без значений причин и текста плагина.
10. Контракт для 3.4/3.6: `stale_after_s` не входит в подпись; push строится ТЕМ ЖЕ построителем сообщения, форка формата нет (иначе `pid`/`incarnation` не доедут и `_admit_heartbeat` отбросит). Тест «ключи push == ключи регулярного».

## Риск

Шторм: ограничен дважды — воркером снимка (~2 Гц) и антидребезгом; при `at` вне подписи ≈ 2 сообщения/с на процесс в худшем случае.
**Риск «fault на ходу» (НОВЫЙ, решение владельца):** `transition(running, tick, ready=False)` даёт `fault` без гистерезиса, `fault` липкий, выход только `ack`. Раньше PM видел срез раз в ~5 с, и короткие провалы плагина часто не доходили. После 3.3 любой провал длиннее ~0,5 с дойдёт и положит `running`. Какие реальные плагины мигают `not_ready` на ходу — не проверено. Решение владельца: принять (честная авария) или гистерезис в PM (отдельная задача). Обязателен soak `running` 10 мин на стенде: число переходов `running -> fault` до и после; ожидание 0 и 0.

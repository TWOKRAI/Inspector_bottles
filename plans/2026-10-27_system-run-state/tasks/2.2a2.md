Невышедший поток -> инцидент `device_hub.scope` (Ф12) — ПРИНЯТОЕ последствие, как у `request_stop_all`. Секции `_pause_lock` без IO. Робот + лента: ОСТАНОВИТЬ -> `stop` ленты не позже 0,5 с от команды при любой длительности ответа робота (лог драйвера) — на прямом ПЧ; ОТДЕЛЬНО на мосте `gd20_bridge` (носитель v1, Ф11): число пишется как есть, превышение 0,5 с — вопрос владельцу (общий транспорт), не провал среза. Повтор `pause` при отказе ленты не шлёт команду роботу (счётчик драйвера). Команда робота дольше 1,5 с -> `RuntimeError` и инцидент `device_hub.scope` в health (принято). Замер для порога: по счётчику `ts` в `devices.state.<id>.conn` — наибольший промежуток между тактами v2 и ПЧ за 10 мин `running` (soak 2.2a); `conn_stale_s` = 3 × этот промежуток, но не меньше 2,0 с, — в рецепт (YAML). Кабель робота v2 в `running`: `fault` не позже 1,5 с при обнаруженном обрыве; при `tick`, бросающем с живой связью, — не позже `3 × poll_interval_s + 1,0 с`; при висящем такте — не позже `conn_stale_s + 1,0 с`, только если порог задан. Уровень стопа меняется YAML `params.pause_action` без правки кода.

### Что осталось открытым / ненадёжно

- Код не написан; запуском подтверждены только опыты B1–B4 (Ф1) и базовая линия тестов (ревьюер: `2 failed, 61 passed`). Пп. 4, 7, 9 DESIGN и Ф9, Ф12 — по чтению кода.
- Висящий такт при выключенном пороге не ловится: первый запуск без `conn_stale_s` в рецепте защищён только от обрыва и от ≥ 3 исключений подряд. Варианты на решение лида после замера: (в) исключать «законно блокирующий» такт v1 по публичному `driver.busy` (`robot_driver.py:168-176`) и включить порог для v1; (г) консервативный `conn_stale_s` 30 с для v2 и ПЧ в рецепт первого запуска (строка YAML), замер потом ужесточает.
- Мост ПЧ: `abort` v1 и `stop` ПЧ сериализуются `RLock` носителя (Ф11) — выигрыш параллельного обхода на мосте ограничен длительностью транзакции робота; поведение под нагрузкой не измерено. Потокобезопасность `call` v2 параллельно `tick` не читалась (логику не меняем).
- Поздний успех команды (после срока) не помечает устройство остановленным: следующий повтор шлёт ей стоп ещё раз — принято (не чаще раза в 1 с, только неподтверждённым).
- `worker.pause_all` останавливает такты -> при заданном пороге — «нет обновления связи»; так задумано (устройство не опрашивается), оператору может быть неожиданно.
- Аргументы `params.pause_action` проверяет драйвер, и не всякий: v2 на `level: "FOO"` -> ответ `error` -> `RuntimeError`, а v1 `_op_abort` берёт любой `int` (`robot_driver.py:601-604`; `{"op": "abort", "args": {"mode": 1}}` повезёт робота «домой»). Решение лида: пока рецепты `params.pause_action` не переопределяют — умолчание класса; проверка аргументов (допустимый набор по `op`) — вопрос владельцу. Набор `PAUSE_OPS = {stop, abort}` — дополнение manager к правилу `immediate=True` (Ф10: `park`, `jog_hold` тоже `immediate`), лиду подтвердить.
- Хвост ветки `except` такта (`health`, `_publish_state(last_error)`, `_set_conn`) сам не защищён: сбой публикации завершит поток воркера — на HEAD так же (`:693-695`), вне задачи.
- Hazard 2.2a RED 11 при бюджете 1,5 с держится на окне `entered -> release` < 1,5 с — на загруженной машине возможен ложный красный (Б5 измеряет).

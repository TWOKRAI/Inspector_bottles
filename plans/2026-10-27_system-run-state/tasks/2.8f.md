## DESIGN (решено лидом — исполнитель переносит, не выводит)

Один механизм в одном месте: `GuiStateBindings` собирает узел сам. Потребители не меняют ни шаблоны, ни колбэки.

1. **Маркер конца пачки.** `GuiProcess._on_state_deltas_to_bridge` (`frontend/process.py`) после цикла по дельтам, если пачка не пуста, один раз зовёт `bridge.dispatch(state_batch_end_message())`. Константа `STATE_BATCH_END = "state_batch_end"` и сборщик — в `frontend/state/delta_message.py`. В `bridge_impl.py` этот `data_type` идёт в kind `"state"` (та же очередь Qt, поэтому маркер приходит после всех дельт пачки).
2. **Только `bind_fanout` и только шаблоны без `**`.** `bind()` (виджет + свойство) не меняется: сегодня он на узле не получает ничего, и получить dict в setter он не должен.
3. **Грязные узлы.** Дельта с путём D, не совпавшая с шаблоном P целиком, но у которой `len(D) > len(P)` по сегментам и префикс `N = D[:len(P)]` матчит P, помечает пару (handle, N). Повторные дельты того же узла в пачке пару не дублируют. Порядок пар — порядок первой пометки.
4. **Точное совпадение пути** (`set` целого узла, delete узла) — как сейчас, сразу, и **снимает уже помеченную пару (handle, D)**: иначе `[лист, set узла]` даёт два одинаковых вызова. Листовая дельта ПОСЛЕ точной помечает узел заново.
5. **На маркере:** на каждую пару один вызов `callback(N, read_model.get_node(N, DELETED))` (`telemetry_view_model.py`, `get_node`; без второго аргумента вместо `DELETED` придёт `None`; протокол `_ReadModelLike` в `bindings.py` дополнить `get_node`). Узла в read-model нет — придёт `DELETED`. Перед вызовами набор грязных пар забирается и очищается (дельты, пришедшие из колбэка, копятся для следующего маркера). Снятый хэндл (`unbind_fanout`, destroyed владельца, `clear`) не вызывается. Исключение одного колбэка не мешает остальным (тот же `try/except`, что у прямого fan-out).
6. **Порядок с read-model.** Листовая дельта сначала идёт в bindings, потом в VM (`app.py`, не меняется): внутри обработки дельты VM отстаёт на неё. Поэтому узел читается ТОЛЬКО на маркере.
7. `read_model is None` — узловой доставки нет (поведение как сегодня).
   **Принятое расхождение с сервером:** read-model хранит только листья. Удалены все листья узла (на сервере узел `{}`) — подписчик получает `DELETED`; пустой вложенный словарь (`params: {}`) из узла пропадает.
8. **VFD-хэндл.** `vfd/controller.py` сохраняет хэндл своего `bind_fanout` и снимает его в `_unbind_state` (образец — `robot/controller.py`, `_fanout_handles`). Хэндл fanout снимается ТОЛЬКО через `unbind_fanout` и в `_status_handles` не кладётся: `unbind(fanout_handle)` молча ничего не делает. Без этого после смены устройства на виджет пойдут живые данные чужого устройства.

## REDS (слепой tester; ожидания — литералы)

1. Четыре листовые дельты `devices.state.vfd1.status.{a,b,c,d}` и маркер: ровно один вызов `("devices.state.vfd1.status", {все четыре значения})`; до маркера вызовов нет.
2. Шаблон `devices.registry.*`: пачка с листьями двух устройств — по одному вызову на устройство, в порядке первой дельты.
3. Два подписчика одного узла — оба получают.
4. Удалён один лист — узел без этого ключа; удалены все листья — `DELETED`, один вызов.
5. `[лист, точный set узла]` + маркер — 1 вызов. `[точный set, лист]` + маркер — 2 вызова, во втором слитый узел. `[лист, delete узла]` + маркер — один `DELETED`.
6. Снятие: `unbind_fanout` между дельтой и маркером — вызова нет; колбэк первой пары снимает второй хэндл (отдельно — зовёт `clear()`) во время flush — второго вызова нет.
7. Колбэк первого подписчика бросает — второй получает. Дельта, поданная из колбэка, приходит только на следующем маркере.
8. Маркер без грязных узлов — ничего. `bind()` на узле и шаблон с `**` — поведение прежнее (литералом, что приходит сегодня). `read_model=None` — 0 вызовов узлу.
9. Лист на глубине N+2 (`...status.pose.x`) — узел с вложенным словарём `{"pose": {"x": ...}}`.
10. Проводка настоящих объектов, только так: `GuiProcess._on_state_deltas_to_bridge(SimpleNamespace(_bridge=bridge), deltas)` из НЕ главного потока, две пачки поставлены в очередь до `processEvents`; подписчик узла получает два вызова, в первом значения первой пачки или новее, во втором — второй (ожидание с дедлайном). Маркер тест сам НЕ шлёт.
11. VFD с настоящим `GuiStateBindings` и read-model: после `set_device("old")` -> `set_device("new")` (а) лист `devices.state.old.status.x` + маркер -> 0 вызовов `set_status`; (б) точный `set` `devices.state.old.status` -> 0 вызовов `set_status`.

## Риск (принят)

Стартовый replay потерян — узел в read-model неполный: после одной листовой дельты придёт, например, `{"enabled": False}` без `kind`, и `combo._on_registry_delta` уберёт устройство из списка (сегодня комбо просто не обновляется). Исполнитель проверяет этот вход на комбо и, если так и есть, предлагает лиду правку — молча не чинит.

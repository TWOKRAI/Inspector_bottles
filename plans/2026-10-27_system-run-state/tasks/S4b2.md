## Факт

Тесты `Plugins/hub/device_hub/tests/test_readiness_pause_v2_hazards.py` (`test_b8_*`, `_fail_scene`) гоняют `tick_fails_limit` на ДВОЙНИКЕ драйвера (`Steps(["raise", …])`). Настоящий `RobotDriverV2.tick` (`Services/device_hub/drivers/robot_driver_v2/driver.py` ~548-595) оборачивает в `try` пульс, чтение TLM и `poll_errors`; `self._park.step(...)` и `self._dispatch(...)` (~591-592) — вне `try`.
**Честная граница теста:** при чтении кода пути исключения из этих двух строк без подмены не найдено (`ParkMachine.step` по контракту «не бросает», `park.py:188`, внутри `except Exception → _on_error`; `_run_next_job` ловит `except Exception`, `jobs.py`). Ревью стадии 5 нашло кандидата: сбой публикатора в `except`-ветках `_run_next_job` (`_publish_error` → `_pub` вне `try`, `driver.py:639`) — воспроизведён на уровне драйвера, на боевом публикаторе hub не проверен (`OPEN_QUESTIONS` 2026-11-21). Тест доказывает «воркер hub переживает ЛЮБОЕ исключение из `RobotDriverV2.tick` и считает подряд по `tick_fails_limit`», а не живой сценарий. Так и называть в докстроке и отчёте.
Кто что пишет (проверено ревьюером запуском): счётчик подряд — локальная `fails` в `tick_loop` плагина (наблюдаем только через `conn`); `tick_fails_limit` читает ПЛАГИН (`plugin.py:691-696`, `drv.entry.params`, один раз при старте воркера), драйвер ключ не использует; `last_error` и `conn` пишет воркер плагина.

## DESIGN

Файл теста собирает НАСТОЯЩИЕ объекты, без `make_scene` (его фабрика берёт двойники по `_CLASS_BY_PROTOCOL`, `Scene.close()` зовёт `cmd_gate` у драйверов из `Scene.drivers`):
- свой фикстур: `make_ctx` + настоящий `DeviceHubPlugin` (`configure`, `start`), запись устройства `protocol: delta_v2`;
- транспорт: `plugin._manager.set_driver_options("robot", "delta_v2", transport=FakeRobotTransport(RobotSimCoreV2()))` — ДО подключения (драйвер создаётся лениво); именно `RobotSimCoreV2`: `sim_core`/`fake_transport` из conftest плагина построены на v1-ядре и дают `WrongFirmware`/`conn disconnected`;
- подключение: `cmd_device_connect` + `_process_conn_queue`; драйвер брать `plugin._manager.get_driver(id)`; в `Scene.drivers` НЕ класть; `Scene(plugin, ctx, ids=[...])` с пустым `drivers` переиспользует `start_worker`, `readiness`, `wait_readiness`, `last_conn_record`, `close`; `Scene`, `until`, `bounded`, `_LINK_ERROR` — импорт из `test_readiness_pause_v2` (приём `test_readiness_pause_v2_hazards.py:23-34`); клиент не подменять (`RobotClientV2` на `FakeRobotTransport` — достаточно);
- инъекция: `drv._dispatch = wrapper` / `drv._park.step = wrapper` на экземпляре; обёртка принимает `*a, **k` (`_dispatch(client, free, stop_event)`, `_park.step(telemetry, free)`), для исхода «ок» ДЕЛЕГИРУЕТ исходному методу, сохранённому до подмены (иначе «настоящий драйвер» работает только до `_park.step`); один список исходов на сцену; каждый шаг ждёт ВХОДА воркера в следующий такт (как `Steps.step`) — иначе умерший воркер незаметен (без `conn_stale_s` `readiness` остаётся `[]` навсегда); дедлайны ожидания ограничены, потоки daemon, `join` с дедлайном.
Если тест краснеет на продуктовом коде — это находка: не править `plugin.py`/драйвер (владелец Р2), вернуть лиду «вход → наблюдение».

Гипотезу «квант опроса PM ≈ 0,5 с» НЕ писать: опровергнута кодом (`process_manager_process.py:204` `_STOP_POLL_S = 0.05`, `_wait_all_paused` спит `min(_STOP_POLL_S, remaining)` ~2163). ## REDS (ожидаются ЗЕЛЁНЫМИ; красный = продуктовая находка)

0. Предусловие: прямой `drv.tick()` из потока теста с подменённым `_dispatch` (и отдельно `_park.step`) БРОСАЕТ `RuntimeError`. Если Р2 обернёт строки 591-592 в `try`, 0 краснеет — сигнал «дефект драйвера починен, тест устарел», а не дефект воркера.
1. Одна сцена, исходы `[бросок, ок, бросок, бросок, ок]` (подмена `_dispatch`): после каждого шага `sc.readiness() == []`, `last_conn_record()["conn"] == "connected"`, `drv.is_connected is True`; в конце поток воркера жив.
2. `_dispatch`: `[бросок, бросок, бросок]` при `is_connected is True` → после ТРЕТЬЕГО: `sc.readiness() == _LINK_ERROR` и `last_conn_record()["conn"] == "error"` (поле `ts` не утверждать); после первого и второго `readiness == []`. `ctx.health.report_error` вызван на каждом броске: `kwargs["context"] == "device_hub.tick.<id>"`, `args[0]` — `RuntimeError` (контекст НЕ равен `device_hub.tick`). `last_error`: `state_proxy.merge("devices.state.<id>.last_error", "<текст исключения>")`, читать `merge.call_args_list` (пишется на КАЖДОМ броске, включая первый, и не очищается после восстановления — зафиксировать).
3. То же для `_park.step`.
4. `[бросок, бросок, ок, бросок, бросок, бросок]`: `readiness == []` до последнего шага, `_LINK_ERROR` только на ТРЕТЬЕМ подряд после «ок» (хвост делает тест невакуумным).
5. `params.tick_fails_limit` рецепта доходит до воркера через `drv.entry.params`: лимит 1 → `_LINK_ERROR` с первого броска; 2 → не на первом, на втором; негодное (`0`, `"x"`) → умолчание 3 и РОВНО одна WARNING со словом `tick_fails_limit` в `ctx.log_warning`. 2–3 случая, не полный parametrize.
6. После снятия подмены следующий успешный такт возвращает `conn == "connected"`, `readiness == []`; поток воркера жив.

## Break-injection (предсказания лида ДО прогона; патчи — в копии)

(а) счётчик подряд не сбрасывается успехом (копия `plugin.py`) → красны {1, 4} (в сцене 1 есть «бросок, ок, бросок, бросок»: без сброса счёт дойдёт до 3);
(б) порог игнорируется (сразу `error`) → красны {1, 2, 4, 5};
(в) `except` вокруг такта убран (копия `plugin.py`) → красны {2, 3, 4, 6}; REDS 1 краснеет, только если шаг ждёт входа в следующий такт или проверяет `is_alive()` (спека требует — значит {1, 2, 3, 4, 6});
(г) `try/except Exception: pass` вокруг `self._dispatch(...)` в копии `driver.py` → красен {0} и {2}; вокруг `_park.step` → {0} и {3};
(д) ветка успеха не публикует `_set_conn` (копия `plugin.py`) → красен {6}.

# Task S4b2 — `tick_fails_limit` на НАСТОЯЩЕМ драйвере v2: юнит-инъекция бросающего `_dispatch` / `_park.step`; допуск `run_stop_timeout_s`

Основание: ревью CTO 2026-11-20 §3 «S4b»: «юнит-инъекция сейчас, стенд в день №2; бросающий `_dispatch` вне `try` драйвера — задача без железа»; запись `docs/claude/OPEN_QUESTIONS.md` 2026-11-20 «S4b на сим-линии» п.(б). Допуск: CTO §3 «2.7 и 2.9 влиты без стенда» — «исправить допуск в спеке». Ветка — своя от main `dc56f14df`.

## Факт

Тесты `Plugins/hub/device_hub/tests/test_readiness_pause_v2_hazards.py` (`test_b8_*`, `_fail_scene`) гоняют `tick_fails_limit` на ДВОЙНИКЕ драйвера (`Steps(["raise", …])`). Настоящий `RobotDriverV2.tick` (`Services/device_hub/drivers/robot_driver_v2/driver.py` ~548-595) оборачивает в `try` пульс, чтение TLM и `poll_errors`, но `self._park.step(...)` и `self._dispatch(...)` (строки ~591-592) — вне `try`: исключение оттуда уходит в воркер hub. Стенд на сим-роботе (20.11) честно воспроизвести не смог: любой сбой сети превращается в `_link_lost`, а не в исключение. Правило «fake-harness suite needs one test that wires the real objects» — настоящих объектов у этого свойства нет.

## DESIGN

Тест (не продуктовый код) собирает НАСТОЯЩИЕ `RobotDriverV2` (с тестовым транспортом/двойником КЛИЕНТА уровня провода — как в тестах `Services/device_hub/drivers/robot_driver_v2/tests`, найти по `git grep`) и НАСТОЯЩИЙ воркер `DeviceHubPlugin` (`Plugins/hub/device_hub/plugin.py`, схема сцены `Scene` из `test_readiness_pause_v2.py`: допустимо подменить только `state_proxy`/`ctx`). Инъекция — подмена `driver._dispatch` (и отдельно `driver._park.step`) на бросающую (monkeypatch на экземпляре настоящего драйвера).
Ожидаемое поведение (по DECISIONS ADR-PH-004, `tick_fails_limit` = 3, связь жива): одиночное исключение и пара исключений подряд готовность НЕ снимают; три подряд — `conn = error` («ошибка связи»), узел `devices.<id>` перестаёт быть готовым; успешный такт между ними сбрасывает счётчик; поток воркера жив во всех случаях.
Если тест красный на продуктовом коде (воркер умер, счётчик не сработал, исключение улетело) — это дефект: чинить fix-forward в `plugin.py`/драйвере (владелец: Р2 — НЕ править, написать находку и вернуть лиду; PM-файл не трогать).
Вторая часть — допуск `run_stop_timeout_s` в `plans/2026-10-27_system-run-state/tasks/2.7.md` (строка ~120, ACCEPTANCE п.5): вместо «`run_status().since − t0 = 2,0 ± 0,5 с`» записать наблюдённое: «2,0 … 2,6 с (замер стенда 20.11: 8 прогонов 2,046…2,532 с, строго в ±0,5 — 4 из 8; квант опроса PM ≈ 0,5 с — гипотеза, не проверена)»; если какой-то тест с этим допуском есть в коде (`git grep -n "run_stop_timeout"` по тестам и `scripts/`) — перечислить в отчёте, не править без слова лида.

## REDS (акцептанс; красные ожидаются ТОЛЬКО если найден продуктовый дефект)

1. `_dispatch` бросает 1 раз, затем ок → `conn` остаётся `connected`, узел готов; 2 раза подряд, затем ок — то же.
2. `_dispatch` бросает 3 раза подряд при `is_connected == True` → `conn = error`, `last_error`/`health` по ADR-PH-004; ≥ 1 диагностика `device_hub.tick` в логе ctx.
3. То же для `_park.step`.
4. Успех между исключениями сбрасывает счётчик: «бросок, бросок, ок, бросок, бросок» → готов; «бросок, бросок, бросок» → не готов.
5. `tick_fails_limit: 1` и `2` из params рецепта доходят до драйвера (негодное — умолчание 3 и одна WARNING, как в `test_b8_*`).
6. Поток воркера жив после всех серий; снятая подмена возвращает `connected` на следующем успешном такте.

Break-injection (лид предскажет до прогона, патч на копии плагина): (а) счётчик не сбрасывается успехом → красен 4; (б) порог игнорируется (сразу `error`) → красны 1, 4; (в) `except` вокруг такта убран → красны 1–3; (г) подмена `_park.step` не покрыта (тест ходит только в `_dispatch`) → красен 3.

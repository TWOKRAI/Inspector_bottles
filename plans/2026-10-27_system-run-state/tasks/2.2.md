## DESIGN (лид; developer печатает, не выводит)

### 2.2a — `Plugins/hub/device_hub/plugin.py`

**П.1. Снимок соединений без замков и IO.** `_publish_state` для пути `devices.state.<id>.conn` дополнительно кладёт значение в `self._conn_snapshot` — НОВЫЙ dict на каждую запись (`self._conn_snapshot = {**self._conn_snapshot, id: conn_str}`; присваивание атомарно, читатели видят целый dict). Нестрочные/неконнектные пути снимок не меняют. `start()` сохраняет `self._recipe_ids: tuple[str, ...]` (id устройств рецепта) до запуска супервизора. Новые поля инициализируются в `__init__`.
**П.2. `readiness(ctx)`.** Для каждого `id` из `self._recipe_ids`, у которого `self._desired_connected.get(id)` истинно, и чей снимок `conn` не равен `"connected"` (нет записи — тоже «не подключено»), — запись `{"severity": "failure", "reason": f"{id} не подключено"}`; порядок — как в `_recipe_ids`. Устройства без желания подключения (`auto_connect false`) не перечисляются. Ничего не берёт: ни `_workers_lock`, ни `_registry_lock`, ни IO. Не бросает (при сбое — `[{"severity": "failure", "reason": "device_hub: состояние устройств недоступно"}]`). До первой публикации снимок пуст — все желаемые устройства «не подключено» (честно на boot). Значение `conn` для «подключено» уточняет стадия 0 по `:476-478` (какие строки публикуются при успехе).
**П.3. `pause(ctx)`.** Из потока `run_watch`, без `_shutting_down` и без защёлки выключения: для каждого устройства рецепта вида `robot` с протоколом `delta_v2` — операция `stop` с `level == PAUSE_STOP_LEVEL` (константа модуля, рабочее значение `"SOFT"`; вопрос владельцу — уровень SOFT/HALT, документ протокола робота; константу легко сменить); для вида `robot` v1 — операция `abort`; для вида `vfd` — операция `stop`. «Домой» (`park`) НЕ вызывается. Исключение на одном устройстве не мешает остальным (каждое в своём `try`, лог ERROR без значений); отсутствующее/неподключённое устройство пропускается молча. Вызов не должен блокировать `run_watch` дольше срока одной команды драйвера: путь и срок берутся у существующего механизма стопа (`request_stop_all_begin`/потоки области) — стадия 0 подтверждает, можно ли звать его без выставления `_shutting_down`; если нет — остановиться и вернуться к лиду, не изобретать второй путь.
**П.4. `resume(ctx)`** — no-op: движение и лента НЕ запускаются (лента — кнопкой пульта).
**П.5. Защёлка драйвера.** Вопрос стадии 0 (читать `robot_driver_v2/state.py:181-184, :519-523`): после `stop` из `pause()` принимает ли драйвер следующую команду движения (пульт/следующий `START`)? Если защёлка блокирует до connect — найти способ, не меняющий её семантики выключения (иначе — вопрос лиду); тест на симуляторе (`RobotSimCore` + `FakeRobotTransport`, `tests/conftest.py:104-115`).

### 2.2b — `Services/ml_inference/plugin/plugin.py`

# Task 1.8b: супервизор — новое воплощение процесса начинает с чистого статуса, смерть заменяемого воплощения не считается падением

- **Статус:** [PENDING] · **Level:** Senior · **Assignee:** developer (sonnet) <!-- lint-language: allow -->
- **Goal:** авто-рестарт супервизора работает на КАЖДОЕ падение и зависание процесса, а не один раз за жизнь процесса; одна поломка тратит ровно одну попытку из `max_restarts`; статус восстановленного воплощения — `running`, не `crashed`/`unresponsive`; `failed` (исчерпание попыток) достижим, и run-state видит «сдался» раньше окна 1.8.
- **Files:** `process_manager_module/monitor/process_monitor.py`, `process_manager_module/process/process_manager_process.py` (путь `restart_process`), `shared_resources_module/...` (`register_process`, только если лечение L1 вариантом (а)); тесты — новые.
- **Handoff:** слепой tester (RED) -> developer (GREEN) -> hazard -> матрица -> стенд; ревью — одно на Ф1
- **Gate:** medium · **Dependencies:** 1.7c, 1.8 · **Layer:** framework · **Module contract:** без изменения публичного API (поведение супервизора)
- **Источник:** находка стенда 1.6-1.8-1.7c (часть A: второй `kill -9` через 35–65 с не лечится — R1#2, R2#2, P-on#2; двойной перезапуск зависшего при флаге ON — 2 из 2) + диагностика Opus (`reports/1.8b.supervisor-restart.investigation.md`, воспроизведено на настоящих `ProcessMonitor` + `ProcessStateRegistry` + `PM.restart_process`). Запись `docs/claude/OPEN_QUESTIONS.md:2293` («супервизор не перезапустил второе воплощение») — это дефект №1.

Корень (общий): супервизор хранит статус процесса по ИМЕНИ, а не по воплощению. Дефект №1: при рестарте новое воплощение регистрируется в `ProcessStateRegistry` по тому же имени, запись уже есть → статус `crashed`/`unresponsive` не сбрасывается; монитор каждый такт перезаписывает `previous_states` из реестра; промоушен в `running` только из pre-running статусов → живой процесс навсегда `crashed`, его следующая смерть пропускается (`_handle_dead_process`: терминальный статус → return), следующее зависание — тоже; статус «мигает» по heartbeat. Дефект №2: рестарт держит мёртвый старый объект в `os_processes` пока не подтвердит его смерть; статус `unresponsive` не терминальный; `_pending_restarts` уже снят → смерть старого pid (SIGTERM, `-15`) засчитывается как новое падение → второй рестарт. Дефекты независимы (два лечения), причина общая. Почему тесты зелёные: во всех тестах PM реестр состояний — `MagicMock`.

DESIGN (лид; лечение причиной, не заплаткой; без сброса по таймеру, без флагов):
  L1. Путь рестарта регистрирует новое воплощение со статусом `initializing` (как boot и switch), очереди/`metadata`/`custom` сохраняются. Место — решение исполнителя из двух вариантов: (а) `SRM.register_process` при `reuse_queues=True`; (б) явный сброс в `restart_process` между `remove_process` и `create_and_register`. Критерий выбора: изменение там, где нарушен инвариант; разобрать все три вызова `register_process` (`process_manager_process.py`: ≈424, ≈5056, ≈6043) и правило «запись есть — статус не трогать» (`process_state_registry.py`, коммит `b136863d5`) — не сломать другие пути; обоснование — в отчёте.
  L2. `_handle_dead_process`: смерть процесса, чей pid равен pid, который супервизор сам решил заменить (`_restarting[name]`, 1.7c), не считается новым падением; смерть любого другого pid (в том числе нового воплощения до первого heartbeat) — честное падение.
  L3. Пороги, `max_restarts`, backoff, критерий `recovered` — не менять; ручной `process.restart` (выход старого процесса кодом 0 → новое воплощение навсегда `stopped`; смерть `-15` → ручной рестарт сам ставит авто-рестарт) должен вести себя как автоматический: ровно одно воплощение, статус `running`.
  L4. Тесты супервизора на настоящем `ProcessStateRegistry` (не `MagicMock`) — один вспомогательный фикстур-модуль, чтобы дефект такого класса не прятался.

ACCEPTANCE (поведение; юнит на настоящих `ProcessMonitor` + `ProcessStateRegistry` + `restart_process`, двойники — только процесс ОС):
  1. Падение процесса → рестарт 1/N → воплощение живёт (heartbeat) → второе падение → рестарт 2/N (счётчик растёт, событие `restarting 2/N`, ещё один `process.restart`).
  2. То же для зависания (`unresponsive` → рестарт → снова `unresponsive` → рестарт).
  3. Нет мигания: после рестарта и heartbeat статус процесса (`supervision_status`, `previous_states`) — `running` на N подряд тактах монитора.
  4. Процесс `unresponsive`; старое воплощение умирает от SIGTERM (`-15`) во время стопа рестарта → ровно один рестарт, `sends == 1`.
  5. Ручной `process.restart` (старый выходит с 0 / с `-15`) → новое воплощение `running`, следующее падение → рестарт 1/N, а не пропуск и не двойной.
  6. Исчерпание `max_restarts` → статус `failed`; при флаге `run_auto_restart` run-state уходит в `fault` с причиной «сдался» раньше окна `run_restart_grace_s` (30 с).
  Стенд: после авто-рестарта `kill -9` через 35 с лечится второй раз (R1#2, P-on#2, R2#2); зависание SIGSTOP при флаге ON — одна поломка = один рестарт (pid меняется один раз); `supervision_status` без мигания.

OUT OF SCOPE: проверка pid в `_on_heartbeat_received` для позднего heartbeat старого pid (hazard H5 — только фиксируется тестом, лечится, если красный; иначе — в открытое); `_broadcast_shm_reclaim` и займы нового воплощения на переиспользованных очередях (отдельная проверка, в открытое отчёта).

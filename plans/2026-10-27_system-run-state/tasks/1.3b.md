DESIGN (decided by the lead — v2, срез 1.0: только `boot`; `recipe_load` — 2.0, `amendments.md` §7):
  1. Новый `process_module/progress.py` (чистый, без IO, без Qt; Purpose/Public API/Stability в docstring файла, DbC Pre/Post у `advance` и `finish`).
     Причина места (ревью A1): прецедент контракта путей state — `process_module/health/schema.py`, его уже импортируют PM (`process_monitor.py:18`),
     плагины и GUI; `state_store_module` — ярус optional, у PM на него runtime-импортов нет (PM пишет в стор утиной связью, `_state_op`), новое ребро
     core → optional не нужно. Содержимое: `PROGRESS_ROOT = "system.progress"`, `progress_path(id)`; `ProgressTracker(steps: list[tuple[str, int]])`;
     `advance(step, fraction=1.0, *, label="") -> dict`; `finish(label="") -> dict`. Лист: `{"percent": int 0..100, "label": str, "done": bool, "updated_at": float}`
     (без `stage` — потребителя нет, ревью A8; без параметра `done` в `advance` — один способ закрыть шкалу). Процент монотонный (max с прошлым);
     `fraction` вне 0..1 обрезается; неизвестный шаг — `ValueError` без значения в тексте. Причина «класс без IO»: принцип 4 — писатель кладёт dict в СВОЙ
     API записи. Трекер для плагинов не расширяется: требование владельца «любой узел сообщает» выполняют лист и константа пути.
  2. Издатель `boot` в `process_manager_process.py`, **только из `initialize()`** (не из `_run_apply`: `settled` зовётся и в итоге STOP `:1298`, и после 1.5;
     рестарт `_wait_processes_ready(..., "restart")` `:4764` лист `boot` не трогает): `ProgressTracker([("store", 5), ("started", 45), ("ready", 50)])`.
     Веса — по фазам, не по времени: стор поднят — 5; «запущен» растёт по `started: set` (`:4329`, `:4350`), k из N; «готов» — по результату барьера. N = число
     процессов, прошедших валидацию (`valid`, `:4316-4326`). `ready` накапливается как **объединение** множеств готовых по всем вызовам барьера (волновой гейт
     `:4338` возвращает подмножество апстримов) — процент не уходит назад на итоговом барьере.
  3. **Ступенька принята осознанно** (ревью A3, вариант б; барьер и его тесты не меняем, ADR-PMM-034): `_wait_processes_ready` возвращает dict только на выходе,
     поэтому на плоском boot (без `depends_on`, `:4401-4402`) шкала стоит на 50 % до `boot_ready_timeout_s` (по умолчанию 5 с, `:4374`) и прыгает на 100.
     Процент ≠ готовность узлов (это `system.run.*`); на дедлайне барьера ожидающие считаются готовыми (`:5127-5128`, фолбэк по liveness) — записать в README.
  4. `finish(label)` — один вызов в конце `initialize()` рядом с `_run_apply("settled", ...)` (`:439`), **и при `ready`, и при `not_ready`** (причина: окно закрывается
     по выходу из `booting`, причины «не готов» оператор видит в Task 2.3). `label` несёт «запущено k из N», если k < N (иначе 100 %/`done` скроет неподнятый процесс).
     N = 0 (пустая топология): сразу `finish`, без деления. Провал `initialize()` (`except`, `:458`) оставляет `boot` с `done: false` — допустимо, PM закрывается.
  5. Запись — `_state_op("handle_state_set", {"path": progress_path("boot"), "value": leaf, "source": "ProcessManager"})` (как `_publish_run_state`, `:1011`).
     `_state_op` сам глотает сбой стора и пишет только `_log_debug` (`:2282-2285`) — **`log_error` не обещаем** (ревью A6); требование: сбой записи не валит boot и не откатывает процент.
  6. Без стора (`_state_op` — no-op) и при `run_gate: false` поведение boot не меняется (тесты).

2. `run_stop` -> `await_condition` `system.run.state = "ready"`; `state_subscribe "system.run.*"`, через 60 с `events`: ни одного `state.changed` со значением `running`; `run_status().since` не изменился.
3. `fault` (способ вызвать — лид по стенду) -> `run_ack` -> `await_condition` `system.run.state = "ready"`; 60 с: в `events` нет `running`, `since` прежний.
4. Без флага и ключа: `await_condition` `system.run.state = "ready"`; `watch_like_gui`, через 10 с `telemetry_snapshot(process=<источник>, metric="fps")` — все значения 0 или `count=0`.
5. `system.yaml` стенда с `run_stop_timeout_s: 2`, процесс, не уходящий в `paused` (способ — лид по стенду): `run_stop` в момент t0 -> `await_condition` выхода `system.run.state` из `stopping`; `run_status().since − t0 = 2,0 ± 0,5 с`.

## Что осталось открытым / ненадёжно

- Ничего из DESIGN не написано и не запущено. Запуском подтверждены только Ф1, Ф2, Ф5, Ф13 (вес импорта) и моделирование латча ревьюером (Ф12) — на копии латча, не на настоящем `_run_apply`. Свойство «STOP при `run_gate: false` ничего не останавливает» — по чтению и существующему тесту, сам тест не гонял; живого стенда не было.
- Save (п.9a): правило «как в исходном файле» верно, пока у плоских ключей нет редакторов. Появится редактор — правило менять (Save отбросит правку ключа, которого нет в файле). Секции из `user_overrides.yaml` при Save по-прежнему уходят в `system.yaml` — не 2.7.
- И10 снят: вызов `observe` вне `_run_lock` тестами не ловится, держит только контракт в докстринге и ревью.
- Порядок замков `_run_lock -> _routing_lock` (И14, форма под замком): есть ли где-то обратный порядок, не проверял (5 мест `with self._routing_lock` в PM не читал). DESIGN п.12 подаёт после замка — риск только при нарушении п.12.
- S3c 4 ни одна инъекция таблицы не убивает (держат потраченный латч и гашение `ack`) — страж решения владельца, не детектор.
- S3c′ 1d повторяет шов `spawner.py:95-96` вызовами `update_config`; настоящая передача конфига в PM проверяется только стендом (ACCEPTANCE 1, строка лога).
- Вес импорта (Ф13) принят в ADR-PMM-049. Вариант на будущее: вынести `RunConfig` в место, импорт которого не тянет `__init__` пакета PM (например отдельный модуль без зависимостей PM) — не исследован.
- ACCEPTANCE 3 и 5: как вызвать `fault` и непаузящийся процесс на стенде, не указано. ACCEPTANCE 4: точный счётчик кадров источника не выбран (`fps` из `telemetry_snapshot` — замена; копится только при активной подписке `processes.**`).
- Латч гасится любым `apply`. По ревью (чтение и `git grep`) прототип сам `topology.apply` при старте не шлёт, headless без GUI-процесса; стендом не проверено.
- START автостарта может пойти до `attach_ready_event` (поток `initialize()`); безопасно ли — не проверено (источники ждут `system_ready_event`, ADR-PMM-034, по ревью).
- Отказ автостарта из-за гонки (готовность ушла между тактом и START) не повторяется — по решению «ровно один раз»; линия стоит в `ready` с WARNING.
- GUI-зонды и `bootstrap()`-вызывающие после коммита B без START: каким нужны кадры — не проверено (2.1 «Порядок слияния» п.3).
- Номера ADR закрепил лид; параллельные ленты могут занять 049–051 раньше — сверить перед записью ADR.

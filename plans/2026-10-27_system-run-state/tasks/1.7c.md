# Task 1.7c: воплощение процесса — допуск и готовность не принимают лист процесса, приговорённого к перезапуску

- **Статус:** [PENDING] · **Level:** Senior · **Assignee:** developer (sonnet) <!-- lint-language: allow -->
- **Goal:** `ack`/START не проходят по листу готовности процесса, который супервизор уже решил перезапустить (или перезапускает); оживший старый процесс и поздний heartbeat старого воплощения не делают лист «свежим»; в `running` без флага падение по решению супервизора — `fault` сразу, а не через backoff после допущенного START.
- **Files:** см. FILES ниже (4 пути + тесты)
- **Handoff:** слепой tester (RED) -> developer (GREEN) -> hazard -> матрица -> стенд; ревью — одно на Ф1
- **Gate:** medium · **Dependencies:** 1.3, 1.7, 1.8 · **Layer:** framework · **Module contract:** public-api-change (новое аддитивное поле `pid` в heartbeat, новое множество «перезапускается» из монитора)
- **Источник:** находка стенда 1.5/1.7b + диагностика Opus (2026-11-13, `reports/1.7c.investigation.md` — текст отчёта investigator), A/B `reports/1.7b.ab.stand.md`: 0 повторных fault из 16 при выключенном рестарте; при включённом — fault через ≈ backoff после START.

Корень (воспроизведён юнитом на настоящих `ProcessMonitor` + `ProcessManagerProcess`): супервизор решает перезапустить процесс по `unresponsive` и исполняет через backoff (по умолчанию 2 с); лист готовности снимается только при исполнении; оживший (SIGCONT) старый процесс снова кладёт свежий лист; в листе нет идентичности воплощения → `ack` → `ready`, START → `running` по листу приговорённого; после исполнения лист снят, процесс жив → «нет отчёта о готовности» → `fault`. Пороги 15 с супервизора и `stale_s` 15 с в PM — от двух часов одного heartbeat; подгонять их нельзя.

DESIGN (решает лид; владелец воплощения — супервизор `ProcessMonitor`, вариант «c» диагностики):
  1. `ProcessHeartbeat`: в конверт heartbeat добавляется `pid` ребёнка (`os.getpid()`), аддитивно (Dict at Boundary сохраняется; получатель без поля — совместимость: такой heartbeat принимается как раньше).
  2. `ProcessMonitor`: множество `_restarting` (имена). Ставится в `_try_auto_restart` и `_cascade_restart` вместе со снятием листа (`_forget_readiness`) — в момент РЕШЕНИЯ, не исполнения; ручной `process.restart` (`restart_process` PM) — то же. Снимается первым heartbeat с `pid` == pid реестра ПОСЛЕ исполнения рестарта. Пока имя в `_restarting`, `_on_heartbeat_received` лист НЕ принимает (heartbeat учитывается как жизнь, событие «recovered» — только по heartbeat нового воплощения, не по оживлению старого). `forget_process` чистит и его.
  3. Один снимок: `readiness_view() -> (листы, frozenset перезапускаемых)` под одним замком; `readiness_snapshot()` остаётся (совместимость).
  4. `run_state.evaluate(..., restarting: frozenset[str] = frozenset())`: процесс из `restarting` даёт причину `failure` «<процесс>: перезапускается супервизором» (`liveness`), независимо от листа, блокирует `ack`/START; прочие причины процесса не показываются. В `running` процесс с флагом `run_auto_restart` из `restarting` — в окне 1.8 (`out_of_spec`, окно от момента решения), без флага — `failure` → `fault`.
  5. `_admission_stale_s` (1.7b) остаётся: он закрывает замороженный процесс без решения супервизора (A/B: 8 из 8 отказов против 0).
  6. Пороги не менять.

FILES: `process_module/heartbeat/process_heartbeat.py`, `process_manager_module/monitor/process_monitor.py`, `process_manager_module/process/run_state.py`, `process_manager_module/process/process_manager_process.py`; тесты — новые.

ACCEPTANCE (юнит на настоящих объектах, как `inv_restart/repro.py`): рестарт запланирован (`unresponsive`) → `ack_allowed` может стать true, но `ack` → `not_ready` с причиной «перезапускается»; START отказан с той же причиной; после heartbeat нового pid и свежего листа — `ready`; ручной `process.restart` не допускает по листу старого воплощения; поздний лист старого pid после исполнения не принимается; в `running` без флага решение супервизора → `fault` сразу. Стенд: ≥ 13 кругов «STOP → fault → CONT → ack → start» при ВКЛЮЧЁННОМ рестарте — 0 повторных fault после допущенного START.

OUT OF SCOPE: отмена перезапуска при самоисцелении (противоречит ADR-PMM-015 «рестарт не отменяется»); номер воплощения от PM вместо pid (вариант на будущее, если реиспользование pid ОС станет проблемой).

## DESIGN (лид; developer печатает, не выводит)

**П.1. Чистая модель (без Qt).** `widgets/chrome/run_control.py`: функция `build_view(snapshot: dict, busy: bool) -> RunView` (frozen dataclass), где `snapshot` — словарь листьев `{state, since, reasons, start_allowed, ack_allowed, last_fault}`, любые ключи могут отсутствовать. Поля `RunView`: `state_text`, `level` (`neutral|ok|warn|danger`), `start_enabled`, `start_tooltip`, `stop_enabled`, `ack_visible`, `ack_enabled`, `detail_text`, `indicators_text`, `fault_text`.
 - Имена состояний (литералы): `booting` «Поднимается», `not_ready` «Не готов», `ready` «Готов», `running` «Работает», `stopping` «Останавливается», `fault` «Авария», `shutting_down` «Завершение». Нет листа `state` или значение вне таблицы: «Нет данных», `level=neutral`, все кнопки неактивны, `ack_visible=False`.
 - `level`: ready/running → `ok`; booting/stopping/shutting_down → `neutral`; not_ready → `warn`; fault → `danger`.
 - `start_enabled = bool(start_allowed) and not busy` (отсутствие листа = False). `stop_enabled = state == "running" and not busy`. `ack_visible = state == "fault"`; `ack_enabled = ack_visible and bool(ack_allowed) and not busy`.
 - Неактивная ЗАПУСТИТЬ: `detail_text` = reason первой записи с `severity == "failure"`, иначе первой с `check_function`; если блокирующих нет — пусто (в `ready` причин нет). `start_tooltip` = все блокирующие причины построчно `node: reason` (failure раньше check_function; порядок внутри — как в списке). Блокирующие = `failure`, `check_function` (как `READINESS_BLOCKING_SEVERITIES`).
 - В `fault`: пока `ack_allowed` ложно — `detail_text = "идёт остановка"`; иначе первая причина из `last_fault.reasons` (если есть).
 - `indicators_text` (В8): причины `out_of_spec` → «Вне допуска: r1; r2», `maintenance` → «Обслуживание: r1» (две части через « · »), только при `state == "running"`; цвет аварии не используют (`level` от них не зависит).
 - `fault_text`: при `last_fault` не `None`: «Последняя авария ЧЧ:ММ:СС — <первая причина>» + (« — квитирована ЧЧ:ММ:СС» если `acknowledged_at`, иначе « — не квитирована»); время — локальное `strftime("%H:%M:%S")` от `at`. Строка остаётся, пока лист не станет `None` (PM сбрасывает при успешном START).
 - Ввод нетипичен (reasons не список, запись не dict, нет ключей) — не бросает; пропускаются негодные записи.

**П.2. Виджет.** `RunControlWidget(QWidget)`: метки состояния/деталей/индикаторов/последней аварии, кнопки «ЗАПУСТИТЬ», «ОСТАНОВИТЬ», «Квитировать». Метод `apply_leaf(path, value)` — кладёт значение в `_snapshot[path.removeprefix("system.run.")]`, пересобирает `RunView`, перерисовывает. Узел удалён (значение `MISSING`/дельта удаления) — лист убирается. Виджет получает объект команд `commands` с методами `run_start_async/run_stop_async/run_ack_async(on_result)` через `set_commands(commands)`; без него клики — no-op с текстом «нет связи».
 - Клик: `busy=True` (кнопки неактивны) → вызвать соответствующий метод; в `on_result(result)`: `busy=False`; если `result["success"]` истинно — ничего (состояние придёт листом); иначе показать в `detail_text` русский текст отказа (таблица ниже) + при наличии первой причины из `result["result"]["reasons"]`; транспортный сбой (нет `result`, таймаут) — «нет ответа от системы». Текст отказа сбрасывается при следующем изменении листа `state`.
 - Коды отказа (литералы): `not_ready` «система не готова», `already_running` «уже работает», `stopping` «идёт остановка», `fault_unacknowledged` «авария не квитирована», `fault_stopping` «идёт остановка после аварии», `no_fault` «аварии нет», `shutting_down` «система завершает работу»; незнакомый код — «отказ: <код>».
 - GUI ничего не запускает сам (принцип 6): виджет только шлёт команды PM и рисует листья.
 - QSS: свойство `level` на метке состояния, файл стилей по образцу `error_banner` (путь и регистрация в `style_manifest.py` — по образцу, без новых механизмов).

**П.3. Подписка и размещение.** `MainWindow`: поле `_run_control = RunControlWidget()` между баннером и image panel (`addWidget` после `_error_banner`). В `connect_bindings` — `bindings.bind_fanout("system.run.*", self._run_control.apply_leaf, owner=self._run_control)` (одиночный `*`: шесть листьев; `last_fault` — лист-значение целиком). Сеттер окна `set_run_commands(commands)` → `self._run_control.set_commands(commands)`; `app.py`: одна строка `window.set_run_commands(process_manager_proxy)` после `set_close_coordinator`.

**П.4. Прокси.** `ProcessManagerProxy`: `run_start_async(on_result)`, `run_stop_async(on_result)`, `run_ack_async(on_result)` → `_dispatch_async("system.run.start"|"system.run.stop"|"system.run.ack", {}, on_result)`. Больше ничего в прокси не менять.

**П.5. Условная ветка (решает лид по живой приёмке, в код не закладывается заранее).** Если на стенде GUI, запущенный при уже `ready` PM, не получает `system.run.*` из replay (кнопка неактивна дольше 5 с) — добавить затравку одним `system.run.status` через прокси; без неё не усложнять.

## REDS (слепой tester; ожидания — литералы; Qt-тесты под `qtbot`, без модальных окон)

Модель (`build_view`, без Qt):
1. Пустой snapshot `{}` -> `state_text == "Нет данных"`, `start_enabled` False, `stop_enabled` False, `ack_visible` False.
2. Таблица состояний: на каждое из 7 значений `state` — `state_text` из списка выше и `level` из правил П.1 (параметризованно).
3. `{"state": "not_ready", "start_allowed": False, "reasons": [out_of_spec «A», failure «диск не найден», check_function «B»]}` -> `start_enabled` False; `detail_text == "диск не найден"`; `start_tooltip` содержит «диск не найден» и «B», не содержит «A».
4. `ready` + `start_allowed True` -> `start_enabled` True, `detail_text == ""`; с `busy=True` -> `start_enabled` False.
5. `stop_enabled` True только при `state == "running"` (перебор 7 состояний).
6. `fault`, `ack_allowed False` -> `ack_visible` True, `ack_enabled` False, `detail_text == "идёт остановка"`; `ack_allowed True` -> `ack_enabled` True, `detail_text` — первая причина `last_fault.reasons`.
7. `running` + reasons `out_of_spec «диск»` + `maintenance «замена»` -> `indicators_text == "Вне допуска: диск · Обслуживание: замена"`, `level == "ok"`; те же причины при `state == "ready"` -> `indicators_text == ""`.
8. `last_fault` `{at: 100.0, reasons: [failure «обрыв»], acknowledged_at: None}` -> `fault_text` содержит «обрыв» и «не квитирована»; с `acknowledged_at: 120.0` — «квитирована» без «не »; `last_fault None` -> пусто.
9. Негодный ввод: `reasons` строкой, запись не dict, `last_fault` числом — `build_view` не бросает.

Виджет (`qtbot`, фейк `commands`, записывающий вызовы и сохраняющий `on_result`):
10. `apply_leaf` листьями `state=ready`, `start_allowed=True` -> кнопка ЗАПУСТИТЬ включена; клик -> ровно один вызов `run_start_async`, до `on_result` кнопка выключена; повторный клик ничего не шлёт.
11. `on_result({"success": False, "result": {"state": "not_ready", "error": "not_ready", "reasons": [failure «нет диска»]}})` -> `busy` снят, текст деталей содержит «система не готова» и «нет диска»; следующий лист `state` сбрасывает этот текст.
12. Транспортный сбой (`on_result({"success": False})`) -> текст «нет ответа от системы», кнопки не зависают.
13. `state=running` -> ОСТАНОВИТЬ включена, клик -> `run_stop_async`; `state=fault`, `ack_allowed=True` -> «Квитировать» включена, клик -> `run_ack_async`.
14. Без `set_commands` клик по включённой кнопке не бросает, текст «нет связи».
15. Лист удалён (`state` -> `MISSING`) -> «Нет данных», кнопки неактивны.

## ACCEPTANCE (живая, окно машины, числами)

GUI + backend с `run_gate: true` (после 2.1 коммит B; до него — рецепт с гейтом через `BackendHarness`/ручной манифест): (1) после boot ЗАПУСТИТЬ неактивна до `ready`, в подсказке/деталях причина; (2) `ready` -> клик -> «Работает» ≤ 2 с; (3) ОСТАНОВИТЬ -> «Останавливается» -> «Готов»; (4) GUI, запущенный при уже `ready` PM, показывает активную ЗАПУСТИТЬ ≤ 5 с (иначе П.5); (5) принудительная авария (`failure` в `running`) -> «Авария», «Квитировать» неактивна «идёт остановка», затем активна; клик -> «Не готов»/«Готов». Скриншоты — qt-mcp (`qt-mcp` на этой машине недоступен — тогда `backend_ctl` `state_get system.run.*` + скриншот владельца).

# Task 2.7d: запрет команд плагина в `running` — флаг `run_active` от PM и ключ плагина `run_locked_commands`

- **Статус:** [PENDING] · **Level:** Senior (межпроцессный флаг, путь регистрации команд) · **Assignee:** developer (Sonnet) по точному DESIGN; слепой tester до кода (новый механизм)
- **Goal:** команда плагина из его ключа `run_locked_commands` (в `config` плагина; `release_device` камеры и т.п.) в `running` не исполняется. По GUI `request_command` и `backend_ctl` — конверт ответа `{"success": False, "result": {"status": "error", "error": "running", "message": "сначала ОСТАНОВИТЬ"}}`. По relay (кнопка GUI, fire-and-forget) PM отвечает GUI `{"success": True, "target_process": …}` до исполнения; отказ виден только WARNING `Command 'release_device' failed: running` в журнале ребёнка, оператор в GUI его не видит. В остальных состояниях команда исполняется; плагины не меняются.
- **Решение (лид, по расследованию `scratchpad/f/command-guard-investigation.md`, вариант (б'), §5–§6):** второй `RunFlag` `_run_active` в PM (= состояние `running` и нет хода системного стопа, при любом `run_gate`), доставка детям путём `run_event`, ключ ПЛАГИНА `run_locked_commands: [...]` в `config` плагина (читается как `ctx.config`), обёртка при регистрации команды в базе плагина. Владелец 2026-11-16: «как правильно, без временного решения».
- **Резка:** этап 1 (до 2026-11-22, этот текст) — framework, список по умолчанию пустой, рецепты не трогаются: поведение не меняется. ## DESIGN (лид; developer печатает, не выводит)

Почему корневая форма: проверка у получателя закрывает все три пути без нового слоя на пути каждой команды; состояние — проекция единственной точки записи PM; политика (какие команды) — в рецепте у плагина. Что удаляется: ничего; заплаты (гашение кнопок в GUI, список в PM) не вводятся. Якоря в `process_manager_process.py` — текстом.
1. PM: `self._run_active = RunFlag()` рядом с `self._run_event = RunFlag()` (всегда, независимо от `run_gate`); классовое умолчание `_run_active: RunFlag | None = None`. `ProcessRegistry(..., run_active=self._run_active)` рядом с `run_event=self._run_event`. Флаг — производная двух признаков PM, своего хранилища у него нет: `want = state is RunState.running and self._system_stop_snapshot() is None` (ход системного стопа, Ф8: ставит только `_begin_system_stop`, сброса нет). Пишет флаг одна функция `_run_active_sync_locked(state)`: `active = self._run_active`; `if active is None: return` (двойники PM из `__new__`, как для `run_event`); `if active.is_set() != want: active.set() / active.clear()`. Её зовут только под `_run_lock`, из двух мест:
   - 1а. `_run_apply`, блок «Событие переключаем ДО записи состояния» (после переключения `run_event`, до `if new is not prev:`), БЕЗ условия `run_gate`: `self._run_active_sync_locked(new)`. `stopping`, `fault`, `shutting_down` — снят (шаги `pre_stop` STOP оператора и восстановление после аварии проходят). Поздний такт или START (проверка стопа вне замка, Ф8) идут через `_run_apply` и читают признак уже под `_run_lock` — флаг обратно не взведут; переносить их проверку не нужно.
   - 1б. `_begin_system_stop` (единственная точка начала хода стопа, любым путём: команда, `supervision.status`, стоп детей корня), внутри `with self._run_lock, self._system_stop_lock:` (порядок `_run_lock` -> `_system_stop_lock`; вызывающий `_run_lock` не держит): `if self._system_stop_info is not None: return False`; `self._run_active_sync_locked(self._run_state, stop_begun=True)` ДО записи `self._system_stop_info = info` (замок не реентерабелен — `stop_begun` передаётся явно). Не в `_run_shutdown_pass` (ADR-PMM-051 п.2): так флаг верен при любом пути начала стопа, а не только у graceful `system.shutdown`. Состояние `running` -> флаг снят до шагов; `run_event` не трогается (шаги при взведённом событии работы — Task 1.4, amendments §9).
   Порядок замков: `_run_lock` -> `_system_stop_lock`. `_system_stop_lock` листовой: в 7 блоках `with self._system_stop_lock:` (`_system_stop_snapshot`, `_begin_system_stop`, `_escalate_system_stop`, `_shift_system_stop_deadline`, `_set_system_stop_phase`, `_set_pre_stop_step`, `_leave_pre_stop`) других замков нет — обратного порядка нет.
2. `ProcessRegistry.__init__(..., run_active: Event | None = None)` рядом с `run_event` -> `self._run_active`; `"run_active"` — в кортеж pop-фильтра bundle `custom` рядом с `"run_event"` (защитно: ключ из рецепта не уедет в bundle) и в литерал kwargs `Process`: `"run_active": self._run_active` рядом с `"run_event": self._run_event`. `run_process_function(..., run_active: Event | None = None)` рядом с kwarg `run_event`; `if run_active is not None: process_instance._run_active = run_active` рядом с такой же строкой для `_run_event`; докстринг — одна строка рядом с `run_event`. `run_active=None` (корневой PM — `launcher/spawner.py:116`, `Process(target=run_process_function, …)` без `run_active`; двойники PM из `__new__`, реестр без флага) — атрибут не ставится.
3. `plugins/base.py` `_auto_register_commands`: перед циклом `for cmd_name, method_name in self.commands.items():` — `locked = self._run_locked_names(ctx)` (новый приватный метод):
   - `raw = ctx.config.get("run_locked_commands")`; `None` -> `frozenset()`;
   - не `list`/`tuple` или есть элемент не `str` -> одна строка ERROR `f"Plugin '{self.name}': run_locked_commands негоден (нужен список имён команд) — запрета нет"` и `frozenset()`;
   - имена не из `self.commands` -> одна строка ERROR: `shown = [n[:40] for n in sorted(unknown)[:5]]`, `extra = len(unknown) - len(shown)`, текст `f"Plugin '{self.name}': run_locked_commands — нет таких команд {shown}"` + (`f" (+{extra})"` если `extra`); остальные имена берутся.
   Ключ читается один раз — при регистрации команд; смена ключа без пересборки узла не действует.
4. В цикле: имя в `locked` -> регистрируется `method = self._run_guarded(ctx, method)` вместо `method` (тот же вызов `register_command` / `_register_command_with_options`, сигнатура метода сохраняется через `functools.wraps`). Обёртка: `flag = getattr(ctx.services, "_run_active", None)`; `flag is not None and flag.is_set()` -> вернуть `{"status": "error", "error": "running", "message": "сначала ОСТАНОВИТЬ"}`, метод не вызывается; иначе `return method(*args, **kwargs)`. Флаг читается в момент вызова (на потоке исполнителя для команд с `executor`). Команды вне списка регистрируются байт в байт как сейчас.
5. Принятое ограничение (TOCTOU у START): команда, начавшая исполнение до `set()` флага, исполняется во время `running` — окно = время исполнения одной команды (флаг читается на исполнении, ожидание в очереди не в счёт). Исход в окне — как до защиты: охраняемая команда исполнилась в `running`. `fault` после неё — только у узлов, чья `readiness()` даёт причину (камера — после 2.2c, Ф10). Закрытие требует замка, общего для PM и ребёнка, — новый межпроцессный слой; на этапе 1 не закрываем. В ADR-PMM-051 — этими словами.
6. ADR:
   - `process_manager_module/DECISIONS.md`, ADR-PMM-051 — второй `RunFlag` `run_active`: производная «`running` и нет хода системного стопа», одна функция записи `_run_active_sync_locked` под `_run_lock` (вызовы 1а, 1б), порядок замков `_run_lock` -> `_system_stop_lock`, доставка путём `run_event`, TOCTOU (п.5).
   - `process_module/DECISIONS.md`, ADR-PM-062 — ключ плагина `run_locked_commands`: место — `config` плагина, не узел; пример `plugins: [{plugin_name: camera_device, config: {run_locked_commands: [release_device]}}]` (плоская форма в элементе `plugins` — тот же ключ, `_extract_plugin_config`); ключ на уровне узла молча игнорируется; читается один раз при регистрации команд; форма отказа (конверт, журнал relay, Ф9); формат строк ERROR (п.3); правки регистров не закрыты.

## Out of scope

## ACCEPTANCE (стенд, окно машины)

`run_gate: true`, tmp-копия рецепта камеры (этап 1), ключ в `config` плагина камеры: `plugins: [{plugin_name: camera_device, config: {run_locked_commands: [release_device]}}]`. `backend_ctl run_start` -> `send_command("<камера>", "release_device")` -> конверт `success: False`, `result.error == "running"`, `result.message == "сначала ОСТАНОВИТЬ"`; кадры идут (счёт за 5 с > 0); `run_stop` -> `ready` -> та же команда -> `success: True`, камера закрыта. То же при `run_gate: false`. Кнопка GUI (relay) в `running`: GUI получает `success: True` (отказа не видит), в журнале ребёнка WARNING `Command 'release_device' failed: running`, камера не закрылась, кадры идут.

- Опыт расследования (Ф1) я не повторял; пути B и C — по чтению расследования. Опыты ревьюера (Ф5 межпроцессно, Ф6 `camera_device`, Ф8 shutdown из `running`) я не повторял — цифры из его отчёта.

## Факты (`main` `6aa7d0dad`)

- `SplashController.poll()` (`splash/window.py:124-135`): сначала запрошенная причина, затем `_drain()`, затем `gui_done`, затем `timeout`, если от создания контроллера прошло `>= timeout_s`. `SPLASH_TIMEOUT_S = 60.0` (`splash/protocol.py:23`).
- Стенд 2.4 часть В, 100 % CPU, n=3: `closed reason=timeout` на 60,0 с при шкале 60 / 27 / 29 %; главное окно на 92,5 с / нет за 150 с / 145,3 с. Без нагрузки окно на 17–28 с.
- Писатели `system.progress.<id>`: лончер (`launch`), PM только в `initialize()` (`boot`), GUI (`gui`). Шкала заставки монотонна, 0..100 (`SplashScale`); посылка с неизвестным `id` её не двигает.
- Паузы между посылками под нагрузкой не мерялись (в логах их нет). По #1 (`shown` 4,95 с, окно 92,5 с) пауза не больше ~88 с, по #3 (20,9 / 145,3 с) не больше ~125 с; по #2 данных нет (окна нет за 150 с).
- Заставка уходит и без таймаута: `gui_done`, `parent_gone` (лончер умер), `sigint`, закрытие окна.

## DESIGN

1. `timeout_s` отсчитывается от **последнего роста общей шкалы** `window.percent()`; пока роста не было — от создания контроллера.
2. Рост — это `window.percent()` после `apply()` строго больше, чем до него. Посылка с тем же или меньшим процентом, с неизвестным `id`, мусорная датаграмма отсчёт не сдвигают. Поэтому сдвигов не больше 100 и заставка не может висеть без конца из-за повторяющихся посылок. `__init__` окно не читает: `percent()` берётся до и после `apply()` в `_drain` (тест `test_hazards_author.py:195-213` строит контроллер с пустым окном).
3. Порядок в `poll()` прежний: запрошенная причина, дренаж сокета, `gui_done`, `timeout`. Посылка с ростом, лежащая в сокете, учитывается до суда о таймауте (в пределах `_DRAIN_LIMIT` = 256 датаграмм за один `poll()`).
4. `SPLASH_TIMEOUT_S = 180.0`. Смысл: «столько секунд без роста шкалы». Число: замеренная верхняя граница паузы 125 с плюс запас; под 100 % CPU в повторе без окна данных нет.
5. Время контроллер берёт только через `time.monotonic()` модуля `splash.window` (тест может подменить атрибут `time` этого модуля своим объектом с `monotonic()`).
6. Подписи, строки stderr, имена причин, прочие пути закрытия не меняются.

Цена (принята):
- GUI упал до первого окна при живом лончере — заставка уйдёт через 180 с после последнего роста, а не через 60 с от старта.
- Не дошёл финальный `done` (нет `_gui_state_proxy`, `install_if_enabled` вернул `False`, запись без подтверждения) — заставка остаётся при уже открытом главном окне до 180 с после последнего роста.
- GUI перезапущен до первого окна — `SplashScale` берёт максимум по `id`, новые листья не растят шкалу, пока не превысят прежнюю отметку; заставка может уйти по `timeout`, пока новый GUI грузится.

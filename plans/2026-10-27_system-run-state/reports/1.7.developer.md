## По пунктам DESIGN

1. **Таблица `transition` для `ack`** — проверена, правок нет: `fault` + `stop_done` → `ready`/`not_ready`; `stop_done` False → `fault_stopping`; вне `fault` → `no_fault`; `shutting_down` → `shutting_down`. STOP в `fault` — no-op, shutdown из `fault` проходит без `ack` (слепые тесты 6 и 9 зелёные).
2. **Команда `system.run.ack`** — `_cmd_system_run_ack`, зарегистрирована в `_register_builtin_commands` без `executor` (класс R). Ответ `{"success": bool, "state": str, "error": code | None}`. Свежая оценка готовности (`_evaluate_run_readiness`, вне замка) → `_run_apply("ack", ready=..., reasons=...)`. Пока PM гасится или идёт системный стоп — `shutting_down`, как у START.
   - **Гонка:** `_run_apply` получил `stop_done: bool | None = None`; для `None` признак `_fault_stop_done` читается внутри `_run_lock` в одном критическом участке с `transition` и записью состояния (не отдельным чтением до замка). Явное `stop_done=True/False` (тесты 1.1) работает как раньше.
   - Успешный `ack` пишет `last_fault.acknowledged_at = time.time()` (значение `last_fault` заменяется целиком, под тем же замком); признак `_fault_stop_done` сбрасывается существующим правилом выхода из `fault`.
   - Успешный START (`new is running`) обнуляет `_run_last_fault` под замком; отказанный START (`not_ready`, `fault_unacknowledged`) и такт `last_fault` не трогают.
3. **`ack_allowed`:** `_run_ack_allowed()` (под `_run_lock`: `fault` и `_fault_stop_done`) — в `system.run.status` и в стор-листе `system.run.ack_allowed` (общая дедупликация `_publish_run_state`). Авария при `run_gate: false` (`_fault_stop_done` сразу True) теперь тоже публикует состояние (без этого `ack_allowed` в сторе остался бы False).
4. **`system.shutdown` из `fault`, STOP в `fault`** — уже были верны (проверено слепыми тестами 6, 9).

## Что я оставил открытым / ненадёжным

- Мутация B («ack без `_run_lock`») моделирует гонку добавлением `sleep(3 мс)` между проверкой и записью, как у слепого тестера; реальная гонка с окном в микросекунды тестами не доказана. Настоящая защита — чтение `_fault_stop_done` и запись состояния в одном `with self._run_lock` внутри `_run_apply` (в коде так).
- Сквозного теста через настоящий `CommandManager` нет (см. выше); класс R подтверждён только отсутствием `executor` в регистрации на двойнике.
- Приёмка стенда (авария → 5 с в `fault` → START → `fault_unacknowledged` → ack → `ready` ≤ 1 с → START → `running`, `last_fault` null) юнитами не покрыта; ограничение «≤ 1 с» не проверялось.
- `ack` при ошибочном ответе (`no_fault`, `fault_stopping`) тоже заменяет `_run_reasons` свежей оценкой (так же делает START); в `running` ack `no_fault` до следующего такта подменяет `reasons` результатом оценки — безвредно (то же, что даст такт), но это не «ничего не трогает».
- Состояние `stopping` + ack → `no_fault` по таблице 1.1; тестера это устраивает (тест 4), дизайн §3.2 говорит то же.

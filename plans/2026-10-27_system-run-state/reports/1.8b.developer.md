## L1 — где и почему (критерий: менять там, где нарушен инвариант)

Инвариант: новое воплощение процесса стартует со статусом `initializing` (boot, switch — так и есть: запись PSR создаётся с
`INITIALIZING`). Нарушает его рестарт: он единственный путь, где запись PSR ПЕРЕЖИВАЕТ замену воплощения.

Разбор трёх вызовов `SRM.register_process` в `process_manager_process.py`:
- `:424` — PM регистрирует сам себя в `initialize()` (единожды, защита от повтора выше): записи нет, ветка «новая запись».
- `:5056` — boot (`_create_processes_from_config`): имена новые, записи нет.
- `:6043` — `_topology_provision` (switch/apply): cleanup перед ним снимает запись (`unregister_process`), записи нет.
Все три идут с `reuse_queues=False`. Единственный вызов с уже существующей записью — `:5467` (рестарт).

Правило PSR «запись есть — статус не трогать» (`process_state_registry.py:83-99`, пришло в `b136863d5`, «Рефакторинг»: коммит
добавил `RLock`, `register_process` стал идемпотентным «зарегистрировать или обновить»; `update_state` вызывает его под тем же
замком, `add_queue`/`add_event` — тоже). Это свойство самого реестра: им пользуются дочерние процессы
(`process_runner.py:382`, `bundle_builder.py:64,113`) и `update_state` — повторная регистрация живого процесса обязана быть
безвредной. Менять правило нельзя: оно защищает живые записи.

Почему (б), а не (а) (`SRM.register_process(reuse_queues=True)` ставит `INITIALIZING`):
- `reuse_queues` — про очереди; статус воплощения — отдельный факт. Связь через флаг неявная.
- (а) НЕ лечит путь с откатом `restart_reuse_queues: false`: там `reuse_queues=False` при существующей записи — дефект
  остался бы. (б) лечит оба.
- «Рождение воплощения» знает PM (`restart_process`: он остановил старое, снял его из реестра ОС и создаёт новое); SRM о
  воплощениях не знает.
- (б) использует существующий публичный `update_state`, API не расширяется; `update_state` ещё и эмитит `PROCESS_STATE_CHANGED`.

Тонкость: сброс стоит ПОСЛЕ `remove_process` и `register_process`, до `create_and_register`. Смерть старого воплощения, если
монитор успел её увидеть, записывает `stopped`/`crashed` ДО сброса — сброс перекрывает.

## L2

Смерть pid, равного `_restarting[name]`, — исход собственного решения супервизора. Выход ранний: нет события `crashed`, нет
записи статуса в PSR/`previous_states`, нет `_try_auto_restart`, нет `_broadcast_shm_reclaim` (см. «Открыто» п. 3). Любой другой
pid (в т.ч. нового воплощения до первого heartbeat) идёт дальше как честное падение (H1). Pid `None` (реестр не знал pid в
момент решения) или не `int` — не совпадает, вело себя так же и в 1.7c.

## L3 — ручной `process.restart`

Отдельного кода нет: ручной рестарт ведёт себя как автоматический за счёт L1+L2. Слепые 5a (старый выходит с 0) и 5b (с -15)
зелёные. Разложение по мутациям: без L1 5a/5b остаются зелёными (L2 глотит смерть старого, статус не портится); без L2 5a
зелёный (смерть `0` пишет `stopped`, затем сброс L1 его перекрывает), 5b красный (`-15` -> `crashed` -> авто-рестарт). Значит
оба слоя нужны и каждый закрывает свой кусок.

## Обход симптома (`process_monitor.py` ~стр. 898–901)

Комментарий фиксировал симптом «после рестарта prev_status="crashed" не проходит промоушен» как довод в пользу критерия
`recovered` по heartbeat. С L1 причина исчезла. Оценка: сам критерий `recovered` по heartbeat НЕ удаляется и не меняется
(по брифу не менять; и он не пустой обход): промоушен до `running` срабатывает уже на живом объекте, без heartbeat, поэтому
«воплощение поднялось и отчиталось» по статусу не определить — heartbeat остаётся нужным сигналом. Устарел только довод;
переписал две строки комментария (код не менялся). Блокировка по `_restarting` в условии `recovered` (1.7c) — не обход, остаётся.

## Что я оставил открытым / ненадёжным

1. **Стенд не гонял.** Стендовые пункты ACCEPTANCE (`kill -9` через 35 с лечится второй раз; одна поломка SIGSTOP = один рестарт;
   `supervision_status` без мигания) — только на юните с двойниками процесса ОС. Порядок «старый мёртв, ещё в `os_processes`»
   на настоящем `ChildProcessStop` я не измерял: тест H2 тикает настоящий цикл монитора, но стоп — двойник с `sleep`.
2. **Гонка H5 (статус из heartbeat) не вылечена** — `xfail(strict=True)` в hazard-файле. Окно: от позднего heartbeat старого pid до
   следующего такта (<= `poll_interval`), эффект — ложный `status_changed paused` на GUI и один такт чужого статуса.
3. **`_broadcast_shm_reclaim` при смерти заменяемого воплощения больше НЕ рассылается** (раньше уходил, если такт монитора
   видел смерть до `remove_process`, — то есть по гонке). Довод: смерть
   заменяемого воплощения — не «читатель ушёл» (ADR-PMM-030: рестарт стопит со `mark_reader_gone=False`, очереди
   переиспользуются). Но займы SHM старого воплощения при рестарте теперь не возвращаются через этот путь вовсе —
   отдельного пути реклейма на рестарте я не нашёл (`git grep reclaim` по PM). Это OUT OF SCOPE по Task («займы нового
   воплощения на переиспользованных очередях»), но моё изменение сдвигает порог: нужна проверка лидом/на стенде с
   `FW_SHM_LOAN_PROTOCOL` on. Если лид решит оставить рассылку — нужен дедуп по pid (иначе будет повтор на каждый такт окна стопа).
4. **`update_state` без охраны на `None`:** `restart_process` предполагает `shared_resources.process_state_registry` не `None`
   (у настоящего SRM он всегда есть; монитор читает его так же). Моки с `shared_resources=MagicMock()` проходят.
5. **Слепой `_Rig` и `_Registry` импортируются hazard-файлом из слепого файла** (приватные имена; так делает и остальной набор с

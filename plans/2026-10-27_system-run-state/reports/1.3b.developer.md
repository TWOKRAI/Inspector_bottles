## Что я оставил открытым / ненадёжным

* **M1 выжил как эквивалентный мутант**: `max(self._percent, ...)` в `advance` избыточен (процент монотонен по построению через
  max долей шагов). Оставил по тексту задачи («max с прошлым»); защиту реально держит `max` по долям шага (M1b).
* **Объединение готовых (M5) слепой набор не ловит**: слепые тесты закрывают его лишь косвенно (процент и итог 100/`done`); поймал только мой
  `test_waves_union_...` на искусственной цепочке с выключенным итоговым барьером. На реальном boot итоговый барьер даёт надмножество, поэтому на
  проценте различие в основном не видно — свойство — страховка, а не наблюдаемое поведение.
* **Стенд — фейковый реестр и `StateStoreManager` без IPC**: живой стенд `dualcam_synth` headless и опрос `backend_ctl state_get_subtree system.progress`
  (вторая часть ACCEPTANCE: первое значение >= 50, затем 100/`done`, без убывания) **не запускал** — числа стенда в отчёт не вошли. Нужен прогон лида.
* **Ступенька 50 % на плоском boot** — принято осознанно (барьер не менялся); оператор видит 50 % до `boot_ready_timeout_s`. Задокументировано в README.
* **Сбой записи логируется `_log_warning`** (а `_state_op` сам пишет только debug). Если WARNING на каждый сбой стора шумно (6 записей за boot) — это решение лида.
* **N = число `valid` по конфигу**, не число реально нужных процессов; процесс, провалившийся при create, остаётся в N (метка `запущено k из N` это показывает).
* Состояние шкалы живёт в атрибутах PM и не потокобезопасно по построению (один писатель — initialize-поток); защищено тестом на поток записи,
  но не замком: если кто-то позже позовёт хук не из initialize, гонку замок не остановит — поэтому после `finish` трекер снят.
* Полный каталог тестов не гонял (семафоры); sentrux-проверку слоёв не запускал — новое ребро `process_manager_module -> process_module.progress` того же яруса, что уже существующее `process_module.health.schema`.

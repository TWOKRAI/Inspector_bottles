## Что я оставил открытым / ненадёжно

1. **2a слабый.** Снимок считается раз в 0,5 с, окно серии 1,05 с — в окно помещается максимум 3 такта снимка, граница «не более 3» совпадает с этим максимумом.
   Удаление строки антидребезга (`_last_push_at`) тест НЕ убьёт. Настоящая проверка: граница `<= 2` при окне 1,05 с, либо серия на стенде с быстрым снимком;
   но `<= 2` не следует из брифа — не менял.
2. **9 / 9b слабые.** Условие «регулярный унёс снимок раньше внеочередного» гонкой внутри потока снимка (между записью снимка и вызовом push — микросекунды) снаружи не воспроизводится.
   Тест проверяет следствие: после внеочередного и регулярного с тем же снимком других сообщений вне сетки нет. Убивает «push на каждом такте при not ready» и «не обновлять ушедшее
   в регулярном пути» только если это даёт видимые лишние сообщения; тонкий дубль «регулярный первым, потом внеочередной» не пойман.
3. **Критерий 3 зависит от гонки старта.** Предусловие: первое сообщение с `readiness` уже `ready False`. Во всех трёх прогонах так и было; на очень быстрой машине первый heartbeat мог бы
   уйти уже с `ready True` — тогда тест упадёт на предусловии (с понятным текстом), а не пройдёт вхолостую. Если это станет флаком, предусловие надо ослабить, а не удалить.
4. **Сетка регулярных heartbeat (6 расписание, 9)** меряется по моментам прихода в очередь (допуск 0,4 с, интервал 3 с, ~8–10 с на тест). На сильно загруженной машине допуск может не хватить.
5. **Не покрыто:** уменьшение набора блокирующих причин при неизменном `ready` (A и B падали, B починился); смена ТЕКСТА причины при тех же `node`/`severity`;
   смена `ready` при одновременной смене `paused`; поведение при `heartbeat_interval <= 0`; сбой отправки внеочередного по новому триггеру (есть только у paused в старом файле).
6. Тесты читают внутренний `proc._readiness_snapshot` (как `test_heartbeat_paused_push`) — только как предусловие «снимок смену увидел»; поведение проверяется по принятым сообщениям.
7. Стенд в одном интерпретаторе с daemon-потоком и глобальный `SHARED`: параллельный запуск (xdist) не рассчитан. Машинный `machine_gate.sh` не использовался (прямой запуск по брифу).
8. В логах стенда шум `Queue 'system' not found for 'ProcessManager'` — так же и в соседних тестах, на результат не влияет.

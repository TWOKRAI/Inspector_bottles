## Решения, которые DESIGN оставил мне

- **Аннотации `Optional[Event]`** в `process_registry.py` / `process_runner.py` вместо `Event | None`. Причина: в этих модулях нет
  `from __future__ import annotations`, а `multiprocessing.Event` — функция. `Event | None` падал на импорте:
  `TypeError: unsupported operand type(s) for |: 'method' and 'NoneType'`. Соседний параметр `system_ready_event` написан так же.
- **Кэш `_run_published`** (уровень класса, как `_system_stop_published`). Нужен для «неизменённые значения пропускаются».
  Без стора кэш не трогается (иначе boot-запись `ready` при подключении стора позже была бы ложно «записана»).
- **В стор пишется `state.value` (строка), не член `RunState`**: правило Dict at Boundary.
- **`_run_since` — `time.time()` (wall)**: значение для GUI/стора. Меняется только при смене состояния; no-op переход его не трогает.
- **Ответ STOP при коде отказа** (в 1.1 это только `shutting_down`) — `{"success": False, "state", "error"}` без `accepted`, литерал DESIGN.
  `accepted = prev is running` (код `None` уже проверен), затем `_run_apply("settled")` с `ready=None` (последний `tick`).
- **`None` у `run_gate`** — без WARNING: неотличим от «ключа нет». Тест допускает 0 или 1.
- **Текст WARNING**: `"run_gate негоден (нужно true или false) — гейт работы выключен"`, без значения ключа.

## What I left open / unreliable

- **Живой стенд (ACCEPTANCE `backend_ctl`, счётчик `cycles`) не проверялся** — стадия лида. Полный путь `initialize()`
  (`_publish_run_state()` после `_setup_state_store()`, `settled` после `_wait_boot_ready()`, регистрация трёх команд в
  `CommandManager`) не исполнен ни одним тестом: тесты собирают PM через `make_pm` + `_create_components()`. Нужна проверка:
  стенд, `system_command system.run.status` → `state == "ready"`; `state_get system.run.state`.
- **TOCTOU в `system.run.start`.** Проверка `_pm_stopping() or _system_stop_snapshot()` идёт ДО `_run_apply("start")`,
  вне `_run_lock`: так требует листовой замок (`_system_stop_snapshot` берёт свой замок). Если системный стоп начнётся
  между проверкой и записью, START может взвести событие в момент гашения. Окно закроет Task 1.4: подача `shutdown` в машину
  даёт `shutting_down` под тем же замком. В 1.1 вред ограничен: при стопе дети и так гаснут.
- **Сбой стора не виден.** `_state_op` глотает исключение и не возвращает итог, поэтому значение помечается записанным и при сбое.
  Повтор будет только при следующей смене значения. `_publish_system_stop` проверяет ответ стора, этот путь — нет: DESIGN велит
  `_state_op`. Если нужна та же строгость — решение лида.
- **Слабость `test_run_state_published_in_order`.** Инъекция «снимок до `_run_publish_lock`» остаётся зелёной: сон фейка
  стоит внутри записи, а нужное окно — между снимком и захватом замка. Реализация берёт снимок под замком (по DESIGN), но тест
  этого не доказывает. Сильная проверка: фейк замка/снимка, который спит между `_run_snapshot()` и входом в publish-lock.
- **Race-тест ловит инъекцию «toggle вне замка» на macOS со сном 1 мс.** На Windows и под другой нагрузкой не проверял.
- **Windows-spawn не проверял.** Событие идёт Process-kwargs (как `system_ready_event`, ADR-PMM-034), в bundle custom его нет,
  но spawn-тест гонялся только на macOS.
- **Полный прогон двух каталогов на этой машине — не вердикт** из-за исчерпания семафоров (ENOSPC). Сравнение с HEAD — по
  разнице множеств и изолированным повторам. Прогон лида на чистой машине надёжнее.
- **`config_of` на каждый source-плагин зовётся один раз в `_init_data_pipeline`.** `run_gated` живой правкой конфига
  плагина не переключается. Это по DESIGN; горячая смена — не в 1.1.

# C-36: вердикт cto по эскалации — BLOCK слияния до правки транспорта (2026-11-26)

`a0ac1a2d3a87dfa55`; ветка `fix/c36-fresh-queues` (`0b71ec3db` + `2a67fbbb7`). Записано лидом по ответу cto.

**Причина.** Выживший писатель, положивший в брошенную очередь больше буфера pipe и применивший `routing.refresh`, не
выходит сам: `release_queues_at_exit` берёт очереди только из текущего PSR (`queues/core/manager.py:219-221`), а
`drop_process_queues` её уже снял, поэтому метка ADR-PMM-030 не читается. В сценарии (з) наступает всегда. Воспроизвёл
cto: без отпуска, 40 x 1 КБ — не вышел за 8 с; с отпуском при сбросе — `exit 0`, join 0,06 с (метка взведена и нет).
**Опровергло бы вердикт:** правка больше одной функции и двух мест вызова — тогда объём решает владелец.

## Дизайн правки (обязателен)

- Одна функция `retire_queue(q) -> int` в `queues/core/reader_gone.py`: посчитать буфер; `q.close()`; под `q._notempty` —
  `q.cancel_join_thread()`; `q._released_at_exit = True`; вернуть число из первого шага. `Event` метки не читать и не
  взводить (замок может быть осиротевшим). Очередь без запущенного feeder'а — то же, счёт 0. `_notempty` нужен против
  гонки с первым `put` (вывод по stdlib по памяти — сверить с `multiprocessing/queues.py` 3.12).
- Вызов 1: внутри `ProcessStateRegistry.drop_process_queues` — объекты снять под замком реестра, отпускать вне замка.
- Вызов 2: PM, `_restart_process_replace` при `reuse_queues=False`, сразу после метки, на тех же брошенных объектах.
- Счётчики `queues_retired`, `buffered_dropped_at_retire` в статистике реестра очередей.
- `release_feeders_at_exit` для обычных очередей не меняется; метка PM остаётся.
- Документы: абзац в ADR-PMM-054, дополнение ADR-SRM-016; остаток назвать прямо (сообщения в pipe брошенной очереди
  теряются без счёта; заблокированный daemon-feeder живёт до выхода процесса).

## Тесты (литералы, выход в daemon-потоке со сроком)

1. Настоящие PSR и реестр очередей в spawn-ребёнке: 40 x 1024 Б соседу без читателя -> `drop_process_queues` ->
   `release_queues_at_exit(..., False)` -> `exitcode == 0` за 5 с; два варианта: метка взведена и нет.
2. `queues_retired == 1` после одного сброса одной записанной очереди.
3. `put` после сброса: доставка возвращает отказ и счётчик ошибок +1.
4. Hazard автора: первый `put` одновременно со сбросом -> `exitcode == 0` за 5 с; если инъекция «`cancel_join_thread`
   вне `_notempty`» не падает за 200 повторов — записать как неподтверждённую гонку.
5. Очередь, в которую не писали: сброс -> exit 0, счётчики 0.
6. PM-писатель: 40 x 1024 Б в очередь ребёнка, `restart_process` со свежими очередями -> выход PM не ждёт feeder старой
   очереди; тест красный без вызова в PM.

После правки: `sentrux check .` (импорт `state` -> `queues.core.reader_gone` без цикла), радиус
`test_writer_outlives_*`, `test_pm_marks_gone_*`.

## Условия стенда (добавлены)

1. После (з) для приёмника и после `process.restart` приёмника под потоком — системный стоп: `stop_outcome == "exited"`
   у каждого, `terminated`/`killed` 0, время стопа не больше контроля + 1 с.
2. `queues_retired` у `vision` и `line` = числу рестартов приёмника.
3. Свободные слоты кольца SHM до и после рестарта — без изменения.

2 x fps и каскад из 3 рестартов остаются условиями до слияния, на сливаемом HEAD.

Цепочка на настоящем PM и ребёнке; зависание PM на своём выходе (по чтению); тот же дефект на topology switch на стороне

займы SHM у кадров, застрявших в брошенной очереди.

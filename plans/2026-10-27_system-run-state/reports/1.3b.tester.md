## Допущения (не слепые части — форма, не контракт)
1. Лист boot читается из стора как dict по пути `system.progress.boot` (`store.store.get`), запись — через `handle_state_set`
   (как `_publish_run_state`); дельты `system.run.*` писать в тот же стор допустимо.
2. N = число записей `processes_config` с ключом `class` (как `valid` в `_create_processes_from_config`).
3. Стор подключается подменённым хуком `_setup_state_store` до первой публикации; лист «5» пишется после подъёма стора.
4. Последовательность сравнивается с «схлопнутыми» подряд идущими повторами: `advance("ready")` (100) и `finish` (100, done)
   могут быть двумя записями; требую done=true РОВНО у одной записи (finish один раз).
5. N=0: допустимые проценты записей — только {5, 100}; финал 100/done.
6. k=N: `label` не содержит «запущено» (в брифе — «если k < N»); при k<N — подстрока «запущено 2 из 3».
7. «Значение шага» в тексте ValueError = переданная строка шага (и переданная доля 0.4242); тест ищет подстроки.
8. После ValueError трекер остаётся рабочим; `advance` не ставит `done=True` даже на 100.
9. Сбой записи имитирую выбросом из `pm._state_op` на записи с percent=20 (сам `_state_op` исключения обработчика уже глотает —
   это не то, что проверяется); ожидание дошедших до стора: 5, 35, 50, 100 (запись 20 потеряна, 35 не «переиграно»).
10. Волны: «готовы объединением» проверяю косвенно (монотонность по записям + итог 100/done на цепочке a<-b<-c с мёртвым b);
    ready-события и жизнь процессов — из фейкового реестра, барьеры — настоящий код.
11. Тест «не трогают лист» гоняет `_run_apply(tick/start/stop/settled/apply)`, `_settle_run_state()` и настоящий
    `restart_process` на `make_readiness_pm`; лист boot засеян вручную (запечатанный 100/done).

## Что я оставил открытым / ненадёжным
- `run_gate: false` и «без стора» (boot прежний) НЕ покрыты: лимит 10 функций. Без стора `_state_op` — no-op, но то, что
  издатель не падает без стора и не пишет, ничем не доказано.
- Реальный `topology.apply` (`_cmd_topology_apply`) в «не трогают лист» не гоняется — только событие `apply` машины
  состояний и `restart_process`; путь apply целиком проверит ревью/живой стенд.
- Согласованность цифр «ready 50» проверена только на итоге 100/done: формулу ready-шага (долю при мёртвом b, при liveness-фолбэке)
  тесты не пинят — в брифе она не задана. Монотонность в волнах защищена только от «издателя, пишущего убывающее»; если трекер
  сам зажимает процент, этот тест слабее: настоящая гарантия — инъекция «публикатор берёт ready последнего гейта» (не делалась).
- `updated_at` проверяется только по типу (float), не по свежести/монотонности времени.
- Хрупкость: стенд опирается на внутренние имена существующего кода (`_create_components`, `_state_op`, `_setup_state_store`,
  `_wait_processes_ready`, `os_processes`); смена этих имён сломает стенд, а не тест значений.

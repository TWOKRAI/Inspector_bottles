Стенд: worktree `rs-1.2-inj` (коммит 450fcf329), macOS (Darwin), основной venv, рецепт `recipes/dualcam_synth.yaml`
(`camera_0`/`camera_1` -> `consumer_0`/`consumer_1`, плюс `devices`), `run.py --headless`, `BACKEND_CTL=1 BACKEND_CTL_PORT=8791`.
Запуск через `machine_gate.sh heavy inspector-bottles-85` (окно дано, код 75 не было).
`multiprocess_framework.__file__` = `.../worktrees/rs-1.2-inj/multiprocess_framework/__init__.py` (внутри worktree).

Управление: python-driver `backend_ctl.BackendDriver(port=8791)`. Четыре подъёма приложения:
boot 1 (I, G, H-stop), boot 2 (H-fault, J, K), boot 3 (I повторно, вариации J), boot 4 (повторение «start сразу после ack»).
Скрипты и логи — в scratchpad сессии, каталог `st14/` (`ctl.py`, `i_poll.py`, `g.py`, `h.py`, `jh.py`, `v.py`, `w.py`, `app1..4.log`, `*_out.txt`).

## Находки (не подгонялись)

1. **Критерии G и H выполняются с запасом.** Лист `paused` переключается за 0,36–0,61 с (раньше 2,97 / 4,79 с),
   `stop` без шагов `pre_stop` доводит до `ready` за 0,56–0,65 с (ожидалось <= ~2 с).
2. **Повторный fault после `ack` -> `start` сразу после оттаивания (перемежающийся).** Boot 4, раунд 1:
   `kill -CONT` -> `ack_allowed` +0,33 с -> `ack` -> `ready` -> `start` (+0,36 с от CONT) ответил `running`;
   через 2,09 с после start `state` снова `fault`, причина `нет отчёта о готовности` (source `liveness`, camera_0),
   хотя процесс жив и кадры шли. В первом чтении после start лист `readiness` имел возраст 15,5 с (снимок до заморозки).
   Позже `camera_0 не готов` (+3,08 с), `reasons` пустые (+7,69 с), `state` остался `fault` (липкий). Раунд 2 с тем же
   сценарием и теми же интервалами — без fault (`running` весь 9 с). Boot 3: R1 -> R2 (ack на +0,56 с, start примерно
   на +1,1 с после CONT) — fault сразу после start (в R2 `fault` наступил за 0,01 с после STOP, то есть до заморозки;
   `start` в R2 я не печатал — то, что состояние было `fault` до STOP, выведено по таймингу, не прочитано напрямую).
   Итог: 2 случая из 3 попыток «ack, затем сразу start». С паузой 5 с между CONT и ack (boot 2 J, boot 3 R3 -> R4) — не воспроизводилось.
   Гипотеза (не проверена): liveness-проверка PM читает устаревший `at` листа, который обновляется heartbeat-ом (~5 с),
   поэтому окно после оттаивания до первого свежего снимка даёт ложное «нет отчёта». Это поведение 1.7 (`ack` не ждёт свежего снимка).
3. **`ack` -> `not_ready` в одном случае.** Boot 2, последовательность «stop в fault -> пауза 5 с -> ack»:
   ответ `{"success":true,"state":"not_ready","error":null}`, `ready` лишь через 3,13 с. Та же последовательность в boot 3 (R3)
   дала `ready` сразу. Причины в статусе в момент `not_ready` не снял. Не воспроизведено — один случай.
4. **Шкала загрузки: `label` всегда пустая строка.** Оба подъёма: `percent` 50 -> 100, `label ""`. Если контракт 1.3b
   подразумевает подписи этапов — их нет (или они не доезжают до листа). Всего два значения (50, 100); промежуточных нет.
5. **Порт backend_ctl отвечает уже на `percent 50`, а `done:true` через ~0,7 с.** `state` `ready` выставляется позже:
   `since` = ~5,0 с после `updated_at` шага 100 (boot 1: 1794557416,72 против 411,72; boot 3: 736,31 против 731,24). Шкала 100%
   не означает «можно start»; первое готовое состояние совпадает по времени с первым heartbeat. Что `state` показывал
   в эти 5 с — не читал.
6. **Время до fault 13,3–14,6 с** (раньше 14,67 / 15,27 с); зависит от момента STOP относительно heartbeat. Запас до окна 16 с — 1,4–2,7 с.

## Что я оставил открытым / ненадёжным

- Один рецепт (`dualcam_synth`), один компьютер (macOS, spawn-старт), синтетический источник (30 кадр/с), машина была свободна.
  Реальная камера, Windows, нагрузка (медленные плагины, полные очереди) не проверялись.
- Шаги `pre_stop` с реальным «домой» не гонялись — в рецепте их нет; H2 (0,56–0,65 с) — время STOP без шагов,
  оно не говорит ничего про остановку с pre_stop.
- Находка 2: два случая из трёх, но в одном (boot 3 R2) я не печатал ответ `start` и не читал `state` до STOP, вывод про fault до заморозки
  косвенный. Boot 4 раунд 1 прочитан напрямую. Гипотезу про устаревший `at` не проверял (код продукта не читал).
- Находка 3 — один случай, причины в статусе не сняты.
- Шкала I: шаги 50 -> 100 прочитаны опросом 0,2 с; промежуточные значения короче 0,2 с не видны. Опрос начался при первом ответе порта,
  то есть значения до порта (если были) не читались. На boot 1 / boot 3 одно и то же — два подъёма.
- G замерено с опросом 0,1 с + запрос ~0,01 с; погрешность ~0,1–0,2 с. Интервал `at` 4,53 с — один случай, не объяснён.
- `ack_allowed` в H5 читал статусом (опрос 0,1 с), в `fault` без CONT не мерил, сколько он остаётся `false` при длительной заморозке
  (максимум 14 с до CONT, остановка в аварии не завершается, пока процесс заморожен — по всем замерам).
- На boot 1 `K` снят сырой командой без итогов по детям (в отличие от boot 2–4).
- Листы других процессов (`camera_1`, `consumer_*`, `devices`) не читал.
- Кадры в H3 считал по `camera_0` (`source_producer_synthetic_frame_source.cycles`), `camera_1` не смотрел.
- `resource_tracker` pid 76148 после boot 4 — не наш (старт 11:18, после последнего shutdown); родителя не успел определить.

## S8: займы SHM при замене воплощения (чтение кода, без прогона; коммит `e4a946849`)

(а) `_broadcast_shm_reclaim` (`monitor/process_monitor.py:1110-1143`) при выключенном `FW_SHM_LOAN_PROTOCOL` — **no-op**: строка 1126 `if not is_enabled("FW_SHM_LOAN_PROTOCOL"): return` до любой рассылки; docstring: «Off = прежнее поведение бит-в-бит». Флаг FROZEN, дефолт `False` (`config_module/feature_flags.py:96`, `default=False`, «заморожен выключенным, не развивать»); включают его только пробы `backend_ctl/probes/g7_*_probe.py` (переменной окружения `=1`) и тесты. Прочих включателей в `multiprocess_prototype/` и рецептах нет (`git grep FW_SHM_LOAN_PROTOCOL -- '*.py'`).

(б) Другого пути возврата займов на рестарте нет. Единственный отправитель `shm_reclaim` — `_broadcast_shm_reclaim`, вызывается из `_handle_dead_process` (`process_monitor.py:1094`) после обновления статуса; единственный получатель — `GenericProcess._handle_shm_reclaim` (`generic_process.py:400-410`) → `FrameShmMiddleware.reclaim_reader` (`frame_shm_middleware.py:922`) → `pool.reclaim` (`loan_ledger.py:210`); `git grep "\.reclaim("`/`reclaim_reader(` вне тестов находит только эту цепочку. ADR-PMM-030 — не про займы: это метка «читатель ушёл» на очередях PM; `restart_process` её сознательно не ставит (`process_manager_process.py:5452` «метку НЕ ставить — очереди переиспользуются новым воплощением», `stop_process(..., mark_reader_gone=False)`), то есть возвращать займы она не может. Комментарий `frame_shm_middleware.py:926` называет инициатором реклейма «supervisor/incarnation», но «incarnation»-пути в коде нет (grep выше).

(в) Вывод: ранний выход `if self._is_replaced_incarnation(proc): return` (`process_monitor.py:1042`) стоит ДО `_broadcast_shm_reclaim` (строка 1094), поэтому для pid из `_restarting` реклейм больше не рассылается. **Регрессия существует только при включённом протоколе** (флаг off — рассылки и так нет, поведение не изменилось). При включённом: затронуты только смерти, о которых супервизор уже решил рестарт (его собственный STOP-случай `unresponsive` → завершение замороженного воплощения; ручной `process.restart`), там читатель держал займы и теперь не освобождается; смерть, ещё не помеченная `mark_restarting` (обычный `kill -9` → `crashed` → рестарт), проходит ниже и реклейм рассылает, как раньше (в S1/S4/S5 в логе этот путь отработал бы). Живого прогона с флагом ON не было (только код); стоит ли это замораживаемого протокола чинить — решение лида (принцип 3: заморожено, не развивается).

## Находки

1. **Главное ожидание 1.8b выполнено: каждое падение лечится.** S1: 3 из 3 `kill -9` на одном подъёме — новый pid через 2,09–2,65 с, кадры растут через 3,06–3,40 с (раньше второй сбой не лечился совсем: R1#2/R1#3, R2#2, P-on#2/#3). S4 (без флага): 2 из 2, fault → ack → start. S6: рестарт после двух ручных `1/3`. Тупика «`ack` → `not_ready` «процесс не жив» бессрочно» нет ни в одном из ~16 сбоев.
2. **Двойного перезапуска нет.** S2 (STOP при флаге ON ×3): один сдвиг pid за круг, `exitcode=-15` в логе 0, `restarting` — одна строка на сбой; было 22023→22342→22350 (2 из 2).
3. **Мигание `supervision_status` ушло.** В покое после ready 0 из 402 выборок (S1) и 0 из 402 (S2) со статусом ≠ `running` при `alive: true` (раньше 67–95 % и `running` 0,3 с каждые ~5 с). Единственные выборки ≠ `running` — на самом перезапуске (~0,5 с `crashed`/`unresponsive` у нового pid, 6,5 с `unresponsive` у ещё живого замороженного pid в S2).
4. **Счётчик попыток — окно 60 с, не «k-й сбой за подъём».** S1 круг 3 и S2 все круги дают «попытка 1/3»/«2/3» при 2–3 рестартах (метки старше 60 с не считаются); `restart_count` ≠ `instance_restarts` (S1: 2 против 3). Это дизайн `RestartPolicy.window_sec`, но ожидание «1/3, 2/3, 3/3» в брифе при выдержке 35 с недостижимо; 1/3→2/3→3/3→gave_up показано в S5 (интервал 8,5 с).
5. **Исчерпание (S5) работает и громко:** `[ERROR] gave_up — 3 рестартов за 60.0с (crashed) → сдался`, статус `failed` через 0,52 с, `fault` через 0,85 с с причиной «супервизор отказался от перезапуска», деталь — в `last_fault`. Замечание: в живом листе эта причина держится 0,52 с (+0,85 … +1,37 с), дальше остаётся только «процесс не жив»; пока `failed`, `ack` → `not_ready`, `start` → `not_ready`, выход — ручной `process.restart`. Отказ `ack` в `failed` — правдивое поведение (процесса нет), но оператор видит после 0,5 с причину «процесс не жив» вместо «супервизор сдался»; не дефект 1.8b, в ACCEPTANCE не входило.
6. **Побочное:** `restart: 'camera_0' ready via liveness-fallback (event не получен за 0.5s; подряд таких: 4/5/6)` в `app1.log` после ручных и авто-рестартов (счётчик «подряд» уже 4 на первом же предупреждении ⇒ три прежних рестарта этого подъёма тоже прошли через fallback без WARNING; см. `restart_process` / `_wait_processes_ready`, ADR-PMM-011). Ready-событие на рестарте не доходит за 0,5 с (6 из 6 рестартов, по счётчику), рестарт закрывается по liveness. К 1.8b не относится (механизм из Ф3.2); отмечаю как наблюдение.
7. **`instance_restarts` +2 за один ручной рестарт** в S5-допроверке (после `failed`: 3 → 5; в S6 один ручной рестарт давал +1). Не расследовано.

## Что я оставил открытым / ненадёжным

- **Старого поведения на этом стенде я не воспроизводил**: числа «раньше» (R1#2 / P-on#2, 22023→22342→22350, мигание 67–95 %) взяты из отчёта прежнего стенда `1.6-1.8-1.7c.stand.md` (коммит `def2fe874`), а не из прогона того же скрипта на старом коде. Сценарии наблюдения у меня другие (`kc.py`: без stop/start между кругами, без `settle` перед каждым kill), так что сравнение количественно приблизительное; качественно (новый pid на каждом сбое, нет двойного рестарта, нет мигания) совпадает с тем, что 1.8b должен был вылечить.
- **S1 круг 3 «попытка 2/3», не 3/3** — объяснено окном 60 с по арифметике (95 с между метками) и подтверждено S5 (3/3 при интервале 8,5 с); «окно протухает метки» читал по логике `restart_count` и по коду `restart_policy.py:82`, но прямо внутренности окна не проверял.
- **Один подъём на сценарий, один проход на кружок.** Число сбоев: S1 3, S2 3, S4 2, S5 4+1, S6 1 (всего 14 сбоев/рестартов + 2 ручных в S6). Это не серия: редкая гонка (например, kill в момент `backoff` или во время `ready` нового воплощения) могла не попасться. Сбой внутри окна `backoff`/до первого heartbeat нового pid — условие, ради которого 1.8b вводил «воплощение», — **специально не воспроизводил** (kill через ≥ 8 с после предыдущего). Покрытие этого — только юнит 1.8b, не стенд.
- **S3 с «мигание ≠ 0» ждал в покое, не на кадре после рестарта.** Полные 35 с в покое — 0 из 134 ×6 окон; на самом перезапуске ~0,5 с `crashed`/`unresponsive` с `alive: true` (1 выборка из 34–35 при KILL, 7 из 84–92 при STOP) — не считаю миганием, но если «≠ running при alive» понимать буквально, ожидание «0» для окна самого перезапуска не выполняется.

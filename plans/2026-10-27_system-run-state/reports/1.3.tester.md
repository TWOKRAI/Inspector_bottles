## ВОПРОС ЛИДУ (допущения там, где DESIGN не называет API)

1. Форма `leaves` в `evaluate`: принял `leaves[name]` = сам dict `readiness` (`{"ready","reasons","paused","at"}`),
   нет ключа = нет листа; `alive[name]` — bool. Если у `_readiness[sender]` обёртка (например `{"readiness": ..., "updated_at": ...}`),
   пять тестов `evaluate` правятся одной функцией `_leaf` в test_run_state.py.
2. Форма причины: dict с ключами `severity` / `source` / `node` (`severity` взят из standards.md §9.2:
   `failure`, `check_function`, `out_of_spec`, `maintenance`). Ключ текста причины (`message`?) не назван — не проверяю.
   У причин, добавляемых `evaluate` (`liveness`, `report`), ожидаю `node` = имя процесса.
3. «Такт монитора» = одна итерация `monitor._run_iteration()` (под `monitor._iteration_lock`). Если лид поставит
   вызов оценки в `_monitoring_loop` вне `_run_iteration`, функция `tick` в test_run_commands.py правится на
   вызов цикла с коротким `poll_interval`; прочие тесты не меняются.
4. Состав ожидаемых процессов = ключи `pm._process_configs`; `run_required` — на верхнем уровне конфига процесса
   (по образцу ключа `protected`, `process_manager_process.py:2146`); живость процесса — `get_process_by_name(name).is_alive()` /
   `os_processes` реестра (`MockProcess` в `make_pm`).
5. Интервал heartbeat PM может читать из ключа `heartbeat_interval` или `heartbeat_interval_sec` (в кодовой базе есть оба).
   В стенде заданы оба = 5.0; «снимок устарел» везде = на час в прошлом, «свежий» = `time.time()`; границу `stale_s` PM-тесты не пинят
   (её пинит `evaluate`-тест: 2.5 с — свежий, 3.5 с — устарел при `stale_s` 3 с; ровно `stale_s` не проверяется — DESIGN говорит «старше»).
6. Форма `last_fault` не названа: проверяю только `is not None` и что имя узла `cam` встречается в `repr(last_fault)`.
7. Ответ START в `fault` (`fault_unacknowledged`) беру из таблицы 1.1; список `reasons` в нём не проверяю (текущие или аварийные — не названо).
8. Заглушка `evaluate` из scratchpad использовала порядок проверок «нет листа/устарел -> «не жив» -> причины листа». Тесты порядок
   между «нет листа» и «не жив» не пинят (мёртвый процесс в `evaluate`-тестах — только вне `expected`).

## Что я оставил открытым / ненадёжным

- Не покрыто REDS (по правилу «ровно REDS», но есть в DESIGN п.1): причина «процесс не жив» (`alive[name]` False при свежем
  листе); `check_function` блокирует START и в `running` равен потере готовности (К3); `out_of_spec`/`maintenance` не блокируют.
  Дешёвые параметры в `test_fresh_leaf_...` или отдельные тесты — решает лид.
- Не покрыто: публикация `processes.<n>.readiness`, `system.run.reasons`, `start_allowed`, `last_fault` в стор
  (нужен `_Store`-двойник и имена путей из design.md §4 — я их не читал); непрерывная оценка вне `running`
  (`ready` -> `not_ready` на такте при пропаже отчёта — проверено только через START); переход `booting` -> `ready/not_ready`
  по `evaluate` в `initialize()` (в стенде boot = `_run_apply("settled", ready=True)`, как в 1.1); `apply` -> `booting`.
- Гонки/замок держателя (TRAPS: снимок `_readiness` копией под замком, `evaluate` вне замка) не покрыты — hazard-тесты за автором.
- Тесты PM-уровня зелёными я не видел: реализации нет, для неё нет заглушки. Их приёмка зависит от допущений 3-5; ошибка допущения
  даст красный «не по той причине» уже после GREEN — лиду смотреть первую ошибку, а не сам факт красного.
- `test_fault_stays_fault_when_readiness_returns` до GREEN красный на промежуточном «дошли до `fault`»; «липкость» как таковая
  проверяется только после реализации потери готовности.
- Стендовая приёмка (заморозка процесса, `fault` за `3 x heartbeat_interval + 1 с`, кадры 0) здесь не воспроизведена — только юниты по REDS.
- Тест 1.1 `test_status_reports_ready_after_boot` не трогал (по условию заменяет лид); в `test_run_command_replies` (1.1) после 1.3
  при пустой топологии ожидание `reasons == []` остаётся верным (набор пуст -> готов).
- Перекрёстный импорт: test_run_state.py импортирует хелперы из test_run_commands.py (`beat`, `tick`, `make_readiness_pm` и др.) —
  из-за ограничения FILES на два файла; если лид заведёт общий helper в conftest.py, импорт переедет.

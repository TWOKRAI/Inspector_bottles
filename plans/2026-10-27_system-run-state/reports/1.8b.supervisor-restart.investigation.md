## Итог

Две ошибки, одно семейство: **статус супервизора привязан к имени процесса, а не к воплощению (pid)**.

1. **Находка №1 (второй сбой не лечится, «мигание») — статус прежнего воплощения переходит к новому.** Монитор при сбое
   пишет `crashed` / `unresponsive` в PSR. `restart_process` регистрирует новое воплощение через
   `SRM.register_process` -> `PSR.register_process(name)`; запись уже есть, статус не сбрасывается. Монитор каждый такт
   читает PSR и перезаписывает `previous_states` этим старым статусом. Повышение до `running` идёт только из
   pre-running статусов. Итог: живое новое воплощение навсегда в `crashed`; его смерть пропускает ранний выход
   `_handle_dead_process`, его зависание — `_check_heartbeat_timeout`. Уверенность HIGH (репро A, S, C; контрфакт fix_a).
2. **Находка №2 (двойной перезапуск зависшего) — смерть воплощения, которое убивает сам рестарт, засчитывается как
   новое падение.** Рестарт держит старый объект в `os_processes` до подтверждения смерти; монитор в это время видит
   «мёртв», статус `unresponsive` не терминальный, `_pending_restarts` уже снят диспатчем -> `crashed` + попытка 2/3.
   Уверенность HIGH для механизма (репро B; контрфакт fix_b); MEDIUM для того, что на стенде сработал ровно этот
   порядок (см. «Открыто»).

Гипотеза стенда «в `os_processes` остаётся старый мёртвый объект рядом с новым» — **опровергнута**: после рестарта
`os_processes=[(41002, True)]` (репро A); `remove_process` снимает по имени срезом (`core/process_registry.py:249`).
Строка `process_monitor.py:1035` — место проявления №1, не причина: для ОДНОГО воплощения ранний выход нужен
(иначе `crashed` и попытка на каждом такте).

## Одна причина или две

Две точки дефекта, одна недостающая сущность — воплощение в машине статусов супервизора:
- №1 — статус не сбрасывается при рождении воплощения (PM/SRM, путь рестарта).
- №2 — смерть заменяемого воплощения не отличается от смерти текущего (монитор, `_handle_dead_process`).
Репро B fix_b показывает независимость: без №2 статус всё равно залипает (`unresponsive`). №2 усиливает №1: второй
`crashed` от старого pid записывается в PSR и залипает уже на третьем воплощении (стенд P-on#2: «`crashed` зависший»).

## Лечение причиной (без кода)

**L1 (№1): новое воплощение рождается со статусом нового воплощения.** Путь рестарта PM
(`restart_process`, `:5466-5467`) регистрирует воплощение в SRM/PSR со статусом `initializing` — как boot и
`switch`. Очереди, `metadata`, `custom` (incarnation, routing) сохраняются: сбрасывается только статус. Дальше работает
существующий путь: такт читает `initializing` (`:808-812`) -> повышение (`:884-894`) -> `running` в PSR. Новых
флагов нет. Где именно — решение исполнителя/ревьюера: (а) `SRM.register_process(..., reuse_queues=True)` ставит
статус `INITIALIZING` (единственный вызыватель с существующей записью — рестарт; проверить вызовы `:424`, `:5056`,
`:6043`); (б) явный сброс статуса в `restart_process` между `remove_process` и `create_and_register`. Не лечение:
сброс `previous_states` в мониторе (п. 5 перезапишет его из PSR на следующем такте), `forget_process` на рестарте
(теряет историю рестартов -> give-up недостижим), удаление `crashed` из `:1035` (повторы на каждом такте).

**L2 (№2): смерть воплощения, которое супервизор сам заменяет, — не новое падение.** В `_handle_dead_process`:
целый `proc.pid`, равный pid из `_restarting[name]` (ставят `_try_auto_restart`, `_cascade_restart`, ручной
`restart_process`), — ожидаемый итог рестарта: без события `crashed`, без `_try_auto_restart`, без терминального
статуса в PSR. Смерть ДРУГОГО pid (новое воплощение упало до первого heartbeat) — честное падение, считается. Это
закрывает и дыру дедупа между диспатчем и первым heartbeat (`:1609`), и ручной рестарт (C exit15), и induced-членов
каскада (NEW-6b), не вводя флагов. Вопрос для ревью: `_broadcast_shm_reclaim` по подтверждённой смерти старого pid
оставить (это факт смерти читателя, не учёт падений) — но он может прийти уже после старта нового воплощения на тех
же очередях; сейчас тот же порядок возможен и без L2 (см. «Открыто»).

Совместимость: R2/ADR-PMM-015 (сброс `_last_heartbeat` при планировании и диспатче) — не затронут; H3 watchdog
(`_recovery_deadline`, `:1647-1679`) — не затронут, тихий провал рестарта по-прежнему ловится; NEW-6b — поведение
induced-членов становится правильным (их выход при рестарте сейчас даёт `stopped`-залипание или лишнюю попытку).
Комментарий `:898-901` устареет (повышение заработает), критерий `recovered` по heartbeat менять не нужно.

## Минимальный набор тестов 1.8b

Обвязка — настоящие `ProcessMonitor`, `ProcessStateRegistry`, `ProcessManagerProcess.restart_process`; pid старого и
нового воплощения разные и заданы явно; ожидаемые значения — литералы.

Слепые приёмочные (tester, до кода):
1. crash -> авто-рестарт -> heartbeat нового -> crash нового: событие `crashed`, `restarting` попытка `2/3`, второй
   `process.restart` отправлен.
2. crash -> авто-рестарт -> новое воплощение без heartbeat > `heartbeat_timeout`: `unresponsive`, попытка `2/3`.
3. После авто-рестарта живое воплощение с heartbeat: `get_supervision_snapshot()[name]["status"] == "running"` на
   каждом из N тактов (нет мигания).
4. unresponsive -> рестарт; старый умирает (`-15`) во время стопа, монитор делает такт до `remove_process`: ровно один
   рестарт (`restart_count == 1`, один `process.restart`, нет `crashed` со старым pid).
5. Ручной `process.restart` из `running`, старый выходит с кодом 0 во время стопа: статус нового `running`; его crash ->
   попытка `1/3`.
6. Исчерпание: 3 последовательных crash разных воплощений в окне -> 3 рестарта; 4-й -> `gave_up`, статус `failed`; при
   флаге ON в `running` run-state даёт `fault` с причиной «сдался» до окна 30 с.

Hazard (автор):
- H1: новое воплощение умирает ДО первого heartbeat (пометка `_restarting` ещё держит старый pid) -> считается
  падением (`2/3`): L2 не глотает crash-loop.
- H2: настоящий поток монитора (`poll_interval` 0,01) + `restart_process` со стопом, где смерть наступает с задержкой;
  50 повторов, у каждого ровно один рестарт; вызов в daemon-потоке с дедлайном join.
- H3: один и тот же мёртвый объект виден много тактов -> ровно одно событие `crashed` (семантика `:1035` сохранена).
- H4: каскад `rest_for_one`: выход induced-члена при его рестарте не засчитан ему как падение; после — `running`.
- H5: поздний heartbeat старого pid со `status: running` после рестарта не меняет статус/лист нового воплощения.
- Матрица инъекций: убрать сброс L1 -> красные 1, 2, 3, 5; убрать проверку L2 -> красные 4, H2; сравнивать по имени
  вместо pid -> красный H1.

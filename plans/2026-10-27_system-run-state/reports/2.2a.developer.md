## Как вызван стоп из `pause` и граница блокировки

Путь: `self._manager.snapshot_registry()` -> `get_driver(id).is_connected` (предпроверка) -> `self._manager.call(id, op, args)` (публичный `DeviceManager.call`, `manager.py:579`; он ещё раз проверяет `is_connected` и зовёт `driver.call`). Без `request_stop_all_begin`, без `_shutting_down`, без `park`.
Граница блокировки потока `run_watch`: обход последовательный, n × срок команды драйвера (n — число подключённых robot/vfd). `shutdown` оркестратора ждёт замок сверки 2 с (`_SHUTDOWN_LOCK_SEC`): при n × срок > 2 с `shutdown` может не дождаться — измерить на стенде (срок `stop` v2 включает запись + ожидание эха). Замков плагина `pause` не держит; `snapshot_registry`/`get_driver` — короткие секции `_registry_lock` без IO (hazard-тест `readiness_does_not_wait_for_a_slow_pause` держит `pause` на медленной команде и проверяет, что `readiness` и `cmd_device_list` возвращаются).

## Поведение очереди после `stop` (RED 8)

Слепые `test_red8_*` зелёные на `RobotSimCore`: после `pause` (`stop` SOFT, без `park`) драйвер v2 принимает следующие `jog_hold` и постановку задания; два задания, стоявшие в очереди, после `pause` и хода драйвера уходят оба. Это ФАКТ П.5, а не гарантия: очередь драйвера после `stop` оператора не удерживается (правка — файлы драйвера v2, вне FILES; вопрос владельцу/координатору).

## Что решил сам вне текста Task

1. Различение v1/v2: `entry.protocol == "delta_v2"` из записи реестра (как `DeviceManager.robot_park_all`, «не из драйвера»); любой другой `robot` — v1 (`abort {"mode": 1}`); константы `_PROTOCOL_V2`, `_V1_ABORT_MODE`, `PAUSE_STOP_LEVEL`.
2. Порядок обхода `pause` — порядок `snapshot_registry()` (вставки в реестр), не сортировка по id (в отличие от `robot_park_all`); слепые тесты порядок не фиксируют (сортируют).
3. Ответ без ключа `status` или с `status != "ok"` (в т.ч. `{}`) — сбой, не только `"error"`; все три реальных драйвера на успех отвечают `{"status": "ok", ...}` (проверено по `_op_abort`/`_op_stop`).

## Что сделано по пунктам

1. **v1 = режим 3.** `_V1_ABORT_MODE = 3` (литерал, не импорт `STOP_IN_PLACE`: по брифу «меняй `_V1_ABORT_MODE` = 3»; в комментарии ссылка на `registers.py:41`); докстринг `pause` и ADR обновлены. В моём файле литерал заменён в одном месте (`red12_manager_error`) и в новых тестах он 3.
2. **Окно `sync_set`.** До цикла `upsert`, под `_workers_lock`: при `connect=True` новым id `_desired_connected[id]=True` (прежнее желание запомнено), затем `_recipe_ids` = старый кортеж + новые id в порядке присланного. После `upsert`: у id с упавшим `upsert` возвращено прежнее желание (нет прежнего — снято). В конце — прежний финальный кортеж из успешных id. Порядок «желание -> кортеж» проверен: читатель `readiness` берёт кортеж, потом желание, поэтому «id в кортеже без желания» (ложный `[]`) возможен только при обратном порядке записи; здесь желание пишется первым. Только `str`-id (непригодный к хешу id уронил бы команду до `upsert`). Прежнее желание ВОЗВРАЩАЕТСЯ, а не снимается безусловно (решение вне текста): оператор мог отключить устройство (`False`), упавший `upsert` этого не меняет.
3. **Лог `pause`.** Тексты сбоев накапливаются в списке, логируются после обхода; цикл записи лога обёрнут в `try/except Exception` с тегом `# no-health:` — сбой логгера не прерывает останов и не подменяет `RuntimeError`. Выбран «лог после цикла» + `try`, потому что один лог после цикла сам мог бы бросить (простейшее без нового механизма).
4. **Лог `readiness`.** Выбран флаг `_readiness_fault_logged` (сброс при следующем успешном чтении), а НЕ удаление лога: хук перехватывает исключение сам, оркестратор его не видит, без лога текст причины поломки нигде не записан. Первый сбой серии пишется, остальные нет; после успешного чтения следующий сбой снова пишется.
5. **Тесты** (`test_readiness_pause_hazards.py`, было 14, стало 19, ожидания — литералы):
   - `test_review_sync_set_window_lists_the_new_device_instead_of_an_empty_answer` — окно: блокирующий `disconnect` старого устройства, `sync_set` в daemon-потоке с join-дедлайном, в окне `readiness == [«r_new не подключено»]`, после команды то же, `removed == ["r_old"]`;
   - `test_review_sync_set_failed_upsert_is_not_listed_and_keeps_the_previous_wish` — упавший `upsert`: не в `readiness`, желание не утекло, прежнее `False` сохранено, поздно добавленный вручную тот же id в рецепт не попал;
   - `test_review_is_connected_raising_stops_the_others_then_raises_once` — `is_connected` бросает у первого в обходе: v1 (`abort mode 3`) и vfd остановлены, затем одно `RuntimeError`;
   - `test_review_logger_failure_inside_pause_does_not_abort_the_walk` — логгер бросает `OSError`: второе устройство остановлено, наружу `RuntimeError`;
   - `test_review_readiness_logs_only_the_first_failure_of_a_series` — 10 вызовов при сломанном снимке = 1 запись, после успешного чтения новая серия = 2-я запись.

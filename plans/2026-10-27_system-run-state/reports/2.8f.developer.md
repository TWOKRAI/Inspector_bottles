### 2. Комбо удаляет устройство по частичному узлу (регрессия относительно сегодня)

Проба на настоящих объектах: в комбо есть `vfd1` (из `device_list`), read-model стартовый replay не получил,
приходит одна дельта `devices.registry.vfd1.enabled = False` и маркер.

```
combo до дельты: 1 vfd1
узел в read-model: {'enabled': False}
combo после одной листовой дельты: 0 None
```

Предложение для `devices_common/combo.py::_on_registry_delta`, перед фильтром по kind:

```python
entry = {**self._registry.get(dev_id, {}), **value}
if "kind" not in entry:
    return  # частичный узел неизвестного устройства
```

Дальше фильтровать и класть в кэш `entry`, а не `value`.

### 3. Вкладка ПЧ показывает STOP по частичному узлу (в задаче не назван)

Та же причина. Пришли только `current_a` и `heartbeat`:

```
['[STOP] f=0.00 Гц  I=1.4 А  Udc=0.0 В  hb=7  rsErr=0']
```

`_apply_vfd_status` подставляет STOP и нули вместо отсутствующих ключей. `merge` шлёт только изменившиеся листья,
поэтому постоянный `running=True` после потерянного replay не придёт. Оператор видит STOP у работающего привода.
Предложение для `vfd/controller.py`: нет ключа `running` → «?», нет числа → «—». Я считаю это обязательным до 1.0.
Код не менял: это вне DESIGN.

## Что осталось открытым

1. **Вложенная доставка внутри обработки дельты.** Если прямой callback или setter крутит цикл Qt (или подаёт
   дельту синхронно), вложенные сообщения доходят до read-model раньше внешней дельты. Вложенный маркер тогда читает
   узел без неё, а внешняя дельта может затереть более новую. Причина: порядок «bindings, потом VM» в `app.py`,
   этот порядок read-model нарушал и до 2.8f. Таких callback среди подписчиков я сплошь не проверял.
2. **Callback крутит цикл Qt во время flush.** Потерь и устаревших значений нет, но пара из внешнего набора может
   прийти повторно с тем же значением. Для ПЧ повтор покажет `rsErr (+0)`. Поведение закреплено тестом H.
3. Принятые расхождения DESIGN: пустой узел приходит как `DELETED`; `set`/`delete` предка без листьев под шаблоном
   узел не будит.
4. Прежнее поведение не менял: в прямом fan-out подписка, снятая callback'ом соседа на той же дельте, всё ещё
   вызывается.
5. Живого стенда не было (он входит в 2.4). qt-mcp и sentrux не запускались.

memory hits: `search.py GUI state bindings fanout delta coalescing` → подходящих уроков по этому механизму нет
(ближайший: `project_gui_system_queue_storm.md`).

прежние значения, и вкладка показывает их под «Нет данных.» или «Данные устарели».

не становится: сегодня комбо не обновляется вовсе.

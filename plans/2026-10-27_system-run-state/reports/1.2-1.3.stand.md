## Находки (не подгонялись)

1. **Каданс `readiness.at` — ~5,03 с, а не ~0,5 с (A4).** Процесс пересчитывает снимок по такту 0,5 с
   (`process_module.py`, воркер `readiness_snapshot`), но в стор лист попадает с heartbeat (`heartbeat_interval` 5 с,
   поле `readiness` в сообщении). Читатель листа видит снимок со сдвигом до 5 с.
2. **`paused` в листе отстаёт от реального события (B3, C3):** кадры реально идут/встают за 0,12–0,13 с,
   а лист переключается через 2,97 с (start) и 4,79 с (stop) — по той же причине (heartbeat). Критерий «<= 1,5 с»
   на листе стоя не выполняется; выполняется на кадрах. Либо критерий про кадры, либо лист нужно публиковать чаще — решает лид.
3. **Лист `readiness` не стареет сам (D):** пока процесс заморожен, лист `processes.camera_0.readiness` остаётся
   `ready:true, paused:false` (последний снимок), хотя `system.run.status` уже `fault`. Состояние системы верное,
   но лист в сторе без отметки «протух».
4. **Окно приёмки D1 — запас 0,7 с:** fault на 15,27 с после последнего `at` при окне 16 с. Один замер на boot 2
   (первый прогон D не сохранил числа до fault — вывод оборван `tail`, повторён на boot 2).
5. **Супервизор не перезапустил второе воплощение camera_0 (отдельно от задачи).** После первого `kill -9`
   (pid 29097, перезапущен как 29850) я остановил работу (`system.run.stop`), через 2 с убил 29850 тоже `kill -9`.
   За >= 60 с перезапуска не было: `supervision.status` camera_0 = `status:"crashed", alive:false, restart_count:1`,
   лог без второй строки `[supervisor]`, `system.run.status` = `not_ready` / `процесс не жив` до самого shutdown.
   Различие с первым убийством не изолировано (убивали уже перезапущенный экземпляр; сразу после `run.stop`).
   Причину не искал; воспроизводится или нет — не проверено (один случай).

## Что я оставил открытым / ненадёжным

- Один рецепт (`dualcam_synth`), один компьютер (macOS, spawn-старт), синтетический источник (30 кадр/с).
  Реальная камера, Windows-spawn, нагрузка (медленные плагины, полные очереди) — не проверялись.
- `run_event` напрямую не читал (внутренность PM); снятие подтверждено косвенно — у `camera_1` (живой) прирост кадров 0.
- Листы `processes.camera_1/consumer_*/devices.readiness` не читал (при обработке ответа я смотрел не тот ключ,
  результат `null` для них — ошибка моего скрипта, не данные); подтверждён только лист `camera_0`.
- Квитирование fault (ack) не пробовал — команды в задаче нет; выход из `fault` не измерен.
- Время перехода `stopping -> ready` после `run.stop` не снято (статус читал позже +0,1..9 с); известно только, что итог `ready`.
- Замер D1 — один чистый (boot 2); окно 16 с и измеренные 15,27 с различаются на 0,7 с, разброс по нескольким прогонам не снят.
- Находка 5 — один случай, причина не изолирована; без отдельной проверки не считать дефектом.
- Тайминги измерены опросом 0,1–0,25 с через TCP-драйвер; погрешность порядка 0,1–0,3 с.
- Первый прогон D (boot 1) показал те же ответы (fault, `нет отчёта о готовности`, `fault_unacknowledged`, липкость),
  но его вывод до STOP оборван, поэтому числа D1 взяты со второго.

## Допущения о форме

1. Ответ — `dict` с `success`/`error`/`message`; лишние ключи не сверяются. Текст `message` — подстрокой («сначала ОСТАНОВИТЬ» / «сначала Квитировать»); у `shutting_down` текст не проверяется (в брифе его нет).
2. «Побочные эффекты» = `_process_configs`, id объектов процессов в `pm._process_registry._processes`, `run_event`, `last_fault` из `_cmd_system_run_status()`, состояние, `communication.broadcast.call_count`.
3. Состояния `stopping` и `fault` выставлены прямыми событиями `_run_apply` (`stop` из `running`; `tick ready=False` из `running`), без запуска последовательностей STOP/аварии. `fault_stop_done` не выставляется: отказ в `fault` проверяется независимо от завершения остановки.
4. Во время применения состояние видит обёртка вокруг `pm.apply_topology` (подмена атрибута экземпляра, внутри зовётся настоящий метод): `("booting", run_event снят)`. Предполагается, что `_cmd_topology_apply` зовёт `self.apply_topology` (так и есть в коде сегодня).
5. Тест путей использует `handle_command(..., reply=...)`: ответ — тот же `dict` обработчика без обёртки (уточнится, когда тест позеленеет).
6. `recipe`-тест импортирует `multiprocess_prototype.orchestrator` лениво внутри функции (как делает `test_lifecycle_command_classes.py` — прецедент нарушения «framework не импортирует prototype» в тестах; `sentrux check` не запускал).

## РАСХОЖДЕНИЕ С БРИФОМ (важно лиду)

Бриф: «RecipeService ответ PM не переписывает; при `running` ответ `recipe.activate` содержит `error == "running"`». Проверено запуском:
```
RecipeService(... apply_topology=lambda a: {"success": False, "error": "running", "message": "m"}).activate({"name": "a"})
-> {'success': False, 'error': 'apply_failed', 'message': 'topology.apply отказал',
    'apply': {'success': False, 'error': 'running', 'message': 'm'}}
```
То есть корневой `error` == `"apply_failed"`, отказ PM лежит в `reply["apply"]["error"]`. Тест написан под реальную форму (`reply["apply"]["error"] == "running"`), корневой `error` не сверяется. Приёмка стенда («`recipe.activate` -> `error == "running"`») в буквальном чтении невыполнима без правки `RecipeService` (бриф запрещает) или без смены формулировки приёмки на «`apply.error`». Решение лида/владельца.

## Решение лида (2026-11-13)

RecipeService отказ PM оборачивает (`error: "apply_failed"`, причина в `reply["apply"]["error"]`) и правке не подлежит. Приёмка стенда читается так: `recipe.activate` в `running` → `apply.error == "running"`, в `fault` → `apply.error == "fault_unacknowledged"`; топология та же (`topology.get` до/после равны). Тест пишет ровно это. Охранные тесты `test_apply_in_ready_goes_booting_not_running[*]` зелёные до реализации — так и должно быть (проход как раньше). Покрытие «исполнитель занят, отказ мгновенный» — не требуется: гейт стоит в начале `_cmd_topology_apply`, до любой работы.

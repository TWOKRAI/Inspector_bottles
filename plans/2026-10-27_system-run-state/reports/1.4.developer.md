## Что сделано (по пунктам DESIGN)

Файлы: `process/process_manager_process.py`, `process/run_state.py`. `pre_stop.py` не трогал (API хватило).

1. **STOP → `stopping`, ответ сразу.** `_cmd_system_run_stop`: `_run_apply("stop", hold_event=<есть шаги и гейт>)`, ответ `{"success": True, "accepted": True, "state": "stopping"}`, последовательность — `_submit_run_sequence` на `pm-lifecycle` (`_lifecycle_submit.submit(action, None, reply)`); PM без исполнителя (двойник из `__new__`) — одноразовый daemon-поток. Без работы (`run_gate` false либо нет ни шагов, ни процессов набора) итог ставится инлайн — так 1.1-тесты (стоп → сразу `ready`) остались зелёными. Пока идёт системный стоп (`_pm_stopping()` или ход стопа), STOP отказан `shutting_down` (как START) — иначе второй проход `pre_stop` рядом с shutdown.
2. **Шаги → clear → ждать paused.** `_run_stop_sequence`: `_run_stop_steps` (через `_run_pre_stop_step`/`_pre_stop_step_outcome`, получили необязательный `cancel_source`; STOP добавляет отмену по `shutting_down`) → `_run_stop_clear_event` (под `_run_lock`, только если состояние `stopping`) → `_wait_all_paused` (опрос листов монитора срезом 0.05 с, вне любых замков). Событие в `stopping` не мигает: `_run_apply` не трогает событие при `new is stopping` и `_run_stop_hold`; прямой `_run_apply("stop")` (без `hold_event`) ведёт себя как в 1.1.
3. **Итог.** `_run_stop_finish`: не подтвердившие входят в `_run_unconfirmed` `{процесс: N}`, затем `settled` с `evaluate` → `ready`/`not_ready`. Мёртвый (`_process_alive == False`) в ожидание не входит. Причина «<имя> не подтвердил остановку за <N> с» (`{:g}`: 0.5 → «0.5», 10.0 → «10»; `node` = процесс, `source: report`) добавляется на КАЖДОЙ оценке в `_evaluate_run_readiness` (чистый помощник `run_state.unconfirmed_stop`: выход по `paused: true` / не жив / нет в наборе). Срок — `_run_stop_timeout()`: ключ `run_stop_timeout_s`, умолчание 10.0, негодное → 10.0 + WARNING.
4. **Авария.** `_run_readiness_tick` при переходе в `fault` зовёт `_start_fault_stop` → та же последовательность без шагов и без `clear` (событие снято в `_run_apply`); состояние остаётся `fault`; `_fault_stop_done = True` (атрибут PM, один с такой подстрокой), причины срока дописываются в `last_fault.reasons` (значение заменяется целиком, дубли по (node, reason) не пишутся), `_fault_seq` защищает от поздней последовательности старой аварии. `fault` не заходит в `stopping`.
5. **shutdown.** `force`: `_run_apply("shutdown")` после проверки аргументов, до `set_force_deadline` и событий. `graceful` из `running` при включённом гейте: `_run_shutdown_pass` = один проход шагов (`_run_pre_stop_loop`, вынесен из `_run_pre_stop`) при взведённом событии → `_run_apply("shutdown")` (снимает событие) → ждать `paused` → `finally _finish_pre_stop()` (события стопа). С шагами проход идёт на `pm-pre-stop` (фаза `pre_stop`, окно + `run_stop_timeout_s`), без шагов — на `pm-lifecycle` (фаза `children`). `graceful` не из `running` — `_run_apply("shutdown")` первым шагом, дальше как gui-graceful-close.

Решение по `run_gate: false` (записано): STOP не трогает событие, шаги `pre_stop` не исполняются, `paused` не ждём (событие не снимается, ждать было бы всегда до срока); итог сразу. Авария при `run_gate: false` — `_fault_stop_done = True` сразу (иначе `ack` 1.7 вечно получал бы `fault_stopping`).

Отклонение от текста: множество `unconfirmed_stop` защищает собственный листовой замок `_unconfirmed_lock`, а не `_run_lock`: 1.3-тест `test_evaluation_takes_neither_run_lock_nor_monitor_lock` запрещает оценке брать `_run_lock` (при первой версии под `_run_lock` он был красным — 1 из 23). Запись/выход — под `_unconfirmed_lock`, чтение ссылки в оценке — без замка (значение заменяется целиком).

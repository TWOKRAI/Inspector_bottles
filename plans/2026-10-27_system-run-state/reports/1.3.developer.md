## 1. Что сделано по DESIGN

**П.1. `run_state.evaluate(expected, leaves, alive, now, stale_s) -> (ready, reasons)`** — `process/run_state.py`. Чистая функция, без IO и часов.
Для каждого процесса набора, по порядку `expected`:
- не жив (нет ключа в `alive` = не жив) — `failure` / `liveness` «процесс не жив», дальше процесс не читается;
- нет листа или `at` старше `stale_s` (строго `now - at > stale_s`) — `failure` / `liveness` «нет отчёта о готовности»;
- иначе причины листа копией; лист `ready: false` без `failure` среди причин — добавлена `failure` / `report` «<процесс> не готов».

`ready` = среди причин нет `failure` и нет `check_function` (К3). `out_of_spec` и `maintenance` не блокируют. Судит по `readiness.at`, не по heartbeat. Таблицу переходов `transition` не менял: её строки для `not_ready` / `fault` из 1.1 уже верны.

## 6. Что я оставил открытым / ненадёжным

- **Интервал heartbeat читаю только из конфига PM** (`heartbeat_interval`, `heartbeat_interval_sec`). Per-process `heartbeat_interval` в конфиге процесса (ключ есть у `ProcessHeartbeat.start`) и рантайм-правка `heartbeat_interval_sec` в самом ребёнке PM не видит. Процесс с интервалом больше PM-значения получит ложный `fault`. В репозитории такого ключа в рецептах нет (`git grep` по yaml/json — только sample); при появлении нужен `stale_s` по процессу.
- **Процесс с `heartbeat_interval <= 0`** (heartbeat выключен) никогда не отчитается: вечный `not_ready`. Выход — `run_required: false`. Не обработано, не проверено.
- **Первый `readiness` после boot.** После `initialize()` состояние `not_ready` (причины `liveness`), пока дети не пришлют первый heartbeat с `readiness`. Момент первого heartbeat (сразу или через интервал, до `_announce_ready` или после) я не проверял. Если он идёт до `_announce_ready`, ждать до 5 с до `ready`. Нужна проверка на стенде; шкала загрузки — 1.3b.
- **GUI-процесс**: `run_required: false` остаётся страховкой; присылает ли GUI `readiness` в живой системе, не проверено (по коду — да, `HeadlessGuiProcess` с `ProcessHeartbeat`).
- **Авторестарт в `running` даёт `fault`.** Упавший процесс (не жив или без отчёта) = потеря готовности, как задумано в DESIGN. Авторестарт после этого не вернёт систему из `fault` (липкий; выход — `system.shutdown`, квитирование — 1.7).
- **`apply` в `running`** пока проходит (отказ — 1.5): после замены процессов «нет отчёта» даст `fault`. Я код отказа машины не читаю.
- **Рестарт одного процесса.** Лист забывается на диспатче рестарта и на `forget_process`, не на планировании рестарта (`_last_heartbeat.pop` в двух местах планирования я не дублировал). До диспатча прежний процесс либо не жив (ловит `alive`), либо жив, но сломан (лист состарится по `at`).
- **Стор.** Публикацию проверял двойником `_Store`, не настоящим `StateStoreManager`: что настоящий `handle_state_set` принимает список dict (`system.run.reasons`) и dict (`last_fault`), не доказано. Ошибки `_state_op` глотает с `_log_debug` (как у соседей). Листья `readiness` пишутся на каждое изменение `at`, то есть по 1 записи на процесс за heartbeat; нагрузка не измерялась.
- **`process_manager_module/process/__init__.py` форматтер пометил** — не мой, не трогал.

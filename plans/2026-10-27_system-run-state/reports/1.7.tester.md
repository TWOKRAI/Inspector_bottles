## Допущения о форме (список)

1. Имя команды-диспатча: обработчик берётся по имени `"system.run.ack"` из вызовов `register_command` в
   `_register_builtin_commands()` (на `MagicMock` менеджера команд); имя метода неважно. Вызов без аргументов. Регистрация без `executor` (класс R).
2. Ответ — dict с `success` / `state` / `error`; у успеха `error` None или отсутствует; прочие ключи не сверяются. Для отказов `state` в ответе не проверяется (проверяется через статус), кроме START в `fault` (`state == "fault"`, `reasons == [литерал]`).
3. `ack_allowed` читается из `pm._cmd_system_run_status()["ack_allowed"]` и из стора по пути `system.run.ack_allowed` (последняя запись). Публикация должна доходить синхронно после завершения остановки в аварии (ждём ≤5 с).
4. Оценка готовности при `ack` (свежая или с последнего такта) тестами не различается: перед ack всегда heartbeat + такт.
5. STOP в `fault`: проверяется только `accepted is not True`, шаги не выполнены, состояние `fault` (форма ответа `{"success": True, "accepted": False, "state": "fault"}` не пинится).
6. `acknowledged_at` — `float` в окне `[time.time() до, time.time() после]`.
7. Признак остановки в аварии читается тем же способом, что в `test_run_stop.py` (атрибут с `fault_stop_done` в имени); после успешного ack он `False` (тест 10 это пинит — следствие существующего сброса при выходе из `fault`).
8. После ack в `not_ready` процесс `last_fault.reasons` остаётся причинами аварии (литерал cam), а не заменяется оценкой ack.

## Что я оставил открытым / ненадёжным

* Тест 10 ловит гонку только на заметном окне: мутация с `sleep(3 мс)` между проверкой и записью ловится в 3 из 3 прогонов,
  реальная гонка с окном в микросекунды может проскочить. Окно «остановка завершена» узкое: на практике оно попадает
  в круги 16-17 (смещение ~50 мс = `_STOP_POLL_S`); распределение исходов win/late на настоящей реализации не измерено.
  Честная проверка — инъекция на настоящем коде: убрать `_run_lock` вокруг чтения `_fault_stop_done` и записи состояния.
* Время: тест 10 завязан на `_STOP_POLL_S = 0.05` и 10-мс heartbeat двойника; смена периода опроса сдвинет окно (тест не упадёт, но может перестать попадать в окно).
* Существующий `test_run_commands.py::test_run_command_replies` сверяет ключи статуса точным `set(status) == {...}` —
  после добавления `ack_allowed` он покраснеет (файл не трогал, это дело автора реализации/лида).
* В красном прогоне тест 3 оставляет daemon-поток `run-fault-stop` (plc не освобождён, срок 10 с) — отчёт guard G4 `threads without scope path: 1`; на зелёной стороне поток завершается.
* Тесты 1/6/7/9 сильнее связаны со стором (`_Store` из test_run_commands и путь `system.run.ack_allowed`): если автор опубликует поле иным путём, красными будут они.
* Приёмка стенда (авария -> 5 с в fault -> start -> fault_unacknowledged -> ack -> ready ≤ 1 с -> start -> running, last_fault null) тестами не покрыта (по брифу — не для юнитов); ограничение «≤ 1 с» юниты не проверяют.
* Сквозной тест с настоящим `CommandManager`/диспатчем (как `test_lifecycle_command_classes`) не писал — лимит 10 функций; регистрация проверена на `MagicMock`, класс R — по отсутствию `executor`.
* Не зафиксировано: поведение `ack` при `run_gate: false` (остановка в аварии «завершена» сразу, `_start_fault_stop`), и `ack` при гаснущем PM (`_pm_stopping()`) отдельно от состояния `shutting_down`.

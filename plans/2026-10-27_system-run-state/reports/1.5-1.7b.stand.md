### Что нашёл про три повторных fault

- Во всех трёх подъёмах с L1, L6, L11 в логе приложения ровно одна запись супервизора:
  `[supervisor] camera_0: unresponsive — heartbeat timeout 15.0с > 15.0с` (boot 1: 11:30:15, 15,1 с; boot 2: 11:33:26, 15,5 с; boot 5: 11:39:19,383, 15,0 с),
  затем `restarting (попытка 1/3)`. Больше таких записей в этих логах нет (во втором–пятом кругах подъёма — не было).
- Boot 5 (метки времени): STOP 11:39:06,186; **супервизор объявил `unresponsive` и перезапуск в 11:39:19,383 — на 63 мс раньше CONT (11:39:19,446)**;
  ack/start пришли после (start в 11:39:19,867); fault снова через ~2 с. То есть в L11 повторный fault совпал по времени с перезапуском camera_0 супервизором
  (заморозка 13,3 с + интервал heartbeat превысили 15 с). Для L1 и L6 привязка только по счёту записей (метки времени в тех прогонах не писал).
- `ack` и `start` не отказали, хотя дочерний процесс в этот момент перезапускался: `ack` -> `ready`, `start` -> `running`, и лишь через ~2 с `fault`.
- Возраст листа при ack >= 14 с (L3 14,30; L6 15,94; L11 15,45) не остановил `ack`: он прошёл с `ready` каждый раз.
  Ожидание «допустим ack -> not_ready до свежего снимка» не наступило ни разу. Гистерезис по свежести листа на этом сценарии не виден.
  (L3: возраст 14,30 с, перезапуска в логе нет, повторного fault нет.)

## Находки

1. **Повторный fault 3 из 13 в сценарии L — все три совпадают по числу (L1, L6) и по времени (L11) с перезапуском camera_0 супервизором**
   (порог heartbeat 15 с), а не с проверкой готовности после `ack`. Ожидание лида «повторного fault нет ни разу» не выполнено; причина по логу — не 1.7b-гистерезис.
   Но связанное наблюдение к 1.7b: `ack` и `start` проходят (`ready`, `running`) в тот момент, когда супервизор уже перезапускает ребёнка.
2. **Возраст листа 14–16 с (3 круга) не задерживает `ack`** (всегда `ready`). «ack -> not_ready до свежего снимка» не наблюдалось ни разу.
3. **Заморозка >= 13 с в одном круге из пяти доводит camera_0 до перезапуска супервизором** (порог 15 с): при такой проверке сам стенд (`kill -STOP` ~13,5 с + CONT) вплотную к порогу.
   Только первый круг каждого подъёма (3 из 3 подъёмов) — почему не следующие, не выяснял (гипотеза без проверки: heartbeat перед STOP старше).
4. **recipe.activate на успешном пути перезапускает 4 из 6 процессов и ведёт `ready` -> `booting` -> `not_ready` -> `ready` за ~7,3 с** — это не обязательно дефект, зафиксировано как поведение.

## Что я оставил открытым / ненадёжным

- Один рецепт (`dualcam_synth`), macOS, spawn-старт, синтетика, свободная машина; Windows и реальная камера не проверялись; `pre_stop`-шагов нет в рецепте.
- Причина «только первый круг подъёма» (находка 3) и связь L1/L6 с перезапуском — по числу записей в логе, а не по меткам времени (метки есть только для L11).
- Заморозка 13–14 с у порога супервизора 15 с — условие моего сценария; стенд не отделяет эффект 1.7b от эффекта перезапуска. Чистый тест 1.7b требует способа сделать fault без заморозки у порога (его здесь нет).
- M2 сравнение pid/топологии выполнено до перезапуска camera_0 супервизором (он произошёл позже в той же сессии); после activate в `fault` процессы на момент ответа не менялись, но дальше не отслеживал.
- В boot 3 N не получен (скрипт упал на чтении листа в момент перезапуска); N снят в boot 4 — один раз по каждому замеру.
- `run_event` напрямую не читал; «снят» — по кадрам (0 кадров за 3 с до START).
- `topology.get` до/после при успешном activate: различие подтвердил по равенству словарей, содержимое различий не разбирал.
- Трасса `state` в M3a: опрос 0,03 с вторым клиентом; значения короче этого не видны.
- `resource_tracker` после серии — 0 процессов (проверено `ps`).

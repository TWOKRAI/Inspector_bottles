# Разбиение `process_manager_process.py` на под-модуль — дизайн на согласование

Дата: 2026-11-15. Автор: teamlead. Статус: **предложение**. Код и тесты не менял. База: `main` `506eea281`.
Компромисс C7 из [`phase1.known-compromises.md`](phase1.known-compromises.md).

## 1. Рекомендация

Перенести класс в пакет `process/pm/` из 14 миксинов. Каждый миксин — одна ответственность, не больше ~560 строк.
Фасад `process_manager_process.py` оставить на месте. В нём остаются сборка класса, `__init__`, `initialize`, создание
компонентов и `HUB_QUEUES`. Путь импорта и `IProcessManagerProcess` не меняются. Миксины выбираю, потому что перенос
получается чистым: 137 приватных имён PM тесты трогают 1410 раз, и все обращения через `self`/`pm.` остаются рабочими.
Компоненты с явными зависимостями потребовали бы переписать эти обращения или добавить слой делегатов (принцип 4).
Порядок работ: сначала правки M1 и M2 на текущем файле, M3 идёт параллельно (он в `process_monitor.py`). Затем
пробный перенос одной группы (`run_*`) и перенос остальных отдельным коммитом. Каждый шаг доказывают три проверки:
равенство AST методов до и после, одинаковый набор зелёных тестов, инъекции поломки. Последний шаг — чистка
docstring и комментариев по ADR-175 (Google-стиль, русский, без задач и фаз), по отдельному коммиту на файл.

**Миксины или компоненты** (по принципам владельца, root `CLAUDE.md`):

| критерий | миксины | компоненты с явными зависимостями |

| 2. fix forward, не ломать | чистый перенос; тесты почти не меняются (§8) | 1410 обращений к 137 именам в 67 тестах: переписать или проксировать |
| 5. тестируемость | как сейчас: тесты собирают PM через `__new__` (57 мест в 26 файлах) | лучше: компонент проверяется сам. Но run ↔ sysstop связаны в обе стороны (18 пар) — нужен общий контекст |
| риск переноса | MRO и затенение имён; ловит страж (V3) | меняется поведение проводки; нужна новая приёмка |
| прецедент | `GuiProcessMixin` (ADR-040). ADR-013 отклонил миксины для CRM из-за MRO-конфликтов. Здесь имена не пересекаются, `__init__` у миксинов нет | `TopologyManager`, `ProcessMonitor` (уже вынесены) |

**Решение: миксины.** Компонентами позже стоит сделать только группы без обратных связей. Кандидаты:
`telemetry_journal` (свёртка — `@staticmethod`, наружу 7 вызовов рассылки) и «ход стопа» (словарь + замок).
Это отдельная задача, не часть переноса.

**Правила переноса.**
1. У миксина нет базы и нет `__init__`. Умолчания уровня класса (`_run_state = RunState.booting` и т. п.) и ленивые
   замки `__dict__.setdefault` переходят в миксин своей группы. Через MRO их видят двойники из `__new__`.
2. Миксины стоят в списке баз раньше `ProcessModule`. Хуки базы (`initialize`, `capabilities_extra`,
   `observability_introspect_extra`, `_own_work`, `_own_work_late`, `_own_transport`) определены ровно в одном классе.
3. Имена миксинов не пересекаются. Это проверяет постоянный тест-страж (V3).
4. Миксины импортируют только `run_state`, `pre_stop`, `core/*` и помощники из `pm/commands.py`. Фасад они не
   импортируют, иначе цикл.
5. Поля хоста объявляются в начале миксина аннотациями без значения (`_process_registry: Any`). Объект от этого
   не меняется. pyright получает типы, шапка — проверяемый список зависимостей. Сколько диагностик pyright даст
   без аннотаций, неизвестно: это замеряет пилот (стадия 1).
6. Тела методов не меняются ни на символ. Это проверяет V2.

## 6. Шаблон-образцы

Формат docstring взят из проекта, не придуман: ADR-175 П2. Первая строка — одна фраза «что делает». Секции `Args:`,
`Returns:`, `Raises:` ставятся, когда есть что сказать. `Pre:`/`Post:` — принятая конвенция (29/31 файл фреймворка).
Пожелание владельца ложится на этот формат так: **назначение** = первая строка, **вход** = `Args:`,
**выход** = `Returns:`, **побочные эффекты** = `Post:`, **замки и потоки** = `Pre:`. Тривиальный метод получает
одну строку.

### (а) Шапка файла-компонента: `pm/run_control.py`

```python
"""Машина работы системы в ProcessManager: состояние, команды system.run.*, последовательность STOP.

Входит:
    - единственная точка записи состояния машины (`_run_apply`) и снимки под замком;
    - публикация ключей `system.run.*` в стор;
    - команды `system.run.status`, `system.run.start`, `system.run.stop`, `system.run.ack`;
    - последовательность STOP оператора и остановка при аварии: ожидание `paused`, итог.

Не входит:
    - таблица переходов — `process/run_state.py` (чистая функция без IO);
    - оценка готовности, окно перезапуска, «не подтвердили остановку» — `pm/run_readiness.py`;
    - ход системного стопа и шаги `pre_stop` — `pm/system_stop.py`.

Зависимости от хоста (объявлены аннотациями в классе): `_state_op`, `_state_store_manager`,
`_lifecycle_submit`, `_pre_stop_steps`, `_log_error`; из `run_readiness.py`: `_evaluate_run_readiness`,

из `system_stop.py`: `_pm_stopping`, `_system_stop_snapshot`, `_pre_stop_cancel_source`, `_run_pre_stop_step`.

Замки:
    `_run_lock` — состояние, причины, `last_fault`, `run_event`. Листовой: под ним только переход

    исполнитель `pm-lifecycle` (у PM без исполнителя — одноразовый daemon-поток).
```

```python
    def _run_stop_sequence(self, *, fault: bool, seq: int) -> None:
        """Выполнить последовательность STOP оператора или остановки при аварии.

        STOP: шаги `pre_stop` → снять `run_event` → ждать `paused` → итог. Авария: шаги пропускаются
        (событие уже снято переходом в `fault`), дальше так же.

        Args:
            fault: `True` — остановка при аварии.
            seq: Номер аварии (`_fault_seq` на момент подачи); итог по чужой аварии отбрасывается.

        Pre:
            Поток исполнителя `pm-lifecycle`; замков не держит.
```

## 10. Оценка

| стадия | исполнитель | модель | токены (грубо) |
|---|---|---|---|

| 1–2 прогоны V0–V6, правка 16 строк целей патчей по точному списку §8 | test-runner / junior | Haiku | ~0,3 M |
| 3 чистка | 4 исполнителя по 3–4 файла, последовательно в одном дереве или в worktree | Sonnet | ~1,2–1,6 M |
| 3 кандидаты, V8–V10 | Haiku | Haiku | ~0,1 M |
| ревью чистки (выборка: утверждения про замки и потоки в `Pre:`/`Post:`) | reviewer | Opus | ~0,3 M |

Итого: 16 файлов кода (фасад + 14 + `__init__`), ~15 тестовых файлов (~20 строк) и 1 новый тест-страж,
3–4 документа. Строк кода после переноса ~6500–6900: шапки, импорты и аннотации добавляют ~600, чистка убирает
~400–700. Токены ~2,5–3 M без цикла M1–M3.

**Haiku:** запуск скрипта и прогонов, счёт строк и grep, правка целей патчей по точному списку, кандидаты чистки.
**Не Haiku:** карта и правила MRO (готовы здесь), аннотации хоста, текст docstring (утверждения о замках и потоках —
факты, неверный docstring хуже его отсутствия), M1 и M2 (конкурентность, IPC).

## 11. Что оставил открытым / ненадёжно

- Карту групп собрал я по именам и AST-графу. Спорные методы — `_cmd_supervision_status` (commands или
  system_stop), `_process_alive`, `_state_op`. На поведение это не влияет, только на размер файлов.
- Размеры файлов оценены ±15 %. Насколько чистка сократит текст, не мерил.
- Радиус тестов посчитан по токенам `._имя` в 84 файлах. Ложные совпадения возможны: `_process_registry` есть и у
  `SystemLauncher`. Пропуски тоже: динамический `getattr` по строке этим способом не виден.
- Тесты, pyright, `atlas check` и `sentrux check` не запускал: это дизайн. Базы V0 нет. Число диагностик pyright
  на миксинах неизвестно.
- Порядок замков проверил только для `_run_publish_lock` → `_run_lock`.
- В шаблоне шапки номер ADR — заглушка `ADR-PMM-NNN`. Есть ли уже ADR по run-state, не проверял: ревью говорит
  «записать в ADR (2.5)».
- Посылки брифа, которые не подтвердились: «267 методов» — это 234 у класса + 25 у вспомогательных классов + 8
  вложенных функций; «~247 строк со ссылками» — по моему набору семейств их 308; «M1–M3 в том же файле» — M3 в
  `process_monitor.py`, M2 затрагивает оба файла.
- Соседние файлы (`run_state.py`, `pre_stop.py`, `topology_manager.py`, `observability_broker.py`, `monitor/`)
  содержат ссылки того же рода. Сколько их, не считал.
- Живые карты с номерами строк (`docs/maps/pm-lifecycle-commands.md` и др.) устареют. Исторические отчёты в
  `plans/` и `docs/reports/` (342 файла упоминают PM-файл) не правлю.

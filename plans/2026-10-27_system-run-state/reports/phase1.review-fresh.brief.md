## Углы, которых прежние раунды не брали (идти по ним, не по списку находок)

1. **Живость и тупики таблицы состояний.** `process/run_state.py` + `_run_apply`: из каждого состояния есть выход? `fault` всегда покидается только стопом? Есть ли комбинация событий, после которой система зависает в `stopping`/`running`/`not_ready` без пути назад? Проверь перебором (модель таблицы + случайные/полные последовательности событий), не чтением.
2. **Порядок замков и обратные вызовы.** `_run_lock`, `_readiness_lock`, замки реестра pid, исполнитель `OrderedExecutor`: граф «кто держит → что берёт». Вызовы пользовательского кода/логгера/коллбэков под замком. Возможен ли deadlock или инверсия? Покажи граф и проверь инъекцией задержки/гонкой.
3. **Отказ каждого внешнего вызова.** Очередь закрыта, поток монитора умер, исполнитель бросает, реестр pid вернул None, `readiness()` плагина бросает, heartbeat битый (не dict, pid не int, `readiness` с мусором). Что видит владелец системы (какое состояние, какая причина)? Молчаливые проглатывания (`except`, `return False` без следа).
4. **Тесты как доказательство.** Для 8–10 самых важных свойств (машина состояний, гейт apply, допуск heartbeat, обход отказа исполнителя) проверь: тест краснеет, если свойство сломать? (инъекция в отдельном worktree, откат cp). Тесты на двойниках: есть ли хоть один сквозной на настоящих объектах (PM + ProcessMonitor + OrderedExecutor)? Ожидаемые значения — литералы или выведены из кода?
5. **Потребители состояния вне PM.** GUI, `backend_ctl`, рецепты, `state_store`: кто читает `run_state`/причины готовности/`restart_policy`; не сломан ли контракт (Dict at Boundary, ключи, версии)? Что будет у старого потребителя при новых полях/причинах? (C11: расширение публичного контракта heartbeat `pid` — дай вердикт, нужен ли cto.)
6. **Избыточность и простота.** Принципы владельца: меньше слоёв, без костылей. Есть ли механизмы, которые можно убрать без потери свойства (повтор защиты в двух местах, флаги-исключения, пороги/sleep как заплатка)? Размер `process_manager_process.py` (~6500 строк) — не оценивай (это Task 3.2, после 1.0); оценивай только новую логику.
7. **Эффективность.** Что на горячем пути (heartbeat, тик, оценка готовности) делается на каждый вызов: разбор политики, копии dict, замки, логирование. Измерь (микробенч `timeit` на настоящих объектах), числа — в отчёт; не измерил — так и пиши.
8. **Согласованность код ↔ документы.** Таблица в `design.md`/`amendments.md` против кода: расхождения (шкала §5, порядок shutdown §9, внеочередной heartbeat §10).

## Правила запуска (STRICT)

- Только диагностика и отчёт: не коммитить, не пушить, код проекта не править. Инъекции — в отдельном worktree/копии, откат cp, не `git checkout`.
- Каждая находка — вход → наблюдаемый результат (воспроизведение запуском); без воспроизведения — только advisory. Слова «невозможно/гарантировано» — только с воспроизведением.
- Тесты и стенд — через `bash "$(git rev-parse --path-format=absolute --git-common-dir)/../scripts/machine_gate.sh" light|medium <имя-сессии> <команда>`; heavy и стенд НЕ запускать. Основной `.venv` + `PYTHONPATH=<корень worktree>`; не `uv sync`.
- Каталог `process_manager_module/tests` целиком на macOS упирается в `ENOSPC` (`kern.posix.sem.max`) — гонять отдельными файлами; чужие сессии тоже гоняют, `OSError: [Errno 28]` — повтор, не находка.
- Если запускаешь живой бэкенд: только со своими `INSPECTOR_PID_FILE` и `INSPECTOR_DATA_DIR` (общие файлы — чужих сессий).
- Долгих ожиданий нет: на зависании пропусти проверку, скажи об этом, вердикт выдай.
- Скрипты воспроизведения — в scratchpad, не в дерево проекта.

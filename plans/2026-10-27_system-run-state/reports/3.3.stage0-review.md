## Ответы на пять вопросов

### 1. DESIGN реализуем? Что уходит, кто зовёт, антидребезг (чтение)

- Внеочередной heartbeat сегодня = ТОТ ЖЕ построитель, что регулярный (`_send_heartbeat_locked`, `process_heartbeat.py:412-456`): `type=system`, `command=heartbeat`, `sender`, `timestamp`, `status`, `pid`, `workers_status` (без `metrics`) и `readiness` — `deepcopy` снимка с полями `ready`, `reasons`, `paused`, `at`. Телеметрия, health, GC, дренаж остаются на регулярном такте (`_loop`, `:269-303`). Расписание не трогается: push не пишет `_last_heartbeat_sent` (`:305` — только регулярный).
- Кто зовёт: воркер `readiness_snapshot` ПРОЦЕССА (`ProcessModule._readiness_snapshot_loop`, `process_module.py:1130-1142`), после каждого пересчёта, период `wait(0,5 с)`. Единственный вызывающий; `_push_readiness_change` (`:1144`) глотает исключения. Не поток heartbeat. `readiness()` плагинов на потоке heartbeat не зовётся (инвариант `process_heartbeat.py:440-442` сохраняется).
- Антидребезг: `_PUSH_MIN_INTERVAL_SEC = 0.5` (`:15`), `_last_push_at` под `_send_lock` (`:392-394`); пишется при попытке (в том числе неудачной). Подавленная смена не теряется: сравнение с УШЕДШИМ повторяется на следующем проходе.
- Наблюдение: единственный боевой вызывающий сам ходит не чаще 1 раза в 0,5 с + время пересчёта, значит окно антидребезга в бою почти недостижимо; он защищает прямые вызовы (тесты, будущие вызывающие). Недоказанная оговорка: если `Event.wait(0,5)` на Windows вернёт чуть раньше 0,5 с, push подавится и уйдёт на проходе позже (задержка 1,0 с вместо 0,5) — не проверено, нужна Windows-проверка.
- Полна ли подпись `(paused, ready, блокирующие (node, severity))`? Для PM-решений — да: `ready` у PM берётся из листа и из `has_blocking` по `failure`/`check_function` (`run_state.py:44, :226`), `paused` — для `_paused_pending`. Не покрыто, по замыслу: тексты причин, неблокирующие причины, порядок, `at` (см. п.5 списка). Дыра по форме: `ready` отдельно от причин — путь boot-а (п.5).
- Блокирующие severity: `("failure", "check_function")` — `health/schema.py:128`; копия `run_state.py:44` (`frozenset`). Выбор источника — п.5.
- Первый снимок: `_last_sent_*` None до первого регулярного heartbeat с `readiness` -> push молчит (`:388-390`, находка 1.2 `reports/1.2.developer.md:200`). Для 3.3 это ЗНАЧИМЕЕ: самый ценный push — `ready False -> True` при boot (защёлка); если первый регулярный heartbeat ушёл раньше первого снимка, подпись `None` до следующего регулярного (<= 5 с), и boot-задержка не уменьшится. Порядок «снимок раньше heartbeat» по коду почти всегда (воркер снимка стартует в `initialize()`, heartbeat — в `run()`, `process_module.py:1520`), но гарантии нет. Записать как принятое или закрыть тестом (первый heartbeat без снимка -> первый снимок с `ready`/блокирующими -> push).

### 2. Риски

- Шторм при дребезге: ограничен ДВАЖДЫ — периодом воркера снимка (~2 Гц) и антидребезгом 0,5 с: не больше ~2 сообщений в секунду на процесс (чтение). Условие: `at` вне подписи. Нагрузка на PM: каждое сообщение даёт `_admit_heartbeat` с обращением в реестр (`process_monitor.py:363`); 5–7 процессов x 2/с — единицы в секунду; 3.6 это обращение уберёт. Без замера.
- Гонки (чтение): снимок — dict, заменяется целиком одним присваиванием (`process_module.py:1179`), `reasons` строится заново каждый вызов (`plugin_orchestrator.py` `readiness_snapshot`, `_cap_reasons`), в месте не мутируется. Регулярный и push читают его внутри `_send_lock` (`:446`), порядок сообщений по замку: более позднее сообщение не несёт более старый снимок. `_last_sent_*` пишется и читается только под замком (`:387-389`, `:456`) — сохранить. Остаётся одна гонка: сравнение ДО замка читает одну версию снимка, ушедшая копия может быть другой -> записывать подпись из копии (п.5).
- Гонка на `workers_status`: push зовёт `_collect_workers()` (`:396`) и `w.pop("metrics")` (`:438`) из потока снимка, регулярный путь — из потока heartbeat.

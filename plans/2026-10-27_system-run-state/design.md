# Design: состояние работы системы — «готов → ЗАПУСТИТЬ → работает → ОСТАНОВИТЬ»

Спецификация к [`plan.md`](plan.md). Факты — чтение `main` `3aa2c0b8f` (2026-10-27), индекс qex устарел — всё ниже
найдено `git grep`/чтением; номера строк сверять перед правкой (файлы PM у полосы Ф, они сдвинутся после 1.10/1.11).

## 1. Требование владельца (дословно, 2026-10-27)

1. «при старте РЕЦЕПТ не должен запускаться. Он прогружается, но для полноценной работы нужно нажать кнопку ЗАПУСТИТЬ.
   И есть кнопка остановить. Сейчас неправильно что при запуске рецепт сразу активен. Должна система полностью поднять
   все узлы и дать готовность после чего разрешать нажимать кнопку ЗАПУСКА».
2. Уточнение (через координатора): «сначала получить от каждого узла процесса и модуля состояние готовности (по рецепту),
   и когда все готовы — давать разрешение на запуск». Требования, не варианты:
   - R1 иерархическая самоотчётная готовность: плагин/устройство → процесс (все его плагины) → система (все процессы,
     **которых требует рецепт**);
   - R2 молчание = НЕ готов (liveness-фолбэк барьера для гейта START не годится);
   - R3 готовность непрерывна: потеря во время работы → не готов / авария, реакция определена;
   - R4 каждое «не готов» несёт именованные причины (узел + причина) в state; находки preflight C-55b — такие причины.
3. «подтягивай промышленные стандарты» — [`standards.md`](standards.md) §9.

## 3. Решение (рекомендация менеджера; архитектуру утверждает `cto`, Task 0.1)

### 3.1. Кто владеет и где видно

- **Владелец машины состояний — PM** (`process_manager_module`): он поднимает топологию рецепта, держит барьер,
  `system.shutdown`, `topology.apply`, StateStore. Не `recipe` (сервис поверх PM, его нет без `recipes:` в манифесте),
  не `app_module` (это подкласс PM для приложений — framework должен уметь сам, принцип 1). Чистая логика переходов —
  новый файл `process_manager_module/process/run_state.py` (функция/класс без IO, юнит-тесты без процессов); проводка —
  в `process_manager_process.py`.
- **Публикация:** `system.run.state` (строка состояния), `system.run.reasons` (список причин §3.3),
  `system.run.since` (время входа), `system.run.last_fault` (последняя авария с причинами), через `_state_op`.
- **Снимок по команде:** `system.run.status` (класс R — на приёмном потоке) отдаёт то же dict'ом — для `backend_ctl` и
  приложений без state-plane.
- **Команды:** `system.run.start`, `system.run.stop` — к PM. GUI, пульт (строки 15–17), `backend_ctl` — только
  вызывающие (принцип 6). Имя `system.stop` не берём: путается с `system.shutdown`.

### 3.2. Состояния (подмножество PackML, §9.1)

| наше (state) | по-русски (GUI) | PackML | вход | START | STOP | ACK | `topology.apply` |
|---|---|---|---|---|---|---|---|
| `booting` | поднимается | Resetting | boot; `topology.apply`/`recipe.activate` | отказ `not_ready` | no-op | `no_fault` | снова `booting` |
| `not_ready` | не готов | Stopped (с причинами) | не все требуемые узлы готовы | отказ `not_ready`, ответ несёт причины | no-op | `no_fault` | → `booting` |
| `ready` | готов | Idle | все требуемые узлы готовы, нет `failure` | → `running` | no-op | `no_fault` | → `booting` |
| `running` | работает | Execute | START из `ready` | no-op (`already_running`) | → `stopping` | `no_fault` | отказ `running` |
| `stopping` | останавливается | Stopping | только STOP оператора | отказ `stopping` | no-op | `no_fault` | отказ `stopping` |
| `fault` | авария | Aborted | потеря готовности в `running` (R3) | отказ `fault_unacknowledged` | no-op | ok при `fault_stop_done`, иначе `fault_stopping` | отказ `fault_unacknowledged` |
| `shutting_down` | завершение | — | `system.shutdown` | отказ `shutting_down` | отказ `shutting_down` | отказ `shutting_down` | отказ `shutting_down` |

Правила таблицы. (1) Авария **не** проходит через `stopping`: `fault` сразу снимает `run_event`, ждёт `paused` и ставит
внутренний признак `fault_stop_done`; состояние остаётся `fault` до `ack`; готовность вернулась — всё равно `fault`.
(2) Потеря готовности в `stopping` состояние не меняет. (3) Для ожидания `paused` (STOP и авария) остановленным считается только мёртвый процесс (`alive == False`) —
ожидание не висит `run_stop_timeout_s` на нём, причина «процесс не жив» остаётся в `reasons`. Живой, но без свежего
отчёта (завис) процесс ждёт `paused` до срока: срок истёк — в STOP `not_ready` + `failure` «не подтвердил остановку», в
аварии та же причина пишется в `last_fault.reasons`, а `fault_stop_done` не ставится до подтверждения или срока;
после срока `ack` разрешён, но причина остаётся видимой и блокирует START до следующего подтверждённого `paused`.
PM держит множество `unconfirmed_stop` (под замком держателя): процесс входит в него по истечении срока ожидания `paused`
(STOP оператора или авария) и выходит, когда его лист показывает `paused: true` или `alive == False`. На каждой оценке PM
добавляет к причинам `evaluate` `failure` «<процесс> не подтвердил остановку за <N> с» (`node` = имя процесса, `source:
report`) для каждого процесса из множества — `tick` её не стирает, `ack` и итог STOP ведут в `not_ready`, START отказан
`not_ready`. (4) Все переходы — под одним замком держателя состояния: тик монитора (оценка готовности) и
`message_processor` (команды) пишут состояние только через него. (5) Классы команд PM (README модуля): `status`,
`start`, `ack` — быстрые, без ожиданий; `stop` принимается мгновенно, последовательность идёт на L-исполнителе (Task 1.4).
(6) Автоперезапуск (§3.5): процесс с флагом вне окна `run_restart_grace_s` ведёт себя как без флага — `fault`.
«Загружен» владельца = момент до спавна; отдельным состоянием не публикуется: оператор видит «поднимается» → «готов» →
«работает» (**В1, решение владельца 2026-11-02**). `stopping` после завершения → `ready`/`not_ready` по текущей
готовности.

**Квитирование (В4, решение владельца 2026-11-02; Task 1.7).** `fault` сам не уходит: после аварийной остановки система
стоит в `fault` с `last_fault`, пока оператор не нажмёт «Квитировать» — команда `system.run.ack` к PM (PackML Clear:
Aborted → Clearing → Stopped). `ack` в `fault` принимается, когда аварийная остановка завершена (все требуемые процессы
подтвердили `paused` или истёк `run_stop_timeout_s`); иначе отказ `fault_stopping`. После `ack` → `ready`/`not_ready`
по текущей готовности; `last_fault` получает `acknowledged_at` и остаётся видимым до следующего START. `ack` вне `fault`
→ отказ `no_fault`. START в `fault` → отказ `fault_unacknowledged` с причинами `last_fault`. Порядок оператора:
«Квитировать», затем ЗАПУСТИТЬ (ISA-18.2, §9.5).

### 3.3. Готовность (R1, R2, R4)

**Причина** — dict: `{"node": "<процесс>[.<плагин>]", "severity": "failure|check_function|out_of_spec|maintenance",
"reason": "<текст>", "source": "readiness|preflight|liveness|report"}`. Шкала — NAMUR NE 107 (§9.2). START блокирует
только `failure` (и `check_function` — **вопрос CTO К3**).

**Уровень плагина.** Новый необязательный метод `ProcessModulePlugin.readiness(self, ctx) -> list[dict]` (пустой список
= готов), форма как у C-55b/C-60: метод с пустым умолчанием, без реестра. Контракт: быстро (без IO, читает своё
состояние — «камера открыта», «модель загружена», «робот подключён»), не бросает (исключение → причина `failure`
«readiness() упал: …»). Плагины без метода — готовы, как только `RUNNING`/`PAUSED`.

**Уровень процесса.** Ребёнок на такте heartbeat (тот же прокси, что `publish_health`, `health/state.py:677`) пишет
`processes.<n>.readiness = {"ready": bool, "reasons": [...], "paused": bool, "updated_at": t}`; `ready` = все плагины
готовы и `run()` дошёл до `_announce_ready`. `paused` = все плагины в `PAUSED` (подтверждение STOP, §3.5).

**Уровень системы (PM).** Требуемый набор = процессы применённой топологии рецепта (то, что PM уже считает текущим
после `topology.apply`/boot). Для каждого: нет листа `readiness` или `updated_at` старше `3 × heartbeat_interval` →
причина `failure` `source: liveness` «нет отчёта о готовности» (**молчание = не готов**, R2); процесс мёртв → `failure`
«процесс не жив»; иначе — его причины; лист свежий, `ready: false`, и среди его причин нет `failure` → добавить `failure`
`source: report` «<процесс> не готов». Первый элемент результата `evaluate` (`ready`) = среди итоговых причин нет
`failure` (и `check_function` — по вердикту К3). Оценка непрерывная — на такте монитора PM (существующий поток монитора), плюс
сразу при START.

**Почему отдельный сигнал, а не правка барьера.** Барьер (`_wait_processes_ready`) обслуживает boot-волны, switch и
restart; liveness-фолбэк там сознателен (медленный ребёнок не роняет boot, DECISIONS.md:131) и закреплён тестами §2.
Гейт START строится на другом сигнале (лист `readiness`) и барьер не меняет. Плата: два понятия «готов» — «процесс
поднялся» (барьер) и «узел готов к работе» (гейт); различие пишется в ADR. Вариант «сделать барьер строгим» отвергнут:
ломает boot с медленной ML-моделью и 4 файла тестов.

**Preflight C-55b → причины (Task 1.6).** При включённом гейте работы (§3.6) `error` preflight не прерывает boot, а
передаётся PM в конфиге (dict) и становится причиной `failure` `source: preflight` до перезапуска/смены рецепта;
`warning` → `out_of_spec`, `info` → `maintenance` (не блокируют). Гейт выключен → поведение C-55b (отказ до спавна) не
меняется. `recipe.activate` с `error` — отказ, как в C-55b.3: старый рецепт остаётся (**В5**, решение владельца
2026-11-02: при смене не активируется; на старте — «не готов» с причиной).

### 3.4. Что делает START / STOP с плагинами и данными

Механизм — **один `mp.Event` работы на систему** (`run_event`), проводка как у ADR-PMM-034, но создаёт его PM (он
спавнит детей; launcher не трогаем):

- PM → `ProcessRegistry` → kwargs `Process` → `run_process_function(..., run_event=...)` → атрибут ребёнка →
  `SourceProducer`: цикл `run_loop` не зовёт `produce()`, пока событие снято (как ветка `pause_event`
  `source_producer.py:144-147`), **без срока** (в отличие от preroll).
- Ребёнок держит маленький системный воркер-наблюдатель события: фронт «взведено» → `_do_resume` всех плагинов;
  фронт «снято» → `_do_pause` всех плагинов; после подъёма плагинов, до `_announce_ready`, при снятом событии — сразу
  `_do_pause` (плагины в `PAUSED`, ресурсы удержаны). Это первый живой вызывающий `pause/resume` — новых хуков нет.
- Рестарт ребёнка в `running` — событие наследуется взведённым, ребёнок поднимается сразу в работу; гонок команд нет
  (событие, а не IPC-рассылка, которую ребёнок без обработчика уронил бы — класс гонки C-57).

**Работает в `ready`/`not_ready`:** процессы, heartbeat, команды, state, телеметрия, логи, связь с устройствами
(device_hub держит соединение — иначе готовность «робот подключён» не проверить), веб/GUI-серверы. **Не работает:**
кадры источников — кроме источников с `run_gated: false` (превью, ниже); поэтому вся обработка и задания роботу стоят.

**Превью камеры в `ready` (В2, решение владельца 2026-11-02; Task 1.1 п.6, 1.2 п.4).** Разрешено, если камера уже
открыта; включается флагом источника `run_gated: false` (умолчание `true` — кадров нет до START). Источник с флагом
производит кадры в `ready`/`not_ready`, наблюдатель его процесса не паузит плагин-источник. Обработка, запись и задания
роботу работают только в `running`: их плагины в `PAUSED` кадры не обрабатывают. Где режется поток — на потребителе
(плагин в `PAUSED` не получает `process()`) или на маршруте источника (в `ready` только канал display) — **К6**; факт
«что делает плагин в `PAUSED` с входящим кадром» — проверка §8.

Варианты, отвергнутые для механизма:

| вариант | минус |
|---|---|
| Только IPC-рассылка `plugins.pause_all` детям | рестарт/поздний ребёнок не знает состояния; гонка «команда до обработчика» (C-57); подтверждение — отдельный канал |
| `worker.pause_all` | паузит воркеры устройств и телеметрию; плагины не узнают |
| Гейтить в каждом плагине по своему флагу | N реализаций одного и того же; принцип 4 |

### 3.5. Последовательность STOP и аварии (IEC 60204-1, §9.3)

- **STOP (оператор)** = останов категории 1/2: `stopping` → шаги `pre_stop` (точка из `gui-graceful-close` Task 1.4,
  `pre_stop.py`, источник — конфиг PM/рецепт; «домой» робота — шаг T5.3e) → снять `run_event` → ждать `paused: true`
  у всех требуемых процессов, срок `run_stop_timeout_s` (умолчание 10 с) → `ready`/`not_ready`. Срок истёк →
  `not_ready` с причиной `failure` «<процесс> не подтвердил остановку». Лента: хук `pause()` плагина ленты (ПЧ) — стоп
  ленты (Task 2.2).
- **Авария (потеря готовности в `running`)** — реакцию определяет framework одинаково для всех: `fault` → снять
  `run_event` **сразу**, шаги `pre_stop` («домой») пропускаются (как `force` в gui-graceful-close 1.4) → ждать
  `paused` → `last_fault` = причины. Робот: хук `pause()` его плагина = стоп движения на месте (кат. 2), не «домой»
  (**В3**, решение владельца 2026-11-02: «домой» — только по ОСТАНОВИТЬ). Состояние остаётся `fault` до `ack` (§3.2).
  Что «потеря готовности» — **все** требуемые процессы (кроме §3.5 «автоперезапуск»); порог дребезга — `readiness_grace_s` (умолчание 0)
  (**К4**).
- **Рестарт упавшего ребёнка в `running`** — это потеря готовности → `fault` → система останавливается; супервизор
  поднимает процесс как сейчас (`RestartPolicy`, `process_monitor.py`); после возврата готовности — «Квитировать», затем
  START оператором (**В6**, решение владельца 2026-11-02).
- **Опциональный автоперезапуск (В6, Task 1.8).** Флаг процесса в рецепте `run_auto_restart: bool` (умолчание `false`).
  Прочтение лида (подтвердить у владельца — В9): падение процесса с флагом в `running` — не авария; супервизор поднимает
  его, ребёнок наследует взведённый `run_event` и встаёт сразу в работу (§3.4); пока он не готов — причина-индикатор
  `out_of_spec` «перезапуск <процесс>», линия не останавливается. Супервизор сдался (`gave_up`) или окно
  `run_restart_grace_s` (умолчание 30 с) истекло без готовности → `fault`. Второе прочтение — «авария, затем
  автоквитирование и авто-START после готовности» — отвергнуто лидом: линия всё равно стоит, а робот без оператора
  стартует сам (В3). Не путать с `RestartPolicy`: она решает, поднимать ли процесс; флаг решает, авария ли это.
- `system.shutdown` из любого состояния → `shutting_down`; graceful-путь сначала выполняет STOP-последовательность, если
  было `running` (согласовать с gui-graceful-close 1.4: один `pre_stop`, не два).
- **Программный STOP — не аварийный останов.** E-stop — аппаратная функция безопасности (ISO 13849 / IEC 62061), этот
  план её не реализует и не заменяет.

### 3.6. Включение (обратная совместимость)

Ключ конфига PM `run_gate: bool`. **Умолчание framework — `false`**: `run_event` создаётся взведённым, состояние
публикуется (`ready ↔ running` без гейта источников) — framework-тесты, minimal_app, line_sim, стенды не меняются.
Прототип включает `run_gate: true` в манифесте (Task 2.1) и учит стендовые сценарии слать `system.run.start` после
`ready` (**К1**). Наблюдаемость — без новых флагов: состояние — несколько листьев state, ноль кадров.

### 3.7. Смена рецепта и правка топологии на ходу

`topology.apply` (оба пути: `recipe.activate` и редактор топологии GUI) в `running|stopping|fault|shutting_down` → отказ
`{"success": False, "error": "<имя состояния>", "message": "сначала ОСТАНОВИТЬ" | "сначала Квитировать"}` (код ошибки
для `fault` — `fault_unacknowledged`); в `booting|not_ready|ready` → `booting` → по готовности `ready`/`not_ready`,
**никогда не `running` сам**; из `fault` смена рецепта не обходит квитирование. Проверка — в PM `_cmd_topology_apply` (одна точка на оба
пути). Параметры на ходу (`param`, поле «Слово», решение 25) — не `topology.apply`, не блокируются (**В7**, решение
владельца 2026-11-02: смена рецепта — только после ОСТАНОВИТЬ).

**«Нет диска / лента пустая» (В8, решение владельца 2026-11-02).** Состояния машины не вводим: система в `running` ждёт
диск и ничего не делает, кроме отображения. Оператор видит индикатор — причину `out_of_spec` (`source: report`) в
`system.run.reasons`; START/STOP она не блокирует и `fault` не вызывает. Кто её ставит — плагин сцены/ленты через
`readiness()` (Task 2.2 п.6; источник — кандидат `word_layout`, подтверждает лид до брифа).

## 4. Контракт для GUI / пульта / backend_ctl

`system.run.status` и state `system.run.*`:

```
{"state": "ready", "since": 1793000000.0,
 "start_allowed": true, "ack_allowed": false,
 "reasons": [{"node": "recog.ml_inference", "severity": "out_of_spec", "reason": "…", "source": "preflight"}],
 "last_fault": null | {"at": t, "reasons": [...], "acknowledged_at": null | t}}
```

Кнопка ЗАПУСТИТЬ активна ⇔ `start_allowed`; «Квитировать» активна ⇔ `ack_allowed` (`state == "fault"` и `fault_stop_done`;
в первые секунды аварии, пока идёт остановка, неактивна, подпись «идёт остановка»); неактивная показывает первую причину `failure` (ISA-101, §9.5).
ОСТАНОВИТЬ активна ⇔ `state == "running"`. «Квитировать» активна ⇔ `ack_allowed`. Ответы команд:
`system.run.start` → `{"success": bool, "state": ..., "error": "not_ready|already_running|stopping|fault_unacknowledged|shutting_down",
"reasons": [...]}`; `system.run.ack` → `{"success": bool, "state": ..., "error": "no_fault|fault_stopping"}` (Task 1.7).

## 6. Риски

- Стенды и e2e, ждущие кадров сразу после boot, станут красными при `run_gate: true` — перечень вызывающих собрать до
  Task 2.1 (Haiku-опись).
- Хуки `pause/resume` зовутся из потока наблюдателя, параллельно `process()` плагина: реализации в Task 2.2 должны
  быть потокобезопасны; ADR пишет это в контракт.
- Готовность по heartbeat-такту: задержка перехода `ready` до `3 × heartbeat_interval`; приемлемо для оператора, но
  число — в приёмке Task 2.4.
- Плагины, которые грузят тяжёлое в фоне после `start()` (проверить `ml_inference`), объявят готовность рано, если не
  реализуют `readiness()` — Task 2.2.
- Окно `run_restart_grace_s` (30 с) против подъёма тяжёлого процесса: `ml_inference` грузит модель в фоне, здоровый
  рестарт с флагом может уйти в `fault`; срок подбирает 2.4 по измеренному подъёму (Task 1.8).
- Процесс робота (`device_hub`) с `run_auto_restart` встаёт в работу сам, без оператора (против В3): в рецепте 1.0 флаг
  у процессов с `device_hub` не ставится (Task 2.1).
- `ack` в `fault` ждёт `fault_stop_done` до `run_stop_timeout_s` (10 с), если процесс жив, но завис; мёртвый процесс
  срок не держит (правило 3 в §3.2). `ack_allowed` в §4 не даёт нажать раньше.
- Два потока пишут состояние (тик монитора и `message_processor`): гонки «ack с завершением аварийной остановки» и
  «start с потерей готовности» закрываются замком держателя; hazard-тесты в 1.7 (project-rules §9).
- Превью (В2): предпосылка «плагин в `PAUSED` не получает `process()`» не проверена (§8); без неё К6 не решить.

## 7. Не делаем в 1.0

Held/Suspended (голодание ленты, нет диска — индикатор, В8), режимы Production/Maintenance/Manual, OPC UA-сервер,
частичный запуск (часть узлов), аппаратный e-stop. Квитирование (В4) и превью в `ready` по флагу (В2) — в 1.0 по
решению владельца 2026-11-02.

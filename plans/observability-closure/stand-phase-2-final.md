## Критерий 1 — операторская сессия: три плоскости, ноль новых имён команд. **ВЗЯТ**

Одними и теми же тремя инструментами (`introspect_observability`, `config_reload_verified`,
`events_page`) оператор видит, меняет и подтверждает все три плоскости:

| Плоскость | Что подано | Ответ |
|---|---|---|
| **логи** | `{"log_level": "WARNING"}` | `verdict: confirmed`, `checked: 1`, `unverifiable: []`; effective `logger.default_level: WARNING` |
| **уровни** | `{"heartbeat_interval_sec": 1}` | `heartbeat_interval_applied: 1.0`; такт **5.0 → 1.0** (см. критерий 3) |
| **числа** | `observation.rules`, `stats.enabled` | предъявлено стендом Task 2.1, [`stand-phase-2.md`](./stand-phase-2.md) |

Новых имён команд — **ноль**: всё это существующие инструменты, они же обслуживали логи до фазы.

### Побочно предъявлена ЦЕЛЬ фазы — ключ без эффекта не принимается молча

Опечатка `{"logger": {"default_level": "WARNING"}}` (правильное имя — `log_level`) **отвергнута** с
адресом и подсказкой:

```
слой session отвергнут — ключей нет в контракте наблюдаемости (ключ есть, эффекта нет):
logger.default_level; возможно, имелось в виду: log_level, logger_groups, loggers
```

Формулировка «ключ есть, эффекта нет» — дословно предмет Task 2.2.

### Работа Task 2.2 видна в живом readback

В `effective` появились и читаются: `logger_groups` (не `groups`), `retention_days`,
`retention_total_mb`, `compress_rotated`, `retention_sweep_interval_sec`, `channels.<имя>.enabled`,
`error.include_stacktrace`, `command.log_success`, `session_ttl_sec`, и вся секция
`history` (`level`/`max_rows`/`max_age_sec`/`purge_interval_sec`).

## Критерий 2 — сценарий переполнения очереди. **НЕ ПОСТРОЕН**

Критерий требует: «`gui` под нагрузкой → ≤ 1 голос на окно при растущем `queue_full_events`».

**Не предъявлен, и я не отмечаю его сделанным.** На живом стенде все очереди всех восьми процессов
стояли на нуле (`introspect.queues` → `{"system": 0, "data": 0, "state": 0, "observability": 0}`),
`queue_full_events` не рос естественным образом. Чтобы получить событие, надо было бы искусственно
залить never-drop очередь — то есть построить нагрузочный сценарий, которого в дереве нет.

Это ровно тот пункт, который **ревью Ф1 уже поймало один раз**: чекбокс Task 1.4 был закрыт
«(стенд 2026-08-31)» на сценарий, который тот же файл ниже объявлял непостроенным. Повторять эту
ошибку в обратную сторону — отмечать галочкой то, чего я не видел, — не буду.

**Что нужно, чтобы закрыть:** отдельный нагрузочный харнесс (заливка `data`-очереди `gui` до
`Full`) с замером «голосов на окно» против растущего счётчика. Это работа на отдельную задачу, не
на попутный пункт стенда.

Сторожа при этом ЕСТЬ и доказаны инъекциями A1/A2/A4 (`injections-phase-2.md`): пара
«событие есть → счётчик растёт» и «события нет → дельта 0» краснеет поимённо. Не построен именно
ЖИВОЙ сценарий, не сторож.

## Критерий 3 — аномалия `health_errors` через НАСТОЯЩИЙ MCP-сервер. **ВЗЯТ, парой**

Первый стенд после перезапуска сессии, `system_overview` вызван MCP-инструментом, без драйвера из
скрипта — то есть ровно как это увидит холодная агентская сессия.

**До инъекции:** у всех процессов `health: {"status": "ok", "errors": 0}`, аномалии `health_errors`
в сводке нет.

**Инъекция:** `send_command(camera_0, diag.thread_raise)` — исключение в ПОТОКЕ, не в основном
исполнении. Ответ: `{"thread": "diag-thread-raise", "joined": true, "thread_exceptions": 1}`.

**После:** в `anomalies` появились ДВЕ записи —

```
{"kind": "health_errors", "process": "camera_0",
 "detail": "errors=1, последняя: RuntimeError: F2 phase stand: проверка health_errors через
            настоящий MCP (context=thread:diag-thread-raise, ts=1788334197.4666355)"}
{"kind": "thread_exceptions", "process": "camera_0", "detail": "thread_exceptions=1"}
```

Плюс в дереве состояния (`telemetry_snapshot`) заполнены `health.last_error.type` =
`"RuntimeError"`, `.message`, `.context` = `"thread:diag-thread-raise"`, `.ts`.

**Что этим доказано сквозным путём:** исключение, брошенное в потоке, перехвачено
`install_process_hooks` (находка **C3** фазы Ф1), доехало до плоскости ошибок, поднялось в health
процесса и всплыло в сводке под именем — через настоящий MCP-сервер. До Ф1 такое исключение
исчезало молча.

## Критерий 4 (перенесён из Task 2.3) — честный такт живьём. **ВЗЯТ readback'ом, половина критерия переформулирована**

**Пара по readback, до и после `config.reload`:**

| `introspect.telemetry` | до | после |
|---|---|---|
| `tick_effective_sec` | **5.0** | **1.0** |
| `resolved.fps.interval_sec` | 1.0 | 1.0 |
| `resolved.fps.effective_interval_sec` | **5.0** | **1.0** |
| то же у всех восьми метрик и у `port_paths` | 5.0 | 1.0 |
| `observation.effective["processes.*.state.plugins.**"]` | — | `{interval_sec: 1.0, effective_interval_sec: 1.0}` |

`tick_sec` при этом `null` — то есть такт берётся от heartbeat, и это РОВНО тот случай, в котором
до Ф2.3 readback молчал, а голос не звучал вовсе. Расхождение «сконфигурировано 1 с, действует
5 с» теперь видно числом. Применилось без рестарта (`heartbeat_interval_applied: 1.0`).

### Половина критерия сформулирована неверно — исправляю формулировку, не наблюдение

Критерий писал: «дельты каждые 1 с (пара по `events_page`)». **Так это не измеряется.**
`telemetry.delta` несёт `old_value`/`new_value`, то есть публикуется **на ИЗМЕНЕНИЕ значения**, а не
на тик. Замер это подтвердил: за одно окно у `processes.camera_0.state.fps` — 4 дельты с
интервалами `[1.0, 6.0, 3.02]`, у `uptime` соседнего процесса (публикатор `ProcessMonitor`, свой
такт 0.5 с) — 21 дельта с ровными `[0.5, 0.5, …]`. Каденция дельт отражает частоту изменения
величины, а не такт публикации.

Механизм доказан двумя другими наблюдениями (readback-пара выше и `heartbeat_interval_applied`).
Формулировку критерия в плане надо править на «readback показывает эффективный такт», а
наблюдение — нет.

## 🔴 Находка стенда — `unverifiable` БЕЗ ИМЕНИ, хуже прошлой

`config_reload_verified(camera_0, {"heartbeat_interval_sec": 1})` вернул:

```
"verdict": "unverifiable", "checked": 0, "mismatches": [], "unknown_keys": [], "unverifiable": []
```

При этом ручка ПРИМЕНИЛАСЬ (`heartbeat_interval_applied: 1.0`, readback изменился с 5.0 на 1.0).

Это тот же класс, что находка прошлого стенда про `stats.enabled`, но **в худшей форме**: там ключ
хотя бы назывался в списке `unverifiable`, здесь список **ПУСТ**. Оператор получает «я не смог
проверить» и не узнаёт, ЧТО именно не проверено. Ответ, не отличимый от «проверять было нечего».

Ключ введён задачей 2.3 этой же фазы — то есть фаза, чинившая молчащие ручки, завела ручку, о
которой молчит верификатор.

**Не чинил:** это добор к Task 2.2 (покрытие верификатора), а стенд — не место для правки кода.
Кладётся рядом с открытым долгом по `stats.enabled`: у обоих одна причина и, вероятно, одно
лечение.

   контроль `interval_sec=0.02, tick=None → {'fps': {…0.02, 0.05}}`. Совпадает с находкой 2 ревью Task 2.11 и её починкой.
2. **Дефолт поддерева через `observation_rules`** (`{"processes.*.state.plugins.**": {"enabled": True, "interval_sec": 0.0}}`):

3. **`capped_metrics`**: `tick 5.0 → [('fps', 1.0), ('processes.*.state.plugins.*.x', 1.0)]` при явных единицах; `tick 0.0 → []`, `tick -3 → []`.

## 3. Находки

### F1 (medium, ошибка модели в безопасную сторону) — сверщик потолков судит заявку, которую публикатор не сделает

```
detect_throttle_caps({'metrics': {'fps': {'interval_sec': 1.0}}}, throttle={'**.state.fps': 2.0}, effective_tick=5.0)
-> {'fps': {'publisher_interval_sec': 1.0, 'throttle_interval_sec': 2.0}}
тот же вход по правилу пути (processes.*.state.plugins.*.fps: 1.0, троттл 2.0, tick 5.0)
-> {'processes.*.state.plugins.*.fps': {'publisher_interval_sec': 1.0, 'throttle_interval_sec': 2.0}}
```

При такте 5.0 публикатор просит **5.0** (это ровно `effective_interval_sec = max(interval, tick)`, введённый
Task 2.3 как «честный такт»), троттл 2.0 его не режет — а отчёт называет потолок. Task 2.11 сделала
замещение тактом только для **нуля**; для положительной заявки ниже такта та же логика не применена, и
у двух сверщиков одного публикатора остались две модели его частоты. Ошибка в сторону лишнего
предупреждения, не молчания, поэтому не блокер; но Ф2 называлась «честный readback», и это её предмет.
На боевых правилах троттла (0.05 с) не проявляется — только при операторском строгом правиле.

**Лечение** — одна строка в `_publisher_ask`: при известном такте `asked = max(pub_interval, tick)`;
при неизвестном — как сейчас (для нуля — «не судить», F2). Пара тестов литералами: `(1.0, тик 5.0,
троттл 2.0) → {}` и `(1.0, тик 0.5, троттл 2.0) → потолок`. Предсказание инъекции «снять `max`» — ровно
первый из пары красный.

### F2 — вердикт CTO по веерной рассылке `telemetry.broadcast` (открытый вопрос из `OPEN_QUESTIONS.md`)

**Вариант (б): назвать непосуженных кандидатов отдельным списком в ответе.** Не (а) и не (в), по
следующим воспроизведённым доводам.

- **Почему не (а).** `_cmd_telemetry_broadcast` (`process_manager_process.py:3151`) зовёт сверщик без
  такта и кладёт `capped_by_throttle` в ответ только при непустом отчёте. Ответ на `interval_sec: 0`
  теперь **неотличим** от ответа «потолков нет» — это класс «`checked=true` отвечает за вызов, а не
  за охват», который в этом проекте уже дважды стоил живого разбора. Тест-якорь
  `test_an_explicit_zero_interval_is_no_longer_flagged_here` пришпиливает тишину, но тишина
  осталась неразличимой.
- **Почему не (в) сейчас.** Чтобы веер судил «по-честному», ProcessManager обязан знать такты
  адресатов. Сегодня он их не знает **структурно**: heartbeat читает `heartbeat_interval` один раз
  на старте (`process_heartbeat.py:116`) и в payload такт не публикует — грепом по
  `process_heartbeat.py` ни одного места, где `_interval` уходит в сообщение. Значит (в) — это новое
  поле в heartbeat-payload плюс сверка по каждому адресату: настоящая задача Ф4 рядом с 4.11, а не
  закрытие фазы.
- **Форма (б), чтобы не плодить второй механизм.** Не вторая функция с копией цикла, а один
  проход: `judge_throttle_caps(...) -> (caps, unjudged)` — `unjudged` собирается там же, где
  `_publisher_ask` возвращает `None`; `detect_throttle_caps` остаётся тонкой обёрткой,
  возвращающей `caps` (оба вызывающих и GUI-presenter `_telemetry_controls.py:349` не трогаются).
  В ответе веера — `publish.throttle_unjudged: [...]` только при непустом списке (та же дисциплина,
  что у `capped_by_throttle`), с причиной `"publisher tick unknown at fan-out"`. Тест-якорь при этом
  краснеет и переписывается — ровно так, как обещал его докстринг.
- **Объём:** `telemetry_reload.py`, `process_manager_process.py` (три строки), два теста. Вместе с F1 —
  один файл механизма. Это и есть предлагаемая **Task 3.0**, до merge в `main`.

# Живой стенд Task 3.5 — `history_query` (2026-09-04)

Стенд: `BackendHarness`, рецепт `region_pipeline`, 8 процессов, headless (`QT_QPA_PLATFORM=offscreen`).
Стор — настоящий файл, накопленный прошлыми прогонами: `logs/prototype_2/observability.db`.
Два захода: первый снял основную часть, второй перемерил два пункта, испорченных **моим зондом**, а не механизмом.

## Заход 1 — WAL-хазард на файле, который пишут прямо сейчас

Это был главный риск задачи: read-only соединение к БД в режиме WAL может не открыться вовсе.

| Проверка | Результат |
|---|---|
| `-wal` и `-shm` рядом с файлом | оба **есть** |
| Чтение через `file:…?mode=ro` под живым писателем | **7629 строк**, соединение не подвисло |
| `INSERT` через то же соединение | **отказ**: `attempt to write a readonly database` |
| Тот же файл через 6 с | **7633** строки — лента росла, пока читатель работал |
| Свежайший `id` после этого | 311694 |

Хазард закрыт живьём, а не рассуждением: писатель и читатель сосуществуют, запись отвергается по факту.

## Заход 2 — перемер того, что испортил мой зонд

**M1. Окно `since`/`until`.** В первом заходе я поставил `limit=500`, и все три вызова упёрлись в
него — «сузило/не сузило» было неразличимо (500 / 500 / 500). Это дефект замера, а не механизма.
С `limit=20000`:

| Вызов | Строк |
|---|---|
| без окна | **8788** |
| `since=-600` (последние 10 мин) | **2298** |
| `until=-600` (всё, что старше) | **6490** |
| сумма двух окон == всей ленте | **True** (2298 + 6490 = 8788) |
| контроль прямым SQL по тому же файлу | **(8788, 2298)** — совпало точно |

Окно не просто «что-то сузило»: **на этих данных** разбиение оказалось точным, и то же число даёт
независимый SQL-счёт мимо драйвера.

**Поправка ревью (Н-5).** Первая редакция этой строки читалась как свойство МЕХАНИЗМА («делит без
потерь и без перекрытия»). Механизм даёт `ts >= ?` и `ts <= ?` — **обе границы включающие**, и
«сейчас» у двух вызовов резолвится в два разных момента: запись ровно на границе попала бы в оба
окна. Точность разбиения здесь — свойство данных: `COUNT(*) WHERE ts = now-600` на том же файле
дал **0**, граничных строк не было. Заявление сужено до факта.

**M2. `trace_id`.** В первом заходе я искал его на верхнем уровне `extra` и получил 0 из 4 — снова
зонд, а не механизм. `trace_id` лежит в `extra["context"]`:

| Проверка | Число |
|---|---|
| ошибок за час | 4 |
| из них с `trace_id` в `extra["context"]` | **4 из 4** |
| с `trace_id` на верхнем уровне `extra` | 0 |
| строк с ОДНИМ и тем же `trace_id` | **2** (`76ade735…` — два лица одного инцидента: `send_to_queue(...) failed: Full()` и `RouterSendError: delivery_failed`) |

**Поправка к критерию приёмки.** В плане было написано «строки с `trace_id` **колонкой**». Колонки
такой нет и не планируется: `trace_id` — вложенный ключ JSON-поля `extra.context`. Критерий выполнен
по существу (корреляция доезжает и связывает строки одного инцидента), формулировка исправлена.

**M3. Пара по severity.** `severity=["critical"]` → **0** при `severity=["error"]` → **98**;
`min_severity=17` → те же **98**. Ноль стоит рядом с ненулём, порог и членство сходятся.

## Что стенд показал сверх задачи

Первая же строка `kind=log` на живом стенде:

```
metrics snapshot (ts=1788523141, count=2): [{'name': 'capture.frames', 'type': 'counter', …
```

То есть снапшоты чисел лежат в сторе как **логи**. Это ровно посылка **Task 3.1** («`kind=log`
строк „metrics snapshot“ в сторе = 0»), и теперь она подтверждена числом, а не ожиданием:
3751 лог-строка на 1019 stats-строк.

## Сверка ревьюером на том же файле (позже, 2026-09-04)

Ревьюер повторил golden path по тому же файлу БД **после** обоих моих заходов и получил другие
числа родов: `log 4908 · error 98 · stats 1036 · observation 2778` (всего 8820) против моих
`3751 · 98 · 1019 · 2760` (7629) в первом заходе и 8788 во втором. Расхождение объяснимо и
проверяемо арифметикой: файл **накопительный** и растёт с каждым прогоном стенда — 7629 → 8788 →
8820 по возрастанию времени снятия. Ни одно из трёх чисел не отменяет другое; сравнивать между
собой можно только замеры одного захода.

Сверка ревьюера при этом усилила посылку **Task 3.1**: строк «metrics snapshot» с `kind=log` ровно
**1036** — столько же, сколько записей `kind=stats`. Равенство чисел само по себе было бы лишь
намёком, поэтому я вытащил обе последние строки и сверил их:

| | `kind=stats` | `kind=log` |
|---|---|---|
| `ts` | 1788523259.9637876 | 1788523259.962787 (**на 1 мс раньше**) |
| `process` | ProcessManager | ProcessManager |
| `module` | `ProcessManager` | `multiprocess_framework.modules.statistics_module` |
| содержимое | «metrics snapshot (count=18), имён 6: …» | «metrics snapshot (ts=…, count=18): [{…}]» |

Это ОДИН снапшот, записанный ДВАЖДЫ двумя разными путями, а не «иногда дублируется». Сверх того
лог-копия ещё и **усечена**: её хвост — `… опущено 7 из 18 метрик, предел 2048 байт`. То есть
дубликат не только удваивает объём, но и теряет больше трети содержимого — ровно то, что Task 3.1
чинит шагом «в стор только через hub, `message` = JSON, без усечения по 2048 Б».

## Чего стенд НЕ доказал

- `-shm`, недоступный на запись, не проверялся: на Windows не нашлось надёжного способа сделать
  каталог read-only на время прогона. Ветка отказа открытия остаётся непокрытой.
- Все замеры сделаны на ОДНОЙ машине: расхождение часов писателя и читателя (`since` считается по
  часам драйвера) на одном хосте не воспроизводится в принципе. Дыра названа в докстроке и
  закреплена hazard-тестом как **документируемая**, а не как гарантия.

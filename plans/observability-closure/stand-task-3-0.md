> INSPECTOR_LOG_DIR=logs_live/f3_task30_stand2 .venv/Scripts/python.exe multiprocess_prototype/frontend/run.py`.
> Топология: `ProcessManager`, `camera_0`, `devices`, `gui`, `lines`, `points`, `pult`, `seg`.

## Что предъявлялось

Сверщик потолков живёт только там, где есть **центральный троттл**, а он есть только у
оркестратора: `introspect.telemetry(points).throttle_rules` = `null`,
`introspect.telemetry(ProcessManager).throttle_rules` — 11 боевых правил с предохранителем `0.05`.
Поэтому обе пары сняты на `ProcessManager`; такт обоих — `tick_effective_sec: 5.0`.

**Боевой вход находки F1 нашёлся в системе сам, без подстройки.** На буте лог даёт:

```
[points] heartbeat: частота ... ограничена тактом 5.0с: fps (interval_sec=1.0с),
latency_ms (interval_sec=1.0с) — публикация фактически по одному такту
```

то есть заявка `1.0` при такте `5.0` — не выдуманный случай, а конфигурация прототипа.
Readback подтверждает число: `resolved.fps.effective_interval_sec: 5.0` при `interval_sec: 1.0`.

## Пара F1 — реальный ask публикатора

Правило порта `processes.points.state.fps` с `interval_sec: 1.0` (сессионный слой, TTL 300 с),
такт `5.0`, меняется только правило троттла на этот путь.

| Вход | `capped_by_throttle` | Читается как |
|---|---|---|
| троттл **2.0** | `{}` | потолка нет: публикатор попросит 5.0, правило 2.0 его не режет |
| троттл **6.0** | `{"processes.points.state.fps": {"publisher_interval_sec": 5.0, "throttle_interval_sec": 6.0}}` | потолок есть, и назван **реальный** ask 5.0, а не заявленная 1.0 |

До правки первый вход дал бы отчёт о потолке (ask читался дословно: `2.0 > 1.0`) — это и есть
находка F1 вердикта CTO. Обе половины сняты подряд, `throttle_checked: true` в обеих.

## Пара F2 — веер «не судил»

Окно без такта — **0.08 с** (три вызова одним скриптом; см. «Ограничение стенда» ниже).

| Вход | `caps` | `capped_by_throttle_unjudged` |
|---|---|---|
| такт `5.0` (контроль) | `publisher_interval_sec: 5.0` | **ключа нет** |
| `heartbeat_interval_sec: 0` (такт выключен) | `publisher_interval_sec: 1.0` | `{"processes.*.state.plugins.**": "no_tick"}` |
| такт возвращён `5.0` | `publisher_interval_sec: 5.0` | **ключа нет** |

Три вещи разом: (1) без такта регресс сохранён — судим по заявке, `1.0`, как до Ф3; (2) дефолт
поддерева, который рассудить нечем, назван вслух, а не пропущен молча; (3) ключ появляется
и исчезает вместе с причиной — «пустой список» и «ключа нет» не смешиваются.

## Порядок стадий внутри одного `config.reload` — наблюдение, не дефект задачи

Первый вызов с `heartbeat_interval_sec: 0` вернул `heartbeat_interval_applied: 0.0` **и при этом**
отчёт, посчитанный по СТАРОМУ такту 5.0 (`publisher_interval_sec: 5.0`, веера нет). Новый такт
виден только следующему вызову. Это согласуется с трёхстадийностью команды (решение B2 / Task 5.7):
политика порта применяется раньше, чем такт. В область Task 3.0 не входит, но читателю отчёта
это не объявлено нигде — кандидат в наблюдение к Task 4.11, где голос переезжает на стадию
«применяю».

## Ограничение стенда — F2 нельзя предъявлять долго

Первая попытка держала `heartbeat_interval_sec: 0` на оркестраторе ~2.5 минуты, пока я вёл
диалог с системой. Итог: `ProcessManager` перестал принимать сообщения
(`RouterSendError: ни один из 1 адресатов не принял`, `command='state.merge'`, у всех детей),
супервизор ушёл в `restart-not-confirmed` по `camera_0` (попытка 3/3), стенд пришлось погасить и
поднять заново. На узком окне 0.08 с система этого не заметила: после возврата такта
`system_overview` — 8 процессов `running`, `errors: 0` у всех роутеров, единственная аномалия
`telemetry_readmodel_empty` (безобидная, подписки нет).

**Это находка не Task 3.0, а ручки `heartbeat_interval_sec` на оркестраторе:** значение `0`
принимается схемой (`min=0.0`) как «heartbeat отключён», применяется без возражений и без
предупреждения о последствиях, а через минуты кладёт доставку сообщений всей топологии.
Записана в [`OPEN_QUESTIONS.md`](../../docs/claude/OPEN_QUESTIONS.md).

**Второе ограничение, названное вслух:** связка «есть центральный троттл + такта нет» существует
ТОЛЬКО на оркестраторе, поэтому предъявить F2 на детском процессе нельзя в принципе — у детей
`throttle_checked: false`, сверщик не зовётся. Это же ограничение делает оптовый путь
`telemetry.broadcast` (Task 4.12) единственным местом, где веер будет иметь второго читателя.

## Чего стенд НЕ проверял

- Цену вызова: сверщик считает над словарями правил (единицы записей), тайминга не снимал.
- Поведение при `heartbeat_interval_sec < 0`: с дороги конфига недостижимо (схема `min=0.0`) —
  это находка F6 вердикта CTO, и она в силе.
- GUI-представление отчёта: presenter задачей не трогался, глазами не смотрел.
- Оптовый путь `telemetry.broadcast`: он F1 не получил (Task 4.12), на стенде не предъявлялся.

### Task 5.1 — Экспозиция счётчиков `SimJournal` + инвариантный прогон

**Level:** Middle+ (Sonnet, extended thinking)
**Assignee:** developer
**Goal:** счётчики `SimJournal` (`jobs_seen`, `dups_seen`, `jobs_done`) читаемы
СНАРУЖИ процесса `robot` (команда/state), и есть воспроизводимый прогон, измеряющий
ГЛАВНЫЙ инвариант — «один объект → одна команда роботу» — на реальном
end-to-end тракте.

**Контекст:** `SimJournal` (перенесён в Ф0) уже умеет то, что нужно: детектор дублей
по инварианту трекинга ленты, с break-injection-проверенными тестами (per worktree
STATUS.md). Здесь НЕ пишется новый детектор — берётся готовый и подключается к
`RobotSimProcessPlugin` (Task 1.2), затем публикуется наружу.

**Files:**
- `Plugins/sim/robot_sim_process/plugin.py` — подключить `SimJournal` (аналогично
  `run_sim_robot(gui=True)`, но БЕЗ Qt-окна — публикация через command/state, не
  через `SimMonitorWindow`, которое встраивается в GUI отдельно в Task 6.2)
- `Plugins/sim/robot_sim_process/plugin.py` — `commands: {"get_journal_counters":
  "cmd_get_journal_counters"}` (или state-путь, по аналогии с Task 2.2)
- `plans/line-sim/scratch/invariant_run.md` — НЕ создавать; тестовый харнесс — файл
  теста, см. ниже
- `Services/robot_comm/tests/test_sim_e2e.py` ИЛИ новый интеграционный тест на
  уровне line_sim (`Services/line_sim/tests/test_invariant_no_duplicate_jobs.py`) —
  прогон N объектов, проверка `dups_seen == 0`

**Steps:**
1. В `RobotSimProcessPlugin.start()`: создать `SimJournal()`, передать
   `on_write=journal.on_write` в `SimRobotServer(...)`, передать `journal.on_event`
   как второй sink в `RobotSimCore(on_event=...)` (см. `sim_robot.py` `emit()` —
   список sinks; переиспользовать тот же паттерн `sinks.append`, не переизобретать).
2. `cmd_get_journal_counters(data) -> dict` — возвращает `journal.counters()`
   (`{"jobs": int, "dups": int, "done": int, "reads": int}`) — прямой прокси
   существующего метода, без переформатирования.
3. Написать интеграционный прогон (для теста, не для прод-кода): поднять
   sim-топологию (Ф1) целиком ИЛИ, если полный e2e через `run.py` слишком тяжёл для
   pytest, — минимум подключить реальный `RobotDriver`/`device_hub` к реальному
   `SimRobotServer` (как уже делают существующие тесты `test_sim_e2e.py`) и
   ПРОГНАТЬ через него N job'ов, сформированных из line_sim's spawn (Task 3.3) —
   вычисляя `e_capture` для каждого так, как это делает реальный тракт
   (`pixel_to_robot`/`RobotDriver._apply_pick_lead`), а НЕ подавая идеальные
   несовпадающие координаты вручную (иначе тест доказывает не то, что нужно —
   инвариант должен быть проверен на РЕАЛИСТИЧНОМ потоке заданий, где дубли в
   принципе МОГЛИ БЫ возникнуть, если бы дедуп был сломан).
4. Зафиксировать, что «реалистичный тайминг» (per worktree DECISIONS/STATUS —
   `--job-ms 2500` дефолт, НЕ 20мс) — обязателен для этого прогона: на мгновенном
   роботе дефект «одна деталь → три задания» не воспроизводится (задокументировано в
   `server/__main__.py` docstring, уже прочитано при планировании) — тест ОБЯЗАН
   держать `job_ms` близким к реалистичному (или явно варьировать его как параметр,
   чтобы показать, что при БЫСТРОМ роботе инвариант тривиально держится, а измерение
   ценно именно при МЕДЛЕННОМ).

**Acceptance criteria:**
- [ ] `cmd_get_journal_counters({})` возвращает словарь с ключами `jobs`, `dups`,

- [ ] Прогон с ТЕМ ЖЕ объектом, инференс на КОТОРЫЙ вызывается искусственно 3 раза
      подряд (симулируется намеренно сломанный тракт — прямой вызов

      всегда возвращает 0). Это break-injection-проверка САМОГО измерения, не

- [ ] `pytest Services/robot_comm -q` — 0 failed (не регрессирует существующие 40+

**Out of scope:** confusion-matrix (caught/missed/false_alarm) — это Task 5.2/5.3,

**Edge cases:** объекты спавнятся БЫСТРЕЕ, чем робот успевает разобрать очередь —
это ОЖИДАЕМЫЙ сценарий, в котором дубли МОГУТ появиться на реальном железе тоже (это

#### Контракт лида 5.1 (ред. 3, 2026-09-23, до тестера)

**Зачем владельцу (слова 2026-09-23):** на живой линии робот забирал одну деталь трижды, и
было непонятно — приходят три одинаковые фотографии, дублируются команды или виноват робот.
Сим подменяет робота, поэтому его журнал отвечает однозначно: **сколько заданий пришло от
прототипа и почему повтор**. Если задание на деталь одно — дефект в роботе, не в прототипе.

**Разведка (лид):** `SimJournal` уже считает `jobs/dups/done/reads`, но к `robot_host` не
подключён — наружу течёт только `writes_seen`. `RobotDriver.enqueue_job` берёт `e_capture` из
кадра, если pipeline его протянул, иначе читает энкодер В МОМЕНТ ПОСТАНОВКИ в очередь. Тогда
повторный кадр даёт одинаковые X/Y с РАЗНЫМ энкодером — детектор по трекингу ленты считает
это разными деталями, а робот едет забирать трижды со сдвигом. Одного числа «дубли» мало:
нужна причина повтора. Пути ред. 1 в тексте выше читать по таблице в шапке файла.

**1. `Services/robot_comm/server/sim_journal.py` (extends-contract).** Для нового задания
против недавних в окне `dup_window_s`, радиус `r = dup_radius_mm`:
- дубль по трекингу (как сейчас, невязка `< r`) → `dups += 1` и причина:
  `ecap == prev.ecap` → `dups_same_capture` (одна съёмка отправлена дважды — дубль команды);
  иначе → `dups_tracked` (та же деталь снята на другом кадре — прототип не отсеял);
- иначе, если есть недавнее с `hypot(Δx, Δy) < r` и `ecap != prev.ecap` →
  `repeats_frozen_xy += 1` (те же координаты с новым энкодером: повтор кадра или энкодер
  читался при постановке в очередь); в `dups` НЕ входит; строка журнала с тегом `"repeat"`.
- `counters()` — прежние ключи без изменений (`jobs, dups, done, reads` — их читает
  `SimMonitorWindow`) плюс `dups_same_capture`, `dups_tracked`, `repeats_frozen_xy`;
  `reset()` обнуляет и их. Инвариант: `dups == dups_same_capture + dups_tracked`.
- Литералы (`r = 5.0`, лента по +Y, 0.144473 мм/счёт): `(10.0, 20.0, e=1000)` затем
  `(10.0, 20.0, e=1000)` → `dups=1, dups_same_capture=1`; затем вместо второго
  `(10.0, 164.473, e=2000)` → `dups=1, dups_tracked=1`; вместо второго `(10.0, 20.0, e=2000)` →
  `dups=0, repeats_frozen_xy=1`; `(10.0, 20.0, e=1000)` и `(60.0, 20.0, e=1000)` → все нули.
- Известный предел: на СТОЯЩЕЙ ленте два честных кадра одной детали дают `Δenc = 0` и
  попадут в `dups_same_capture` — причину читать вместе со скоростью ленты.
- **Дополнение ревью 2026-09-23 — зона неразличимости шире стоящей ленты:** при
  `|Δenc| * 0.144473 < r` (r = 5 мм → меньше ~35 отсчётов, на 101 мм/с — меньше ~50 мс между
  постановками) повтор X/Y с новым энкодером идёт в `dups_tracked`, не в `repeats_frozen_xy`
  (замер: `(10, 20, e=1000)` + `(10, 20, e=1020)` → `dups_tracked=1`). Порядок проверок —
  по контракту; различить внутри зоны может только номер кадра на стороне прототипа (Task 5.3).

**2. `Plugins/sim/robot_host/plugin.py`.**
- `_start_server` создаёт `SimJournal()` (word_order — тот же, что у ядра); существующий
  `_on_write` дополнительно отдаёт каждую запись/чтение в `journal.on_write`; ядро получает
  `on_event=journal.on_event` (рядом с `on_job_done` из 3.5 — оба колбэка в одном конструкторе).
- Уровни на такте публикации (`publish_metric`, ADR-PM-038; `declare_metric` в `configure`):
  `jobs_seen`, `dups_seen`, `dups_same_capture`, `dups_tracked`, `repeats_frozen_xy`, `jobs_done`.
- Такт публикации забирает `journal.drain()` в свой `deque(maxlen=50)` только строк с тегами
  `job/dup/repeat/done` (drain разрушающий — забирает один владелец; память журнала плоская).
- Команды: `"sim_robot.journal"` → `{"status": "ok", "counters": {...counters()}, "recent":
  [≤ 50 {"t", "side", "text", "tag"}, старые первыми]}`; `"sim_robot.journal_reset"` →
  `journal.reset()` + очистка `recent`, ответ `{"status": "ok"}`. Сервер не поднят →
  `{"status": "error", ...}` (как `_no_server` у `belt.*`). `sim_robot.status` получает ключ
  `"journal"` со снимком `counters()`.

**3. `Plugins/sim/pult_web/plugin.py`.** `GET /api/journal` → форвард `sim_robot.journal`;
`POST /api/journal/reset` → `sim_robot.journal_reset` (через тот же `_client.request`). На
странице блок «Задания от прототипа», опрос раз в 1 с: `принято N · повтор той же детали M
(та же съёмка A / новый кадр B) · те же X/Y с новым энкодером C · выполнено K`, кнопка «Сброс
счётчиков». Логики подсчёта в пульте нет — только показ.

**4. Живой стенд (лид, после слияния).** Два приложения (8765 + 8766), `job_ms` не меньше
1000: (а) N ≥ 20 объектов, поток без перекрытий → `dups = 0`, `repeats_frozen_xy = 0`,
`jobs_seen` = числу заданий, которые прототип сообщил отправленными; (б) break-injection
самого измерения: одно задание трижды через `backend_ctl` прототипа (та же точка, тот же
`e_capture`) → `dups_same_capture >= 2`; трижды без `e_capture` (драйвер читает энкодер сам)
на едущей ленте → `repeats_frozen_xy >= 2`.

**Кто что пишет.** Тестер (worktree до реализации): п.1 полностью, п.2 на фейковом ctx
(команды, reset, ключ `journal` в статусе, уровни), п.3 форвард двух маршрутов с подменой
клиента. Автор: hazard — `drain` из такта публикации против `on_write` из потока сервера;
reset во время потока заданий. Стенд п.4 — лид.

### Task 5.3 — Счётчики наружу + сквозной прогон обоих инвариантов

**Level:** Middle+ (Sonnet, extended thinking)
**Assignee:** developer
**Goal:** счётчики из Task 5.1 (`SimJournal`) и Task 5.2 (`SimTruthEvalPlugin`)
читаемы ОДНИМ способом (для пульта Ф6.2 и для тестов) и есть ОДИН сквозной
интеграционный прогон, подтверждающий v1 целиком: N объектов проезжают ленту, робот
получает по одному job на объект (Ф5.1), а вердикты инспектора сравнены с правдой
(Ф5.2) — оба измерения в одном прогоне, не в изоляции.

**Files:**
- `Services/line_sim/tests/test_v1_end_to_end_invariants.py` (или в
  `multiprocess_prototype/tests/` — выбрать по месту, где уже есть похожие e2e-тесты
  на весь рецепт, если такие существуют — проверить перед созданием нового каталога)
- Мелкая доводка API из 5.1/5.2 для единообразного чтения (например единый префикс
  state-путей `line_sim.journal.*` / `line_sim.eval.*`) — правки НЕ архитектурные

**Steps:**
1. Свести оба измерения в один прогон: топология Ф1 полностью (robot + line_cam +
   боевой vision/line/recog/layout), N=20+ объектов с фиксированной пропорцией
   брака, `job_ms` реалистичный (см. Ф5.1 Step 4).
2. Собрать итоговый отчёт прогона: `{jobs_sent, dups, caught, missed, false_alarm}`
   — assert на согласованность (например `jobs_sent - dups` не должно катастрофически
   расходиться с `caught + missed + false_alarm`, с разумным допуском на объекты,
   не успевшие завершить цикл к концу прогона).

**Acceptance criteria:**
- [ ] Прогон 20 объектов (пропорция брака ~20%), `job_ms>=1000`,
      завершается за разумное время (задать явный timeout, например 120с);
      по завершении: `dups == 0` (или ниже явно задокументированного порога, если
      0 недостижим по не зависящим от line_sim причинам — задокументировать
      причину, не молчать про несовпадение с ожиданием per STRICT-канон).
- [ ] `caught + missed + false_alarm >= 0.8 * <число объектов, реально пересекших
      триггер-линию за время прогона>` (не 100% — часть объектов у самого конца
      прогона может не успеть завершить цикл, это ожидаемо и не дефект; порог 0.8 —
      отправная точка, Developer вправе уточнить по факту первого прогона, указав

### Task 5.4 (новая) — Ручки отказов: инвариант дублей под отказом

**Level:** Middle+ (Sonnet)
**Assignee:** developer
**Goal:** отказ устройства — воспроизводимая команда, а не случайность. Главный вопрос
задачи: **рождает ли инспектор дубли заданий, когда робот замолчал и вернулся?** На железе
этот сценарий не повторить по заказу; ради него симулятор и нужен.

**Files:**
- `Plugins/sim/robot_host/plugin.py` — команды `fault.drop`, `fault.delay_ms`,
  `fault.vfd_code`, `fault.clear`; активные отказы — в `sim_robot.status`
- `Services/robot_comm/server/sim_core.py` — регистр FAULT зеркала ПЧ (`0x1210 + 4`,
  сегодня жёстко 0) берётся из ручки
- `Plugins/sim/robot_host/tests/`, `README.md`

**Steps:**
1. `fault.drop {seconds: N}` — готовыми `SimRobotServer.stop()` → пауза → `.start()`.
2. `fault.delay_ms` — **сначала разведка**: позволяет ли сервер pymodbus задержать ответ,
   не блокируя свой цикл. Если нет — ручка не делается, ограничение записывается в README
   числом и причиной; выдумывать обход не нужно.
3. `fault.vfd_code {code}` — значение FAULT в зеркале ПЧ после следующего пульса команды.
4. Прогон инварианта: 100 объектов, `fault.drop {seconds: 3}` в середине.

**Acceptance criteria:**
- [ ] `fault.drop {seconds: 3}`: `socket.create_connection(("127.0.0.1", 5021), timeout=1)`
      отказывает в течение 1 с и снова удаётся не позже чем через 5 с. Тест не может
      повиснуть: вызов в daemon-потоке с дедлайном `join`.
- [ ] `fault.vfd_code {code: 7}` + пульс команды ПЧ → чтение `0x1214` даёт 7;
      `fault.clear` + пульс → 0.
- [ ] `sim_robot.status` перечисляет активные отказы; после `fault.clear` список пуст.
- [ ] Живой стенд двух приложений, 100 объектов с обрывом в середине: `dup_jobs`,
      `SimJournal.dups_seen`, `missed` — **три числа в отчёте**. Ноль дублей — критерий
      пройден; не ноль — находка с воспроизведением в `docs/claude/OPEN_QUESTIONS.md`
      (дефект инспектора, а не симулятора).

**Out of scope:** отказы камеры (замирание потока) — следующая ручка, по тому же образцу.
**Dependencies:** Task 5.1; живой прогон — Task 5.2.
**Module contract:** impl-only.

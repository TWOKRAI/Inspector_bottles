# Phase 5 — Правда и измеримый инвариант

Часть плана [`plan.md`](plan.md). Реализует «Функция правды в v1: паспорт объекта +
счётчики «поймал/пропустил/ложная тревога»; ГЛАВНЫЙ измеряемый инвариант: один
объект → одна команда роботу». Два НЕЗАВИСИМЫХ измерения на двух разных концах петли:
Task 5.1 — на стороне робота (готовый инструмент, `SimJournal`), Task 5.2/5.3 — на
стороне вердикта инспектора (новый evaluator).

---

### Task 5.1 — Экспозиция счётчиков `SimJournal` + инвариантный прогон

**Level:** Middle+ (Sonnet, extended thinking)
**Assignee:** developer
**Goal:** счётчики `SimJournal` (`jobs_seen`, `dups_seen`, `jobs_done`) читаемы
СНАРУЖИ процесса `robot` (команда/state), и есть воспроизводимый прогон, измеряющий
ГЛАВНЫЙ инвариант — «один объект → одна команда роботу» — на реальном
end-to-end тракте.

**Контекст:** `SimJournal` (перенесён в Ф0) уже умеет то, что нужно: детектор дублей
по инварианту трекинга ленты, с break-injection-проверенными тестами (per worktree
STATUS.md). Здесь НЕ пишется новый детектор — берётся готовый и подключается к
`RobotSimProcessPlugin` (Task 1.2), затем публикуется наружу.

**Files:**
- `Plugins/sim/robot_sim_process/plugin.py` — подключить `SimJournal` (аналогично
  `run_sim_robot(gui=True)`, но БЕЗ Qt-окна — публикация через command/state, не
  через `SimMonitorWindow`, которое встраивается в GUI отдельно в Task 6.2)
- `Plugins/sim/robot_sim_process/plugin.py` — `commands: {"get_journal_counters":
  "cmd_get_journal_counters"}` (или state-путь, по аналогии с Task 2.2)
- `plans/line-sim/scratch/invariant_run.md` — НЕ создавать; тестовый харнесс — файл
  теста, см. ниже
- `Services/robot_comm/tests/test_sim_e2e.py` ИЛИ новый интеграционный тест на
  уровне line_sim (`Services/line_sim/tests/test_invariant_no_duplicate_jobs.py`) —
  прогон N объектов, проверка `dups_seen == 0`

**Steps:**
1. В `RobotSimProcessPlugin.start()`: создать `SimJournal()`, передать
   `on_write=journal.on_write` в `SimRobotServer(...)`, передать `journal.on_event`
   как второй sink в `RobotSimCore(on_event=...)` (см. `sim_robot.py` `emit()` —
   список sinks; переиспользовать тот же паттерн `sinks.append`, не переизобретать).
2. `cmd_get_journal_counters(data) -> dict` — возвращает `journal.counters()`
   (`{"jobs": int, "dups": int, "done": int, "reads": int}`) — прямой прокси
   существующего метода, без переформатирования.
3. Написать интеграционный прогон (для теста, не для прод-кода): поднять
   sim-топологию (Ф1) целиком ИЛИ, если полный e2e через `run.py` слишком тяжёл для
   pytest, — минимум подключить реальный `RobotDriver`/`device_hub` к реальному
   `SimRobotServer` (как уже делают существующие тесты `test_sim_e2e.py`) и
   ПРОГНАТЬ через него N job'ов, сформированных из line_sim's spawn (Task 3.3) —
   вычисляя `e_capture` для каждого так, как это делает реальный тракт
   (`pixel_to_robot`/`RobotDriver._apply_pick_lead`), а НЕ подавая идеальные
   несовпадающие координаты вручную (иначе тест доказывает не то, что нужно —
   инвариант должен быть проверен на РЕАЛИСТИЧНОМ потоке заданий, где дубли в
   принципе МОГЛИ БЫ возникнуть, если бы дедуп был сломан).
4. Зафиксировать, что «реалистичный тайминг» (per worktree DECISIONS/STATUS —
   `--job-ms 2500` дефолт, НЕ 20мс) — обязателен для этого прогона: на мгновенном
   роботе дефект «одна деталь → три задания» не воспроизводится (задокументировано в
   `server/__main__.py` docstring, уже прочитано при планировании) — тест ОБЯЗАН
   держать `job_ms` близким к реалистичному (или явно варьировать его как параметр,
   чтобы показать, что при БЫСТРОМ роботе инвариант тривиально держится, а измерение
   ценно именно при МЕДЛЕННОМ).

**Acceptance criteria:**
- [ ] `cmd_get_journal_counters({})` возвращает словарь с ключами `jobs`, `dups`,
      `done`, `reads`, все — неотрицательные целые.
- [ ] Прогон с N=20 РАЗЛИЧНЫМИ объектами (интервал спавна БОЛЬШЕ, чем время
      прохождения одного объекта через кадр — т.е. объекты не перекрываются в
      кадре) и `job_ms` не менее 1000мс — по завершении `dups == 0`.
- [ ] Прогон с ТЕМ ЖЕ объектом, инференс на КОТОРЫЙ вызывается искусственно 3 раза
      подряд (симулируется намеренно сломанный тракт — прямой вызов
      `enqueue_job`/`send_test_job` трижды с координатами, отличающимися ровно на
      величину сдвига ленты за интервал между вызовами, ± `dup_radius_mm`) — даёт
      `dups >= 2` (детектор РЕАЛЬНО обнаруживает дубли, когда они есть — не просто
      всегда возвращает 0). Это break-injection-проверка САМОГО измерения, не
      только его отсутствия.
- [ ] `pytest Services/robot_comm -q` — 0 failed (не регрессирует существующие 40+
      тестов ядра).

**Out of scope:** confusion-matrix (caught/missed/false_alarm) — это Task 5.2/5.3,
другая половина «правды».
**Edge cases:** объекты спавнятся БЫСТРЕЕ, чем робот успевает разобрать очередь —
это ОЖИДАЕМЫЙ сценарий, в котором дубли МОГУТ появиться на реальном железе тоже (это
не баг теста, это то, что владелец просил измерять) — не путать с багом дедупа.
**Dependencies:** Task 1.2, Task 3.3 (для реалистичного прогона).
**Module contract:** impl-only.

### Task 5.2 — Паспорт объекта едет по цепочке, evaluator сверяет с вердиктом

**Level:** Senior+ (Opus, extended thinking)
**Assignee:** teamlead
**Goal:** `item["sim_truth"]` (Task 3.4) доезжает от `line_sim_camera` через
`vision`/`line`/`recog` до узла, где уже есть вердикт `ml_inference` (`predictions`),
и новый evaluator-узел сравнивает класс/угол предсказания с истиной, публикуя счётчики
через `state_proxy`.

**Контекст:** Это архитектурное решение с реальной неопределённостью — см. Decisions
log в `plan.md`: подтверждено ТОЧЕЧНО (`pixel_to_robot`, `ml_inference` строят
`{**item, ...}`, чужие ключи переживают), но не для ВСЕХ узлов цепочки. Step 1 ниже —
обязательная проверка перед выбором механизма; если проверка провалится — переключиться
на запасной план (join-режим), а не пытаться протолкнуть sidecar через
непрокидывающий узел патчами.

**Files:**
- Разведка (без изменений кода): `Plugins/processing/color_convert/plugin.py`,
  `Plugins/processing/roi_crop/plugin.py`, `Plugins/processing/hsv_mask/plugin.py`,
  `Plugins/processing/morphology/plugin.py`,
  `Plugins/processing/circle_detector/plugin.py`,
  `Plugins/filter/line_filter/plugin.py`,
  `Plugins/processing/center_crop/plugin.py`
- НОВЫЙ `Plugins/processing/sim_truth_eval/plugin.py` — `SimTruthEvalPlugin`
- НОВЫЙ `Plugins/processing/sim_truth_eval/__init__.py`
- `multiprocess_prototype/recipes/hikvision_letter_robot.yaml` — если выбран
  join-режим (запасной план): добавить процесс `sim_eval` + wires (`recog.
  ml_inference.predictions` → `sim_eval...predictions`, `<camera>.line_sim_camera.
  sim_truth` → `sim_eval...sim_truth`, `mode: join` по образцу `recog`/`draw`)

**Steps:**
1. **Обязательная проверка (делать ПЕРВЫМ, до выбора архитектуры):** прочитать
   `process()`/`process(items)` каждого узла из списка выше; для каждого
   зафиксировать вывод: «прокидывает неизвестные ключи item (да/нет)», с цитатой
   строки, которая это доказывает (`return {**item, ...}` = да; `return {"frame":
   ..., "detections": ...}` без spread = нет). Записать таблицу в PR-описание/
   docstring нового плагина — это тот самый вердикт, который снимает риск,
   зафиксированный в Decisions log `plan.md`.
2. **Если ВСЕ узлы прокидывают (ожидаемый исход по уже проверенным 2/7):**
   `SimTruthEvalPlugin` подключается к ТОМУ ЖЕ выходу, что и `ml_inference`
   (следующий узел цепочки после `recog`), читает `item["sim_truth"]` и
   `item["predictions"]` из ОДНОГО item — сравнение per-item, без join-механики.
3. **Если ХОТЯ БЫ ОДИН узел не прокидывает:** использовать `mode: join` (уже рабочий
   паттерн — `recog`/`draw` в текущем рецепте) — `sim_truth` идёт ОТДЕЛЬНЫМ wire
   напрямую от `line_sim_camera` к новому `sim_eval` узлу, минуя непрокидывающие
   промежуточные узлы; `predictions` — вторым input тем же join.
4. Матчинг per-frame: паспорт из `sim_truth`, ближайший к позиции сработавшего
   триггера (`center_px`/аналог), считается «объектом этого вердикта». При JOIN-
   режиме (нет общего item) — матчинг по времени/энкодеру: `sim_truth` несёт
   `spawn_encoder` и текущую позицию на момент кадра, `predictions` несёт
   `e_capture` (уже в item по цепочке `pixel_to_robot`) — тот же класс вычисления,
   что `SimJournal._residual_mm`, но здесь сравнивает «предсказание vs истина», а не
   «job vs job» — САМОСТОЯТЕЛЬНАЯ реализация (не импортировать `SimJournal` напрямую
   — разные данные, разная цель), но тот же математический инвариант
   (`FACTOR_MM`/`BELT_UX`/`BELT_UY`), задокументировать это родство в docstring.
5. `SimTruthEvalPlugin` копит счётчики `caught` (класс совпал, дефекта не было),
   `missed` (дефект был, но не задетектирован/неверный класс), `false_alarm`
   (дефекта не было, но инспектор дал брак/низкая confidence) — публикует через
   `ctx.state_proxy.set("sim_eval.counters", {...})` на каждое сравнение.

**Acceptance criteria:**
- [ ] Разведка Step 1 задокументирована (таблица узел→прокидывает да/нет) —
      проверяется по наличию в PR/docstring, независимый reviewer сверяет с кодом.
- [ ] `sim_truth`, прикреплённый к объекту с `defect=None`, при предсказании
      `ml_inference` с совпадающим классом — увеличивает `caught` на 1, не трогает
      `missed`/`false_alarm`.
- [ ] `sim_truth` с `defect="damaged"` (объект РЕАЛЬНО бракованный) при
      предсказании, НЕ отметившем брак (или неверный класс/низкая confidence по
      порогу) — увеличивает `missed` на 1.
- [ ] `sim_truth` с `defect=None` (объект РЕАЛЬНО годный), но предсказание с низкой
      confidence/пометкой брака — увеличивает `false_alarm` на 1.
- [ ] Прогон с ИЗВЕСТНЫМ числом годных/бракованных объектов (например 15 годных +
      5 брак, `defect_probability` фиксирована для теста) даёт
      `caught+missed+false_alarm+<не сработавшие def=0, но верно проигнорированные>`
      согласованное с числом объектов, реально попавших в кадр (не больше, не
      меньше — граница сходится, независимый tester пишет это как арифметическую
      проверку).

**Out of scope:** отображение счётчиков в GUI (Ф6.2); учёт нескольких предсказаний
на один объект (это ПОКРЫВАЕТСЯ Task 5.1's dup-инвариантом на другом конце петли —
здесь предполагается, что дублей нет, по построению Ф5.1).
**Edge cases:** объект покинул кадр БЕЗ единого сработавшего триггера (например
`line_filter` не среагировал) — считается `missed` (пропущенный ПОЛНОСТЬЮ, не только
неверно классифицированный) — задокументировать это явно как отдельную причину
`missed`, отличимую в логах/счётчиках от «задетектирован, но неверно».
**Dependencies:** Task 3.4 (источник `sim_truth`).
**Module contract:** new-lite (новый однофайловый плагин `SimTruthEvalPlugin`).

### Task 5.3 — Счётчики наружу + сквозной прогон обоих инвариантов

**Level:** Middle+ (Sonnet, extended thinking)
**Assignee:** developer
**Goal:** счётчики из Task 5.1 (`SimJournal`) и Task 5.2 (`SimTruthEvalPlugin`)
читаемы ОДНИМ способом (для пульта Ф6.2 и для тестов) и есть ОДИН сквозной
интеграционный прогон, подтверждающий v1 целиком: N объектов проезжают ленту, робот
получает по одному job на объект (Ф5.1), а вердикты инспектора сравнены с правдой
(Ф5.2) — оба измерения в одном прогоне, не в изоляции.

**Files:**
- `Services/line_sim/tests/test_v1_end_to_end_invariants.py` (или в
  `multiprocess_prototype/tests/` — выбрать по месту, где уже есть похожие e2e-тесты
  на весь рецепт, если такие существуют — проверить перед созданием нового каталога)
- Мелкая доводка API из 5.1/5.2 для единообразного чтения (например единый префикс
  state-путей `line_sim.journal.*` / `line_sim.eval.*`) — правки НЕ архитектурные

**Steps:**
1. Свести оба измерения в один прогон: топология Ф1 полностью (robot + line_cam +
   боевой vision/line/recog/layout), N=20+ объектов с фиксированной пропорцией
   брака, `job_ms` реалистичный (см. Ф5.1 Step 4).
2. Собрать итоговый отчёт прогона: `{jobs_sent, dups, caught, missed, false_alarm}`
   — assert на согласованность (например `jobs_sent - dups` не должно катастрофически
   расходиться с `caught + missed + false_alarm`, с разумным допуском на объекты,
   не успевшие завершить цикл к концу прогона).

**Acceptance criteria:**
- [ ] Прогон 20 объектов (пропорция брака ~20%), `job_ms>=1000`,
      завершается за разумное время (задать явный timeout, например 120с);
      по завершении: `dups == 0` (или ниже явно задокументированного порога, если
      0 недостижим по не зависящим от line_sim причинам — задокументировать
      причину, не молчать про несовпадение с ожиданием per STRICT-канон).
- [ ] `caught + missed + false_alarm >= 0.8 * <число объектов, реально пересекших
      триггер-линию за время прогона>` (не 100% — часть объектов у самого конца
      прогона может не успеть завершить цикл, это ожидаемо и не дефект; порог 0.8 —
      отправная точка, Developer вправе уточнить по факту первого прогона, указав
      измеренное число в PR).
- [ ] Оба счётчика (`SimJournal`, `SimTruthEvalPlugin`) читаются ОДНИМ и тем же
      механизмом снаружи процессов (единообразие подтверждается тем, что тест не
      использует два РАЗНЫХ способа чтения — например один через command, другой
      напрямую импортируя внутренний объект процесса).

**Out of scope:** GUI-отображение (Ф6.2 использует ЭТИ counters, но их визуализация
— другая задача).
**Dependencies:** Task 5.1, Task 5.2.
**Module contract:** impl-only.

# Phase 2 — Общая правда о ленте (один энкодер)

Часть плана [`plan.md`](plan.md). Реализует владельческое решение: «робот — отдельным
процессом; общая с линией — только правда о ленте (один энкодер) через канал».
Канал — `StateProxy` (`multiprocess_framework/modules/state_store_module`), НЕ второе
Modbus-соединение line→robot (см. Decisions log в `plan.md`).

---

### Task 2.1 — ПЧ-команда → живая скорость энкодера в `RobotSimCore`

**Level:** Middle (Sonnet)
**Assignee:** developer
**Goal:** живая команда `vfd_run`/`vfd_set_freq` (та же, что инспектор шлёт на
железо через bridge `vfd_belt→robot_main`) меняет ФАКТИЧЕСКУЮ скорость приращения
энкодера в `RobotSimCore`, а не только зеркало телеметрии ПЧ.

**Контекст:** `RobotSimCore._handle_vfd` уже эмулирует зеркало ПЧ (0x1200 команда /
0x1210 статус), но `_enc_rate` — константа, заданная один раз в `__init__` и никогда не
меняется по ходу работы. Из-за этого «инспектор может притормозить конвейер» сейчас
физически невозможно в sim — заявленное в vision.md поведение, которое эта задача
реализует буквально. Расчёт мм/с из частоты — приблизительный (владелец одобрил
«точность мира — примерная, достаточно»): физическая константа реального стенда
(мм ленты на Гц ПЧ) в коде не найдена, вводится новый конфигурируемый параметр.

**Files:**
- `Services/robot_comm/server/sim_core.py` — `RobotSimCore.__init__` (новый параметр),
  `_handle_vfd`
- `Services/robot_comm/tests/test_sim_e2e.py` (или новый `test_sim_core_vfd_speed.py`
  рядом) — тесты автора на этот механизм (hazard: гонка/порядок применения на тике)

**Steps:**
1. Прочитать `Services/vfd_comm` (register map/scale для frequency-регистра ПЧ), чтобы
   узнать, в каких единицах приходит `self.regs[_REG_VFD_CMD_FREQ]` в
   `_handle_vfd` (сырые Гц, Гц×10, и т.п.) — команда `vfd_run`/`vfd_set_freq` от
   `VfdDriver._op_run`/`_op_set_freq` передаёт `freq_hz` до scale транспорта;
   зафиксировать найденный масштаб в docstring.
2. Добавить `RobotSimCore.__init__` параметр `belt_mm_s_at_max_freq: float = 100.0`
   (дефолт = текущий `DEFAULT_BELT_MM_S` из `server/__main__.py`) и
   `freq_max_hz: float = 50.0` (дефолт = `freq_max_hz` из `vfd_belt.params` в
   рецепте) — оба НЕ хардкодить внутрь, оставить настраиваемыми (как остальные
   тайминги ядра).
3. В `_handle_vfd`, при `run == True` и валидной `freq`: вычислить
   `belt_mm_s = (freq_hz / freq_max_hz) * belt_mm_s_at_max_freq`, затем
   `self._enc_rate = max(1, round(belt_mm_s * TICK_INTERVAL_S / FACTOR_MM))`
   (та же формула, что уже использует `server/__main__.py._ms_to_ticks`-соседняя
   `enc_rate`-формула — переиспользовать константу `FACTOR_MM` из `core/registers.py`,
   не дублировать число). При `run == False` — `self._enc_rate = 0` (лента стоит;
   `tick()` продолжает вызываться, просто прирост энкодера — 0, что уже поддержано
   существующей веткой `self._encoder += self._enc_rate`).
4. Учесть, что зеркало обновляется ТОЛЬКО по `VFD_FLAG` (существующее ограничение,
   намеренно воспроизводящее Lua) — значит `_enc_rate` тоже меняется ТОЛЬКО в момент
   пульса команды, не непрерывно. Это ожидаемо и соответствует «инспектор
   притормаживает» как дискретному действию (нажал — послал команду — сработало), а
   не непрерывному ПИД-регулированию — задокументировать это ограничение в docstring
   `_handle_vfd`, не заявлять «плавно» нигде в коде/докстрингах.
5. Автор пишет hazard-тест: `_handle_vfd` выполняется на ticker-потоке, значит гонки с
   другим потоком, пишущим `_enc_rate` напрямую, — НЕТ (единственный писатель — сам
   `tick()`); тест на это — assert, что `_enc_rate` меняется СИНХРОННО в рамках одного
   `tick()`, вызванного напрямую (без реального потока), не через `time.sleep`-гонки.

**Acceptance criteria:**
- [ ] `core = RobotSimCore(enc_rate=999, belt_mm_s_at_max_freq=100.0,
      freq_max_hz=50.0)`; после записи в регистры команды ПЧ (run=1, freq=25 [ед. по
      найденному в Step 1 масштабу], vfd_flag=1) и одного `core.tick()` — `core.
      encoder` вырос ровно на `round(50.0 * TICK_INTERVAL_S / FACTOR_MM)` (половинная
      частота от максимума → половинная скорость от `belt_mm_s_at_max_freq`), а НЕ на
      999 (старое поведение — конструкторный `enc_rate` больше не используется после
      первой команды ПЧ).
- [ ] Команда ПЧ с `run=0` (стоп) → следующий `tick()` даёт прирост энкодера `0`.
- [ ] Без единой команды ПЧ (флаг `vfd_flag` никогда не взводился) — `core.encoder`
      растёт с конструкторным `enc_rate` (обратная совместимость: существующие тесты
      `test_sim_e2e.py`, не трогающие ПЧ, остаются зелёными без изменений).
- [ ] `pytest Services/robot_comm -q` — 0 failed.

**Out of scope:** плавное (непрерывное) изменение скорости между пульсами команды;
публикация энкодера наружу процесса (Task 2.2).
**Edge cases:** `freq_max_hz == 0` (деление на ноль) — защититься (например
`enc_rate = 0` вместо исключения, залогировать предупреждение); отрицательная/
некорректная `freq` — clamp к `[0, freq_max_hz]`.
**Dependencies:** нет (не зависит от Ф1, но Ф2.2 зависит от неё).
**Module contract:** impl-only.

### Task 2.2 — Канал энкодера робот→line через `StateProxy`

**Level:** Middle+ (Sonnet, extended thinking)
**Assignee:** developer
**Goal:** робот-процесс (Task 1.2) публикует текущее значение энкодера в
`state_store` на throttled-интервале; line-процесс (Task 1.1) подписывается и
позиционирует ОДИН тестовый объект на сцене синхронно с этим значением — видимое
доказательство «энкодер один, через канал».

**Контекст:** `REG_ENC` — единственный источник истины (живёт в регистровом
пространстве робота). Публикация через `StateProxy.set(path, value)` /
`subscribe(pattern, callback)` — тот же механизм, что уже использует
`ModbusPlugin._push_state`. Никакого второго Modbus-клиента со стороны line не
заводится (см. Decisions log).

**Files:**
- `Plugins/sim/robot_sim_process/plugin.py` (из 1.2) — добавить throttled-паблишер
- `Plugins/sources/line_sim_camera/plugin.py` (из 1.1) — добавить подписку/чтение +
  простейшее позиционирование одного тестового спрайта (заглушка до Ф3 — реального
  движка слоёв ещё нет)
- `multiprocess_prototype/recipes/hikvision_letter_robot.yaml` — секция `sim:` —
  задокументировать путь канала (например `sim.belt.state_path: "line_sim.belt"`)

**Steps:**
1. В `RobotSimProcessPlugin`: завести periodic-паблишер (worker/таймер — по образцу
   `ModbusPlugin._poll_loop`, но БЕЗ Modbus — просто читает `self._core.encoder`
   каждые N мс, N по умолчанию 50мс, конфигурируемо) →
   `ctx.state_proxy.set(f"{state_path}.encoder", {"value": core.encoder, "t":
   time.monotonic()})`. Не публиковать чаще, чем нужно для плавности на 25 fps камеры
   (50мс — с запасом).
2. В `LineSimCameraPlugin`: подписаться через `ctx.state_proxy.subscribe(f"
   {state_path}.encoder.*", callback, sync=False)` (async-режим — не блокировать поток
   продюсера кадров) ИЛИ читать через `ctx.state_proxy.get(path, default=...)`
   каждый `produce()` (проще, без колбэков; выбрать вариант с меньшей связностью,
   задокументировать выбор). Хранить последнее известное значение энкодера как
   `self._last_encoder` с дефолтом `0`, если канал ещё пуст (процесс `robot` мог
   стартовать позже line-процесса — не падать, деградировать до неподвижной сцены).
3. Позиционировать ОДИН фиксированный тестовый спрайт (простая цветная фигура —
   реальные спрайты придут в Ф3) вдоль горизонтальной оси кадра:
   `x = (encoder - spawn_encoder) * FACTOR_MM * <px_per_mm>` (константа
   масштабирования сцены — новый конфиг `sim.camera.px_per_mm`, дефолт подобрать так,
   чтобы объект помещался в кадр за разумное время). Использовать `FACTOR_MM` из
   `Services.robot_comm.core.registers` (импорт, не копия числа).
4. Автор пишет hazard-тест: канал ещё не опубликован (гонка старта процессов) — `get`
   с `default` не бросает, camera-плагин не падает.

**Acceptance criteria:**
- [ ] С `sim.enabled: true`, после старта системы `ctx.state_proxy.get("<state_path>.
      encoder")` (или эквивалент через `mcp__backend-ctl__state_get`) в GUI/tester-
      процессе возвращает растущее целое число в течение работы (два снятия с
      интервалом 1с — второе больше первого).
- [ ] Отправка ПЧ-команды на остановку ленты (`DeviceManager.call("vfd_belt", "stop",
      {})`) останавливает рост опубликованного `encoder` (два снятия подряд после
      команды — равны, с точностью до последнего опубликованного тика).
- [ ] Отправка ПЧ-команды на запуск (`run`, `freq_hz>0`) возобновляет рост.
- [ ] Тестовый спрайт в кадрах `line_sim_camera` (проверяется по нескольким
      последовательным `produce()`-вызовам в тесте или по позициям в реальных кадрах
      дисплея) смещается по X монотонно, пока энкодер растёт, и НЕ смещается, когда
      энкодер не растёт (лента остановлена).
- [ ] Если процесс `robot` ещё не опубликовал ни одного значения (например тест
      запускает только line-процесс изолированно) — `produce()` не бросает исключение,
      возвращает кадр с объектом в дефолтной позиции.

**Out of scope:** несколько объектов, спавн/деспавн (Ф3); реальные спрайты (Ф3);
экспозиция счётчиков `SimJournal` (это Ф5.1, другой канал/другая цель).
**Edge cases:** переполнение/сброс энкодера (32-бит signed, per `RegDW(signed=True)`)
— смещение по X должно корректно обработать переход через границу диапазона (или явно
задокументировать, что v1 не рассчитан на прогоны длиннее переполнения — уточнить
числом: `2**31 / enc_rate_typical` тиков при типичной скорости, на порядок больше
разумной длительности демо-прогона).
**Dependencies:** Task 1.2 (паблишер), Task 2.1 (чтобы скорость реагировала на
команды — иначе канал технически работает, но демонстрировать «одна лента, одна
правда» через изменение скорости нечем).
**Module contract:** impl-only.

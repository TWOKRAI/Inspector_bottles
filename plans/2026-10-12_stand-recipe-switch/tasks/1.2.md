# Task 1.2: Смена — фоновая работа PM: исполнитель, job_id, флаг debounce → машина состояний

- **Статус:** [PENDING] (после 4.1) · **Level:** Senior+ · **Assignee:** teamlead (конкурентность, IPC)
- **Goal:** транзакция смены (`apply_topology`) идёт на внутреннем исполнителе PM, не на `ProcessManager_message_processor`.
  Команда отвечает сразу `{success: true, accepted: true, job_id}`; фаза и итог — в ключах `state_store` по контракту 4.1.
  PM отвечает на прочие команды во время смены (R-8). Флаг `_replace_in_progress` без лока (срез B §6) становится
  машиной состояний с атомарным переходом — вне одного потока флаг даёт гонку.
- **Files:**
  1. `multiprocess_framework/modules/process_manager_module/process/switch_job.py` — НОВЫЙ: один поток-исполнитель,
     очередь из одной работы, машина `idle → running → idle`, публикация фаз через переданный `publish(path, value)`
  2. `multiprocess_framework/modules/process_manager_module/process/process_manager_process.py` — `_cmd_topology_apply`
     (:751-796) отдаёт работу исполнителю; `_topology_debounce_reject` (:798-824) и флаги в `apply_topology`
     (:3861, :3871, :4037-4039) — через машину; остановка исполнителя в пути shutdown PM
  3. `multiprocess_framework/modules/process_manager_module/tests/test_switch_job.py` — НОВЫЙ (RED от tester)
  4. `multiprocess_framework/modules/process_manager_module/tests/test_switch_job_hazards.py` — НОВЫЙ (автор)
  5. `multiprocess_framework/modules/process_manager_module/DECISIONS.md` — ADR: смена вне потока сообщений
  6. `backend_ctl/tests/test_switch_honest_state_live.py` — ждать итог по `job_id` из состояния, не из ответа
- **Запрещено:** `process/topology_manager.py` (полоса Ж); тело транзакции `apply_topology` (:3878-4035) — переносится
  на другой поток без изменения шагов; `backend/assembly/planner.py`.
- **Steps:**
  1. Перечислить команды PM, которые меняют дерево процессов (`process.start/stop/restart`, `topology.apply`, …) —
     по реестру `_register_builtin_commands`. Во время `running` они отвечают `{success: false, error: "busy", job_id}`.
     Читающие (`get_status`, `system.stats`, `supervision_status`) работают. Перечень — в ADR.
  2. Исполнитель: один поток с именем `ProcessManager_switch_job`; переход `idle → running` под локом, проверка и
     установка — один атомарный шаг. Cooldown `replace_debounce_s` (:815) сохраняется как правило машины (по 4.1 Q3).
  3. Работа зовёт существующий `self.apply_topology(td)` (через override прототипа `orchestrator.py:50-52`) и
     публикует фазы `system.switch.job` по 4.1. Исключение в работе → фаза `failed`, машина возвращается в `idle`.
  4. Ответ команды не ждёт работы. Поздний ответ и отложенный `reply_to_request` не делаются.
  5. Shutdown PM во время `running`: исполнитель доделывает текущий шаг или отменяется по бюджету стопа; поток
     закрыт до возврата `shutdown`. Если полоса Ж влила `BaseManager.scope` — поток регистрируется в области.
  6. Автор пишет hazard-тесты (гонки, повторный вход, порядок, shutdown посреди работы).
- **Acceptance criteria:**
  - [ ] Подменённый шаг стопа спит 3 с: ответ `topology.apply` < 0.5 с, `accepted: true`, `job_id` — непустая строка.
  - [ ] Во время этой работы `system.stats` отвечает < 0.5 с (5 запросов подряд).
  - [ ] Второй `topology.apply` во время работы → `error: "busy"` с `job_id` первой; тело apply исполнено ровно 1 раз.
  - [ ] 50 потоков одновременно шлют apply в `idle`: принят ровно 1, остальные 49 — `busy`.
  - [ ] `process.restart` во время работы → `busy`; `get_status` → ответ.
  - [ ] Последовательность фаз в `system.switch.job.phase` для успешной смены — ровно список из 4.1 (литерал).
  - [ ] Исключение внутри работы → фаза `failed`, текст ошибки в `result.error`; следующий apply принят.
  - [ ] Shutdown PM посреди работы возвращается за бюджет стопа + 2 с; поток `ProcessManager_switch_job` не жив.
  - [ ] Один тест собирает настоящий PM (harness), не подделку: apply → итог в состоянии.
  - [ ] Каждый тест, который может зависнуть, — вызов в daemon-потоке с дедлайном join.
- **Out of scope:** `recipe.activate` (4.2), фаза устройств (5.1), барьер готовности (8.1), консольный сток (план
  наблюдаемости), отмена работы по таймауту клиента.
- **Handoff:** tester(RED по контракту 4.1) -> teamlead(GREEN + hazard) -> reviewer(concurrency, IPC)
- **Module contract:** new-lite (`switch_job.py`) + impl-only (`process_manager_process.py`)
- **Traps:** побочный эффект на success-пути в своём `try` — иначе он откатит успешную смену
  (`feedback_side_effect_must_not_undo_the_transaction.md`). H1 этим не чинится: поток работы, вставший в записи в
  замёрзшую консоль, тоже не закончит смену. Ключи `processes.<name>.*` режет гейт топологии (`project_state_topology_gate.md`).

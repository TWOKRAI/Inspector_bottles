## Цели

1. Датасетом владеет бэкенд. Картинки, разметка, классы, статусы и снимки экспорта лежат у него. GUI диск бэкенда не
   читает: данные идут командами, картинки — каналом «файлы по id».
2. Всё, что умеет GUI, умеет и `backend_ctl send_command` по тем же адресам: разработчик или агент может заскриптовать
   импорт, разметку и экспорт.
3. Удобная разметка: браузер снимков с фильтрами, холст с рамками, классы на горячих клавишах, копия рамок с
   предыдущего, undo/redo, сохранение с ревизией (два клиента не затирают друг друга молча).
4. Сбор с линии: «В датасет» одним кликом с живой камеры; автоматический сбор кадров-отбраковок; импорт папки.
5. Экспорт для облака: YOLO detect (`data.yaml` + images/labels) и классификация (папки по классам), zip, детерминированный
   сплит, снимок-манифест.

## Out of scope

- Обучение и его перенос на бэкенд (решение о `ml_train` — открытый вопрос 2). Загрузка в конкретное облако.
- Полигоны/сегментация (отложено), SAM и подобные ассистенты (не планируется), ключевые точки.
- Разметка с другой машины по сети — только после gui-service Ф2 (см. «Зависимости»).
- Загрузка файлов с машины клиента на бэкенд (upload) — вместе с удалённой разметкой.
- Поиск почти-дубликатов (перцептивный хеш) — дубликаты ловятся только побайтно.
- COCO-экспорт — добавить, когда облачный сервис владельца его потребует (YOLO читают Ultralytics HUB, Roboflow,
  CVAT, Label Studio — **по общим знаниям, в этой сессии не проверено**).
- Правка `dataset_gen_section.py` / `disk_cutter_section.py` (они тоже читают локальный диск — отдельная строка в
  «Открытых вопросах», не здесь).

## Решения (decisions log)

### Хранение и владение

- **2026-09-26 (планирование): новый сервис `Services/dataset`, не расширение `dataset_gen`.** `dataset_gen` —
  генератор синтетики с задачей «класс + угол» и без боксов; у датасета другой жизненный цикл (данные копятся годами,
  правятся людьми, имеют ревизии). **Rejected:** (1) расширить `dataset_gen` — смешает генератор и хранилище; (2)
  расширить `Services/sql` — это инфраструктура, не предметный срез; (3) положить во фреймворк — предметное слово
  «датасет» и один потребитель (правило двух потребителей, `constructor-layers.md:36`).
- **2026-09-26 (планирование): источник правды — SQLite-индекс + картинки по хешу содержимого; YOLO-раскладка — продукт
  экспорта.** Уточняет направление лида («YOLO на диске как источник правды + индекс»). Причины: в YOLO сплит зашит в
  путь (`images/train/…`), пересплит = перенос файлов; некуда положить ревизию, статус («не размечено» vs «размечено,
  объектов нет» — для YOLO это разные вещи, а файл один и тот же), класс всего снимка, источник, «проверено»;
  переименование класса = переписать все `.txt`; транзакций нет. SQLite через `Services/sql` — по вердикту
  стека хранения, ноль новых зависимостей. **Rejected:** (1) YOLO как правда — причины выше; (2) JSON-файл рядом с
  каждой картинкой без БД — фильтр «не размечено» на 10 тыс. снимков = обход всех файлов, нет атомарного
  compare-and-swap; (3) Label Studio/CVAT как хранилище — внешний сервер как владелец данных линии.
- **2026-09-26 (планирование, поправлено по ревью CTO): хозяин команд — процесс `dataset` в подключаемом фрагменте
  `backend/topology/dataset.yaml`** + строка в списке `base:` манифеста `app.yaml` (механизм `observability_sink.yaml:1-20`,
  `app.yaml:25-35`), плагин `Services/dataset/plugin`. Команды доступны при любом активном рецепте (фрагмент — уровень
  приложения). **Rejected:** (0) процесс в `base.yaml` — решение репозитория с замером (`base.yaml:31-36`: «вписанный
  сюда процесс платят ВСЕ сборки», 2026-08-23 golden-снимки +375 строк каждый, `hello_world` удвоен); (1) на хабе, как
  `recipe.*` — импорт тысяч снимков и генерация миниатюр в процессе-маршрутизаторе останавливают маршрутизацию;
  `recipe.*` там уместен, потому что лёгок; (2) через `service_module` — сервисы исполняются в процессе хаба
  (`service_module/host.py:1-30`), тот же довод. Цена: +1 процесс только у приложений, подключивших фрагмент;
  golden-снимки `base.yaml` не меняются.
- **2026-09-26 (планирование): имена команд — `dataset_<глагол>`** (конвенция плагинных команд, `device_list` у
  `device_hub`), адрес `process=dataset, command=dataset_list`. «`dataset.*`» в тексте — имя семейства. Точечные имена
  (`recipe.list`) — у обработчиков хаба, это другой механизм.
### Транспорт картинок и захват

- **2026-09-26 (планирование): картинки — отдельный HTTP-канал «файлы по id», не команды и не дерево состояния.**
  Ответ команды из процесса `dataset` идёт через pipe процесса → хаб → сокет: картинка 1–3 МБ повторила бы дефект L-6
  (`transport-single-policy` Ф4), а README сокета запрещает крупные грузы в канале управления (тот же довод, что у
  кадров в gui-service). Сервер — stdlib `ThreadingHTTPServer` внутри процесса `dataset` (прецедент `mjpeg_sink`),
  по умолчанию `127.0.0.1`, порт эфемерный, адрес публикуется в состоянии. Клиент — во фреймворке рядом с
  `remote_frame_source.py`, его оборачивает контекст виджета (четвёртый канал, зарезервирован в
  `constructor-layers.md:171`). **Rejected:** (1) base64 в ответе команды — L-6 и блокировка очереди; (2) SHM по имени —
  работает только на одной машине, а канал должен дожить до сети; (3) общий диск на одной машине — ровно то нарушение
  «GUI без диска», которое снимала фаза 1b gui-service.
- **2026-09-26 (планирование): захват кадра — на стороне бэкенда, плагином в пайплайне**, а не из картинки дисплея GUI.
  Дисплей `inspection_full` показывает `renderer.render_overlay.rendered_frame` — кадр с красным оверлеем; учить на нём
  нельзя. Плагин `dataset_capture` держит кольцо последних сырых кадров и пишет выбранный в датасет. **Rejected:**
  снимок из GUI + загрузка — не тот кадр (оверлей) и крупный груз из клиента.
- **2026-09-26 (планирование): писателей датасета два и они названы:** процесс `dataset` (всё) и плагин
  `dataset_capture` (только вставка новых снимков, через ту же библиотеку `DatasetStore`, SQLite в WAL). Разметку
  правит только процесс `dataset`. Ревизионный конфликт с захватом невозможен по построению: захват не трогает
  строки разметки существующих снимков — **утверждение проверяется тестом в Task 3.1**, не принимается на слово.
- **2026-09-26 (планирование): ревизия разметки — на снимок**, compare-and-swap одним `UPDATE … WHERE rev = :base_rev`
  (rowcount 0 → `conflict` с текущей ревизией). Тот же контракт, что `recipe.save` (gui-service 1b.1). **Rejected:**
  блокировка снимка на время редактирования — повисает при падении клиента (тот же довод, что в gui-service).
### GUI, внешние инструменты, сплит

- **2026-09-26 (планирование): виджеты разметки пишутся до контекста виджета, против узкого порта той же формы.**
  Пакет `Services/dataset/gui/` зависит только от `AnnotationPorts` (запрос команды, файлы, подписка на состояние) —
  это подмножество контекста виджета из `plans/gui-constructor/`. До его готовности порты собирает **один** файл-адаптер
  в прототипе (секция в группе «Нейронные сети»), после — `WidgetSpec` пакета, адаптер удаляется задачей 2.5 с
  sunset-тестом. Это не второй путь: виджеты одни, заменяется источник портов. **Rejected:** (1) ждать gui-constructor
  Ф1 — вся видимая ценность плана ждёт чужой план без срока; (2) писать виджеты прямо на `RuntimeDeps` — это 38
  зависимостей (ревью CTO, идея b), выпиливать потом по всему пакету.
- **2026-09-26 (планирование): встраивание в GUI до конструктора — секцией, не вкладкой верхнего уровня.** Новая вкладка
  трогает `frontend/app.py`, а у него очередь одного писателя (gui-service 1b.2b и T4.2–T4.4). Секция добавляется в
  `neural/__init__.py`, `app.py` не меняется.
- **2026-09-26 (планирование): только внешний инструмент — отвергнут, но совместимость с ними обязательна.**
  Внешние инструменты (CVAT, Label Studio, X-AnyLabeling) **в этой сессии не открывались и не проверялись**; всё, что
  ниже про них, — общие знания, требующие проверки перед ссылкой на них в решении владельца: CVAT и Label Studio —
  серверы (Docker / веб), X-AnyLabeling — настольное Qt-приложение; все три читают и пишут YOLO. Почему своё: (1) «В
  датасет» с линии одним кликом и автосбор отбраковок — внешний инструмент линии не видит; (2) датасет — данные бэкенда,
  доступные `backend_ctl`; (3) один стек, без сервера рядом с Orin. Совместимость: импорт YOLO (Task 1.4) и экспорт YOLO
  (Task 4.4) — сложная разметка (полигоны) может уйти во внешний инструмент и вернуться. **Rejected:** встроить Label
  Studio веб-вкладкой — второй владелец данных и серверный стек, отклонённый вердиктом хранения.
- **2026-09-26 (планирование): сплит детерминированный по хешу**, `split = f(sha256(group_key), seed, доли)`; добавление
  новых снимков не перемещает старые между train/val. Ключ группы — сессия захвата, если есть, иначе хеш снимка (соседние
  кадры одного изделия не должны разъезжаться по train и val). Подробности — Task 4.3.

## Риски и ограничения

- **Память кольца захвата на Orin.** Кольцо = `ring_size` × байты кадра: 640×480×3 — 0.9 МБ, 2448×2048×3 — 15 МБ
  (разрешение камеры на линии не сверено). Дефолт `ring_size` 8, фактический объём — в состоянии; литерал в Task 3.1.
- **Какой кадр «тот».** Клик по дисплею отстаёт от сырого кадра на задержку пайплайна. Если сообщение дисплея несёт
  `seq`/`frame_id`, захват идёт по нему; если нет — «последний сырой». Несёт ли — **не проверено** (греп по
  `multiprocess_prototype/frontend` на `frame_id|seq_id` в коде дисплея → 0 совпадений), разведка Task 3.1.
- **Где встречаются сырой кадр и вердикт.** В `inspection_full` вердикт рождается у `inspector`, кадр — у камеры;
  несёт ли элемент `inspector` исходный кадр — не проверено. Если нет — Join по `seq_id` с известным риском таймаута
  (`dataset-circle-capture.md`, P1). Разведка Task 3.1 до кода.
- **Утечка между train и val** соседними кадрами одного изделия — снимается ключом группы (Task 4.3), но только если
  захват пишет сессию; импорт папки сессии не знает.
- **Два писателя SQLite** (процесс `dataset` и плагин захвата) — WAL + `busy_timeout`; число «сколько ждал писатель»
  снимается на стенде 3.1, не предполагается.
- **Hot-reload:** пакеты `Services/*/gui` кнопкой «Перезапустить интерфейс» не перезагружаются (ревью CTO, находка 10,
  `frontend/process.py:392`) — принято как известное ограничение до решения в gui-constructor.
- **Горячие клавиши 1–9** могут конфликтовать с глобальными сочетаниями окна — Task 2.4 проверяет, не предполагает.
- **Тестовый канон (STRICT):** tester на каждой задаче до кода, в worktree; инъекции по каждому заявленному свойству;
  reviewer синхронно. На 1.3 (HTTP, пути, bind) — reviewer в режиме security обязателен.

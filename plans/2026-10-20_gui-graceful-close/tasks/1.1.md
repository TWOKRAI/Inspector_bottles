DESIGN (decided by the lead — you type it, you do not derive it). Якоря — по `main` `c07fb7cb7`, пересчитать перед правкой:
  1. `CloseCoordinator(QObject)` в новом `frontend/shutdown/close_coordinator.py` (+ `__init__.py`); Qt-родитель — окно.
     Состояния `RUNNING → CONFIRMING → STOPPING → CLOSING`, свойство `state`. Все эффекты — внедряемые вызовы (иначе
     слепой тест не написать):
     `CloseCoordinator(window, *, confirm_discard: Callable[[], bool], send_shutdown: Callable[[], dict],
     poll_status: Callable[[float], dict], ignore_names: frozenset[str], ask_force_stop: Callable[[], bool], force_stop: Callable[[], None],
     quit_app: Callable[[], None], on_shutdown_sent: Callable[[], None], unattended: bool = False,
     clock: Callable[[], float] = time.monotonic, poll_interval_ms: int = 250, no_answer_s: float = 2.0)`.
     `ignore_names` — имена, которые не ждём: собственное имя `gui` И имя ProcessManager (PM отдаёт в `supervision.status`
     запись о себе с `alive: True` — `process_manager_process.py:875-881`; без исключения окно ждало бы выхода PM = H2 снова).
     Методы: `request_close()` (крестик), `request_restart()` (рестарт UI), `backend_gone()` (`should_stop` при
     `RUNNING`/`CONFIRMING`), `commit_close()` (`→ CLOSING`, затем `quit_app()`). Отправка `system.shutdown` — один раз;
     после неё `on_shutdown_sent()` ставит `GuiProcess.shutdown_sent = True` (простой булев атрибут процесса: его читает
     `GuiProcess.run` после возврата `run_gui`, когда Qt-объектов уже может не быть).
  2. `request_close()`: состояние не `RUNNING` → ничего (второй крестик в `CONFIRMING`/`STOPPING`/`CLOSING` = `ignore()`
     без повторной отправки; принудительный режим — Task 2.1). Иначе `CONFIRMING`: `confirm_discard()`
     (= `window.confirm_discard_topology_changes`); «Отмена» → `RUNNING`, ничего не отправлено. Иначе `send_shutdown()`
     (= `process_manager_proxy.shutdown_system()`, :112), `on_shutdown_sent()`, `STOPPING`, показать прогресс. Исключения: сбой `confirm_discard` → ERROR в лог, `RUNNING`;
     сбой `send_shutdown` (`process_manager_proxy.py:149-152` не перехватывает) → ERROR в лог, `commit_close()` БЕЗ
     `on_shutdown_sent` (сработает прежний путь `_request_system_shutdown`) — иначе состояние навсегда `CONFIRMING`.
  3. Прогресс: `QProgressDialog`, окно-модальный, показывается через `show()` (не `exec()`), без кнопки отмены
     (`setCancelButton(None)`), `setMinimumDuration(0)`, `setAutoClose(False)`, `setAutoReset(False)`, Esc/`reject`
     игнорируются. Заголовок «Остановка системы… k из N».
  4. Опрос: `QTimer` 250 мс → координатор сам отдаёт `poll_status(1.0)` в `RequestRunner.submit`; результат приходит сигналом в
     главный поток (тест ждёт `qtbot.waitUntil`). Реальный `poll_status` = `command_sender.request_system_command(…,
     timeout=1.0)` (параметр есть, `command_sender.py:253-257`; по умолчанию 30 с). Литерал ответа handler'а: плоский
     `{"success": True, "epoch": …, "processes": {имя: {"alive": bool|None, "pid": …, …}}}`; не-dict `RequestRunner` оборачивает
     в `{"success": True, "result": …}` (`request_runner.py:40-48`) — teamlead первым шагом сверяет форму живым вызовом
     `supervision.status` через `command_sender` и при расхождении задаёт вопрос лиду. Тестовые фейки отдают плоскую форму. В полёте не более одного запроса. Ответом считается только результат с
     `success is True`; `{"success": False, "error": "timeout"}` — не ответ. «Все процессы остановлены»: у всех детей,
     кроме имён из `ignore_names`, `alive is False` → `commit_close()` (`alive: None` — «неизвестно», не «мёртв»).
  5. Нет ни одного ответа за `no_answer_s` (2,0 с, `clock` — monotonic, отсчёт от `send_shutdown()`) →
     `ask_force_stop()` с текстом: «Бэкенд не ответил на команду остановки за 2 с. Остановить систему принудительно?
     Шаги подготовки («домой») будут пропущены.» Кнопки «Остановить» (default) / «Подождать» (ещё 2,0 с от момента
     ответа). «Остановить» → `force_stop()` (= `set()` общего `system_stop_event` + WARNING) и ожидание детей
     продолжается; если после `force_stop()` ещё `no_answer_s` нет НИ ОДНОГО ответа (PM мёртв или завис — механизма
     обнаружения смерти PM нет, сторож родителя на Windows отключён: `process_runner.py:166`) → `commit_close()` + WARNING
     (иначе модальный диалог без отмены не имеет выхода — регрессия против сегодняшнего «X закрывает окно»); unattended — без вопроса «Остановить». Ответ пришёл, пока вопрос открыт —
     вопрос закрывается как «Подождать» без сброса счётчика, опрос идёт дальше. GUI общий `system_stop_event`
     НЕ взводит сам при `RUNNING → STOPPING`. Наблюдение события и внешний стоп — Task 2.1; в 1.1 внешний стоп ведёт себя как
     сейчас (H2), в 1.1 его не тестируют.
  6. `MainWindow.set_close_coordinator(c)`; БЕЗ координатора `closeEvent` ведёт себя по-старому (confirm + геометрия): на этом
     держатся существующие тесты `test_close_layout_unsaved_blind.py:56`, `test_topology_dirty_indicator.py:101` и закрытие в teardown.
     `MainWindow.closeEvent` (`main_window.py:287`) с координатором: состояние `CLOSING` → `_save_geometry()` + `super().closeEvent(event)`,

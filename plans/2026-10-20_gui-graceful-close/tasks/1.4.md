DESIGN (decided by the lead — you type it, you do not derive it):
  1. `_cmd_system_shutdown` (после Task 0.2): новый аргумент `initiator` (по умолчанию `sender`) → `system_stop.initiator`
     (Task 1.2). Ответ дополняется `"accepted"` и `"phase"`. Повтор `graceful` во время стопа → `{"success": True,
     "accepted": False, "reason": "already_stopping"}`; `force` во время `graceful` → таймер Task 0.2 + отмена шага.
  2. `graceful`, стопа нет: `phase = "pre_stop"`; шаги исполняет `KeyedExecutor` LSO 1.9a/1.9b (ключ — `"system"`), НЕ
     `message_processor`. Шаг = запрос ребёнку через существующий `_send_child_command` с `timeout_s`; таймаут или ошибка
     → WARNING `pre_stop: шаг '<process>.<command>' — <причина>`, следующий шаг. После шагов — события как сейчас. Пустой
     список — события сразу (задержка 0).
  3. `force`: шаги пропускаются; идущий — прерывается (флаг отмены между шагами и в ожидании ответа шага); затем
     поведение Task 0.2. `system_stop.pre_stop_step` — имя текущего шага или `null`.
  4. В фазе `pre_stop` исполнитель LSO 1.9b отклоняет новые команды жизненного цикла с `reason: "system_stopping"` —
     требование к 1.9b (`design.md` → «Соседи»); если 1.9b этого не даёт — ESCALATION -> cto.
  5. Новый `process/pre_stop.py`: схема шага `{process: str, command: str, args: dict = {}, timeout_s: float, 0 < t <= 60}`
     и исполнение списка с флагом отмены. Источник — ключ `pre_stop` конфига процесса PM (манифест приложения); ошибка
     схемы — отказ старта PM с текстом «pre_stop[<i>]: <поле> — <причина>». Пустой по умолчанию.
  6. `driver.system_shutdown` (Task 0.2): при `wait` вместо пробы соединения — опрос `supervision_status` (:1042) каждые
     100 мс (после Task 1.1 PM отвечает весь стоп) до `alive is False` у всех детей или разрыва; `outcomes` = `{name:
     outcome}` из последнего снимка (значения LSO 1.10: `exited | terminated | killed | survived | handed_over`).

**1. [шаг 6] `supervision_status_async(on_result)` и `shutdown_system_async(...)` «по образцу `stop_process_async`» получают таймаут 30 с — срок опроса 1,0 с, правило F и A8 перестают выполняться.**
`_dispatch_async` (`process_manager_proxy.py:154-158`) зовёт `self._sender.request_system_command(command)` без `timeout`; значение по умолчанию — `DEFAULT_REQUEST_TIMEOUT` (30 с, `command_sender.py:253-257`). Шаг 6 «координатор переходит на них с прямого `RequestRunner`» эту единицу теряет.
Вход: PM убит во время хода (A8). Результат: первый запрос висит 30 с, «в полёте не более одного» не пускает второй, ни одного «неудачного опроса» за 30 с, F не срабатывает; окно закроет только сторож тишины 1.1 (вопрос на 2,0 с, затем хвост). A8 «≤ 2,5 с» красный.

Либо: «F заменяет вопрос A5 и хвост (в)» — тогда поправить 1.1-тесты (п. 2) и decision 4 владельца (вопрос оператору «не молча») — это решение владельца, не исполнителя → ESCALATION лиду. ### Major

**4. [шаг 3, ACCEPTANCE] `stop_deadline_at` — `time.time()`, а `clock` координатора — `time.monotonic`: «фейковые часы» не определены.**
`_stop_deadline_at` (`process_manager_process.py:1152`) = `signalled_at + окно`, где `signalled_at` — wall (ADR-PMM-042). Конструктор 1.1: `clock=time.monotonic` (`close_coordinator.py:142`), фейк в тестах стартует с 1000.0 (`test_close_coordinator.py:65`).
Вход: `clock() >= stop_deadline_at` с monotonic (порядок 1e5) против epoch (порядок 1,7e9). Результат: «пережил срок» никогда не верно — вопрос зависания не появится ни на одном стенде; фейковый `clock` на нём ничего не проверит. Вход с `time.time()` напрямую: фейк `clock` не управляет.
Замена шага 3: «`wall_clock: Callable[[], float] = time.time` — второй внедряемый источник; `stop_deadline_at` сравнивается только с ним; `clock` остаётся для сторожей тишины. ACCEPTANCE: фикстура с литералами `stop_deadline_at = 1700000005.0`, `wall_clock` ставится на 1700000004.99 → вопроса нет, на 1700000005.0 → вопрос». Учесть, что опрос идёт раз в 250 мс: «ровно на сроке» верно по часам теста, вживую вопрос появляется на срок + до 0,25 с + время ответа (A4 допускает ± 0,5 с — согласуется). Записи с `stop_deadline_at: null` (волна `last` до сигнала, ADR-PMM-043; вне стопа) не считаются зависшими — добавить в шаг 3 и в RED 1.

**5. [шаг 3, REDS 1–2; запрос лида (2)] Вопрос «процесс завис» после решения 1.3 (А): недостижим для окна `g`, а там, где достижим, PM эскалирует в тот же миг; «Подождать ещё» на стороне PM ничего не меняет; у вопроса нет отзыва.**
Факты: у ребёнка без `stop_window_s` окно = `g` = 5,0 (реестр `stop_window_s(name)` :140-142), `stop_deadline_at = сигнал + 5,0`; `terminate` уходит в `min(request + окно, deadline)` (`child_process_stop.py:365`) — то есть в тот же момент; на путях с `gui: last` карта окон строится по всем именам (ADR-PMM-043), на пути без `last` `terminate` идёт на `kill()` области, тоже ≈ 5,0. В прототипе окна детей не заданы (1.3-ревью: `git grep stop_window_s|max_stop_window_s` по `multiprocess_prototype` вне тестов — 0).
Вход: ребёнок `devices` с окном `g`, завис. Результат: GUI видит `now ≥ stop_deadline_at` только опросом после 5,0 с; к этому опросу PM уже терминировал ребёнка (Windows `TerminateProcess` — мгновенно) → `alive False` → вопрос не задан. Вход: ребёнок с `stop_window_s = 3` (фикстура A4): вопрос появляется на 3,0 с, `terminate` уже ушёл на 3,0, `kill` — на 4,0 (`TERMINATE_GRACE_S`); «Подождать ещё — ещё одно окно» (шаг 3, RED 2) не продлевает ничего: через 1 с ребёнок мёртв, а вопрос на экране.
Что не так в DESIGN/REDS: (a) шаг 3 и RED 2 (`test_wait_more_rearms_by_child_stop_window`) описывают «Подождать ещё» как действенное, фиксируя только GUI-сторону; это тот же вопрос, что в `OPEN_QUESTIONS` 2026-11-08 и ADR-PMM-043, DESIGN его не называет; (b) у вида нет `hide_hang()` — API шага 1 `set_rows/set_phase/set_subtitle/set_elapsed/show_hang/show_backend_lost`: вход «зависший умер, остальные ещё останавливаются» → вопрос с активными кнопками остаётся на экране до «Система остановлена»; нажатие «Закрыть принудительно» шлёт `force` по уже мёртвому; (c) REDS 1–2 строят `alive True` после срока синтетически — в реальной цепочке PM такого окна нет; по правилам проекта «набор с фейками требует одного теста на настоящих объектах» (`project-rules` §9).
Это сужает решение владельца 7 (порог вопроса — окно стопа процесса) — решение живёт дольше задачи → **ESCALATION → lead** (и далее владелец): вариант 1 — принять, записать в DESIGN: «вопрос появляется только для ребёнка, переживающего свой `terminate`/`kill`; “Подождать ещё” сдвигает только сторону GUI; текст кнопки не обещает продления»; вариант 2 — порог вопроса `stop_deadline_at + TERMINATE_GRACE_S` (вопрос появляется, когда `terminate` уже не помог; вопрос осмыслен); вариант 3 — PM-сторона (вне 2.1). Рекомендую 2: GUI-сторона, одна константа, согласуется с `stop_outcome` (`killed`/`survived`). Независимо от выбора добавить `hide_hang()` и RED «зависший умер → вопрос снят, кнопки неактивны».

**6. [шаг 3, «Закрыть принудительно»] Путь `force`: PM сам терминирует `gui` в `deadline_s`; «ждёт итогов до 3,0 с, выжившие — WARNING» не выполнится; при молчащем PM система остаётся жить без GUI.**
(a) Порог из ADR-PMM-043: при `deadline_s ≤ 2,0` обе волны сигналятся на первом проходе, `terminate` уходит каждому живому ребёнку на `D` = 0,5 с. `gui` — ребёнок PM, он тоже в этом множестве. Вход: «Закрыть принудительно» при зависшем ребёнке.

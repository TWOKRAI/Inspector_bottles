# Конструктор интерфейса: слои, эталоны, форма (решение владельца 2026-09-26)

Часть плана [`plan.md`](plan.md). Меняет направление дизайна T4.1
[`gui-bootstrap-design.md`](gui-bootstrap-design.md): тот писался как «пакет вкладок + окно от пакета», теперь
единица — **виджет**, окна принадлежат **оболочке**. Связанные планы:
[`gui-service`](../2026-09-22_gui-service/plan.md) (Пульт, подключения, N бэкендов), `app_module` / `examples/minimal_app`
(constructor-master 5.11–5.13). Схема для чтения —
[страница «Конструктор интерфейса Inspector»](https://claude.ai/artifact/UoDWrLzyYwNLy6JnHBfkWL) (приватная, у владельца).

## Решение владельца

Слова владельца 2026-09-26, пересказ близко к тексту:

1. Фронт собирается конструктором из виджетов и вкладок. Основа — окна и вкладки плюс связь с бэкендом. Виджеты
   вставляются в окна, легко общаются друг с другом и с бэкендом, их можно быстро раскидывать между окнами.
2. Во фреймворке остаётся **конструктор из модулей**. В `Services` — готовые прикладные блоки (приложение «как в
   прототипе, но улучшенное») и Пульт. Прототип — **тонкий слой**: связывает фреймворк и сервисы и через топологию
   рецептов создаёт приложение под задачу инспекции.
3. Прототип — первый потребитель конструктора. Будущие потребители могут быть из другой сферы.
4. Эталоны: бэкенд — `examples/minimal_app` (уже есть), фронт — `examples/minimal_gui` (завести).

## Слои

| Слой | Что лежит | Чего быть не должно |
|---|---|---|
| **framework** (`frontend_module`, `app_module`) | оболочка: окна, доки, раскладка, замок; подключение (в дереве / сокет); контракт виджета и его контекст; шина событий интерфейса; загрузчик пакетов; формы и примитивы | ни одного предметного слова (камера, рецепт, дефект) |
| **Services** | вертикальные срезы: бэкенд-часть + клиентский порт + свой пакет виджетов (`recipe`, `auth`, устройства, `line_sim`); типовое приложение — **набор пакетов + раскладка по умолчанию**, не монолит | задача инспекции |
| **Plugins** | словарь обработки (бэкенд) | Qt-код: форма настроек плагина строится из описания регистров |
| **prototype** | пакет инспекции (камера с рамками, результаты), раскладки по ролям, топология и рецепты по умолчанию, `app.yaml` | общие механизмы |

Направление импортов прежнее: `framework → Services → Plugins → prototype`, плюс `examples/* ↛ multiprocess_prototype/*`
(`.sentrux/rules.toml:119-122`, уже действует).

**Правило двух потребителей.** Механизм уходит во фреймворк, когда он нужен двум потребителям (инспекция и
`apps/line_sim`, или инспекция и `examples/*`). Нужное одной инспекции остаётся в прототипе. Урок: поколение 1
`frontend_module` (`WidgetRegistry`, `WindowRegistry`, `layout_composer`, ~1250 строк) построили заранее, у него
0 потребителей, заморожено как LEGACY (`frontend_module/STATUS.md:17-35`).

## Эталоны — измеримый критерий «фреймворк стал конструктором»

| Эталон | Состояние | Что доказывает |
|---|---|---|
| `examples/minimal_app` | **есть** (Ф5.11–5.13, `tests/test_ci_smoke.py`) | бэкенд собирается из фреймворка + данных + трёх строк bootstrap |
| `examples/minimal_gui` | **завести** | фронт собирается из фреймворка + раскладки + своего виджета, без прототипа |

**`minimal_app` сегодня тонкий (сверено 2026-09-26, smoke 1 passed за 2.4 с).** Он доказывает загрузку и
межпроцессную доставку: два процесса на `GenericProcess`, 146 строк плагинов, плоский `pipeline.yaml`,
`wires: []`, сервис — пустой маркер. Он **не трогает** ничего из того, на чём стоит прототип и что понадобится
`minimal_gui`: рецепты и топологию из рецепта, регистры, запись в состояние и подписку, команды с ответом,
кадры, настоящий сервис. Добавлять по одному пункту, когда его тянет `minimal_gui` или потребность прототипа:

| Шаг | Что добавить в `minimal_app` | Кто тянет |
|---|---|---|
| 1 | `ticker` пишет счётчик в дерево состояния | виджет `minimal_gui` видит растущее значение |
| 2 | команда с ответом (сброс счётчика, смена интервала) | проверка «команда туда и обратно», gui-service 1b.2c |
| 3 | `interval_sec` как регистр плагина | форма настроек из описания, без Qt-кода в плагине |
| 4 | два рецепта в `recipes/` (медленный и быстрый) и переключение | главное в решении владельца: приложение собирается через топологию рецептов |
| — | кадры (`wires`), настоящий сервис из `Services` | позже: кадры уже проверяет `apps/line_sim`, сервисы — отдельный эталон уровня `Services` |

Для сравнения: бэкенд прототипа вне `frontend/` — 13 998 строк (`backend` 4 607, `domain` 4 093, `adapters` 2 473,
`recipes` 1 345, `registers` 1 037). Сборка уже идёт через `app_module` (`orchestrator.py` — `GenericProcessManagerApp`
плюс два хука), но «тонким» бэкенд прототипа пока не назвать. Что из этого общее, покажет тот же инвентарь.

Приёмка `examples/minimal_gui` (черновик, уточняется при постановке задачи):
- состав: `run.py` (несколько строк), `layout.yaml`, один локальный пакет с одним виджетом (счётчик тиков
  `minimal_app`), `README.md` в стиле `minimal_app` — исполняемая документация «сделай свой GUI»;
- ноль импортов `multiprocess_prototype`, `Services`, `Plugins` (grep-контракт + правило sentrux по образцу 119-122);
- CI-smoke headless (`QT_QPA_PLATFORM=offscreen`): поднять `minimal_app` через `BackendHarness`, запустить оболочку
  с подключением по сокету, виджет получает счётчик из состояния и растущее значение за литеральный срок; команда
  проходит туда и обратно;
- плюс один общий виджет фреймворка (процессы или телеметрия) — доказывает, что пакет фреймворка грузится так же,
  как прикладной.

Когда достижим: после T4.3 (стадии сборки), минимальной оболочки с доками и `RemoteGuiRuntime` (gui-service 1.4).
Разумно сделать его **приёмкой 1.4 со стороны фреймворка**: второй потребитель оболочки рядом с инспектором.
Пока `minimal_gui` не собирается без прототипа, общее ещё сидит в прототипе — это и есть счётчик долга.

## Форма конструктора

- **Оболочка (host).** Окна, доки, вкладки из доков, вынос панели в плавающее окно, сохранение и восстановление
  раскладки, **замок** (оператор не может закрыть камеру посреди смены), статус подключений. Сегодня докинга в коде
  нет (греп `QDockWidget|saveState|restoreState` по `frontend_module` и `prototype/frontend` — 0).
- **Подключение.** `GuiHostRuntime` из T4.1 §4 почти без изменений; их может быть N (gui-service Ф3).
- **Виджет.** `WidgetSpec` (Qt-free): `id`, `title`, `backend_role`, `params`, `multi_instance`, `factory` строкой.
  Фабрика получает только **контекст виджета** — узкий фасад над рантаймом: `state.subscribe(glob)`,
  `commands.request` (ответ или ошибка), `frames.subscribe`, `ui_bus`. Другие виджеты не импортирует, окна не знает.
- **Раскладка = данные.** Файл: подключения → окна → доки → виджет + параметры + подключение. Пресеты по ролям.
- **Три канала общения:** факт о системе — состояние бэкенда; действие — команда с ответом (это gui-service 1b.2c);
  контекст интерфейса (выбранный дефект) — шина событий, события объявлены в пакете. Прямая ссылка виджета на
  виджет запрещена.
- **Перетаскивание:** начать с нативных `QMainWindow` + `QDockWidget`. Qt Advanced Docking System — только если
  понадобится стыковка между разными главными окнами; новая зависимость, лицензия и сборка под PySide6 6.10 / aarch64
  не проверены.

## Что меняется в T4.1

| Решение T4.1 | Было | Стало |
|---|---|---|
| Р-E «чьё окно» | (а) окно отдаёт пакет | **развёрнуто:** окна у оболочки. Переходный шаг: весь нынешний `MainWindow` — один крупный виджет `inspector.classic`, чтобы не задержать 1.4 |
| `GuiAppSpec` | вкладки + хуки сборки | каталог `WidgetSpec` + раскладка по умолчанию; нынешние вкладки регистрируются виджетами 1:1 |
| `GuiHostWindow` (T4.6) | Блок В, к gui-service 3.1 | **раньше, к 1.4**, в минимуме: доки, раскладка, замок |
| Контекст виджета | нет (`RuntimeDeps` целиком) | добавить как фасад над `GuiHostRuntime` |
| Шина событий | `QtEventBus` без контрактов | оформить, когда придёт второй пакет (симулятор), не раньше |
| Р-A, Р-B, Р-C, Р-D, Р-F | рекомендации (а) | ложатся в схему без изменений; владелец не возражал, но **явно не утверждал** каждое |

## Порядок

1. T4.2–T4.4 как в дизайне + контекст виджета + регистрация вкладок виджетами. Поведение не меняется.
2. Минимальная оболочка с доками + gui-service 1.4 (Пульт = оболочка вне дерева) + `examples/minimal_gui`.
3. gui-service Ф3: второй бэкенд и пакет симулятора — второй потребитель контракта виджета и шины.
4. По нужде: `inspector.classic` дробится на камеру, результаты, управление; перенос прикладных срезов
   прототипа в `Services` — по инвентарю T3.0, не по оценке.

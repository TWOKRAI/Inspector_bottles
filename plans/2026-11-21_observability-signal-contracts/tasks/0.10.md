УТОЧНЕНИЯ ПО РЕВЬЮ СТАДИИ 0 (перекрывают DESIGN выше там, где расходятся):
  (а) ШАГ 1 ПЕРЕПИСАН: `snapshot(prefix)`, `get`, `history()` НЕ МЕНЯЮТСЯ (у `snapshot` плоская форма `{путь листа: значение}` и 7 потребителей: driver.py, _node_read.py, conditions.py, recorder.py, frontend bindings.py, _panels.py, TelemetryViewModel). Листья `_fresh.*` остаются в `snapshot` как есть с 0.9; их исключение из `metrics`/`count` делает 0.10b. Новое — только метод `read` (шаг 3). Метка читается «из текущего состояния, не кэшировать» по причине: `seq`/`src_ts` приходят порознь, кэш с первой dict-дельты даёт ложный `stale`.
  (б) `read(path, key, alive_incarnation=None)`: `path` — корень записи `processes.<name>`; любой другой путь (листьев `<path>._fresh.*` нет) → `{"class": "no_data", "value": None, "age_s": None}`. Сборка для `read_value` O(1): минимальное поддерево `{"_fresh": {seq, src_ts, incarnation, tick_sec из get(f"{path}._fresh.<k>")}}` плюс цепочка `key` из `get(f"{path}.{key}")`; `key`, указывающий не на лист (например `"state"`) → `no_data`. `now = self._clock()`. Класс через `read_value` (0.2), литералы классов: `no_data`, `fresh`, `stale`, `writer_gone`. Лист `None` (0.8) → `no_data`, не исключение. Pre/Post в докстринг (`module-contract`). Вызывающий в проде: читатель контракта I2 (`test_contract_freshness.py[read_model]`); GUI-вид «устарело» — вне задачи; у драйвера свой путь (0.10b зовёт `read_value` сам со своими часами; `BackendDriver` строит `TelemetryReadModel()` без `clock` — помечено для 0.10b).
  (в) M-16 (точка истории несёт `src_ts`, а не время приёма) — МЕХАНИЗМ «довыставление хвоста»: порядок дельт живого тика — значения РАНЬШЕ метки (тик 1: dict `workers`, `state`, затем dict `_fresh`; тик 2+: листья `effective_hz`, `state.fps`, затем `_fresh.seq`, `_fresh.src_ts`), поэтому метку нельзя читать в момент записи точки (точка отстанет на такт: `src_ts == 100.0` вместо `105.0`). На каждый корень `processes.<P>` ведётся список путей колец, в которые писали с прошлого прихода `…_fresh.src_ts`; когда листовая дельта `src_ts` приходит, последняя точка каждого такого кольца заменяется на `(src_ts, значение)`. Если метка пришла внутри той же dict-дельты, `_record_history` читает её напрямую (она уже в `_state`). Метки нет вообще — остаётся `self._clock()` (иначе краснеют `test_history_ts_is_wall_clock`, `test_injected_clock_stamps_history_ts`, экспорт/импорт, реплей рекордера). Меняются `_record_history`/`_apply_put`, а НЕ `history()`. Довыставление не двигает `write_seq`, не трогает `_push_seq` (инвариант 2 модуля) и не лежит в `ingest_poll_snapshot` (инвариант 1: опрос в кольцо не пишет). Недовыставленные точки (метка потеряна) остаются на времени приёма.
  (г) Исключение: `.state.uptime` (в `DEFAULT_TRACKED_SUFFIXES`) пишет `ProcessMonitor` (~1 Гц, не писатель метки) — его точки ВСЕГДА держат время приёма (константа модуля `_RECEIPT_TIME_SUFFIXES = (".state.uptime",)`), иначе кольцо перестанет быть хронологическим. Новые имена из Task 1.8 попадают в тот же список — пометка для 1.8.
  (д) Потоки: ядро лока НЕ получает; `read` и довыставление идут под локом вызывающего, как `get`/`snapshot`/`history`; `read` зовёт только `self._clock()` и чистую `read_value`; довыставление — в потоке `ingest`. Чтение между дельтой значения и дельтами метки даёт новое значение со старой меткой: возраст завышен не более чем на такт (безопасное направление), НЕ «чинить» кэшем.

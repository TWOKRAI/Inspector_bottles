  `:218`) выкидывает стадию медленнее 1 Гц. Якоря — имена, номера строк — справка.
  1. `record()` хранит метки и `_last_interval_s`: у первого завершения — время от создания рекордера (`_t_created`
     в `__init__`), далее — между двумя последними завершениями; частоту не пишет. Усечение окна в `record()` (память)
     остаётся, но на расчёт не влияет (см. шаг 2).
  2. `get_cycle_metrics()` и `record()` читают часы ВНУТРИ `with self._lock` (сейчас `now` берётся до лока — читатель
     получил бы отрицательный возраст). Расчёт — в хелпере `_metrics_locked(now)` (имя с `_locked`: `Lock` не
     реентерабелен, хелпер зовут только под локом). В момент `now`: `age = max(0.0, now - последняя метка)` (`None`, если
     циклов не было). Окно считается ОТ `now` ЧТЕНИЯ: метки с `t >= now - _HZ_WINDOW_S` (отбор в `get_cycle_metrics`, а не
     только в `record()`). `measured` = `(n - 1) / span` по меткам окна при n ≥ 2 и `span > 0`; иначе `1 / _last_interval_s`
     при `_last_interval_s > 0`; иначе неизвестна. Граница `1 / age` — только при `age > 0`. `effective_hz` — меньшее из
     известных чисел; все неизвестны → `None`. Циклов не было — как сейчас: 0.0, воркер не публикуется (причина: у такого
     воркера нет метки, его возраст от создания тревожил бы штатно ждущие воркеры, `IdleWorker`; зависание ДО первого
     цикла — вопрос 1.8 по `cycles == 0` и статусу, не этой задачи). Новый ключ `last_cycle_age_s` (не округляется).
     `round(…, 2)` для `effective_hz` в `get_cycle_metrics` УБРАТЬ (причина: при округлении до 2 знаков стадия медленнее
     ~1 цикла/200 с публикуется как 0.0 — «медленная выглядит мёртвой» возвращается в хвосте); прочие метрики
     `get_cycle_metrics` не трогать. `_HZ_WINDOW_S` не менять. Докстринг: мгновенная нижняя оценка, у нерегулярного потока
     шумит, до второго завершения грубая; истинный темп — счётчик `stage_items_out` (1.1).
  3. `build_worker_telemetry`: воркер «отработал», если `last_cycle_age_s is not None` в его снимке. Для таких воркеров
     в `workers_payload[<w>]` публикуются `effective_hz` (число или явный `None`, если оно неизвестно — иначе merge
     оставит под свежей меткой старое число) и `last_cycle_age_s`, вне флага `include_cycles`. `last_cycle_age_s`
     идёт вне гейта метрик (как `cycles`, диагностический ключ воркера); `effective_hz` — по прежнему правилу гейта
     (`hz_ok`) без изменений. Ноль — показание; фильтры `hz > 0` убрать. Пара процесса — воркер с наименьшей
     `effective_hz` среди ВСЕХ отработавших с числовым `effective_hz`, без фильтра статуса (стоящая или упавшая стадия
     спадает как 1/возраст, а не выпадает); воркер с `None` в выбор не входит. `latency_ms` читается у воркера пары
     напрямую, фильтр `lat > 0` для пары убрать (ноль — показание). Агрегат включён, а набор пуст → `fps` и
     `latency_ms` публикуются как `None`: старое число не живёт под свежей меткой. Это же происходит у процесса, чьи
     воркеры без `CycleMetricsRecorder` (нет поля `cycles` — норма, `frontend_module/state/telemetry_poller.py`): листья
     `None` уходят в merge каждый тик — осознанно, консьюмеры проверены ревью стадии 0 (`None` проходит).
  4. `round(x, 1)` из сборщика убрать ТОЛЬКО для `fps`, `latency_ms`, `effective_hz` (и пары); `queue_wait_ms` и
     `transport_ms` не трогать (их тесты ждут округления); округляет показ.

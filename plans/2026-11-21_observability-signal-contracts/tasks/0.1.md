  1. `interfaces.py`, рядом с `channel_accepted` (:61). Импорт: `from typing import Any, Dict, List, Literal, Optional`.
     Тексты — дословно:

         type Outcome = Literal["accepted", "refused", "failed"]

         _FAILED_STATUSES = ("error",)
         _REFUSED_STATUSES = ("dropped", "refused")

         def outcome_of(result: Any) -> Outcome:
             if not isinstance(result, dict):
                 return "accepted"
             status = result.get("status")
             if status in _FAILED_STATUSES:
                 return "failed"
             if status in _REFUSED_STATUSES:
                 return "refused"
             return "accepted"

     Статус проверяется кортежем, не `set`. Причина: `{"status": ["error"]}` (список) даёт `accepted`, а `set` бросил бы
     `TypeError: unhashable`. Прочее — `success`, `ok`, `skipped` (`log_channel.py:1167`), `dict` без `status`,
     `None`, не-`dict` — `accepted`. Причина «`None` и не-`dict` принятые»: канал без ответа считался принявшим и раньше; ломать это нельзя.
     `channel_accepted(result)`: докстринг оставить, тело заменить на `return outcome_of(result) == "accepted"`.
     `__all__` (`interfaces.py:208–213`): добавить `"Outcome"` и `"outcome_of"`. `__init__.py` не нужен.
     **Расширение, не «бит в бит».** `channel_accepted({"status": "refused"})` сегодня `True`, после правки `False`.
     Для всех остальных входов поведение прежнее. Причина: `refused` — тот же отказ, что `dropped` (расширение 2.1). Ни один
     канал репозитория так не отвечает (`git grep '"status": "refused"'` вне тестов — пусто). Строка об этом — в ADR-CRM-019.
  2. `channel_routing_manager.py`, сразу после `DELIVERY_COUNTER_KEYS` (:71). Импорт `Outcome` — в строку `from ..interfaces import …` (:29).
     Тексты — дословно:

         LOSS_KEY_BY_HOP: dict[str, dict[str, str]] = {
             "channel": {"refused": "channel_refused_records", "failed": "channel_refused_records"},
             "tap": {"refused": "tap_refused_records", "failed": "tap_write_errors"},
             "bridge": {"refused": "lost_responses", "failed": "lost_responses"},
         }

         def count_outcome(counters: dict, hop: str, outcome: Outcome) -> None:
             keys = LOSS_KEY_BY_HOP.get(hop)
             if keys is None:
                 raise ValueError("count_outcome: unknown hop")
             if outcome == "accepted":
                 return
             key = keys.get(outcome)
             if key is None:
                 raise ValueError("count_outcome: unknown outcome")
             counters[key] = counters.get(key, 0) + 1

     Правила: возвращает `None`. Мутирует `counters`: прибавляет 1 (`counters.get(key, 0) + 1`). `accepted` — ничего не делает.
     Неизвестный `hop` или `outcome` — `ValueError` с фиксированным текстом, без значения в сообщении. `hop` проверяется
     раньше `outcome`, и до ветки `accepted`: опечатка в имени звена видна и на здоровом пути. Лок держит вызывающий; функция ничего
     не лочит и не логирует. Причины таблицы:
       - `channel`: `failed` и `refused` — в `channel_refused_records`. `channel_write_errors` остаётся «звено БРОСИЛО исключение»
         (ADR-CRM-011: классы не сливаются, лечатся разным). Ответ `{"status": "error"}` — это «сток жив и отказывает»;
         так `_write_record_to_channels` считает его и сегодня (`channel_routing_manager.py:1060–1085`, тест
         `test_delivery_counters.py:43–44,103`).
       - `tap`: `refused` — НОВЫЙ ключ `tap_refused_records`. Tap судил только исключения (ADR-CRM-016), «ответил отказом» не считалось.
         `failed` — в `tap_write_errors`: ответ `error` и исключение у приёмника хвоста — одна болезнь (дефект приёмника).
       - `bridge`: оба — в `lost_responses`. Адаптер моста ведёт один счётчик потерянных ответов (`get_stats()["lost_responses"]`); второго нет.
     Ключ `tap_refused_records` в `LOSS_COUNTER_KEYS` и `PLANE_COUNTER_KEYS` НЕ вводить: это делает Task 0.5. Здесь
     `count_outcome` работает на обычном `dict`. После 0.1 у `count_outcome` ноль живых вызывающих; вызовы подключают 0.4–0.6.
     Свойство «звено не вправе улучшить исход нижнего» здесь НЕ вводится (у `worst` нет вызывающего). Его проверяет приёмка 0.5 и 0.6.

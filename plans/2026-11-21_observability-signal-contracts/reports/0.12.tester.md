## Что истолковано, а не выполнено буквально

- `test_read_token_variants` — один тест на все варианты (пустой, пробелы, strip, нет файла, каталог): три из них зелёные против заглушки (`None`), а красных поимённо по плану только один тест; разнесение по параметрам дало бы зелёные параметры вне списка стражей.
- `test_hello_and_command_in_one_segment` содержит ДВЕ проверки (верный hello + команда; плохой hello + команда): иначе инъекции (a) и (g) по плану лида не краснели бы на одном имени.
- Строка отказа до EOF: `_assert_rejected(require_line=True)` требует строку при `eof`, но допускает `reset` без строки; для deadline/garbage/oversize строка не обязательна (`require_line=False`).
- `no_broadcast`: B молчит открытым, проверка `pytest.raises(socket.timeout)` на `recv` 0.5 с; ожидание A — `clients >= 1` (до 2 с) перед `send()`.
- `authenticator_exception_rejected`: authenticator бросает ТОЛЬКО на первом вызове (счётчик), на втором делегирует `token_authenticator(TOKEN)`; иначе «следующий клиент проходит» невозможно.
- `token_never_logged`: сервер ждёт `"cd" * 32`, чтобы `"ab" * 32` был неверным токеном; A идёт сырым сокетом (проверяется ответ), B — клиентом (проверяется `SocketAuthError`); добавлен `caplog` на DEBUG для DEBUG-логов канала через `get_std_logger`.
- Тайминги ожиданий отказа — 1.5 с на чтение (реальная реализация отвечает за миллисекунды), чтобы тело теста стабильно укладывалось в join 5 с декоратора `_bounded`.

## Что осталось открытым / ненадёжным

- Угадывание контракта: (1) `log_error` — это тот самый канал «ERROR без содержимого строки»; тест `authenticator_exception_rejected` требует хотя бы одну запись в `log_error` за 1 с. Если GREEN логирует через `get_std_logger().error(...)`, а не через инжектированный `log_error`, тест покраснеет ложно: решение лида. (2) `SocketClient.session` — публичный атрибут/свойство (используется в `connect_timeout_leaves_state_clean`, против заглушки до него не дошло; `subscriber_address` в старых тестах им пользуется, так что вероятно есть). (3) `client.connect(timeout=...)` и `client.request(msg, timeout=...)` вызываются по ключу `timeout=`.
- Против заглушки `request()` при таймауте возвращает dict `{'success': False, 'error': 'timeout'}`, а не бросает; тесты клиента к этому устойчивы (любой исход, кроме нужного, — красный по утверждению).
- Тесты `dripping`, `silent`, `oversize` зависят от гранулярности recv-timeout 0.5 с канала: порог EOF 3.0 с по контракту, запас ~6x.

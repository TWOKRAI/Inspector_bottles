## Что оставил открытым / ненадёжно

- **Стенд не запускался**, SIGSTOP на живом процессе не посылался. Все формы ответов (`state.get_subtree` -> `subtree`, `introspect.status` -> `pid`, `supervision_status` -> `processes`, `telemetry_snapshot` -> `metrics[...]`) взяты из кода, а подставной драйвер написан мной по тому же чтению: если я неверно прочёл форму, тест и зонд ошибутся одинаково. Реальный ответ покажет только стенд лида.
- Лист `state.fps` у `processor` на `inspection_full` не проверен; если `None`, зонд возьмёт другой лист (запись об этом — в `observed`, не в `NOTES`).
- `introspect.status` даёт pid через `os.getpid()` внутри процесса, `supervision_status` — pid из реестра PM. Если они разойдутся (процесс-обёртка), зонд пошлёт сигнал pid из `introspect.status`, а сравнение до/после пойдёт по pid супервизии; сверки двух pid до стопа нет.
- Окно 10.75 с / 12 с взято из задачи (замер фазы 0: `stale` с ~10.4 с, рестарт при стопе >= ~14 с); запас до рестарта монитором ~1-3 с, вероятность раннего рестарта (20-40 %) остаётся допущением ревью. Тогда SF1 = `UNVERIFIED`, повтор.
- Читатель (2) использует приватные `drv._telemetry_model` / `_telemetry_lock`; читатель (1) — не независимый (класс считает сам зонд).
- Каждый вызов IPC в зонде — таймаут 15 с; зависший `state.get_subtree` во время стопа продлит окно, SIGCONT всё равно уйдёт в `finally`, но чтение может прийти уже после рестарта (рестарт даст `UNVERIFIED`).
- Тесты на `NOTES` (троттл, `gap_count`, `seq`) не написаны — по задаче это записи отчёта, не вердикты.
- Строки 0.12b, стенд, итог `tasks/0.13.result.md` — лид. Контр-тесты среза из ACCEPTANCE (`12 + 13 passed` по 0.1–0.3) не гонял: файлы вне моих изменений.

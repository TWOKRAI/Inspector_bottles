Спецификация к [`plan.md`](plan.md). Источник фактов — ревизия
[`docs/reports/2026-11-21_observability-review.html`](../../docs/reports/2026-11-21_observability-review.html)

## 1. Решения лида D1–D7 (обязательны; спор — в «Открытые вопросы», не молча)

| # | Решение | Где в плане |
|---|---|---|
| D1 | Класс «ответ выглядит здоровым» закрывают три инварианта; у каждого один параметризованный контракт-тест, он пишется до экземпляров. I1 «исход»: принял / отказал с причиной / сбой; звено не улучшает исход нижнего; счётчик потерь — одна функция. I2 «свежесть»: номер, время источника, воплощение; читатель отдаёт возраст и класс {`no_data`, `fresh`, `stale`, `writer_gone`}; ноль — значение, не класс; «нет данных», «ноль», «устарело», «писатель ушёл» — разные пары (класс, значение). I3 «причинность проверки»: образ до + подтверждение + образ после; равный образ до — `vacuous` | 0.1–0.13 (с 0.10b, 0.11b, 0.12b) |
| D2 | Четыре роли в процессе: тонкий разъём эмиссии; один писатель записей (`ErrorManager` — обогатитель, это closure 4.17); один реестр инструментов в `statistics_module`; приёмники с одним контрактом исхода. Публичные `_log_*`, `_record_*`, `ctx.*` не меняются | 1.2, 1.3, 3.1–3.8 |
| D3 | Метрики выводятся из отчёта о мощности: семь инструментов стадии в шве `PipelineExecutor.run_loop`, `DataReceiver`, `SourceProducer`; хоп-лаг — одно число в конверте; часы — в одном месте с самопроверкой; отчёт — два снимка, таблица, строка вывода. Не зависит от `ServiceContext` и нейтрального словаря | 1.1–1.12 |
| D4 | Порт управления — граница продукта (срез 0: рукопожатие 0.12, включение 0.12b): рукопожатие, роль на хосте, очередь на выход у клиента, `max_clients`, потолок таймаута, проверенная и подтверждаемая запись на хосте, поставка `enabled: false`. Клиент без прототипа; зонды вне пакета; MCP по намерению 57 → 19, старые имена — скрытые алиасы | 0.12, 2.1–2.14 |
| D5 | Стор: сначала замер (closure 4.8, отказы блокировки на 20 процессах); сегмент на процесс — только по триггеру, никогда центральный писатель | 1.10, 1.11 |
| D6 | Не строим: менеджер ручек, SDK OTel во фреймворке, свою трассировку, базу временных рядов, новое поколение планов | §2 |
| D7 | Четыре среза, каждый кончается строкой чек-листа приёмки | Phase 0–3; Phase 4 — хвосты (вариант A) |

## 2. Не делаем — доводы (блок G ревизии)

| Что | Почему |
|---|---|
| Менеджер ручек (closure 4.9) | Слои настроек со сроком и обратным чтением работают: на стенде прошли все исполненные строки семейства «ручки» |
| SDK OpenTelemetry во фреймворке | Накопительные счётчики и гистограммы с границами `le` ложатся в OTel и Prometheus без преобразований; читатель — сервис (3.10) |
| Своя трассировка | Широкие записи с выборкой `first_n` / `every_mth` уже работают; к ним добавляются отметки по хопам (1.7) |
| База временных рядов | Снимков реестра в сторе хватает отчёту о мощности |
| Новое поколение планов | Один план со срезами; каждый срез кончается строкой чек-листа |
| Смена топологии стора заранее | 7 процессов: 677 строк за прогон, медиана «запись → строка» 108 мс; сначала замер 1.10 |

## 4. Модули и границы

| Что | Модуль-владелец | Почему там |
|---|---|---|
| `outcome_of`, `count_outcome`, таблица ключей потерь | `channel_routing_module` (`interfaces.py`, `core/channel_routing_manager.py`) | рядом с `channel_accepted` и `LOSS_COUNTER_KEYS`; база трёх плоскостей |
| Конверт свежести `_fresh`, `classify`, `age_s` | `state_store_module/core/freshness.py` (NEW файл) | значение идёт через дерево; модуль ниже `process_module` и `telemetry_readmodel_module` (тот уже импортирует `state_store_module.core.leaf_copy`) |
| Метка свежести на слиянии | `process_module` (heartbeat) | единственный сборщик такта |
| Возраст у читателей | `telemetry_readmodel_module`; `backend_ctl` | читатели D1 |
| Рукопожатие, токен `~/.multiprocess_framework/ctl_<port>.token` | `router_module/channels/socket_auth.py` (NEW файл) | канал и клиент общие (`SocketChannel`, `SocketClient`); путь не зависит от каталога журнала |
| Стадия-нагрузка `delay_stage` | `Plugins/utility/delay_stage` (NEW плагин) | словарь плагинов; знает только `PluginContext` |
| Форма вердикта I3 | `backend_ctl/verdict.py` (срез 0) → контракт хоста в `process_manager_module` (2.6) | сначала клиент, затем хост по D4 |
| Реестр инструментов | `statistics_module` | D2 |
| Инструменты стадии, часы хопа | `process_module/generic` (`pipeline_executor.py`, `data_receiver.py`, `source_producer.py`, `frame_trace.py`) | шов уже есть (D3) |
| Самопроверка часов, темп линии | `process_manager_module/monitor` | читает heartbeat всех детей |
| Отчёт о мощности | `scripts/capacity_bench` | строим на бенче, не рядом |
| Рукопожатие, очередь на выход, потолки | `router_module` (`SocketChannel`, общий) + `process_manager_module` (токен, роли) | канал общий; политика — у хоста |
| Профиль приложения | адаптер рядом с приложением (2.9) | `backend_ctl` не импортирует прототип |
| Экспорт метрик | `Services/otel_export` | D6: экспорт — сервис |

Направление импорта: `multiprocess_framework → Services → Plugins → multiprocess_prototype`; `backend_ctl` сверху всех.
Новых модулей нет: каждый новый кусок — файл внутри существующего модуля. Если исполнитель увидит, что модуль
кусок не держит, — стоп и вопрос лиду (тогда README, STATUS, interfaces, tests по правилу 2).

# План: Hikrobot MV-ID3013PM-06M — автономная работа с ПЛК + внедрение в систему (slug `qr-code-reader`)

## Контекст

Появилось железо — **Hikrobot MV-ID3013PM-06M-Sensotec** (серия ID3000; «Sensotec» —
дистрибьютор, железо то же). Smart code reader: 1.3 МП монохром, global shutter, объектив

рецептом, наблюдать и настраивать. Плюс: «в будущем может понадобиться, чтобы из камеры в
ПК шло» — значит слой наблюдения не одноразовый.

**Режим работы — по триггеру** («должно по триггеру делать фотографию кьюркода»).

**ПЛК ещё нет в железе** («пока только камера, ПЛК будет позже»).

### Два прежних допущения плана ОТМЕНЕНЫ

| Было в плане | Оказалось |
|---|---|
| «Роль камеры в Modbus (ведомая/ведущая) — интерпретация, не цитата» | **Подтверждено дословно** (англ. оригинал, разд. 3.6): «The device only uses holding registers…»; ПЛК **пишет** в REG0 (Trigger Enable / Trigger / Results Ack / Clear Error) и **читает** REG1–REG3. ⚠ Но роль **настраиваемая**: `ModBus Mode = Server` → считыватель ведомый (наш случай), `Client` → считыватель сам подключается к ПЛК. Ф0 п.3 закрыт **при условии** Server-режима, что и проверяется в IDMVS |
| «Сетевого триггера не найдено» | **Найден.** Триггер подаётся битом **REG0.1** по Modbus. Более того, это и есть штатный боевой способ для связки с ПЛК. Task 2.2 может реализовать `trigger()` честно, а не заглушкой |

### Карта регистров (holding registers, смещения настраиваемые)

**Управление** — ПЛК → устройство, смещение по умолчанию **0**, размер 1 регистр:

| Бит | Название | Смысл |
|---|---|---|
| REG0.0 | Trigger Enable | ПЛК включает работу по триггеру |
| REG0.1 | **Триггер** | Импульс: снять изображение и один раз прогнать алгоритм. Условия: задан Trigger Enable, устройство не занято, задан Trigger Ready |
| REG0.2 | Results Ack | ПЛК подтвердил приём результата → устройство чистит Results OK/NG |
| REG0.3–14 | Reserved | — |
| REG0.15 | Clear Error | Сброс General Fault |

**Состояние** — устройство → ПЛК, смещение по умолчанию **1**, размер 1 регистр:

| Бит | Название | Смысл |
|---|---|---|
| REG1.0 | Trigger Ready | Готов принять новый триггер |
| REG1.1 | Trigger Ack | Триггер получен |
| REG1.2 | Acquiring | Идёт съёмка |
| REG1.3 | Decoding | Идёт распознавание |
| REG1.4–7 | Reserved | — |
| REG1.8 | Results OK | Есть новый результат; чистится по Results Ack |
| REG1.9 | Results NG | Код не прочитан. **Примечание мануала: при использовании сигнала NG функцию NoRead надо отключить** |
| REG1.10–14 | Reserved | — |
| REG1.15 | General Fault | Внутренняя неисправность; снимается Clear Error |

**Результат** — устройство → ПЛК, смещение по умолчанию **2**, размер **от 4 до 500
регистров (по умолчанию 100)**:

| Регистр | Название | Смысл |
|---|---|---|
| REG2 | Result Length | Длина данных результата |
| REG3… | Данные результата | Сам код. Короче модуля — хвост забивается нулями; длиннее — **лишнее обрезается** |

### Протокол обмена (гл. 3.7 «Триггер-тест», дословный порядок)

1. ПЛК задаёт **Trigger Enable REG0.0**; устройство, когда готово, поднимает **Trigger Ready REG1.0**.
2. Увидев Trigger Ready, ПЛК выдаёт **триггер REG0.1**.
3. Устройство снимает и декодирует: успех → **Results OK REG1.8**; неудача → **Results NG REG1.9** и **очистка начального адреса REG2**.
4. ПЛК читает длину и данные из REG2.
5. ПЛК выставляет **Results Ack REG0.2**.
6. Цикл повторяется.

**Обработка сбоя:** если устройство не может выдать результат из-за внутренней ошибки
(пример из мануала — «после подключения считывателя кода к IDMVS не включается получение
изображений»), поднимается **General Fault REG1.15**; ПЛК выясняет причину, выдаёт
**Clear Error REG0.15**, после устранения работа продолжается.

**NoRead:** при включённом NoRead неудачное чтение возвращает **Results OK + символ NoRead**;
при выключенном — **Results NG**. Это прямо отвечает на критерий приёмки «`no read` отличим
от кода» — отличие настраивается, и для ПЛК правильнее NoRead выключить.

### ⚠ РАСХОЖДЕНИЕ ВЕРСИЙ — пространства и смещения зависят от версии прошивки

**ПЕРЕПИСАНО 2026-09-28 (второй заход).** Первая редакция раздела сравнивала русский перевод
с UM V4.0.1 и приписала свежему мануалу три «нововведения», которых он не вводил. После того
как нашёлся **английский оригинал протокольного руководства** (`id3000-protocols-en`,
UD26848B V1.0.0), сравнение стало корректным — сравниваются два английских документа.

| Параметр | UD26848B V1.0.0 (протокольный, 2023) | UD47062B V4.0.1, табл. 8-16 (2026-06-15) |
|---|---|---|
| Control Space | `holding_register`, offset **configurable**, 0 по умолч. | `holding_register`, «**not editable**» |
| Control Size | **1 регистр (2 байта)** | **2 Word** |
| Status Space | **`holding_register`**, offset 1 | **`input_register`**, offset **0** |
| Result Space | **`holding_register`**, offset 2 | **`input_register`**, offset **4** |
| Result Size | 4–500 регистров (100 по умолч.) | не указан |

**Что из прежней редакции ОТМЕНЕНО (три пункта были неверны):**

1. ~~«`ModBus Mode`: Server/Client — не упомянут в старом мануале»~~ — **упомянут.**
   Раздел 3.3, шаг 5: «Выберите режим ModBus в качестве сервера или клиента», плюс два
   скриншота IDMVS (рис. 3-3 «Серверный режим», рис. 3-4 «Режим клиента») и отдельные
   разделы 3.4.1 ModBus Poll / 3.4.2 ModBus Slave под каждый режим. Режим выбирался и в
   2023 году — это **не** новая возможность прошивки.
2. ~~«`ModBus Result Byte Swap` — новое в V4.0.1»~~ — **есть на скриншоте рис. 3-3**
   старого мануала, вместе с `ModBus Result Timeout(s)` и `ModBus Control Poll Interval`.
3. ~~«Утверждение "устройство использует только регистры хранения" устарело»~~ — формулировка
   сохраняется, но у неё есть уточнение, которого раньше не заметили: в **серверном** режиме

   **клиентском** — «можно настроить адрес смещения и размер модуля результата».

**Что осталось верным и важно:** пространства Status/Result действительно разошлись —
`holding_register` против `input_register`, Result Offset 2 против 4. Зонд, написанный по
одному документу, на прошивке из другого читал бы не ту область и видел нули.
**Биты и логика обмена совпадают полностью** — расходятся только адреса и пространства.

**Что с этим делать (без изменений):** в Ф0 обязательный пункт — снять фактические значения
`ModBus Control/Status/Result Space` и `Offset` прямо из IDMVS на нашем устройстве и записать
в `context.md`. Источник истины — прибор, не документ.

### Дефект «недопустимая длина» — в АНГЛИЙСКОМ ОРИГИНАЛЕ, а не в переводе

**ГИПОТЕЗА ОБ ОШИБКЕ ПЕРЕВОДЧИКА ОТМЕНЕНА 2026-09-28.** Найденный английский оригинал не снял
инверсию, а показал, что она пришла сверху.

Регистр **Result Length** описан как «**invalid** data length» ровно **четыре** раза, и в
оригинале, и в переводе, в одних и тех же местах:

| Физ. стр. EN | Глава | Оригинал | Перевод |
|---|---|---|---|
| 18 | 1 Ethernet/IP | «The **invalid** data length in the result area.» | «Недопустимая длина данных» |
| 49 | 3 ModBus (REG2) | «The result area includes **invalid** data length.» | «содержит недопустимую длину данных» |
| 62 | 4 MELSEC/SLMP (D2) | то же | то же |
| 73 | 5 FINS (D2) | то же | то же |

И **три** раза в главе 2 (Profinet, табл. 2-3/2-5/2-6, стр. 29–31) — **правильно** в обоих:
«Result Data contains the **actual** length of data» / «содержат фактическую длину данных».

Распределение 4 «invalid» + 3 «actual» совпадает один в один. Значит **перевод воспроизводит
оригинал точно**, а инверсия внесена раньше — на этапе китайский → английский (вероятно,
有效 «valid» прочитано как «invalid»).

**Правильное прочтение — действительная длина результата.** Подтверждается тремя местами
того же документа: (1) глава Profinet называет тот же регистр «actual length»; (2) логика
3.7: «put code **length and contents** into the address starting from REG2»; (3) описание
REG3 — короче модуля дополняется нулями, длиннее обрезается, то есть длина нужна, чтобы
знать, сколько байт читать. **В контракт для ПЛК — только исправленная формулировка**, с
пометкой, что оба официальных документа здесь ошибаются.

### Серия прибора — ВОПРОС ЗАКРЫТ, и проверяется физически

Прежняя формулировка «ни один из двух мануалов перечня моделей не содержит, значит по
документам неразрешимо» верна **про мануалы** и неверна как вывод. Разрешается двумя
независимыми способами:

1. **Каталог производителя.** Hikrobot «Machine Vision Smart Product Catalog», стр. 55,
   раздел «ID3000 Series Smart Code Reader»: `MV-ID3013PM` — 1280 × 1024, 60 fps,
   84 кода/сек, белый/синий/красный/ИК, **20 Вт @24 VDC**, фокусные 6 / 12 / 14.8 мм.
   В той же таблице `MV-ID3016XM`, `MV-ID3030XM`, `MV-ID3050XM`. Суффикс `-06M` — объектив
   6 мм. Совпадает с прибором владельца (1.3 МП, 6 мм, белая подсветка).
2. **Проверка на столе, читать ничего не нужно — пересчитать контакты разъёма.**
   ID3000 Series (UD47062B V4.0.1) описывает **17-pin M12**. ID3000X / ID3000R
   (UD46372B) описывает **12-pin M12 и 8-pin M12**, слова «17-pin» в нём нет вовсе
   (grep по обоим `full_text.txt`). У прибора владельца — 17-pin M12.

**Вывод: MV-ID3013PM-06M — серия ID3000, применимый мануал `id3000-series-um-en-v401`
(UD47062B V4.0.1). `id3000xr-series-um-en` к прибору не применим и в контракт не
цитируется.** Остаточная неопределённость — не серия, а **версия прошивки**: V4.0.1 от
15.06.2026 может описывать ревизию новее той, что стоит на приборе. Это и есть причина,
по которой Ф0 всё равно снимает значения из IDMVS.

Потребление 20 Вт @24 VDC — цифра для расчёта питания в Task 0.0, взята из каталога;
в UM V4.0.1 таблицы характеристик нет (grep по «20 W» — ноль совпадений).

### Что это меняет в задачах

- **Task 1.2** — ветка определена **при условии `ModBus Mode = Server`** (считыватель ведомый, мы опрашиваем). Это режим по умолчанию и наш рабочий случай, но он **переключаемый** — в `Client` считыватель сам подключится к `ModBus Server IP:Port`, и тогда нужен принимающий сервер, а не мастер. Первым делом в Ф0 посмотреть значение `ModBus Mode` в IDMVS. В Server-режиме зонд должен уметь не только читать, но и **писать** REG0 (Trigger Enable / Trigger / Results Ack) — иначе цикл не поедет: без Results Ack устройство не отдаст следующий результат.
- **Task 1.4 (контракт для ПЛК)** — карта регистров выше уже есть, её надо только сверить с живым устройством и дополнить таймингами.
- **Task 2.2** — `trigger()` для канала `modbus` реализуем честно (запись бита REG0.1). Оговорка «может оказаться неподдержанным» снимается для Modbus; для сырого TCP остаётся в силе.
- **Другие протоколы**: мануал описывает ровно тем же способом Ethernet/IP (гл. 1), Profinet (гл. 2), MELSEC/SLMP (гл. 4), FINS (гл. 5) — у каждого свой «Триггер-тест». Если ПЛК окажется Siemens или Mitsubishi, схема будет аналогичной.

### Главный результат — не код

Это настроенный считыватель плюс зафиксированный контракт (режим триггера, карта регистров,
назначение выходов), который отдаётся программисту ПЛК. Артефакт переживёт и ПК, и наш
репозиторий. Отсюда порядок: **сначала доказать автономный режим**, пока железо на столе,
и только потом строить интеграцию (трек B), которая трек A не блокирует.

| Pin | Сигнал | Цвет | Куда идёт в штатном кабеле |
|---|---|---|---|
| 1 | POWER_IN (+12…24 В) | красный | pin 8 клеммника |
| 11 | GND | чёрный | pin 7 клеммника |
| 16 | **DI_0** | серый | pin 1 клеммника |
| 17 | **DI_1** | белый | pin 2 клеммника |
| 9 | **DI_2** | синий | pin 3 клеммника |
| 8 | **DO_0** | сине-белый | pin 4 клеммника |

**Ловушка при монтаже:** `IN_R` и `OUT_R` — открытые провода, их нет в 8-pin клеммнике.
Именно ими задаётся схема NPN/PNP, и без них вход/выход работать не будет.

#### ✅ Кабель сверен на нашем экземпляре — 2026-09-28

**Первый факт, снятый не с мануала, а с железа.** Владелец прочёл порядок жил в штатном
кабеле: `красный · чёрный · коричневый · коричнево-белый · сине-белый · синий · белый · серый`.
Это **ровно Table 4-1, прочитанная с клеммы 8 к клемме 1** — восемь цветов из восьми, без
лишних и без пропусков. Кабель соответствует мануалу, расхождений нет.

| Порядок в жгуте | Клемма | Сигнал | Линия в IDMVS |
|---|---|---|---|
| 1-й · красный | **8** | POWER_IN **+** | — |
| 2-й · чёрный | **7** | GND **−** (и земля сигналов) | — |
| 3-й · коричневый | 6 | DO_2 | Line 5 · выход |
| 4-й · коричнево-белый | 5 | DO_1 | Line 4 · выход |
| 5-й · сине-белый | 4 | DO_0 | Line 3 · выход |
| 6-й · синий | 3 | DI_2 | Line 2 · вход |
| 7-й · белый | 2 | DI_1 | Line 1 · вход |
| 8-й · серый | 1 | DI_0 | Line 0 · вход |

**Нумерация клеммника идёт против порядка чтения жгута.** Якорь — красный: это всегда
клемма 8, плюс питания. Если на колодке напечатаны цифры, сверить по ним; если нет —
отсчитывать от красного.

**Что проверить отдельно:** розового (`IN_R`) и фиолетово-белого (`OUT_R`) в этих восьми
нет — и не должно быть, по мануалу это открытые концы мимо колодки. Но убедиться, что они
физически есть на кабеле, надо: без них вход и выход не работают, а мануал предупреждает
«the 17-pin cable may differ by device model». Их отсутствие — находка, а не мелочь.

#### Электрика I/O (гл. 6, V4.0.1)

| Что | Значение |
|---|---|
| Питание прибора | **12 или 24 В ⎓** — пороги входов едут вместе с ним |
| Вход Low / High при VCC = 24 В | 0…9 В / 11…24 В |
| Вход Low / High при VCC = 12 В | 0…5,4 В / 7,56…12 В |
| Ток входа max · напряжение пробоя | 25 мА · 36 В |
| Выход | **не источник, а ключ**; уровень задаёт внешняя подтяжка, max 200 мА |
| Выход при внешних 12 В и 1 кОм | Low 212 мВ · High 11,8 В · фронт 0,4 мкс |
| Подтяжка (версия 2.0) | PNP — **330 Ω** вниз; NPN — **1 кОм** вверх |

**Две ловушки, каждая с прямой цитатой:**
- **DB9 несёт 12 В.** Питать можно либо через 8-pin клеммник, либо через DB9 — одновременно
  оба «may cause the burnout of the power supply».
- **VCC внешнего ≤ PWR камеры.** «The voltage of VCC should not higher than that of PWR.
  Otherwise, the device's output signal may have exception». Камеру на 12 В с 24-вольтовым
  ПЛК так не соединяют.

**Монтажные схемы** — [`docs/diagrams/wiring/id3013-wiring.html`](../docs/diagrams/wiring/id3013-wiring.html):
питание, развязанный вариант 3.0, общий GND версии 2.0, минимальная связка с ПЛК.
Топология снята с **текстовых подписей** к рис. 6-5…6-15, не с самих картинок — перед
монтажом сверять с `source.pdf` глазами.

#### Task 2.2 — Backends: Protocol, `sim`, `tcp`, фабрика, sim-сервер
**Level:** Middle+ · **Assignee:** `developer` · **Module contract:** new-full (`Plugins/sources/code_reader`) · **Layer:** plugins
**Архитектурное решение:** каналы живут **внутри плагина**, не в `Services/` — как у `camera_service`. На старте это ~60 строк socket-кода; каталог сервиса с `interfaces.py`/`README`/`STATUS`/`tests` под это — лишний каркас. **Порог выноса назван заранее и реалистичен:** появление биндингов `MvCodeReader` **или** второй потребитель помимо этого рецепта → карве-аут в `Services/code_reader/`, как было с `hikvision_camera`. Форма Protocol + фабрика переезжает без переписывания.

```python
# Plugins/sources/code_reader/backends/base.py
@runtime_checkable
class CodeReaderBackend(Protocol):
    def connect(self) -> bool: ...
    def disconnect(self) -> None: ...
    @property
    def is_connected(self) -> bool: ...
    def read(self, timeout_ms: int = 50) -> CodeResult | None: ...   # None = нет кода
    def trigger(self) -> bool: ...        # наладочный; может оказаться неподдержанным
    def get_status(self) -> dict: ...
```
`CodeResult` — `@dataclass(frozen=True)`: `code: str`, `symbology: str`, `ts: float`, `quality: str`, `raw: bytes`.

**Про `trigger()` — осторожно.** Сетевого триггера в мануале серии **не найдено**: подтверждены только аппаратный DI и кнопка «Execute» в клиенте. Поэтому `trigger()` реализуется на `sim` (там он честный), а в `tcp` — **только если Ф0 п.5 нашла команду**; иначе `tcp.trigger()` возвращает `False` и пишет в статус «не поддержано этим каналом». Строка команды берётся из конфига, в коде не зашивается.

**Files:** 1) `__init__.py` 2) `backends/base.py` 3) `backends/__init__.py` — `create_backend(kind, **kw)`, `READER_TYPES = ("sim","tcp")`, `DEFAULT_READER_TYPE = "sim"` 4) `backends/sim.py` — режимы `free_run`/`triggered`, коды из списка/файла, доля «no read» 5) `backends/tcp.py` — `socket`, оба направления (камера умеет и Server, и Client), настраиваемый терминатор, неблокирующее чтение с буфером 6) `sim_server.py` — CLI `python -m Plugins.sources.code_reader.sim_server --port 5055 --mode triggered|free_run --interval 2.0` 7) `README.md`
**Acceptance criteria:**
- [ ] `create_backend("sim", codes=["A","B"])` → `read()` отдаёт `A`, потом `B`, между ними `None`.
- [ ] Режим `triggered`: без `trigger()` `read()` всегда `None`; после одного `trigger()` — ровно один код, не поток.
- [ ] Кадрированность: два кода в одном TCP-сегменте → два `CodeResult`; код, разорванный на два сегмента → один.
- [ ] `read(timeout_ms=50)` возвращает управление за < 150 мс, когда данных нет.
- [ ] Сервер убит на ходу → `is_connected` False, следующий `connect()` поднимает заново, процесс жив.
- [ ] `trigger()` при оборванном соединении → False, без исключения и без зависания.
- [ ] Если сетевой триггер не поддержан — `tcp.trigger()` → False **и** внятный статус, а не тихое «ок».
- [ ] `isinstance(create_backend("tcp", ...), CodeReaderBackend)` — True.
**Инъекции (лид, не делегируется):** снять срезание терминатора → падает тест кадрированности; сделать `read()` блокирующим → падает тест таймаута; убрать буфер склейки → падает тест разорванного сегмента; заставить `triggered` отдавать код без `trigger()` → падает тест режима, и только он.
**Out of scope:** плагин, рецепт, SDK, serial, Modbus, кадр.

- [ ] Записано, как имя файла связано со срабатыванием (или что не связано — тогда корреляция невозможна и задача закрывается).

  - **Режим «адаптер».** `summarize_plan(paths)` восстанавливает аргументы `analyze_plan` из `paths`: есть `plan.md` → `main` = он, `plan_dir` = его каталог; один файл вне `tasks/` → `main` = он, `plan_dir` = `None`; иначе `plan_dir` = общий каталог, `main` = `plan_dir/plan.md` (может не существовать). Пустой `paths` → `PlanSummary(0, 0, None)`. Отображение полей:
    - `done` = `plan.done`; `total` = `len(plan.tasks)` (ledger считает в `total` и снятые, и без статуса); `dropped` = `plan.dropped`; `unknown` = `plan.unknown`; `counted` (свойство) тогда равно `plan.total`.
    - `open_tasks` = id задач со статусом не `done` и не из снятых, в порядке `plan.tasks`.
    - `phase` — фаза первой задачи из `open_tasks`, найденная прежним кодом ledger (пункт раздела порядка → `item.phase`; иначе заголовок `## Phase N`/файл `phase-N.md`); не найдена → `None`. Фаза — подпись, не счёт; второго разбора набора и статусов это не создаёт.
  - **Гейты не трогаются:** `contract.lock`, `approve`, `amend`, `check_plan_sizes`, `check_plan_gate`. Они берут `summarize_plan(...).total`, в режиме «адаптер» число может измениться; `contract.lock` в репозитории нет (замер 1.0) — перепроверить числом в итоге.
  - **Характеризационные тесты ledger — в обоих режимах.** Сейчас фикстуры в `tmp_path` не содержат `scripts/plans_progress`, поэтому каждый тест ledger проверяет только прежний режим. Фикстура `make_root` получает параметр «с парсером» (копия настоящего `plans_progress.py` в `<tmp>/scripts/plans_progress/`); тесты ledger, которые считают задачи, гоняются в обоих режимах. Тест, ожидание которого в режиме «адаптер» иное, — находка: в итоге задачи строка «тест → прежнее → новое → почему» и решение лида, какой ответ верен.
  - **Что не меняется:** CLI, формат `status`/`status --json`, ключи `PlanSummary`, `plans_progress.py` (парсер не трогаем; нашли в нём ошибку — находка лиду, не правка).

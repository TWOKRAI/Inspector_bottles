Главный риск: потолок мерили на одном наборе, а судят на другом

Потолок — бесплатная проверка: есть ли в выводе паспорта адрес, которого ждёт вопрос. Модель при этом не запускается. Если адреса в паспорте нет, агент не возьмёт его из паспорта при любой модели.

  • Половина адресов r1 лежит не в Python. Из 22 ожидаемых адресов 11 находятся в .gitmessage, COMMIT_GUIDE.md, шаблонах .claude/plugins и pyproject.toml. У трёх вопросов из восьми в Python нет ни одного адреса. Паспорт читает только файлы .py.
  • Ещё 3 адреса — модульные константы (STATUSES, NON_GATING_CODES, KNOWN_TRAILERS). ref отвечает на них «not found», карта файла перечисляет только классы и функции. Ещё 3 адреса — строки шапки докстринга. Достижимы 5 адресов из 22.
  • Выборка смещена. Набор r1 собран из пяти задач самого плана Атласа про скрипты и шаблоны. Он не похож на работу в коде фреймворка.

Доказано

В паспорте есть адреса ответов на вопросы «что это, где объявлено, кто наследует» по известному классу. Это свойство вывода, а не поведение агента.

Не доказано

Что агент с паспортом тратит меньше вызовов и токенов, чем с grep. Базы C0 на k0 и на hold-out нет. В опыте 0b агент с готовым эталоном всё равно шёл читать код: 1, 19 и 18 вызовов.

Не закрыто

Найти файл по описанию задачи. Здесь C0 худший: 57 вызовов и 0–1 попадание из 8. Поиск по описанию стоит в плане после суда.

Что видит агент: пропуски паспорта

Самая дорогая ошибка паспорта — когда «не искали» выглядит как «искали, нет». Агент делает вывод и не идёт в код. Каждый пример воспроизведён командой на main.

Импорт через __init__.py

ref RouterManager пишет «из продукта 2, из тестов 158». Создание в продукте есть: process_managers.py:356. У ProcessModule в списке нет подкласса ProcessManagerProcess. Импорт идёт через фасад модуля, и запись пропадает молча. Для map это исправлено в задаче 4.2b-2, для ref нет.

Команды

map process_module печатает «commands: —». Сканер ждёт функцию command_specs, а таких функций в коде нет ни одной. В builtin_commands.py 13 вызовов register_command.

Потоки

map worker_module печатает «threads: —». worker_lifecycle.py создаёт threading.Thread в трёх местах. Сканер видит поток, только когда создание и .start() стоят в одной функции.

Вызовы метода

ref IRemoteExecutable.execute_remote пишет «найдено 0» и «call_sites_unresolved: 3». Эти три места индексу известны, и они — ответ на вопрос hold-out. Печатается только счётчик. В коде продукта 57 % вызовов идут через атрибут.

Срез

ref ProcessModule занимает 69 строк при бюджете 40: члены класса не режутся. В разделе «кто использует» из 48 записей остаётся одна, и это файл тестов.

Первая команда

atlas ref ProcessModule без --format passport отвечает «module not found». Цель плана записана командой без этого флага.

В Kill-2 план считает только ложные строки паспорта. Пропуски не считает никто. Все 15 находок с командами: docs/reports/2026-11-10_cto-atlas-system-review-passport-output.md.

Что сделано хорошо. Кэш хранит разбор по содержимому файла, поэтому новая ревизия при готовой базе стоит 1,1 с. Холодный запуск 19 с случается после правки сканера и в каждом новом рабочем дереве.

Лучше ли новый Атлас старого

Да, по конструкции. По пользе для агента пока ничья: не доказана ни старая идея, ни новая.

Лучше и проверено запуском

Истина берётся из кода, а не из рукописных списков: старый pack для задачи 4.3 предлагает 27 файлов не из того каталога. Скорость: card process_module 10,7 с против map process_module 1,0 с. Адрес: символ и файл со строкой вместо модуля. Есть бесплатная проверка потолка и остановка до кода.

Не доказано у обоих

Старый план на замере K0c получил «не различимо». У нового прогонов с атласом ещё не было. Главное мерило — тратит ли агент меньше — не закрыто ни там, ни там.

Что старый умел, а новый теряет

Старая карточка считала всех импортёров модуля (426 файлов у process_module) и писала, чего не видит. Новый ref ProcessModule пишет «из продукта 8» без оговорки про фасад. Рабочий контекст (открытые задачи по модулю, коммиты) в паспорт не входит по решению плана.

Баги и костыли в коде: итог охоты

Два ревьюера прошли код атласа с воспроизведением: 28 находок. Пять главных из верхнего слоя перепроверены запуском на main; находки нижнего слоя воспроизведены ревьюером на временных репозиториях.

Паспорт приписывает связи

Если параметр функции назван так же, как функция рядом, вызов параметра отнесён к этой функции. На main из 73 562 отнесённых вызовов ложны не меньше 709, из них 2 в продукте. Это единственный класс находок, который бьёт по критерию «ложных не больше одной».

Падение вместо работы без кэша

Каталог базы только для чтения, обрезанный файл базы или путь не в UTF-8 — и любая команда падает с трассировкой. Кэш объявлен оптимизацией, но без него атлас недоступен.

Стенды считаются продуктом

У ref GenericProcess первая запись «кто использует» — скрипт из docs/reports, и он входит в «из продукта 6». В docs и plans таких файлов 62.

Ввод принимается молча

--exclude без --format не действует, код 0. --budget -5 принят. ref main --budget 5 печатает 206 строк кандидатов. map ./путь.py отвечает «not found».

Неверные строки паспорта

all: — для имени, которое есть в __all__ своего файла. При двух объявлениях одного имени показано первое. doc_missing нет, когда файла README нет в дереве.

Цена

Холодный скан 17,7 с, из них 12 с — три обхода AST. С пулом из 8 процессов 2,3 с (сверено на 300 файлах из 4 373). На каждый id в ref — около трёх лишних запусков git.

Что чисто. Арифметика среза на 200 000 случайных наборов, побайтный детерминизм вывода, шесть одновременных процессов на холодной базе, обрыв посреди записи, разбор всех проверенных форм кода. Все находки с местом в коде и правкой: docs/reports/2026-11-10_cto-atlas-code-bugs.md.

  • Исполнитель почти не ошибается при ясной спеке: 5 дефектов из 83. Дефектов самой спеки 43.
  • Проза не сходится. Три раунда stage 0 по задаче 4.2b-2 дали 14, 13 и 11 находок. Главный вид находки — недостающий случай (54 из 123), а не номера строк (7).
  • Расхождение с реальным деревом ловит тот, кто запускает на реальном дереве: 12 раз ревьюеры stage 0 с прототипом и 2 раза opus в самом конце.

Какую систему предлагаю

Новых больших частей нет. Остаётся то, что уже построено; чинится то, что врёт или молчит; соседние инструменты подключаются рядом и сравниваются замером, а не встраиваются.

Меньше вызовов на вопрос

Строка паспорта говорит одно из трёх: найдено, искали и нет, не видно. Агент не тратит вызовы на проверку ложного «нет» и не уходит с неверным выводом. В срезе первым идёт то, что нужно для решения: продукт, а не тесты.

Дешевле в работе

Кэш ключуется содержимым файла, поэтому одна база может служить всем рабочим деревьям репозитория: сейчас их 7 и 312 МБ, и каждое новое дерево платит 19 с. Холодный скан с пулом процессов — около 2,3 с вместо 17,7 (по замеру ревьюера на части дерева).

Дешевле в разработке

Форму вывода задают эталоны на реальном дереве, а лид читает вывод глазами агента до тестов. Это заменяет третий раунд ревью прозы и ловит то, что сейчас всплывает только в конце. Расход пишется в итог задачи.

Что предлагаю и что нужно решить вам

Вариант 2: цель плана меняется на «найти место по описанию задачи». Тогда r1 судит верно, но до суда нужны поиск по описанию, константы и файлы не на Python.

# Task 1.9b — факт, «Почему так», интерфейс для `gui-graceful-close`, риски механизма

> Вынесено из [`T1.9b.md`](T1.9b.md) 2026-10-25 (бюджет размера документа).

## Факт (код `ee3174515`; строки — `process_manager_module/process/process_manager_process.py`, если не указано иное)
- Все команды PM исполняются синхронно на `message_processor` внутри `router_manager.receive()`: прямая дверь —
  `RouterManager._dispatch_command`; вложенная — `process.command` (`_handle_process_command`, :3292-3372).
- Ожидание стопа (`stop_process` :3722 → `ChildProcessStop.join_until`) держит поток до `stop_process_timeout` + 2,0 = 7,0 с.
  Проба P1: вторая команда на +1,0 с исполнена на +5,09 с. backend_ctl ждёт ответ 5 с (`socket_bridge_adapter.py:51`),
  relay GUI (`command_sender.py:97-110`) стоит всё ожидание.
- Неявная сериализация: рестарт супервизора идёт командой `process.restart` в свою очередь (`monitor/process_monitor.py:
  1476-1481`); `recipe.activate` (`multiprocess_prototype/orchestrator.py:78-83`) зовёт `_cmd_topology_apply` синхронно
  (`recipe/service.py:356`).
- Гонка, которую вынос создаёт (investigator): `process.relay` в перезапускаемого ребёнка ляжет в переиспользуемую очередь
  и будет вычерпан `_drain_process_queues` (:3774) — сегодня relay ждёт конца рестарта и доходит.


## Почему так

- Граница «сам / отдать» — свойство обработчика («ждёт другой процесс»), не вид почты ([1.9a](T1.9a.md), «Почему так»).
  Одна последовательная очередь, а не FIFO на ребёнка: `topology.apply` трогает многих.
- Развилка T — в адаптере: `CommandManager` отказывает `executor=` вместе с `manages_own_reply` (`command_manager.py:
  306-307`), без `executor=` роутер не передаёт `reply`.


## Интерфейс для `gui-graceful-close` (что 1.9b оставляет)

- `supervision.status` — класс R: отвечает весь одиночный стоп (I4), от исполнителя не зависит; если план GUI продлит жизнь
  `message_processor` и сокета на фазу детей, ответ пригоден как ход остановки без правок 1.9b.
- `_ChildrenStop.request_stop()` зовёт `request_stop()` исполнителя, `_ChildrenStop.join_until` — его `join_until` (не
  закрытие `workers`): перестановка `workers`/`children`/`transport` в корне PM (их задача) не меняет порядка «FIFO →
  дети».
- Отказы очереди (`system_stopping`) уходят через `reply_to_request` до закрытия `transport` (ADR-PMM-036) — при
  перестановке порядок «отказы → сокет» обязан сохраниться (их Acceptance).


## Риски (механизм)

- **Ожидающее действие гейта** занимает рабочего до 15–30 с и стопа не видит. В 1.9b гейт не меняется (daemon-поток
  `ready-gate-<имя>`); риск возникает при переходе гейта на исполнитель — [1.9c](T1.9c.md) (hazard `_WorkersStop`).
- **I1 условен.** При `join_until=False` у исполнителя (операция в непрерываемом участке: `process.start()`,
  `apply_priority`, `remove_process`, `_wait_started_ready`, `_resume_monitor`) второй владелец стопа возможен: ERROR в
  лог, стоп детей всё равно. Условие записано в ADR-PMM-039; безусловным I1 не называть.
  - При `False` `_resume_monitor` в `finally` `apply_topology` (PMP:1939-1945) снова запускает монитор во время стопа
    детей; спавна нет (рестарт — командой, `process_monitor.py:1501-1516`, отказ), остаётся шум событий; правка — вместе
    с 1.9c или при регрессе (стадия 0 р.3 п.E).
  - Путь «только стоп раннера» (без `system_stop_event`): `create_and_register` смотрит лишь `system_stop_event`
    (`process_registry.py:298`); операция, прошедшая вход `restart_process` до шага 1 D4, может породить ребёнка. При
    `join_until=True` его заберёт группа (строится после возврата операции), при `False` — сирота. Непрерываемый участок
    в перечень ADR-PMM-039.
- **`_routing_lock` листовой.** Регресс — любой вызов IPC, сна или ожидания под ним: читатели R (`supervision.status`)
  снова встанут на весь стоп. Стражи — H3 (лок свободен, пока исполнитель ждёт ребёнка) и H7 (читатели R при
  `topology.apply`); инъекция И7.
- **Снимки R-читателей** (`list(d.items())`) атомарны под GIL CPython 3.12 только для словарей со строковыми ключами;
  смена модели исполнения Python или нестроковые ключи — пересмотр D3.

**Out of scope / НЕ делать:**
- Правка корня PM (`message_processor` и сокет переживают фазу детей системного стопа, CTO D4) — план `gui-graceful-close`.
- `_run_when_child_ready` / `_drain_child_actions` поверх исполнителя, `max_workers`/`max_pending` гейта, правки тестов
  ADR-PMM-024 — [Task 1.9c](T1.9c.md).
- `_wait_processes_ready` и `apply_priority` (`core/process_priority.py:144`) — только местом исполнения: вызовы из команд
  (restart :3811, switch :4261, start/create :616/:3684/:3693/:3804/:4361) идут на потоке исполнителя;
  `_wait_processes_ready` получает лишь опрос `should_abort` (D4). Вызовы загрузки (`_wait_boot_ready` :4220, boot-deps
  :3437, `apply_priority` :3463) — вне объёма (до приёма команд); ребёнок с `request()` к PM до готовности → `OPEN_QUESTIONS.md`.
- Ожидания внутри Services/Plugins (`service_module/host.py:150`, `chain_module/...`) — внутрипроцессные, не трогать.
- (в) как политика `request()` (отвергнута CTO D2); Task 3.1 (quiesce → ack) — по триггерам Ф2.
- FIFO на каждого ребёнка; сужение `targets="all"` у `topology.apply` до diff — после замера.
- Таймаут ответа backend_ctl (5 с) — не менять; стоп дольше 5 с остаётся таймаутом на стороне driver.
- `Services/device_hub/**`, `Plugins/hub/**` (Р2), возврат робота домой (T5.3e).

## DESIGN

Один предикат, пять точек проверки, один путь стопа. Новый путь стопа **не** заводится: прерванный подъём гасится тем же
`stop()` → `root.cancel()` → `close_root()` в `finally` раннера, что и warm.

### D1 Предикат (`app_module/orchestrator.py`, класс `GenericProcessManagerApp`)

```python
def boot_stop_requested(self) -> bool:
    """Стоп уже взведён: свой ``stop_event`` или системный стоп (в том числе начатый стоп детей).

    Для точек прерывания подъёма (C-82). Читается мягко: PM из тестов может не иметь атрибутов."""
```

Тело: `ev = getattr(self, "stop_event", None)`; `True`, если `ev is not None and ev.is_set()`; иначе
`self._pm_stopping()` (`process_manager_process.py:531-538`; читает `_system_stop_event` мягко). Нового лока нет: чтение
`Event.is_set()`. *Почему оба события:* `system.shutdown` ставит оба (`:823-825`); стоп от лаунчера (Ctrl+C, сигнал)
ставит только `system_stop_event`; одиночный `stop_event` PM ставит только `system.shutdown`. *Почему публичный:* хук
прототипа и тестер обращаются к нему; приватный `_pm_stopping` прототипу не отдаём.

Литералы строк лога — для hazard-тестов автора; приёмка тестера на них не опирается.

**Почему не внутри `app_discover` (P3).** «Внутри» = протянуть предикат в `PluginRegistry.discover`
(`process_module/plugins/registry.py`, публичный API другого модуля, вне FILES). Цена ниже пользы: дорогое внутри —
`import` модулей плагинов и загрузка DLL SDK, а импорт из Python не прерывается; проверка между плагинами сэкономит
только остаток списка. Плюс полупустой глобальный реестр плагинов в PM. Поэтому P2 + P4 вокруг. Хвост P3 (стоп пришёл,
когда `discover` уже идёт) остаётся и меряется в S5b; если он выше порога — это вход решения 3 владельца (ленивый
`discover`), не этой задачи.

**`initialize()` при прерывании возвращает `True`, не `False`.** `False` даёт в раннере `Process initialization failed`
и состояние `error` (`process_runner.py:416-419`) — ложь: подъём не провалился, его отменили. `True` + P6 ведёт по
обычному пути стопа. Повторный `initialize()` (`orchestrator.py:71-72`, корень уже открыт) — без изменений.

**Порядок в `orchestrator.py`** (вместо `:75-77`):

```python
if self.boot_stop_requested():
    self._log_info("стоп во время подъёма — _configure_runtime и observability-watcher пропущены")
    return True
self._configure_runtime()
if self.boot_stop_requested():
    self._log_info("стоп во время подъёма — observability-watcher пропущен")
    return True
self._start_observability_watcher()
return True
```

**Хук (`orchestrator_hooks.py`).** В начале тела: `stopping = getattr(orchestrator, "boot_stop_requested", None)`;
проверка — `callable(stopping) and stopping()` (оркестратор без метода — старое поведение; тесты собирают фейки). Ранний
выход при `sys_config` отсутствует (`:40-45`) — как был. P2 и P4 — по таблице; больше ничего в хуке не меняется.

**Раннер (`process_runner.py`, `_run_lifecycle`)** — перед `if hasattr(process_instance, "run")`:

```python
own = stop_event is not None and stop_event.is_set()
system = system_stop_event is not None and system_stop_event.is_set()
if own or system:
    log.info("Stop signal received before run() — run() skipped" + (" (system-wide)" if system and not own else ""))
    if hasattr(process_instance, "stop"):
        process_instance.stop()
    return
```

`stop()` зовётся, а не пропускается: `ProcessModule.stop()` (`process_module.py:1398-1410`) ставит статус STOPPING и
`root.cancel()` — тот же шаг, что в warm (`:196-197`). Дальше `finally` раннера (`:471-483`) — `close_root()`, отчёт
корня, отпуск очередей, выход 76 при выживших — **без изменений**.

### D3 Что делает уже взведённый стоп в раннере

- **`outcome` стопа (1.10).** Прерванный подъём не заводит своего стопа детей: `stop()` → `root.cancel()` → фаза 1
  области `work/children` → `_ChildrenStop.request_stop()` (`process_manager_process.py:4671-4694`: флаг
  `_children_stopping`, снятие очереди исполнителя, пауза монитора, `children_stop(mark_reader_gone=True)`) → группа
  корня `_ChildrenGroupStop` со сроком `pm_graceful_s`, `terminate`/`kill` по ADR-PMM-036/038, окна по имени (1.11).
  Итог по ребёнку честный ровно в той мере, в какой он честен в warm: ребёнок вышел сам — `exitcode` 0 и без сигнала;
  `terminated`/`killed` — строки группы; выжившие — строка `survivors after root close` и выход PM 76. `outcomes()` у
  `_ChildrenGroupStop` — открытый пункт 1.10, здесь **не** добавляется (Out of scope).
- **Осиротевшие дети.** К моменту P1 PM уже породил **всех** детей boot-конфига: `_create_processes_from_config`
  (`:307`, тело `:3595-3642`) идёт в `initialize()` до `_configure_runtime`, монитор стартует на `:309`. Каждый ребёнок
  регистрируется в реестре до `process.start()` (`_boot_create_and_start`, `:3650-3654`), `_ChildrenStop` читает реестр
  поздно, в фазе 1. Поэтому группа корня видит всех порождённых. После взведения системного стопа новые дети не
  рождаются (P0). Гонки «порождение ↔ сборка группы» нет: `system.shutdown` не отменяет корень, он только взводит
  события; порождение и `stop()` идут на одном главном потоке строго друг за другом. На Windows Job Object лаунчера
  снёс бы сироту молча (`spawner.py:250`) — поэтому «нет сирот» проверяется моментом выхода каждого ребёнка **до**
  выхода PM, а не «жив ли после».
- **Дедлоки.** `system.shutdown` исполняется на `message_processor`, подъём — на главном потоке: друг друга не ждут.
  `stop()` с главного потока блокирует в фазе 1 не дольше `infra_s` (исполнитель + пауза монитора, общий срок,
  `:4683`); поток исполнителя `is_executor_thread` не совпадает с главным. Источники детей ждут `system_ready_event`
  кусками со стопом (`source_producer.py:250-261`) — то, что PM при прерывании никогда не взведёт готовность, их стоп не
  держит. Лаунчер: `wait_until_ready` возвращает `False` при смерти PM (`system_launcher.py:520-545`, докстринг) —
  ожидание конечное.
- **Повторный `system.shutdown`** во время подъёма: события взводятся повторно (безвредно); `mode=force` ставит срок
  через `_children_stop.set_force_deadline` (`:808-821`) — `_children_stop` существует с `_own_work` в
  `super().initialize()` (`:3807`), первый срок выигрывает. Корень закрывается один раз (`close_root` идемпотентен,
  `process_module.py:403-408`).

## TRAPS

1. **P6 касается каждого процесса.** Ребёнок, у которого плагины (камера, SDK) поднимаются в `initialize()`, при стопе
   до `run()` пропустит `run()`. Урок `feedback_do_shutdown_on_unbooted_plugin_is_a_silent_noop`: `do_shutdown` на
   неподнятом плагине — молчаливый no-op. Если «поднят в `initialize()`, но закрывается только из пути `run()`» —
   ресурс утечёт (камера «занята» на следующем старте). H10 первым; красный по существу → стоп, эскалация.
2. Лог-строки раннера — английские (как `:195`); строки оркестратора и хука — русские (как соседние).
3. `conftest.make_pm` строит PM через `__new__` без `__init__` — предикат читает атрибуты через `getattr`.
4. `GenericProcessManagerApp.initialize()` при открытом корне уходит в `super().initialize()` (`:71-72`) — проверки
   P1/P5 туда не ставить.
5. На Windows `getppid`-сторож детей — no-op (`process_runner.py:163-166`): сирота живёт до Job Object. Проверка сирот —
   по моменту выхода, не по «жив ли после».
6. Стенд и тесты радиуса — только через `machine_gate.sh`; в worktree — основной `.venv`, `PYTHONPATH` = корень
   worktree, без `uv sync`.
7. `StdLoggerFacade`, не stdlib: `caplog` не видит строки процесса; образец захвата — `process_module/tests/test_blueprint_extras.py:164-177`.

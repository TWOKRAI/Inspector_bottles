## Факт (код `a5485097a` = `37235a122` по этим модулям)

- `CommandManager.handle_command(message)` (`command_module/core/command_manager.py:262-317`) — единственный, кто знает
  регистрацию и вызов обработчика (`dispatcher.dispatch(message, key_field="command", data_field="data")`, `:293`);
  метрика длительности — `:287-316`, сегодня меряет исполнение. Своих потоков в `command_module` нет.
- `RouterManager._dispatch_command` (`router_module/core/router_manager.py:1323-1371`): `cm.handle_command(processed)`,
  исключение → `{"status": "error", "reason": str(exc)}`, авто-ответ `reply_to_request(processed, result,
  success=_result_is_success(result))`, если у команды нет `manages_own_reply` (`:1362`).
- Готовое ядро «FIFO на ключ + один поток на занятый ключ» — `_run_when_child_ready` / `_drain_child_actions`
  (`process_manager_process.py:1499-1594`, ADR-PMM-024); не хватает потолка, `reply` ровно раз, `shutdown` + join,
  ключей-множеств, владельца потока. Потоки — `WorkerManager` (`worker_module/core/worker_manager.py:26`, образец —
  `ProcessMonitor`, `process_monitor.py:195`); контракт закрытия — `Stoppable` (`base_manager/interfaces.py:252-304`).

## DESIGN

### D1 Контракт `KeyedExecutor` (`worker_module`, по навыку `module-contract`)

- Протокол `OrderedExecutor` — в `worker_module/interfaces.py`; реализация `KeyedExecutor` — `worker_module/keyed_executor.py`
  (`Stability: lite`); раздел в `worker_module/README.md`. Клиенты (`CommandManager`, PM) знают только протокол.
- `submit(action: Callable[[], Any], key: frozenset[str] | None, reply: Callable[[Any], None]) -> None`.
  - **pre:** исполнитель не закрыт; иначе `reply({"success": False, "error": "system_stopping"})` сразу, на вызывающем потоке.
  - **post:** `reply` зовётся **ровно один раз**: результат `action`; исключение `action` → `{"success": False,
    "error": "<тип>: <текст>"}`; отказ → `system_stopping` / `executor_busy`. Исключение внутри `reply` — `log.error`,
    поток живёт.
  - **Порядок:** операции с пересекающимися ключами или с `key=None` — строго в порядке подачи; с непересекающимися —
    параллельно. Режим `serial=True` (конструктор): все операции — одна очередь, как будто у всех `key=None`.
  - **Никогда не блокирует:** очередь достигла `max_pending` (конструктор; черновик по умолчанию — 64, число предлагает
    стадия 0) → `reply({"success": False, "error": "executor_busy"})` + один WARNING на эпизод.
  - `submit` с потока самого исполнителя (операция, подающая операцию) — исполняется на месте, без дедлока.
- `shutdown(deadline: float) -> bool` (`deadline` — `time.monotonic()`), идемпотентен, по контракту `Stoppable`:
  `request_stop()` — отказ всей очереди (`system_stopping` каждому), новые `submit` — отказ; `join_until(deadline)` —
  ждать текущие операции. Не вернулись к сроку → `False` + WARNING с именем операции. Как текущая операция возвращается
  досрочно — дело её `action` (опрос события у потребителя, в PM — `should_abort`, 1.9b D4).
- Конструктор: `name`, `max_pending`, `serial`, `max_workers` (для `serial=False`), `should_reject: Callable[[], bool] |
  None` (проверка перед каждой операцией; `True` → отказ очереди — так потребитель снимает очередь до `shutdown`), `log`.

### D2 Устройство: обобщение `_run_when_child_ready`, не второй механизм

- Ядро — то же, что ADR-PMM-024: `deque` на ключ, один рабочий на занятый ключ, опустошение очереди и снятие флага
  «занят» — под одним локом (без потерянного пробуждения). Обобщения: ключ — множество (операция ждёт все раньше
  поданные пересекающиеся; `None` пересекается со всеми), потолок, `reply` ровно раз, отказ очереди.
- Особенности PM (ожидание `ready_event`, `still_relevant`, перечитывание инкарнации) в исполнитель **не переносятся** —
  остаются внутри `action`, которую строит PM (1.9b D5).
- Потоки — через `WorkerManager` (именованные `keyed-<name>-<n>`, daemon, stop_event), не голый `threading.Thread`.
- Лок исполнителя не держится поверх `action` и `reply` (H7).

### D3 Развилка в `CommandManager` (`command_module`, только расширение)

- `register_command(..., executor: OrderedExecutor | None = None, key_from: str | None = None, targets: str | None = None)`
  — новые необязательные kwarg, прежние аргументы и умолчания не меняются. Объект исполнителя — в отдельном реестре
  записи команды, **вне `metadata`** (метаданные уходят в `introspect.capabilities` — Dict at Boundary). В `metadata`
  кладутся только строки: `executor` (имя исполнителя), `key_from`, `targets` — их видно в контактной книжке.
- Ключ извлекает приёмник: `targets="all"` → `key=None`; `key_from="process_name"` → `frozenset({data["process_name"]})`.
  Отправители не меняются.
- `handle_command(message, *, reply: Callable[[Any], None] | None = None)`:
  - у команды нет исполнителя → как сегодня (синхронно, на вызывающем потоке);
  - есть исполнитель и `reply` → `action` = вызов `dispatcher.dispatch(...)` **внутри** обёртки, которая ловит
    исключение (`{"status": "error", "reason": str(exc)}` — тот же конверт, что у роутера) и пишет метрику длительности
    **после исполнения** (риск (б) CTO); `executor.submit(action, key, reply)`; возврат — сентинел `DEFERRED`
    (экспорт `command_module`);
  - есть исполнитель, нет поля ключа → громкий отказ сразу: `{"success": False, "error": "key_missing", "command": ...}`
    + WARNING, без `submit` (`None` — только через `targets="all"`);
  - есть исполнитель, `reply` не передан (консоль, тесты CM, вложенные вызовы) → исполнение на месте + один WARNING на
    имя команды; **без `reply` никогда не `DEFERRED`** (риск (а) CTO, страж R8).
- `manages_own_reply` не трогать (риск (г)): у такой команды с исполнителем роутер передаёт `reply`-no-op.

### D4 Роутер — ~5 строк в `RouterManager._dispatch_command`

- Построить `reply = lambda r: self.reply_to_request(processed, r, success=_result_is_success(r))` (для
  `manages_own_reply` — no-op), звать `cm.handle_command(processed, reply=reply)`; `result is DEFERRED` → выйти до
  авто-ответа. Остальное в `router_manager.py` не трогать.
- Middleware приёма идёт до развилки (`router_manager.py:1451`): `receive_time` = снятие трубки, не конец исполнения —
  записать в ADR (риск (в)).
- Подделки CM в тестах роутера без kwarg `reply` — опись стадии 0; правка подделки — только с разрешения лида.
- Вариант «развилка в роутере» (D2 прежнего T1.9) — **отвергнут, решение владельца 2026-10-20.**

## Почему так

- Граница «сам / отдать» — свойство обработчика «ждёт другой процесс / не ждёт», не вид почты: роли-потоки по видам почты
  CTO отверг замером (под GIL один занятый поток: p99 снятия трубки 10 → 31 мс, два потока → 190 мс; проба
  [`cto_probe_dept.py.txt`](../../../docs/reports/2026-10-20_L-9-residual-evidence/cto_probe_dept.py.txt)).
- Развилка в `CommandManager`, а не в роутере: только он знает регистрацию; роутер остаётся транспортом (CTO р.2).

## REDS — слепой тестер

Файлы: `worker_module/tests/test_keyed_executor_acceptance.py` (R1–R6), `command_module/tests/test_command_executor_fork_acceptance.py`
(R7–R10). Каждый ждущий вызов — в daemon-потоке с дедлайном join; ожидания — литералы.
- R1 `test_overlapping_keys_run_in_submit_order` — `{a}`, `{a,b}`, `{b}` поданы подряд, каждая 0,2 с: порядок
  завершения — подачи; `None` ждёт все раньше поданные.
- R2 `test_disjoint_keys_run_in_parallel` — `{a}` и `{b}` по 0,5 с при `serial=False`: обе кончились за ≤ 0,8 с.
- R3 `test_serial_mode_orders_disjoint_keys` — то же при `serial=True`: ≥ 1,0 с, порядок подачи.
- R4 `test_reply_called_exactly_once_on_every_branch` — результат, исключение (`{"success": False, "error":
  "ValueError: x"}`), отказ: счётчик вызовов `reply` = 1 в каждом случае.
- R5 `test_shutdown_rejects_queue_and_later_submits` — 3 ждущих + `shutdown`: каждому `{"success": False, "error":
  "system_stopping"}`; `submit` после — тот же отказ на вызывающем потоке.
- R6 `test_submit_never_blocks_refuses_at_ceiling` (бывш. R11 T1.9) — исполнитель занят 1 с, очередь на `max_pending`:
  следующий `submit` возвращается ≤ 10 мс, `reply` — `{"success": False, "error": "executor_busy"}` ровно раз.
- R7 `test_deferred_command_gets_one_reply_same_envelope` — команда с исполнителем через настоящий `RouterManager` +
  `CommandManager`: ровно один ответ, тот же конверт и `success`, что у той же команды без исполнителя.
- R8 `test_handle_command_without_reply_never_returns_deferred` — команда с исполнителем, вызов без `reply`: результат —
  dict обработчика, не `DEFERRED`; WARNING один на имя за 3 вызова.
- R9 `test_missing_key_field_is_refused_loudly` — `key_from="process_name"`, поля нет: `{"success": False, "error":
  "key_missing", ...}`, обработчик не вызван.
- R10 `test_command_without_executor_runs_on_receive_thread_as_before` (бывш. R12 T1.9) — регистрация без новых аргументов:
  исполнение на потоке `receive()`, авто-ответ прежней формы (страж, зелёный и до, и после).

**Hazard-тесты автора (H1–H7, `test_keyed_executor_hazards.py` и `command_module/tests/`):** H1 `submit` с потока
исполнителя — на месте, без дедлока (дедлайн 2 с); H2 `shutdown` с застрявшей операцией → `False` + WARNING не позже
срока + 0,1 с; H3 метрика длительности ≥ 0,3 с у операции 0,3 с (меряет исполнение, не подачу); H4 исключение в
обработчике отложенной команды → конверт `{"status": "error", "reason": ...}`, как у синхронной; H5 исключение в `reply` —
лог, следующая операция исполняется; H6 (бывш. H7 T1.9) p99 «снятия трубки» (от `put` до входа в обработчик команды без
исполнителя) ≤ 20 мс на 200 командах, пока исполнитель 1 с занят; H7 лок исполнителя свободен во время `action`.

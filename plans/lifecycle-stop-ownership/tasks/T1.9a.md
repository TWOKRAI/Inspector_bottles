## DESIGN

### D1 Контракт `KeyedExecutor` (`worker_module`, по навыку `module-contract`)

- Протокол `OrderedExecutor` — в `worker_module/interfaces.py`; реализация `KeyedExecutor` — `worker_module/keyed_executor.py`
  (`Stability: lite`); раздел в `worker_module/README.md`. Клиенты (`CommandManager`, PM) знают только протокол.
  `KeyedExecutor` реализует `Stoppable` — иначе 1.9b не отдаст его во владение `Scope` (`lifetime.py:361`).
- Конструктор: `KeyedExecutor(name, *, worker_manager, max_pending=64, serial=False, max_workers=4, should_reject=None, log=None)`.
  - `worker_manager` — обязателен: потоки только через `WorkerManager` (CTO р.2), иначе их некуда подключить.
  - `max_pending=64` — потолок очереди ниже потолка транспорта (system-очередь процесса `maxsize: 100`,
    `process_manager_process.py:66`, `process_launch_config.py:15`); худший всплеск PM (start-all/restart-all на 8 процессах
    × start + relay + telemetry ≈ 24, плюс `topology.apply` / `wire.*`) < 32 — запас ×2. Расчёт — в ADR.
  - `max_workers=4` (при `serial=True` игнорируется, рабочий один): R2 нужен ≥ 2; рабочие ждут на `Condition` и CPU не
    берут. 4 — только умолчание: 1.9b задаёт `max_workers` для `_ready_gate_executor` явно, не меньше числа детей
    (сегодня у каждого неготового ребёнка свой поток, ADR-PMM-024).
  - `log: logging.Logger | None` — `None` → `logging.getLogger("multiprocess_framework.worker_module.keyed_executor.<name>")`;
    все WARNING/ERROR — через `.warning` / `.error` этого логгера (тестер ловит их `caplog`).
  - Пул создаётся в конструкторе: `max_workers` (или 1) постоянных воркеров `keyed-<name>-<i>` через
    `worker_manager.create_worker` с `ThreadConfig(worker_type=SYSTEM, restart_on_failure=False, execution_mode=LOOP)` —
    SYSTEM, чтобы `pause_all` и GUI worker CRUD их не останавливали. Воркеры не создаются и не удаляются на каждый эпизод
    (имя уникально, STOPPED остаётся в реестре — `worker_lifecycle.py:62-63, 247-250`). После конструктора исполнитель
    готов, отдельного `start()` нет. Цель воркера — `target(stop_event, pause_event)` (`worker_lifecycle.py:216`); рабочий
    ждёт `Condition.wait(timeout=0.1)` и проверяет `stop_event`; взведён → исполнитель делает `request_stop()`, вся очередь
    получает `system_stopping` (иначе `stop_all_workers`, `worker_manager.py:228-253`, ждал бы поток до 5 с, а очередь
    осталась бы без ответа). Воркеры создаются с `auto_start=True`; `create_worker` вернул `False` (имя занято) →
    `ValueError` в конструкторе.
- `submit(action: Callable[[], Any], key: frozenset[str] | None, reply: Callable[[Any], None], *, inline_if_idle: bool = False) -> bool`.
  - Возврат: `True` — поставлено в очередь; `False` — `reply` уже вызван на вызывающем потоке (исполнено на месте или отказ).
  - **pre:** исполнитель не закрыт и `should_reject()` не `True`; иначе `reply({"success": False, "error": "system_stopping"})`
    сразу, на вызывающем потоке, возврат `False`.
  - **post:** `reply` зовётся **ровно один раз**: результат `action`; исключение `action` → `{"success": False,
    "error": "<тип>: <текст>"}`; отказ → `system_stopping` / `executor_busy`. Исключение внутри `reply` — `log.error`, рабочий
    живёт; на вызывающем потоке — `log.error`, `submit` возвращается штатно.
  - **Порядок:** операции с пересекающимися ключами — строго в порядке подачи; с непересекающимися — параллельно. `key=None`
    значит «все ключи»: пересекается со всеми, в том числе с ключами, которых ещё нет ни в одной операции. Режим `serial=True`
    ≡ один рабочий, все операции в порядке подачи.
  - **Никогда не блокирует:** в очереди уже `max_pending` операций → `reply({"success": False, "error": "executor_busy"})`,
    возврат `False`, один WARNING на эпизод; эпизод кончается, когда очередь опустела.
  - `inline_if_idle=True` (задел тонкой обёртки 1.9b над `_run_when_child_ready`, `:1586-1600`): если под локом ключ не
    пересекается ни с исполняемыми, ни с ждущими операциями — ключ помечается занятым, `action` и `reply` исполняются на
    вызывающем потоке, возврат `False`; иначе обычная постановка, `True`. Решение «свободен → на месте» принимается под
    одним локом (без гонки «проверил, потом сделал»). Ключ, исполняемый на месте, учитывается в `running`; снятие — под
    локом в `finally` с `notify_all()` (иначе рабочие, ждущие тот же ключ, не проснутся). При `serial=True` на месте —
    только если `running` и `pending` пусты.
  - **Повторный вход** (`submit` с потока рабочего этого исполнителя): на месте — только если `key ⊆` ключа текущей операции
    этого рабочего (при `serial=True` — всегда); иначе обычная постановка (`submit` не блокирует — дедлока нет). `action` не
    вправе ждать `reply` вложенной операции. Вложенная с `key ⊆` считается частью родителя (родитель подан раньше ждущих);
    с ключом `⊄` — обычная постановка: её ключи не захвачены.
  - `should_reject: Callable[[], bool] | None` — зовётся в `submit` (True → `system_stopping` на вызывающем потоке) и
    рабочим перед взятием каждой операции (True → эта операция и вся очередь получают `system_stopping`). Без защёлки, вне
    лока; исключение в нём → `log.error`, считать `True`. Так потребитель снимает очередь до `shutdown`.
- Закрытие по `Stoppable`: `request_stop()` — идемпотентен; под локом `closed=True` и опустошение очереди, каждой снятой
  операции `system_stopping`; новые `submit` — отказ. `join_until(deadline) -> bool` (`deadline` — `time.monotonic()`) — ждать
  текущие операции и выход рабочих; не вернулись к сроку → `False` + WARNING с именем операции. `shutdown(deadline) -> bool`
  ≡ `request_stop(); return join_until(deadline)`. Как текущая операция возвращается досрочно — дело её `action` (опрос
  события у потребителя, в PM — `should_abort`, 1.9b D4).

### D2 Устройство: обобщение `_run_when_child_ready`, не второй механизм

- Ядро — по ADR-PMM-024 (FIFO, исполнение по ключу, без потерянного пробуждения), но одной «deque на ключ» мало: `None`
  должен задерживать ключи, которых нет ни в одной очереди, а `{a,b}` в голове очереди `a` держал бы рабочего, пока занят
  `b` (при одном рабочем — дедлок). Поэтому структура:
  - одна общая `pending: deque` в порядке подачи + `running: Counter[str]` + флаг `running_all` (исполняется операция `None`);
  - запись исполнима, если её ключ не пересекается с `running`, нет `running_all` и ключ не пересекается с ключами всех
    более ранних записей `pending`; `None` исполнима, только когда ничего не исполняется и впереди никого нет;
  - рабочий под `Condition` берёт первую исполнимую запись; просмотр прекращается, когда накопленное множество ключей
    более ранних записей = «всё». Сложность O(`max_pending`). Дедлока нет — рабочий не ждёт конкретную операцию;
    голодания нет — запись ждёт только более ранние.
- Потерянное пробуждение и `reply` ровно раз: проверка «закрыт» + постановка в `submit`, опустошение + `closed=True` в
  `request_stop` — под одним локом; ожидание — `Condition.wait` в цикле с предикатом; запись переходит QUEUED→TAKEN или
  QUEUED→REJECTED только под локом, `reply` зовёт её владелец после освобождения лока.
- Лок исполнителя не держится поверх `action`, `reply` и `should_reject` (H7).
- Особенности PM (ожидание `ready_event`, `still_relevant`, перечитывание инкарнации) в исполнитель **не переносятся** —
  остаются внутри `action`, которую строит PM (1.9b D5).

### D3 Развилка в `CommandManager` (`command_module`, только расширение)

- `register_command(..., executor: OrderedExecutor | None = None, key_from: str | None = None, targets: str | None = None)`
  — новые необязательные kwarg, прежние аргументы и умолчания не меняются. Объект исполнителя — в отдельном реестре
  записи команды, **вне `metadata`** (`get_handler_info` отдаёт `metadata` по ссылке — `dispatcher.py:657-661`). В `metadata`
  кладутся только строки: `executor` (имя исполнителя), `key_from`, `targets` — их видно через `get_command_info`; вывод в
  карточку `introspect.capabilities` — правка `builtin_commands.py:866-870`, не в 1.9a.
- Регистрация отклоняется (`False` + WARNING, команда не зарегистрирована): `executor` без ровно одного из `key_from` /
  `targets="all"` (оба или ни одного); `targets` вне `{None, "all"}`; `executor` при `metadata.manages_own_reply=True` (no-op `reply` проглотил бы отказы
  `system_stopping` / `executor_busy`, инициатор ждал бы до таймаута; в 1.9b такой связки нет).
- Ключ извлекает приёмник: `targets="all"` → `key=None`; `key_from="process_name"` → `frozenset({data["process_name"]})`.
  `data[key_from]` — непустая `str`; отсутствует, `None`, `""` или не `str` → громкий отказ сразу:
  `{"success": False, "error": "key_missing", "command": <имя>}` + WARNING, без `submit`; текст отказа и WARNING не содержат
  значения поля. Отправители не меняются.
- `handle_command(message, *, reply: Callable[[Any], None] | None = None)` (и `ICommandManager.handle_command` — тот же kwarg):
  - у команды нет исполнителя → как сегодня (синхронно, на вызывающем потоке), `reply` не используется;
  - есть исполнитель и `reply` → `action` = вызов `dispatcher.dispatch(...)` **внутри** обёртки, которая ловит исключение
    (`{"status": "error", "reason": str(exc)}` — тот же конверт, что у роутера) и исполняет весь блок после диспетчеризации
    (`:295-316`: лог ошибки/успеха, метрика длительности) **после исполнения** (риск (б) CTO); `execution.attempts` — при
    подаче; `executor.submit(action, key, reply)`; возврат — сентинел `DEFERRED` (экспорт `command_module`);
  - есть исполнитель, `reply` не передан (консоль `console_adapter.py:66`, тесты CM, вложенные вызовы) → исполнение на
    месте + один WARNING на имя команды с текстом «исполнено вне очереди ключа»; **без `reply` никогда не `DEFERRED`**
    (риск (а) CTO, страж R8). Записать в ADR.
- `overwrite_command` (`:415-445`) снимает запись исполнителя — команда снова синхронная. `update_command_metadata` (`:389`),
  стёршая строку `executor`, ведёт к исполнению на месте + WARNING (роутер не передаст `reply`, D4) — `DEFERRED` не утечёт;
  записать в ADR.

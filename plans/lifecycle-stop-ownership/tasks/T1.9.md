# Task 1.9 — стоп вне `message_processor`: одна FIFO жизненного цикла PM, отложенный ответ (конечное состояние L-9)

> Вынесено из [`plans/lifecycle-stop-ownership.md`](../../lifecycle-stop-ownership.md) 2026-10-20 (размер плана). «Файлы полосы Ф» и «Открытые решения О1–О5» — в плане.

**Статус:** DRAFT 2026-10-20 · **Level:** Senior+ · **Assignee:** стадия 0 — `reviewer` (Opus); тестер — слепой
(Sonnet) в worktree на коммите открытия; реализация — `teamlead` (Opus); инъекции — Haiku; ревью — `reviewer` (Opus)
· **Layer:** framework · **Module contract:** public-api-change (`process_manager_module`: момент ответа команд
жизненного цикла, новый способ регистрации команды жизненного цикла; содержимое ответов прежнее)
**CHAIN:** `reviewer`(стадия 0) → `tester`(RED, worktree) → `teamlead`(GREEN + hazard) → лид (инъекции, стенд) → `reviewer`
**Источник:** [отчёт L-9 остаток](../../../docs/reports/2026-10-20_lifecycle-stop-ownership_L-9-residual_details.md) §4–§7,
[investigator Q5 (б)](../../../docs/reports/2026-10-20_L-9-residual-evidence/investigator_code.md); вердикт CTO §7 D2, D4.
**Goal:** PM не глохнет ни на одну команду, пока ждёт смерти ребёнка: команды жизненного цикла исполняет один поток
FIFO вне `message_processor`, ответ уходит после подтверждённой смерти через обе двери; `system.shutdown` исполняется
сразу и снимает очередь; в каждый момент у стопа ребёнка один владелец.

#### Факт (код `a5485097a`; строки — `process_manager_module/process/process_manager_process.py`, если не указано иное)

- Все команды PM исполняются синхронно на `message_processor` внутри `router_manager.receive()`: прямая дверь —
  `RouterManager._dispatch_command` (`router_module/core/router_manager.py:1323-1371`, авто-ответ, если у команды нет
  `manages_own_reply`); вложенная — обёртка `process.command` (`_handle_process_command`, :3251-3331, сама строит
  `process.command.response` через `reply_to_request`).
- Ожидание стопа (`stop_process` :3681 → `ProcessRegistry._stop_many` → `ChildProcessStop.join_until`) держит поток до
  `stop_process_timeout` + 2,0 = 7,0 с. Проба P1: вторая команда, положенная на +1,0 с, исполнена на +5,09 с.
  backend_ctl ждёт ответ 5 с (`socket_bridge_adapter.py:51`), relay GUI (`command_sender.py:97-110`) стоит всё ожидание.
- Неявная сериализация, на которую опирается код: рестарт супервизора идёт командой `process.restart` в свою очередь
  (`monitor/process_monitor.py:1476-1481`: «рестарт НЕ может бежать параллельно с заменой топологии»);
  `recipe.activate` (регистрирует `multiprocess_prototype/orchestrator.py:78-83`) зовёт `pm._cmd_topology_apply`
  синхронно (`recipe/service.py:356`).
- Механизм отложенного ответа есть: `manages_own_reply` + `reply_to_request` с любого потока (`router_manager.py:1274`,
  самоответ ADR-RTR-013); success конверта — `_result_is_success` (`router_manager.py:108`); прецедент воркера вне
  `message_processor` — `_run_when_child_ready` (:1498-1587).
- Гонка, которую вынос создаёт (investigator): `process.relay` в ребёнка, которого FIFO сейчас перезапускает, ляжет в
  переиспользуемую очередь и будет вычерпан `_drain_process_queues` (`restart_process` :3727-3733) — сегодня relay ждёт
  конца рестарта и доходит.

#### DESIGN

- **D1 Исполнитель отделён интерфейсом от логики PM (лид 2026-10-20: вердикт CTO «отдел вместо одного телефона»
  может сделать 1.9 первым потребителем общего примитива фреймворка — см. О5).** PM зависит только от протокола
  `OrderedExecutor` и не знает, кто его реализует:
  - `submit(action: Callable[[], Any], key: frozenset[str] | None, reply: Callable[[Any], None]) -> None` — `key` —
    цели операции (`None` = вся топология). `reply` зовётся **ровно один раз**: результат `action`; исключение →
    `{"success": False, "error": "<тип>: <текст>"}`; отказ → `{"success": False, "error": "system_stopping"}`.
    Исключение в `reply` — `log.error`, поток живёт.
  - `shutdown(deadline: float) -> bool` (`deadline` — `time.monotonic()`) — идемпотентен: отказ очереди, ожидание
    текущей операции до срока; `False` + WARNING, если не вернулась. `submit` после `shutdown` — `reply(отказ)` сразу
    на вызывающем потоке.
  - Реализация 1.9 — `core/lifecycle_executor.py` (новый, внутренний, `Stability: lite`, из `__init__.py` не
    экспортируется): `LifecycleExecutor(name, should_reject: Callable[[], bool], log)`, один daemon-поток
    `pm-lifecycle`, `deque` под `threading.Condition`; **одна** очередь на все ключи (порядок общий — `topology.apply`
    трогает многих). Перед каждой операцией — `should_reject()`; `True` → отказ всей очереди. `submit` с потока самого
    исполнителя (команда жизненного цикла изнутри другой) — исполняется на месте, без дедлока.
  - Учёт «цель в переходе» — **на стороне PM, не в исполнителе:** обёртка `_submit_lifecycle` PM ведёт под своим локом
    счётчик ключей (`+1` при `submit`, `-1` в `reply`) и отвечает `_in_transition(name)` / `_lifecycle_busy()`. Так
    протокол остаётся двумя методами, и замена реализации общим примитивом CTO не трогает классы D2.
- **D2 Классы команд и двери (`process_manager_process.py`).** Класс задаёт регистрация, не имя в коде двери:
  метаданные команды `lifecycle: True` (+ `lifecycle_targets: "name" | "all"`). Публичный метод PM
  `register_lifecycle_command(name, handler, *, targets: Literal["name", "all"], description)` регистрирует команду с
  `expects_full_message=True`, `manages_own_reply=True`, `lifecycle=True` и обёрткой-входом.
  - **Прямая дверь:** обёртка-вход вынимает `data`, ставит `fn = lambda: handler(data)` в FIFO, `reply` =
    `router_manager.reply_to_request(msg, result, success=_result_is_success(result))` — тот же конверт, что авто-ответ
    сегодня (`_result_is_success` импортировать из `router_module.core.router_manager`; код роутера не трогать).
  - **Вложенная дверь (`process.command`):** до `command_manager.handle_command(inner_msg)` — проверка метаданных
    вложенной команды; команда жизненного цикла → FIFO, `reply` = нынешняя эвристика success (вынести в
    `_process_command_success(result)` без изменения логики) + `reply_to_request(..., response_command=
    "process.command.response")`. Остальные — как сегодня.
  - **Без correlation-id** (GUI fire-and-forget) — `reply_to_request` и сегодня no-op; поведение то же.
  - **Класс L (всегда FIFO):** `process.create`, `process.start`, `process.stop`, `process.restart` (`targets="name"`);
    `topology.apply`, `wire.setup`, `wire.teardown` (`targets="all"`); `recipe.activate` (`targets="all"`, пометка —
    одна строка в `multiprocess_prototype/orchestrator.py`: регистрация `recipe.activate` через
    `register_lifecycle_command`; остальные `recipe.*` — как были). Внутри FIFO `recipe.activate` зовёт
    `_cmd_topology_apply` прямым вызовом — синхронно, на том же потоке, `recipe/service.py` не меняется.
  - **Класс T (адресные, FIFO только если цель в переходе):** `process.relay` (цель — `target_process`),
    `process.pause`, `process.resume` (цель — `process_name`): `_in_transition(цель)` → FIFO (исполнятся после
    перехода, дальше — существующий путь, включая `_run_when_child_ready`), иначе — сразу на `message_processor`.
    `telemetry.broadcast` (fan-out и адресно), `observability.tail.subscribe_all` / `unsubscribe_all`: FIFO, если
    `_lifecycle_busy()`, иначе сразу (журнал телеметрии и намерения брокера доигрываются при рождении — порядок
    относительно рестарта сохраняется как сегодня). Ответ этих команд в FIFO — тоже отложенный, той же дверью.
  - **Класс R (чтение, сразу, без FIFO):** `process.list`, `process.status`, `system.stats`, `supervision.status`,
    `topology.get`, `topology.diff`, `wire.status`, `introspect.*` (включая `capabilities_extra`), `recipe.list/get/
    validate/save/delete`, `service.*`, команды сессий backend_ctl, `state.*`, heartbeat, `state.changed`.
  - **Класс S:** `system.shutdown` — никогда не в FIFO (ни одной дверью): взводит `system_stop_event` и `stop_event`
    сразу, как сегодня (:666-681); исполнитель видит событие через `should_reject` и снимает очередь.
  - Таблица выше — черновик менеджера по чтению; **шаг 0 подтверждает или правит каждую строку**, итог — в
    `docs/maps/pm-lifecycle-commands.md`, строка в плане меняется по нему.
- **D3 Чтение под локом, а не под FIFO.** Один `threading.RLock` PM `_lifecycle_state_lock` (если шаг 0 найдёт
  существующий лок на те же словари — взять его, второго не заводить). Писатели (`_process_configs`, `_incarnations`,
  `_routing_epoch`, словарь проводов, журнал телеметрии, реестр) берут лок только вокруг самой мутации; читатели класса R
  — только вокруг снятия копии (`dict(...)`, `list(...)`). **Лок не держится поверх ожидания, сна, спавна или отправки
  IPC** — иначе `supervision.status` снова глохнет на весь стоп (инъекция И7).
- **D4 Один владелец стопа (I1).** `ChildProcessStop(..., should_abort: Callable[[], bool] | None = None)` —
  `join_until` проверяет его на каждом проходе (шаг `STOP_POLL_S`) и возвращается досрочно: без `terminate`, без метки,
  выжившие не подтверждены; `ProcessRegistry.stop_abort` (атрибут, по умолчанию `None`) → `_build_child_stop`. PM
  ставит `stop_abort = system_stop_event.is_set` для стопов из FIFO. Прерванная операция: `stop_process` → `False`,
  `remove_process`/`create_and_register` не зовутся (последний и так отказывает после системного стопа, Task 1.2),
  ответ — `{"success": False, "process_name": ..., "error": "system_stopping"}`. Тот же опрос — в цикл
  `_wait_processes_ready` (:4065-4123). `_ChildrenStop.request_stop()` (:4338) **первым шагом** зовёт
  `self._lifecycle.shutdown(deadline=now + infra_s)`, затем пауза монитора и `children_stop` — как сегодня. Путь `shutdown()`
  без `stop()` (`_stop_children_once`) — тот же вызов.
- **D5 Заморозка (в), принцип 3.** `RouterManager.pump_inbound`, `ProcessRegistry.stop_wait_idle`,
  `ChildProcessStop(idle=)`, `ProcessManagerProcess._stop_wait_idle` — **не удаляются, не меняются**. Присвоение
  `stop_wait_idle` в PM остаётся: на потоке FIFO `pump_inbound` возвращает 0 (вне `receive`, ADR-RTR-014 pre) — ноль
  затрат; если опись пропустила путь стопа на приёмном потоке, страховка (в) там работает. Запись заморозки:
  - ADR-PMM-037: статус → «superseded by ADR-PMM-038 (2026-10-xx); код FROZEN, не удалять»;
  - ADR-RTR-014: статус → «FROZEN — после ADR-PMM-038 штатные стопы идут вне `receive`, вычерпывание не срабатывает;
    контракт и тесты живы»; докстринг `pump_inbound` — одна строка о том же;
  - `process_manager_module/STATUS.md` и `router_module/STATUS.md`: строка «Замороженный API (принцип 3)» с четырьмя
    именами и ссылкой на ADR-PMM-038; снятие — только решением владельца;
  - тесты, держащие замороженный API живым, **остаются без правок и зелёными**: `router_module/tests/
    test_pump_inbound_acceptance.py`, `test_pump_inbound_hazards.py`, `process_manager_module/tests/
    test_child_stop_idle_acceptance.py`, `test_stop_wait_idle_hazards.py`, `test_pm_stop_drains_own_queue_acceptance.py`
    (R10/R10b/R11 гоняют механизм на приёмном потоке напрямую). Нужна правка любого из них — стоп, эскалация.
- **D6 ADR-PMM-038** «Команды жизненного цикла PM исполняет одна FIFO вне `message_processor`; ответ — после
  подтверждённой смерти» (в `process_manager_module/DECISIONS.md`): решение D1–D5, инварианты I1–I4 как контракт,
  таблица классов (ссылка на `docs/maps/pm-lifecycle-commands.md`), отвергнутое (FIFO на ребёнка — `topology.apply`
  трогает многих; (в) как политика `request()` — CTO D2), предел (backend_ctl ждёт ответ 5 с — стоп дольше 5 с и
  сегодня таймаут), Reversible. ADR-RTR-011 не меняется и становится единственной политикой «приёмный поток не ждёт
  другой процесс». Затем `python -m scripts.sync`.
- **Не менять:** обработчики `_cmd_*` (кроме вынесения эвристики success), `stop_process`, `restart_process`,

#### Интерфейс для `gui-graceful-close` (что 1.9 оставляет)

- `supervision.status` — класс R: отвечает весь одиночный стоп (I4) и не зависит от исполнителя; если план GUI продлит
  жизнь `message_processor` и сокета на фазу детей системного стопа, этот ответ пригоден как ход остановки без правок 1.9.
- `OrderedExecutor.shutdown(deadline)` зовёт `_ChildrenStop.request_stop()`, а не закрытие `workers`: перестановка
  `workers`/`children`/`transport` в корне PM (их задача) не меняет порядка «FIFO → дети».
- Отказы очереди (`system_stopping`) уходят через `reply_to_request` до закрытия `transport` (ADR-PMM-036: сокет
  закрывается после детей) — при их перестановке порядок «отказы → сокет» обязан сохраниться (их Acceptance).

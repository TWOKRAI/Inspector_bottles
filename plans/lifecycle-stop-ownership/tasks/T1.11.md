**Обозначения:** `g` = graceful PM = `stop_budget(shutdown_timeout)["pm_graceful_s"]`; `C` = `max_stop_window_s`
(по умолчанию `g`); `G = max(g, C)`; `w_i` — окно ребёнка после проверки и потолка.

**DESIGN:**
1. **Ключи.** Конфиг процесса `stop_window_s: float` — на верхнем уровне словаря процесса, как `restart_policy`
   (`_process_configs[name]["stop_window_s"]`). Доезжает из рецепта: `ProcessConfig` называет поле и переносит его в
   `as_generic_config` (`_pick`), `ProcessLaunchConfig.build()` кладёт его в proc_dict. Конфиг PM `max_stop_window_s`.
   Имена ключей — константы в `core/stop_budget.py` рядом с `SHUTDOWN_TIMEOUT_KEY` (сторож G6 запрещает строку
   `"shutdown_timeout"` вне `stop_budget.py`; новые ключи — так же). *Почему верхний уровень:* окно — свойство процесса
   для PM, не payload плагина.
2. **Проверка — один раз, при регистрации.** Годно: `int`/`float`, не `bool`, конечное, `> 0`. Негодное (`0`, `<0`, NaN,
   inf, `bool`, строка) — ключ считается отсутствующим, WARNING с именем процесса и словом `stop_window_s`, без значения.
   Процесс создаётся (ошибка конфига не роняет создание). Негодный `max_stop_window_s` — `C = g` + WARNING без значения.
   Путь стопа не бросает (как DESIGN 7 Task 1.1). *Почему 0 негодно:* `stop_budget(0)` = 5,0, `_stop_timeout_s(0)` = 0,0 —
   у нуля два смысла, ни один не «окно».
3. **Потолок.** `w_i = min(stop_window_s, C)`; если обрезано — WARNING с именем, исходным числом и `C` (числа печатаются
   после проверки в конечный float). WARNING — на каждое создание воплощения (restart повторяет его: одна строка на
   воплощение). Окно без ключа потолком не трогается: одиночный стоп — `stop_process_timeout`, системный — `g`. При
   `C < g` ключ может только сократить окно ниже `g`; это так задумано (потолок — граница для ключей, внешние сроки — от `G`).
   *Почему кламп с WARNING, а не отказ:* опечатка в одном процессе не должна валить топологию (принцип 5 владельца).
   *Почему `C` по умолчанию = `g`:* без настройки числа PM и спавнера те же, что сегодня (страж R2, тесты Task 1.4).
4. **Владелец карты окон — реестр.** `ProcessRegistry` получает `C` в конструкторе (как `child_stop_budget`), запоминает
   `w_i` в `_create_process` (рядом с `:203`) и снимает в `remove_process`. Все пути (`stop_one`, `stop_many`,
   `stop_all`, `children_stop`) получают окна в `_build_child_stop` без правки мест в PM. Скаляр `timeout` вызова остаётся
   окном для имён без ключа. Если ни у одного имени группы нет ключа — `ChildProcessStop` строится **без** `windows_s`
   (старый путь байт в байт).
5. **`ChildProcessStop(…, windows_s: dict[str, float] | None = None)`** — окна в секундах **от `request_stop`**
   (группа строится до срока области). Pre: ключи ⊆ имён группы; значения конечные `> 0`. Post: `None` — поведение
   прежнее. С `windows_s`: в `join_until` порядок на каждом опросе — «опрос живых → проверка abort → сроки имён»;
   срок имени = `min(_stop_requested_at + w_i, deadline)`; по сроку имени — `terminate` этому имени (в `_terminated`),
   через `TERMINATE_GRACE_S` — настоящий kill имени (в `_killed`), подтверждение до `KILL_CONFIRM_S`. При `aborted` —
   ни одного сигнала по имени (стоп передан, `handed_over`, 1.9b D4). `kill()` области добивает только тех, кому по имени
   ещё не слали; повторный `terminate` уже терминированным не шлётся; лог `waited` — по имени. Инвариант docstring
   `child_process_stop.py:21-22` меняется на: «без `windows_s` до `kill()` сигналов нет; с `windows_s` — сигнал имени
   только по его сроку и только без abort». Дополнение ADR-PMM-035. *Почему одна группа со сроками по имени, а не группа
   на окно:* одна группа видит смерть соседа и держит один `join_until` (ADR-PMM-035 «Отвергнуто»).
6. **Бюджет ребёнка.** Ребёнок с ключом получает `stop_budget(w_i)` (окно после потолка); без ключа — как сегодня,
   `stop_budget(shutdown_timeout)` (`process_manager_process.py:172` остаётся от `g`: «g → G везде» дало бы ребёнку
   без ключа `work_s` 0,8·G − 1 внутри окна PM `g`).
7. **Внешние сроки — от `G`.** `_budget()` PM = `stop_budget(G)`: область `children` (`:3700`) и корень `_root_budget`
   (`:3687`) — от `G`. Спавнер в `stop()`: `outer = stop_budget(max(X, G))["outer_s"]`, где `X` — явный `stop(timeout)`
   или graceful оркестратора; `C` читается из `_orchestrator_config` в момент `stop()` (не при спавне — юнит-тесты с
   подставным `_process`). PM и спавнер читают одно число из одного конфига оркестратора. Арифметика ADR-PMM-031 не
   меняется, меняется аргумент. Вложенность: ребёнок `0,8·w_i < w_i ≤ G`; `children`: terminate `w_i`, kill `w_i+1`,
   подтверждение `w_i+2 ≤ G+2`; корень `G+3`; спавнер `G+3,5` — запас 0,5 с, как сегодня.

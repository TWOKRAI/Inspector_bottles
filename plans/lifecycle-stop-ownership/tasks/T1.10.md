## DESIGN

**D1. Пять значений.** `exited` — смерть подтверждена, этому имени не доставлен ни `terminate()`, ни `kill()`;
`terminated` — подтверждена после доставленного этому имени `terminate()`, без `kill()`; `killed` — после доставленного
этому имени настоящего `proc.kill()`; `handed_over` — не подтверждена, стоп прерван системным стопом (1.9b D4, решение
CTO по О1), ребёнка добивает `_ChildrenStop`; `survived` — не подтверждена без прерывания (пережил kill). Источник —
шаг эскалации, **не exitcode** (замер стадии 0 на Windows: сам — 0, `terminate()` — −15, `kill()` — −15; ребёнок,
вышедший сам с кодом ≠ 0, по exitcode неотличим от убитого).

**D2. `ChildProcessStop`.** Пошаговые множества `_terminated` и `_killed` **на имя**, пополняются там, где сигнал
доставлен этому имени (не флаги группы `_kill_started_at`/`_real_kill_sent`: имя, умершее между окном и `kill()`,
сигнала не получает и остаётся `exited`). `outcomes() -> dict[str, str]` — один снимок на всю группу: подтверждённое
имя → `killed` / `terminated` / `exited` по множествам; неподтверждённое при `aborted` → `handed_over` (даже если
`terminate()` уже доставлен); неподтверждённое без `aborted` → `survived`. `outcomes()` **сам начинает с
`_observe()`** — последний проход наблюдения, который сегодня делает `survivors()` (`child_process_stop.py:278-282`):
ребёнок, умерший через миллисекунды после последнего `join_until`, подтверждается (итог по множествам,
`on_confirmed_dead` — ровно один раз, метка ADR-PMM-030 ставится), а не уходит в `survived`/`handed_over`.

**D3. `ProcessRegistry`.** `_stop_many` строит и `result` (bool на имя), и итоги из **одного** снимка `outcomes()`
(`result[name] = outcomes[name] in {exited, terminated, killed}`), не из `survivors()` отдельно — иначе `success: False`
при `outcome: "exited"`. `stop_outcome(name) -> str | None` — итог последнего стопа **текущего воплощения**:
пишет любой стоп через `_stop_many` (`process.stop`, рестарт, `topology.apply`, `stop_all`); `add_process` того же
имени сбрасывает в `None` (новый инстанс после рестарта — `None`; сброс терпит двойники без `name` —
`getattr(process, "name", None)`). Имена, не дошедшие до `ChildProcessStop` (призраки и уже мёртвые,
`process_registry.py:435-449`, — в т.ч. из `topology.apply`/`stop_all` через `stop_many`), запись `stop_outcome` **не
трогают** — как короткий выход `stop_process` (`process_manager_process.py:3834-3839`). Гонка «`stop_process` увидел
живого, реестр — уже мёртвого» → `outcome: None`, `success: True`. Чтение без нового лока; запись — там же, где
`_stop_many` пишет свои метки.

**D4. Ответ PM.** `_cmd_process_stop` и `_cmd_process_restart` отвечают `{"success", "process_name", "outcome"}`, где
`outcome` — итог стопа **этого вызова** (не чтение записи реестра после вызова: она может быть от прошлого стопа или
уже сброшена `add_process`). Публичные `stop_process`/`restart_process -> bool` и `interfaces.py` не меняются.
`_cmd_process_stop` и `restart_process` **по-прежнему зовут публичный `self.stop_process(name, mark_reader_gone=...)`**
(его подменяют/оборачивают `test_pm_marks_gone_reader_acceptance.py:422-427` и H8
`test_lifecycle_fifo_hazards.py:357-372` — обходной приватный вызов их сломает). Итог идёт **боковым каналом**:
`stop_process` сбрасывает его на входе и заполняет на каждом выходе (поток исполнителя переиспользуется — без сброса
на входе короткий путь «нет в реестре / мёртв» вернёт итог прошлой операции, R11). Хранилище канала выбирает
developer. Пути:

| Путь | `success` | `outcome` |
|---|---|---|
| стоп живого ребёнка | как сегодня | D1 |
| имени нет в реестре / процесс уже мёртв до стопа | как сегодня | `None` |
| рестарт: стоп подтверждён, `create_and_register` упал | `False` | итог фазы стопа |
| рестарт отказан до фазы стопа | как сегодня | `None` |
| стоп прерван системным стопом | `False` | `handed_over`; ключа `error` нет |
| отказ исполнителя `key_missing` / `system_stopping` / `executor_busy` | как сегодня | ключа нет |

`error` у прерванного стопа отсутствует, как сегодня: ADR-PMM-039 I3(в) оставляет `system_stopping` только снятым из
очереди (решение лида 2026-10-27). `supervision.status` — поле `stop_outcome` на запись процесса =
`registry.stop_outcome(name)`.

**D5. Документы.** ADR-PMM-039 I3 — пункт (г): «`outcome` — только в ответах `_cmd_process_stop`/`_cmd_process_restart`;
отказы исполнителя без него». Дополнение к ADR-PMM-039 про D1–D4; README — формы ответов. `IProcessRegistry` не
меняется (решение лида 2026-10-27: протокол и сегодня не перечисляет `stop_many`, `exit_report`, `get_ready_event`;
`stop_outcome` — метод конкретного реестра). Карта `pm-lifecycle-commands.md` не меняется.

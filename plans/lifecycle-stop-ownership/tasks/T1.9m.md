## DESIGN

### D1 Место — подмодуль `worker_module/executor_manager.py`, не новый модуль

- Один файл (`Stability: lite`), рядом с ядром (`keyed_executor.py`) и `WorkerManager`, от которого он зависит. Число модулей,
  `MODULE_TIERS.md`, `modules.yaml` не меняются. Новый модуль `executor_module` потребовал бы строку в `MODULE_TIERS.md`
  (`test_tier_map_matches_disk`), правку счёта модулей (`test_module_count_is_stated_correctly`), свой `interfaces.py` и
  `__all__` (`:129`, `:139`), строку в атласе (`test_modules_map.py`) — четыре контракт-теста и слой ради одного файла
  (принцип 4 владельца).
- Схема конфига `ExecutorSpec` — в том же файле (не в `worker_module/configs/`): один публичный класс данных при одном
  менеджере, FILES ≤ 8.
- Экспорт из `worker_module/__init__.py` — **нет** (как у `KeyedExecutor`): потребители импортируют
  `worker_module.executor_manager` / `worker_module.interfaces`.

### D2 Контракт (`module-contract`): протоколы в `worker_module/interfaces.py`, класс в `executor_manager.py`

- `IExecutorRegistry(Protocol)`, `@runtime_checkable` — **узкий вход для `CommandManager`**:
  `get(name: str) -> OrderedExecutor | None` — объект по имени или `None`; не бросает.
- `IExecutorManager(IExecutorRegistry, Protocol)` — для владельцев (процессы, PM, ServiceHost):
  - `create(name: str, spec: Mapping[str, Any] | None = None, *, should_reject: Callable[[], bool] | None = None) -> OrderedExecutor`.
    **pre:** `name` — непустая `str` без `/` (имя записи `Scope`), не занято; менеджер не закрыт. `spec` → `ExecutorSpec`
    (`None` → умолчания). **post:** создан `KeyedExecutor(name, worker_manager=<WorkerManager процесса>, max_pending,
    serial, max_workers, should_reject, log=None)`; область привязана → объект сразу во владении области (D5); одна строка
    INFO: имя, kind, `serial`, `max_workers`, `max_pending`. Ошибки — исключения (код — fail fast): занятое имя или
    `create` после закрытия → `ValueError` / `RuntimeError`; неверный `spec` → `ValueError` с текстом pydantic; исключение
    конструктора `KeyedExecutor` (имя воркера занято) пробрасывается, запись не создаётся.
  - `register(name: str, executor: OrderedExecutor) -> None` — готовый объект по имени (адаптеры-политики PM).
    **pre:** имя как у `create`; `callable(getattr(executor, "submit", None))`, иначе `TypeError`. **post:** только
    маршрутизация по имени; **менеджер им не владеет** (не зовёт `request_stop` / `join_until`, даже если объект
    `Stoppable`) — владелец остаётся у регистрирующего (без второго владельца).
  - `load_config(section: Mapping[str, Mapping[str, Any]] | None) -> list[str]` — исполнители из секции конфига процесса;
    **на каждую запись своя попытка:** неверная запись → одна строка ERROR (имя + причина), запись пропущена, соседние
    создаются (принцип 5). Возврат — имена созданных. `None` / `{}` → `[]`, ни строки лога.
  - `names() -> list[str]` — все имена (созданные и зарегистрированные) в порядке появления.
  - `describe() -> dict[str, Any]` — интроспекция (D6), Dict at Boundary, снимок под локом.
  - `is_executor_thread(name: str) -> bool` — текущий поток — рабочий созданного исполнителя `name`; признак — точное
    совпадение `threading.current_thread().name` с одним из `f"{wm.manager_name}_keyed-{name}-{i}"`, `i < число рабочих`
    (`worker_lifecycle.py:75` + `keyed_executor.py:146`; связь в одном модуле, страж — R5). Для зарегистрированного или
    неизвестного имени — `False`.
- `ExecutorManager(BaseManager, ObservableMixin)` — `ExecutorManager(manager_name, *, worker_manager, process=None,
  managers=None, config=None)`; `initialize()` → `True`, без потоков. Состояние — `dict[name, _Entry]` под `threading.Lock`
  (лок не держится поверх конструктора `KeyedExecutor`, `scope.own` и логов: проверка имени и резерв — под локом, создание —
  вне, запись — под локом; повторная проверка «закрыт» после создания → закрыть только что созданный `shutdown(now)` и
  `RuntimeError`).
- `ExecutorSpec(SchemaBase)`: `kind: Literal["keyed"] = "keyed"`, `serial: bool = False`, `max_workers: int = 4` (≥ 1),
  `max_pending: int = 64` (≥ 1) — умолчания `KeyedExecutor` (`keyed_executor.py:110-112`); `model_config` — копия
  `SchemaBase.model_config` + `extra="forbid"` (опечатка — громкий отказ записи, а не тихий умолчательный исполнитель).
  `should_reject` и `log` в схеме нет — это код, не данные (только `create(..., should_reject=)`).

### D3 Как процесс получает менеджер (`process_module`)

- `ProcessManagers.create_all`: сразу после `worker` — `executors = self._create_executor_manager(worker)` (manager_name
  `f"executors_{process.name}"`, `managers={"logger": logger}` — создать после `logger`; порядок create_all:
  worker → logger → **executors** → error → …). `_create_command_manager(..., executors=executors)` → `CommandManager(...,
  executors=executors)`. `ManagersBundle.executors: Any | None = None` (умолчание — тесты соседей собирают bundle вручную).
  `register_all`: `process.register_manager("executors", bundle.executors, enabled=True)`.
- `ProcessModule.__init__`: `self.executor_manager = None` (рядом с `self.worker_manager = None`, :173).
  `_apply_managers_bundle`: `self.executor_manager = bundle.executors`; **сразу после записи `plugins` (:533)** —
  `work.own(self._attr_call("executor_manager", "shutdown"), name="executors", kind="callable")`,
  `self._attach_manager_scope(work, "executor_manager")`, затем
  `self.executor_manager.load_config((self.get_config("config") or {}).get("executors"))` (если менеджер не `None`).
- **Почему здесь:** (1) исполнители из конфига есть до любой регистрации команд, которая может их назвать (плагины — шаг 6,
  встроенные — `run()`, наследники — после `super().initialize()`); (2) в `work` фаза 1 идёт по порядку регистрации →
  приём исполнителей закрывается раньше `_own_work` и `workers`; (3) фаза 2 обратная: `workers` (ждёт потоки рабочих,
  в том числе текущую операцию) → `_own_work` → `executor_manager-scope` (уже пусто — `True` сразу) → `executors` → `plugins`
  → `hooks` — операция исполнителя не переживает ни ресурсов наследника, ни плагинов, а `transport` (CM, роутер)
  закрывается после всего `work`.
- **Ноль, когда исполнителей нет:** объект менеджера, пустая дочерняя область и одна запись-вызов в `work` (решение
  владельца: «без записи или пустая запись»); потоков — 0, строк лога — 0, команд в CM — только `introspect.executors` (D6).
- **Конфиг:** ключ `executors` в `proc_dict["config"]` (тот же путь, что `plugins`): `{"<имя>": {"kind": "keyed", "serial":
  …, "max_workers": …, "max_pending": …}}`. `ProcessLaunchConfig`: поле `executors: dict[str, dict[str, Any]] = {}`
  (`FieldMeta("Executors", info=…)`); в `build()` пустое значение **снимается** с payload (`if not payload.get("executors"):
  payload.pop("executors", None)`) — форма `proc_dict` у всех нынешних процессов прежняя (как `restart_policy`, :170-174).
  Наверх `proc_dict` (как `workers`) не выносится: путь `config` уже доставляет вложенные dict, лишняя ветка не нужна.

### D4 Разрешение имени в `register_command` (`command_module`, только расширение)

- `CommandManager.__init__(..., executors: "IExecutorRegistry | None" = None, **kwargs)` — новый keyword с умолчанием;
  хранится как `self._executor_source`. Через `managers=` **не** передаётся: этот словарь уходит в `ManagerRegistry`
  миксина как наблюдатель.
- `register_command(..., executor: "OrderedExecutor | str | None" = None, ...)` — сигнатура и умолчания прежние, расширен
  только тип. Строка разрешается **в момент регистрации** (fail fast), до `_executor_refusal`:
  - `""` → отказ «пустое имя исполнителя»; `self._executor_source is None` → отказ «исполнитель по имени '<имя>' без
    менеджера исполнителей»; `get(имя) is None` → отказ «исполнитель '<имя>' не найден». Отказ = `False` + WARNING (текст
    содержит имя), команда не зарегистрирована, метрика `registration.failed` — как прочие отказы (:247-254).
  - найден → дальше прежний путь с объектом; в `metadata["executor"]` — **строка, переданная вызывающим** (имя в реестре
    менеджера), а не `obj.name` (у адаптеров PM своё `.name`). Объектная форма — без изменений (`obj.name`, :259).
- Объект в `self._executors` фиксируется при регистрации (раннее связывание): `register`/`create` с занятым именем запрещены
  (D2), подмены под тем же именем нет — позднее связывание не нужно.
- **Команда, зарегистрированная до исполнителя,** — отказ по имени (как сегодня отказ `key_from` без исполнителя,
  `command_manager.py:296-298`). Порядок PM (`:267` → создать и зарегистрировать → `:273`) — обязанность 1.9b (стадия 0
  1.9b п.10), 1.9m его не меняет.
- `ICommandManager` (`command_module/interfaces.py`) не трогается: `register_command` там через `**kwargs`, конструктора нет.
- Обратного импорта нет: `command_module` знает только `worker_module.interfaces.IExecutorRegistry` под `TYPE_CHECKING`;
  `worker_module` о `command_module` не знает.

### D5 Остановка: владение в области менеджера, общий срок, без ожидания со своего потока

- Созданный исполнитель отдаётся во владение `self.scope.own(_OwnedExecutor(ex, thread_names), name=<имя>,
  kind="executor")`. `_OwnedExecutor` — приватная обёртка `Stoppable`: `request_stop()` → `ex.request_stop()` (не блокирует,
  идемпотентен — 1.9a); `join_until(deadline)`: текущий поток ∈ `thread_names` → WARNING «исполнитель '<имя>' закрывается
  со своего рабочего — без ожидания» и `False` сразу; иначе `ex.join_until(deadline)`. Срок общий: `Scope` передаёт всем
  записям один `deadline` сегмента (`lifetime.py:568-593`) — сумма ожиданий не растёт с числом исполнителей.
- Области нет (менеджер вне `ProcessModule`: тесты, PM через `__new__`, будущий ServiceHost до своей проводки) — исполнитель
  в `_unowned`; `_on_shutdown()` закрывает их сам: `request_stop` всем, затем `join_until` с одним сроком
  `monotonic() + _UNOWNED_JOIN_S` (константа 2,0 с, в ADR) через ту же обёртку. При привязанной области `_on_shutdown`
  ничего не закрывает (одно место закрытия).
- **Идемпотентность с 1.9b:** PM зовёт `request_stop()` / `join_until()` своего lifecycle-исполнителя из `_ChildrenStop`
  ДО детей (стадия 0 1.9b п.6) — это вызовы, не владение; владелец один — область менеджера. Порядок при закрытии `work`:
  фаза 1 менеджера (`request_stop`, очередь снята) идёт раньше `_ChildrenStop.request_stop` (D3) → повторный `request_stop`
  — no-op; `join_until` области после остановленного исполнителя → `True` сразу (`keyed_executor.py:265-272`).
- `create` после закрытия области — `RuntimeError` до создания потоков (D2); гонку «создание ↔ закрытие» закрывает
  повторная проверка после создания (H1).

### D6 Интроспекция: `describe()` и команда `introspect.executors`

- `describe()` → `{"executors": {<имя>: {...}}, "unavailable": [...]}`:
  - созданный: `{"kind": "keyed", "source": "config" | "code", "serial", "max_workers", "max_pending", "owned": bool,
    "workers": {<имя воркера>: {"is_alive": bool, "status": str}}}` — воркеры через публичный
    `worker_manager.get_worker_status(name)` (как `_WorkersStop`, `process_lifecycle.py:198-201`);
  - зарегистрированный: `{"kind": "registered", "source": "code", "type": <имя класса объекта>}`;
  - `"unavailable": ["pending_depth", "running_keys", "accepted", "refused_busy", "refused_stopping"]` — чего у
    `KeyedExecutor` нет публично (Факт). **В ядро не дописывается**; нужен публичный `stats()` у `KeyedExecutor` — отдельное
    решение (OPEN_QUESTIONS).
- Команда `introspect.executors` — новый кортеж в списке `_register_introspect_commands` (`builtin_commands.py:654-704`) +
  метод `_cmd_introspect_executors` (≈ 10 строк): `mgr = _safe_get_manager(svc, "executors")` (:152) → `{"success": True,
  "process": svc.name, **mgr.describe()}`; менеджера нет → `{"success": True, "process": …, "executors": {},
  "unavailable": []}`. Поле в `introspect.status` не добавляется (форма его ответа — чужой контракт, `overview.py`). Правка
  `builtin_commands.py` — **через координатора** (файл полосы Д; зоны :866-870 и :1003-1007 не трогаются; карточка
  `introspect.capabilities` команду покажет сама — она перечисляет команды CM).
- backend_ctl: `driver.send_command(<процесс>, "introspect.executors")` (`driver.py:658`); отдельного MCP-инструмента нет.

### D7 Наблюдаемость

- Логи менеджера — только `self._log_info/_log_warning/_log_error` миксина (тот же `module=`, что у `WorkerManager`; сверить
  в коде). Нового логгера нет; `KeyedExecutor` создаётся с `log=None` — его логгер 1.9a (`get_std_logger("worker", …)`).
- Строки: INFO — один раз на созданный исполнитель; ERROR — неверная запись конфига (имя + причина, без значений полей
  чужих записей); WARNING — закрытие со своего потока (D5). Нет исполнителей — ни одной строки.

## Риски (механизм)

- **Имя потока как признак (D2, D5)** держится на двух строках одного модуля (`worker_lifecycle.py:75`, `keyed_executor.py:146`);
  переименование одной — `is_executor_thread` молча `False`, закрытие со своего потока снова ждёт срок. Страж — R1 (точное
  имя потока) и R5.
- **Пересборка `ManagersBundle` вручную** в тестах соседей: поле с умолчанием `None` → `self.executor_manager = None`,
  `load_config` пропускается, `introspect.executors` отвечает пустым. Риск — только в проводке D3 (`if mgr is not None`).
- **Порядок `create_all`** (executors после logger, до command): перестановка ломает `CommandManager(executors=…)` —
  `NameError` при подъёме, видно сразу (R8).
- **`extra="forbid"`** у `ExecutorSpec` строже соседних схем (политика рецептов — вопрос владельца в OPEN_QUESTIONS); опечатка
  в рецепте даёт ERROR и отказ команд, названных этим исполнителем, — громко, но процесс поднимается без исполнителя.
- **Чужие файлы:** `builtin_commands.py` (полоса Д) и публичная сигнатура `command_manager.py` (полоса Р2) — до Б2 и до слияния
  нужен ответ координатора.
- **Унаследовано от 1.9a (строка отчёта, не правка):** `start_worker` на мёртвом потоке `keyed-*` после закрытия
  (`worker_lifecycle.py:99-100`) перезапустит `_worker_loop` закрытого исполнителя → `finally` снимет `_live_workers` ниже
  нуля (`keyed_executor.py:351-353`). `run()` зовёт `start_all_workers` один раз до закрытия — сегодня не достижимо; не
  проверено прогоном.

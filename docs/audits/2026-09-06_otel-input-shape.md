# Форма записи на входе экспортёра — Task 1.0 плана `otel-export`

**Дата:** 2026-09-06 · **Сырьё:** `tools/otel_stand/samples/1f40ce0d/` (снял ведущий closure на
стенде живой приёмки Task 3.2) · **Метод:** разбор сырых ответов инструментов скриптом; посылки
плана проверены **по данным и по коду**, не пересчитаны из плана.

**Зачем задача существует.** Ред. 1 плана описывала маппер над плоским `extra` и была неверна на
обеих дорогах; ред. 3 не знала `kind=observation`, `origin` и `NUMBER_SEVERITY`. Карточка нужна,
чтобы Ф1 строилась на настоящих записях, а не на третьей по счёту догадке.

---

## 1. Конверт сообщения

Обе формы живут одновременно — маппер обязан принимать обе:

| Форма | В странице хвоста |
|---|---|
| `data.records` (пачка) | 36 сообщений |
| `data.record` (одна) | 18 сообщений |

54 сообщения → **144 записи**. Посылка плана (`frontend/process.py:194-197`) подтверждена числом.

**Страница, а не окно.** `tail_debug.json` — одна страница на 54 сообщения (`count: 54`,
`next_cursor: all:54@014b3e`). README снимка называет по окну `{error: 6, log: 272,
observation: 183, stats: 67}` = 528 записей за 5 минут. Доли родов брать из README, состав
формы — из страницы.

## 2. Ключи записи — одни и те же у всех родов

```
kind, process, module, ts, severity, severity_number, metric, message, extra
```

Форма **единая по построению**, а не по совпадению: оба нормализатора
(`hub_record_to_display`, `log_record_to_display` в `record_display.py`) собирают один и тот же
набор ключей, и докстринг `log_record_to_display` называет причину — «пороговый фильтр работал бы
на половине данных». У лога и ошибки `metric` присутствует со значением `None`: ключ есть всегда,
чтобы форма не расходилась.

Стор добавляет ровно один ключ — `id` (PRIMARY KEY). Больше между дорогами **разницы по ключам
верхнего уровня нет**.

## 3. `extra` — вот здесь дороги расходятся, и план это описывал неверно

| `kind` | Форма `extra` | Ключи (по снимку) |
|---|---|---|
| `log` | **вложенная** `{"context": {...}}` | `proc_name`, `pid`, `fw_version`, `incarnation`, `recipe`, `origin` |
| `error` | **вложенная** `{"context": {...}}` — по коду, в окне не попалась | то же (общий нормализатор) |
| `observation` | **плоская** | `writer`, `metric`, `value` |
| `stats` | **плоская** | `aggregate`, `metrics`, `total_count`, `window_ts`, `bucket_bounds` |

`bucket_bounds` присутствует не всегда: 26 из 50 строк стора, 1 из 18 в хвосте — только у
агрегатов, содержащих `timing`-метрики.

**Следствие для Task 1.1:** маппер не может обращаться с `extra` одинаково. Одна ветка на
`extra.context.*` (лог/ошибка), другая на плоский `extra` (числовые рода) — и «плоский словарь как
вход» из ред. 1 неверен ровно наполовину, а не целиком.

## 4. Посылки плана — что подтвердилось, что нет

| Посылка плана | Вердикт | Основание |
|---|---|---|
| Конверт `data.records` против `data.record` | **подтверждена** | 36 против 18 в странице |
| `origin` лежит на `extra.context.*` | **подтверждена** | 18/18 записей `kind=log` |
| Пятёрка Resource на `extra.context.*` | **неверна** | в `context` шесть полей другого состава: `proc_name`, `pid`, `fw_version`, `incarnation`, `recipe`, `origin`. Слова «пятёрка» снимок не подтверждает |
| `trace_id` на `extra.context.*` | **не подтверждена** | 0 вхождений на обеих дорогах. Честно: в окне не было операций с трассировкой — это «не наблюдалось», а не «невозможно» |
| **«У стора `origin` поднят на верх записи»** | **ОПРОВЕРГНУТА КОДОМ** | в `CREATE TABLE records` колонки `origin` нет вовсе (`observability_store.py:237-247`), `grep origin` по файлу стора — пусто. `origin` остаётся в `extra.context` на **обеих** дорогах |
| `observed_ts` появляется только у приёмника | **согласуется** | 0/144 и 0/200 — в сырье его нет, ставит его приёмник (`_ENVELOPE_KEYS:40` его перечисляет) |
| `scope` в display-вид не копируется | **подтверждена** | 0 вхождений на обеих дорогах |
| `kind` в конверте | **подтверждена** | `_ENVELOPE_KEYS` (`record_display.py:40`) |

Опровергнутая посылка — не косметика: на ней стояло правило Task 3.4 сверять тождество, «зная, что
у стора `origin` наверху». Сверять нужно **одинаково на обеих дорогах**.

## 5. Шкала важности

| `kind` | `severity` | `severity_number` |
|---|---|---|
| `log` | `info` | 9 |
| `observation` | `number` | 0 |
| `stats` | `number` | 0 |
| `error` | `error`/`critical` | 17 / 21 — **из кода**, в окне не попалось |

У числовых плоскостей оси важности нет вовсе: `severity_number_for` возвращает `UNSPECIFIED`
по `kind`, не по неудаче ранжирования. `kind_for_severity` — порог `ERROR_SEVERITY` (≥17 → `error`).
То есть **`error` и `log` — одна форма и один нормализатор**, различаются только значениями трёх
полей. Это снижает цену того, что `error` в окно не попал: форма выводится из кода одной функции,
а не угадывается.

## 6. Чего в снимке НЕТ — назвать, а не эмулировать

| Требуемая форма | Форвардер | Стор | Итог |
|---|---|---|---|
| `log` | 18 | **0** | стор не покрыт |
| `error` | **0** | **0** | **не покрыт вовсе** (README обещает 6 за окно — не в этой странице) |
| `stats` агрегат | 18 | 50 | покрыт |
| `stats` одиночная метрика | **0** | **0** | **не покрыт** — все 68 записей `aggregate=true` |
| `observation` | 108 | 150 | покрыт |

Все 144 записи страницы — от **одного** процесса `camera_0`; двух источников с разным `Resource`
в сырье нет, это предмет Task 4.1, а не Ф1.

**Что с этим делать.** Тесты Ф1 на непокрытые формы строятся на выводе из кода
(`log_record_to_display` — общий нормализатор лога и ошибки) и **помечаются как выведенные, а не
снятые**. Синтетический плоский словарь как вход остаётся запрещённым: непокрытая форма берётся из
нормализатора живого фреймворка, а не сочиняется. Догрузить недостающее — просьба к сессии closure
на её ближайшем стенде: одна `error`-запись и одна `stats` с `aggregate=false`.

## 7. Что из этого следует для Ф1

- **Task 1.1** (`record_to_otlp`): две ветки разбора `extra`, а не одна. `metric: None` у лога —
  нормальное значение, не отсутствие поля. `trace_id` в сырье отсутствует: код обязан работать при
  его отсутствии, а тест «`trace_id` доехал» строится на выведенной записи с пометкой.
- **Task 1.2** (`Resource`): состав `extra.context` — шесть полей, и `host.name` среди них **нет**.
  Значит `host.name` берётся не из записи, а из окружения экспортёра; находка ред. 4 про
  «`service.instance.id = incarnation` не различает устройства» подтверждается составом снимка.
- **Task 1.3** (числа не экспортируются): отличать по `kind ∈ {stats, observation}`, а не по
  `severity == "number"` — оба поля дают одно и то же на снимке, но `kind` считает источник, а
  `severity` может разойтись (докстринг `kind_for_severity` описывает ровно такой случай в истории).

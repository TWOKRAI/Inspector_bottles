# Зависимости под Python 3.14: подбор версий и сборка окружения

Дата: 2026-11-22. Ветка `chore/deps-py314` (от main d42f188ac), дерево `Inspector_bottles--deps-py314`. Платформа замера: macOS arm64, CPython 3.14.7.

## Суть

Проект переведён в `pyproject.toml` с `requires-python = ">=3.12,<3.13"` на `>=3.14,<3.15`. Нижние границы подняты до версий, которые реально поставились. Окружение собрано отдельным venv вне дерева. Из всех зависимостей колёс cp314 нет только у одной: `pygame` (последний релиз 2.6.1 — колёса cp310-cp313). Это блокер, решение за владельцем (см. «Блокеры»). **Решение владельца 2026-11-22: `pygame` снят** (без потребителей в коде). После этого `uv lock --python 3.14 --no-build` проходит, `uv.lock` в дереве пересобран (`requires-python = "==3.14.*"`, пакета `pygame` в lock нет).

Два пакета оставлены не на последней версии по доказанной причине: `mcp` (2.x ломает `backend_ctl`) и `opentelemetry-*` (1.45 ломает `Services/otel_export`).

Что известно для решения:
- В репозитории `pygame` не импортируется нигде: `git grep -n "pygame" -- ':!uv.lock' ':!docs/reports' ...` даёт только строку `pyproject.toml` и упоминания в документах. Тот же вывод в `docs/direction/TECH_STACK_2026.md:355` («Мёртвые core-deps»).

Развилка для владельца (я выбрал НЕ молча — строку в `pyproject.toml` оставил как была, с комментарием-блокером):
1. Снять `pygame` (зависимость без потребителя). Минус: теряется заготовка для симуляции, если кто-то ставит её руками.
2. Заменить на `pygame-ce>=2.5`. Минус: чужой форк ради пакета, который не импортируется.
3. Остаться на Python 3.12 — ради мёртвой зависимости не оправдано.

Остальные сомнительные места по колёсам (не блокеры): `debugpy`, `isort` без колёс cp314 под Linux aarch64 (только dev-инструменты; `debugpy` через `ipykernel`, `isort` через `pylint` из группы `diagrams`), в рантайме Orin не нужны.

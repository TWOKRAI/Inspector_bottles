# Отчёт: T5.3g — окна W1 и W4 гонки `connect` ↔ `request_stop` драйвера робота v2 (полоса Р2, 2026-10-21)

Лид: inspector-bottles-a9. Ветка `feat/robot-v2-t53g`, перебазирована на main `cf5855f9c`. Слияние — «да» владельца
(передано координатором 10:10), после «ок» координатора.

## Итог

Решение владельца от 2026-10-20 выполнено. Простой робот, которому `request_stop` пришёл посреди `connect`, получает
ровно один SOFT и не становится «готовым» после выключения. Закрыты четыре окна:

| окно | что было на main (проба, факт) | как закрыто |
|---|---|---|
| W1 | `connect()` → True после выключения, SOFT 0 | `connect_finish` под замком отказывает при `_stopping`/`_shutdown` |
| W1′ (нашла стадия 0) | `request_stop` состоит из двух секций, между ними `connect` успевает выйти → SOFT 0 | одна точка линеаризации: снимок `_stop_linked` в `request_stop_begin`, в той же секции, что `_shutdown` |
| W4 | `connect_reset` после стопа снимал `stopping` и «стоп не подтверждён» | `connect_begin`: проверка и сброс в одной секции |
| WW (широкое) | `request_stop` внутри `probe`/`sync` → SOFT 0 | `process_stop_plan` считает «идёт подключение и связь поднята» подключением |

`_ready` перенесён в `RobotState`: геттер без замка, сеттер под замком. Решение записано в ADR-DH-011
(`Services/device_hub/DECISIONS.md`). Новых замков нет: `git grep` даёт 4 строки, как до правки.

## Уроки

- Сторож, который сверяет число файлов литералом, краснеет от любого нового файла тестов. Лид закоммитил пробу, прогнав
  только её файл; красный сторож нашла стадия 0. Перед коммитом нового файла тестов гонять весь каталог.
- Барьер, который держит поток `connect` до возврата `request_stop`, не видит окна между секциями самого `request_stop`
  (W1′). Окно нашло перечисление порядков на стадии 0, а не проба.
- Инъекция, которая отравляет замок, превращает каждый тест в сумму дедлайнов: прогон шёл минутами без вердикта. Нужен
  первый тест с коротким дедлайном.
- Тестер прочитал запрещённые тела (`_check_stop_echo`, начало `_connect_locked`) и честно сказал об этом. Взял оттуда
  только способ изобразить «нет эха» (публичный контракт клиента); лид принял слепоту как не нарушенную по существу.

## Что осталось открытым

- Повторы ×5 барьерных тестов на нестабильность не сделаны: каждый файл прошёл один-два раза.
- Сторож с дедлайном 1 с может краснеть на сильно загруженной машине и без инъекции (без нагрузки весь набор из 31 теста
  прошёл за 1,5 с).
- Не закреплены тестами: отказ `connect_finish`/`connect_restore` только по `_shutdown`; повтор записи стопа после
  упавшей при `_stop_linked`; `_note_reconnect_failed()` считает стоп посреди `connect` неудачной попыткой.
- Готовый робот с упавшим транспортом: снимок `_connect_linked = was_ready` наступает раньше переподключения сокета.
- `issue_stop` в WW делает свою `probe` без бюджета срока: на мёртвой связи теряется не больше одного бюджета, договор
  `stop.py` не нарушен (minor).
- Окно «проверка → запись» перед SERVO/DO в `_run_on_connect` осталось (ADR-DH-011 «по возможности»).
- Оракул сбросов защёлки `_LATCH_ROWS` не знает новых переходов — в задачу SPI хаба.
- Решение владельца нужно: SOFT при обычном «Отключить» посреди `connect` (сейчас нет; решение 2026-10-20 — только про
  `request_stop`).
- Для SPI хаба (от полосы Ф): после Task 1.9m `register_command(executor=...)` примет имя исполнителя из конфига —
  опираться на имя, не на объект.

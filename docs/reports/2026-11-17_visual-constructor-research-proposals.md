# Визуальный конструктор и движок исполнения: улучшения и целевая архитектура

**Дата:** 2026-11-17. Пометки **[И]** / **[З]** и метод — в основном файле.

## 5. Конкретные улучшения

Сложность: **М** — малая (дни, 1–3 файла), **С** — средняя (1–2 недели, один модуль),
**Б** — большая (несколько модулей, миграция рецептов). Оценки грубые, без замера.

### 5.1 Фундамент

| # | Улучшение | Польза | Сложность | Недостатки и риски |
|---|---|---|---|---|
| F-1 | **Связь — единственный источник маршрута.** `chain_targets` и порядок плагинов выводятся из `wires` при компиляции рецепта. Перенаправление по `item["target"]` остаётся как явный узел-маршрутизатор | Убирает двойную запись; делает выразимыми разветвление по портам и DAG; открывает путь F-3, U-5 | Б | Трогает горячий путь и 20 рецептов. Нужна миграция формата и период, когда читаются обе записи |
| F-2 | **Размещение — отдельный слой.** Узел получает атрибут «группа исполнения»; группа = процесс с политикой перезапуска, приоритетом, устройством | Один граф можно разложить по процессам по-разному без правки логики. Прямо служит цели «выявлять требования к мощности» | С после F-1 | Автору нужно понимать два понятия вместо одного. Нужны разумные умолчания |
| F-3 | **Вид исполнителя на группу:** цепочка (как сейчас), DAG (подключить замороженный `DagRunnable`), пул потоков для `thread_safe` | Параллельные ветви внутри процесса без лишних переходов | С | Гонки в плагинах, которые неверно объявили `thread_safe`. GIL ограничивает выигрыш чистым Python |
| F-4 | **Типы портов с версией** (в бэклоге как N-1) + проверка dtype, формы и устройства в рантайме в отладочном режиме | Ошибка стыковки видна на связи, а не в трассе плагина | С | Проверка на каждый кадр стоит времени — только под флагом. Нужен словарь типов |
| F-5 | **Проверка связи в домене, одна на редактор и на `blueprint.check`.** Неизвестный порт — отказ, а не «можно» | Закрывает V-3; нельзя сохранить рецепт, который упадёт при запуске | М–С | В разреженном окружении (без реестра плагинов) нужен явный режим «проверка пропущена» с видимой пометкой |
| F-6 | **Перенос ядра редактора во framework** (`frontend_module`): модель графа, команды, сцена, элементы. Прототип регистрирует расширения: секции инспектора, подписи, цвета | Выполняет принцип «framework — конструктор». Второе приложение получает редактор даром | Б | Большой перенос с риском регрессий; делать после F-1, иначе переносится старая модель |

| R-3 | Модель GPU (N-4): один процесс владеет устройством; соседние узлы в нём передают тензор без NumPy; узел-батчер на несколько камер | Важно для 4 ГБ RTX 3050 и Orin NX: один контекст CUDA вместо нескольких | Б | Передача GPU-памяти между процессами хрупка на Windows и Jetson — не делать, держать GPU-узлы в одной группе |

### 5.4 Оценка ваших предварительных гипотез

| Гипотеза | Вердикт |
|---|---|
| Разделение редактора, модели проекта и движка | Верно и на две трети уже сделано. Не хватает общей модели графа (F-1) и переноса во framework (F-6) |
| Универсальная система типов и портов | Верно. Каркас есть (`Port`, `are_ports_compatible`), не хватает версий и рантайм-проверки (F-4, F-5) |
| Переиспользуемые составные модули | Верно, но только после F-1 (U-5) |
| Единый интерфейс регистрации модулей | Уже есть и хорош. Добавить `entry_points` (R-5) |
| Управление многопроцессным исполнением | Надзор сильный. Не хватает слоя размещения (F-2) и частичного применения (R-2) |
| Передача больших данных без копирования | Сделано и измерено. Развитие — GPU (R-3) и нативные узлы (R-4) |

## 6. Целевая архитектура

```
┌──────────────────────────────────────────────────────────────────────┐
│ РЕДАКТОР (framework: frontend_module)                                │
│   команды → модель графа; сцена = проекция; оверлей из телеметрии    │
│   расширения приложения: секции инспектора, подписи, цвета           │
└───────────────┬──────────────────────────────────────▲───────────────┘
                │ dict (рецепт)                        │ состояние, метрики
┌───────────────▼──────────────────────────────────────┴───────────────┐
│ МОДЕЛЬ ГРАФА (framework, без Qt)                                     │
│   Узел: тип + версия + порты + параметры                             │
│   Связь: порт → порт + QoS                 ← единственная истина     │
│   Группа: составной узел с интерфейсом                               │
│   Размещение: узел → группа исполнения (процесс, исполнитель,        │
│               перезапуск, приоритет, устройство)                     │
└───────────────┬──────────────────────────────────────────────────────┘
                │
┌───────────────▼──────────────────────────────────────────────────────┐
│ КОМПИЛЯТОР (вырастает из SystemBlueprint.check)                      │
│   разворачивает группы → проверяет типы, циклы, join →               │
│   строит таблицы маршрутов, кольца, очереди → diff с работающим      │
└───────────────┬──────────────────────────────────────────────────────┘
                │ план запуска / частичный план
┌───────────────▼──────────────────────────────────────────────────────┐
│ РАНТАЙМ (существующий)                                               │
│   ProcessManager + надзор │ процесс с исполнителем: цепочка│DAG│пул  │
│   плоскость данных: кольца SHM + seqlock │ телеметрия, state_store   │
└──────────────────────────────────────────────────────────────────────┘
```

Четыре правила целевой архитектуры:

1. **Логика и размещение разделены.** Граф отвечает на вопрос «что с чем соединено»,
   размещение — «что в каком процессе». Переход между процессами — единица изоляции, не логики.
2. **Когда узлу нужен свой процесс:** источник (камера), блокирующий ввод-вывод, владелец GPU,
   ненадёжный или чужой код, узел с другим приоритетом. Всё остальное по умолчанию живёт
   вместе.
3. **Движок не знает о составных узлах, редактор не знает о процессах ОС.** Их связывает
   компилятор.
4. **Граница между слоями — dict**, как и сейчас.

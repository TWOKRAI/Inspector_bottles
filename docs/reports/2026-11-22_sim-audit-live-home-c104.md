## Находки

1. **Н2 в исходной формулировке (`robot_servo` off) не даёт C-104:** задание уходит на провод, сим-робот отвечает `RES_STATUS = 2, RES_ERRNO = 6`; `jobs_dropped` не растёт, health-строки нет. C-104 (строка «включите серво») срабатывает после «Домой» до «Серво ВКЛ» (Н2b, 3 из 3). Если для железа ожидается отказ при простом `servo off`, этого нет: решает, что делать с таким заданием, прошивка (ответ 2/6), а на ПК оператор получает потерю без `last_error`.
2. **Потеря «парком» не видна в `jobs_dropped` и в layout** (Н1 попытка 3): `jobs_forwarded` +1, `forward_ok True`, `jobs_dropped` прежний, health-строки layout нет; видны только `park.dropped.jobs = 1` и WARNING в `devices/system.log`. Для монитора пульта счётчик `jobs_dropped` недооценивает потери (Н1: 4 из 5).
3. **Н1 предсказывал `SC_RUN` в журнале:** при `home: already` `SC_RUN` нет, только `SERVO 0`.
4. **Первый диск после «Серво ВКЛ»:** задание уходит через 0,30…0,40 с (Н2b), в Н2 после `servo on` — 0,035…0,33 с; предсказание «≈ 0,1 с» выполнено не во всех случаях.
5. **errors.log:** строка отказа хаба есть в `errors.log` с уровнем ERROR и без префикса `[health]` (в `system.log` — WARNING с `[health]`); при поиске по `messages.log` её не найти.

## Что я оставил открытым / ненадёжным

- Н1: «диск в полёте» — окно между строкой диска и `CVT_JOB`; скрипт стреляет по файлу строки layout (опрос 2 мс); в 4 из 5 `robot_park` обогнал задание (отказ в хабе), в 1 — задание попало в очередь драйвера и было снято парком. Какой путь выпадет в конкретный раз — зависит от гонки двух потоков (`jobs_dropped` — «старая гонка», `2026-11-22_R2-merge-request.md`), n = 5, распределение 4:1 ничего не доказывает.
- «Домой при диске в полёте» здесь всегда с `home: already` (робот дома): сценарий, где робот в движении (задание уже исполняется), не проверялся; вывод «`SC_RUN` не нужен» верен только для этого случая.
- Н2: errno 6 не расшифрован (по смыслу — серво выключено; код `RES_ERRNO` не открывал). Реакция реальной прошивки v2 на такое задание не проверена (сим).
- Первая попытка Н1 была засчитана скриптом как «промах» из-за `None` в `robot_io` до первого события (ошибка моего скрипта, учтена при разборе: по журналам это захват).
- Времена `CVT_JOB` после строки диска (0,035…0,40 с) измерены по меткам файлов двух журналов (layout, обмен) на одной машине; точность ±1 мс заявлять не буду.
- В `ProcessManager/busy.log` заход 1 содержит `Command 'state.merge' failed: Поле 'data' обязательно и должно быть dict` (19:56:37,221) — случайное совпадение по времени с Н2 №1 или ошибка в другом месте, не исследовалось.
- Аудит с `--zone-max-mm 500` в этом заходе не запускался. Данные Н1/Н2 не прогонялись через α. Прогон сделан один раз на заход (n = 1 по заходам).
- Подсчёты `CMD_SEQ`, строк журналов и задержек сделаны моими скриптами (`an2.py`, `home_c104.py` в scratchpad), не repo-инструментами; байтовое соответствие строк журналов проверял `grep -n`.

## 3. Задача окна стенда: условие отмены CTO для C-36/A

Решение CTO по C-36: вариант A отменяется, если data-линия `camera_0 → перезапущенный preprocessor` через relay PM не держит поток. Тест **не требует кода** (флаг `restart_reuse_queues` уже есть; приём — `monkeypatch` как в `backend_ctl/tests/test_fencing_live.py:57-63`), поэтому он идёт **шагом 0, до слота писателя**: писатель не тратит слот до решения о годности A. Прогнан только минимум (command-груз через relay: 30/30 на прототипе против 0/30 на `main`, `BackendHarness(with_base=True)`); data-линия и потолок relay не мерились.

- **Класс и срок:** класс — `heavy`; железа не требует (сима); срок — окно стенда после дня №1 (задание полосы), но тест не требует кода и идёт ДО слота писателя C-36/A (по `machine.lock`; на Mac без `machine.lock` — только `light`-версия: один рестарт, N кадров, F не 2×). Единая строка с брифом C-36/A.
- **Исполнитель:** одноразовый стендовый скрипт (не pytest-тест набора) `backend_ctl/probes/probe_c36_cancel_condition_live.py`; пишет лид полосы Д2 (или `developer`/`tester` по его заказу); результат — таблица «контроль / A» в `docs/reports/`. Запуск: `G heavy <session> <python> -m backend_ctl.probes.probe_c36_cancel_condition_live`. Скрипта пока нет: не написан, не прогнан. Регрессионный `test_c36_relay_flow_live.py` пишет слепой tester позже.
- **Стенд:** `BackendHarness(with_base=True)`, настоящий PM; рестарт одного процесса оставляет остальных выжившими. Писатель — `camera_0`, потребитель — `preprocessor`. Живые тесты `backend_ctl` без `-m harness_smoke` пропускаются (`1 skipped` — не зелёный).
- **Не трогать** `process_manager_process.py` и `launcher/spawner.py` (зона Ф).

Шаги:

0. **Посылка.** На контроле (`restart_reuse_queues=true`) `relayed_to_hub` у `camera_0` растёт на 0; при `false` растёт. Если при `false` тоже +0, кадры идут не через relay (loan/wire-протокол: `generic_process.py:38-50` `chain_targets`; ADR-PMM-010 `:108`): критерий relay заменить на «принято/отправлено» и записать в бриф C-36/A.
1. **Нагрузка.** F = 2 × максимум суммарного fps линии через перезапускаемый процесс по рецептам 1.0; **число посчитать и записать ДО прогона.** Окно T = 60 с после ready, 3 повтора, плюс каскад из 3 рестартов подряд разных процессов. `run_gate=False` (умолчание харнесса, гейта нет, кадры идут сразу, `harness.py:108-110`); авто-рестарт выключать (`FW_AUTORESTART=0` в env стенда или `launcher._orchestrator_config["restart_policy"] = {"enabled": False}`, `process_manager_process.py:376-384`) только в (б) и в каскаде с kill (иначе `process.restart` после `kill -9` гонится с монитором и `instance_restarts` растёт на +2); оба рычага — по чтению ревьюера, не прогонялись. Контроль на текущем `main` идёт без патча (умолчание `True`).
2. **Метрики** (контроль `true` и A при одном F): отправлено камерой; принято и обработано `preprocessor` (счётчик в `introspect.telemetry` выбрать и проверить первым шагом — сейчас не выбран); `relayed_to_hub`; `errors_delivery_failed` у `camera_0`; `queue_system_evict_blocked` и `queue_data_evicted` из `drv.introspect_router_stats(proc)["router_stats"]` у `camera_0`, `preprocessor` и `ProcessManager` (читать с `assert key in router_stats`, не `.get(key, 0)`: на неверном ключе проба уже получала молчаливый 0, `g7_soak_probe.py:59-62`; relay кладёт билет в system-очередь PM из роутера отправителя, поэтому вытеснение видно у `camera_0`, а не у PM — по чтению, не проверено; разбивка `data_evicted.<жертва>` в `router_stats` не выводится, откуда её читать — не выяснено); p95 RTT `introspect.status` PM; свободные слоты кольца SHM `camera_0` до/после (риск утечки займов `_frame_loan_active` при доставке relay'ем из PM — не проверялся).
3. **Порог** (утверждает CTO ДО прогона):
   - принято_A ≥ 0,95 × принято_контроль;
   - `errors_delivery_failed` +0;
   - `queue_system_evict_blocked` (`camera_0`) +0;
   - `queue_data_evicted` (`camera_0`) ≤ контроля;
   - p95 RTT PM ≤ 2× контроля и < 1 с;
   - ни одного `unresponsive`/`crashed`;
   - свободные слоты SHM к концу окна ≥ значения до рестарта − 1.
4. **Красный по любому пункту:** умолчание остаётся `True` (B); в коде остаются проба и откат C (Р3) и метка при `reuse=false`; C-36 закрывается как вариант C. Пересмотр порога — только новым замером у CTO.

Главный риск (то, что этот тест и ловит): кадры в system-очередь PM (100 мест, never-drop) переполнят её и задержат message-loop PM — heartbeat всех детей.

Дополнительно к тесту, тоже на стенде: (б) 30 раз `kill -9` по pid из `supervision.status` у простаивающего `preprocessor`, затем `process.restart`; «глухой» = за 5 с после ready не дошло ни одной из 3 команд или ни одного из 3 элементов data; порог 0/30; контроль на `main` — предсказано ≥ 29/30 глухих (расследование: 142/142). Наблюдаемый счётчик кадров потребителя выбрать до прогона. Простой потребителя — `BackendHarness(with_base=True, run_gate=True)` без START (`harness.py:108-110, 359-366`; несовместим с `launcher_factory`), авто-рестарт выключен (`FW_AUTORESTART=0` или `restart_policy.enabled=false`).

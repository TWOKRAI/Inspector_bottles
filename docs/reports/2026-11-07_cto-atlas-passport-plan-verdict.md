## 6. Взгляд через призму «лучший инструмент для агентной разработки»

1. **Агент как пользователь.** Сильно: один вызов `ref` вместо цепочки grep→Read; фиксированный порядок шести разделов; `path:line`, пригодные для `Read`. Слабо: один символ за вызов — добавить `atlas ref a b c` (несколько id за вызов, ~10 строк) в 4.2 — это прямо снижает `calls_ratio`; немые нули и усечение — закрыты P1/P2.
2. **Доверие.** Сильно: `sha`/`scanner` в конверте, `null` ≠ `0`, `scope: prod|test`, F1 как красный. Слабо: паспорт ревизии `sha` молчит о грязном рабочем дереве агента — идея «`status.stale: [пути]`» (пересечение `git status --porcelain` с путями паспорта, ~20 строк) — нет ни в одном плане.
3. **Цикл правки.** Слабо: план отвечает «где и кто зовёт», но не «что запускать и чего нельзя задеть». `links.used_by` + `checks.tests` + правило слоя уже есть как факты — не хватает **одного вида «радиус правки»**: `atlas radius <символ>` → файлы-зависимые (prod), тесты по символу и по файлу, правило слоя, пины. Цена ~100–150 строк над `links.py`, после С1; это то, ради чего агенту нужна карта, и ни один план этого не называет.
4. **Стоимость.** Сильно: кэш по oid, тёплый 0,06 с, `--budget` по рангу; общая машина — все прогоны через гейт. Слабо: 18-минутный каталог тестов на Windows — цена каждой задачи; рукописного остаётся `modules.yaml` до Д5 и образцы потоков в конфиге.
5. **Масштаб за пределы атласа.** Сильно: три слоя с одним владельцем на факт; R1–R3 как тесты; соседи не входят. Один вход для агента — `atlas` для статики, `backend_ctl` для живого; sentrux судит слои, qex ищет по смыслу — четыре входа с разными вопросами, не дубли. Риск дубля один: `graph_slice` и `atlas map` до A2 (названо).
6. **Конкуренты.** Взято правильно: Aider (ранг+бюджет), SCIP-id, Glean-подобные факты с инкрементальным кэшем (= A1), code-graph-rag трасса (отложено). Лишнего не взято (tree-sitter при одном языке — верно). Недоиспользовано у Aider одно: **персонализированный ранг относительно файлов текущей задачи** (`--near <путь>`), у нас ранг глобальный; идея после С1, цена средняя. MCP `tools/list` как форма каталога — верно отдано Ф9.2. `[поиск]`-строки (co-change CodeScene, RepoGraph-замеры) план не использует как доводы — правильно.
7. **Измеримость.** Сильно: порог до прогона, min/max по повторам, фиксированный `repo_sha`, эталон до кода паспорта. Слабо: (а) вопросы `k0` писал тот же лид, что проектирует паспорт — риск «учить к тесту»; мера: 5 вопросов hold-out, сочинённых свежим агентом после 4.2 и до 5.1, со своим `grep-read` ×3 (+~$3); (б) Haiku как агент бенча — не тот пользователь, что Sonnet/Opus в треке; записать как ограничение; (в) Kill-1 нынешний — самообман (правка 1).
8. **Простота.** Следует: атлас не касается фреймворка (R1), прототип не задействован, FREEZE вместо KILL после правок 2/5, слоёв четыре без рантайма.

**Самые сильные выводы (5):** (1) конструкция верна и единственна — три слоя, один владелец у факта, читатель без импортов; (2) главная слабость — измерение: Kill-1 пустой, вопросы не независимы, бюджет посчитан в «неплатёжных» токенах; (3) план отвечает на «найти», но не на «безопасно изменить» — радиус правки отсутствует во всех планах; (4) честность вывода (P1–P3) — лучшее, что есть в плане, её надо довести до «рабочее дерево ≠ sha»; (5) дорогие соблазны (tree-sitter, MCP-сервер, эмбеддинги) отвергнуты правильно.

**Что сделало бы инструмент заметно лучше, чего нет ни в одном плане (идеи, не правки):** `atlas radius` (цикл правки; ~100–150 строк; мерить новым типом вопроса «какие тесты гонять»); `status.stale` против рабочего дерева (~20 строк); несколько id за вызов (~10 строк); `--near <путь>` персонализация ранга (средняя цена); hold-out набор вопросов (+~$3). Все — после С1, кроме «несколько id», которое дёшево и идёт в 4.2.

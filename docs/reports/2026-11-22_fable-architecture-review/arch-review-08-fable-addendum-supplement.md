# Дополнение к вердикту Fable 5.2: стратегия «не заменять, а дополнять» (§5.9)

Автор: cto (Fable 5.2), 2026-11-22, по сообщению лида после основного отчёта. Сохранено лидом без правок по тексту. Вставляется как §5.9 к [части 2](arch-review-07b-fable-verdict-2.0.md). Только чтение, файлы не менял, тесты не запускал.

**Вердикт по стратегии: ПРИНЯТЬ С УСЛОВИЕМ.** «Дополнять» — верное умолчание на краях системы. Для второй дороги к той же работе оно неверно.

## 5.9.1 Три стратегии рядом

| Стратегия | Когда верна | Когда вредна | Пример в проекте |
|---|---|---|---|
| Заменять | новый путь делает ту же работу и доказанно лучше; старый после этого убирают или замораживают | когда новое в статусе Beta, а старое измерено и работает | камера W4: задача 4.2b убирает старый путь Hikvision (по хэндофу лида) |
| Взять идею и сделать своё | в ядре, которым продукт отличается | в обвязке, где нет отличия | loan-протокол, seqlock, QoS уже взяты идеей |
| Дополнять | новая возможность на краю: новый канал наружу, новый сток, новый клиент, новый драйвер | когда «дополнение» — вторая дорога к той же работе | драйверы в `camera_device`, провайдеры ONNX Runtime |

## 5.9.2 Главное различие

Есть два разных «дополнения». Их нельзя оценивать одинаково.

1. **Дополнение возможностью.** Раньше пути не было, теперь есть. Zenoh для второй машины, OPC UA для ПЛК, веб-клиент по существующему протоколу, сток OTel наружу, Rerun для разработчика. Это безопасно почти без правил.
2. **Вторая дорога к той же работе.** Два транспорта для одного провода на одной машине. Два сериализатора одного сообщения. Два редактора графа. Два пути сборки изображения. Это по сути «замена в два шага», и она удваивает матрицу проверок.

Правило выводится из принципа 4 владельца: «меньше слоёв строго лучше при той же функциональности». Дополнение, которое добавляет функцию, принципу не противоречит. Дополнение с той же функцией противоречит и допустимо только как пилот со сроком и заранее записанным решением.

**Риск, который лид не назвал.** «Дополнять» плюс «заморозить, не удалять» дают рост поверхности только в одну сторону. У проекта это уже было: четыре механизма «схема → виджет», три стека привязки, шесть форм регистрации команд (по аудиту 07-04 и вердикту CTO 11-01, не пересчитывал). При семействе продуктов каждая замороженная дорога становится публичной.

## 5.9.3 Правила лида: что принять, что поправить

Согласен с четырьмя правилами лида. Поправки и добавления:

1. **Один основной путь — на работу, а не на слой.** В слое «транспорт» три работы: системная плоскость, кадры, связь между машинами. У каждой свой основной путь.
2. **Критерий повышения измерим — и рядом критерий отказа и срок.** Оба записаны до начала пилота.
3. **«Старый путь заморозить» — да. Неудавшийся новый путь удалить.** Пилот не стал контрактом, принцип 3 на него не распространяется. Для этого пилот живёт под флагом и в отдельном extra, не в публичном API. Это уточнение принципа владельца; решает владелец.
4. **Тест с настоящими объектами — да, и сильнее.** Один набор соответствия, параметризованный по всем реализациям шва. Отдельная задача CI на каждый extra с настоящей библиотекой. На приёмке фазы — ненулевой трафик через дополнение на стенде.
5. **Выбор пути — данные в одном шве** (рецепт или конфиг), не `if` по коду.
6. **Дополнение объявляет, каких гарантий шва оно не даёт.** Проверка рецепта не пускает на него провода, которым эти гарантии нужны. Пример: канал Zenoh не даёт сигнала «читатель умер» по владению очередью и возврата слотов loan; системные провода на него ставить нельзя.
7. **Сбой дополнения не тормозит основной путь.** Ограниченный буфер, сброс со счётчиком. Мёртвый коллектор OTel не должен останавливать журнал.
8. **Дополнение строится по триггеру от продукта, не впрок.** Не больше одного пилота «второй дороги» одновременно. Впрок уже строили первое поколение GUI-конструктора.
9. **У Beta-библиотек — верхняя граница версии.**

Про запись владельца «второй путь сборки изображения — дефект»: это тот же принцип. Он прямо задевает два дополнения из списка, см. строки «отладка кадров» и «клиенты GUI» ниже.

## 5.9.4 Рекомендация по слоям

| Слой (работа) | Стратегия | Основной путь | Дополнение | Условие |
|---|---|---|---|---|
| Команды и стоп на одной машине | своё, не дополнять | `mp.Queue` | нет | вторая дорога запрещена |
| Кадры на одной машине | своё | SHM-кольцо | нет; iceoryx2 только пилотом со сроком | триггер: потолок своего кольца |
| Связь между машинами | дополнять | пути нет → Zenoh третьим типом канала Router | Zenoh | триггер: вторая машина в продукте |
| Формат сообщений | идея + дополнение на краю | dict и pickle внутри | версия в конверте; msgspec или JSON на внешней границе | не второй сериализатор внутри |
| Логи, ошибки, статистика | дополнять | свой logger | сток OTel | основным не становится никогда |
| Состояние | своё | StateStore | мост для удалённых подписчиков | не второе хранилище |
| Конфиг | своё | `config_module` | нет | два конфига — дефект |
| Отладка кадров | дополнять | Qt-дисплей | Rerun как dev-extra | кадр берётся из уже собранного изображения |
| ПЛК | дополнять | Modbus | asyncua сервисом над State | протокол выбирается на устройство в рецепте |
| Клиенты GUI | дополнять | Qt-станция | веб-клиент по протоколу `backend_ctl` | одна спека UI; изображение собирает бэкенд один раз |
| Редактор графа | своё | свой редактор | нет | два редактора — дефект; замена только по измеренной боли |
| Инференс, драйверы камер | дополнять (уже так) | ONNX Runtime; `camera_device` | провайдеры; драйвер на марку | образец правильного дополнения |
| Супервизия, рецепт, контракт плагина, `backend_ctl` | своё, идеи | — | — | отличие продукта |

**Где прячется второй путь сборки изображения.** Если веб-клиент или Rerun сами рисуют оверлеи или шлюз собирает картинку отдельно от плагина отрисовки, появятся две сборки. Правило на 2.0: изображение с оверлеями собирает бэкенд один раз; Qt, веб и Rerun показывают одни и те же пиксели. Оверлеи данными — позже и тоже одним описанием.

**Итоговая формула:** дополнять на краях, своё в ядре, заменять только дубль той же работы. Двух основных путей для одной работы не держать.

# GUI-конструктор: PySide6, TypeScript или гибрид (мнение лида, 2026-11-22)

Статус: мнение лида сессии, не решение и не замер. Владелец попросил добавить в отчёт. Fable: оспорить, где неверно.
Контекст вопроса: GUI-конструктор выносится из прототипа во фреймворк (2.0); сейчас PySide6; владелец думает о TypeScript или других библиотеках; инспектор много работает с изображениями и должен быть близко к памяти.

## Почему просмотр кадров лучше оставить нативным

Браузер не может подключиться к разделяемой памяти фреймворка. Кадр пришлось бы закодировать (JPEG или H.264), отправить по WebSocket, декодировать и нарисовать. Это копии, задержка и нагрузка на CPU. В PySide6 кадр из SHM можно превратить в `QImage` без копирования. Для просмотра в полном разрешении, ROI и точной отладки пикселей это решающий довод. Веб подходит только для уменьшенного превью.

## Где веб оправдан

- **Редактор графа плагинов.** Отчёт исследователя (`arch-review-04-lib-tooling.md`) показал, что активного Qt-редактора нод для PySide6 в 2026 нет. Веб-редакторы графов (например, React Flow) зрелые и живые. Это знание лида вне отчётов, актуальность не проверена.
- **Формы, настройки, пульт оператора и удалённый доступ с планшета.** Принцип «бэкенд headless, GUI только клиент» это допускает: веб-клиент подключился бы к тому же протоколу, что `backend_ctl`.

## Варианты

| Вариант | Для чего | Цена |
|---|---|---|
| Всё остаётся на PySide6 | кадры, ROI, текущий редактор | нет новых слоёв, но редактор поддерживается самим |
| Гибрид: веб-редактор графа внутри PySide6 (`QWebEngineView` + `QWebChannel`), кадры нативные | редактор и формы в вебе | Chromium в составе, два стека, отладка сложнее |
| Dear ImGui (`imgui-bundle`) | отладка изображений, текстуры из numpy, узлы в комплекте | нестандартный вид, слабее для форм. Что узлы в комплекте, лид помнит по документации, не проверял |
| Qt Quick (QML) | декларативный конструктор на GPU | кадры из Python в QML идут тяжелее |
| Всё на TypeScript (Electron, Tauri) | удалённый пульт | кадры только через кодирование и копирование |

## Что советует лид

1. Оставить PySide6 для всего, что смотрит на кадры. Это требование «близко к памяти».
2. Описывать UI данными, а не кодом виджетов: схемы регистров, раскладка пульта, граф плагинов в декларативном виде. Тогда отрисовщик заменяем: сегодня PySide6, позже веб-клиент, не трогая фреймворк. Это сильнее любого выбора библиотеки и вписывается в слои «фреймворк толстый, приложение тонкое».
3. Веб подключать только по замеру боли. Если собственный редактор нод устраивает, не трогать. Если станет слишком дорогим в поддержке, пробовать гибрид для одного редактора, не для всего GUI.
4. Принцип владельца «меньше слоёв строго лучше» работает и здесь: каждый новый стек GUI удваивает отладку.

## Что не проверено

- Затраты на `QWebEngineView` на железе владельца не измерены.
- Зрелость веб-редакторов графа взята из знания лида, не из отчётов.
- Наличие узлового редактора в `imgui-bundle` не проверено.
- Zero-copy из SHM в `QImage` в текущем коде проекта лид не проверял; проверить по `frontend_module` и путям чтения кадров.

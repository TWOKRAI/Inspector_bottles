### 7. 1.x и 2.0 параллельно — отвечаю, с возражением.

Параллельное второе дерево для одного инженера — классический отказ: две кодовые базы, починки расходятся, 2.0 не достигает паритета и остаётся хобби. Проект уже отклонил `multiprocess_prototype_2` по этим причинам (`app-template-idea.md` §5, по записи). Рекомендация:

- **Форма.** 2.0 — не второй каркас, а набор заменяемых частей за швами 1.x в том же репозитории. Каждая часть попадает в приложения 1.x, когда выигрывает замер.

- **Починки.** Сначала в 1.x, потом перенос в 2.0. Никогда наоборот.
- **Совместимость.** 2.0 читает рецепты 1.x через цепочку миграций и плагины 1.x через диапазон `api_version`.
- **Плагины.** Общие, не ветвить: в них ценность продуктов.
- **Бюджет.** 20–30% недели и только после двух приложений в работе. У каждой части — критерий отказа.

## B. Защитим ли довод «Python-оркестрация + нативные горячие узлы» против «всё на C++»

**Да — для этого класса задач: 30–100 fps, 1–8 камер, робот по шине с циклом 10–100 мс, пульт, частая смена рецепта.** Это обычная архитектура отрасли (ROS 2, DeepStream, Halcon). Тезис «Python не медленнее C++» защитить нельзя. Защитим другой: «система выполняет требования ячейки при меньшей цене разработки, и любой узел уходит в нативный код по замеру».

**Где C++ выигрывает на самом деле:**
1. Хвосты задержки и детерминизм. Нет GC и GIL, есть потоки реального времени. У проекта до `gc.freeze` был выброс p99 33,7 мс (по записи).
2. Цена на элемент. Десятки микросекунд на сообщение в Python. При 100 fps терпимо, при 10 тыс. сообщений в секунду нет.
3. Один процесс и указатели вместо хопов. Меньше копий, меньше памяти, быстрый старт.
4. Развёртывание: один бинарник, проще защита кода.
5. Проверка типов при компиляции по всей системе.
6. SDK камер и GPU-тракт — C/C++ в первую очередь.
7. Старт и память: каждый Python-процесс с numpy, OpenCV и torch тяжёл (сотни МБ — не проверено).

**Где выигрывает подход Python:**
1. Время до первого работающего стенда и скорость правки. С агентами разрыв больше.
2. Обучение и инференс в одной экосистеме.
3. Тяжёлая работа уже нативная (OpenCV, ONNX Runtime). Доля Python — клей. **Число не измерено (B-3).**
4. Изоляция сбоев. Надёжная система на C++ с чужими SDK тоже станет многопроцессной и заплатит за IPC. Это главный контрдовод монолиту.
5. Классы дефектов. Оба жёстких краха в памяти проекта пришли из нативного кода: numba без проверки границ (`0xC0000374`) и серый кадр в Qt (`0xC0000005`) (по записи).
6. Найм: плагин на Python может править технолог или ML-инженер.

Честная оговорка: каркас в 160 тыс. строк имеет bus factor 1 на любом языке.

**Гибрид, который убедит коллег:**
- **Шов для их кода.** Формат SHM и протокол управления документом (B-5). Коллега пишет узел на C++ и включает его в тот же рецепт. Спор «или–или» превращается в «по узлу, по замеру».
- **Правило перехода.** Узел уходит в нативный код, если клей Python больше X% его цикла или джиттер p99 больше Y мс от требования.
- **Жёсткое реальное время вне ПК.** Аппаратный триггер камеры, слежение за лентой в контроллере робота (`CVT_JOB`). Проект уже так устроен. Это сильнейший довод: Python задаёт уставки, а не крутит сервоконтур.
- **Нативные узлы — на C++, раз коллеги его хотят.** Каркасу язык за швом безразличен.

Предупреждение: цель «самая универсальная и самая быстрая система, чтобы показать превосходство» содержит конфликт. Универсальность и предельная скорость тянут в разные стороны. Спор «лучше C++ во всём» проигрывается. Выигрывается спор по требованиям.

## C. План доказательств

**Правила, чтобы результат нельзя было отбросить:**
1. Вопросы, нагрузки, метрики и пороги записаны и согласованы с коллегами до замеров.
2. Одно железо, одна ОС, один источник кадров, один файл модели, одна сборка OpenCV, одинаковое число потоков.
3. Базовый вариант на C++ пишет или настраивает сторонник C++. Его часы записываются.
4. Не меньше пяти повторов; p50, p99, максимум; CPU и память; сырые данные и скрипты открыты.
5. В таблице есть строки, где Python заведомо проигрывает (старт, память).

| # | Нагрузка | Метрики | С чем сравнивать |
|---|---|---|---|
| W1 | Транспорт: 480p, 720p, 1080p, 5 Мп × 1/3/5 хопов × 30/60/100 fps (расширенный B-2) | p50, p99 на хоп, CPU, копии | C++ в одном процессе (ноль) и C++ в нескольких процессах |
| W2 | Цикл плагина: пустой и типовой (B-3) | мс каркаса против мс тела | та же операция в цикле C++ |
| W3 | Ячейка целиком: 1, 2, 4 камеры 1080p → подготовка → ONNX → решение → задание роботу, 1 час | потолок fps, «триггер → результат» p50/p99/макс, CPU на камеру, память, потери кадров | тот же тракт на C++, один процесс, потоки |
| W4 | Сбой: kill -9 узла камеры; прогон 24–72 ч | время восстановления, живы ли соседи, утечки | монолит C++ |
| W5 | Цена разработки: чистая машина → стенд; добавить шаг инспекции | часы, изменённые строки, дефекты за неделю | та же задача стороннику C++ |
| W6 | Холодный старт и смена рецепта | секунды | то же |

**Когда владелец уступает часть:**
- W2: клей Python больше 20–30% цикла на целевом fps → горячий путь этих узлов уходит в нативный код.
- W3: p99 «триггер → результат» выше требования, и причина в Python или IPC, а не в инференсе → ядро тракта (источник → инференс → решение) становится одним нативным процессом.
- W1: на 1080p × 3 хопа транспорт больше 10% бюджета кадра или больше одного ядра → меньше хопов, передача ссылок, пилот iceoryx2.
- W6: старт или смена дольше требования → постоянные процессы, ленивый импорт.
- W5: сторонник C++ добавляет шаг не дольше чем в 1,5 раза → довод о скорости разработки для этой команды снимается.
- W4: сбоев нет ни у кого за 72 ч → вес довода об изоляции снижается.

**Когда уступают коллеги** (записать заранее): клей меньше 10%, p99 в требовании, W5 быстрее в 2 раза и более → гибрид остаётся.

Пороги выше — мои предложения, не данные. Их задаёт требование ячейки: при ленте 200 мм/с джиттер 10 мс равен 2 мм.

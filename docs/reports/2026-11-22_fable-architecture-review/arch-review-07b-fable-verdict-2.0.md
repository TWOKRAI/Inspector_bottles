# Вердикт Fable 5.2, часть 2: советы на 2.0 (§5)

Часть вердикта Fable 5.2 от 2026-11-22. Разделы §5.1–§5.8; дополнение §5.9 («дополнять, не заменять») в [arch-review-08-fable-addendum-supplement.md](arch-review-08-fable-addendum-supplement.md). Индекс: [arch-review-07-fable-verdict.md](arch-review-07-fable-verdict.md).

## 5. Советы на 2.0

### 5.1 Состав 2.0
1. Второй продукт в `apps/`, собранный по шаблону. Он задаёт требования, а не вкус.
2. GUI-конструктор во фреймворке: спека UI v1 (данные) + эталонный отрисовщик на Qt + `examples/minimal_gui` (сегодня его нет, проверено).
3. Фреймворк как версионируемый пакет; продукты закрепляют диапазон версии.
4. Ядро управления: каталог команд с `access` (ваше решение 11-01).
5. Второй фронт по тому же протоколу: веб-пульт для планшета.
6. По триггеру: нативный узел через документированный SHM; Zenoh на границе машин; OPC UA.

### 5.2 Стратегия «взять всё лучшее и сделать лучше» и правило лида

**Оценка стратегии.** Как лозунг она опасна для одного инженера: рамки не ограничены. За каждым из названных продуктов 20–500 человек и 10+ лет. «Лучше всех во всём» недостижимо. Достижимо «лучше в одном, достаточно хорошо в остальном».

**Где «лучше» реально** (там, где конкуренты слабы по устройству):
- время от чистой машины до работающего стенда на Windows без Docker для инженера с агентом;
- управляемость агентом: живую систему можно осмотреть, изменить и проверить исход (`backend_ctl`);
- связка «камера + сеть + робот + ПЛК + пульт» в одном рецепте;
- изоляция сбоя устройства (против Node-RED и однопоточных конструкторов);
- открытый контракт плагина и цена (против Cognex/Halcon).

**Где «лучше» нереально и не нужно:** латентность транспорта против iceoryx2; межмашинная маршрутизация против Zenoh/DDS; GPU-тракт против DeepStream; библиотека алгоритмов зрения против Halcon/Cognex; жёсткое реальное время против TwinCAT; визуализация против Rerun; число готовых узлов против Node-RED и драйверов против ROS 2.

**Правило лида** («идея — своё только в отличии; код — зависимостью для обвязки; „лучше“ измеримо») верно. Три поправки:
1. **Зависимость только за своим швом и только зрелая:** стабильный релиз, Windows первым классом, набор соответствия, замена одним адаптером. Иначе это не экономия, а долг (примеры из ваших же документов: харвестеры без релизов, форк NodeGraphQt, смена лицензии Nuitka).
2. **Правило действует на новый код.** Уже написанная и измеренная обвязка бесплатна, пока её не растят. Замена стоит денег.
3. **Мерило — планка «достаточно», а не «лучше X».** И лимит: одна заимствованная идея в работе, у каждой критерий отказа.

| Источник | Взять идеей | Взять кодом | Мерило |
|---|---|---|---|
| ROS 2 | версии типов сообщений, QoS-профили, запись и повтор | ничего; мост по триггеру | сессия 10 мин повторяется с тем же журналом |
| DeepStream / Savant | батч N камер в один инференс | ONNX Runtime + EP | кадров/с при N камерах |
| Node-RED | составной узел, «применить изменённое» | ничего | правка узла не рестартит остальные |
| Cognex / Halcon | настройка на живом кадре, pass/fail, галерея брака | anomalib, OpenCV | пропуск брака и ложные на наборе |
| TwinCAT | ПЛК первым классом, дедлайн «триггер → результат» | asyncua в `Services/opcua` | p99 отклика, мс |
| iceoryx2 / Zenoh | уже взято (loan, seqlock, glob-ключи) | позже, за швом | p99 хопа 1080p на своём стенде |
| Rerun | — | `rerun-sdk` как dev-extra | свой просмотрщик не писать |

Список идей у вас уже есть: N-1…N-5 в `backlog.md`. Нужен не новый список, а порядок: N-1 (версии) → N-2 (pass/fail, вместе с продуктом №2) → N-5 (OPC UA).

### 5.3 Готовое и своё

- **Своё, развивать:** рецепт и топология, супервизия, контракт плагина, StateStore, `backend_ctl`, device hub, спека UI и Qt-отрисовщик, line-sim.
- **Своё, заморозить (работает, не растить):** Router, очереди, SHM-кольцо, `Message`, logger/error/statistics.
- **Готовое уже сейчас:** OpenCV, ONNX Runtime, pymodbus, pydantic, numba, OTel как экспорт.
- **Готовое по триггеру:** Zenoh, asyncua, msgspec (внешняя граница), PyO3, iceoryx2, React Flow.
- **Не брать:** ROS 2 целиком, dora как основу, Hydra, акторные фреймворки, WASM как рантайм, Electron/Tauri для станции инженера.

### 5.4 Транспорт: когда и как менять

**Когда.** Три триггера, любой один:
- в продукте появилась вторая машина → Zenoh третьим типом канала Router, только на межмашинных проводах;
- нативному узлу нужны кадры → сначала свой документированный SHM (п. 5 из §4); iceoryx2 — только если своё кольцо упёрлось и у iceoryx2 вышел 1.0 с Windows первого класса;
- дефекты транспорта съедают заметную долю квартала.

**Как.** Через набор соответствия (п. 6 из §4). Флаг на провод в рецепте. A/B на одном стенде одним пробником: p99 на 1080p, kill -9 читателя, рестарт процесса. Системную плоскость (команды, стоп) на одной машине не менять никогда.

Чужой замер (iceoryx2 ~12 мкс против Zenoh 127–464 мкс на 1–4 МБ) сделан на ROS 2 C++, в одном процессе, среднее, в VM (не проверено, отчёт 02). Для вашего случая это не довод.

### 5.5 Free-threading, субинтерпретаторы, WASM, Rust

- **Free-threading.** Роль: параллельность лёгких плагинов внутри одного процесса. Процессы не заменяет. Триггер пилота для headless-процессов: t-колёса `opencv-python` и `onnxruntime` под Windows (второе не проверено). Qt здесь не блокер.
- **Субинтерпретаторы.** Роли нет. Падение нативного SDK убивает все интерпретаторы процесса. Статус NumPy в них неизвестен (не проверено), и это уже не важно.
- **WASM.** Только песочница для чужих плагинов чистой логики (dict → dict). Триггер: первый сторонний автор плагинов. До этого наблюдать.
- **Rust.** Сначала функция через PyO3 внутри процесса, как сделано с numba. Триггер: профиль цикла плагина (B-3, не сделан) показывает Python узким местом, или требование > 200 fps. Отдельный нативный узел — после B-5 и версии конверта.

### 5.6 Стек GUI-конструктора и мнение лида (`arch-review-01b`)

**Рекомендация.** Станция инженера остаётся на PySide6. TypeScript — второй фронт для оператора, а не замена.

| Часть | Отрисовщик | Причина |
|---|---|---|
| Просмотр кадров, ROI, пиксельная отладка | нативный Qt | нет кодирования, точные пиксели, нет лишнего процесса |
| Редактор графа | свой на `QGraphicsScene` до конца 2.0 | работает, мал (`graph_scene.py` 457 строк, проверено по одному файлу) |
| Формы, настройки | из спеки UI; Qt сейчас | данные, а не код виджетов |
| Пульт оператора, планшет, удалённый доступ | веб (TypeScript) через шлюз по протоколу `backend_ctl` | здесь веб сильнее; кадры — уменьшенное превью |
| Отладка многокамерного тракта | Rerun | готовое, своё не писать |

**Где лид прав:** кадры нативно; UI данными; веб по замеру боли.

**Где лид неточен:**
1. **«QImage из SHM без копии — решающий довод».** В текущем коде копия есть: `frontend_module/widgets/image_panel.py:40` делает `.copy()`, презентеры прототипа оборачивают `rgb.data` после преобразования цвета (проверено по строкам grep, путь целиком не читал). Одна копия 6 МБ стоит около 1 мс (оценка). Решает не «ноль копий», а отсутствие кодирования и потерь. Довод верный, обоснование нет.
2. **«Нет живого Qt-редактора нод» — слабый довод за веб.** У вас свой редактор, и он недорог. React Flow жив (`@xyflow/react` 13.0.2, MIT, проверено) и удобнее, но тянет Node-сборку, мост и второй отладчик.
3. **В таблице вариантов нет главного: два фронта, один протокол.** Встраивание веба в Qt (`QWebEngineView` + `QWebChannel`) — худшее из двух для упаковки. Если веб, то отдельным клиентом через шлюз. Прецедент в проекте есть: `Plugins/sim/pult_web` (проверено: существует; код не читал).
4. **«Два стека удваивают отладку»** в 2026 слабее, чем считает лид: агенты пишут TypeScript хорошо. Реальная цена — мост и упаковка, не язык.
5. **QML недооценён, ImGui переоценён.** QML уже внутри PySide6 и сам является «UI данными». ImGui годится только для внутренней отладки, а её закрывает Rerun. Ни то ни другое сейчас не вводить.

**Всё на TypeScript (Electron/Tauri):** нет. Браузер не видит SHM. Путь «Rust читает SHM и отдаёт текстуру» возможен, но это исследование, не продукт.

**До любого решения о веб-просмотре кадров** — замер за один день: 1080p, 30 fps, JPEG и сырые байты по WebSocket, нагрузка ядра и задержка. Все мои числа здесь — оценки.

### 5.7 UI данными

Да, это самое сильное решение, и вы на полпути: `ControlSpec`, `FieldMeta`, `GuiAppSpec`, контекст виджета с четырьмя каналами. Чтобы отрисовщик стал заменяемым:
1. Спека — чистые данные: JSON, версия, без типов Qt и без Python-вызовов.
2. Контекст виджета — протокол, а не объект Python. Тогда TypeScript реализует его поверх сокета.
3. Канал кадров абстрактный: ссылка на кадр. Qt читает SHM, веб просит у шлюза превью.
4. Тест соответствия: одна и та же спека проходит обход без Qt.
5. Предел: формы, панели, раскладка, граф. Без языка выражений сверх простых условий. Особые виджеты остаются кодом с идентификатором.

Порядок: сначала `examples/minimal_gui` как второй потребитель (ваше правило от 09-26), потом вынос.

### 5.8 Продукты, плагины, версии

- **Не обобщать по одному примеру.** Механизм входит во фреймворк при втором потребителе, обобщается при третьем. Сегодня потребителей три: прототип, `apps/line_sim`, `examples/minimal_app` (проверено: существуют). Все от одного автора.
- **Шаблон продукта.** `app_module` + `minimal_app` есть. Генератор `app new` — после замера P-2: его список трений и есть ТЗ генератора. Продукты в `apps/<имя>`, CI гоняет смоук каждого против HEAD фреймворка.
- **Словарь плагинов.** 58 файлов `plugin.py` в `Plugins/` (проверено). Часть из них продуктовая (например `word_layout`). Правило: плагин живёт в продукте, в общий словарь переходит при втором использовании. Идентификатор `<набор>.<имя>` + версия. Рецепт хранит имя и версию. Сейчас достаточно метки области, файлы не двигать.
- **Версии контрактов.** Механизм манифеста плагина во фреймворке есть (`process_module/plugins/manifest.py`, проверено по grep; объявляют ли версию сами плагины — не проверено). Нужны: semver фреймворка, версия конверта, диапазон `api_version`, миграции рецепта, дифф CAPABILITIES в CI с меткой «ломающее», одна минорная версия с предупреждением перед удалением.

## 1. Прямой ответ владельцу

2. **Свой транспорт был верным решением на старте и остаётся приемлемым сегодня.** Он измерен, работает и занимает малую долю кадра. Обе «готовые замены» сегодня в статусе Beta (проверено, §6). Менять его сейчас — потратить недели и получить чужие дефекты вместо своих, уже найденных.
3. **Главное вложение — не строки кода, а проверенное поведение.** Матрицы инъекций, владение стопом, контракты исхода. Код в 2026 дёшев, проверенное поведение дорого. Оно переживёт смену любой библиотеки, если швы сделаны правильно.
4. **Что было ошибкой масштаба.** Фреймворк вырос до 159 тыс. строк (проверено) раньше, чем появился второй потребитель. Часть сделана впрок и осталась без потребителей (первое поколение GUI-конструктора, по вашей же памяти от 09-26). Обвязка процесса (планы, карты, гейты, ~220 worktree) стала третьим продуктом.
5. **Настоящее слабое место — отсутствие версий на швах и отсутствие второго продукта.** Поля версии в конверте IPC нет (проверено: 0 совпадений). Вы объявили семейство продуктов. Без версий первое же ломающее изменение ударит по всем продуктам сразу.
6. **Как оставаться актуальным.** Не гнаться за библиотеками. Сделать пять-шесть швов с версией и набором соответствия. Тогда любую библиотеку можно подключить за шов, когда она созреет. Актуальность даёт заменяемость, а не новизна.

## 2. Тезис лида: где верно, где нет

**Верно:** транспорт не узкое место; Zenoh только каналом для второй машины; WASM не замена; процессы нужны для изоляции сбоев; работающее не переписывать; слабое место — доказательства продукта.

**Где разбор лида ошибается или льстит:**

1. **«С нуля короче на 30–40%» не подтверждается.** Слои, которые лид «заменил бы»: транспорт 19,6 тыс. строк (`router` 6 856 + `shared_resources` 6 516 + `channel_routing` 6 195), `message` 2,2 тыс., логи/ошибки/статистика 14,9 тыс., конфиг 2,0 тыс. Итого 38,6 тыс. из 159,3 тыс. = **24%** (проверено, `wc` по .py без тестов). Это потолок, если бы замена стоила ноль строк. С адаптерами реальная экономия 10–15% (моя оценка, не проверено). Масса лежит в «своём»: `process_module` 35,1 + `frontend_module` 25,6 + `process_manager_module` 17,3 = 78 тыс. = **49%** (проверено).
2. **HTML-схема 2 противоречит брифу лида.** В брифе: «Zenoh только третьим каналом, замена очередей рискованна». На схеме: Zenoh единая шина под всем, GUI и ProcessManager — пиры, в таблице «Транспорт: заменил бы». Владелец увидит схему, а не оговорку.
3. **Транспорт не чистый шов.** В очередях живёт семантика супервизии: `ReaderGoneQueue`, запрет переиспользовать очередь убитого ребёнка (C-36), инкарнации, loan-протокол с возвратом слотов после kill -9. По карте ядра 208 из 426 импортов идут вглубь мимо `interfaces.py`, `process → router` 11 из 14 (по записи 2026-10-26, не пересчитывал). Общая шина pub/sub этого не даёт; пришлось бы строить заново и заново ловить L-9, C-36, C-82.
4. **«Логи → stdlib + OpenTelemetry» — неверно.** Логи в Python-реализации OTel имеют статус Development (не проверено, отчёт 04). В проекте уже есть правильная форма: `Services/otel_export` (проверено: каталог есть). Июльский аудит прямо сказал: не переписывать журнал на OTel SDK, только экспортёр. Свой журнал несёт то, чего у OTel нет: контракты исхода и свежести для агента.
5. **«Message → msgspec» решает не ту задачу.** Скорость не болит: receive p50 0,001 мс (по записи, `baseline.md`). Болит отсутствие версии контракта. msgspec полезен на внешней границе (сокет, чужой язык), а не вместо pickle в `mp.Queue`.
6. **«Готового аналога на Python нет» — слишком сильно.** dora-rs дошёл до 1.x: YAML-граф, узлы на Python и Rust, SHM (не проверено, отчёт 05). Это аналог нижней и средней трети. Windows у него «best effort», GUI, рецептов с пультом, device hub и `backend_ctl` нет. Замена не нужна, но день на разбор идей оправдан.
7. **«Free-threading блокирует Qt» — неточно.** Qt нужен только процессу GUI. Дочерним headless-процессам мешает другое: у `opencv-python` нет t-колёс (проверено: 5.1.0.95, все колёса abi3). У PySide6 6.12.0 тоже все 5 колёс abi3 (проверено).
8. **Триггер «iceoryx2 v1.0» плохой.** Релиз не причина. v1.0 не вышел: 0.10.1 от 2026-11-20, Beta (проверено). И iceoryx2 даёт ту же схему, что у вас уже есть (loan + seqlock + чтение без копии). Выигрыш — чужая поддержка, не скорость.
9. **P-1 и P-2.** Лид прав, но не договаривает: 1.0 в текущем определении P-1 в исходной формулировке не закрывает («брака в 1.0 нет», решение 24), а P-2 в строках 1.0 отсутствует.

Числа лида: «~0,3 мс p50 на хоп, < 5% кадра» — сходится с записью (restore p50 0,05 / p99 0,16–0,21 мс; receive 0,001 / 0,004; send 0,23 — по аудиту 09-04). Оговорка: 640×480, синтетика, Windows, один хоп. Для 1080p по хопам сетки B-2 нет. В плане транспорта записано, что на 1080p при 100 fps транспорт держит, упираются источник и вычисления (по записи, `phase-4.md:185-194`; сам аудит не открывал).

## 3. Что такое «1.0»

Определение есть. **1.0 = «прототип 1.0»** (решения 23, 24, 25, 27 в `plans/queue/decisions.md`; строки 1–27.1 очереди `ORDER.md`; приёмка `plans/release-1.0/plan.md`). Сценарий: слово на пульте → диски с буквами → камера читает букву и угол → робот v2 берёт, доворачивает, кладёт. Веха α (сим, журнал) закрыта по механизму 2026-11-12, точность открыта. Веха β (MVS + робот) ждёт железа.

**Чего в определении нет:** «1.0 фреймворка». Нет списка замороженных контрактов, нет своей версии пакета фреймворка (`pyproject`: один пакет `inspector-bottles` 0.1.0, проверено). **Моё допущение и предложение:** считать 1.0 закрытым двумя шагами — β прототипа и тег заморозки контрактов фреймворка (п. 4 ниже).

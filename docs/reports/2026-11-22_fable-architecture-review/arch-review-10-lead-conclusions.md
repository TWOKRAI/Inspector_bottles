# Выводы лида по ревью архитектуры: что решено, что открыто, что дальше

Дата: 2026-11-22. Автор: лид сессии (Claude Sonnet 5.5) по просьбе владельца. Статус: выводы, не решения; решения принимает владелец. Основа: вердикт Fable 5.2 ([индекс](arch-review-07-fable-verdict.md), [ответ на возражения](arch-review-09-fable-reply-and-cpp-debate.md)), пять отчётов исследователей (02–06), схемы ([HTML](arch-review-01-architecture-schemes.html)).

## 1. Контекст владельца (со слов владельца в сессии)

- Идёт довоз 1.0 как есть. Затем несколько приложений на нём, 2.0 параллельно с улучшенной системой.
- Цель: максимально универсальная, эффективная, производительная система; показать коллегам, что подход лучше, чем писать всё на C++.
- Целевая архитектура по желанию владельца: **Python как оркестратор, нативные части на Rust или C++.**
- Будет не один продукт, а семейство продуктов. GUI-конструктор выносится из прототипа (2.0), сейчас на PySide6; рассматривается TypeScript как дополнение.
- Принцип: дополнять, а не заменять; брать лучшее у других и улучшать.

## 2. Согласие лида с вердиктом (после ответа Fable)

Согласен:
- ядро верное, главная ценность — проверенное поведение;
- транспорт, журнал и сообщения заморозить, дополнять только на краях и по триггеру (Zenoh и iceoryx2 в Beta);
- слабые места: нет версий на швах (в конверте IPC поля версии нет, проверено) и нет второго продукта;
- B-2 (цена хопа на 720p и 1080p) и B-3 (доля Python в цикле плагина) идут до остального;
- форма 2.0: части за швами 1.x в одном репозитории, а не второе дерево;
- довод против C++ защитим в форме «выполняет требования ячейки при меньшей цене разработки, узел уходит в нативный код по замеру».

Оговорки лида:
- «транспорт держит» пока гипотеза (замер 640×480, один хоп) до B-2;
- если клей Python в цикле плагина окажется больше 20–30% (B-3), гибрид придётся пересматривать;
- независимость вердикта низкая: Fable и лид — модели одной семьи; довод коллег владельца не известен никому;
- цены в днях — суждения; точные числа даёт `manager`;
- статистика обвязки процесса (58% коммитов — документация, 264 worktree) косвенная;
- статусы библиотек из отчётов Haiku в части не перепроверены.

## 3. Нативные узлы: формы и швы

Четыре формы: (1) расширение внутри процесса (PyO3, pybind11, nanobind); (2) отдельный нативный процесс-узел в рецепте; (3) библиотека через C-ABI; (4) сервис по сокету. Начинать с формы 1, она не требует новых контрактов. Форма 2 нужна, когда коллеги пишут целые узлы.

Для формы 2 нужны документами: формат SHM-кольца и заголовка кадра с автономным читателем (B-5); версия конверта сообщений; протокол управления (команды, стоп, «жив», инкарнация, возврат слотов loan после `kill -9`); манифест плагина с `api_version`; один набор соответствия для Python- и C++-узлов.

Rust или C++ (мнение лида): C++ там, где его требуют SDK камер, OpenCV, CUDA, TensorRT и код коллег; Rust для новых небольших горячих библиотек внутри процесса (оба жёстких краха проекта пришли из нативной памяти). Контракт один на оба языка.

Не проверено: как сегодня устроены протокол управления и возврат слотов loan на нативной стороне; это нужно прочитать в коде до проектирования формы 2.

## 4. Решения за владельцем

1. Что считать «1.0 фреймворка»: тег заморозки контрактов после β прототипа?
2. Принять ли форму 2.0 «части за швами 1.x» вместо параллельного дерева?
3. Какой продукт №2 и из какого домена?
4. Заморозить ли полосу механизмов (атлас, доставка памяти, панель планов, механизм коммитов) до продукта №2?
5. Уточнить принцип 3 (FREEZE, не KILL): неудавшийся пилот «второй дороги» удаляется, а не замораживается?
6. Кому из коллег задать вопрос «по каким критериям вы примете результат» (до замеров).
7. Заказывать ли у Fable контракт нативного узла (§3) как заготовку для `docs/direction/`.

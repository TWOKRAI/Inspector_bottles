# Карточка модуля в base_manager: один источник команд для всех

Дата: 2026-11-01. Автор: основная сессия Claude по запросу владельца. Это проект, не решение: ничего не запускалось и не прототипировалось.
Продолжает `2026-11-01_control-core-vision-and-review-brief.md` и уточняет его: «ядро инструментов» оказалось не новым модулем, а контрактом в `base_manager` плюс таблицей в `CommandManager` (раздел 3).

## 1. Что сказал владелец

1. Нужен один универсальный инструмент в `base_manager`, доступный всем модулям. Образец: карточки модулей в Atlas (`python -m scripts.atlas card <модуль>`).
2. `CommandManager` берёт команды из карточек. Раньше владелец считал, что через него каждый процесс умеет управлять всеми модулями; новая карточка несёт ещё и общую информацию о модуле.
3. `console_module` задуман как терминал разработчика: аналог `backend_ctl`, но внутри процесса, плюс видимая среда каждого процесса (логи, ввод команд в `CommandManager`). Модуль полезен, хоть и редко используется.
4. Слои добавлять можно, только при необходимости. Лаконичность лучше.
5. `stats`, `state_store`, `console` регистрируют команды каждый по-своему. Они должны идти тем же путём, что остальные.
6. Все сервисы строятся на `service_module`, а он стоит на `BaseManager` (раздел 4а).
7. Лучше формировать правильные интерфейсы и импортировать интерфейсы каждого модуля: так сбор автоматизируется (раздел 3а).

## 3. Предложение: ядро уже есть, его надо собрать

Три части, ни одного нового модуля.

```
base_manager/interfaces.py   CommandSpec   — объявление одной команды (чистые данные, stdlib)
base_manager/core            BaseManager.command_specs() -> ()     — крючок, по умолчанию пусто
command_module               CommandManager.register_from(owner)   — читает объявления и регистрирует
process_module (boot)        для каждого зарегистрированного менеджера: command_manager.register_from(m)
```

`CommandSpec` (замороженный dataclass, поля — данные):

| Поле | Назначение | Замена чего |
|---|---|---|
| `name` | `семья.действие`, например `worker.stop` | строка в `register_command` |
| `handler` | вызываемое, привязанное к владельцу | то же |
| `description` | одна строка | `metadata["description"]` |
| `tags` | теги | `tags=[...]` |
| `access` | `read` / `write` / `escalated` / `destructive`, по умолчанию `write` | `READ_SAFE_COMMAND_PREFIXES` в `backend_ctl` (команды через `send_command`). `TOOL_SAFETY` для 53 типизированных инструментов остаётся: `ToolSpec` без записи в нём роняет импорт (`mcp_tools.py:1658`) |
| `params` | схема параметров или `None` | запись в `command_contracts.py` |
| `executor`, `key_from`, `targets` | как в `register_command` | то же |

Общая информация о модуле отдельным полем не вводится: её отдают существующие `get_stats()` и `get_debug_info()`. Вместо команд «по одной на модуль» процесс регистрирует одну пару: `module.list` (какие менеджеры есть, их состояние) и `module.info {name}` (stats + debug_info). Любой менеджер, зарегистрированный в процессе, становится управляемым без единой строки своего кода — это и есть «блок с розеткой». Сейчас процесс регистрирует 9 менеджеров: worker, logger, stats, observation, command, router, console, error, executors (`process_managers.py:172-200`). `StateStoreManager`, `RegistersManager`, `PluginManager` и другие в этот реестр не входят: чтобы попасть в `module.list`, их надо зарегистрировать (раздел 6, п. 7).

Что получаем:
1. Одно место объявления вместо трёх для команды процесса (регистрация, контракт параметров, префиксы безопасности в клиенте).
2. `backend_ctl`, консоль, будущие CLI и REPL читают один каталог `introspect.capabilities`. Класс безопасности команд, идущих через `send_command`, приходит из каталога, а не из префиксов в клиенте.
3. Новая команда с объявлением видна клиентам без правки клиента, если её вызывают через `send_command` или консоль.

Чего это НЕ решает: 53 типизированных инструмента MCP в `mcp_tools.py` (отдельный реестр №2) по-прежнему пишутся вручную, каждый со своей записью в `TOOL_SAFETY`. Сокращать их или генерировать из каталога — отдельное решение, в этот проект не входит. Четыре класса `access` совпадают с классами `TOOL_SAFETY`; уровни L0–L3 с прошлой страницы — это правила политики поверх классов, они появятся позже.

Что остаётся снаружи, без изменений: сессионные инструменты `backend_ctl` (курсоры событий, `await_condition`, рекордер, аудит, реконнект), потому что они живут на клиенте, а не в процессе. Свод по процессам остаётся за ProcessManager (`capabilities_extra`) и `driver.capabilities()`.

### 3а. Интерфейс как источник (предложение владельца, принято)

Идея владельца: формировать правильные интерфейсы и импортировать интерфейсы каждого модуля, тогда сбор автоматизируется. Проверил: у каждого из модулей `multiprocess_framework/modules/` есть `interfaces.py` с `__all__`. Правило проекта «внешние модули импортируют только из `interfaces.py`» уже делает интерфейс стабильной поверхностью.

Как это работает:

1. **Отметка на методе интерфейса.** В `base_manager/interfaces.py` (stdlib) добавляется маркер `@expose(access="read", description=...)`. Он ставится на абстрактный метод в `interfaces.py` модуля и не требует правок в реализации. Пример: `IConsoleManager.show` помечен `@expose(access="write")`.
2. **Сбор по живому объекту.** `register_from(obj)` обходит `type(obj).__mro__`, берёт классы из модулей `*.interfaces`, находит помеченные методы и берёт у объекта привязанные реализации. Имя команды по умолчанию `<id модуля>.<метод>` (`console.show`), коллизий между модулями нет. Описание — первая строка docstring, параметры — из сигнатуры метода.
3. **Статический сбор без запуска.** Тот же код импортирует `<модуль>.interfaces` и даёт API и список команд для Atlas и документации.
4. **`command_specs()` остаётся запасным выходом** для обработчиков, которым нужно всё сообщение целиком, исполнитель (`executor`, `key_from`, `targets`), динамические команды или перенос старых имён без префикса (`get_metrics`, `set_enabled`). Оба пути дают один и тот же `CommandSpec`.

Что это даёт: описание API модуля больше не пишется отдельно, потому что интерфейс уже есть, а команды объявляются отметкой на строке метода.

Границы идеи:

- **Интерфейс не знает, что безопасно открывать наружу.** Поэтому отметка явная (`@expose`), по умолчанию метод не виден. Класс доступа автоматически не вывести.
- **Метод и команда говорят на разных языках.** Метод принимает типизированные аргументы, команда получает `dict` (правило «Dict at Boundary»). Автоадаптер возможен только для параметров, которые передаются как JSON (строки, числа, словари). Методы с обратными вызовами (`enable_input(callback)`) не помечаются. Схема параметров из сигнатуры через Pydantic v2 не прототипировалась.
- **Протоколы без наследования.** MRO-обход находит интерфейсы только у классов, которые их наследуют (`ConsoleManager(IConsoleManager)`). Структурные реализации `IService` по MRO не найдутся; их закрывает `BaseService`, который наследует.
- **Большая часть существующих команд — приватные `_cmd_*` в `BuiltinCommands`**, не методы публичных интерфейсов. Они переходят через `command_specs()`, а не `@expose`.
- **Имена существующих команд менять нельзя**: на них завязаны `CAPABILITIES.md` и клиенты `backend_ctl`.

### Почему не нужен новый слой

Слой нужен, когда два потребителя расходятся в одном решении. Сейчас решение одно: «какие команды у процесса и какого они класса». Его уже принимает таблица `CommandManager`. Кандидаты на слой, если появятся признаки:

| Слой | Признак необходимости |
|---|---|
| Политика доступа (проверка `access` до диспетчеризации) | Появился хотя бы один фронт вне доверенной зоны. Тогда один крючок в `handle_command` с умолчанием «разрешить» |
| Общий каталог между процессами | Удалённый фронт без сокета PM. Сейчас хватает `driver.capabilities()` |
| Модуль «ядро инструментов» | Не нужен, пока всё помещается в `base_manager` + `CommandManager` |

## 6. Риски

1. **Обработчики `BuiltinCommands` завязаны на `services` процесса** (`services.worker_manager`, `services._log_info`, приватные поля). Перенос семьи к владельцу требует либо отдать ему нужные зависимости, либо оставить обработчик в процессе, а владельцу отдать только объявление. Объём не оценён.
2. **Порядок загрузки.** `register_from` надо звать после создания всех менеджеров и до `log_registration_summary`. Плагины и воркеры добавляют команды позже; для них нужен тот же вход в любой момент.
3. **Имя `commands` занято семантикой** в нескольких классах (`get_commands`). Предлагаю `command_specs`.
4. **Тест импортов `base_manager/interfaces.py`**: файл сейчас импортирует только список stdlib (`Task 0.1`). `CommandSpec` с полем `params: Any` его не нарушает; наличие теста-сторожа не проверял.
5. **Поле `access` по умолчанию.** Предлагаю `write`, а не `read`: забытое объявление не должно стать «безопасным для чтения».
7. **Откуда `register_from` берёт менеджеры.** Реестр процесса (`register_manager`) знает 9 менеджеров. `StateStoreManager`, `RegistersManager`, `PluginManager`, менеджеры `Services/` в нём нет. Либо их регистрируют в реестре (малая правка, но касается жизненного цикла и порядка создания), либо `register_from` зовёт владелец сам в своём месте сборки. Выбор не сделан.
6. **Статическая и рантайм-карточки** могут разойтись. Atlas читает код, процесс — реестр. Связь — по id модуля; общего источника нет, и вводить его сейчас не предлагаю.

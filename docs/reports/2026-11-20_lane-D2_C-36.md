Расследование — `investigator` (Opus), инвентарь логов — haiku. Скрипты стенда лежат в `docs/reports/2026-11-20_lane-D2_C-36_harness/` (пути внутри скриптов абсолютные, под scratchpad сессии; сырые `*.jsonl` и логи (~12 МБ) в git не вошли). ## Итог

- Механизм подтверждён на настоящем `GenericProcess`: ребёнок поднят через настоящие `run_process_function`, `ProcessRegistry.create_and_register`, `SharedResourcesManager.register_process(reuse_queues=True)` и `ReaderGoneQueue` с `DEFAULT_QUEUES`. После `kill -9` межпроцессный `_rlock` очереди остаётся занятым; новое воплощение на той же очереди глухо в **60 из 60** случаев (system 5/5, data 55/55). При свободном замке глухих **0** (system 0/104, data 0/54).
- **Data-очередь** (`DataReceiver`, `get(timeout=0.05)`): `kill` простаивающего потребителя оставляет замок занятым в **142 из 142** (Вильсон 97,4–100 %). Это не редкость, а почти каждый `kill`.
- **System-очередь** (`get_nowait` раз в ~12 мс): замок занят 0,33–1,41 % времени — это и есть вероятность попадания для `kill` в случайный момент. Стенд C-92 дал 0,42 % (2/480, интервал 0,11–1,5 %) — то же. Но в серии kill investigator'а попадание было чаще: 11/226 = 4,9 % (2,7–8,5 %); расхождение не объяснено.
- Контроль (а), свежие очереди на воплощение: глухих **0/57**. Контроль (б), SIGTERM: то же, что SIGKILL (ребёнок SIGTERM не ловит).
- **Новая находка, не воспроизведена:** в первой серии после 2-го `kill` все 13 следующих воплощений зависли на старте, в том числе на свежих очередях (главный поток в `SemLock.acquire → sem_wait`). Осиротел какой-то разделяемый замок вне очередей; кандидат — общий `mp.Event`. Не подтверждено.
- Решение (очередь на воплощение или очередь без межпроцессного замка чтения) — за CTO/владельцем. Эскалация: `ESCALATION -> cto` (текст в конце).

## Причина

1. Любое чтение `mp.Queue` берёт межпроцессный семафор `_rlock` без владельца (CPython 3.12, `multiprocessing/queues.py`): `get(timeout)` — `:108` `acquire(block, timeout)`, затем `:113` `_poll(timeout)`, замок держится **всё время ожидания**; `get_nowait()` (`:132-133`) — `acquire(False)` → `_poll()` → `release` (`:120`). Процесс, убитый между `acquire` и `release`, семафор не отпустит; ядро его не освобождает (`sem_open` на macOS и Linux). SIGTERM убивает так же: в `process_module` и `runner` нет `signal.signal(SIGTERM)`.
2. Рестарт по умолчанию переиспользует очереди: `process_manager_process.py:5719-5728` (`restart_reuse_queues` по умолчанию True → `register_process(reuse_queues=True)`), `shared_resources_manager.py:192-197`; `_drain_process_queues` (`:4886-4911`) на занятом замке получает `Empty` и выходит через `except Exception: break` молча. Новое воплощение навсегда получает `Empty`; состояние поглощающее.
3. Читатели в ребёнке: system/state/observability — `system_threads.py:79-87` → `receive(timeout=0.0)` → `queue_channel.py:127-134` (`get_nowait` до `Empty`), затем `sleep(0.01)`; data — `data_receiver.py:450-454` → `queue_channel.py:119` `get(timeout=0.05)`.
4. Формула: `P(замок занят при kill в случайный момент) = D = f_poll · E[T_hold] = E[T_hold] / T_tick`. Data: `T_hold` ≈ 50 мс подряд, D ≈ 1 (измерено 99,89 %, на kill 142/142). System: `T_tick` = 12,1 мс; без соперников `E[T_hold]` ≈ 10–14 мкс, D ≈ 0,1 %; в настоящем ребёнке D = 0,33–1,41 %, то есть эффективное `E[T_hold]` ≈ 40–170 мкс (раздувают соперники: `_poll` отпускает GIL на системном вызове и возвращает его после соседнего потока, до 5 мс; плюс вытеснение ОС). Каждую составляющую отдельно не измеряли, только сумму. Стенд C-92 (0,42 %) попадает в измеренный D.
5. Почему на kill 4,9 %, а не ~1 %, не установлено. Гипотеза: момент `kill` связан с фазой 10-мс цикла (объединение таймеров macOS). Не проверено.

## Контроли

- **(а) очередь на воплощение** (правило владельца 2026-10-26): глухих 0/57 при 58/58 зависших замков на выброшенных data-очередях — пересоздание лечит.
- **(б) SIGTERM вместо SIGKILL:** разницы нет (data 29/29, system 3/58; глухих после зависшего замка 29/29) — обработчика нет, `finally` не выполняются.
- **(в) неблокирующее чтение** (`get_nowait`) против `get(timeout=0.05)` на одном ребёнке: доля занятого замка 0,88 % против 99,89 %; на kill system 11/226 против data 142/142. Окно сужается в ~100 раз, но не закрывается: риск остаётся у любого чтения `mp.Queue`.

Пометка investigator'а: B — главное лечение (убирает причину и опасность «писатель убит во время вытеснения»), A — временное правило. Минус A: весь data-трафик к перезапущенному процессу навсегда идёт через relay PM. Минус B: перенос вытеснения и дренажа в читателя. Это решение по QoS (ADR-173), за CTO.

## Критерий закрытия C-36 для приёмки фазы PM (ORDER 6а)

1. **Живой тест на data-линии** (настоящий PM `restart_process`, не стенд): ребёнок — `GenericProcess` с processing-плагином; 30 раз `kill -9` простаивающего потребителя в случайный момент; после каждого рестарта PM кладёт 3 команды в system и 3 элемента в data. Порог: глухих **0/30**. Сегодня ожидается ≥ 29/30 глухих (у стенда 55/55).
2. **Детерминированная инъекция для system:** помощник берёт `_rlock` system-очереди ребёнка и умирает от SIGKILL; затем `restart_process`; новое воплощение отвечает на команду за 1 с — **10/10**; без лечения (принудительный reuse) — красный 10/10.
3. **Голос, а не молчание:** занятый `_rlock` без живого читателя (повтор ~50 мс) на рестарте даёт ERROR с именем процесса и типом очереди и счётчик; `_drain_process_queues` больше не глотает это. Тест проверяет строку.
4. **Горячий путь после рестарта:** писатель → перезапущенный потребитель без вечного `delivery_failed`; для A — через выбранный путь relay.
5. Пункты 1–4 остаются в тестах. Стенд-харнесс — источник чисел, а не тест.

## Что осталось открытым / ненадёжно

- **Путь настоящего PM не пройден.** Стенд повторяет очередную часть `restart_process` (`create_and_register`, `register_process(reuse)`, копия `_drain_process_queues`); нет `ProcessManagerProcess`, `routing.refresh`, ready-gate. Строка `:4624` не достигнута; в логах детей шум `delivery_failed` к `ProcessManager` (PM нет).
- **Расхождение по system:** kill-серии 4,9 % [2,7; 8,5] против доли времени 0,33–1,41 % и стенда 0,42 % [0,11; 1,5]; интервалы не пересекаются. Причина не найдена. Глухих по system проверено всего 5 воплощений.
- **Аномалия первой серии** (13/13 воплощений зависли на старте, в том числе на свежих очередях): осиротел разделяемый `SemLock` вне очередей; кандидат — внутренний замок общего `mp.Event` (`Event.is_set()` берёт `_cond`, `synchronize.py:335-341`; runner опрашивает `system_stop_event.is_set()` раз в 0,1 с, `process_runner.py:191-201`). Если так, в продукте зависнут **все** процессы и `system_stop_event.set()` у PM. Не воспроизведено: в 226 следующих kill и 3 отладочных подъёмах зависаний 0; Python-стек зависшего не снят (faulthandler тогда не был включён).
- `_wlock` (писатель убит в `send_bytes`): 0/226, но ребёнок почти не пишет; писатель с тяжёлым трафиком (`camera_0`) не проверен.
- Вытеснение `get_nowait` писателем из чужой очереди (`manager.py:532`) берёт `_rlock` читателя; убитый в этот момент писатель оглушит соседа — выведено чтением, не воспроизведено.
- Последствия зависших замков state (и observability, 5 случаев) не изучены: вероятно, теряются `state.changed` и хвост записей.
- На стенде C-92 data-линия `consumer_0`, по этим числам, должна была умирать почти с первого kill; логи C-92 не сохранились (в логах и репо 0 совпадений «потеряна»; `c92series.py` и `repro_orphan_rlock.py` отсутствуют), проверить нельзя.
- Windows и Orin (Linux aarch64) не проверены; ожидается то же (семафор без владельца), на Windows `_wlock` нет.
- Машина общая: доли занятости зависят от фоновой нагрузки (0,33 % и 0,99 % у одного варианта в двух прогонах).
- Каждый замер — один прогон; сырые данные серий (`*.jsonl`, логи) лежат только в scratchpad сессии, в git не вошли.

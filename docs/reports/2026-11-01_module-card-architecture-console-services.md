# Карточка модуля: console_module и сервисы

Дата: 2026-11-01. Продолжение [`2026-11-01_module-card-architecture.md`](2026-11-01_module-card-architecture.md) (общая схема, интерфейсы как источник, порядок работ, вопросы). Файл разрезан по лимиту размера документа.

## 4. console_module: инвентарь и место в схеме

Что в модуле есть (всё прочитано):

| Часть | Что делает | Судьба в схеме |
|---|---|---|
| `IPlatformConsole`, `WindowsConsole`, `UnixConsole` | терминал платформы: create/write/show/hide/read_input | остаётся, это «экран» |
| `ConsoleManager` | основной и дополнительные терминалы, `write`, `enable_input`/`disable_input`, `setup_redirect`, `get_stats`, `get_debug_info` | остаётся. Получает `command_specs()` |
| `ConsoleRedirector` | stdout/stderr в консоль | остаётся |
| `ConsoleLogChannel` | канал `LoggerManager` в консоль: видимая среда процесса | остаётся |
| `ConsoleAdapter` | связывает логи, ввод и команды | остаётся; перестаёт регистрировать команды сам |
| `SystemCommandHandler`: `help`, `status`, `ps`, `stats` | текстовый вывод | становятся отображением каталога, не отдельными командами |
| `RegisterCommandHandler`: `reg list/get/set/info` | работа с регистрами | дубль `introspect.registers` и записи регистра. Предлагаю перенести в карточку `registers_module` |
| `ConsoleConfig`: `enabled`, `interactive`, `title`, `redirect_stdout` | три уровня: пассивный, команды, God Mode | остаётся |

Собственная карточка консоли: `console.show`, `console.hide`, `console.write`, `console.open`, `console.close`, `console.list`, `console.redirect`. Агент сможет открыть окно процесса и писать в него.

Ценность модуля, которую стоит сохранить: ввод консоли вызывает `handle_command` на своём потоке мимо роутера. Если `message_processor` завис, команды через `backend_ctl` не дойдут, а команда из консоли теоретически дойдёт. Это аварийный вход. Проверено только чтением кода; зависание не воспроизводилось.

Ограничение: ввод с клавиатуры не имеет проверки доступа. Для станка это допустимо (человек за машиной), для удалённого доступа нет. Решается после фундамента, как решил владелец.

## 4а. Сервисы: все на service_module, а он на BaseManager

Решение владельца (2026-11-01): все сервисы строятся на `multiprocess_framework/modules/service_module`, а тот стоит на `BaseManager`. Сервис, добавленный в проект, сам отдаёт информацию о себе и своих командах (API и прочее).

### Что есть сейчас (прочитано и посчитано)

| Факт | Следствие |
|---|---|
| `service_module` **не стоит на `BaseManager`**. `IService` — `@runtime_checkable Protocol` с `name`, `start(config)`, `stop()`, `get_status()`; `ServiceHost` — обычный класс; `ServiceRegistry` — singleton, хранит классы, не экземпляры (ADR-SVC-001..003) | Предпосылка владельца неверна для кода сегодня. Это решение, а не факт: его надо принять и записать как ADR |
| Протокол выбран сознательно: ADR-SVC-002 отверг ABC, чтобы существующие сервисы не наследовали базу и фреймворк «не диктовал структуру application-слою» | Переход на базу отменяет это решение. Довод 2026-05-25 устарел: `Services/` и framework в одном репозитории, слой `Services → framework` разрешён |
| У 9 из 18 сервисов есть `service.py` с `@register_service`: `auth`, `dataset_gen`, `hikvision_camera`, `ml_inference`, `ml_train`, `modbus`, `robot_comm`, `sql`, `vfd_comm`. Без него 9: `camera_device`, `code_reader`, `control_panel`, `device_hub`, `documents`, `layer_render`, `line_sim`, `otel_export`, `phone_gateway` | Единообразия нет и в реестре сервисов |
| `Services/sql/service.py` — **оболочка**: `SqlService` хранит строку `status`, `start()` ставит `"running"` и возвращает `True`, подключения нет («реальное подключение — Phase 4+»). Настоящий `SQLManager(BaseManager)` лежит отдельно и в `SqlService` не используется. `modbus/service.py` — настоящая обёртка над `ModbusDevice`. Остальные 7 файлов не читал | Реестр сегодня может показывать `running` у сервиса, который ни к чему не подключён |
| `ServiceHost` регистрирует `service.list/status/start/stop/restart` через собственный `handlers()` (словарь имя → обработчик), на хабе (`orchestrator.py`) | Ещё одна форма самостоятельной регистрации (см. раздел 2) |
| Команды сервиса `device_hub` в систему попадают через плагин, а не через сервис | Для всех остальных сервисов команд нет вообще |

### Что предлагается

1. **`BaseService(BaseManager)` в `service_module`.** `start(config)` соответствует `initialize` с конфигом, `stop()` — `shutdown`, `get_status()` собирается из `get_stats()`. Структурный `IService` остаётся как проверка совместимости: старые классы по-прежнему проходят `isinstance`. Ломающих изменений нет (принцип «чинить вперёд»).
2. **Сервис держит настоящий менеджер или драйвер.** `SqlService` владеет `SQLManager`, а не строкой статуса. Условие приёма: сервис, чей `start()` ничего не запускает, не считается сервисом. Это правило ADR-007 для статуса: «работает» верно, только если показано на живой системе.
3. **Все 18 сервисов получают `service.py` на `BaseService`.** Библиотеки (`layer_render`, `line_sim`) получают тонкий класс: `start` загружает ресурсы (пресеты, модели), `stop` освобождает. Если ресурсов нет, класс пустой, но карточка у сервиса есть.
4. **`ServiceRegistry` и `ServiceHost` остаются.** Реестр знает классы и даёт список «что есть». Хост запускает и останавливает по имени. Запущенный экземпляр объявляет свои команды в том же виде, что любой менеджер (раздел 3а).
5. **Новый ADR в `service_module/DECISIONS.md`** (следующий номер ADR-SVC-005): отмена варианта B из ADR-SVC-002 с причиной.

### Что сервис отдаёт о себе

| Что | Откуда берётся | Писать вручную |
|---|---|---|
| Публичный API | `interfaces.py` и `__all__`; у менеджера методы его интерфейса читаются через `inspect` | нет |
| Конфиг | схема `SchemaBase` с `FieldMeta` | нет |
| Состояние | `get_stats()`, `get_debug_info()`, `get_status()` | нет |
| Команды | `@expose` на методах интерфейса или `command_specs()` | одна отметка |
| Готовность и слой | карточка Atlas из `modules.yaml` и `STATUS.md` | да: `modules.yaml` ведётся руками, таблица в `Services/STATUS.md` устарела (14 из 18) |

### Новые риски этого решения

1. **Нет `unregister_command`.** В `command_module` и `dispatch_module` команду можно перезаписать, но не удалить. Если команды сервиса появляются при `start`, после `stop` они остаются в таблице. Варианты: добавить удаление (правка framework) или оставить команды всегда и отвечать «сервис не запущен».
2. **Оболочки могут лгать и после перехода.** Перевод 9 `service.py` на базу без замены тела `start()` даст те же ложные `running`, но в красивой обёртке. Нужен тест на каждый сервис: после `start()` виден ресурс.
3. **Хост на хабе.** `ServiceHost` живёт в ProcessManager. Команды запущенного сервиса окажутся в таблице хаба. Для `device_hub`, который работает в процессе `devices`, это другая таблица. Как они соотносятся, не выяснено.
4. **`AuthManager` создаётся в GUI-процессе** (`frontend/app.py:666`). Есть ли там доступный агенту `CommandManager`, не проверено.

### Слои

`BaseService` лежит в framework (`service_module`) и импортирует только framework. `Services/` импортирует `service_module`: направление `Services → framework` разрешено. `register_from` ничего не импортирует из `Services/`. `sentrux check .` не запускался.

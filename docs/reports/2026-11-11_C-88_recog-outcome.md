## Шаг 0 — диагноз (до кода)

Исполнитель: `investigator` (opus, xhigh), 5 прогонов с инструментированием; лид повторил без инструментирования 2 раза.

| Пункт брифа | Вход → наблюдение | Вывод |
|---|---|---|
| 1. Есть ли запись у `recog`, не затёрта ли | инструментирование `_record_stop_outcome`: `+0.488 RECORD recog=exited`; `add_process` после команды — 0 строк; `reset_call_stop_outcomes` на пути корня не зовётся | запись есть, не затёрта — не вклад |
| 2. Чем `recog` отличается | хвост выхода процесса после atexit: `recog` 0.29–0.39 с, остальные ≤ 0.17 с (torch); имя, волна, порядок — один проход опроса группы | `recog` всегда последний; само имя — не вклад |
| 3. Гонка | запись последнего итога, `PHASE -> done` и стоп message_processor — в одну мс; последний отданный снимок (+0.457 с) с `recog: None`; следующий запрос драйвера (+0.508) без ответа, сокет закрыт (+0.551) | гонка доказана |
| 4. Чей дефект | ветка выхода цикла драйвера — `BackendUnavailable` 5 из 5; PM ни разу не отдал снимок с итогом `recog` | дефект PM, не драйвера и не реестра |

Воспроизведение лида (без инструментирования, `BackendHarness(letter_robot_sim + base)`, порт 18765, через `machine_gate.sh light`), 2 из 2:
`outcomes={… 9 × 'exited' …, 'recog': None}`, `unconfirmed=['recog']`, `pm_gone=True`, `timed_out=False`; `LOOP EXIT BRANCH: BackendUnavailable from supervision_status`.

**Причина.** `_ChildrenStop.join_until` (`process_manager_process.py:5310-5316`) объявляет `done` сразу после записи итога последнего ребёнка, область тут же закрывает `workers` (message_processor) — примерно через 1 мс. Драйвер опрашивает `supervision.status` раз в ~60 мс, и снимок с итогом последнего ребёнка не отдаётся никогда. Это окно ADR-PMM-042 «Предел контракта». Ребёнок честный итог получает; PM его не отдаёт.

## Исправление (ADR-PMM-045)

После `done` PM ещё отвечает на `supervision.status`, но только если статус опрашивают прямо сейчас (последний ответ во время стопа моложе 0,25 с). Ожидание — до события «снимок с `done` отдан», не дольше `min(0,5 с, остаток срока)`, затем пауза 0,05 с на уход ответа (время, не гарантия доставки). Без наблюдателя цена нулевая. Один раз на `_ChildrenStop`; сбой — ERROR, стоп идёт. `outcomes()`, `_confirm`, правило ранга, порядок фаз, драйвер — не менялись.

Отвергнуто: (B) PM рассылает итоги до закрытия транспорта — новое сообщение, правка драйвера и endpoint; (C) статус вне message_processor — смена маршрутизации; правка только драйвера — PM снимок не отдаёт.

Порядок цикла: стадия 0 `reviewer` (sonnet) — 2 раунда, CHANGES REQUESTED ×2, все правки приняты (метка свежести вместо «наблюдатель был», события на экземпляре, граница по остатку срока, пауза на отправку, без мёртвого стража, H1–H10); слепой `tester` — до кода, коммит `5065d7378`; `developer` (sonnet) — `797d9cec6`.

## Ответ на замечания координатора

1. Диагноз доказан воспроизведением, не выведен: итог `recog=exited` в реестре есть (+0,488 с), PM его не отдаёт — окно ~1 мс до закрытия message_processor; драйвер не «читает рано». Правка не маскирует симптом: она отдаёт наблюдателю итог, который PM уже подтвердил; честность итога (сигнал по имени, ранг) не менялась.
2. В штатных ветках без наблюдателя задержки нет (H1, H2); с наблюдателем — не больше 0,55 с и не дальше остатка срока (H4, H7); соседи не блокируются (ожидание после итогов всех детей). Константы проверены hazard-тестами; инъекции — частично (см. выше).
3. Порядок соблюдён: стадия 0 (2 раунда) → слепой тестер (коммит `5065d7378`, RED) → исполнитель (`797d9cec6`). Исполнитель стартовал после коммита тестов.

## Что оставил открытым / ненадёжно

- **Матрица инъекций неполная:** прогнаны INJ-1 (слепые — совпало, hazard — красных больше предсказанного) и INJ-2 (точка недостижима, R3 этой инъекцией не проверен). INJ-2b, INJ-3…7 и инъекция «убрать вызов в ветке F1 / в `close()`» не прогнаны: классификатор прав отказал в запуске скрипта инъекций; отказ не обходил. Нужно решение владельца, как запускать инъекции (разрешить скрипт `c88/inj_run.sh` или иной способ).
- Пауза 0,05 с после события — время, не гарантия доставки ответа: `_close_backend_ctl` не ждёт отправку в полёте. На стенде 3 из 3 и в стрессе 21 из 21 — без потерь; под сильной нагрузкой не проверено.
- `force` с малым остатком срока получает мало или ноль ожидания — итог последнего ребёнка там может остаться `None` («PM не подтвердил»); живьём не проверялось.
- GUI, переставший опрашивать прямо перед `done`, продлевает выход PM до 0,55 с (запас спавнера 1,5 с); живой замер GUI-закрытия не делал.
- Пометку «предел драйвера» в `scripts/alpha_sim/logic.py:697-723` не трогал — правка скрипта в полосе его владельца; после C-88 она на стенде не срабатывает (`unconfirmed` пуст).
- Радиус `process_manager_module/tests` целиком чистым не видел: у исполнителя шум `OSError: [Errno 28] No space left on device` (места на диске 284 ГБ — вероятно, лимит POSIX shm/семафоров macOS при параллельных полосах) и 8 давних красных (`test_cv_threads.py` ×6, `ShutdownOrder` ×2 из-за занятого порта 8765 — `Errno 48`), те же на коде без правки.
- Почему `recog` выходит на 0,3–0,4 с дольше после atexit (torch или потомок потомка) — не измерял.

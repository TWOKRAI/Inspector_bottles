## 1. Видение владельца (решения 2026-11-01)

Фреймворк — **открытый конструктор многопроцессных приложений**, «блоки как в Майнкрафте»: каждый модуль прозрачен и управляем до низкого уровня. На нём строятся сложные системы, а **ИИ-агенты помогают разработчикам создавать, отлаживать, настраивать, дорабатывать и улучшать** их. Дальняя цель: Python как оркестратор над сервисами любого рода, открытая система.

Принято владельцем:
1. **Ядро одно.** Модуль фреймворка, который предоставляет инструменты ко всем модулям и функциям. `backend_ctl` и другие потребители привязываются к нему как **фронты: CLI, REPL, MCP**.
2. **Инструментов может быть много**, у них **уровни доступа**; агентам нужен **каталог инструментов**.
3. **God Mode нужен** и связан с `backend_ctl`.
4. **Кадры** доступны и файлом, и через MCP; цель — максимальная функциональность отладки.
5. **Один план на MCP**, новое идёт фазами в него.
6. **Безопасность сознательно позже:** сначала функциональное здание, потом надёжные ворота и двери. Владелец прямо признаёт, что это небезопасно.

Связь с уже принятым: [`FRAMEWORK_CONSTRUCTOR_OVERVIEW.md`](../claude/FRAMEWORK_CONSTRUCTOR_OVERVIEW.md), [`CONSTRUCTOR_BLUEPRINT.md`](../../multiprocess_framework/docs/CONSTRUCTOR_BLUEPRINT.md) (§6.B «CLI с диалогом — console_module (God Mode)»), принципы владельца 1–5 в корневом `CLAUDE.md`.

## 2. Что есть сегодня (кратко)

Подробно и с оценками — в отчёте об оценке. Здесь только то, что нужно для архитектурного разговора.

- **Внешний клиент** `backend_ctl/` (около 11 800 строк): TCP-драйвер, MCP-сервер на 53 `ToolSpec`, события курсорами, flight recorder, аудит, режимы `--read-only` и `--disable-destructive`, проверка аргументов по `params_schema`.
- **В фреймворке уже есть каталог команд:** `CommandManager` с метаданными (описание, теги), схемы параметров в `BUILTIN_COMMAND_CONTRACTS` (`command_contracts.py:370`), генерация `docs/contracts/CAPABILITIES.{md,yaml}` с проверкой дрейфа в CI. Команды есть у ProcessManager (около 85) и у каждого дочернего процесса.
- **Два списка, которые не связаны:** команды фреймворка (источник — модули) и `ToolSpec` в `backend_ctl` (источник — ручной реестр). Обращение к первым из MCP идёт через общий `send_command` класса `escalated`.
- **Консоль** `console_module`: интерактивный God Mode (`reg`, `help`, `status`, `ps`, `stats`), внутри системного процесса, заморожен как фича (`MODULE_TIERS.md`, G0 №3).
- **Не покрыто:** CLI, кадры, стеки потоков и профайлер, запрос трассы по `trace_id`, модель прав, `outputSchema` MCP.

## 3. Принципы для проектирования ядра

Следуют из видения и из уже принятых принципов владельца:
1. **Инструмент — свойство модуля, а не клиента.** Модуль объявляет, что умеет, в стандартной форме; клиент ничего не придумывает за модуль.
2. **Один источник, много фронтов.** Каталог, схема, класс безопасности, уровень доступа живут в одном месте; MCP, CLI, REPL и любой будущий фронт (HTTP, GUI) только отображают.
3. **Каталог для агента — прогрессивный.** Агент сначала видит обзор по намерениям, затем детали нужной семьи (иначе 50+ инструментов ломают выбор; Anthropic: выбор деградирует после 30–50).
4. **Уровни доступа — часть контракта с первого дня,** принуждение к ним — позже. Включение защиты не должно требовать переписывать каждый инструмент.
5. **Fix forward, FREEZE не KILL.** Существующее (`CommandManager`, CAPABILITIES, `ToolSpec`) не удаляется, а подводится под ядро или замораживается.
6. **Сбой одного инструмента или модуля не валит соседей.**

## 4. Предлагаемая архитектура (предложение, не решение)

### 4.1. Схема

```
   Люди и агенты
   ┌─────┐ ┌──────┐ ┌─────┐ ┌─────────────────────────┐
   │ CLI │ │ REPL │ │ MCP │ │ GUI «Пульт» / HTTP (позже) │   ФРОНТЫ
   └──┬──┘ └──┬───┘ └──┬──┘ └────────────┬────────────┘
      └───────┴────────┴─────────────────┘
                       │ один клиентский слой: сессия, подписки,
                       │ курсоры событий, аудит, режимы (backend_ctl)
                       ▼
        ┌──────────────────────────────────┐
        │   ЯДРО ИНСТРУМЕНТОВ (модуль)     │   в multiprocess_framework
        │  каталог · схема · уровень ·     │
        │  политика · аудит-хук · поиск    │
        └───────────────┬──────────────────┘
          регистрируют │ IToolProvider (Protocol в interfaces.py модуля)
   ┌──────┬─────┬──────┴──┬────────┬─────────┬──────────┐
   │router│state│ process │ worker │ logger/ │ Services │   БЛОКИ-МОДУЛИ
   │      │store│ manager │ module │ stats   │ /Plugins │
   └──────┴─────┴─────────┴────────┴─────────┴──────────┘
```

In-process фронт: `console_module` (God Mode) тоже может быть фронтом ядра, потому что ядро живёт во фреймворке (раздел 4.4).

### 4.2. Контракт инструмента (набросок полей)

`Tool`: имя; описание для агента; домен и теги (семья по намерению); схема параметров и схема результата; **класс безопасности** (read / write / destructive, как сейчас `TOOL_SAFETY`); **уровень доступа** (предложение: L0 наблюдение, L1 диагностика — дорогие чтения: стеки, профайл, кадры, L2 управление — запись регистров, воркеры, L3 администрирование — топология, создание процессов, остановка системы); стоимость (для оценки нагрузки); провайдер (модуль); версия контракта; где исполняется (процесс-владелец).

Модуль подключает инструменты через `IToolProvider` в своём `interfaces.py` (зависимость идёт от модуля к Protocol, а не к ядру — правило «зависимости через `interfaces.py`»).

### 4.3. Граница: системные и сессионные инструменты

Это самое спорное место, нужна проверка рецензента.
- **Системные инструменты** исполняются в процессах системы и принадлежат модулям: `introspect.*`, `diag.*`, `worker.*`, `state.*`, `wire.*`, команды сервисов. Это и есть содержимое ядра.
- **Сессионные инструменты** зависят от состояния клиента и поэтому в ядро фреймворка попасть не могут: курсоры событий (`events_page`), `await_condition`, flight recorder, аудит сессии, реконнект с восстановлением подписок. Они остаются в `backend_ctl`.
- Каталог для агента объединяет оба вида, а различает их флагом «исполняется в системе / в сессии».

### 4.4. Фронты и God Mode

- **MCP, CLI, REPL внешние:** живут в `backend_ctl`, подключаются к работающей системе по сокету, переживают её перезапуск, пишут общий аудит. Человек в REPL и агент в MCP работают через одно ядро.
- **`console_module` как in-process фронт** допустим, если ядро находится во фреймворке: зависимость идёт «фреймворк → фреймворк», слои не нарушаются. Ранее я возражал против прямой связи `console_module` с `backend_ctl`; при размещении ядра во фреймворке это возражение снимается, остаётся вопрос, нужен ли внутренний God Mode, если есть внешний REPL (вопрос 9.6).

### 4.5. Кадры

Профиль «и файл, и MCP» реализуется без нарушения буквы ADR-RTR-008: процесс при включённом перехвате кодирует кадр в каталог-кольцо (лимиты размера и срока), по сокету идёт только путь, MCP-сервер на той же машине читает файл из этого каталога и отдаёт `ImageContent`. Перехват включается командой, в выключенном состоянии стоит ноль. Нужна одна уточняющая строка в ADR-RTR-008. Предел: одна машина; удалённый случай — gui-service Ф2 (уже в плане).

## 5. Как это ложится на существующее

| Сегодня | В ядре | Что происходит |
|---|---|---|
| `CommandManager` + метаданные + `BUILTIN_COMMAND_CONTRACTS` | источник системных инструментов | Первый шаг: адаптер, который публикует имеющиеся команды как `Tool`, ноль изменения поведения |
| `CAPABILITIES.md/yaml` и `dump_capabilities` | один из видов отображения каталога | Остаётся, генерируется из ядра |
| 53 `ToolSpec` в `backend_ctl` | делятся: часть уходит в ядро (проекции команд), часть остаётся (сессионные) | Без переименований на первом этапе, чтобы не ломать клиентов и тесты |
| `send_command` (escalated) | универсальный вызов по каталогу | Остаётся как нижний уровень; уровень доступа L3 |
| `console_module` (God Mode) | возможный in-process фронт | Размораживать только после того, как ядро и CLI работают |
| gui-service «Пульт» | ещё один фронт | Использует тот же каталог |

## 6. Риски и возражения (честно)

1. **Принцип «меньше слоёв».** Ядро добавляет слой. Оправдано, только если оно **заменяет** три разрозненных места (метаданные команд, генератор CAPABILITIES, ручной реестр `ToolSpec`), а не лежит рядом с ними. Без удаления дублей это нарушение принципа 4 владельца.
2. **Безопасность «потом».** Для разработки на localhost приемлемо. Но: (а) при «открытой системе» умолчание обязано быть закрытым до первого релиза наружу; (б) поле уровня доступа, точка политики и аудит нужны в контракте **сейчас**, иначе позднее добавление ломает каждый инструмент; (в) уже сегодня нет проверки bind-адреса: можно открыть порт не на loopback без токена. Рекомендую зафиксировать «ворота» как **условие релиза**, а в фундамент заложить хуки.
3. **Универсальные инструменты = удалённое исполнение.** Пока `send_command` может адресовать любую команду, любой локальный клиент управляет всей системой. Это не новая проблема, но ядро и каталог делают её видимой; нужна модель угроз.
4. **Динамика каталога.** Команды регистрируются в рантайме по процессам; каталог должен быть версионирован (epoch) и обновляться при рестартах, иначе агент работает по устаревшему списку.
5. **Контракты инструментов — публичный API.** Агентские промпты и скрипты зависят от имён. Нужны версия контракта и правила депрекации.
6. **«Создание» агентами — другая область.** Текущий `backend_ctl` покрывает отладку и настройку живой системы. «Создавать и улучшать» требует инструментов времени разработки (заготовка модуля, правка топологии и рецептов, запуск тестов и гейтов), которые сегодня живут в `/dev:*` и `scripts/`. Нужно решить, входят ли они в ядро или интегрируются с ним.
7. **Нагрузка и побочные эффекты инструментов.** Профайлер, перехват кадров и стеки стоят ресурсов и могут менять поведение; принцип владельца «ручка наблюдаемости: вкл/выкл везде, ноль нагрузки выключенной» должен выполняться для каждого.
8. **Открытая система.** Лицензирование, доверие к сторонним плагинам и провенанс инструментов — отдельная тема; в этот бриф не входит, но влияет на формат `Tool` (подпись, происхождение).

## 7. Конфликты с текущими правилами и планами

## 8. Черновая дорожная карта фаз (порядок спорный)

0. **Контракт.** `Tool` v1 (поля раздела 4.2), `IToolProvider`, ADR о границе «системные / сессионные», уточнение ADR-RTR-008, решение по запрету.

2. **Фронты.** Перепривязка `backend_ctl` к каталогу; **CLI** (один файл поверх `dispatch_tool`); внешний **REPL**.
3. **Диагностика.** Семейство `diag`: стеки, затем профайл (двухфазный), память; сначала эксперимент `faulthandler.dump_traceback_later` на Windows.
4. **Кадры.** Перехват с включением по команде, каталог-кольцо, `ImageContent` в MCP.
5. **Трасса.** Закрыть резидуал G.6, колонка и индекс `trace_id` в `ObservabilityStore`, инструмент `trace`.
6. **Уровни доступа и аудит.** Хук политики, единый аудит для всех фронтов, привязка `TOOL_SAFETY` к уровням.
7. **Спецификация MCP и эргономика.** `outputSchema`, профили инструментов по намерению, resources и prompts (после проверки статуса MCP 2026-07-28).
8. **Ворота (условие релиза).** Токен (gui-service 2.2), защита bind, модель угроз, закрытое умолчание.
9. **Инструменты разработки для агентов** (создание и улучшение): отдельное решение после фаз 1–6.

## 9. Вопросы рецензенту

1. Допустимо ли ядро как **модуль фреймворка** (core-tier) и не нарушает ли оно принцип «меньше слоёв»? Что именно должно быть удалено или заморожено в ответ?
2. Верна ли граница **системные / сессионные** инструменты (4.3)? Нет ли третьего вида?
3. Правильный ли набор **уровней доступа** (4.2)? Достаточно ли поля в контракте с политикой «разрешить всё» на первом этапе?
4. Согласны ли с заменой запрета на новые инструменты **воротами**?
5. Выдержит ли схема **кадров через каталог-кольцо** (4.5) требование «лучшее решение» без правки Dict at Boundary сверх одной строки ADR?
6. Нужен ли **внутренний God Mode** (`console_module` как фронт), если есть внешний REPL? Или оставить заморозку?
7. Где проходит граница между **runtime-инструментами и инструментами разработки** (раздел 6.6)?
8. Верен ли **порядок фаз** (раздел 8)? Что можно резать, что нельзя откладывать?
9. Достаточны ли «хуки сейчас, принуждение потом» для заявленной цели **открытой системы**, или нужен минимум защиты уже в фундаменте?

## 10. Что не проверено и ненадёжно

- Это **предложение**, а не проверенный дизайн: ни одна часть ядра не прототипировалась.
- Отчёты фоновых агентов выборочно не перепроверялись; код читался, стенд и тесты не запускались.
- Не изучено, как ядро ляжет на `command_module` и `process_module` по зависимостям (риск циклов) и не появляется ли конфликт с лайфсайклом (`lifecycle-stop-ownership` активен).
- Не проверено: как динамическая регистрация команд по процессам поведёт себя с версионированием каталога; как работает `ProcessHeartbeat` при зависании; влияние `FW_SHM_LOAN_PROTOCOL` на перехват кадров; ломает ли hello или токен около 40 скриптов `backend_ctl/probes`.
- Уровни L0–L3, имена семей и структура `Tool` — **предложения** без обоснования опытом эксплуатации.
- Внешние сравнения неполны: Illustrator отдельно, Unity и Godot MCP, Autodesk MCP, Copilot для Word/Excel по первоисточникам не изучались; часть страниц вернула 403.
- Оценки размера работы в отчёте об оценке — мои суждения, `manager` их не подтверждал.
- Не читались `docs/audits/2026-07-23_backend-ctl-max-review.md` и `docs/reviews/`; там могут быть решения, противоречащие этому брифу.

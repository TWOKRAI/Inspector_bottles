# device_hub: роль, размер драйверов, структура для роста (анализ 2026-10-20)

Вопрос владельца (2026-10-20): драйверы большие (`robot_driver_v2.py` ~2037 строк) — не должен ли каждый драйвер жить в
своём сервисе, а device_hub давать шаблон/интерфейс; какова роль device_hub. Анализ — investigator (Opus), только
чтение кода и отчётов ревью, без прогонов; дерево `feat/robot-v2-t53cd`. Лид: inspector-bottles-a5.

## Вердикт

- Интуиция владельца верна в главном: домен робота живёт не там, контракт хоста неявный. Неточна в одном: драйверы в
  целом не большие — `vfd_driver.py` 334, `hikvision_driver.py` 174, `generic_modbus_driver.py` 188 строк, это тонкие
  адаптеры над клиентами своих сервисов. Выброс один — `robot_driver_v2.py` (2037): это не адаптер, а среда исполнения
  робота (потоки, очереди, программы, поводок, синхронизация параметров).
- Дефекты T5.3a–d дал не размер файла, а число одновременных исполнителей над общим состоянием: ~20 полей состояния
  под одним `_flags_lock` и 3 замка драйвера, плюс второй автомат стопа в клиенте.
- «Адаптер между прототипом и сервисами» — неточно: GUI шлёт IPC-команды
  (`multiprocess_prototype/frontend/widgets/tabs/services/robot/presenter.py`), с хабом напрямую не работает.

## 4. Варианты

- **A. Раскладка та же, `robot_driver_v2` → пакет компонентов** (`drivers/robot_v2/`: state, link, stop, jog, jobs,
  programs, params, ops). Слоёв не добавляет. Гонки сам не снимает — полезен только внутри T5.3f, где состояние одно,
  а компоненты — переходы. Риск: перенос по стабилизированному пути стопа; тесты в приватных полях сломаются.
- **B. Драйвер в сервисе устройства, хаб = хост + SPI** (`Services/robot_comm/runtime/`; `device_hub/spi.py`:
  `Protocol DeviceDriver`, `OpSpec{name, args_schema, needs_link, threaded, description}`; хост даёт `spawn`,
  `publish`, `store`, срок, часы; плагин регистрирует команды из дескрипторов). Новый вид = драйвер + строка фабрики.
  Слоёв столько же. Цена и риск высокие: импорт меняет направление (`robot_comm → device_hub.spi`), цикл, если
  менеджер продолжит импортировать `robot_comm`; имена команд — контракт 7 потребителей (FREEZE).
- **C. Только явный SPI, файлы на месте**: `Protocol` для неявных хуков в `base.py`, `OpSpec` у драйвера, плагин
  генерирует `<kind>_<op>`, `robot_data`/`_store_refusal` — один путь, дроссель — в `base.py`. Цена низкая/средняя;
  дрейф ловит CAPABILITIES-гейт. Шаг к B без смены направления импортов.
- **D. Процесс на сервис устройства** — отвергнуто ADR-DH-001 (общий RLock носителя ADR-DH-002, IPC-хоп на тике).

## 5. Рекомендация и порядок

0. Сейчас ничего структурного: слить T5.3c/d; путь стопа заморожен.
1. Порядок T5.3e ↔ T5.3f — решение владельца: T5.3e добавляет седьмой путь остановки над теми же флагами.
2. T5.3f = одно состояние + пакет (A внутри f); перенос модуля — отдельный коммит без смены поведения; сторожа —
   `test_t53r2_stop_hazards.py`, приёмка T5.3r2, повтор инъекций M1–M10 и H1–H4; один тестовый accessor состояния.
3. SPI (C): `Protocol`, `OpSpec`, генерация команд при тех же именах; сторожа — CAPABILITIES-гейт,
   `test_no_private_access.py` (+ `driver._client`), тест «новый вид = только фабрика».
4. Перенос среды робота в `Services/robot_comm` (B) — после C, когда T5.4/T5.5 прибавят поведения; до него —
   `sentrux check .` на цикл `robot_comm ↔ device_hub`.

Не делать сейчас: двигать файлы до слияния T5.3c/d; переименовывать `robot_*`; трогать порядок фаз стопа; сливать v1 и
v2; выносить устройства в процессы; убирать второй автомат стопа до T5.3f.

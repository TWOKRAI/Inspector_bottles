## 4. Сценарий робота: штатный стоп с возвратом домой (приёмка 4)

По коду и пробам investigator ([`investigator_code.md`](2026-10-20_L-9-residual-evidence/investigator_code.md) → Q4).

- Окна PM: одиночные стопы — ключ `stop_process_timeout` (5,0 с) конфига PM; системный — `stop_budget()`
  (`core/stop_budget.py:73-96`): work 3,0 / PM 5,0 / с эскалацией 7,0 / спавнер 8,5 с. **Оба ключа — на весь PM, не на
  ребёнка.** Свой `stop_budget` у ребёнка меняет только его внутренние сегменты, PM всё равно бьёт по своему окну.
- Ребёнок, которому нужно 8 с (проба P1): `terminate` на +5,0 с (Windows — TerminateProcess, exitcode -15) — возврат
  домой обрывается посреди движения. Ответ команды при этом `success: True` (`process_registry.py:470-472`): «вышел сам»
  и «убит» не различаются, разница только в WARNING.
- `process.stop`, `system.shutdown`, `process.restart` — одно и то же: terminate на 5 с. Чтобы 8 с поместились в
  системный стоп, `shutdown_timeout` должен быть ≥ 11,3 с — для **всех** детей системы.
- **Во время ожидания (до 7 с) PM не исполняет ни одной команды**: backend_ctl (у него таймаут 5 с), `process.relay`
  (все команды GUI другим процессам идут через PM, `command_sender.py:97-110`), рестарт супервизора, `system.shutdown`
  (проба P1: положен на +1,0 с, исполнен на +5,09 с). Heartbeat не разбираются.
- **Не помещается.** Штатный стоп с возвратом домой нельзя делать внутри `process.stop` / `system.shutdown` при
  нынешней архитектуре.

Лечится: команды, трогающие цель в переходе, ждут её через существующий `_run_when_child_ready`; шаг 0 — опись всех команд PM, читающих/пишущих состояние жизненного цикла. Механизм отложенного ответа уже есть (`manages_own_reply`, `reply_to_request` с любого потока, прецедент обёртки `process.command`) | **рекомендую** |
| **(Task 3.1) протокол quiesce → ack → exit** | убирает хвост останавливаемых детей и гонку на системном стопе | S–M, поверх (б) | ack тоже приходит в `ProcessManager.system` — ждать его на `message_processor` тот же класс дефекта; на одиночном стопе соседи не замолкают, а их фон и есть то, что забивает pipe (п. 3) | не альтернатива; слой поверх (б), по триггерам Ф2 |

**Рекомендация — (б)**, с тремя малыми задачами рядом:
1. Одна FIFO жизненного цикла в PM (start/stop/restart/pause/resume/create, `topology.apply`, `recipe.activate`,
   `wire.*`, рестарт супервизора); ответ после подтверждённой смерти; `system.shutdown` идёт **мимо** FIFO (взвести
   события сразу). Отдельная FIFO на каждого ребёнка не нужна: `topology.apply` трогает многих сразу.
2. **Честный итог стопа**: ответ `process.stop` различает «вышел сам / terminate / kill» — сейчас `success: True` и при убийстве.
3. **Окно стопа на ребёнка**: ключ в конфиге процесса вместо одного `stop_process_timeout`; внешние сроки PM и спавнера
   выводятся из максимума (вложенность ADR-PMM-031).
4. **Решение владельца для T5.3e (не фреймворк):** штатный стоп робота — команда устройству «домой» ДО `process.stop`
   (сценарий остановки линии на уровне приложения), а не длинный стоп процесса. Жизненный цикл процесса остаётся
   коротким и ограниченным; бизнес-последовательность выключения — выше.

**Почему не (в):** она разрывает дедлок, но оставляет PM глухим на всё время ожидания, а порог падает обратно
пропорционально длине стопа (R* = 4096 / T) — ровно в том сценарии (длинный стоп робота, окно закрытия GUI с ходом
остановки), который идёт следующим. (в) остаётся страховкой до прихода (б), потом замораживается (принцип 3).

## 7. Вердикт CTO (Fable, 2026-10-20): ACCEPT WITH CONDITIONS

Воспроизвёл сам через light: P1 (вторая команда положена +1,00 с, исполнена +5,11 с), P3 (`resolved_inside_wait=False`),
P2 (2000 сообщ/с: буфер полон на 2,08 с, в pipe остаётся 1908). Инъекция `pump_inbound → 0` на R10b и R10 даёт ровно
числа «до» Task 1.8 (5,047 с, -15) — тесты меряют эффект, а не имя API.

- **D1.** Условие по L-9 для T4.x выполнено с условием: стоп робота на T4.x — только аварийный (≤ 2,5 с) внутри
  `process.stop` / `system.shutdown`; возврат домой туда не класть; `stop_process_timeout` / `shutdown_timeout` не поднимать.
- **D2.** Конечное состояние — (б), одна FIFO жизненного цикла PM вне `message_processor`, отложенный ответ после
  подтверждённой смерти, `system.shutdown` мимо очереди. (в) для `request()` отвергнута. `pump_inbound`,
  `stop_wait_idle`, `ChildProcessStop(idle=)` после (б) — FREEZE (принцип 3) с пометкой «заменено ADR-PMM-038».
  Инварианты ADR-PMM-038 = приёмка Task 1.9:
  - (I1) владелец стопа детей в каждый момент один: на `system_stop_event` исполнитель FIFO отклоняет очередь, текущая
    операция возвращается на ближайшем опросе, только потом `_ChildrenStop` раннера;
  - (I2) шаг 0 — опись команд PM, читающих/пишущих реестр, `_process_configs`, эпоху, провода; команды в цель
    «в переходе» (`process.relay`) — через `_run_when_child_ready` или ту же FIFO;
  - (I3) ответ через обе двери (прямую и `process.command`), содержимое для GUI `_async` и backend_ctl прежнее;
  - (I4) `message_processor` и `supervision.status` живы весь одиночный стоп — контракт прогресса для GUI.
- **D3.** (1) Честный итог: `success` остаётся «смерть подтверждена», добавить `outcome` = `exited | terminated |
  killed | survived` в ответ и в `supervision.status`. (2) Окно стопа на ребёнка — малая задача конфига, сроки PM и
  спавнера — из максимума (ADR-PMM-031); не носитель возврата домой. (3) T5.3e: «домой» — команда устройству ДО
  `process.stop` на уровне приложения (сохранить → «домой» → `system.shutdown`); принудительный режим backend_ctl «домой» пропускает.
- **D4.** Task 1.9 = (б) — сейчас, без триггера: на неё опирается план закрытия окна GUI. T4.x её не ждёт. В плане GUI
  отдельно: сегодня `message_processor` PM закрывается раньше детей (ADR-PMM-036, LIFO) — прогресс при `system.shutdown`
  требует, чтобы приёмный поток и сокет пережили фазу детей; это правка корня PM, не Task 1.9.
- **D5.** Поправки к отчёту внесены выше (обрыв на потолке, статистика по всем сериям, точность порога 2×).
  Дефект стенд-скрипта: `verdict: OK` у зависших прогонов — чинить скрипт (не фреймворк).

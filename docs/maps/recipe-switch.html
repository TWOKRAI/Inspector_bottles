Транзакция apply в PM

Диаграмма шире экрана — прокручивается внутри рамки →
План
(planner.py): diff всегда «есть изменения» (:197-214); все non-protected сносятся и пересоздаются, даже если не менялись — IncrementalPlanner упомянут в planner.py:11, не создан. Сборка и валидация proc_dict — до первой stop-команды (:241): невалидный рецепт ничего не трогает.
Protected
PM и процессы с protected: true (process_manager_process.py:1228-1238): в прототипе devices (backend/topology/base.yaml, единственный процесс фундамента — проверено) и gui (overlay презентации). Конфликт их конфига (planner.py:305-344) сравнивает полный proc_dict, включая лог-пути и recipe_devices — поля, которые от рецепта к рецепту ОБЯЗАНЫ отличаться. Итог: ERROR почти на каждой смене, процесс остаётся со старым конфигом, устройства всё равно приходят через device_sync_set. Это шум по построению, а не сигнал.
Стоп
Одна process.stop_all → stop_many параллельно, лестница graceful → terminate → kill; неподтверждённая смерть → hard-fail и откат.
Готовность
(проверено, :4186-4196, :4110-4140): окно start_ready_timeout_s = 0.5 с; на дедлайне живой процесс без события считается готовым. Код сам называет единичный фолбэк «нормой старта при холодном импорте тяжёлого процесса»; на стенде 2026-10-13 фолбэк шёл подряд 4…7 раз — значит барьер систематически не ждёт. Не готов → report_error, но ответ остаётся success: true. При откате барьера нет (:1888).
Откат
(_rollback_to_snapshot, :1801-1893): тем же конвейером, best-effort; 2PC нет; неподтверждённые стопы выпадают из топологии до следующей смены — возможна смесь старого и нового.
Ответ
Синхронно после всей работы (router_manager.py:1345); отмены по таймауту клиента нет.

Устройства

  • cmd_device_sync_set (Plugins/hub/device_hub/plugin.py:562-629): upsert в порядке рецепта → удаление recipe-устройств прошлого рецепта (мосты первыми) → connect в очередь из set (:617-622) — порядок случайный между процессами (R-10). Ручные устройства (origin не recipe:*) не трогаются.
  • Мост проверяет носителя только в момент connect (Services/device_hub/manager.py:293-299); при отказе повторяет сам драйвер, 3 попытки, затем desired_connected=False навсегда до ручного «Подключить» (drivers/base.py:190-217). Каскада «носитель подключился → разбудить мост» нет (каскад только на disconnect, manager.py:323-330).
  • devices protected → при apply не перезапускается, sync не теряется; но его конфиг (recipe_devices) после apply остаётся старым — правда о составе устройств живёт только в рантайме.
  • Порядок с apply: sync уходит ДО apply и не ждёт ответа; при откате apply устройства нового рецепта остаются.

R-8: ведущая гипотеза H1 — запись в консоль на потоке сообщений

H1 · ведущая гипотеза R-8Проверено чтением кода, на стенде НЕ воспроизведено.
  • Консольный сток журнала — ConsoleChannel (multiprocess_framework/modules/logger_module/channels/log_channel.py:1043) пишет через logging.StreamHandler в stderr процесса. Запись идёт синхронно на потоке вызывающего: прямой путь channel_routing_manager.py:1069 зовёт ch.write(record) в цикле по каналам (батчинг снят в Ф7.4) — проверено.
  • Защита от залипшего стока _guarded_write ограничивает только ожидание лока; сам emit() идёт под локом без предела — докстринг прямо говорит: «всё, что происходит внутри него, — уже за пределом досягаемости дедлайна». Первый поток, вошедший в запись к замёрзшей консоли, висит бесконечно; остальные отбрасывают записи по пределу.
  • Консоль Windows замерзает, когда в окне PowerShell выделяют текст (режим QuickEdit, заголовок «Выделить»): любая запись в эту консоль ждёт, пока выделение не снимут. Владелец копирует вывод из окон стенда — это ровно такое выделение.
  • Совпадение с симптомом R-8: обработчик «не возвращается сразу после ERROR планировщика» — ERROR пишется на потоке сообщений PM (шаг 16); если консоль заморожена, поток встаёт внутри записи журнала. Путь backend_ctl в Task 1.1 консоль не замораживал — 0 из 6.

Проверка (дёшево)

  1. Стенд → выделить текст в окне prototype.
  2. topology.apply через backend_ctl → ждать зависания (очередь PM растёт).
  3. uvx py-spy dump PM: поток ProcessManager_message_processor в StreamHandler.emit / write.
  4. Снять выделение (Esc) → apply доходит.
Предсказание: зависание 1 из 1, стек на записи в консоль; без выделения — 0.

Попутно: с 2026-10-13 run_sim_all.ps1 пишет консоль через трубу в файл — при замёрзшей консоли теперь сначала заполнится труба, затем встанет тот же emit. Класс опасности тот же.

Если H1 подтвердится — правка двух уровней: консольный сток не пишет на потоке вызывающего (своя очередь и писатель с дропом, по принципу «один пишущий логгер»); и независимо — Task 1.2, apply не на потоке сообщений.

Правильный порядок (предложение, решает владелец / teamlead)

Сейчас GUI сначала меняет своё состояние (store, домен, устройства), потом просит бэкенд, а при провале откатывает своё, не зная, что успел бэкенд. По ADR-RCP-007 и принципу владельца 6 порядок обратный:

Диаграмма шире экрана — прокручивается внутри рамки →
  1. GUI шлёт recipe.activate(name) — одна команда, с recipe_path, без своих побочных эффектов.
  2. Бэкенд: валидация → apply (вне потока сообщений) → устройства как часть той же транзакции (носители раньше мостов) → барьер готовности по событию → запись манифеста → публикация «рецепт активен».
  3. GUI отражает опубликованное состояние, а не своё ожидание; таймаут GUI — только индикатор, без отката.

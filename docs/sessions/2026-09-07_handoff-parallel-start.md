# Точка входа: как запустить несколько чатов параллельно (2026-09-07)

Этот файл — **первое, что читает новый чат**. Он отвечает на три вопроса: где мы, за что
берётся именно эта сессия, и чего ей нельзя трогать, чтобы не столкнуться с соседней.

Правило одной строкой: **одно дерево — один писатель**. Столкновение здесь стоит дороже, чем
кажется, и это измерено, а не предположено: pre-commit **на каждом** коммите стешит все
незастейдженные правки tracked-файлов и накладывает обратно (в кэше 1176 патч-файлов по 77–86 КБ).
То есть чужая работа в общем дереве проходит цикл снятия/наложения при **каждом чьём угодно**
коммите — аккуратность стейджа тут ни при чём. Один раз чужая правка уже уехала под чужим
сообщением коммита.

## 3. Что обязан знать каждый чат, независимо от полосы

- **Стенд `8765` эксклюзивен** — два бэкенда конфликтуют по PID-реестру и SHM-cleanup.
  По умолчанию принадлежит полосе A. Занял — объявил, освободил — объявил. Коллектор `4318`
  не эксклюзивен.
- **Стейджить только явные пути.** `git add -A` в общем дереве уже утаскивал чужие правки.
  Перед `git add` на файл со статусом `M` — `git diff -- <путь>` глазами.
- **Слияние одностороннее:** closure → otel по ходу работы; обратно — только на фазовой точке и
  рукой ведущего closure. На файлы памяти `merge=union` **не ставить**: сжатие индекса
  не append-only, union дал бы обе версии хунков.
- **`docs/sessions/*.md`** сливаются union по `.gitattributes` — туда писать безопасно из любой полосы.
- Числа для вердикта считать `grep -F`, а не `grep`: точка в паттерне ловит соседнее имя
  с подчёркиванием и завышает счёт молча.

## 4. Два решения владельца — они блокируют, а не откладываются

**Решение 1. Merge в `main` — подготовлен, ждёт одной команды.**

Владелец попросил слить три ветки. Проверено пробным слиянием (`git merge-tree`, ничего
не меняет) — **сливать надо две, а не три**:

| ветка | пробное слияние | вердикт |
|---|---|---|
| `feat/otel-export` | **0 конфликтов** | сливать; **уже содержит closure целиком** (`3fd7d816`) |
| `feat/observability-closure` | — | приезжает внутри otel, отдельного действия не нужно |
| `rescue/wt-cto-task-2-11` | **5 конфликтов** | **не сливать** |

**Почему `rescue` не сливается — это замер, а не осторожность.** Ветка стоит на старой точке
линии closure (`3ef53392`, эпоха Task 2.11) и по спорному файлу **отстаёт**:
`test_f2_task211_zero_interval_hazards.py` — у closure **526** строк с классом
`TestADegenerateTickIsNotATick`, у rescue **450** без него. Конфликты: `DECISIONS.md`,
`observability_reload.py`, `telemetry_reload.py`, add/add на том самом тесте и
`test_observation_policy_review_f4.py`. Слияние такой ветки — это не «добавить работу»,
а положить более старое поверх более нового на четырёх файлах, причём вручную разрешая
конфликты в коде, который **никто не прогонял**: rescue тестами не гонялась ни разу.

**Её уникального — 48 строк** из 279 (остальные 231 уже в closure): механизм Р-11,
`detect_throttle_caps` судит кандидата по реальному ask, а не по голому нулю. Правильный путь
для них — **отдельная задача**, где механизм вернётся с тестером, инъекциями и ревью, а не
слияние архива в мейнлайн.

**Гейт на объединённом состоянии прогнан до слияния:** `9810 passed, 9 skipped, 1 xfailed,
0 failed` (6 мин 46 с) плюс собственные тесты otel **103 зелёных**. Оформленное ревью Ф2
существует тремя документами `docs/reviews/2026-08-12_observability-acceptance-f2{,-round2,-round3}.md`.

Остаётся выбор глубины, и он единственный: `main` получит **Ф2 плюс пять девятых незакрытой Ф3
плюс закрытые Ф0/Ф1 otel**. Ранее ведущий рекомендовал вливать ровно Ф2 (граница `6309cbe0`,
196 коммитов) — **эта рекомендация снята**, и вот почему: цель сменилась. Когда речь шла об
одной ветке, принятой единицей была Ф2. Сейчас цель — дать нескольким параллельным чатам **общую
базу**, а база, отстающая от живых веток на две фазы, воспроизводит ровно ту ловушку устаревшего
основания, из-за которой ветки и разъезжаются.

**Решение 2. Рез Ф3 с 9 задач до 6** (решение CTO: метрики отдать потребителю вместо того,
чтобы фреймворк придумывал их за продукт). Срезаются **3.4, 3.6, 3.7**. Проверено:

| задача | цена реза |
|---|---|
| **3.6** восемь метрик | **ноль.** 8 из 8 литералов не существуют в дереве; план otel: «3.6 → ничего, числа v1 не экспортирует» |
| **3.7** уборка стора | **почти ноль.** otel: «нет пересечения»; `purge()` и `auto_vacuum` построены раньше, остаток живёт у потребителя в `Plugins/io/telemetry_sink` |
| **3.4** метаданные метрик | **не ноль.** `declare_metric(name, *, owner)` — 103 вызывающих (11 боевых), `unit=` не передаёт ни один; вход v2 otel «числа → OTLP metrics» упирается именно в неё |

Рекомендация ведущего: 3.6 и 3.7 срезать целиком, **3.4 не резать, а ужать до подписи** —
`declare_metric(name, *, owner, unit="", description="", kind="gauge")` плюс страж единицы
у `record_timing`. Это 11 боевых мест, все с литеральными именами, миграция механическая;
дорогая половина (105 объявлений, колонка GUI, metadata в readback) уезжает к потребителю.

Эти действия отклонил классификатор прав сессии. Обходить их я не стал и соседней сессии

```bash

#    ff-only, БЕЗ checkout — рабочее дерево не трогается, push не делается.
#    feat/otel-export уже содержит closure целиком, поэтому вторая команда не нужна.
git fetch . feat/otel-export:main

# 2. Снять отработавший worktree слепого тестера Task 3.3.
#    Проверено: его файл сохранён в коммите c10c20bd, отличия только форматирование ruff
git worktree remove .claude/worktrees/t33-tester --force

# 3. Снять D:/wt_cto — он чист, работа целиком в ветке rescue/wt-cto-task-2-11 (14 файлов, +800)
git worktree remove D:/wt_cto
```

Ещё два кандидата на уборку, но их я не проверял глубоко и потому не рекомендую вслепую:
worktree `paths-cache` (его ветка `fix/plugins-paths-section-cache` **совпадает с `main`**, то есть
работа уже влита) и ветка-остаток `worktree-wf_4c97158d-0f5-4`, дублирующая `feat/telemetry-stage6`.

## 6. Что унаследовано и что в этом ненадёжно

- **`rescue/wt-cto-task-2-11`** (`9a6d9689`) — **архив, а не рабочая ветка**: тестами её никто
  не прогонял. Из 279 добавленных строк **231 уже есть в closure**, уникальны **48** — механизм
  Р-11 (`detect_throttle_caps` судит кандидата по реальному ask, а не по голому нулю). По одному
  файлу впереди наоборот closure. Уникальность считана сравнением множеств строк, а не
  семантически: строка, переписанная другими словами, попала в «уникальные».
- **Коммит `66858abd`** (numba в `strokes_to_points`) — работа остановленной перф-сессии.
  Тесты зелёные 104/104 на быстром пути, но **алгоритм ведущим не ревьюился**. Extra `perf`
  опционален, без numba работает прежний чистый Python.
- **Долги Task 3.3**, которые унаследует всякий, кто возьмёт `BatchDrainWorker`: оба сторожа
  гонок держатся на искусственно расширенном окне, а не на естественной конкуренции;
  `weakref.finalize` не покрыт тестом; финализатор зовёт `close()` с `join(2.0)` синхронно
  внутри `config.reload`.
- Числа «103 вызывающих» и «0 из 8 литералов» получены грепом, а не прогоном. Плагин **вправе**
  объявить собранное на лету имя через порт наблюдений, и такой вызов греп не увидит; сегодня
  таких вызовов в дереве нет — проверено отдельно.

# Живая команда агентов — руководство владельца

Дата: 2026-09-02. Движок: Claude Code 2.1.222. Что здесь: как устроена команда агентов,
которые создаются один раз и живут в сессии, как ей управлять и за ней наблюдать, во что она
обходится, и что именно изменилось в `.claude/` в этот день.

Короткий ответ на вопрос «так делают профессионалы?»: да, и движок это уже умеет из коробки.
Механизм называется Agent Teams, он экспериментальный, включается одной переменной окружения и
даёт ровно то, что описано в идее: участники-пиры с общим списком задач, перепиской по имени и
хуками-гейтами. Ниже — как этим пользоваться, не потеряв правила проекта, которые уже дорого
оплачены измерениями.

---

## 1. Три механизма движка — когда какой

| Механизм | Что это | Когда брать |
|---|---|---|
| **Субагенты** (`Agent`) | Лид спавнит воркера, тот возвращает отчёт лиду. Можно продолжить через `SendMessage` с сохранённым контекстом. Друг с другом не общаются. Фон по умолчанию. | Одна узкая задача: ревью, поиск, тестер в worktree. То, что делает `/dev:pipeline`. |
| **Agent Teams** (команда) | Лид создаёт команду; участники — полноценные сессии с общим списком задач, зависимостями, самозахватом и перепиской по имени. Хуки `TeammateIdle` / `TaskCompleted` как гейты. | Фаза плана из 3–8 задач, где участникам нужно спрашивать друг друга: тестер → разработчик → ревьюер на одном механизме. **Это то, что ты описал.** |
| **Workflow** (скрипт) | Детерминированный JS-скрипт `agent()` / `parallel()` / `pipeline()`, десятки агентов, результаты в переменных, а не в транскрипте. Запускается только по явному слову владельца («use a workflow» / `ultracode`). | Массовые повторяемые прогоны: 8 углов ревью → верификация каждой находки. Не для разработки фичи. |

Ключевое отличие команды от субагентов — **участники видят друг друга**. Раньше вся
координация шла через главный чат: тестер не мог спросить разработчика, где интерфейс, а
разработчик — тестера, где RED-тест. Теперь могут, и главный чат не тратит ход на пересылку.

## 2. Роли и модели

Схема из твоей идеи легла на существующих агентов почти без изменений — они уже были на этих
моделях. Добавились две роли.

| Роль | Агент | Модель | Effort | Что делает | Когда в команде |
|---|---|---|---|---|---|
| Лид, он же PM | главная сессия | Opus 5 | high | Формулирует задачу, пишет Task X.Y, спавнит, назначает, наблюдает, ломает (инъекции), сводит. Код не пишет. | всегда |
| Техдиректор | `cto` **(новый)** | Fable 5.1 | xhigh | Вердикты: приёмка фазы тремя линзами, merge-гейт, спор teamlead ↔ reviewer, решения, на которые лягут следующие фазы. Только запуском, не чтением. | один раз на фазу |
| Тимлид / сеньор | `teamlead` | Opus 5 | — | Senior+ реализация, эскалация на третьей итерации | по уровню задачи |
| Ревьюер | `reviewer` | Opus 5 | xhigh | Ревью задачи с воспроизведением | после каждой задачи |
| Следователь | `investigator` | Opus 5 | — | Диагноз неочевидного дефекта, read-only | по живому дефекту |
| Менеджер | `manager` | Opus 5 | — | Спека Task X.Y для больших фаз | от 4 файлов |
| Разработчик | `developer` | Sonnet 5 | — | Middle-реализация по спеке | по уровню задачи |
| Тестер | `tester` | Sonnet 5 | — | Тесты от acceptance, слепой, в worktree | один раз на механизм, **до** кода |
| Отладчик | `debugger` | Sonnet 5 | — | Воспроизвести → гипотезы → причина | по FAIL |
| Джуниор | `junior` **(новый)** | Haiku 4.5 | low | Механика с написанным диффом: переименования по списку, докстринги, копии фикстур, STATUS.md. Не коммитит. Останавливается, если нужно решение. | по задаче с готовым диффом |
| Писатель | `docs-writer` / `tech-writer` | Haiku / Sonnet | low / — | README, STATUS / ADR, ARCHITECTURE | по необходимости |

Главная сессия теперь стартует на **Opus, effort high** — это записано в
`.claude/settings.json` (`"model": "opus"`, `"effortLevel": "high"`) и перекрывает глобальный
Fable для этого проекта. Так ты решил ещё 2026-07-14 («главный чат Opus, Fable точечно»), но
глобальные настройки это решение не отражали. Fable остался там, где его цена окупается: `cto`.
Вернуть Fable в главный цикл на одну сессию — `/model fable`; навсегда — убрать две строки из
`settings.json` и из `.claude/plugins/core/settings.partial.json`.

**Что не меняется в командном режиме.** Все правила из `.claude/CLAUDE.md` действуют как
были: тестер один раз на механизм и раньше кода, в worktree на pre-impl коммите; инъекции
делает лид и никому не делегирует; ревьюер синхронно после каждой задачи; Fable только на
приёмке фазы. Команда меняет транспорт между агентами, а не порядок доказательств.

**Почему именно такой состав и не больше.** Отдельного агента-«продукт-менеджера» нет и не
нужно: PM — это главная сессия, у неё уже есть вся история разговора с тобой, и любой агент-PM
был бы копией лида без этой истории. `cto` добавлен потому, что приёмка фазы Fable уже была
измеренной практикой (три линзы, ~580k токенов, находки вне спеки), но жила только в памяти —
теперь это роль с фиксированным протоколом. `junior` добавлен по твоей схеме и оправдан только
ценой: Haiku на переименование по списку или копию фикстуры дешевле Sonnet в разы, а ошибиться
там негде, если дифф написан. Если через месяц у `junior` не будет ни одной задачи — удалить,
это правило проекта («флаг закрыт, когда удалён»). Остальные десять ролей существовали до
этого дня и не менялись по существу.

### Цепочка эскалации — как в настоящей компании

Если агент не справился — не хватает решения, спека противоречит коду, третья итерация
провалилась — вопрос идёт на один уровень вверх, не вбок и не в догадку. Цепочка одна для всех,
записана в skill `project-rules` §7 и известна каждому агенту:

| Кто не справился | К кому идёт вопрос | Типичный повод |
|---|---|---|
| `junior`, `docs-writer` (Haiku) | `developer` / `tech-writer` (Sonnet) | правка требует выбора, которого нет в задаче |
| `developer`, `tester`, `debugger`, `tech-writer`, `spec-writer` (Sonnet) | `teamlead` (Opus) | проектное решение, спека противоречит коду, две неудачные итерации; `debugger` может сначала к `investigator` за диагнозом |
| `teamlead`, `reviewer`, `investigator`, `manager`, `integrator`, `ai-judge` (Opus) | `cto` (Fable) | архитектура, владение, инвариант; спор teamlead ↔ reviewer после двух итераций; решение уровня ADR |
| `cto` (Fable) | ты, через лида | scope, приоритет, железо, бюджет; вопрос записывается в `docs/claude/OPEN_QUESTIONS.md` |

Механика: в команде участник пишет уровню выше по имени (`SendMessage`); если этой роли в
команде нет — пишет лиду тем же текстом, и лид спавнит роль. Субагент вне команды заканчивает
отчёт блоком `ESCALATION -> <role>` (вопрос, что пробовал с выводом, на чём заблокирован,
файлы), и лид спавнит роль. Один уровень за раз: джуниор не пишет техдиректору. Ответ
возвращается тем же путём, и уровень выше отвечает на вопрос, а не забирает задачу — если не
скажет об этом явно. Лид при этом не подменяет собой роль выше: его работа — проследить, что
вопрос дошёл и ответ вернулся спросившему.

## 3. Как запустить: `/dev:team <фаза или задача>`

Команда ведёт лида по девяти шагам; здесь — суть каждого и почему он такой.

1. **Предусловия.** Есть ли инструменты `TeamCreate` / `TaskCreate` (если нет — переменная не
   подхватилась, нужен перезапуск сессии; работать через `/dev:pipeline`). Чистый `git status`,
   `ListAgents` без второй сессии в том же дереве, ветка не `main`. Цена вслух: участник — это
   полная сессия, около 25k токенов до первой строки кода.
2. **Intake.** Лид пересказывает задачу тремя блоками — цель, приёмка (3–6 проверяемых строк),
   вне scope — и показывает тебе до декомпозиции. Вопросов максимум два, только где разные
   прочтения дают разную работу. Это и есть «помогает грамотно формировать задачи».
3. **Декомпозиция.** Task X.Y по формату проекта. Гейт независимости: непересекающиеся `Files:`
   → параллельно, иначе цепочка. От четырёх файлов спеку пишет `manager`.
4. **Состав — минимальный.** Только роли, у которых есть задача. Таблица выше.
5. **Спавн и брифы.** Бриф на английском по шаблону
   [`.claude/plugins/dev/templates/team-brief.md`](../../.claude/plugins/dev/templates/team-brief.md)
   — там же заметки под каждую модель (§7). Пишущие — каждый в своём worktree
   `.claude/worktrees/team-<task>`; читающие — в общем дереве. Не больше трёх пишущих.
6. **Задачи.** `TaskCreate` с зависимостями. Задача тестера называется `[RED] …` — гейт не
   гоняет на ней pytest, красный набор там по замыслу.
7. **Наблюдение.** §4 ниже.
8. **Инъекции и ревью.** Лид ломает каждую заявленную гарантию по отдельности против обоих
   наборов тестов; `reviewer` синхронно после задачи; две итерации → `teamlead`; спор → `cto`.
9. **Merge-back и выключение.** Ветки worktree вливает лид, по одной, с `git show --stat` на
   каждый коммит. Участников попросить остановиться, команду удалить: `/resume` её не вернёт.

**Первый пробный запуск — рецепт на полчаса.** Возьми одну маленькую задачу с одним
механизмом. Состав: `tester` + `developer` + `reviewer`, без `cto`. Цель прогона — не фича, а
проверка проводки: тестер получил RED-задачу и спросил разработчика про интерфейс по имени;
гейт `TaskCompleted` сработал на красном тесте разработчика и отпустил после починки; в
`data/team-journal.jsonl` появились строки старта и финиша; merge-back прошёл без мусора в
коммите. Если хоть одно из четырёх не случилось — это находка, а не повод чинить на ходу.

## 4. Как наблюдать и контролировать

### Клавиши и команды (in-process режим, единственный доступный в Windows Terminal и VS Code)

| Действие | Как |
|---|---|
| Общий список задач: кто взял, что заблокировано | `Ctrl+T` |
| Открыть транскрипт участника, написать ему | `↑` / `↓` выбрать → `Enter`; `Esc` — назад к лиду |
| Остановить участника | выбрать → `x` |
| Всё, что крутится в сессии: фоновые агенты, команды, workflow, `/loop` | `/tasks` |
| Фоновые сессии вне этой | `/agents` (или `claude agents` из shell) |

### Три хука-гейта (`.claude/plugins/dev/hooks/`)

| Хук | Что делает | Когда блокирует | Предохранители |
|---|---|---|---|
| `TaskCompleted` → `team-task-completed-gate.sh` | `ruff check` на изменённых `.py`; `pytest -x` на изменённых тестовых файлах (таймаут 90 с) | ruff красный или тесты красные → задача остаётся открытой, участник получает хвост вывода и указание, что делать | два блока на одной задаче → третий проходит с предупреждением; таймаут не блокирует; `[RED]`, `[docs]`, `[skip-gate]` в заголовке — пропуск; `TEAM_GATES=off` — выключить |
| `TeammateIdle` → `team-teammate-idle-gate.sh` | Проверяет незакоммиченное в рабочем дереве участника | **только внутри linked worktree** (там правки точно свои) — не даёт уйти в idle с незакоммиченным; в общем дереве лишь предупреждает лида: «стейджить явные пути, не `git add -A`» | два блока на одного участника → третий проходит |
| `SubagentStart` / `SubagentStop` → `team-journal.sh` | Пишет строку `{ts, event, agent_type, agent_id, cwd, tail}` в `data/team-journal.jsonl` | никогда | `data/` в gitignore |

Почему гейты «мягкие» после двух срабатываний: хук с exit 2 заставляет участника продолжать
работу, и если условие для него невыполнимо (например, красный тест принадлежит соседу в общем
дереве), жёсткий гейт превращается в бесконечную петлю, которая жжёт токены, а не дефекты.
Два блока и пропуск с предупреждением — то же правило «две итерации → эскалация», что и во всём
проекте. Счётчики лежат в `data/team-gates/` и стираются при первом зелёном проходе.

### Что читать после сессии

- `data/team-journal.jsonl` — хронология: кто стартовал, кто закончил, последние 300 символов
  каждого финального сообщения.
- `data/team-gates/*.strikes` — если файл остался, гейт по этой задаче так и не прошёл.
- `git log --stat` по веткам worktree — совпадает ли diff с сообщением коммита.

## 5. Git-дисциплина в команде — почему именно так

Измерено на этом проекте дважды (2026-05-24 и 2026-05-26): два и больше пишущих агентов в
одном дереве плюс pre-commit хук, который стейджит журнал сессий, дают коммит, чьё сообщение
не соответствует содержимому, и файлы, пропавшие из истории. Правила:

1. **Один worktree на пишущего**, ветка `<type>/<slug>-<task>` от текущего HEAD. Читающие —
   в общем дереве.
2. **Venv в worktree не создавать.** Пакет не установлен в `.venv` как editable (проверено:
   `multiprocess_framework` импортируется по пути, а не из site-packages), поэтому главный
   `.venv` из корня worktree с `PYTHONPATH=$PWD` резолвит именно код worktree. А `uv sync` в
   свежем worktree притащил бы CPU-сборку torch на гигабайты вместо CUDA-колеса.
3. **Стейджить явные пути**, никогда `git add -A`: чужая незакоммиченная работа уедет под твоим
   сообщением.
4. **`git show --stat` после каждого коммита** — pre-commit хук добавляет журнал сессий, коммит
   может нести больше, чем ты стейджил.
5. **Union-merge для `docs/sessions/*.md`** — добавлен в `.gitattributes`; журнал только
   дополняется, конфликт на каждом merge-back снят.
6. **Вливает только лид**, по одной ветке. Осиротевший worktree — эскалация, не `rm`.

## 6. Стоимость и ограничения движка

**Цена.** Каждый участник — полноценная сессия Claude Code: грузит три `CLAUDE.md` и
`MEMORY.md` (около 22k токенов, замер 2026-08-27), системный промпт, схемы инструментов —
порядка 25k до первого действия. Команда из четырёх — 100k на старте, и это до работы.
Отсюда правила: минимальный состав, Sonnet как исполнитель по умолчанию, Haiku на механику,
Fable один раз на фазу. Рычаги ограничения: `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` и
`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` в `env` (сейчас дефолты: 20 и 3 — не трогал, чтобы не
задушить 8-угловое ревью; включай, если увидишь лишний спавн).

**Ограничения Agent Teams в 2.1.222.**
- Участники **не переживают `/resume`**: после возобновления лид может писать тем, кого уже нет.
- Одна команда на сессию; участник не может создать свою команду и не может запускать фоновых
  субагентов (только синхронных).
- Лид фиксирован, передать лидерство нельзя.
- Участник может забыть отметить задачу выполненной и заблокировать зависимые — смотри `Ctrl+T`.
- Останов медленный: участник дорабатывает текущий запрос.
- Разделённые панели недоступны в Windows Terminal и VS Code — только in-process. На macOS с
  tmux можно `"teammateMode": "tmux"`.
- Права одинаковы для всей команды и наследуются от лида.

## 7. Prompt engineering под модели — что учтено

По руководству Anthropic «Prompting best practices» и страницам под конкретные модели
(2026-09). Применено в двух новых агентах, в шаблоне брифа и в общем skill `project-rules`.

**Для всех моделей.** Ясно и прямо: «сделай изменения», не «можешь предложить». Мотивация
рядом с правилом — модель обобщает объяснение лучше, чем запрет. Примеры в `<example>`.
Структура тегами `<role>`, `<task>`, `<context>`, `<working_rules>`, `<report>`. Формат ответа
задаётся тем, что делать, а не чем не делать. Длинные данные — в начало, вопрос — в конец.
Независимые вызовы инструментов — параллельно. «Выбери подход и держись его».

**По ярусам.**
- **Sonnet 5** (developer, tester, debugger): исполняет буквально и не обобщает инструкцию с
  одного элемента на другие — scope называть явно («во всех четырёх файлах»); задачу, намерение
  и ограничения давать сразу одним сообщением. Для поиска дефектов: «сообщай всё, включая
  неуверенное и низкой важности — фильтрует отдельный проход».
- **Opus 5** (teamlead, reviewer, investigator, manager): сам проверяет свою работу — фразы
  «перепроверь», «проверь субагентом» убрать, они дают избыточную верификацию; scope
  ограничивать явно; делегирование капать («не спавнь субагента на то, что сделаешь за
  несколько вызовов»); лаконичность просить словами — effort длину прозы не меняет.
- **Haiku 4.5** (junior, docs-writer): нумерованные шаги, точные якоря и списки файлов, одна
  команда проверки, фиксированная форма отчёта; всё, что не написано, вернётся вопросом — так и
  задумано.
- **Fable 5.1** (cto): сказать, какие отчёты о ходе нужны между вызовами; «сначала составь
  список нужного, потом запроси всё независимое одним ответом»; scope — это deliverable;
  длинные задачи доводит сам — не просить разрешения на уже запрошенную работу.

### Насколько лучше и почему — честно, с числами

1. **Дрейф источника и зеркала устранён.** Все 12 агентов в `.claude/agents/dev/` (зеркало,
   которое читает Claude Code) отличались от своих источников в `.claude/plugins/dev/agents/`
   на 55–65 строк каждый: общие правила, `skills:`, шаг про graphify были дописаны 2026-08-26
   только в зеркало. Любой `claude-kit sync` перезаписал бы зеркало из источника и **молча
   снял бы правила со всех двенадцати агентов**. Сейчас пары идентичны (проверено `diff`,
   12/12). Это самая важная правка дня, и она не про команду.
2. **Правила в одном месте.** Было: один и тот же блок на 60 строк в 12 файлах (12 копий,
   md5 совпадал), править — в двенадцати местах. Стало: один файл-skill, агенты подгружают его
   через `skills:` и заканчиваются четырёхстрочным указателем на случай, если preload не
   сработал. Объём файлов агентов: 2557 → 1907 строк (−650, −25 %). Контекст одного агента при
   этом **не уменьшился** — skill грузится в него целиком и он длиннее старого блока (добавлены
   разделы про MCP, коммиты, субагентов, язык); выигрыш — в сопровождении и согласованности, а
   не в токенах на вызов.
3. **Устаревшая посылка исправлена во всех агентах разом.** В блоке правил стояло: «индекс
   qex живёт устаревшим намеренно». Корневой `CLAUDE.md` эту посылку снял ещё 2026-08-27
   (индекс пересобран, инкремент — 7 минут), а агенты продолжали её читать. В skill стоит
   актуальная формулировка: «возраст индекса узнаётся только по дате».
4. **Один язык на файл.** Агенты — английский целиком; команды, руководства, отчёты —
   русский. Раньше каждый агент был английским телом с русским хвостом.
5. **Гейты вместо надежды.** Раньше «задача закрыта» означало «участник так сказал». Теперь
   закрытие задачи проходит через ruff и pytest на его же изменённых тестах, а уход в idle из
   worktree — через проверку незакоммиченного. Хуки проверены на синтетическом репозитории
   (см. §9), не на живой команде.
6. **Схема моделей записана в конфиг, а не в память.** Главный цикл на Opus, Fable точечно —
   это было правилом в памяти с июля, но глобальные настройки держали Fable на весь цикл.

### Чего это не даёт и что не проверено

- **Живая команда в этой сессии не запускалась**: переменная окружения подхватывается при
  старте сессии, инструментов `TeamCreate` / `TaskCreate` здесь ещё не было. Первый реальный
  прогон — по рецепту из §3; если инструменты не появятся, значит, переменная не читается из
  проектных `settings.json` в твоей сборке — тогда её место в глобальном `~/.claude/settings.json`.
- **Preload skill для участников команды** — из документации следует, что in-process участник
  получает тело определения агента и инструменты лида; про `skills:` там сказано только для
  split-pane режима («игнорируются»). На случай, если и in-process их не грузит, у каждого
  агента остался указатель «прочитай `.claude/skills/project-rules/SKILL.md`». Проверить в
  первом прогоне: спросить участника, видит ли он раздел «Project rules».
- **Хуки проверены на синтетическом репозитории**, не под нагрузкой; сценарий «красный тест
  соседа в общем дереве» закрывается только предохранителем из двух срабатываний.
- **`claude-kit upgrade`** по-прежнему может перетереть `settings.json`; источники (`partial`,
  `plugin.json`) обновлены, так что пересборка воспроизведёт настройки, но после апгрейда всё
  равно сверить `git diff .claude/settings.json`.
- Глобальные файлы `~/.claude/CLAUDE.md` и `~/.claude/TEAM_REFERENCE.md` устарели (там
  «Manager — Sonnet», «Opus 4.6», путь `.claude/agents/company/`), а `~/.claude/agents/company/`
  держит шесть старых русскоязычных дублей с теми же именами, что и проектные агенты; здесь
  они перекрываются проектными, в других проектах — активны. Не правил: это твои личные файлы,
  решение за тобой.

## 9. Как проверялись хуки

Синтетический git-репозиторий в scratchpad: коммит с чистым файлом, потом добавлен файл с
ошибкой ruff и красный тест. Ожидания записаны до прогона:

| Сценарий | Ожидание | Факт (прогон 3, после починки) |
|---|---|---|
| `TaskCompleted`, заголовок `[RED] …` | exit 0, ничего не запускается | exit 0 |
| `TaskCompleted`, ruff красный | exit 2, файл `data/team-gates/task-*.strikes` = 1 | exit 2, strikes = 1, в stderr `F401 os imported but unused` |
| тот же второй раз | exit 2, strikes = 2 | exit 2, strikes = 2 |
| тот же третий раз | exit 0 с предупреждением, strikes удалён | exit 0, файлов strikes 0, предупреждение «third attempt… passing» |
| `TaskCompleted`, ruff чист, тест красный | exit 2 с хвостом pytest | exit 2, `assert False` в stderr |
| всё зелёное | exit 0, strikes удалён | exit 0, файлов strikes 0 |
| `TeammateIdle`, грязное общее дерево | exit 0, JSON с `systemMessage` | exit 0, `{"systemMessage":"team-gate: developer (a1) went idle…"}` |
| `TeammateIdle`, грязный linked worktree, 1-й и 2-й раз | exit 2, текст с путём worktree | exit 2, в stderr путь worktree и `?? new.py` |
| тот же третий раз | exit 0 (fail-open) | exit 0 |
| `TeammateIdle`, чистый worktree | exit 0 | exit 0 |
| `SubagentStop` | строка в `team-journal.jsonl` | строка `{"ts": "2026-09-02T20:55:11", "event": "SubagentStop", "agent_type": "tester", …}` |
| `TEAM_GATES=off` при красном ruff | exit 0 | exit 0 |

Итог: 13 из 13 совпали с предсказанием — **с третьего прогона**. Первые два прогона дали
exit 0 вместо 2 на трёх сценариях worktree, и это была настоящая находка, а не ошибка теста:
Python под Windows печатает поля из JSON с `\r\n`, `mapfile` снимает только `\n`, и путь
`cwd` с хвостовым `\r` не проходил `[ -d ]` — хук молча падал на «текущую папку процесса», то
есть на главное дерево. В общем дереве это выглядело как правильная работа (сценарий S7
проходил по ложной причине), в worktree ломало гейт целиком. Починено снятием `\r` в обоих
гейтах. Урок тот же, что и во всём проекте: зелёный сценарий обязан иметь парный красный.

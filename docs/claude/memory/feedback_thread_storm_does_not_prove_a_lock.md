Тест «N потоков × M инкрементов, числа сошлись» **не доказывает лок**. Инъекция «лок снят»
оставляла его зелёным даже при `sys.setswitchinterval(1e-6)` и при карте, отдающей GIL внутри
чтения (`time.sleep(0)`).

**Why:** в CPython 3.12 `slot[0] += 1` — прямолинейная цепочка байт-кодов без проверки
eval-breaker, планировщику некуда вклиниться; а `time.sleep(0)` отпускает GIL, но не обязан
отдать его ждущему. Измерено на Task 4.1 `telemetry-stage6` (8 потоков × 2000, затем 40 раундов
с враждебной картой — обе редакции зелёные под инъекцией).

**How to apply:** проверять СВОЙСТВО, а не следствие. `threading.Barrier(2)` ставится ВНУТРИ
критической секции (в вызове, который она делает — `dict.get`, `len`, любой CALL):

* под локом второй поток до барьера не доходит → барьер разваливается по сроку
  (`BrokenBarrierError`) — это **ожидаемый** исход, его и утверждаем;
* без лока оба внутри одновременно → барьер срабатывает, факт записывается → красный.

Детерминированно, ~0.5 с, краснеет ровно на снятом локе. Заодно: настоящее окно гонки шире
инкремента — оно между «прочитал графу» и «записал новую», потому что там два CALL'а. На сборке
без GIL (3.13t+) вернутся и инкременты, проверка от этого не меняется.

**Повтор 2026-10-27 (C-55b, `ml_inference/plugin.py`).** Замок `_engine_lock` держит связку
«флаг `_asset_degraded` + `ctx.health.status`». Сторож-гонка из случайных потоков (Г5) остался
зелёным при снятом замке 6/6 прогонов. Детерминированный перекрёст (Г6) ловит снятый замок
5/5. В нём первый поток ставится на паузу `threading.Event` внутри критической секции, между
записью флага и записью статуса. Второй поток в это время пытается войти. Вариант с Event
подходит, когда в секции две записи и надо доказать, что вторую никто не видит раньше первой.
Barrier подходит для проверки «двое внутри одновременно». Правило для брифа: сторож замка —
это всегда детерминированный перекрёст; случайная гонка идёт только дополнением.

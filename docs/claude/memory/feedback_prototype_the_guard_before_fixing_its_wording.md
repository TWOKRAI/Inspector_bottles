Task 1.3c плана `observability-closure` требовала страж «`log_error` рядом с `report_error`
в одной ФУНКЦИИ» с критерием «зелёный на дереве после 1.3b» и запретом whitelist (решение Р-9).
Ревьюер написал этот страж БУКВАЛЬНО по спеке и прогнал: **3 функции / 4 адреса красных**,
зелёным не станет никогда. На предреализационной ревизии тот же прототип воспроизвёл инвентарь
**46/32** — то есть «в одной функции» и БЫЛО методом инвентаря, формулировку просто перенесли
из способа подсчёта в правило, и она пережила своё основание.

Три остатка оказались тремя разными законными случаями: тело определения самого разъёма
(внесено предыдущей задачей), запасной путь `if health is None: log else: report`, и две строки
РАЗНЫХ классов события, разведённые ранним `return`. Ни один не дубль объявления.

**Класс: единица правила (функция / ветка / файл) — часть правила, а не деталь реализации.**
Правило с неверной единицей не «слегка шумит» — оно недостижимо, и единственный выход из него
whitelist, который правило и убивает.

Мой прототип по дороге дважды соврал, и оба раза в СТОРОНУ УЖЕСТОЧЕНИЯ: сперва брал внешний
`try` вместо ближайшей развилки, потом не различал два `except` одного `try` (поле у них одно —
`handlers`, различает только индекс). Оба раза законные `if/else` выглядели нарушением.
Числа стали верными только с третьей редакции.

**Why:** формулировка правила стоит дёшево, пока не написан код; внутри задачи она стоит
переделки задачи и решения владельца в неудобный момент. Прототип на 40 строк AST дал числа
для развилки за один заход.

**How to apply:** если задача обещает СТРАЖ с критерием «зелёный на дереве», прототипировать его
ДО старта задачи и снять два числа: сколько красных на текущем дереве и сколько на дереве до
изменения. Совпадение второго с инвентарём — признак, что формулировка унаследована от способа
подсчёта. Обязателен контроль: подсадить нарушение и убедиться, что страж краснеет ПО АДРЕСУ, —
иначе «ноль красных» означает «никого не ловит».

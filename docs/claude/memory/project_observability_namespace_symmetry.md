Задача 5.10 плана `observability-unified-routing` закрыта 2026-07-28
(`a0ac4ec3`…`f92947eb`). Снятие приёмника на ЛЮБОЙ из трёх плоскостей
(logger / error / stats) пишется в слой L3 и переживает `config.reload`; ключ
повторяет путь секции конфига (`channels.…`, `errors.channels.…`,
`stats.channels.…`). Телеметрия вошла туда же: `publish` — по ключам,
`throttle` — одним непрозрачным листом.

**Главное, что стоит помнить и чего нет в коде очевидным образом:**

1. **Плоский namespace слоёв предполагает, что точек в именах ключей нет.**
   Паттерны центрального троттла (`processes.**.state.fps`) это нарушают:
   `session_set` режет путь по точкам и заводит вложенное дерево РЯДОМ с
   настоящим правилом, а `session_reset_keys` снимает дерево, рапортует успех и
   оставляет правило жить. Обходится списком `OPAQUE_LAYER_PATHS` — это
   **точечное исключение, а не лечение**; корневое лечение (экранирование или
   адресация кортежами) записано резидуалом S1.
2. **`module_*`-каналы логгера** описаны в секции `modules`, а не `channels`.
   Имя канала (`module_camera`) и имя модуля (`camera`) различаются: перевод
   живёт в `LoggerCore._module_channel_disabled`, и второго написания заводить
   нельзя. Запись `channels.module_X.enabled` — это ЗАПИСЬ ОБ ОТМЕНЕ, а не
   описание канала; прочитанная как описание, она строит фантомный файл.
3. **Слияние каналов плоскости ошибок обязано быть глубоким.** Поверхностное
   `{**severity, **extra}` оставляло от канала один ключ `{enabled: false}` —
   без `type` и `file_path`, то есть вернуть его было некуда.

Ключ конфига может читаться на РАЗНЫХ дорогах: стартовая проводка и пересборка после
`config.reload` — это два разных вызова, и запрет, поставленный на одной, на второй не
действует. Тест, прошедший по одной дороге, зеленеет, пока боевая идёт по другой.

**Why:** Task 2.1 `telemetry-stage6`. Ключ `channels.hub_stats.enabled=false` проверялся
только в `_setup_channels`, а боевая проводка шла через `attach_observability_hub` →
`_recreate_channel`, который **намеренно** игнорирует `enabled` (он обслуживает
`sink.enable` — явный override оператора над конфигом). На старте `_setup_channels`
отрабатывает ДО появления hub'а и до этого канала просто не доходит. Итог: снятый
оператором канал поднимался и слал данные, а первый `config.reload` потом молча его
убирал — поведение менялось само, без команды. Мой тест «доказывал» ручку через
`register_manager` + `_setup_channels()`, то есть в обход той дороги, которой ходит
процесс. Нашёл ревьюер воспроизведением; правило §3.2 плана это прямо запрещает
(«доказательство — сборкой на живом процессе, не юнитом в обход дороги»).

Второй виток того же: когда я стал крыть обе дороги ОДНОЙ слом-инъекцией, она дала
ложный вердикт «гарантия не сторожится» — потому что дороги стерегли РАЗНЫЕ тесты
(мой — attach, тест независимого тестера — пересборку).

**How to apply:**
- Прежде чем писать «ручка работает», спросить: **сколько входов у этого ключа** и
  какой из них боевой. Ответ искать вызовами, а не чтением схемы.
- Различать «override оператора» и «проводка процесса»: функция, намеренно игнорирующая
  конфиг ради первого, не годится второму.
- Тест — по боевой дороге и по ЭФФЕКТУ (доехало/не доехало), не по занятости имени в
  реестре.
- Инъекция — по одной на дорогу. Родня: [[feedback_defect_fixed_on_one_path_only]],
  [[feedback_facade_is_a_whitelist_not_a_passthrough]], [[feedback_port_wire_is_not_a_process_route]].

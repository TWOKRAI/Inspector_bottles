Заголовок задачи называет механизм («процессор контекста», «процессор
обогащения»), но выбор механизма — вывод, а не условие. В Ф4 плана
`observability-unified-routing` **три задачи из шести** закрылись не тем, что
названо: 4.4 — одной строкой Resource, 4.6 — сносом, 4.3 — функцией модуля.

**Проверка, работающая в обе стороны: годится ли для X политика ОТКАЗА
механизма.** У цепочки процессоров две политики — «вернул None = поглотил» и
«бросил = запись едет без правки». Для сборки контекста вторая означает запись
без `proc_name` на пути ошибок, то есть регенерацию уже чинёного дефекта →
контекст не перехватчик. Для редакции секретов (4.5) политика не годится в
другую сторону («сломались → показали секрет»), и это не отменило механизм, а
потребовало своего `try` внутри — fail-closed.

Второй вопрос того же ряда: **где живёт механизм**. Цепочка — атрибут
экземпляра, а менеджеров в процессе минимум два (`LoggerManager` +
`ErrorManager`). Всё, что обязано действовать на обоих, инлайном в общем
предке достаётся даром, а перехватчиком требует регистрации у каждого.

**Why:** заявленный объём фазы был вдвое больше настоящего; проверка на входе
в каждую задачу стоит десять минут и экономит механизм.

**How to apply:** входя в задачу с механизмом в заголовке, сперва ответь двумя
фактами — (1) что уже доставлено соседними фазами (grep, не память), (2)
годится ли политика отказа механизма для этой работы. Отказ от механизма
записывать в план явно, иначе таблица «Открыто» его воскресит
([[feedback_a_plans_premise_expires]], [[feedback_one_active_plan_per_tool]]).

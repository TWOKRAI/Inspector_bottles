Владелец 2026-10-03, по итогам диагноза падения `run_framework_tests` (Task 5.5d, transport-single-policy):
«переделать так, чтобы подобных проблем не было»; «должен быть универсальный механизм у всех».

Факты, из-за которых решение принято:
- падение = живой Python-owned QWidget в циклическом мусоре + `gc` на неглавном потоке → shiboken delete-in-main-thread → `abort()`;
- источник цикла — код фреймворка: `NumericPresenter → SyncTrait → RegisterAdapter.subscribe(bound method) → presenter → view`; отписки нет вообще (`SyncTrait` без `unsubscribe`); 60 тестов в 10 модулях `frontend_module/tests`;
- усилитель — утёкшие потоки `batch-drain-*`, которые никто не закрыл.

**Why:** тестовая сборка мусора на главном потоке прячет причину; в проде те же кольца = утечки презентеров/виджетов и риск того же abort в GUI-процессе.

**How to apply:**
- Одна примитива-«владелец» (scope) держит disposable-ручки любого рода: подписка, поток, tap, таймер, виджет, дочерний процесс; упорядоченный dispose с дедлайнами. Не три механизма по областям.
- Тестовый страж Qt-мусора — детектор (валит тест с типами), не уборщик. Условие опасности — `shiboken6.isValid(o) and shiboken6.ownedByPython(o)`, а не просто «QWidget в мусоре».
- Направления «отделить фронт от бэка» и «надёжные подписки» владелец назвал оба — выбор по разведке трёх investigator'ов (подписки / потоки+останов / GUI+граница), затем CTO на архитектуру.
- 5.5d как «починка тестов» не вливать — она поглощается этим треком.
- Планка владельца для архитектуры (2026-10-03): «каждый модуль отвечает за свой функционал, без дублирования, всё связано через интерфейсы как полагается, без костылей». Для каждой функции цикла жизни (примитив, список подписчиков, порождение потоков, эскалация останова процесса, Qt-привязка, бюджет останова, сток отчёта) — ровно ОДИН владелец и Protocol в `interfaces.py`.
- Порядок ревью архитектуры, заданный владельцем: ревьюер получает вердикт CTO → редакция ревьюера → CTO оценивает и советует.

Итог 2026-10-03: план `plans/2026-10-03_lifecycle-owner-scope/` (plan.md + DESIGN.md ред. 3, CTO ACCEPT WITH CONDITIONS три раунда), ветка `feat/lifecycle-owner-scope`, **первый приоритет очереди** (ORDER.md §0, полоса Ж — решение владельца). Механизм: `IScope` в `base_manager`, один корень процесса с барьерами (planes | transport | work), `Subscribers` в `event_module`, `qt_lifetime` во `frontend_module`; abort закрывает Ф5, 5-с ханг — Ф1.

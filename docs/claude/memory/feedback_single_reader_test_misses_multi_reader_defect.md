Task 5.6 (2026-07-30): `observed_rate_per_sec` держал ОДНУ базу отсчёта внутри
менеджера и сдвигал её на каждом чтении. Потребителей readback два — панель
наблюдаемости GUI и backend_ctl; опрашивая с разной частотой, они портили
показания друг другу (второй видел интервал с последнего чтения первого).

**15 тестов и живой зонд 7/7 этого не поймали: все читали в одиночку.** Нашлось
только когда владелец спросил «так это лучшие решения?» — вопрос сработал как
ревью.

**Why:** производная метрика с состоянием внутри поставщика — это скрытая связь
между независимыми потребителями. Одиночное чтение её принципиально не видит,
сколько бы тестов ни было.

**How to apply:** если readback отдаёт ПРОИЗВОДНОЕ число (темп, дельта, «с
прошлого раза»), спроси: где живёт база отсчёта? Внутри поставщика — пиши тест с
ДВУМЯ читателями разной частоты. Лучше — не отдавай производное вовсе: отдай
счётчик и метку времени, частное считает потребитель (так делает любой scraper).
Тогда класс дефекта исчезает вместе с механизмом. См. [[feedback-plausible-is-not-verified]],
[[feedback-single-marker-verdict-lies]].

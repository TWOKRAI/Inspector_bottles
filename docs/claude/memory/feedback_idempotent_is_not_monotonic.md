Проверив, что все команды пути идемпотентны, легко решить, что повторная доставка
безопасна. Это неверно: **идемпотентность ≠ монотонность**. Дубль безвреден —
устаревший конверт, приехавший ПОСЛЕ свежего, нет.

**Как это выглядело (5.11-R4 + ревью Fable, 2026-07-29).** К веерной рассылке
добавили вторую, отложенную доставку («досылку») для процессов, которые ещё не
умеют принимать команды. Идемпотентность всех четырёх команд пути была проверена
по коду обработчиков и подтвердилась. Но два switch подряд давали
детерминированный порядок `['C', 'B']`: досылка конверта B ждала событие
инкарнации, которую следующий switch уже снёс, дотягивала дедлайн и приезжала
последней. У `routing.refresh` был страж по эпохе и он уцелел; у `config.reload`
монотонного стража не было — ребёнок пересобирал слой **покинутого** рецепта.

Правило: **любой второй путь доставки (retry, досылка, реконнект-replay) обязан
нести признак свежести** — поколение, эпоху, версию. Иначе он превращается из
страховки вмеханизм, возящий прошлое в настоящее.

Проверка при проектировании такого пути:
- у команды есть монотонный страж на стороне получателя? если нет — страж нужен у
  отправителя (поколение рассылки, снимаемое при появлении нового конверта);
- ожидание должно уметь **отменяться**: ждать событие, которое уже никто не
  взведёт, — это не задержка, а гарантированная доставка устаревшего;
- «все команды идемпотентны» — не ответ на вопрос о порядке.

Резидуал R6 плана `observability-unified-routing` закрыт 2026-07-29: живой switch
рецепта прогнан на стенде (`dualcam_synth` → `g1_perf_probe`, headless
`BackendHarness`, замена через `topology.apply` с `recipe_path`).

**Четыре дефекта, ни одного не видели 6185 зелёных тестов:**

- **A** — оркестратор снимал свой L3 и не пересобирал конфиг: `session_keys: []`
  при действующем `DEBUG`, тогда как ребёнок вернулся на `INFO` (у него пересборку
  делает `config.reload`);
- **B** — адрес рецепта после switch не обновлялся: `observability.persist` писал
  спутник рядом с ПОКИНУТЫМ рецептом;
- **C** — переживший switch protected-процесс оставался на секции прежнего рецепта,
  пересозданный сосед — на новой;
- **D** — `ProcessModule.update_config(key, value)` мёртв при живом `config_handler`
  (см. [[feedback-config-update-dead-with-handler]]).

**Решение:** switch раздаёт слой L2 — адрес **и** содержимое — всем, кто его пережил.
Адрес ретаргетится ДО `apply_topology` (ассемблер читает его на каждой сборке) с
откатом при неуспехе и при исключении. Содержимое едет **сырой секцией**, долька
резолвится у получателя тем же `resolve_recipe_section`, что и на boot — иначе switch
и старт трактуют один файл по-разному. `{}` = «новый рецепт молчит» и снимает слой,
`None` = «switch про слой молчит», адрес без секции переставляет только источник.

**Why:** переживший процесс — единственный, кто может доказать раздачу; пересозданный
стартует чистым тривиально. Стенд обязан содержать protected-процесс.

**How to apply:** при любой правке switch/topology брать пару рецептов, где есть и
переживший, и пересозданный, и судить их РАЗНЫМИ проверками. Резидуалы (R6-C ..
R6-H) — в плане. См. [[project-observability-config-layers]],
[[feedback-three-lenses-three-defect-classes]].

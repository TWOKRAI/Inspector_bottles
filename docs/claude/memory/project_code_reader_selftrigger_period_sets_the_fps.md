Опыт 2026-10-16 на стенде, две камеры (`192.168.1.10` WBPF-5M-OD, `192.168.1.11` SENSOTEC), зонд `mvcr_probe.py` и одноразовый скрипт записи.

**Что выяснено.**
- Гипотеза «100 Мбит/с канал» отвергнута: поток 33 Мбит/с ровной линией (порт ПК 1 Гбит/с), кадр 1,25 МБ Mono8; раньше один прогон дал 57 кадров/с (~570 Мбит/с).
- Частоту выдачи задаёт собственный триггер камеры: `TriggerMode=1`, `TriggerSource=SelfTrigger` (в `supported` это значение 9; ставится по имени `set_enum_str`), узел `TriggerSelfTriggerPeriod` (int, мс; по умолчанию 300 = 3,3 кадра/с, мин 32, макс 180000). Узел периода закрыт (`0x80020106`), пока источник не `SelfTrigger`; `TriggerSource` закрыт, пока `TriggerMode=0`. Зависимые узлы читаются и пишутся только после смены родителя.
- С периодом 32 мс: камера 2 — 25 кадров/с (201 за 8 с), камера 1 — 4,7–4,9 кадра/с при том же периоде и БЕЗ кодов в поле зрения (зонд, `trigger` растёт на 38 за 8 с). Значит, медленность камеры 1 — не декодирование и не наш конвейер (счётчик `frames` читателя совпал с зондом, `dropped=0`), а ограничение самой камеры; причина не найдена. Повтор после выключения и включения камер: камера 1 при периоде 32 мс даёт 25,1 кадра/с (и при `RunningMode=2`, и при `0`), то есть те же 25, что камера 2; в свободном режиме с `RunningMode=2` — 57 кадров/с, с `RunningMode=0` — 0 кадров. Медленные 4,7 кадра/с не воспроизвелись: это было состояние камеры до перезапуска питания, а не модель и не настройки (узлы двух камер сравнены, различаются только `RunningMode` 2/0, выдержка 799/1035 мкс и усиление 0/4,8).

**Как применять.** Нужна частота выше 3 кадр/с — менять период собственного триггера, а не искать канал. Запись в прибор — только при закрытом захвате и в порядке родитель → зависимый (режим, источник, период); откат — в обратном порядке, исходные значения сохранять до записи. Постоянная съёмка на максимальной частоте греет прибор и бьёт вспышкой подсветки ~30 раз в секунду — не оставлять без надобности. Связано: [[project_code_reader_focus_calibration_streams_frames]].

Задача 3.4 (2026-08-11). Живой зонд мерил тяжёлую стартовую запись так: выставить предел
`0` через `config.reload`, перезапустить процесс, поймать «жирную» строку; потом то же с
дефолтом. Обе строки вышли **1972 байта при count=392** — и «экономия 0» была свойством
метода, а не механизма: рестарт поднимает новый инстанс с конфига **с диска**, установленный
в памяти ноль умирает вместе со старым процессом.

Ловушка тем опаснее, что `process_restart_verified` честно подтверждает рестарт, а
`config_reload_verified` до этого честно подтвердил применение — оба сигнала «успех», а
замер сравнивает одно значение с самим собой.

**Why:** пара «до/после», где обе половины случайно одинаковы, выглядит как доказанное
отсутствие эффекта. Это ложный отрицательный результат, и он убедителен.

**How to apply:** если между окнами замера есть рестарт — runtime-настройка не переживёт
его. Либо два прогона стенда с разным конфигом НА СТАРТЕ, либо «до» берётся из архивных
логов и это называется вслух. Проверять годность метода отдельно: если у пары до/после
совпали не только байты, но и `count`, — сначала подозревай метод, а не механизм. Родня —
[[feedback-double-must-block-like-the-original]], [[feedback-plausible-is-not-verified]].

**Владелец (2026-10-01): «без таймаутов», и каждый реиндекс «с какими-то проблемами с запуском».
Любой таймаут при реиндексе — мой дефект запуска, а не свойство среды.** Ниже порядок, который
отработал; идти по нему, а не вспоминать по частям.

## Что сломалось 2026-10-01 (все три — запуск, не qex)

1. **`ollama serve` через Bash `run_in_background` без `timeout`** — харнесс убивает фон через
   30 мин. Ollama умер на батче 1543/1639 (~94%) → `Connection refused` → `Indexing failed`.
   У векторной половины нет чекпойнта: 30 минут работы потеряны целиком.
2. **Тега `qwen3-embedding:0.6b-qex` не было**, только базовый `0.6b` (список после рестарта
   Ollama/переустановки). Без тега контекст берётся из `OLLAMA_CONTEXT_LENGTH` (там стояло
   65536) → риск CPU-offload. Лаунчер только предупреждает в stderr, не блокирует.
3. **`reindex_progress.py` падает `UnicodeDecodeError`**: родитель читает вывод дочернего в
   cp1251, а `reindex.py` пишет UTF-8. Лечится окружением `PYTHONUTF8=1`, код не трогать.

## Порядок запуска

1. **Статус сначала:** `get_indexing_status` → `last_indexed` числом (см.
   [[feedback-check-qex-freshness-before-use]]).
2. **Ollama — отдельным процессом, вне харнесса:**
   `powershell -NoProfile -Command "Start-Process -FilePath ollama -ArgumentList 'serve' -WindowStyle Hidden"`
   и ждать `until curl -s -m 2 http://localhost:11434/`. Не фоном Bash. Уже запущенный — не трогать.
3. **Тег `-qex`:** `ollama list | grep 0.6b-qex`; нет →
   `ollama create qwen3-embedding:0.6b-qex -f .claude/plugins/mcp-qex/templates/qwen3-embedding-0.6b-win.Modelfile`,
   затем `ollama show ... --parameters` → `num_ctx 2048`, `num_gpu 999`.
4. **Прогрев и проверка GPU до старта:** `/api/embed` с `keep_alive:"120m"`; `/api/ps` →
   `size == size_vram` (100% GPU); три батча по 64 дают ровные ~2.7 с (скачок 40+ с = модель
   выгружается). Лог Ollama `inference compute ... library=CUDA` подтверждает CUDA.
5. **Запуск:** `PYTHONUTF8=1 PYTHONUNBUFFERED=1 python .claude/plugins/mcp-qex/reindex_progress.py --force`
   в Bash `run_in_background` с **`timeout: 7200000`**. НЕ через MCP `index_codebase` (у
   MCP-вызова клиентский таймаут). Без `--clear`: старый индекс жив до успешного конца.
6. **Один индексатор.** Два на одном Ollama выбивают друг друга по зашитому ~10 с таймауту; MCP-сервер
   сессии в это время ничего не индексирует.
7. **Монитор по строкам qex, не по счётчику скрипта.** `grep "Embedding batch"` → `N/M (X chunks
   done)`. Встроенный счётчик `embedded N` читает `%LOCALAPPDATA%\Ollama\server.log` и при Ollama,
   поднятом не приложением, **стоит на 0** при живой работе (ложный «ничего не происходит»).
   Фильтр монитора обязан ловить отказ: `Connection refused|Indexing failed|Traceback|attempt [12]/3`
   и смерть Ollama (`curl` не отвечает) — молчание не значит «идёт».
8. **Фазы:** сначала BM25 на процессоре (GPU ~0–30%, векторов нет) — норма; потом векторы (GPU 65–90%,
   ~55–63 эмбеддинга/с). Замер 2026-10-01: 52 443 чанка, 1639 батчей по 32, ~30 мин всего.

## Что считать результатом

- **Упавший `--force` оставляет индекс разобранным:** `get_indexing_status` → `file_count: 0`,
  `last_indexed: null` при ненулевом `chunk_count`. Это **не рабочий индекс** — `search_code`
  доверять нельзя, до успешного повтора работать на `Grep`. Не принимать за «обновился».
- Успех: `last_indexed` сегодняшний, `file_count > 0`, `dense/vector_meta.json` = 1024 / 0.6b,
  и `search_code` по только что написанному коду находит его.

## Чего здесь нет намеренно

4b. Не помещается в 4 ГБ VRAM (3876 МиБ) и удалена с диска; размерность 1024 зашита в лаунчер,
`reindex.py` и `reindex_progress.py`. Рецепт `keep_alive=-1` из [[feedback-qex-reindex-budget]] был
под 4b и для 0.6b не нужен (модель ~2.1 ГБ, держится в VRAM сама). Смена модели = правка трёх
файлов + размерность + `clear_index`, см. [[project-qex-model]].

Связано: [[project-qex-reindex-timeout]], [[feedback-qex-reindex-budget]], [[feedback-no-global-taskkill]].

## Слито из feedback_qex_reindex_budget (_archive/feedback_qex_reindex_budget.md)

**Причина таймаутов qex найдена 2026-08-03: эмбеддер не держится в видеопамяти.**

`qwen3-embedding:4b` занимает **3876 из 4096 МиБ** на RTX 3050 Laptop. Вместе с
композитором Windows, браузером и КОМПАСом он не помещается, поэтому выгружается;
следующий запрос платит за перезагрузку (**47 с** против 1.9 с на прогретой модели)
и пробивает таймаут, зашитый в бинарь `qex.exe`. Снаружи это выглядит как
`OpenAI API request failed: timeout (SendRequest)`.

**Повторы при этом бесполезны по построению:** один таймаут роняет всю задачу,
а векторная половина не имеет чекпойнта. Счёт того дня — 15 попыток, ~90 минут,
**ноль** записей в `dense/`. Чанкование прогресс копит, эмбеддинги — нет.

#### Рецепт (проверен: успех с ПЕРВОЙ попытки за 742 с)

1. Освободить VRAM — закрыть КОМПАС, браузеры, тяжёлые Electron-окна.
   Проверка: `nvidia-smi --query-gpu=memory.free --format=csv`. Нужно ≥3.2 ГБ
   свободных ДО загрузки модели (см. [[reference-gpu-monitoring-windows]]).
2. Закрепить модель в VRAM, чтобы не выгружалась между батчами:
   ```bash
   curl -s -X POST http://localhost:11434/api/embed \
     -d '{"model":"qwen3-embedding:4b","input":"warmup","keep_alive":-1}'
   ```
   Проверка: `/api/ps` покажет `expires_at` в далёком будущем.
3. Убедиться, что латентность ровная: три батча по 64 подряд должны давать
   ~1.9–2.4 с БЕЗ всплесков. Скачок 40+ с = модель всё ещё выгружается.
4. Запустить `python scripts/qex_retry.py`.
5. **Обязательно снять закрепление после** — иначе 3.8 ГБ из 4 заняты навсегда
   и GPU недоступен для КОМПАСа и ML-стенда прототипа:
   ```bash
   curl -s -X POST http://localhost:11434/api/embed \
     -d '{"model":"qwen3-embedding:4b","input":"x","keep_alive":0}'
   ```

#### Как судить о результате

- Завершение — по `stats.json` / `snapshot_metadata.json` / `dense/` в
  `~/.qex/projects/<slug>/` и по `last_indexed`. Всё это переписывается только
  по доведённому прогону (см. [[project-qex-reindex-timeout]]).
- `chunk_count` — **не показатель**: ходит в обе стороны (97210 → 100550 → 99079).
- Финальная проверка — прогоном: `search_code` по коду, написанному только что.
  Нашёлся — индекс живой.

#### Грабли обвязки

- Не пускать вывод прогона через `tail` без `-f`: держит поток до конца процесса,
  и молчание читается как зависание. На этом я один раз заключил «цикла повторов
  нет», хотя он шёл.
- `scripts/qex_retry.py` глушил stderr в `DEVNULL` — то есть выбрасывал лог, где
  причина названа. Починено (`d3f35d3a`): stderr идёт в `logs/qex_reindex/`.

**Правило владельца остаётся:** на переиндексацию закладывать полтора часа. Но с
закреплённой моделью она укладывается в ~12 минут, и если снова тянется часами —
это не «нормально долго», а признак, что модель опять выгружается.

#### Грабли: два индексатора дерутся за блокировку (2026-08-23)

`scripts/qex_retry.py` поднимает СВОЙ экземпляр `qex.exe`. Если в это же время
MCP-сервер qex сессии выполняет `index_codebase`, второй индексатор не может
взять writer-lock Tantivy и падает сразу:

```
Indexing failed: Failed to create index writer
```

Это НЕ таймаут и не выгрузка модели — лечится не рецептом выше, а тем, чтобы
не запускать две дороги сразу. Порядок: сначала снять MCP-вызов (`TaskStop`
агента мало — сервер держит лок сам), потом `qex_retry.py`.

Симптом, по которому отличать: падение приходит за секунды, лог попытки — 8 строк.
Живая попытка даёт тысячи строк `tantivy::…` и доходит до `committing <N>`.

#### Измерение 2026-08-23: «12 минут» верно только для МАЛОЙ дельты

Прогон на дельте в **17 дней / 834 изменённых файла** снят на 22-й минуте, не
дойдя даже до векторной половины. Условия рецепта были выполнены полностью:
VRAM 3962 МиБ свободно, модель 100% на GPU (`size_vram == size`), латентность
ровная (3 батча по 64: 3.73 / 3.37 / 3.37 с, разброс 0.36 с), блокировки нет,
попытка одна, ЦП свободен.

**Узкое место — не эмбеддер и не GPU, а BM25-половина.** Инкремент коммитит
tantivy ПО ОДНОМУ документу и на каждый тянет слияние ~250 сегментов:

```
committing 410859
committing 410860
committing 410861     ← счётчик растёт на 1
Starting merge - [Seg(...) x ~250]    ← 569 слияний за 22 минуты
```

Темп: **589 документов за 22 минуты ≈ 27 док/мин**. 834 файла × ~8 чанков —
порядка 6700 документов, то есть **≈ 4 часа только на BM25**, и лишь потом
начались бы эмбеддинги (`dense/` за все 22 минуты не изменился, GPU ровно 0%).

#### Как отличать фазы (иначе диагноз ставится неверно)

- **GPU 0% в начале — это НОРМА, а не симптом.** Сначала идут tree-sitter и
  BM25 на процессоре; карта простаивает законно. «Эмбеддер не на GPU» по нулю
  загрузки в этот момент — ложный вывод (чуть не поставил его дважды).
- Признак живой BM25-фазы — рост числа строк лога и счётчика `committing N`.
- Признак начала векторной фазы — рост `dense/` и ненулевая загрузка GPU.

#### Решение владельца 2026-08-23

Прогон снят, qex оставлен устаревшим (индекс от 2026-08-06). Весь день работа
шла на `Grep` + `serena` без потерь. **Планировать реиндекс как фоновую задачу
на часы, а не как шаг внутри сессии.** Полная пересборка (`force=true`,
заявлено 30–60 мин) может оказаться БЫСТРЕЕ инкремента на большой дельте —
пакетная запись против слияния на каждый документ, — но не проверено, а
неудача оставит вообще без индекса.

## Слито из project_qex_reindex_timeout (_archive/project_qex_reindex_timeout.md)

Инкрементальная переиндексация qex регулярно падает с `Indexing failed: OpenAI
API request failed: timeout (SendRequest)`. Причина: батч эмбеддингов к Ollama
стоит **8–10 с**, а клиентский таймаут у qex **зашит в бинарь** (~10 с) —
попадание впритык. Ручки нет ни с какой стороны: в `qex.exe` всего пять
переменных `QEX_*` (провайдер, ключ, base_url, модель, размерность), timeout и
batch_size среди них отсутствуют; `qex --help` — три флага; конфиг-файла нет
(`~/.qex/` содержит только `projects/`).

**Лечится повтором.** Прогресс между прогонами сохраняется, поэтому цикл
попыток доводит дело до конца. Скрипт: `scratchpad/qex_retry.py` (говорит с
MCP-сервером по JSON-RPC через stdio, повторяет `index_codebase` до успеха).
Полный догон 204 файлов / 6753 чанков занял 20 минут.

**Грабли диагностики — три неверные гипотезы подряд** (2026-07-27):
1. «Холодная загрузка модели в VRAM» — опровергнуто: упало и на прогретой.
2. «`localhost` резолвится в `::1`, а Ollama слушает только `127.0.0.1`» —
   опровергнуто: curl по `localhost` отвечает 200 за 0.29 с.
3. «Запрос вообще не доходит до Ollama» — я грепал лог по `api/embed`, тогда как
   qex ходит в OpenAI-совместимый **`/v1/embeddings`**, и отфильтровал его
   собственные запросы. Правильный греп — по `GIN`.

**Свежесть индекса судить по `last_indexed`, а не по `indexed: true`.** После
упавшего прогона BM25-часть обновляется (chunk_count растёт, поиск находит
сегодняшний код), а плотные векторы остаются старыми — и `last_indexed` не
двигается. То есть гибридный поиск деградирует до почти-BM25 молча.

Связано: [[project_graphify_mcp_setup]], [[reference_gpu_monitoring_windows]],
[[feedback_plausible_is_not_verified]].

**Замер 2026-08-31 — инкрементальный проход дёшев.** Дельта в 4 дня: **151 файл / 8861 чанк
за 429 с (7 мин 9 с)**, `incremental: true`. Не часы. Итог индекса — 17224 файла / 52033 чанка.
Это подтверждает гипотезу, что раньше реиндекс упирался в накопленные несмёрженные BM25-сегменты
(полный ребилд 2026-08-27 сжал `tantivy/` с 5.7 ГБ до 127 МБ), а не в qex как таковой.

Практический вывод: **держать индекс свежим дёшево**. После дня работы — поднять `ollama serve`
(модель `qwen3-embedding:0.6b` уже локальна) и один вызов `index_codebase` без `force`. Прежняя
привычка «жить с устаревшим индексом, потому что реиндекс стоит часы» больше не обоснована.

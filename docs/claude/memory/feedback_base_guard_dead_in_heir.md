Механизм, добавленный в `ChannelRoutingManager`, **не работает автоматически у трёх
братьев**. R9 (2026-07-27): откат `reconfigure` брал слепок из `_last_applied_config`,
который база выставляет из своего аргумента `config` — а `LoggerCore` резолвит конфиг
сам и передаёт в базу `config=None`. Слепок пуст → второй рубеж мёртв ровно у логгера
и ошибок, то есть у тех двух, ради которых делался. По коду базы всё выглядело исправно.

Там же второй экземпляр другого класса: `if not isinstance(normalized, dict)` после
`normalize_config` — **проверка с недостижимым отрицательным путём**, потому что
нормализатор на любом отказе возвращает копию `default`, то есть dict. Цена: мусор на
входе (`reconfigure(42)`) применялся как валидный пустой конфиг — сносил все каналы и
рапортовал успех.

**Why:** база и наследник смотрятся исправно по отдельности; дыра живёт на стыке
«что наследник передал вверх». Обе находки сделаны **слом-инъекцией**, не чтением —
предсказание «что покраснеет» разошлось с фактом, и разошлось именно на этом.

**Замер 2026-07-27, три задачи подряд (R9, Ф4.2, P5): расхождение предсказания с
фактом дало находку ТРИ раза из трёх.** Ф4.2 — слом не убил ничего, и выяснилось,
что страж `PLANE_COUNTER_KEYS`, на который ссылался комментарий в коде, **не
существовал**: сверялись отдельные счётчики поимённо, а список не проверялся ничем.
P5 — два слома пустые, значит два свойства (хук резолва module-каналов, книга окна
агрегации) держались ни на чём. Пустой слом — это не «тест уже есть», это «тест
проверяет не то».

**How to apply:** поднял что-то в базу — прогони по КАЖДОМУ наследнику, что там
подано и что фактически инициализировано (`LoggerCore`, `ErrorManager`, `StatsManager`,
`RouterManager`). Для каждой защитной ветки спроси, достижим ли её отрицательный путь;
если нет — это не защита, а комментарий. Слом-инъекция ставится на КАЖДОГО наследника
отдельно, иначе проверяется только тот, у кого механизм и так живой.

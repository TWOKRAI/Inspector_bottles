Задача 2.8 (`observability-unified-routing`) убрала ложную тревогу «потеря записей» при штатном
`sink.disable`: снятый приёмник стали вычитать из маршрута. Отметка «снято оператором» жила в
рантайм-множестве, а `config.reload` пересобирал каналы из конфига — и поднимал снятый канал
заново, **не трогая отметку**. Итог: канал жив в реестре, запись до него не доходит, все четыре
класса потерь — нули. На плоскости ошибок хуже: маршрут схлопывался в пустой, ERROR уезжал в пол
при живом `errors.log`, и `errors_to_floor` поднимал ложный сигнал «маршрут ошибок сломан».

Ни один из 5982 тестов не поймал: были пары «снял → потерь нет» и «reload → канал вернулся», но
не их **последовательность**. Нашло ревью (BLOCK), воспроизведено независимо.

**Why:** ложная тревога шумит и потому находится. Тихая потеря не находится вовсе — она и есть
класс, ради которого пишутся счётчики. Обмен первого на второе выглядит как улучшение и является
регрессом. Тот же корень, что у [[feedback_swallowed_failure_class]].

**How to apply:** любое рантайм-состояние, отменяющее решение конфига, обязано иметь **владельца
жизненного цикла** — точку, где оно снимается при пересборке; ставить её в базу, а не в
наследника (иначе уборка достанется одной плоскости из четырёх). Тест писать на ПАРУ действий
(`disable` → `reload` → запись доходит?), а не на каждое отдельно. И сверять с планом: заявление
«до задачи X это состояние очищается reload'ом» было написано авансом и запуском не проверялось —
см. [[feedback_plausible_is_not_verified]], [[feedback_prove_test_red_without_fix]].

`get_std_logger("gui")` из `logger_module` — готовый путь «импортировал и
пользуешься», без наследования `BaseManager`. Работает в любом файле.

**Замер (отклонённая запись, 2026-07-27):** фасад **1028 нс**, миксин
`_log_debug` **1673 нс**, напрямую `LoggerManager.debug` **746 нс**. То есть
фасад не «запасной путь», а более дешёвый.

**При этом он практически не используется:** в `multiprocess_prototype` +
`Services` + `Plugins` голый `logging.getLogger` — в **76** файлах, `get_std_logger`
— в **2**. У корневого stdlib-логгера в наших процессах нет ни одного приёмника,
поэтому эти 76 файлов пишут **в пустоту**, а не «в другой файл». Перевод —
задача Ф6 плана observability-unified-routing.

**Чего фасаду не хватает** (это и есть задача 2.2, а не переписывание с нуля):
1. имя плоское — `"gui"` это ключ per-module файла, не иерархия; правило для
   `vision` не действует на `vision.capture`;
2. `get_logger()` резолвится на КАЖДОЙ записи (ленивость нужна, потому что модули
   импортируются до `init_logging()`) — нужен один резолв при создании + инвалидация;
3. нет `exc_info`/`stacklevel` — traceback вклеивается в текст руками.

**Отвергнуто: слать записи оркестратору.** Это IPC на каждую строчку — тот самый
механизм, что душил GUI системной очередью ([[project_gui_system_queue_storm]]).
Модель: в каждом процессе свой локальный писатель, фасад находит его сам; наружу
уходит только живая подписка для GUI.

Правило владельца, сказанное не первый раз: **на переиндексацию qex закладывать
минимум полтора часа.**

**Why.** 2026-08-03 я остановил инкрементальный прогон на 35-й минуте и описал его
как структурный сбой («до векторной половины не доходит ни разу»). Основания
выглядели солидно: `stats.json` не переписан, `dense/` не тронут, попытки падали
одинаково с `OpenAI API request failed: timeout (SendRequest)` за ~270 с каждая.
Но всё это — нормальная картина недоработавшего прогона, а не диагноз.

Замер эмбеддера тут же показал, чем на самом деле были таймауты:

| батч | латентность |
|---|---|
| 1 | 47.3 с |
| 8 | 21.4 с |
| 32 | **2.8 с** |

Порядок обратный: меньший батч медленнее. Значит время съедали прогрев модели и
конкуренция с идущим циклом, а не счёт. Разогретый эндпоинт отдаёт 32 вектора за
2.8 с — то есть лечится ожиданием, ровно тем, которого я не дал.

**How to apply.**
- Запустил переиндексацию — планируй 90 минут, а не «посмотрим через полчаса».
- До истечения бюджета не выдавать промежуточное состояние за вердикт.
- Судить о завершении по `stats.json` / `snapshot_metadata.json` в
  `~/.qex/projects/<slug>/` — они переписываются только по доведённому прогону
  (см. [[project-qex-reindex-timeout]]). `chunk_count` — не показатель, ходит в
  обе стороны.
- В `scripts/qex_retry.py` зашито 12 попыток ≈ 55 минут. Исчерпание лимита ≠
  «не сошлось»: перезапустить, прогресс между заходами сохраняется.
- Не пускать вывод такого прогона через `tail` без `-f` — он держит поток до
  конца процесса, и молчание читается как зависание.

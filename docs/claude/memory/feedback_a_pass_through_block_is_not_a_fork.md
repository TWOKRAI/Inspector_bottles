Когда правило формулируется как «две вещи на одном пути исполнения», модель развилок
надо строить от **семантики потока**, а не от вложенности AST. Проходные конструкции
(`try`-тело, `with`, тело цикла, `else`/`finally`) поток НЕ разводят. Разводят: `if`/`else`,
`match`/`case`, `except`-обработчики, ранний `return`/`raise`/`continue`/`break`.

**Ошибка стоит тихого зелёного, а не падения.** Замеры Task 1.3c (2026-09-01), три
редакции одного обходчика, каждая ошибка найдена только инъекцией:

1. **Тело `try:` посчитано веткой** → всё дерево дало ровный **0** нарушений. Ноль
   выглядел здоровьем; на деле сайт `report_error(...)` + `try: _log_error(...)`
   проходил мимо правила. С исправленной моделью — 1 (тело механизма).
2. **Тело `if` без `else` изолировано от родителя** → пара `report_error()` в теле
   функции + `_log_error()` внутри `if x:` зелёная, хотя при истинном `x` исполняются
   обе. Нашла заплатка J9, специально задуманная как «кандидат в дыру».
3. **`break`/`continue` возвращали пустой список путей** → цикл гасил ВЕСЬ остаток
   функции. Живьём: пара ПОСЛЕ цикла → 0 нарушений, та же пара ПЕРЕД ним → 10.
   Поверхность была 20 циклов в 13 функциях.

**Обратная ошибка тоже есть и она дороже:** нераспознанная конструкция (`match`,
тернарник, `except*` = `ast.TryStar`, который `isinstance(x, ast.Try)` НЕ ловит)
сливает взаимоисключающие рукава в один путь → **ложный красный** на законном коде.
При правиле без whitelist у автора такого кода выхода нет вообще: гейт красный, снять
нечем. Проверять обе стороны обязательно.

**Потолок сложности — не «страховка», а подмена правила.** Схлопывание избытка путей в
ОДИН путь молча возвращает правило к единице «функция». Правильно — сливать по классу
эквивалентности того, что правило спрашивает (здесь: `(видел log?, видел track?)` = 4
корзины): точно, без приближения, и потолок становится не нужен.

Владелец (2026-10-17, после Opus-прохода по камерам штрихкодов): «Sonnet пишет код и реализует», Opus проверяет, как реализовано; «главное без костылей и багов, делать как полагается, с лучшей архитектурой»; «может Sonnet'у давать больше работы для экономии токенов»; «пусть использует qex и графы, если нужно».

**Why:** замеры сессии (Opus-оценка в `docs/reviews/2026-10-17_codereader-multicamera-opus-review.md`, «Проход 2»): Sonnet надёжен при точном DESIGN (код, тесты с литералами, hazard-тесты), слаб вне файлов брифа (живые логи, связь выхода приложения с возвратом режима, сомнение в посылке плана). Коммит Sonnet без ревью дал реальный дефект (`labels` с опечаткой роняет `produce()`); коммиты с ревью Sonnet — без новых дефектов. Около четверти токенов ушло на старт новых агентов вместо дозыва.

**How to apply:** реализацию, тесты, hazard-тесты, ревью обычных коммитов — Sonnet (Haiku — механика, опись логов); Opus — стадия 0 и ревью кода только для задач с потоками, IPC, жизненным циклом процесса/прибора, и вердикты по живым дефектам; повторные раунды — `SendMessage` тому же агенту. Правила сессии (слепой тестер, инъекции, ревью после каждой задачи) не отменяются.

**2026-10-18 — стало правилом** (владелец: «давай как лучше»): `.claude/CLAUDE.md` → «Task launch convention», пункт «Model by class». Владелец предлагал ревью только на сложных задачах и фазах; оставлено ревью каждого коммита с кодом (Sonnet для ограниченных правок или одно на волну), потому что единственный замеренный дефект пришёл из коммита без ревью. Haiku делает опись логов перед вердиктом по живому дефекту.

**Расход одного агента (владелец 2026-10-18):** у Opus-ревьюера обычно больше 200k токенов — контекст проекта большой, это норма. 200–400k принимать молча; ~400–500k — мягкий потолок: предупредить владельца и сверить с размером задачи, но не останавливать. Порог «~100k» в `.claude/CLAUDE.md` касается контекста сессии лида, а не расхода субагента. Около 400–500k у любого агента (любая роль и модель) решает сам лид, координатору не сигналит: свежий ревьюер с файлом отчёта раунда 1 и диффом вместо дозыва, или уже объём проверки (`.claude/CLAUDE.md` → «Persistent agents»). Строки на каждый запуск Opus и сигнал `budget:` координатору владелец отменил как лишнюю нагрузку (каждое сообщение — ход координатора). Полный расход — колонки «модель» и «токены» в таблице agentId итогового отчёта. Связано: [[feedback_always_latest_models]], [[feedback_explicit_model_per_agent_role]].

**2026-10-25 — пилот (владелец: «давай попробуем»):** стадия 0 всех задач, включая Senior+, — Sonnet; Opus остаётся на ревью ветки перед слиянием и на вердиктах по живым дефектам. Причина: 5-часовой лимит — за 3 ч ушло 59 %, панель расхода назвала reviewer-субагентов главным потребителем. Довод «против»: Opus на стадии 0 однажды сберёг бы ~189k переделки. Как судить пилот: дефект дизайна, который нашло Opus-ревью ветки, но должна была поймать стадия 0, — запись в очередь координатора; накопились такие записи — вернуть Opus на стадию 0 Senior+.

Записи пилота: 2026-10-25, C-25/C-28 (Middle — стадия 0 на Sonnet и до пилота): Opus-ревью ветки нашло 2 дефекта дизайна мимо стадии 0 — затенение второй секции metadata (поймало ещё ревью задачи, C28.2) и каскад ложных «join-источников: 0» при точке в имени (C28.3). Не довод против пилота Senior+ напрямую (задача Middle), но счёт Sonnet-стадии 0: 2.

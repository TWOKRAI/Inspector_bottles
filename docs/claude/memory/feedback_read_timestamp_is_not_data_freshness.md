Поле `snapshot_ts`, проставляемое в момент ответа на опрос, отвечает на вопрос «когда
я это прочитал», а не «когда это было измерено». Разница невидима, пока источник жив,
и становится опасной ровно тогда, когда он умирает: **замерший датчик отдаёт последнее
значение сколь угодно долго, а штамп продолжает идти**.

**Живьём (Task 3.2 telemetry-stage6, 2026-08-14).** Реальный `CycleMetricsRecorder`:
20 циклов по 47 мс, затем воркер остановлен полностью.

```
опрос #1: snapshot_ts=1786706886.811  state={'fps': 21.0, 'latency_ms': 47.7}
опрос #2: snapshot_ts=1786706890.812  state={'fps': 21.0, 'latency_ms': 47.7}   (+4.00 с)
числа идентичны после 4 с полного простоя; status воркера при этом — 'running'
```

Вырожденный случай той же природы: процесс без heartbeat'а вернул `levels=None` **и**
свежий штамп возрастом 0.000 с — метка есть, показаний нет.

**Why:** поле заводилось под формулировку «потребитель отличает „свежо“ от „процесс
завис“», и эта формулировка успела разъехаться по трём местам — ADR, докстринг команды
и описание MCP-инструмента. Ни один тест этого не ловит: поле присутствует, тип верный,
монотонность соблюдена. А в случае, ради которого поле заводилось — процесс завис
целиком, — ответа не будет вовсе, придёт таймаут. То есть свою заявленную работу поле
не делает **никогда**: пока источник жив, оно избыточно; когда мёртв — недоступно.

**How to apply.** Свежесть данных доказывает признак, который двигается **вместе с
измерением**, а не вместе с чтением: счётчик циклов, момент последнего `record()`,
номер ревизии. Если такого признака нет — писать в докстринге «возраст ОТВЕТА, а не
возраст чисел» и не обещать обнаружение зависания. Проверять запуском одной формы:
**остановить источник и опросить дважды** — если числа совпали, а штамп вырос, поле
меряет не то.

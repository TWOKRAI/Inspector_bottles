`time.get_clock_info('monotonic')` на рабочей машине проекта (Win10, CPython 3.12):
`implementation='GetTickCount64()'`, `resolution=0.015625`. Замеренные промежутки
`sleep(0.05)` — 0.047 / 0.062, ни одного 0.050. `time.perf_counter` — QueryPerformanceCounter,
разрешение 1e-07.

Следствие, стоившее половины телеметрии (Ф8.2, 2026-08-07): `ThrottleMiddleware` решал
допуск как `(now - last) < interval`. При `interval = 0.05` промежуток, реально равный
50 мс, читался как 46.875 мс → «слишком рано» → запись отбрасывалась. Публикатор,
работающий ровно на пределе правила, терял ~половину: 33 из 60 при `T == P` против 60 из 60
при `T == 0.9P`. Починено переходом на фиксированную сетку `floor(now / interval)` —
абсолютное время квантуется безвредно, разности нет вовсе (ADR-SS-021).

**Why:** сравнение разностей наследует ПОЛНОЕ разрешение часов как ошибку, и на Windows это
15.6 мс — величина, сопоставимая с интервалами троттлинга и heartbeat'а. На Linux/macOS та
же строка кода работает, поэтому дефект платформозависимый и в CI может не проявиться.

**How to apply:** для любого механизма с интервалом ниже ~100 мс не сравнивать разность
двух `monotonic` — отображать абсолютное время на сетку. Если разность неизбежна, брать
`time.perf_counter`. Часы держать инжектируемой зависимостью (`clock=` в конструкторе), а
не читать глобально, иначе тест не сможет задать их без патча всего процесса.

## Дополнение A12 (аудит 2026-10-04, из telemetry_self_publish)

`cycle_metrics.effective_hz = 1/cycle_duration` на `time.monotonic()` давал FPS=0 у consumer-воркеров; фикс `b6ce2bb8` — интервал между `record()` на `perf_counter`.

## Дополнение T3.8 (ревью кода 2026-10-18, robot_host `robot_state_hz`)

Ловушка вернулась через бриф: DESIGN задал `now - last >= 1/hz - 1e-9` на `time.monotonic`. При `robot_state_hz = 1000/publish_ms` (20 Гц при 50 мс) настоящий плагин дал 10.0 снимков/с при энкодере 19.7/с. Тест на фейковых часах с точным шагом 0.05 и порог «≥ 5 записей за 1 с» этого не видят.
Решение лида: допуск в полцикла `now - last >= 1/hz - publish_ms/2000` — лечит и квант 1/64 с, и дрожание `sleep`; период округляется до ближайшего кратного `publish_ms`. Сторож — фейковые часы, квантованные шагом 1/64 с, с дрожанием ±1.2 мс: старая формула 57/100 и 40/50, новая 100/50/20 (`Plugins/sim/robot_host/tests/test_robot_state_rate.py`). Поле времени для межпроцессного `lag` остаётся на `monotonic`.
**Триггер:** бриф или DESIGN с периодом ниже ~100 мс — сверить с этим уроком до стадии 0.

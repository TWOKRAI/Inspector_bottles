**Замер вердикта CTO 2026-09-03** (Task 2.12, `observability-closure`), настоящий
`LoggerManager` с файловым каналом, по одной записи ДО подъёма менеджера и после,
обеими дорогами:

| Дорога | В файле журнала | Где на самом деле |
|---|---|---|
| `_fallback.emergency_log` | **0 строк** | stderr через `logging.lastResort` |
| `_fallback.FallbackLogger(name).warning()` | **2 строки** | ранняя слита из буфера `std_facade._EARLY` первой строкой файла, поздняя записана прямо |

Причина: `emergency_log` пишет в stdlib НАПРЯМУЮ («никогда через менеджер» — его
объявленный контракт), а у stdlib-root в процессах фреймворка нет ни одного
хендлера. Дерево знало это с задачи 2.2: `std_facade.py` — «уходят в lastResort и
на практике теряются».

**Довод «аварийный выход работает до подъёма логгера» верен как посылка и ложен
как вывод:** вид работает там же и ещё доезжает до файла.

`emergency_log` остаётся законным ровно для того, для чего объявлен: сообщение
того, «кто сломался, о собственной поломке» (маршрут наблюдаемости не может
рассказать о своём отказе собой же). Валидатор конфига, хук, реестр — не он.
Счёт на 2026-09-03: 21 боевой вызов в 10 файлах, из них **6 в ошибочной позиции**
и 3 пограничных (см. Task 4.11).

**Как применять.** Когда тест проверяет ГОЛОС оператору — `caplog` для этого
вопроса ФЕЙКОВЫЙ харнесс: он слушает stdlib-root, то есть ровно тот адрес, куда
запись не должна была идти. Нужен один тест сквозь настоящий `LoggerManager`,
читающий ИЗ ФАЙЛА. Доказано инъекцией: при неверном адресе 24 теста задачи
остались зелёными, красный дал ровно один — золотого пути.

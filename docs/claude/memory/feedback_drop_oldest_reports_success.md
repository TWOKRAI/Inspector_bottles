У bounded-кольца ДВЕ формы вытеснения, и они отвечают по-разному:

- `drop_newest` — отказывает статусом (`status="dropped"`), это видно;
- `drop_oldest` (дефолт `ObservabilityHub`) — отвечает **`success`** и лишь растит
  счётчик: свежую запись он действительно принял, выбросив ЧУЖУЮ старую.

**Why:** Task 2.1 `telemetry-stage6`. Канал `hub_stats` отдавал `success` на каждую
запись, потому что смотрел на статус. Замер ревьюера: 1100 окон без дренажа при ёмкости
1024 → `hub.dropped['stats'] = 76`, а канал 1100 раз ответил успехом. Счётчик потерь виден
снаружи через `introspect.observability`, но приёмочная арифметика «эмитировано =
доставлено + подавлено» считается по книгам менеджера и **сходилась поверх потери** —
класс «тревога обменяна на тихую потерю».

Вторая половина: общий толкователь `channel_accepted` считал непринятым только
`status="error"`, поэтому даже честный `"dropped"` уезжал в счётчик «записано». Расширен
до `("error", "dropped")` — различать «отброшено» и «записано» обязан общий толкователь,
а не каждый писатель у себя.

**How to apply:**
- Писать в кольцо и верить статусу — нельзя. Сравнивать **прирост** счётчика потерь
  до/после записи (если писатель один; появится второй — считать иначе, и сказать это в
  коде).
- Формулируя приёмочную арифметику, спрашивать: «а если приёмник вытеснил — какое
  слагаемое это покажет?». Если никакое — арифметика сойдётся при потере.

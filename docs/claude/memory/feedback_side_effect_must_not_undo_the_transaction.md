Если на **success-пути** транзакционной операции стоит обслуживающий побочный эффект
(раздать конфиг, доиграть подписки, записать телеметрию), он обязан быть завёрнут в
собственный `try`. Иначе исключение из обслуживания попадает в общий `except` и
откатывает то, что уже успешно применено.

**Как поймали (5.11, 2026-07-29):** чтение адреса рецепта переехало на success-путь
`apply_topology`. Тест с фейковым `get_config` старой сигнатуры уронил туда `TypeError`
— и УСПЕШНО применённая топология откатилась целиком. Симптом выглядел как «debounce
почему-то отклоняет первый apply», то есть указывал совсем не туда.

**Why:** обслуживание и транзакция — разные по цене отказы. Не доехала раздача слоя —
неприятно и должно быть громко; откатилась живая топология — это остановка конвейера.
Позволять первому вызывать второе значит поставить наблюдаемость выше того, что она
наблюдает.

**How to apply:** на success-пути транзакции каждый обслуживающий вызов — в своём
`try/except` с громким логом и деградацией (пустое значение, `reached=0`), никогда с
пробросом. Проверяется парой: враждебный зависимый объект (бросающий `get_config`,
мёртвый `communication`) → операция всё равно `success=True`.
Родня: [[feedback-swallowed-failure-class]] — глушить отказ насовсем тоже нельзя,
поэтому «тихо деградировать» здесь означает «деградировать И сказать».

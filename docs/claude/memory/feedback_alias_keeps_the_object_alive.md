Ф4.6 (2026-08-05): сносил key-based диспетчер из общей базы `ChannelRoutingManager`.
Grep по методам (`route`, `register_route`, `register_broadcast`) дал ноль продовых
вызывающих у всех четырёх наследников — вывод «слот мёртв везде» выглядел доказанным.
После сноса **204 красных теста**: `RouterManager` делал
`self.channel_dispatcher = self._dispatcher`, то есть пользовался ОБЪЕКТОМ базы через
алиас, а свои методы называл иначе.

**Why:** grep по имени метода видит вызовы, но не видит **присваиваний объекта**.
Наследник может не звать ни одного метода базы и при этом полностью зависеть от
созданного ею поля. Это тот же класс, что [[feedback_plausible_is_not_verified]]:
уверенная модель, собранная из верных частных наблюдений.

**How to apply:** перед сносом поля базы грепать **имя атрибута**, а не только API
поверх него (`_dispatcher`, а не `route`) — и отдельно искать присваивания
`X = self._поле`. Дешевле всего это ловит прогон: снести и посмотреть, что покраснеет,
ДО того как написан текст решения. Правильный исход в таком случае — не отмена сноса,
а **передача владения** тому единственному, кто пользуется (база не должна владеть
тем, что нужно одному из четырёх). Родня: [[feedback_defect_fixed_on_one_path_only]].

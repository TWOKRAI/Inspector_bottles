description: Тест, сам поднимающий исключение, сторожит ветку обработки — не механизм, который её порождает
metadata:
  type: feedback
---

Тест, который **сам** поднимает исключение (`monkeypatch` → `raise TimeoutExpired`),
доказывает только то, что `except` его ловит. Механизм, БЕЗ которого это исключение
никогда не возникнет, остаётся без стража.

Найдено Fable при закрытии хвостов Ф3 (2026-08-05): `code_version()` зовёт git с
`timeout=5`, докстринг обещал «зависший git — идентичность неизвестна, а не сбой».
Инъекция ревьюера — **удалить `timeout=5`** — оставила **26 тестов зелёными**:
`test_hanging_git_does_not_hang_the_process` сам поднимал `TimeoutExpired`, то есть
пинил ветку обработки. Без срока зависший git подвесил бы инициализацию процесса,
и ни один тест бы не заметил.

**Why:** это ровно тот класс, что и [[feedback_silent_detector_proves_nothing]] и
[[feedback_prove_test_red_without_fix]], но с другой стороны: детектор не молчит —
он сторожит не то. Зелёный набор выглядит полным.

**How to apply:** когда тест подделывает условие (`raise X`), спроси: *что в
продовом коде делает X возможным?* Этот параметр (`timeout`, `maxsize`, флаг
режима) утверждай **на границе ОС/библиотеки** — в спае, который и так собирает
`kwargs`. Одна строка: `assert seen["timeout"]`. Проверка — инъекцией: сними
параметр в проде, набор обязан покраснеть. Ср. [[feedback_test_survived_its_own_break]].

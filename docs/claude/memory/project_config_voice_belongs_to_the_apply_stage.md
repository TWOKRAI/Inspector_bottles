**Записано 2026-09-03 по вердикту CTO (Fable) над задачей 2.12 плана
`observability-closure`. Дом — Task 4.11 фазы Ф4.**

Команда `config.reload` устроена в ТРИ стадии — `проверить` → `применить` →
`сверить` (сознательное решение B2 / Task 5.7), и секция разбирается **шесть
раз** явно, каждой стадией по-своему. Прямой `ObservabilityConfig.model_validate`
даёт 1, операторская дверь — 6, три reload подряд — 18. Это НЕ «Pydantic
пересобирает вложенные модели» (я так написал, и это было опровергнуто стеком
вызовов) и НЕ дефект пути reload.

**Дефект — ввод-вывод внутри функции, которую зовут как парсер.**
`ObservabilityStatsConfig._complain_about_repurposed_enabled` — `model_validator`,
и он писал оператору.

Задача 2.12 задросселировала симптом окном по ключу. Окно работает, но
**маскирует, а не убирает**: число голосов стало зависеть от часов, а «подавлено:
N» считает РАЗБОРЫ, а не действия — три `config.reload` за одно окно дадут
«подавлено: 17».

**Правильный дом голоса — стадия «применяю»:** `compose_managers_payload`
(единственная со смыслом применения; обе дороги, boot через
`process_managers.py:130` и reload через `observability_reload.py:219`, уже зовут
её). Утверждение «единственная apply-дорога» — гипотеза CTO по докстрингу и
одному стеку, для задачи её надо пересчитать грепом. Окно остаётся ВТОРЫМ
рубежом: на boot родитель-ассемблер зовёт раскладку по разу на процесс.

Задача 3.1 (`plans/observability-roadmap.md`): `PRAGMA incremental_vacuum` возвращает
ОС свободные страницы файла SQLite. Замер всех форм вызова на одинаковом мусоре
(2116 свободных страниц, 9 138 176 байт):

| форма | результат |
|---|---|
| `adapter.execute("PRAGMA incremental_vacuum")` | 2116 → **2115**, одна страница |
| `adapter.execute("PRAGMA incremental_vacuum(1000000)")` | 2116 → **2115**, ТА ЖЕ одна |
| `adapter.query(...)` | `ResourceClosedError` |
| `conn.exec_driver_sql(...).fetchall()` | `ResourceClosedError` |
| сырой курсор DBAPI + `fetchall()` | 2116 → **0**, файл 8.71 → 0.44 МиБ |

**Why:** штатная дорога не отказывает и не молчит совсем — она делает **1/2116 работы**
и отвечает успехом. Механизм при этом называется, ретеншен «работает», файл уменьшается
на 4 КБ за такт, и разница обнаруживается только через месяцы по размеру файла.
Аргумент «сколько шагов» вычерпывание НЕ заменяет: с `(1000000)` уходит та же одна
страница, потому что упирается не в лимит, а в то, что курсор никто не прогнал.
SQLAlchemy для такой прагмы считает, что строк нет, и закрывает результат — то есть
«правильный» публичный API здесь физически не может доработать до конца.

**How to apply:**
- у операции, которая по документации исполняется **шагами** (incremental vacuum,
  курсорные обходы, порционные миграции), проверять не «вернулось без ошибки», а
  **измеримый итог**: свободных страниц 0, байт столько-то, строк столько-то;
- страж писать на итог, а не на размер: «файл стал меньше» проходит и при одной
  странице из двух тысяч, «свободных страниц не осталось» — нет
  ([[feedback_measure_delta_not_file_size]]);
- форму вызова, оказавшуюся единственной работающей, **называть в докстринге вместе с
  таблицей замера** — иначе следующий «упростит» её обратно на штатную
  ([[feedback_named_mechanism_is_not_a_commitment]]);
- родня по SQLite: [[feedback_sqlite_pragma_fails_silently]] — там PRAGMA молчит об
  ОТКАЗЕ, здесь молчит о **частичном выполнении**. Второе тише.

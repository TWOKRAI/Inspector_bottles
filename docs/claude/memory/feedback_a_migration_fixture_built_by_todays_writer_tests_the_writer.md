Тест «старый файл открывается и мигрирует» обязан получить старый файл **вписанным**, а не
воспроизведённым сегодняшним кодом. Иначе новый писатель проставляет всё сам, мигрировать нечего,
и тест зелен, ничего не проверяя.

**Замер (2026-09-05, Task 3.1 фазы Ф3 `observability-closure`).** Приёмочный тест миграции строил
«дореформенный» файл вызовом `ObservabilityStore.append_records(...)` — то есть **сегодняшним**
стором, — а потом требовал, чтобы засыпка вычислила колонку `metric`. Заплата «засыпка не
выполняется ВООБЩЕ» убила **ровно один** тест, и это был hazard-тест автора; приёмочный остался
зелёным. Причина: нормализатор проставляет `metric` **при вставке**, поэтому строка приезжала уже
с именем и без всякой миграции.

**Ловилось это дважды, и первый раз я починил только половину.** Сначала обнаружилось, что та же
фикстура не может изобразить старое значение `severity='snapshot'` — сегодняшний писатель пишет
`'number'`, и тест краснел на собственной невозможности. Я заменил сырым SQL **строку-агрегат** и
успокоился. Строку наблюдения — ту, чьё имя тест и проверял, — не тронул, и вакуум остался.
Нашла его матрица инъекций, а не чтение.

**Why:** фикстура, собранная боевым классом, выглядит надёжнее «сырого SQL на глаз» — и в
большинстве тестов так и есть. У теста МИГРАЦИИ всё наоборот: предмет проверки — разница между
вчерашним и сегодняшним форматом, а боевой класс умеет производить только сегодняшний. Чем он
точнее, тем меньше проверяет.

**How to apply:**
1. Легаси-строки в тестах миграции вписывать **сырым `INSERT`**, с новыми колонками в `NULL`, и
   называть в комментарии, ЧТО именно в них дореформенного.
2. Проверять тест миграции заплатой «миграция не выполняется вовсе». Ноль красных = тест смотрит
   на писателя.
3. Починив вакуум в одной строке фикстуры, пройти по ВСЕМ её строкам: вакуум обычно не один.
4. Соседний признак того же класса: если легаси-фикстуру можно построить боевым классом без
   единого сырого SQL — вероятно, «легаси» в ней нет.

**Замер 2026-08-26, Ф5 `observation-port`, S5.** Заявление «экземпляр
потокобезопасен (RLock на всё мутируемое состояние)» не сторожилось ничем:
инъекция «`with self._lock:` → `if True:` во ВСЕХ семи позициях» оставляла
набор из 12 тестов полностью зелёным при живом позитивном контроле.

Гонкой это не проверяется: окно между чтением и записью флага — два соседних
байткода, CPython почти никогда не переключает поток внутри него. Красный
выходил ТОЛЬКО при искусственно расширенном окне (`sleep` в критической
секции), то есть при поломке, которой в коде нет.

Рабочий приём — **прокси над настоящим локом, считающий входы**
(`_CountingLock.__enter__` инкрементирует и делегирует внутрь). Это наблюдаемый
факт «мутация прошла под локом», а не шпион на тексте `with self._lock` —
разница та же, что между свойством и его написанием.

## Дыра, которая была в самом стороже

Первая редакция проверяла «вошли в лок ХОТЯ БЫ РАЗ за вызов». Инъекция
опрокинула её сразу: снятие лока только у `record_timing` не покрасило ничего
(567 passed). Причина — метод сперва зовёт `_announce_no_reader_once`, а тот
берёт лок ВСЕГДА, потому что проверка флага сама сидит внутри `with`. То есть
за сломанный метод лок брал СОСЕД, и «хотя бы раз» оставалось истинным.

**Лечится литералами по дорогам:** у пишущих методов ДВА входа (голос +
собственная секция), у читающих и `reset` — ОДИН; расхождение в любую сторону
красное. Перебор ловить тоже обязательно: лишняя критическая секция на горячем
пути в той же фазе уже уронила бюджет цены.

Перепроверка после правки: снятие лока у ЛЮБОГО одного метода даёт красный
(проверено пятью точечными заплатами, каждая в своём worktree).

**Обобщение.** «Механизм сработал» — слишком слабый предикат везде, где рядом
есть второй вызывающий того же механизма. Спрашивать надо «сколько раз и на
какой дороге», числом. Тот же класс, что [[feedback-zero-observations-looks-like-a-result]],
только с другой стороны: там ноль читался как результат, здесь ненулевое
читается как доказательство.

## Слито из feedback_a_list_walking_guard_cannot_see_a_removed_item (_archive/feedback_a_list_walking_guard_cannot_see_a_removed_item.md)

Инъекция I16, Task 1.1 `observability-closure`, 2026-08-29: ключ `"hook_delivery_failures"` удалён из `backend_ctl/protocol.py::OBSERVABILITY_LOSS_KEYS`; `test_loss_keys_match_the_real_publisher` остался ЗЕЛЁНЫМ: он обходит список и проверяет, что каждый присутствующий ключ публикуется, а исчезнувший не посещается. Свойство держал один тест тестера (A9b, ассерт по литералу). Предсказано {A9b, G2}, получено {A9b}.
Правило: к каждому свойству «член реестра» писать литерал `assert "key" in REGISTRY` рядом с обходчиком; в матрице инъекций для каждого затронутого реестра держать заплату «запись удалена» и предсказывать, кто её поймает; ответ «обходчик» неверен. Обходчик доказывает согласованность того, что есть, не полноту.

## Слито из feedback_coverage_per_check_is_not_coverage_per_claim (_archive/feedback_coverage_per_check_is_not_coverage_per_claim.md)

Task 2.11 `observability-closure`, 2026-09-03, находка матрицы K6. У сверщика `scripts/docs_verify` тест `test_every_check_is_covered_by_an_injection` требует инъекцию на каждую проверку. Проверка `F2-3` несла три утверждения (L0-дефолт такта, имена двух readback-полей, дефолт поддерева), инъекции были только у первого. Заплата K12 (снять половину про поддерево) давала 0 красных; после закрытия дыры 1 красный поимённо.
Правило: добавляя утверждение в проверку, заводить инъекцию НА НЕГО. Утверждение, отвечающее остановкой сверки (`Unverifiable`), общей таблице не годится: нужен отдельный тест. Проверка на месте: посчитать утверждения в докстринге проверки и строки таблицы инъекций; расхождение = дыра. Связано: [[feedback_injection_must_cover_all_check_sites]].

## Слито из feedback_guard_threshold_hides_partial_blindness (_archive/feedback_guard_threshold_hides_partial_blindness.md)

D2.3, 2026-08-10: страж дедлайнов `test_thread_deadlines.py` нёс самопроверку «видит ≥ 40 файлов». Инъекция и-3 сломала путь одного из четырёх каталогов, и страж остался зелёным: три остальных плюс глобы дали больше сорока. После переписывания на поимённую сверку та же инъекция даёт красный.
Правило: в стороже со списком охраняемых мест (каталоги, глобы, имена команд, ключи конфига) писать цикл по записям и собирать `blind = [...]`, а не сравнивать общее число с порогом. Порог допустим только там, где потеря ЛЮБОЙ записи уводит сумму ниже него, то есть почти нигде.

## Слито из feedback_parametrization_built_from_the_subject_collapses_with_it (_archive/feedback_parametrization_built_from_the_subject_collapses_with_it.md)

Класс судился параметризацией из реестра контрактов («каждая команда × каждое её объявленное поле»). Инъекция «снять три контракта» не покрасила ни одного случая: она УДАЛИЛА тридцать с лишним случаев из сбора, 59 → 47. Страж «таблица не пуста» стоял на порогах (≥25 случаев, ≥8 команд), оба пройдены. Сломай источник, и тесты не падают, а пропадают.
Правило: к параметризации, чей вход вычислен из объекта проверки, добавлять страж ПОИМЁННОГО покрытия: каждый элемент ожидаемого множества даёт хотя бы один случай; судить по именам, не по числу. Страж проверять инъекцией, удаляющей элемент источника: он обязан покраснеть.

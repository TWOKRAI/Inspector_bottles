## Метод

Скрипт `stand_a.py` (сырой путь ниже) создаёт настоящий `WorkerManager` (`initialize()`, логи заглушены, как в `test_worker_start_honest.py`), один воркер `w`, потоки считаются через `threading.enumerate()` по имени `f"{manager_name}_{worker}"` (`c91st_w`). Любой вызов менеджера идёт в daemon-потоке с дедлайном join 15 с (зависание = `HANG`; 5 подряд — прерывание). `sys.setswitchinterval(1e-5)` (чтобы чаще ловить гонки). Seed 7.

Режимы:

1. `serial` — `restart_on_failure=False`, цель короткая работа и затем ожидание `stop_event`; цикл: `start_worker` → пауза 0,5–1,5 мс → `stop_worker(timeout=2)`; проверки: старт вернул True, живых после start ровно 1, stop вернул True, живых после stop 0.
2. `overlap` — `restart_on_failure=True, max_restarts=10**9`; цель в 50 % случаев бросает через 0–2 мс. В каждом цикле параллельный поток 8 раз вперемешку зовёт `start_worker` (55 %) / `restart_worker(timeout=0.3)`, пока клиент трижды делает `start_worker` → пауза → `stop_worker(0.5)`. Затем схождение (ждём до 2 с, пока живых ≤ 1), окно 0,13 с (окно `sleep(0.1)` авто-рестарта), проверка «≤ 1», финальный `stop_worker(2)` (ожидаем True), окно 0,13 с, проверка «живых 0». Фоновый sampler каждые 0,5 мс считает мгновенные случаи «живых > 1».
3. `raise_stop` (добавлен мной под формулировку дефекта «запрос остановки теряется авто-рестартом») — `restart_on_failure=True`, цель бросает через 1–3 мс; клиент: `start_worker` → пауза 0–4 мс → `stop_worker(2)`; после stop == True ждём окно 0,13 с и считаем живых (ожидаем 0).

Команды (внутри `run_all.sh`; для main — `PYTHONPATH=<scratchpad>/c91stand/main_tree`, база распакована `git archive 60e1deb42 multiprocess_framework | tar -x`):

```
PYTHONPATH=<корень дерева> bash scripts/machine_gate.sh heavy D .venv/bin/python <scratchpad>/c91stand/stand_a.py <mode> 1500 <out> 7
```

`framework_file` в каждом JSON подтверждает, какое дерево реально импортировано.

## Что НЕ доказывает этот стенд

* Это одно дерево, один процесс, один воркер, одна ОС (macOS, CPython 3.12, `switchinterval` 1e-5); на Windows/Orin планирование потоков другое. «0 нарушений» — отсутствие нарушения в 1500 циклах конкретной нагрузки, а не доказательство отсутствия гонки.
* Частота 1500/1500 на main в `raise_stop` — не вероятность в проде: цель бросает быстрее, чем клиент вызывает stop, окно подобрано так, чтобы почти всегда попадать в `sleep(0.1)` авто-рестарта. Режим доказывает, что дефект воспроизводим и что правка его закрывает, а не как часто он случается.
* `overlap` на main: 102 цикла из 1500 (потолок времени), а накопление потоков искажает последние циклы (все метрики «живых > 1» с ним растут). Для контроля чувствительности достаточно, как количественный сравнительный замер — нет.
* Не проверялось: `stop_all_workers` и остаточный риск D2d из ADR-WRK-007 (на ветке отдельно остаётся описан в ADR); упрямая цель, игнорирующая `stop_event` (состояние B таблицы A/B/C) — покрыто только юнит-тестами ветки; цели с сотнями мс работы; два менеджера одновременно.
* Часть B: потоки процесса `cam_fake` считались числом (`num_threads`) и реестром воркеров из `introspect.status`, имён потоков в процессе камеры снаружи нет — «число потоков с одним именем» там не измерено (у реестра имена уникальны по построению). Стенд B был один раз на ветке; на `main` не запускался (по заданию не обязателен), поэтому «до/после» на камере нет.
* Прогоны части A и подъём приложения шли одновременно (шесть процессов `stand_a.py` + приложение на одной машине), поэтому время shutdown 1,11 с нельзя сравнивать с 0,53 с из W2-отчёта.

## Что осталось открытым / ненадёжно

1. На ветке в режиме overlap sampler поймал 4 мгновенных замера «живых потоков воркера = 2» (максимум 2) из ~1500 циклов; после схождения (проверка ждёт до 2 с и ещё окно 0,13 с) нарушений 0. Это согласуется с описанным в ADR-WRK-007 хвостом: старый поток авто-рестарта доживает `finally`, пока новый уже создан. Инвариант «≤ 1 после схождения» на ветке выдержан, но «ровно ≤ 1 в любой момент» стенд не подтверждает; сколько живёт этот хвост, не измерено — решать ревьюеру/владельцу, считать ли это допустимым.
2. Прогон main-overlap неполный (102 из 1500 циклов), см. выше; прерванный первый прогон не оставил данных.
3. В режиме `raise_stop` на main уборка после цикла (`stop_worker` повторно) тоже теряется, поэтому `final_live` = 1 и потоки накапливаются; на количестве нарушений это не сказывается, но распределение по циклам не независимо.
4. `multiprocess_prototype/app.state.yaml` в worktree перезаписан запуском приложения (`[run] активный рецепт записан в состояние`: `camera_device_demo`); файл в `.gitignore` (`*.state.yaml`), `git status` чист, но прежнее содержимое (какой рецепт был активным) я не сохранял и не восстанавливал.
5. Скрипт и данные лежат в scratchpad сессии (может быть очищен при перезагрузке); в репозиторий закоммичен только этот отчёт — и он не закоммичен мной, коммитит лид.
6. Нагрузка на общей машине: часть A держала до 6 процессов, один из них (main-overlap, первый прогон) ушёл в 290 % CPU около 6 минут до ручной остановки — на соседей по машине могло повлиять.

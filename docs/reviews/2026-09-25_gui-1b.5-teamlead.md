## Замер командного пути хаба (живой стенд, порт 7912, сервис-заглушка из scratch-манифеста)

Заглушка `sleepy`: `start` = sleep 5 с, `stop` = sleep 3 с; два клиента `BackendDriver` к одному хабу.

- `service.start` (клиент 1) → `0.231 с`, `{lifecycle: ready, pending: True}`; через 5.5 с `status` → `running`.
- `introspect.status` клиента 2 во время pending-старта → **0.187 с** (AC «< 0.5 с» выполнен; это само ожидание 0.2 с).
- `introspect.status` клиента 2 во время синхронного `service.stop` 3 с → **2.947 с**.

Вывод: хаб исполняет обработчики на ОДНОМ пути для всех клиентов; любое ожидание в обработчике — задержка всех команд.
Модбас на стенде (`127.0.0.1:502`, отказ соединения) стартует за 0.026 с с `start_failed` — 9-секундный путь
(таймаут, а не refused) на стенде **не воспроизведён**.

## Что я истолковал, а не выполнил буквально

- Ленивый discover — внутри `ServiceHost` (kwarg `service_paths`), не в оркестраторе: иначе hazard «ровно один раз»
  нельзя положить в framework-тесты. Сигнатура брифа `ServiceHost(registry=None, start_wait_sec=0.2)` расширена.
- `service.list` всегда несёт `failed` (пустой `{}` без сбоев); сбой всего discover — ключ `"<discover>"`.
- `detail` при старте в полёте — `{"pending": True}`: не зову `get_status()` экземпляра, чей `start()` идёт в другом потоке.
- Сбой чтения system-конфига на хабе → лог ошибки и хост с пустыми путями (клиент видит пустой список без `failed`).
- `ServiceManagerFromRegistry._instances` — property-делегат на кэш хоста (test_catalogs кладёт туда экземпляры).
- `python -m scripts.sync` переписал строку в `multiprocess_framework/DECISIONS.md` — вне FILES, но требуется брифом.

## Что оставил открытым / ненадёжно

- **stop/restart во время старта в полёте держит командный путь хаба** до конца старта (для modbus-таймаута — до ~9 с),
  по DESIGN п.2 «stop синхронный». Замер выше; сообщено ведущему. Закрытие — его решение.
- `start_wait_sec=0.2` — ровно столько каждая pending-команда `service.start` задерживает ВСЕ команды хаба.
- 9-секундный `connect()` modbus живьём не проверен (на стенде refused, не timeout); `pending` живьём проверен только заглушкой.
- Поток хаба я мерил латентностью, а не именем потока: какой именно поток исполняет обработчики — не установлено.
- Discover в singleton `ServiceRegistry`: второй discover в том же процессе (например, в тестах, гоняющих хост
  после `scanner` тестов без `clear()`) даст `failed` «уже зарегистрирован» по всем сервисам.
- Радиус не зелёный целиком из-за предсуществующего загрязнения порядка (см. выше).

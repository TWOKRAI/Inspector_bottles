Решение: у SocketClient публичных `subscribe`/`send` НЕТ; fire-and-forget — `send_nowait`, подписки — в прикладных классах.

**Wire-формат сервера** (`socket_channel.py`): JSON + `\n`, UTF-8, `ensure_ascii=False` (`:183`); чтение — `split(b"\n", 1)` (`:303-304`); поле `session` — привязка session→сокет (`:333-335`), адрес ответа (`:224`) или хвост `_address=[<канал>, <sid>]` для push (`:227-229`). Клиент уже совпадает (`transport.py:236`, `:273-276`).
**Серверная обработка** (`socket_bridge_adapter.py:68-138`): КАЖДОЕ входящее — `router.request(msg, timeout)` в read-потоке сокета, затем ответ `{"type":"response","request_id":corr,"result":…,"session":sid}`. Следствия: (а) fire-and-forget без `request_id` всё равно получает ответ с `request_id: None` → клиент выдаст его в push-колбэк как «событие»; (б) такой send держит read-цикл до ответа/таймаута (HOL, 1.3a).

## 2. Контракты команд и стейта

- **`CommandSender` — класс, не Protocol** (`frontend_module/bridge/command_sender.py:59`). Protocol'ы — у его зависимости: `IProcess` (`:35`: `name`, `send_message(target, msg) -> None`) и `IRequestingProcess` (`:44`: + `router_manager` с `request(msg, timeout) -> dict`). Методы: `send_command(target, command, args=None) -> None` `:80`; `send_field_command(..., debounce_ms=0)` `:114`; `send_action_command` `:145`; `flush()` `:195`; `send_system_command(command: dict) -> None` `:203`; `request_command(target, command, args=None, *, timeout=30.0) -> dict` `:225`; `request_system_command(command, *, timeout=30.0) -> dict` `:253`. PM-relay для чужих целей `:107-110`.
- **Стейт:** `IStateProxy(ABC)` (`state_store_module/interfaces.py:184`): `get(path, default=None)`, `set(path, value) -> None`, `merge`, `delete`, `subscribe(pattern, callback, exclude_self=False) -> str`. Реализация GUI — `GuiStateProxy(process_name, router, delta_sink, server_target="ProcessManager", manager_name, logger)` (`proxy/gui_state_proxy.py:42`), колбэк получает **`list[Delta]`**, не `(path, value)`. Роутер — `IRouter` (`interfaces.py:44`: `register_message_handler`, `send_async(msg, priority)`, `send(msg)`); фактически StateProxy ещё зовёт `request(msg, timeout=)` (`state_proxy.py:1502`) и `request_async(msg, on_response=, timeout=, correlation_id=)` (`:979`, при отсутствии — блокирующий фолбэк `:1010`).
- **Инвентарь 1.1 называет:** `IProcess`/`IRequestingProcess` (`command_sender.py:35`, `:44`) и `GuiStateProxy(...)` (`gui_state_proxy.py:42`) — «роутер-подобный объект должен уметь `request`, `send_message`, `register_message_handler`» (инвентарь, стр. 50).

**Вывод (лестница: переиспользовать):** не писать команды и стейт заново, а подложить сокетный адаптер под существующие классы:
- `RemoteCommandSender(CommandSender)` — `__init__(client)` строит адаптер `IRequestingProcess` над SocketClient и передаёт его в `super().__init__`. Debounce, PM-relay, билдеры протокола — даром; `isinstance(x, CommandSender)` у виджетов остаётся истинным.
- `RemoteStateProxy(GuiStateProxy)` — `router=` сокетный `IRouter`-адаптер; кэш, revision/resync, `ensure/release_subscription` (нужны 1.4) — даром.

## 3. Fence

- Штамп: `_fence = {"sender": <имя>, "inc": <own incarnation:int>, "epoch": <own epoch:int|None>}` (`message_module/fencing/token.py:93-97`); не ставится, если incarnation `None` (`:90-91`) или сообщение data-plane.
- Фабрика **чистая**: `make_fence_stamp_middleware(sender, get_fence)` (`token.py:74`), экспорт `message_module/__init__.py:65`. Вызывается без ProcessModule: `stamp = make_fence_stamp_middleware("pult", lambda: (inc, epoch)); msg = stamp(msg)`. Извлечение не нужно.
- Проводка в процессах — **не `process_module.py:654`** (там докстринг про incarnation в логах), а `process_module/commands/builtin_commands.py:3980-4006`; провайдеры `_get_own_fence` `:3903` (свой PSR `routing_incarnation`/`routing_epoch`), `_get_expected_incarnation` `:3919` (PSR отправителя).
- **Фильтр дропает по per-sender incarnation, epoch НЕ сравнивается** (`token.py:130-140`, докстринг `:14-22`, ADR-PMM-014). Дроп только если `inc < PSR[sender].routing_incarnation`; отправитель, которого нет в PSR получателя, проходит всегда (`:134-136`).
- `capabilities` epoch/incarnation НЕ отдаёт: `capabilities_extra` PM — «только КОНТРАКТ, без runtime-значений» (`process_manager_process.py:513-525`). Но уже есть команда PM **`supervision.status`** (`:467`, обработчик `:660-713`): `{"epoch", "processes": {name: {"incarnation", …}}}`. Поле в хост добавлять не нужно — читать отсюда.

## 5. Доставка push

Сегодня: reader-поток (`transport.py:95`, daemon `backend-ctl-reader`) → `_dispatch` (`:313`) → `_emit_event` → `EventHub.emit` → колбэки подписчиков **синхронно в reader-потоке** (`events.py:577-583`). Точка внедрения — `dispatch: Callable[[Callable[[], None]], None]` в конструкторе прикладных классов (не SocketClient): в Qt — `lambda fn: QTimer.singleShot(0, fn)` или сигнал с QueuedConnection, в тестах — `lambda fn: fn()` или очередь. Для стейта готовое место — `delta_sink` GuiStateProxy (`gui_state_proxy.py:109-111`): `on_state_changed` (кэш + revision) идёт в reader-потоке, вызов колбэков — через `dispatch`.
**Ловушка:** `on_state_changed` может запустить `_resync` → если у адаптера нет `request_async`, срабатывает блокирующий фолбэк → `request()` из reader-потока → guard вернёт error-dict (`transport.py:166-169`) → ресинк молча не состоится. Значит SocketClient обязан уметь `request_async` с таймаутом «ровно один раз» (контракт `router_manager.py:1106-1135`); таймауты можно подметать в reader-цикле, который и так просыпается каждые 0.5 с (`transport.py:93`, `:258`).

## 7. Ловушки: где план противоречит коду

1. **Fence-приёмка недостижима как написана.** План: «отвергает команду с устаревшим эпохом». Код: epoch не сравнивается, дроп только по `inc < PSR[sender].routing_incarnation` (`token.py:130-140`). У Пульта нет записи в PSR детей → проходит легаси-веткой (`:134-136`) при ЛЮБОМ штампе. Штамп «той же функцией» даёт паритет структуры, но не отказ. Варианты: (a) Пульт штампует как `sender="gui"` с incarnation gui — подмена личности, и после рестарта бэкенда incarnation заново считается с 1, так что старый Пульт с большим `inc` пройдёт; (b) хост назначает внешнему клиенту incarnation и публикует его в PSR детей через `routing.refresh` — это хаб, уже не «одно поле»; (c) сузить AC3 до паритета структуры и записать «отказ stale для внешнего отправителя» в G1b. → **ESCALATION cto**.
2. **`process_module.py:654`** — неверная ссылка; проводка fence в `builtin_commands.py:3980-4006`.
3. **«Взять эпох/токен из `capabilities`»** — там только контракт (`process_manager_process.py:513-525`); runtime-значения уже есть в `supervision.status` (`:660-713`). Поле добавлять не нужно; если всё же в `capabilities_extra` — это нарушит его докстринг.
4. **«Тот же Protocol, что `CommandSender`»** — Protocol'а нет, `CommandSender` — класс; Protocol'ы у его процесса (`IProcess`/`IRequestingProcess`).
5. **AC2 `RemoteCommandSender.send("ping")` → `{"status":"ok"}`** — метода `send` нет; `send_command` возвращает `None`. Реальный путь — `request_command(target, "ping")`; ответ — конверт `RouterManager.request` (`{"success", "result"}`), а не голый `{"status":"ok"}`. Встроенного `ping` в `builtin_commands.py` нет — стаб регистрирует его сам.
6. **AC4 «`cb` вызван с `("a.b", 1)`»** — контракт колбэка `IStateProxy` — `list[Delta]`. Тест должен разбирать `Delta.path/new_value`, или AC переписать.
7. **Поверхность `SocketClient.subscribe/send`** затенит `_EventChannelMixin.subscribe` в MRO BackendDriver → `backend_ctl` сломается (§1).
8. **«Реконнект с восстановлением подписок»** в `_TransportMixin` сейчас нет — он в `DriverSession` (`mcp_driver_session.py:385-514`: новый driver + `import_subscriptions`/`replay_subscriptions`, `driver.py:568-617`). Перенос «дословно» его не принесёт; для GUI это новая логика.
9. **Subscriber = `backend_ctl.<session>`**, session меняется на каждом connect → `process_name` StateProxy (`subscriber` в `state_proxy.py:390`) устаревает после реконнекта. Нужна правка имени при `on_reconnected` (сеттер в GuiStateProxy или пересборка subscribe-сообщений) — либо стабильный session на экземпляр клиента, с риском гонки с `on_session_closed` старого сокета (`socket_channel.py:381-385`).
10. **Fire-and-forget по сокету — не fire-and-forget** на сервере (§1): read-цикл ждёт ответа обработчика. Для частых `send_field_command` это HOL до 1.3a.

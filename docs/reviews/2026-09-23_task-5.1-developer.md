## Что я интерпретировал, а не просто выполнил

- Контракт §2 говорит «ядро получает `on_event=journal.on_event` (рядом с
  `on_job_done` из 3.5 — оба колбэка в одном конструкторе)» и просит писать
  вызов `RobotSimCore(...)` по одному keyword на строку ради минимального
  диффа с параллельной веткой. Я оставил ТОЛЬКО `on_event=...` (свой
  колбэк) — `on_job_done` уже существует в `sim_core.py` (Task 3.5a слит), но
  его подключение к плагину — предмет параллельной ветки 3.5b, которая, судя
  по RED-тестам `test_job_done_forward.py`, ожидает СВОЙ метод
  `plugin._on_job_done`. Я его не добавлял (не в FILES, не в REDS этой
  задачи) — при мёрже двух веток строку `on_job_done=self._on_job_done,`
  нужно будет добавить в тот же вызов `RobotSimCore(...)`, конфликт должен
  быть однострочным.
- `_find_frozen_xy` — новая функция, которой нет в контракте буквально (он
  описывает ТРИ исхода прозой), я выбрал реализацию через отдельный метод
  (по аналогии с `_find_origin`) вместо встраивания цикла прямо в
  `_register_job` — читаемость ради структурного параллелизма с уже
  существующим методом.
- Существующие тесты, расширенные под новые ключи (см. раздел выше) — решил
  править их напрямую, а не оставлять RED, потому что ACCEPTANCE прямо
  требует «existing SimMonitor/journal tests green», а расхождение
  порождено буквальным следствием контракта, не ошибкой логики.

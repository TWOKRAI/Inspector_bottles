## 1. Что сломалось — править до первого коммита Ф1

### Б-1. База ветки: `feat/observability-roadmap` больше не существует как фронт

План: «ветка отходит от `feat/observability-roadmap`, а не от `main`». Факт:
- roadmap влит в `main` (`aba78bcf`, предок `main`);
- `feat/otel-export` содержит ровно один коммит (`3c50e9df`, пин extras) и **целиком является предком** `feat/observability-closure` — уникального содержимого у ветки нет;
- closure опережает её на **433 коммита**, и среди них — правки формы записи (Б-2).

**Решение:** пересоздать `feat/otel-export` от HEAD closure (не раньше `46e970ab`). Порядок слияния: otel → closure → `main`, либо ждать merge closure в `main` (решение за владельцем, стоит с Task 3.0). Снимок Task 1.0 снимать только на коде closure — снимок с `main` описал бы форму, которой на живой дороге уже нет (ровно дефект ред. 1).

### Б-2. Форма записи изменилась в трёх местах; Task 1.3 сторожит половину числовой плоскости

| Изменение (closure) | Где | Следствие для маппера |
|---|---|---|
| Task 3.1: `severity="number"`, `severity_number=0` (UNSPECIFIED) у **всех** числовых записей; `metric_type` переехал в `extra` | `record_display.py:78,304-325` | `SeverityText="number"` — не OTel-текст; на выход не должен попадать вовсе (см. ниже) |
| Task 3.1: колонка `metric` и `origin` (маркеры `stats_snapshot` / `error_manager`) в записи стора; store-tap поднимает `origin` на верх записи | `store_tap.py:57,130-160` | `origin` — внутренний маркер маршрутизации того же класса, что `scope`: **изымать из `Attributes`**, добавить в Task 1.1 шаг 2 |
| Task 1.4: `trace_id` — в `extra.context.trace_id`, текст постоянный | `phase-1-invisible-failures.md:633+` | совпадает с посылкой плана — подтверждено, а не опровергнуто |
| `_ENVELOPE_KEYS` теперь включает `observed_ts` | `record_display.py:39` | конверт стал шире; `stamp_observed` — `record_display.py:150` |

**Главное.** Числовая плоскость сегодня — это **два** рода, не один: `kind=stats` (агрегат окна и одиночная метрика) и `kind=observation` (порт наблюдений, `writer.metric`). Обе едут батч-дорогой форвардера: `observability_wiring.py:217` собирает `log + stats + observation` и отдаёт форвардерам без фильтра по уровню (`min_level` стоит только на tap'ах ошибок, `push_batch` не фильтрует). Значит экспортёр получит числа при **любом** уровне подписки. Task 1.3 в ред. 3 отбрасывает только `kind == "stats"` — `observation` уехал бы в коллектор как лог с `SeverityText="number"`.

Абзац «Честно: batch-дорога hub'а сегодня не вызывается ни разу» **устарел** — докстринг `wire_observability_forward` прямо говорит «Batch-половина ЖИВА с задачи 2.1, проверено живым хвостом», а стенд Task 3.5 дал число: **1036 строк `kind=stats`** за прогон.

**Правка Task 1.3:** «числовая плоскость (`kind ∈ {stats, observation}`) не экспортируется в v1»; один счётчик `records_skipped_numbers` с разбивкой по kind в readback; приёмка — не синтетическая, а по живому числу (после Ф2 — числа приходят сами). Инъекция Task 1.1 «подменить `severity_number` на ранг 0…4» остаётся, но с оговоркой: 0 у числовых записей — законное значение, тест адресовать логам.

### Б-3. Дверь конфига `observability.otel_export` закрыта задачей 2.2 closure

План: «настройки в `observability.otel_export`, читаются через `read_process_config`». Два расхождения:

1. `read_process_config` (`observability_layers.py:987`) читает **per-process** ключи `proc_dict` (плоско у оркестратора, под `config.` у ребёнка) — это не чтение секции `observability`. Две фразы плана описывают две разные двери.
2. Секция `observability` теперь под контрактом: схема `ObservabilityConfig` с round-trip-сверкой `unknown_section_keys` (`observability_layers.py:1169`). Незнакомый ключ на слое сессии (L3) → **`ValueError`, слой отвергнут**; на файловом/рецептном слое → в вердикт `config.reload` и аудит попадает строка «ВНЕ КОНТРАКТА (ключ есть, эффекта нет)». Плюс страж Task 2.2 «каждое поле схемы имеет читателя» (`test_f2_task22_schema_wiring.py`) — добавить поле в схему без читателя во фреймворке нельзя, а читатель во фреймворке = правка фреймворка.

**Варианты:**
- **(а)** по прецеденту `documents`: подсекция `ObservabilityDocumentsConfig(factory, config)` — строка-фабрика + непрозрачный `config`, читатель `wire_document_sink` во фреймворке (ADR-PM-028). Честно, но это правка фреймворка и, возможно, обобщение «плоскость экспорта» — против «0 правок фреймворка».
- **(б) — рекомендую для v1:** конфиг экспортёра живёт в **собственном** блоке процесса `otel` в blueprint (`processes.otel.config.endpoint`, `…level`, `…queue_capacity`), читается `read_process_config(svc, "endpoint")`. Ноль правок фреймворка, ноль голосов «вне контракта», `endpoint` остаётся обязательным ключом (требование «Три платформы» сохраняется). Цена: ключ не переключается `config.reload` на лету — но hot-apply endpoint и так в out of scope Task 3.1.

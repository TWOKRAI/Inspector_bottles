## Красные и причина (цитата)
Все шесть router-красных и C3/C5 падают на предусловии `_assert_small_wire`:
- c1_foo: `в сообщении остались крупные ndarray (едут inline): [("msg['data']['foo']", 30000)]`
- c1_two_large_keys: `[("msg['data']['rendered_frame']", 921600), ("msg['data']['mask']", 307200)]`
- c2_boundary: `массив ровно 8192 Б остался inline: [("msg['data']['foo']", 8192)]`
- c4: `[("msg['data']['rendered_frame']", 36864)]`
- c6: `[("msg['data']['foo']", 10000)]` (контроль c6 на `frame` зелёный: арифметика «пишется один раз» работает)
- c7: `[("msg['data']['foo']", 8192)]`
- c3 (`mask` 24000, `depth` 20480), c5 x3 (`foo` 10000): то же.
Контроли, зелёные сегодня: c1/c4/c6 на `frame`, c2 «мелочь inline», c3 `frame` (H,W,3)/(H,W,1)/(H,W) в другом ОС-процессе через настоящий DataReceiver.run_loop, c5 consumer-done/evict/reclaim на `frame` (счётчики == 2), c8 x2.

## Интерпретации (не следование)
1. C2 vs существующие тесты: контракт «ndarray < 8192 едет inline» буквально относится и к `frame`, но test_g5d_loan и др. ждут `"frame" not in item` для кадра 32x32x3=3072 Б. C2 проверен ТОЛЬКО на не-`frame` ключах. Решить лиду: порог для `frame` тоже или `frame` всегда ссылкой.
2. «Отдельный заём на ссылку» -> счётчики `frame_slots_released` / `frame_loans_released_on_evict` / `frame_slots_reclaimed` == 2 сообщения x число крупных ключей (4 для frame+foo). Предполагает, что публичные счётчики middleware агрегируют по всем кольцам. Если реализация раскладывает иначе — поправить литерал, а не размывать смысл.
3. Кольцо на ключ (C7 говорит «кольцо ключа B») -> арифметика исчерпания в C5/C6: кольца глубины 2, третий send = None.
4. Потребитель C5 zero-copy требует `FW_SHM_OWNER_INCARNATION=1` (без него `_zero_copy` False и тикетов нет — замерено). Флаг только включён, его семантика не тестируется (out of scope).
5. Тикеты C5: продовый путь `_collect_view_tickets` -> `_accumulate_releases` -> `_flush_releases` -> `GenericProcess._handle_shm_release`. Поверхность для реализующего: `_collect_view_tickets` обязан вернуть тикет на КАЖДУЮ ссылку item'а (не только frame), а `release_slots` — принять их.
6. Восстановление: `frame` — в `msg["frame"]` (как сегодня), остальные ключи — в `msg["data"][key]` (C4); в пайплайне — `item[key]` через `DataReceiver._build_item`.
7. Границы: (1, 8191) uint8 для 8191 Б (8191 простое), (64,128) uint8 для 8192 Б.

## Что оставил открытым / ненадёжно
- Все красные падают на ОДНОМ предусловии. Глубокие утверждения (побайтное восстановление не-`frame` ключей, тикеты/счётчики на `foo`, realloc-независимость, fan-out для `foo`) сегодня не выполняются: их корректность проверена только на контролях `frame` и не подтверждена на реализации. Возможна «чужая модель» — проверять break-injection.
- C7 без зелёного контроля (сегодня `frame`-realloc теряет более ранние кадры, контроль был бы красным по другой причине).

- Оба файла вызывают приватные `_on_frame_evicted`, `_collect_view_tickets`, `_accumulate_releases`, `_flush_releases`, `_build_item`, `_handle_shm_*` — продовые швы; переименование сломает тесты громко (не тихо).

## Что интерпретировал, а не выполнил буквально

- `scene.status.active` считается как `len(self._spawner.active_objects())` из потока команд. Это чтение,
  не мутация: `active_objects()` = `list(self._active)` (копия одной C-операцией под GIL). DESIGN говорит
  «спавнер меняет только `produce()`» — чтение я счёл допустимым; кэшировать счёт в `produce()` не стал.
- Чистка `_removed` по строгому `возраст > dup_window_s` (ровно на границе снятый ещё кандидат).
- Чистка `_removed` и `time.monotonic()` вызываются только при непустой очереди (ранний выход) — на
  исход не влияет: снятые проверяются только при разборе задания.
- `cmd_job_done(None)` → `{"status":"error"}` (через `data or {}` → `KeyError`).
- В H1 добавлен `sys.setswitchinterval(1e-6)` (восстанавливается в `finally`) — без него сторож не ловил ничего.

## Что оставил открытым / ненадёжно

- **5 тестов `test_f1_task11_acceptance.py` не прогнаны** на этой правке — порт 5021 занят чужим живым
  процессом. Они поднимают приложение с `pipeline.yaml`, то есть именно они проверили бы новые ключи на
  живом бутe. Лиду — прогнать при свободном порте.
- Дисциплина передачи между потоками (deque + замок `_recent`) доказана только рассуждением про атомарность
  `deque.append/popleft` в CPython и вероятностным H1; детерминированного сторожа нет.
- Межпроцессная доставка `scene.job_done` robot → camera (роутер, диспетч команды в `cmd_job_done(data)`)
  не проверена — только конверт на мок-роутере. Живой критерий «объекта нет за `job_ms + 1 с`» — стенд лида.
- `recent` и `log_info` на каждое задание: при высокой частоте заданий лог растёт линейно — не троттлится
  (контракт требует «одна строка на задание»).
- Кривой `geometry` в конфиге (нет ключа) → `KeyError` в `configure()`, плагин не поднимется. Сознательно не
  глушил: ошибка конфигурации стенда, как у двух режимов спавна.

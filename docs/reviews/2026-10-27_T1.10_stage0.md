### Блокирующие спецификацию (категория `spec`)

1. **[spec] DESIGN, `ChildProcessStop.outcomes()` — шаг эскалации нельзя брать по флагам группы.**
   `child_process_stop.py:129-141` (`_confirm`) видит только `_kill_started_at` (:91, :201) и `_real_kill_sent` (:223)
   — флаги ГРУППЫ. `kill()` (:203-210) пропускает имя, умершее между сроком и вызовом (`if not self._alive(...): continue`),
   `_send_real_kill(alive)` (:224-229) шлёт `proc.kill()` только именам из списка живых того прохода.
   Воспроизведение (`attr_probe.py`, подделка живая на `request_stop` и первом проходе, мёртвая к `kill()`):
   `join1: False join2: True terminate delivered: 0 real kill delivered: 0 group kill_started set: True survivors: ()`.
   Ввод: ребёнок вышел сам между истечением окна и `kill()` → сигнал не доставлен, флаг группы взведён → реализация
   «после kill() группы ⇒ terminated» даст `terminated`, правда — `exited`. Исправить: в DESIGN записать пошаговые
   множества `_terminated`/`_killed` (имя попадает туда в цикле, где сигнал доставлен: после `terminate()` в `kill()` и
   после `proc.kill()` в `_send_real_kill`), `_confirm` читает их; добавить RED **R9** (подделка, умершая до `kill()`
   группы, даёт `exited`, `terminate` вызван 0 раз). Инъекция «метка по флагу группы» → R9 красный, R1–R8 зелёные.

2. **[spec] DESIGN, `handed_over` — где решает и как не путать с `survived`.** Текущий код разводит чисто, но DESIGN
   этого не пишет (пункт `outcomes()` перечисляет четыре значения, пятое — в абзаце PM). Факты: `join_until`
   (:239-247) сначала `_observe()` (умерший на этом проходе подтверждается: `exited`, `True`, даже если системный стоп
   взведён одновременно), потом `_abort_requested()` → `_aborted = True`, возврат `False`; имя остаётся вне `_dead`.
   `kill()` (:199) при `_aborted` — выход без `terminate`. Фаза 3 области зовёт `kill()` (no-op) и `join_until(until)`
   (`lifetime.py:627-657`) — второй `join_until` снова видит предикат (`system_stop_event` не сбрасывается,
   `process_registry.py:487`) и возвращает `False` сразу. `survivors()` (:278-282) вернёт имя. Правило для DESIGN:
   подтверждённое имя — своя метка; неподтверждённое и `aborted` → `handed_over` (в том числе если `terminate()` уже
   был послан до прерывания); неподтверждённое и не `aborted` → `survived`. Решать должен `outcomes()` (одно место,
   `ProcessRegistry` только копирует). Второе: `_stop_many` сейчас строит `result` из `survivors()` (:466-468);
   `outcomes()` — второй проход наблюдения, между ними имя может умереть → `success False` при `outcome exited`.
   Требовать: `result[name] = outcome ∈ {exited, terminated, killed}` из ОДНОГО снимка (`outcomes()` делает свой
   `_observe()`, как `survivors()`); тогда «success = outcome ∈ …» верно по построению. Добавить RED **R10**
   (юнит, без PM): подделка жива, `should_abort` истинен после посланного `terminate()` → `outcomes()[name] ==
   "handed_over"`, `terminate` вызван ровно 1 раз. Инъекция «`handed_over`↔`survived`» → R4 или R8 и R10.

3. **[spec] DESIGN — не определён `outcome` на путях без стопа; риск устаревшего значения.**
   `stop_process` (`process_manager_process.py:3834-3839`) возвращает `True` для «нет в реестре» и «не жив», не
   доходя до `_stop_many`; `_build_child_stop` (`process_registry.py:435-449`) делает то же для призраков и уже
   мёртвых. Запись `stop_outcome` по имени переживает `remove_process` (так задумано) — значит ответ, читающий реестр
   после такого `stop_process`, вернёт ЧУЖОЙ итог прошлого стопа. Ввод: `process.stop slow` (итог `terminated`), снова
   `process.stop slow` → `success: True`, `outcome` из реестра = `"terminated"` (стоп не выполнялся). Это вывод по
   чтению кода (реализации нет) — считать риском, не наблюдением. Решить в DESIGN таблицей: (а) уже мёртв →
   `exited` (определение «смерть подтверждена до любого `terminate()`» подходит буквально); (б) имени нет в реестре →
   `None` при `success: True` (оговорить в инварианте); (в) `stop_process(None)` — ответа с `outcome` нет;
   (г) `restart_process` до стопа: нет конфига (:3857-3859) или отказ после системного стопа (:3855) — `outcome`
   отсутствует или `None`, `success: False`; (д) ответы-отказы `key_missing`, `system_stopping`, `executor_busy`
   (ADR-039 I3 а, б) `outcome` НЕ несут. Как не читать чужое: `stop_process` пишет запись на КАЖДОМ пути или обработчик
   получает значение возвратом метода. Добавить RED **R11**: повторный `process.stop` мёртвого ребёнка → `success:
   True`, `outcome` по выбранной таблице, не значение прошлого стопа.

4. **[spec] DESIGN — «`success` = `outcome` ∈ {…}» неверно для рестарта.** `restart_process` возвращает `False`
   и после успешного стопа, если `create_and_register` упал (:3883-3886). Ввод: стоп `terminated`, пересоздание не
   удалось → `success: False`, `outcome: "terminated"`. Записать: у `process.stop` `success ⇔ outcome ∈ {exited,
   terminated, killed}` (плюс строки (а), (б) п. 3); у `process.restart` `outcome` описывает только фазу стопа,
   `success` = стоп подтверждён И пересоздание удалось.

5. **[spec] Имя и жизнь поля в `supervision.status` расходятся с потребителем; путь корня не покрыт.**
   Задача и `plans/lifecycle-stop-ownership.md:60` называют поле `stop_outcome`; `gui-graceful-close`

   или `handed_over`. Решение лида/CTO до тестера: (1) одно имя поля на обе стороны (поправить одну из
   спецификаций); (2) срок жизни: либо чистить запись при старте нового воплощения (ответ рестарта тогда берёт
   значение возвратом, не из реестра), либо оставить и записать правило потребителю «сверять с

## Ответы на вопросы лида

1. **Атрибуция по шагу.** Структура цикла позволяет, но НЕ по флагам группы — нужны пошаговые множества (п. 1, есть

   живых; отображение на `handed_over` чистое при правиле п. 2. `survived` отличим: неподтверждено и не `aborted`.
2. **Путь к ответу без смены bool-контракта.** Есть: `_cmd_process_stop` и `_cmd_process_restart` читают
   `registry.stop_outcome(pn)` после вызова; требует п. 3. Затронутые вызывающие: `_cmd_process_stop` (:724),
   `_cmd_process_restart` (:745) → `restart_process` (:3846) → `stop_process` (:3863); `_topology_stop` (:4383) →
   сид `TopologyManager._stop_process` (`topology_manager.py:353`, ждёт truthy); `stop_process(None)` →
   `stop_all`; `stop_one` зовёт только `stop_process` (:3841); `stop_many` — `_topology_stop_all` (:4400) и `stop_all`.
   Контракты `-> bool` в `interfaces.py:153,166,311` и GUI `topology_bridge.stop_process -> bool` не меняются;
   `process_manager_proxy` (`-> dict`) и монитор (`_dispatch_due_restarts`, ответ не читает) не затронуты. Ломаются
   только точные сравнения словарей (п. 6).
3. **R8 без `error`.** Совместимо с кодом: прерванный стоп сейчас отвечает `{"success": False, "process_name": pn}`
   (:724; `stop_process` вернул `False`), ADR-039 I3(в) требует именно этого, тест 1.9b проверяет только `success`.
   Нарушаются: перечень I3 (п. 11) и «ответ несёт `outcome` всегда» (отказы без него, п. 3д). Пара «снятая из очереди
   → `system_stopping` без `outcome`», «текущая → `handed_over`» держится существующим
   `test_queued_lifecycle_ops_rejected_on_system_stop` (:451) — оставить зелёным.
4. **`stop_outcome` в `supervision.status`.** Доступно: остановленный `slow` остаётся в записях (`alive: False`,
   замер); добавление поля — одна строка в `processes[name]`. R5 проверим. R5/R6 на настоящем ребёнке на Windows
   реальны (времена в п. 10). Запись по имени и «`alive: True` с `terminated` после рестарта» — п. 5.
5. **Однозначность R1–R8.** Нет: п. 7, 8, 10 (обвязка, дверь, точность словаря, слой R3/R4).
6. **Инъекция по exitcode.** Прогноз неверен, измерение — п. 9.

Оба теста зелёные сегодня и в списке «литералов, которые станут красными» не значатся. Поправить D4: `_cmd_process_stop` и
`restart_process` продолжают звать `self.stop_process(name, mark_reader_gone=...)`; итог идёт боковым каналом, заполняемым

**E2. [spec, major] D2: `outcomes()` обязан сам делать `_observe()`.** Сегодня последний проход наблюдения после

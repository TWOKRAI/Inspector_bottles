## Проба YamlPatchConflict (ACCEPTANCE 4)

Скрипт и tmp-рецепты — в scratchpad (`.../scratchpad/probe/probe.py`), в репозитории их нет. Цепочка: реальные `RecipeManager` + `RecipeStoreFromManager` (через `build_chain` из `test_save_noise_store.py`) + `RecipeDevicesStore`, без `yaml_patcher`.

Результат: **воспроизведено**, но не на любой правке рецепта с якорем.

- Рецепт: два устройства, у `a` — `transport: &tr {host, port}`, у `b` — `transport: *tr`.
  - `upsert` с изменением `transport` устройства `a` (трогает общий узел) -> `RecipeDevicesError("Рецепт нельзя изменить точечно: общий узел YAML (якорь или алиас) — правьте файл вручную")`, `__cause__` = `YamlPatchConflict`. В лог ушла строка `Рецепт 'r': операция с устройствами отклонена: YamlPatchConflict` (только имя класса).
  - `upsert` нового устройства `c`, `remove("a")` — прошли, файл изменён.
- Рецепт с якорем на самом элементе списка (`- &d1 {id: a...}` + `- *d1`): `upsert` нового, `upsert` обновления `a`, `remove("a")` — все прошли.

Вывод: условие срабатывания узкое — правка значения, на которое ссылается алиас. Текст ошибки (литерал 4) — без значений и без пути. R4 для `YamlPatchConflict` через `yaml_patcher` остаётся валидным и нужным, но реальный путь тоже достижим.

## Находки

- Ветка `raise  # недостижимо` в конце `_translating` нужна только для типизации/защиты на случай рассинхрона кортежа и таблицы; кортеж строится из той же таблицы, поэтому цикл всегда находит совпадение.
- Побочный эффект «ловим по isinstance»: любой `OSError` (в т.ч. не от рецепта), всплывший из `read_canonical`/`save_raw` внутри `with`, переведётся в литерал 5. Это в рамках DESIGN (литерал «нет доступа или места на диске»), но формулировка шире, чем только файл рецепта.

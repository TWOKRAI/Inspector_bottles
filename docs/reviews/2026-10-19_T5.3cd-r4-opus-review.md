## 1. Взаимная блокировка и голодание

Кто зовёт публичный `connect()` в продакшене (`git grep`, без тестов):
- `DeviceManager.connect` (`Services/device_hub/manager.py:433`) — единственный вызов `driver.connect()` для робота.
- Его зовёт только `DeviceHubPlugin._process_conn_queue` (`Plugins/hub/device_hub/plugin.py:433`) из `_supervisor_loop` — поток supervisor.
- `_process_conn_queue` и `manager.connect` не держат замков во время `driver.connect()`.

Граф замков (по чтению):
- Блокирующий захват `_param_lock` один: `connect()`. Вызывающий не держит ни одного замка драйвера.
- Держатели `_param_lock` (тик в `_ensure_connected`, `_resync_maybe`, `param_set`/`param_apply` через `_param_gate`, `connect`) под ним берут только `_flags_lock` (коротко) и делают ввод-вывод. `_jog_tx_lock` под `_param_lock` не берётся.
- `request_stop` и `disconnect` `_param_lock` не берут.
- Цикла нет.

Воспроизведение (тик держит замок в I/O переподключения):
- `request_stop` из другого потока -> вернулся за 0,000 с (проба P3a).
- `disconnect` из другого потока -> вернулся за 0,000 с (проба P3c).
- Ручной `connect()` -> ждёт, пока тик держит замок (`blocked True`), идёт после (P1, P3a).

Голодание: тик берёт замок без блокировки и только без связи; путь порога держит замок микросекунды. Ожидание ручного `connect` ограничено одним держателем (одна попытка тика или один `param_set`). Цена: поток supervisor в это время не разбирает очередь других устройств — задержка соседей до одной попытки, не потеря (по чтению, в sim на мёртвой связи не мерил).

## 2. Гонка «замок взят сразу после probe»

- Новый тест `test_reconnect_holds_param_lock_one_connect_one_probe` зелёный (базовый прогон).
- Проба P1: ручной `connect()` запущен сразу после `probe` тика -> `connect` транспорта 1 (только тик), `reconnects` +1, ручной ждал замок и подключил после тика; замок свободен, `_syncing` False.
- Наблюдение P1 (не дефект, было и раньше): хвост тика (`kick_heartbeat`, TLM, ошибки) идёт без замка параллельно с `probe` ручного connect. `probe` клиента сбрасывает «probed», и `_ensure_probed` тика делает свой `probe`: порядок `probe` — тик, ручной, тик. Клиент к этому готов (`_probe_lock`, поколения баз). Замок сериализует подключение с подключением и с операциями параметров, не тело тика.

### Замечание 1 [IPC] minor, решает лид: проверка `is_connected` вне замка

- `_ensure_connected` читает `is_connected` ДО захвата замка и под замком не перечитывает.
- Вход (проба P2): ручной `connect()` завершился между проверкой тика и его захватом (шов в `_activity_alive`, порог снят `_last_reconnect = -100`).
- Выход: тик подключает второй раз: `connect` транспорта 1, `probe` 2, `reconnects` +1, лишних `PARAM_SET` 0 (метки равны — `sync_params` не пишет), `_ready` False на время повторного подключения.
- Вред малый: лишний `probe`, счётчик `reconnects`, миг «нет связи». В продакшене окно — несколько байткодов на каждой стороне.
- Исправление (2 строки): сразу после `acquire(blocking=False)` — `if self.is_connected: return True` (в `try`, замок отпустит `finally`).
- Утверждение коммита «на подключение один connect транспорта и один probe» верно для гонки с `param_set`; для гонки с ручным `connect` остаётся это окно.

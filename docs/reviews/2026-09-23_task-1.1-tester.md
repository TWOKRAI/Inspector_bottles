# Task 1.1 — независимые acceptance-тесты (RED), tester

Plan: `plans/lifecycle-graceful-stop.md`. Роль: tester (независимый, stage 1,
ДО реализации). Worktree: `.claude/worktrees/l2-tester`,
branch `test/lifecycle-graceful-stop`, коммит на момент старта `21d9c10c`.

## Что проверялось

Дефект (по брифу лида): на `system.stop()` PM гасится за ~0.6s, но потом
виснет в `multiprocessing.util._exit_function -> queues._finalize_join`,
потому что feeder-поток `mp.Queue`, которую он писал, заблокирован в
`send_bytes` к мёртвому/задушенному читателю с полным pipe.
`cancel_join_thread()` нигде не вызывается. Спавнер бьёт `join(5.0)` и
убивает вручную (`launcher/spawner.py:160-165`).

Все три теста проходят ЧЕРЕЗ `run_process_function`
(`multiprocess_framework/modules/process_manager_module/runner/process_runner.py`)
в настоящем дочернем OS-процессе (`multiprocessing.get_context("spawn")`) —
не через сырой stdlib `mp.Queue`, т.к. дефект живёт на границе
`atexit`-финализации очереди, которую нельзя воспроизвести на уровне мока.

## Файлы

## Результаты

### Property A — `test_exit_is_bounded_when_queue_reader_is_dead`

Пишущий процесс (`_FillQueueThenIdle`) забивает очередь 5000×1KB
(`put_nowait`, читатель никогда не осушает) → `stop_event.set()` →
`child.join(timeout=2.0)`.

Три независимых прогона (foreground, каждый со своим дедлайном
`join(timeout=2.0)`, без флуда):

```
run 1: AssertionError: процесс всё ещё жив после join(timeout=2.0); elapsed=2.004s
run 2: AssertionError: процесс всё ещё жив после join(timeout=2.0); elapsed=2.002s
run 3: AssertionError: процесс всё ещё жив после join(timeout=2.0); elapsed=2.003s
```

**RED, стабильно, без флаки** (разброс elapsed 2.002–2.004s — упирается
ровно в наш `timeout=2.0`, процесс остаётся жив все 3 раза).

### Property B — `test_message_to_live_reader_is_delivered_before_exit` (guard)

Пишущий процесс (`_PutMarkerThenIdle`) кладёт один маркер, живой читатель
(родительский тест-процесс) забирает его, затем `stop_event.set()`.

```
1 passed in 3.56s (совместный прогон с Property A)
```

**GREEN уже сегодня** — подтверждает, что штатный путь (без забитого pipe)
не сломан и не станет объектом «нулевой отсрочки» при фиксе.

### Property C — `test_harness_stop_is_under_two_seconds` (live)

`BackendHarness(recipe="multiprocess_prototype/backend/topology/inspection_full.yaml",
port=8850+i)`, headless, без `with_base` (как в CLI-запуске рецепта, шапка
самого yaml). Прогон: `start()` → `sleep(2.0)` (трафик по 7 процессам) →
замер `stop()`.

Прогон только один (i=0) — первый же `assert elapsed < 2.0` падает и
останавливает цикл (по дизайну; тест написан на 3 итерации, но RED-запуск
не должен тратить время на все три):

```
Прогон #1 (первая попытка, caplog-детектор): elapsed=5.540s
Прогон #2 (после правки детектора на capsys):  elapsed=5.033s
```

Обе попытки — падение на `assert elapsed < 2.0` с сообщением
`stop() занял {N}s (>= 2.0s)`; в stderr обоих прогонов видна строка
`[WARNING] [-] spawner: ProcessManager did not stop in 5.0s, terminating...`
(подтверждает механизм из брифа лида буквально).

**RED**, elapsed ~5.0-5.5s — совпадает с ACCEPTANCE ("~5.5s") и с
`join(5.0)` в спавнере + накладные terminate/join.

## Находка по ходу работы (не дефект, а свойство инфраструктуры)

Строка-маркер `"did not stop in"` (`ProcessSpawner.stop()`,
`self._logger.warning(...)` через `StdLoggerFacade`/`get_std_logger("spawner")`)
на живом стенде **не долетает** до `logging.getLogger("mpf.spawner")` тем
путём, который видит `caplog` (первая версия теста с
`caplog.at_level(..., logger="mpf.spawner")` поймала 0 записей, хотя строка
была явно видна в stderr). Похоже, на живом стенде с настроенным
`LoggerManager`/channel routing `warning()` уходит в наблюдаемость
(файлы/stderr), а не в стандартный `logging`-хендлер, который caplog
патчит. Тест переписан на `capsys` (снимает и `stdout`, и `stderr`) —
детектирует строку надёжно (проверено дважды). Это касается ТОЛЬКО
инструмента теста, не самого дефекта.

## Флакиность

Property A: 3/3 стабильно RED, разброс elapsed 2.002–2.004s (упирается в
собственный `timeout=2.0` теста — ожидаемо, никакой дополнительной
вариативности). Property C: elapsed varies 5.033–5.540s между двумя

объём накопленного трафика к моменту stop), но обе кратно превышают
дедлайн 2.0s, RED не под вопросом.

## Что я интерпретировал, а не следовал буквально

- Класс-«читатель» в Property A НЕ является отдельным процессом — это
  просто отсутствие любого `queue.get()` (ни в родителе, ни в ребёнке).
  Бриф говорит «читатель никогда не осушает / мёртвый процесс» — трактовал
  как «reader полностью отсутствует», это самый прямой и надёжный способ
  воспроизвести «pipe никогда не имеет читателя», не требующий отдельного
  OS-процесса-жертвы (которую тоже пришлось бы убивать и которая добавляла
  бы шум в тест).
- Property C: `with_base=False` — вывел из шапки самого yaml
  (`inspection_full.yaml`), где CLI-запуск дан БЕЗ мёржа `base.yaml`, и
  из того, что камера объявлена как simulator-backend (не нуждается в
  `devices`-хабе). В брифе это явно не указано.
- `_RECIPE` передан СТРОКОЙ (относительный путь от корня репо), а не
  `Path`-объектом — `BackendHarness.__init__` принимает `Path | str`,
  строка короче и не тянет лишний импорт `Path` только ради одной
  константы.
- Диапазон портов 8850-8852 выбран после грепа всех `_PORT`-констант в
  `backend_ctl/tests/*.py` (список занятых: 8765-8799, 8813, 8907) — свободный,
  вне списка.

## Что осталось открытым / ненадёжным в моей же работе

- Property A/B не проверяют СОДЕРЖИМОЕ маркера при частичной доставке —
  только факт получения. Если реализация Task 1.1 введёт частичный
  cancel_join (например, отбросит "в полёте" сообщения даже при живом
  читателе), Property B поймает регресс по таймингу/содержимому, но не по
  ПОРЯДКУ доставки (тест кладёт всего одно сообщение, порядок не проверяем).
  Если это важно для контракта — отдельный тест на порядок нужен разработчику
  (hazard-тест автора, не acceptance).
- Property C: я НЕ проверял поведение при `with_base=True` (слияние с
  `devices`). Если реализация фикса как-то завязана на количество/тип
  очередей, а `devices` добавляет свои — сценарий с базой не покрыт.
- Property C гоняется 1 раз вместо предписанных 3 (первый `assert`
  проваливается и останавливает цикл — иначе RED-прогон тратил бы
  ~15-17s на заведомо провальные повторы). Когда реализация появится и тест
  должен стать GREEN, лид/разработчик обязан прогнать ВСЕ 3 итерации перед
  тем, как доверять "стабильно < 2.0s" — сейчас доказано только "падает
  стабильно", а не "трижды пройдёт после фикса".
- caplog-инцидент (см. раздел «Находка») не расследован до конца — я не
  выяснил ТОЧНО, почему `mpf.spawner` не долетает до caplog-хендлера
  (LoggerManager перехватывает propagate? отдельный handler без
  attach к root?). Переключился на `capsys`, который надёжно работает —
  но если разработчику/ревьюеру понадобится проверять уровень/имя логгера
  этой строки для самого фикса, эта развилка не закрыта.
- Не проверял поведение на Windows/Linux — трапы про размер pipe-буфера
  (~64KB-540KB) в брифе даны для macOS; 5000×1KB=5MB payload взят с большим
  запасом, должен покрывать и другие платформы, но не проверено эмпирически.

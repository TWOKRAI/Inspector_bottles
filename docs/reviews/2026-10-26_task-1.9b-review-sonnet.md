## Находки (по убыванию тяжести)

### 1. [architecture, major] Системный стоп посреди `topology.apply` даёт ложный alert «unstoppable» и ERROR-строки

`ProcessRegistry.stop_abort` передаётся в каждый `_stop_many` (`core/process_registry.py:463`), а не только в стоп
одного процесса. Прерванный стоп возвращает `False` — сиды топологии читают это как «не удалось остановить»:
`_topology_stop_all` (`process_manager_process.py:4392-4394`) и откат (`:1986-1990`).

Воспроизведение (скрипт на `Rig` из `test_lifecycle_fifo_acceptance`, 2 spawn-ребёнка: `slow` 3,0 с и `other`):
`topology.apply` (убирает `slow`) -> на +1,0 с `system.shutdown`. Наблюдаемый вывод:

    apply reply: (False, "{success: False, rolled_back: True, ... failed_at: 0, unstoppable: [slow] ...")
    unstoppable alerts published: [[slow], [other, slow]]
    WARNING | стоп slow прерван системным стопом
    ERROR   | topology stop_all: остановка НЕ подтверждена для [slow]; карта результатов: {slow: False}
    ERROR   | rollback: остановка НЕ подтверждена для [other, slow] — имена исключены из пересоздания, retry на следующем switch

Итог: в state/hub публикуется alert о «зависших» именах, включая здорового `other`; два ERROR при штатном стопе,
хотя ADR-PMM-039 D4 обещает WARNING вместо ERROR; ответ говорит `rolled_back: True`, хотя откат тоже прерван.
R7/H1/H8 проверяют только `process.stop` и запрещают другие строки (`did not stop in`, `terminating`,
`всё ещё жив после kill`), поэтому эту дорогу они не видят.

Просьба: решить и записать в ADR-PMM-039 D4, как сиды `apply_topology` читают прерванный стоп.
Вариант А (минимум): в `_topology_stop_all` и в откате перед alert/ERROR проверить `self._pm_stopping()` -> один
WARNING «прервано системным стопом», alert не публиковать. Вариант Б: передавать `stop_abort` только из
`stop_process(name)`, а не из `stop_many`. Выбор — за лидом (в «Не менять» стоит `apply_topology`). Добавить тест
(топология + `system.shutdown`): 0 строк ERROR «НЕ подтверждена», 0 вызовов `_publish_unstoppable_alert`.

### 2. [tests, major] Адаптированный старый тест флакит 3,2 %

`tests/test_process_root_pm_hazards.py:153`: `assert pm._process_monitor.timeouts == [pytest.approx(0.2, abs=1e-3)]`.
`_ChildrenStop.request_stop` теперь считает `deadline = monotonic() + infra_s` и отдаёт монитору
`max(0, deadline - monotonic())`. На Python 3.12.12/Windows `time.monotonic` — `GetTickCount64`, шаг 0,015625 с
(`time.get_clock_info("monotonic")`). Если тик сменился между двумя вызовами, остаток 0,184 — допуск 1 мс не держит.

Воспроизведение: тело теста 3000 раз в одном процессе (venv python, через шлюз): `runs=3000 failures=96` (3,2 %).
Это один из 1288 тестов модуля; он добавит случайный красный в шлюз.

Просьба: подменить `time.monotonic` в `process_manager_process` константой и вернуть точное `[0.2]`, либо допуск
`abs=0.05` (≥ 3 тиков). Отдельно: в этом тесте `pm = MagicMock()` — `pm.executor_manager.is_executor_thread(...)`
возвращает truthy-мок, ветка ожидания исполнителя в нём не исполняется; живой путь покрыт только H1/H8 (на Rig).

  вызывается с одного пути на подачу (ответ исполнителя ИЛИ исключение подачи); флаг `released` защищает от повторного
  списания при `BaseException` из вложенного `_execute`.

  `should_reject` или закрытый исполнитель (`_deliver` на вызывающем), снятая очередь (`_reject_all`), вложенная дверь
  (`DEFERRED` -> `return`; иначе один `reply` внизу), T на месте (`reply` в `try`), прямая дверь (`_dispatch_command`

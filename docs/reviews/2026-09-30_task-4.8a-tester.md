## Что я трактовал, а не следовал

1. **Шва базы рецепта в спеке нет.** Порча базы делается копией пакета в tmp (`<tmp>/scripts/capacity_bench`, без `tests/`),
   правкой копии `recipes/stand.yaml` и вызовом `render_recipe` в подпроцессе с `PYTHONPATH=<tmp>`.
   Допущение: `render_recipe` берёт `recipes/stand.yaml` рядом с модулем (или от cwd). Если разработчик привяжет путь к
   абсолютному корню репо иначе — тест покажет это через проверку `recipe.__file__` и упадёт на контроле, не на порче.
2. Имена полей камеры в YAML — как в базе: `resolution_width`, `resolution_height`, `source_target_fps`
   (спека говорит «ширина/высота»). Порча = удаление `resolution_width/height` по всему дереву YAML.
3. «Максимум» для нескольких воркеров отнесён и к `queue_wait_ms`, и к `transport_ms` (в спеке скобка стоит после обоих).
4. `pacer_late` без единого воркера -> `None`, а не 0; `pacer_late == 0` у воркера -> 0 (не `None`).
5. `shm` при пустом входе -> `None` целиком («все None»); частично заполненный `shm` не тестируется (спека молчит).
6. `write_report`: формат чисел/заголовки не пинятся. Проверяется только: имена процессов, `456`, `1097.9`/`1098`,
   префикс `1.0` для measured=1.013, слова `baseline`/`candidate` (трактовка: метка `tree` выводится словами),
   `commit` целиком. Отчёт читается как UTF-8 — если на Windows запишется в cp1251, литералы не найдутся.
7. `passport` для не-репозитория: `commit is None`; для `commit_dirty` в не-репо значение не пинится.
   `gpu is None` проверяется подменой `PATH` на пустой каталог.
8. `--help` должен содержать `8775` (допущение: дефолт виден через `%(default)s`) — вынесено в отдельный тест.
9. Импорт-тест без `winreg` берёт литеральный список модулей (passport, cpu_probe, matrix, recipe, fields, report, run_case)
   и гоняет `--help` через `runpy` как замену импорту `__main__`. `ctypes` не блокируется: на этой Windows-машине он нужен psutil.
   Импорт `run_case` предполагается безопасным (без подъёма стенда на верхнем уровне).
10. Добавлен пустой `tests/__init__.py` (как у соседних `scripts/*/tests`).

## Что я оставил открытым / ненадёжно

- Тесты ProcessCpu и самопроверки зависят от загрузки машины: соседняя сессия, жадно занимающая ядра, может дать
  busy-ребёнку < 0.95 ядра -> флаки. Допуск 0.05 взят из спеки. Не мерилось на зелёном коде — реализации нет, так что
  порог 1.0 ± 0.05 на этом ноутбуке НЕ подтверждён; первый зелёный прогон разработчика — первая проверка.
- Тест завышения (`measured > 1.10`) опирается на то, что `clock_selfcheck` считает по дельте `read_seconds()`;
  реализация, читающая абсолют один раз, тоже даст ~1.2, но на Windows-`cycles` абсолют включает старт интерпретатора.
- Тест «нет живых детей» отсеивает зомби (Linux) — реализация без `wait()` там пройдёт.
- Полночный риск: `test_report` берёт `date.today()` отдельно от вызова `write_report` (1 c окна раз в сутки).
- Break-injection не проводился (нет реализации): это стадия лида. Слабые места, которые стоит проверять инъекцией:
  `_2/_3` (перезапись старого), `max` vs `last/first` в extract_fields, `sum` pacer_late, `tolerance` (граница в обе стороны),
  корректная работа с последней `)` в parse_proc_stat.
- Не покрыто: `run_case.py`, `--tests`, `--baseline` (worktree add/remove), paths вне Windows, фактическая
  переносимость на Linux (parse_proc_stat проверен только как чистая функция).
- Тест порчи базы предполагает, что корректная реализация ОБЯЗАНА кинуть RuntimeError при отсутствии
  `resolution_*`; реализация, которая добавляет недостающее поле (`setdefault`), пройдёт проверку по YAML,
  но упадёт на этом тесте — это буква спеки, а не мой вымысел.

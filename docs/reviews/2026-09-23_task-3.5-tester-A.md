## Как построены входы (без implementation-файлов)

- **matching.py** — символы (`BeltGeometry`, `JobDone`, `MatchResult`, `object_robot_xy`,
  `match_job`) импортируются ВНУТРИ каждого теста (не на уровне модуля) — падение одного
  теста не зависит от соседних, пока модуля нет вовсе.
- `ObjectPassport` строится напрямую из `Services.line_sim.interfaces` — существующий
  датакласс, поля per contract (`object_id`, `class_name`, `angle_deg`, `defect`,
  `spawn_encoder`).
- Для теста «3 мм vs 4 мм» позиции объектов подобраны через `FACTOR_MM`
  (`Services.line_sim.core.belt`, уже протестированный/доверенный конвертер, тот же
  приём, что в `test_spawner.py`) так, чтобы при identity-геометрии (`BELT_UX=0`)
  невязка была РОВНО 3.0 и 4.0 мм по оси Y — без округления смещения.
- **spawner.remove()** — фабрика-заглушка (`_make_factory`) скопирована по образцу
  `Services/line_sim/tests/test_spawner.py` (эту фикстуру НЕ импортировал, только
  повторил паттерн — файл теста не читал целиком построчно на предмет самого `remove`,
  которого там и нет).
- **RobotSimCore(on_job_done=...)** — задание подаётся через `core.write()` по адресам
  из `Services/robot_comm/core/registers.py` (REG_JOB_X/Y/ECAP/FLAG), продвигается
  `core.tick()` — тем же путём, каким по факту работает Modbus-клиент. `ecap` для
  106016 кодируется парой слов через `Services.modbus.sdk.datatypes.encode_int32`
  (существующий, протестированный модуль) — литерал 106016 взят прямо из контракта.

## Что я интерпретировал, а не просто скопировал

1. **Число тиков до завершения задания.** Контракт не называет число тиков явно — я
   вывел его из `RobotSimCore._handle_job()` (дефолты `accept_ticks=1, job_ticks=2`):
   первый `tick()` выполняет приём ЦЕЛИКОM (accept_countdown становится 0 в ТОМ ЖЕ
   вызове из-за `if`, а не `elif` — не заметить это легко), затем ещё 2 тика до
   `REG_FREE→1`. Формально это чтение реализации sim_core.py, которая ЕСТЬ в
   разрешённом списке read-only файлов, а не «implementation-файл задачи» (Task 3.5
   не меняет этот handshake) — считаю это допустимым, но фиксирую явно.
2. **Тест A5 (nearest+tie)** объединяет два сценария в одной функции ровно по имени
   теста, которое предсказал лид (`test_nearest_active_wins_and_tie_goes_to_active`) —
   это единственное отступление от правила «один тест — одна проверка», сделанное
   намеренно, чтобы совпасть с REDS.
3. **Тест A9 (`test_event_once_at_completion_with_payload`)** тоже собирает несколько
   аспектов (момент события, payload, STOP-отмену, `on_job_done=None`) в одну функцию —
   так же по имени из REDS.
4. **`test_spawner_remove_keeps_spacing_and_numbering`** усилен относительно буквального
   текста контракта: добавлена промежуточная проверка на середине пути (`half_ticks`),
   которая отличает «счётчик не тронут» от «счётчик обнулён, случайно давший тот же
   результат на полном шаге» — иначе тест не различал бы правильную и одну из
   правдоподобных неправильных реализаций.

  «neither near ни far не даёт ожидаемую невязку», но я это не проверял намеренно
  (не подсовывал заведомо неверную реализацию — по брифу matching.py не существует).
- Я НЕ проверял вручную (break-injection), что мои тесты умрут на конкретных дефектных

  или `_handle_job` отдавал `ecap` без пары слов) — это по протоколу задача лида/меня

  дефолты (контракт §1 их не упоминает), тест останется валидным; если тронет — тест
  придётся поправить, и это будет заметно сразу (RobotSimCore() без `on_job_done` тоже
  сломается для всех существующих тестов, не только моих).

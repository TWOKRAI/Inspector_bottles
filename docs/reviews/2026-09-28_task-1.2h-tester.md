## Причина каждого красного

- **H1/H2/H3×3** — 404 `not_found`: маршруты `/api/preset`, `/api/preset/commit` вообще
  не существуют в `do_GET`/`do_POST` сегодня (`_PRESET_ROUTES` не заведена) — правильная причина.
- **H5** — `_client_for("layers")` вернул `None`: третий `DeviceHubClient` не создаётся в
  `configure()` — правильная причина.
- **H6** — в HTML от `GET /` нет ни одного элемента с id, содержащим `layer`/`rev`, ни
  кнопок с текстом «Превью»/«Сохранить» — раздела редактора в `_PAGE_TEMPLATE` нет — правильная причина.
- **H7/H8** — `scene_client.calls` пуст: страница не делает `preset.get` при загрузке и
  не шлёт `preset.commit` по клику — сегодня в `<script>` этого кода просто нет — правильная причина.
- **H4** — ЗЕЛЁНЫЙ, как и предсказано в контракте (старое поведение `/api/run` 413 и
  `belt.*` 504-без-code не меняется этой задачей).

Ни один красный не вызван опечаткой/поломкой сетапа (нет `ImportError`/`SyntaxError`/
неверного HTTP-метода) — во всех случаях `AssertionError` с наблюдаемым «маршрута/
поведения нет».

## Находки — контракт против кода

1. **Явная догадка тестера про id разметки редактора (H6-H8).** DESIGN 1.2h описывает
   раздел словами («контейнер списка слоёв, поле rev, кнопки «превью» и «сохранить»»),
   в отличие от 5.3a, где `<div id="truth">`/`<button id="btnTruthReset">` были в тексте
   контракта буквально. Тестер выбрал: id контейнера/поля rev — по подстроке (`*layer*`,
   `*rev*`, H6 ищет мягко), кнопки — по видимому тексту («Превью»/«Сохранить»), а для
   H7/H8 (реальный прогон скрипта, нужен точный `getElementById`) — конкретные
   `layer0_offset_x`, `btnPresetSave`. Разработчик либо принимает эти id, либо
   согласует переименование с лидом — тот же класс риска, который 5.3a избежал
   буквальным HTML в контракте.
2. **Догадка про форму ответа `preset.get`.** DESIGN говорит только про
   `ScenePreset.to_dict()` (= `model_dump(mode="json")`), не про обёртку команды.
   Тестер предположил `{"status": "ok", "rev": ..., "preset": {"layers": [...]}}`.
   Если реализация вернёт, например, плоскую структуру без ключа `"preset"`, H1
   (побитовое сравнение с ответом двойника — это не зависит от формы, пройдёт) всё
   равно закроется корректно, а вот H7 (`_find_key(args, "offset_px")` — рекурсивный
   поиск, устойчив к вложенности) тоже переживёт другую форму. Риск в основном
   в том, что реализация НЕ будет знать про поле `"preset"`/`"layers"`/`"offset_px": [x, y]`
   как формат, который ждёт тест, — если реальный `ScenePreset.to_dict()` использует
   другие имена полей (сверка с `interfaces.py` `Services/line_sim`, которую я не смотрел —
   вне FILES), тест может остаться красным по неверной причине уже ПОСЛЕ реализации.
3. **`pytest.mark.timeout` не зарегистрирован в этом окружении** — предупреждение
   `PytestUnknownMarkWarning: Unknown pytest.mark.timeout` при прогоне (плагины сессии:
   `anyio, asyncio, cov, qt` — `timeout` среди них нет). Маркер не ломает тест (просто
   не применяет реальный таймаут), но заявленная в CLAUDE.md гарантия «pytest-timeout
   стоит project-wide» в этом venv, похоже, не работает — H5 полагается на честный
   `time.sleep(2.0)` внутри двойника и общий wall-clock прогона, а не на маркер; реальный
   дедлайн от зависания тест не получает. Не проверял `pyproject.toml`/`.venv` глубже
   (вне FILES и вне моей задачи) — просто фиксирую сигнал.
4. **H2 «побитовое» сравнение читается как структурное** — по прецеденту `test_acceptance_5_3a.py`
   (`assert body == fake_response` после `json.loads`, не сравнение сырых байтов) —
   если лид имел в виду ДЕЙСТВИТЕЛЬНО байтовое сравнение сериализации, мои тесты это не проверяют.

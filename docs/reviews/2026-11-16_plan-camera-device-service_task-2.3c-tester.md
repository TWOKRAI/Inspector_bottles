## Вопросы лиду

1. **Форма `apply_params`.** В ACCEPTANCE (стр. 8, 11) встречаются «`apply_params {"exposure_time": 901.0}`», «`{"timeout_ms": 900}`»,
   «`{"frames": 5}`» без обёртки `params`, а стр. 2 требует `ApplyParamsArgs(params={}, x=1)` -> `ValidationError` (то есть
   лишний ключ верхнего уровня запрещён). Я понял короткую запись как содержимое `params` и везде шлю `{"params": {...}}`.
   Если имелась плоская форма — это противоречие стр. 2, нужно решение. Файл: `test_plugin_commands.py`, хелпер `_Rig.apply`.
2. **Текст ошибок вне прямо указанных.** Дословно заданы только `"поле не параметр прибора: 'nope'"`, `"поле только для чтения: frames"`,
   `"нет RegistersManager"`. Для `timeout_ms`, `trigger_managed`, неверного типа, лишнего ключа проверяю только `success is False`
   (и отсутствие `SECRET-42`), текст не пинаю.
3. **`on_device` для политики `restart`.** ACCEPTANCE задаёт `config` -> False и `live` -> True; `restart` не оговорён, не тестируется.
4. **`cmd_set_config` в базе.** `ProcessModulePlugin` даёт унаследованный `cmd_set_config`. Страж «никаких других cmd_-имён» проверяет
   только собственные атрибуты класса плагина (`vars(...)`); если «ровно 11» в 4.2a считается с учётом `set_config`, счёт стоит сверить.

## Что я оставил открытым / ненадёжно

- **Расширение сверх ACCEPTANCE:** `test_reset_stats_обнуляет_dropped_после_битого_кадра` требует, чтобы `reset_stats` обнулял и
  `dropped` (в ACCEPTANCE: «`dropped == 0`» в следующем окне, но без битого кадра до сброса). Если разработчик считает `dropped`
  не частью сброса — тест на выкидывание или правку ACCEPTANCE (решает лид).
- Тест `..._обнуляет_счётчики_и_публикует_ноль` залезает в приватные `plugin._tick_t0` и `plugin_base._TICK_S` (так сказано в
  ACCEPTANCE). Он же косвенно требует сброса `_tick_frames` (иначе `fps < 0`) — это деталь реализации, но она наблюдаема как `fps >= 0`.
- `PluginOrchestrator._on_register_update` в мою проводку не включён: `apply_params` — команда плагина, колбэк 2.4b висит на
  настоящем `RegistersManager`. Если лид хочет букву образца (`_Rig` с orchestrator), это пара строк; доказательной силы не прибавит.
- Политика `config` проверена на подклассе register'а, где `trigger_period_ms` переопределён с `apply="config"` (в базовом register'е
  поля `config` в bindings нет). При `trigger_managed=False` узел при `take_device` не пишется, так что журнал чист; если разработчик
  изменит план `take_device`, тест надо пересмотреть.
- Readonly-тест не вызывает `take_device`: подкласс с `frames` в `bindings()` и несуществующим узлом `Frames` испортил бы план записи.
  Значит, порядок «readonly до записи в прибор» проверен только без сеанса.
- Журнал `read_params` проверен двумя способами: при захвате — без шума (`get_frame` пишется постоянно), после `release_device` — по
  сырой длине `port.calls`. Сырая длина при живом захвате была бы нестабильной.
- Страж потоков — регэксп по тексту файлов, не `git grep` (до коммита `commands.py` неотслеживаем). `commands.py` включается в
  проверку только если файл уже есть; его отсутствие ловят другие тесты.
- Реальный код разработчика не запускался; зелёное на моём черновике доказывает осмысленность тестов, но не качество реализации.
- Каждый тест с живым захватом ждёт эффекта с дедлайном 5 с (`_wait`); «ничего не записано» подтверждается сторожевой правкой после
  (контроль не вакуумный), а не паузой. Возможная флаки-точка: окно ~24 мс между ответом и записью; на очень загруженной машине
  дедлайна 5 с должно хватать.

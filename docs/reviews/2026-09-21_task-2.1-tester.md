## Что я интерпретировал (нет в брифе явно)

1. `_handle_vfd` переводит RAW-регистр частоты (scale=100 по gd20_bridge.yaml) в Гц
   перед вызовом `belt.command(run, freq_hz, reverse)` — raw=0 всегда means 0.0 Гц.
2. `tick()` не меняет сигнатуру; `belt.advance(dt)` вызывается с фиксированным
   `dt=TICK_INTERVAL_S` (0.01с, импортирован из `sim_robot.py`, без pymodbus зависимости).
3. `from_enc_rate` восстанавливает старое поведение энкодера ПОБИТОВО — проверено
   вручную (python-скрипт), что при dt==tick_s накопленная сумма ровно `enc_rate*N`
   без дрейфа округления на N=1000.
4. Для `test_vfd_pulse_changes_speed` не стал полагаться на неизвестные параметры
   belt по умолчанию (`freq_max_hz`, `mm_s_at_max_freq` у `from_enc_rate`) — выбрал
   freq_hz=0.0, что даёт 0 мм/с при ЛЮБОМ freq_max_hz>0 (это предположение №4 в
   docstring файла).
5. Warning при `freq_max_hz<=0` проверяю только по уровню `logging.WARNING`
   (`caplog`), без фиксации текста/имени логгера — сообщение не задано брифом.

## Что осталось открытым / ненадёжно

- Два теста (default-belt и адресный контракт) зелёные уже сегодня — они не дают
  сигнала "реализация появилась", их RED-ценность нулевая по конструкции; ценность
  чисто регрессионная (после Task 2.1 они обязаны остаться зелёными БЕЗ изменений).
- `test_vfd_pulse_changes_speed` полагается на предположение "freq_max_hz>0 у
  belt по умолчанию" — если разработчик решит иначе (например freq_max_hz=0 по
  умолчанию до явной конфигурации), тест всё равно даст 0==0 (пройдёт зря) —
  граничный случай не отличим от "команда не сработала". Не проверял это отдельно,
  т.к. правильный belt по умолчанию с freq_max_hz=0 маловероятен и не описан в DESIGN.
- Не проверял поведение при dt, отличном от TICK_INTERVAL_S (например переменный dt
  между вызовами `advance()`) — DESIGN не описывает варьируемый шаг для этой задачи,
  вне OUT OF SCOPE (ramp/acceleration).
- Не трогал `_impl/`/реализацию — их физически нет в этом дереве (worktree на
  коммите до Task 2.1), поэтому "не читал implementation" гарантировано деревом,
  а не только честным словом.
- Contract test читает YAML напрямую (`yaml.safe_load` + путь), а не через
  `Services.modbus` парсер регистров — так проще и не тянет зависимость от
  внутренностей `vfd_comm`; если у `vfd_comm` есть свой loader с доп. валидацией
  (типы полей, scale-проверки), эта часть контракта им не покрыта — только адреса.

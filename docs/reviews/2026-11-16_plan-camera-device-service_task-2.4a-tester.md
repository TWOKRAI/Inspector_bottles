## Допущения и уточнения для лида (вопросы по интерфейсу)

1. `call(fn, timeout)` возвращает `(ok, результат)` — тест 6: `== (True, owner_id)`; при отказе/сроке/closed проверяется только `result[0] is False` (текст не фиксирован).
2. Тест 7 («call перед stop()»): ACCEPTANCE не говорит, исполнится ли `fn` (`True`) или команда получит «сеанс остановлен» (`False`). Проверяется только «ответ пришёл, кортеж `(bool, _)`, не позже возврата `stop()` + 0.3 с». Если лид хочет жёстко одно из двух — скажите.
3. `apply` вызывается из daemon-потока `_call`, а тест 4 — из двух своих потоков; ждёт «не блокирует» через join-дедлайн 4 с.
4. Строка «id потока журнала == id владельца»: id владельца берётся НЕ из кода сеанса, а как tid записи `open` журнала (порт зовёт только владелец); в тесте 4 — «весь журнал порта и SDK — один tid, не равный tid вызывающих и теста». Прямого сравнения с `session._owner` нет (приватное).
5. «ноль новых вхождений `threading.Thread|...` в session.py» (git grep) НЕ покрыт тестом. Базовая линия сейчас: 4 вхождения, все аннотации (`session.py` строки 115, 132, 213, 333). Лучше проверка лида командой, не тест.

## Что осталось открытым / ненадёжно

- Зависимость от таймеров (машина общая): тест 5 — `arm_hang(0.3)`, затем 0.05 с и два `apply`: если зависание начнётся/закончится не так (задержка планировщика > ~0.25 с), два apply не слипнутся и тест даст ложный красный. Начало зависания ловится сбросом приватного поля фейка `port._hang_s == 0.0` (опора на внутренность фейка; если автор переименует — тест 5/6/7 надо поправить).
- Тест 6: порог «срок 0.05 с -> ответ <= 0.3 с» (ACCEPTANCE говорит 0.1 с; взят запас под общую машину; баг «ждёт зависания 0.5 с» всё равно ловится, зазор ~0.2 с). Тест 7: +0.3 с вместо +0.1 с (баг «ящик не закрыт» ждёт срок 5 с — ловится с запасом).
- Тест 2: окно перезахвата наблюдается опросом раз в 5 мс при `open_delay_s=0.3`; логика окна не проверена на реальной реализации (см. выше). Тест совмещает две строки ACCEPTANCE (журнал без `restart_regrab` и окно) ради лимита <= 8: при красном различайте по сообщению assert.
- Тест 4 допускает оба исхода гонки (61 успел перезахватиться отдельно, либо слитно с 62): проверяет только `max_open_handles == 1` и итог 62 — это ровно ACCEPTANCE; слияние ловит тест 5, а не 4 (см. TRAP в задаче).
- Тест 8 использует `busy_for_s=0.3` и ждёт 0.45 с от создания фейка (реальный sleep ~0.45 с); при очень медленной машине второй `start()` мог бы всё ещё получить busy (ложный красный).
- Тест 1: прогноз лида «restart пишется как live» (запись группы без остановки) ловится по журналу (нет `stop_grabbing`) и по `param_errors`; это предположение о поведении фейка (при захвате узел периода RO), на реализации не проверено.
- Break-injection по тестам ещё не гонялся (тесты красные до кода) — «зелёный без красного под инъекцией» после GREEN обязателен.

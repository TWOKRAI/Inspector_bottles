## Пункт 1. Socket HOL

Команда (5 прогонов подряд):

    cd multiprocess_framework/modules
    PYTHONPATH=<worktree> python -m pytest router_module/tests/test_socket_channel_hol_acceptance.py router_module/tests/test_socket_channel_hol_hazards.py -q --tb=line -p no:cacheprovider

Результат в каждом из 5 прогонов: `3 failed, 13 passed in 11.7s`. Это не гонка и не таймаут 5 с: детерминированно. Текст падения 1a: «клиент A не отброшен за 5.0s (clients=2, отправлено=80)».

Реального HOL нет. `send()` держит `_write_lock` один таймаут сокета (0.5 с), затем сокет попадает в `_dead`, и дальнейшие `send()` занимают 0.000 с (probes/probe_hol.py: send №61–79 по 0.000 с, warn=1, клиент B получил 20.7 МБ).

Красное — требование «A отброшен». A остаётся в `_clients`: снимает его только выход read-loop (`_unregister_clients`), а read-loop ждёт EOF от `recv`, который должен разбудить `shutdown()`. Проба probes/probe_shut.py на этой машине:

    shutdown rdwr -> STILL BLOCKED after 3s
    shutdown rd   -> STILL BLOCKED after 3s
    shutdown rdwr (буфер забит) -> STILL BLOCKED after 3s

Docstring `send()` («shutdown будит recv») верен для POSIX, не для Windows.

Прототип 1a/1b (прогон acceptance + hazards + test_socket_channel.py 3 раза: `1 failed, 44 passed` каждый раз; единственный красный — 1c):

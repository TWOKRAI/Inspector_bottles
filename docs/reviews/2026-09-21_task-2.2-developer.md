## Две находки — ESCALATION -> teamlead (live-тесты тестера)

### 1. `test_introspect_telemetry_levels` — wrong model тестера (не мой дефект)

Тест читает `res.get("levels")` **на верхнем уровне** ответа
`drv.introspect_telemetry("robot")`. Реальная форма ответа — конверт
`{"type": "response", ..., "result": {..., "levels": {...}}}`
(подтверждено сырым дампом; везде в репо, где `introspect_telemetry` реально
используется — `probe_observability_consumer_acceptance.py:534,576,1035,1495` —
идёт через `_leaf_result(...)`, разворачивающий `result`). Данные, которые
тест ищет, **фактически присутствуют** ровно там, где их ждёт DESIGN:
`res["result"]["levels"]["state"]["plugins"]["sim_robot_host"] ==
{"encoder": 210, "belt_mm_s": 92.6, "writes_seen": 0}` — то есть мой паблишер
работает корректно, тест сам неверно разворачивает конверт. Тестового файла
не трогал (инструкция брифа) — эскалирую по арифметике выше.

### 2. `test_mjpeg_sprite_follows_belt` — x_a == x_b (23.5 == 23.5), детерминированно на 2 прогонах подряд

НЕ похоже на упомянутую тестером погрешность в 0.89px («тонкий край») — это
жёсткий, повторяемый ноль движения. Диагностика (сырой HTTP-опрос
`http://127.0.0.1:8091/`, минуя `cv2.VideoCapture`, 6 снятий с интервалом 1с
на отдельном прогоне стенда): SHA1 отдаваемых JPEG-кусков РАЗНЫЙ на каждом
снятии, а `sim.belt.encoder.value` синхронно растёт (217→847→1484→2114→2772→3381).
То есть `scene_source`/`mjpeg_sink` отдают МЕНЯЮЩИЕСЯ кадры по мере роста
энкодера — сам тракт живой. Подозреваю буферизацию `cv2.VideoCapture` на
MJPEG-потоке (`_capture_frame` не сбрасывает внутренний буфер между
`cap.read()`, известная особенность OpenCV/FFmpeg-бэкенда на live-потоках) —
НЕ ПРОВЕРЕНО до конца (не сравнивал `cv2.VideoCapture` бок-о-бок с сырым HTTP
в одном процессе из-за бюджета). Файл тестера не трогал.

## Что я интерпретировал

- **Положение спрайта — один пиксельный столбец, задний край привязки**
  (`col = round(x_px) - 1`, `x_px<=0` → невидим, `x_px` за правым краем →
  зажим к последней колонке). Это НЕ буквальная часть DESIGN-брифа, а
  необходимое следствие метода измерения тестера: диф считается против
  ЭТАЛОНА на `spawn_encoder` (позиция 0), и при любой ШИРОКОЙ полосе/переднем
  крае эталон на spawn был бы виден → любой более поздний кадр даёт ДВА пика
  диффа (опустевшее место + новое), взвешенный центр масс уезжает от формулы
  на десятки px — проверено расчётом и live-прогоном (4/4 acceptance зелёные
  именно с этой схемой, 3× стабильно).
- **`mm_s` — производная энкодера между тиками публикации**, не чтение
  `BeltDrive.mm_s` напрямую: `RobotSimCore`/`BeltDrive` не выставляют
  публичного аксессора скорости, а трогать `Services/robot_comm` — вне
  области (Task 2.1b). Побочный эффект: при команде «стоп» разница энкодера
  между тиками равна 0 → `belt_mm_s=0` естественно (подтверждено
  `test_introspect_telemetry_levels`'ного дампа: после stop он ожидался 0 —
  дамп до стопа показал 92.6, дамп после стопа не снят из-за находки №1 выше
  по тому же тесту).
- **`seed`** — минимальная реализация (оттенок фона), задел на Ф3, без
  текстур/раскладки — YAGNI по правилам проекта.

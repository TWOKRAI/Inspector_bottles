# Внешнее ревью фазы Ф8 — 2026-08-08

**Ревьюер:** внешний (Fable, свежий контекст, ревью запуском).
**Скоуп:** коммиты Ф8.1 (`657ceae6`, `f161f7fb`, `625f892f`, выборочно — закрыта с живой приёмкой)
и заход 2026-08-07 (`40ed9af8`…`a8a789a5`: Ф8.2, Ф8.3, половина Ф8.5, попутные фиксы).
**Заказ владельца:** жёсткое честное ревью решений и реализации, сравнение с индустрией,
live-прогон webcam_sketch, проверка «логи в файл + в БД + внешним потребителям»,
вердикт по развилке сшивки 8.5, go/no-go на следующую фазу.
**План:** `plans/observability-unified-routing.md` (Ф8, строки ~6591–6980).

---

## 1. Оценка и вердикт

**8.0 / 10. GO** на следующую фазу — с одним обязательным условием: дефект схлопывания
аудита при отказе стока (Major-1 ниже) чинится **внутри Ф8.5 до сшивки**, вместе с уже
записанными долгами. Блокеров, останавливающих движение, нет: дефект латентный (в
рантайме `sink is None`), но сшивка без его фикса воскресит ровно тот шторм кольца, от
которого схлопывание заводилось.

Дисциплина фазы — образцовая: посылки трёх задач подряд перепроверены репро и две из трёх
протухли; инъекции предсказываются до запуска; STATUS честен до строчки. Это ревью
подтвердило заявленное почти целиком — расхождения перечислены поимённо.

## 2. Находки

### Блокеры

Нет.

### Major

**M-1. Схлопывание повторов аудита ломается ровно тогда, когда отказывает сток документов.**
`multiprocess_framework/modules/process_module/configs/observability_audit.py:105` —
`_AUDIT_OWNED_FIELDS = {"seq","ts","repeats","last_ts","log_failed"}`. Поля
`document_failed`/`document_error` дописываются в запись **после** публикации
(`_emit_document`, строки 275–279), но в это множество не внесены → следующая идентичная
запись отличается набором ключей, `_same_condition` возвращает False, схлопывание не
срабатывает.

**Репро запуском** (10 тактов одинакового отказа подметальщика):

```
здоровый сток : ring=1  seq=1  repeats(last)=10  вызовов стока: 1
падающий сток : ring=10 seq=10 repeats(last)=1   вызовов стока: 10
```

Сценарий — дословно тот, от которого модуль сам себя документировал по `log_failed`
(«иначе повтор перестал бы схлопываться ровно тогда, когда сломался ещё и журнал»): БД
легла → подметальщик молотит каждый такт → кольцо выедается за ~8 минут, журнал получает
строку на каждый повтор, лежачая БД получает удар на каждый такт. Тест
`test_repeat_emits_one_document_not_two` доказывает схлопывание только на **здоровом**
стоке.

**Фикс:** добавить `document_failed`, `document_error` в `_AUDIT_OWNED_FIELDS` + тест
«повтор при отказывающем стоке всё равно схлопывается».

### Minor

**m-1. Заявление «60/60 при T == P» завышено.** Стенд ревьюера на реальных часах Windows
(60 приходов, `sleep(0.05)`, правило 0.05): **сетка 57/60, скользящее 31/60** (заявлено
60/60 и 33/60). Направление и масштаб подтверждены (потеря упала с ½ до ~5%), но докстринг
`_blocked_by_window` («трафик НА пределе и ниже проходит целиком») на квантованных часах
строго неверен — сам тест автора это признаёт (18/20 на синтетике). Смягчить формулировку.

**m-2. Корректность конкуренции `DocumentStore` держится на случайном дефолте, а не на
решении.** В стеке `Services/sql` WAL и `busy_timeout` не задаются нигде (grep по
`sqlite.py`/`sync_adapter.py`/`engine_factory.py` — ноль упоминаний); стенд 6×50 прошёл
300/300 только благодаря дефолтному `timeout=5s` sqlite3. При этом фреймворковый
`ObservabilityStore` WAL **включает** (проверено на живой базе: `journal_mode=wal`) —
асимметрия двух сторов одного репозитория. Задать WAL + busy_timeout явно при создании
движка documents.

**m-3. Хвост латентности `append` под конкуренцией: max 928 мс** (6 процессов × 50 записей
подряд, медиана 3.6 мс, p95 до 82 мс; под WAL max 712 мс — конкуренцию писателей WAL не
снимает). Аудит зовёт сток синхронно из пути смены конфигурации — для редких смен
приемлемо, но бюджет назвать в докстринге стоит.

**m-4. `_emit_document` собирает документ как `{"kind": "audit", ..., **entry}`** —
extra-kwarg записи с именем `kind`/`summary`/`source` молча перезапишет конверт документа.
Сегодня таких писателей нет; дешёвая страховка — класть конверт **после** `**entry`.

**Live-находка вне скоупа Ф8 (в бэклог):** `worker.pause_all` на процессе `gui` глушит и
командный насос — `worker.resume_all`/`introspect.status` после этого таймаутятся навсегда
(репро: pause_all → success, три попытки resume_all → `success=False {}`, `get_status` →
timeout; соседний `seg` отвечает). Самозапирающаяся ловушка: команду возобновления должен
обработать остановленный воркер.

## 4. Индустриальное сравнение

| Ось | Вердикт |
|---|---|
| **Иерархия имён + корень (8.1)** | **На уровне.** Точная модель logback/log4j2/.NET `ILogger`: категория → longest-prefix → корень, один эффективный порог. Снятие второй оси (scope.min_level) — движение К индустрии, а не от неё; потерянная немонотонная раскладка («INFO писать, WARNING нет») не выразима и в logback — честно названо. Реестр объявлений вместо литерала — аналог `MeterRegistry` Micrometer'а |
| **Severity и словарь OTel** | **Концептуально на уровне** (severity_number, verbosity 5–8 внутри DEBUG — по модели данных OTel Logs). Но соответствие OTel остаётся **заявленным, а не доказанным** — единственная внешняя проверка (8.6, OTLP-экспортёр) отложена владельцем, и цена отсрочки в плане названа верно |
| **Фиксированное окно vs скользящее (8.2)** | **Правильный выбор для этой роли.** Учебниковая критика фиксированного окна — пара через границу — здесь принята и оплачена вслух; для предохранителя от шторма (не для честности API-квоты) она шум. Главный выигрыш инженерный: сетка отображает абсолютное время и не зависит от разрешения часов (15.625 мс), что и было корнем бага. Token bucket дал бы то же с большей машинерией |
| **Multi-process SQLite** | **Годится при текущих темпах, но свойство должно стать спроектированным.** Индустрия: WAL + busy_timeout для многописательных SQLite; выделенный писатель — только при устойчивых сотнях записей/с. Замер: 300/300 при 6 писателях, хвост до ~1 с. Прод-прецедент в самом фреймворке уже есть — общий `observability.db` в WAL. m-2 закрыть обязательно |
| **Quality records в MES/QMS** | **Направление верное:** срок по времени per-kind (не по количеству — правильно отвергнута ротация action_log), «род без срока не удаляется», записи-события без дедупликации, append-only. До коммерческого уровня не хватает: планировщика ретеншена (сейчас `purge_expired` никто не зовёт — срок декларация), потолка/мониторинга роста БД, бэкапа, и — когда появится регуляторное требование — неизменяемости (хэш-цепочка). `ObservabilityStore` при этом сам без ретеншена растёт вечно — дать ему срок той же механикой |
| **Config-owned sink vs runtime-owned подписка** | Различие проведено правильно и уже канонизировано в кодовой базе (`register_sink_factory`, `orchestrator_class_path` vs брокер 5.11). Вердикт по развилке продолжает config-owned линию |

**Советы (по делу, без фантомов):** (1) WAL+busy_timeout в documents; (2) планировщик
`purge_expired` — тем же retention-потоком, что у логов; (3) срок хранения
`ObservabilityStore`; (4) бюджет латентности стока в докстринге аудита; (5) вернуть 8.6,
когда появится настоящий OTLP-приёмник — до тех пор словарь Ф3 считать самопровозглашённым.

## 5. Вердикт по развилке сшивки: **B** (протокол + фабрика по import-path из конфига)

**Проверка находок предыдущей сессии — все подтверждены:** (1) `ServiceRegistry` хранит
классы, не экземпляры (`service_module/registry.py:1-99` — «хранит *классы* сервисов (не
экземпляры)»); (2) пер-процессного хука старта нет — runtime-DI в `AppSpec` существует
только для оркестратора PM (`builder.py:57-83`); (3) прецедент самосшивки —
`wire_observability_store` в `process_module.py:412`; (4) прецедент фабрики —
`register_sink_factory` (`log_channel.py:1319`, строки сместились с 412).

**Решение.**

- **Где живёт точка:** бутстрап дочернего процесса во фреймворке — новый
  `wire_document_sink(svc)` в
  `multiprocess_framework/modules/process_module/managers/observability_wiring.py`, вызов
  из `ProcessModule` рядом с `wire_observability_store` (`core/process_module.py:409-424`),
  teardown рядом с `unwire_observability_store` (`:1000`). Фреймворк сшивает аудит **себе
  сам** — как уже делает со стором (прецедент 3).
- **Что в конфиге (Dict at Boundary, пиклится в `proc_dict["config"]`):** ключ в секции
  observability, например `documents: {factory: "Services.documents.wiring:make_document_sink",
  config: {db_path: ..., retention_sec: {audit: ..., verdict: ...}}}` — строка import-path +
  dict, ничего живого.
- **Что в рантайме:** бутстрап ребёнка резолвит фабрику importlib'ом (канонический
  механизм: `process_manager_module/runner/class_loader.py:23-32`; инвариант «framework не
  знает про приложение — знает строку из конфига» прямо записан в `launcher/builder.py:9`),
  зовёт `factory(config_dict)` → объект с `append(dict)`; фреймворк ставит
  `layers.audit.sink = store.append` и публикует стор процессу (например
  `svc.document_sink`) — **второй клиент** (вердикты из плагинов приложения) пишет в тот же
  экземпляр, один писатель на процесс, одна БД на систему в WAL. Sentrux-границы целы:
  статического импорта Services во фреймворке не появляется.
- **Почему не A** (generic пер-процессный хук): более широкий механизм, чем нужда — прямое
  нарушение собственного правила ADR-APP-006 («хук появляется, только если нужен сегодня И
  minimal_app бутится без него»); произвольный код приложения в бутстрапе — порядковые
  риски; и главное — аудит фреймворковый, ему сток нужен **до** того, как app-код получает
  слово. «Меньше слоёв строго лучше» — хук был бы слоем ради одного клиента.
- **Почему не C:** существующего пер-процессного шва нет (проверено кодом:
  `orchestrator_class_path` — только PM; plugin-система стартует после менеджеров и не
  покрывает процессы без плагинов).
- **Почему не D:** документы — продуктовые данные (изделие, оператор, рецепт), а sql
  вынесен в Services в Phase 4.1; переезд втащил бы SQL-стек во фреймворк — против слоёв и
  против framework-first.
- **Вход от замера конкуренции:** прямая запись из каждого процесса подтверждена (300/300,
  0 отказов при 6 писателях; прод-прецедент — общий observability.db). Выделенный писатель
  **не нужен** при текущих темпах (аудит — редкие события; вердикты — единицы в секунду)
  при условии m-2 (WAL+busy_timeout явно).
- **Оставшаяся приёмка 8.5:** (1) фикс M-1 + тест схлопывания на отказывающем стоке;
  (2) `wire_document_sink` + конфиг-ключ + один тест **реальной сборки** (там же закрыть
  долг «FakeLoggerCore игнорирует min_level»); (3) планировщик `purge_expired`;
  (4) WAL+busy_timeout; (5) живая приёмка T2/A2: смена конфига → документ в БД, «когда
  включили» отвечает командой **после рестарта процесса**; (6) вердикты как второй клиент —
  отдельной задачей с решением владельца о переносе истории action_log.

## 6. Оценка решений Ф8

| Решение | Вердикт | Почему |
|---|---|---|
| **8.1 радиус «один механизм, три пространства»** | **Согласен, 9/10** | Снят доказанный дубль, не функциональность (замер 742 обёрток / 1 call-site / 0 секций убедителен); живьём подтверждено: scopes без второй оси, `gated_metrics` объявлениями, конфиг-смена через reload с `verdict: confirmed`. Минус балл — резидуал «GUI берёт каталог импортом» остался открытым |
| **8.2 выбор C (сетка)** | **Согласен, 8.5/10** | Механизм починен, а не заклеен предупреждением; зоны сетка/детектор не перекрываются (`detect_throttle_caps` не менялся — сверено диффом); тест на интервале расхождения индекса и таймстампа — правильный ответ на урок о совпадении констант. Минус — завышенное «60/60» (m-1) |
| **8.3 нерасширение охвата + настоящий гейт** | **Согласен, 9/10** | Репро воспроизведён ревьюером независимо: три записи эмитированы, в сторе одна (`severity=error`), контроль положителен. Формулировка «допуск гейтится severity, документ не severity» — точная постановка для 8.5; честно записанный долг FakeLoggerCore |
| **8.5 (половина): плоскость в Services + sink-инъекция** | **Согласен архитектурно, 7/10** | Слои соблюдены (структурный тип, ни одного импорта Services во фреймворке), контракт с Pre/Post и 17 тестов на настоящем sqlite, `__getstate__` закрыт тестом, STATUS честен до строчки. Минус — M-1 (дефект того класса, который сам модуль документирует) и m-2/m-3 |

Архитектура конструктора от фазы **выиграла**: три реестра → один механизм объявлений
(новая метрика/группа без правки фреймворка — подтверждено живьём), у порога одна ось, у
долговечности появляется второе правило допуска структурой, а не фильтром.

## file_lock

- `_try_lock`, Windows: занят только errno 13 или 36. Проба с подменой `msvcrt.locking`: errno 13 -> `False`, 36 -> `False`, 39 (ENOLCK), 22 (EINVAL), 9 (EBADF) -> `OSError` с тем же errno. `os.lseek` вынесен из `try`.
- `_try_lock`, POSIX: `BlockingIOError` -> `False`, прочее пробрасывается. Ветка прочитана, не исполнялась (машина Windows). `flock(LOCK_NB)` на занятом файле даёт `BlockingIOError` (EWOULDBLOCK/EAGAIN); `EINTR` повторяет сам Python (PEP 475).
- `_unlock` при летящем исключении: `ValueError` с телом `boom` всплывает (тест + проба); для `KeyboardInterrupt` тоже. Без исходного исключения `_unlock` бросает `OSError` наружу, дескриптор закрыт (проба (a): `OSError 5`, `fd closed: True`).
- Если `_unlock` бросит не `OSError`, исходное исключение подменится с `__context__` — приемлемо.

Код верен (проба с подменой даёт правильные исходы для errno 13/36/39/22/9), но защиты от регрессии нет. POSIX-ветки тестами не исполняются вовсе. Fix: подменить `fl.msvcrt.locking` на бросающий `OSError(errno.ENOLCK, ...)` -> ждать `OSError`, не `False`; `OSError(errno.EACCES)` и `OSError(36)` -> `False`; для POSIX то же с `fl.fcntl.flock` под `skipif(win32)`.
2. NIT (quality) `multiprocess_framework/modules/recipe/yaml_io.py:329` (`_plain`): ветка `tuple` мертва (7 из 7 входов дают те же байты без неё). Удалить; `_kind` уже держит кортеж.

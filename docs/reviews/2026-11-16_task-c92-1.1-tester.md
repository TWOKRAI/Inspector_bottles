## Допущения и места, где критерий неясен (обязательно прочитать)

1. **`core.process_module` «НЕ импортирован» (R3) недостижимо буквально.** Проверено: `import multiprocess_framework` сам выполняет `process_module/__init__` -> `core.process_module` (в чистом интерпретаторе уже в `sys.modules`). Поэтому после П1 любое состояние «пакет `heartbeat` не загружен» в живом интерпретаторе без вмешательства невозможно. Принято: предусловие «`heartbeat`, `heartbeat.process_heartbeat`, `heartbeat.cpu_clock` не в `sys.modules`» для R3/R4/R5 создаётся ВЫСЕЛЕНИЕМ этих трёх ключей (+ `delattr(process_module, "heartbeat")`) после `import multiprocess_framework`; `core.process_module` остаётся загруженным. Следствие: R3/R4/R5 проверяют ленивый путь пакета независимо от шапки (П1), что и нужно слоям «П3 отдельно». Предусловие проверяется в подпроцессе (`precondition_unloaded`, `armed`) и ассертится в тестах.
   Без этого допущения R4 в буквальной формулировке («чистый интерпретатор, `import heartbeat`») был бы красным и после П1+П3: родитель `process_module/__init__` -> `core.process_module` -> (П1) `process_heartbeat`.
2. **R2 не выселяет модули** (ловушка плана: канарейка «как у ребёнка»). Поэтому после П1 шапка уже грузит оба подмодуля, гонку выстроить нельзя, и R2 зелёный по построению. Чтобы это не было зелёным впустую, тест `test_r2_race_armed_or_heartbeat_preloaded_by_header` требует: либо `armed` и все четыре флага перехватчиков (`a_saw_b_in_init`, `b_in_init`, `a_holds_ph`, `b_saw_a_holds_ph`), либо `header_loaded_heartbeat == [True, True, True]`. «Предусловие не загружено до действия» для R2 в брифе записано как общее правило; для R2 оно НЕВЫПОЛНИМО после П1, поэтому заменено этой дизъюнкцией — решение лида, если нужно строже.
3. **Флаг `B_blocked_seen` из repro не ассертится** (на красном коде True, на зелёном по П3 False — B не блокируется). Ассертятся только «перехватчик сработал» и исходы A/B. В `before_ph_body` ожидание B сокращено: выходим, если B завершился (`tb.is_alive()`), поэтому зелёный путь быстрый (0.5 с на фейке), а не 5 с, как в `det`; потолок остаётся 5 с.
4. **R4 «после обращения `heartbeat.ProcessHeartbeat` -> в `sys.modules`»** проверяется после выселения, т.е. на реальном ленивом пути.
5. R3 — `cv2` не импортируется (к гонке пакета отношения не имеет); в R2 `import cv2` под `try/except ImportError`, как в брифе.
6. Все подпроцессы: без `-I`, `PYTHONPATH=_REPO_ROOT`, плюс `PYTHONUTF8=1`; первым действием проверка, что `multiprocess_framework.__file__` под `_REPO_ROOT`; `timeout=60`; потоки с `join(10)`/`wait(5)`; имя «нет_такого» передано ASCII-экранированием.

## Что осталось открытым / ненадёжно

- **Зелёный путь на РЕАЛЬНОЙ реализации не проверен** (реализации нет; читать её запрещено). Зелёное доказано только на фейковом дереве, у которого механизм дедлока (eager `__init__` + `process_heartbeat -> .cpu_clock`) воспроизведён и совпал с настоящим по тексту ошибок. Реальные `process_heartbeat.py`/`telemetry.py` могут иметь побочные эффекты при повторном исполнении после выселения (проверено только на текущем коде: повторный импорт `heartbeat` после выселения идёт без ошибок). Если после П3 реальный повторный импорт `telemetry`/объявление метрик задвоится — R3/R4/R5 покраснеют по причине выселения, а не дефекта; лид увидит это в первом зелёном прогоне.
- **Опора на приватное API CPython 3.12** `importlib._bootstrap._blocking_on` (как в repro) — только для информационного флага `b_blocked_seen`; на других версиях тест не упадёт из-за этого только пока ключ не ассертится (сейчас не ассертится, но функция `blocked()` вызывается в ожидании; при отсутствии атрибута сценарий упадёт — красный с текстом, не молчаливый зелёный).
- R2 в режиме «шапка прогрузила `heartbeat`» (после П1) не доказывает отсутствие гонки при П3 — это задача R3. R2 держит только «симптом как у ребёнка».
- Мутант «`__getattr__` отдаёт `ProcessHeartbeat`, но подмодуль-атрибуты `process_heartbeat`/`cpu_clock` ломаются» (в моём фейке с П1 мутанты `__getattr__` ломали `from ..heartbeat import process_heartbeat` в шапке) на настоящем коде не проверялся; R5 проверяет `from heartbeat import telemetry`/`cpu_clock` через `fromlist`, что для ленивого `__getattr__` существенно.
- Ожидаемое время на зелёной реализации: до ~5 с на R2/R3 только если B упрётся в замок (нет); по оценке на фейке — десятые доли секунды на файл; на реальном — единицы секунд (импорт фреймворка в каждом из 5 подпроцессов, ~0.4 с каждый).
- Не вставал вопрос эскалации (ESCALATION) — блокеров нет.

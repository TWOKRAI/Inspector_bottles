## Прогон и RED-причины

Офлайн (`pytest Plugins/sim/scene_source/tests/... -q --tb=line`):
```
ModuleNotFoundError: No module named 'Plugins.sim.scene_source.plugin'
1 error during collection
```
Все 4 теста красные ЕДИНООБРАЗНО по конструкции (module-level import нового модуля — тот же
приём, что `test_f1_task12_acceptance.py` для `mjpeg_sink`).

Живой (`LINE_SIM_LIVE=1 pytest apps/line_sim/tests/test_f2_task22_live.py -q --tb=short`), один
подтверждающий прогон:
```
4 failed, 1 xfailed in 13.52s
```
- `test_state_get_encoder_grows` — `state.get` вернул `success=False`,
  `"Путь не существует: 'sim.belt.encoder.value'"`. Правильная причина: паблишер энкодера
  (Task 2.2 разработчика) ещё не написан.
- `test_vfd_stop_freezes_and_start_resumes` — падает на ТОЙ ЖЕ причине (путь не существует),
  уже ПОСЛЕ успешного `RobotClient.connect()` + `VfdClient.stop()` к живому Modbus на 5021 —
  то есть мост ПЧ↔робот сегодня уже работает (Task 1.1), красный именно и только на отсутствии
  мира энкодера.
- `test_introspect_telemetry_levels` — `levels.state.plugins` в ответе `introspect_telemetry`
  сегодня вообще не содержит ключа `plugins` (только `shm`) — нет писателя `sim_robot_host`.
  Чистая, однозначная причина.
- `test_mjpeg_sprite_follows_belt` — красный, но **с тонкой маржой**: измеренное смещение
  центроида «пока лента едет» = 0.89 px против порога >1.0 px (я поставил порог как гигиенический
  минимум, не поймал реальное движение спрайта). Сегодня `camera` использует
  `camera_service.simulator`-заглушку (не `scene_source`), и её кадры чуть шумят между вызовами
  сами по себе — RED здесь технически «по правильной причине» (сцены-спрайта, следующего за
  энкодером, нет), но граница 0.89 vs 1.0 достаточно узкая, что при иной заглушке/шуме тест мог
  бы дать ложный PASS на неверной реализации. Не переписывал порог задним числом — фиксирую как
  слабое место, см. «Что оставил открытым».
- `test_camera_alone_serves_frames` — **xfail** (не выполнялся по-настоящему): изоляция
  подмножества процессов пайплайна (camera+mjpeg без robot) потребовала бы отдельного
  фикстурного `pipeline.yaml` (аналог `apps/line_sim/tests/fixtures/state_proxy_app/` тестера
  Task 2.0) — при бюджете контекста этого прогона решил не заводить пятый файл сверх брифа и
  честно пометить xfail с причиной в самом тесте, как явно разрешил бриф.

Порты 8766/5021/8091 — свободны и до, и после каждого прогона (проверено `lsof`), осиротевших
процессов нет (`ps aux` пуст на line_sim/multiprocess_framework после теста).

`ruff check` на обоих файлах — чисто.

Остальные тесты `apps/line_sim/tests/` не запускал повторно: я не менял НИ ОДНОГО существующего

## Что я интерпретировал (не факт брифа)

- Имена конфиг-ключей `spawn_encoder`/`px_per_mm`/`stale_ms` — взял буквально из формулировки
  DESIGN брифа (лид использовал эти слова в самой формуле), не из кода — кода нет. Это МОЯ
  ставка на имена, которые впоследствии станут неформальным интерфейсом для разработчика.
- Форма доставки дельт в фейковый `StateProxy.subscribe`: обе формы, явно названные «Решением
  ведущего» плана — дельта-создание с целым dict на `sim.belt.encoder` И полистовые дельты на
  `.value`/`.mm_s`/`.t`. Использовал НАСТОЯЩИЙ класс `Delta` (не самодельный dict), чтобы не
  закрепить неверную модель контракта (память тестера: «addressing fake needs general
  dot-notation» — тот же принцип, копия реального контракта, а не самодельная фикстура).
- Обнаружение спрайта — генерический метод «диффа со кадром-эталоном» (взвешенный центр масс
  столбцов), не цвет/форма — контракт их не называет, а Out of scope прямо исключает «реальные
  спрайты» из этой задачи.
- `ctx.log_warning` — существование-якорь (`.called`), без проверки текста сообщения (память
  тестера: «negative wording assertion needs an existence anchor»).
- Live-гейт `LINE_SIM_LIVE=1` + порт `8766` — не угадал: нашёл РЕАЛЬНЫЙ прецедент в
  `backend_ctl/tests/test_probe_acceptance_app_param.py` (только это имя переменной во всём
  репозитории) и скопировал его форму (`BackendHarness` на фиксированном порту, а не через
  сабпроцесс-зонд, как тот файл — зонд не входил в разрешённые к чтению файлы, а `BackendHarness`
  такой же живой стенд, дешевле для итерации).

## Что оставил открытым / ненадёжно

- `test_mjpeg_sprite_follows_belt`: порог `>1.0 px` красный с маржой всего 0.11 px относительно
  измеренного шума текущей заглушки — некрепкий сигнал RED, годится для факта «спрайта ещё нет»,
  но реализация, которая случайно попадёт в этот же шумовой диапазон, могла бы дать ложный PASS.
  Разработчику/ревьюеру стоит перепроверить эту границу после реализации, не доверять ей вслепую.
- `test_camera_alone_serves_frames` — не выполнен по-настоящему (xfail), критерий «только camera
  → кадры, нет исключений» остаётся НЕ проверенным этим файлом.
- Имена конфиг-ключей (`spawn_encoder`/`px_per_mm`/`stale_ms`) — моя ставка, не факт; если
  разработчик выберет другие имена, тесты 2 и 3 офлайн-файла придётся поправить синхронно (не
  тихо, с объяснением, что изменилось).
- Не проверял импорт `FACTOR_MM` «из реестров, а не копией числа» статическим способом (только
  через литеральное совпадение чисел в расчёте ожидаемого px) — это доверяет числу, не месту
  импорта; принцип «не копия» из Steps плана тестом не закрыт (он и не должен — Steps вне
  чтения тестера).
- Живой прогон был ОДИН (как и предписано), не серия — обычная для RED-стадии оговорка: не
  исключаю флакийность именно `test_mjpeg_sprite_follows_belt` при повторных запусках сима
  (шум таймингов процессов).
- Не прогонял оставшиеся файлы `apps/line_sim/tests/` живьём для подтверждения «не задеты» —
  вывод сделан по факту «не менял чужие файлы», не по прогону.

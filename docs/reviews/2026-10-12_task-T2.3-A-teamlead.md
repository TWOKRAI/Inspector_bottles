## Что я истолковал, а не взял из брифа

- Порядок проверок `SC_RUN`: `E_SC_COUNT` -> `E_NO_SERVO` -> записи. Спека не задаёт место `E_NO_SERVO`.
- Порядок проверок внутри записи: R_LAST_PASS проверяется сразу после KIND, до ACTION/APARAM/зоны. Если у последней записи несколько ошибок, порядок выбран мной.
- Диапазоны APARAM: DO 1..16; SPEED_PCT 1..100 (0 -> R_APARAM); ACCEL — диапазон `P_ACC_L` (100..50000); ACCUR 0/1; DELAY_MS — весь u16; у NONE APARAM не проверяется. Спека диапазоны не называет.
- `DELAY_MS`: точка опроса mailbox/SOFT — тик конца паузы, не тик прихода. Во время паузы `TLM_MOVING=0`, `TLM_ACTIVITY=4`. `DELAY_MS=0` — без паузы.
- Рука в проверке среза: после JOINT-записи считается `P_HAND`, если `ik` дал решение. Иначе рука не меняется.
- SOFT, который ждал EXACT, на последней записи даёт `E_ABORTED`, а не DONE. Действие этой записи при этом исполняется: стоп обслуживается после действия. Это совпадает с поведением одиночного хода T2.2.
- `TLM_SC_DONE_N`: при старте 0, при успехе = `count`, при обрыве = число завершённых записей (не ноль).
- `TLM_SPD_PCT` для `JOG_STEP` — `spd_pct` или `P_SPD_JOG`. `JOG_CONT` его не меняет: скорость там в мм/с.

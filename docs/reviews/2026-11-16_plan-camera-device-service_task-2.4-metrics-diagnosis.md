# Диагностика: `regrab_ms` / `open_ms` нет в строках `metrics snapshot` (стенд 2.4)

Дата: 2026-11-16. Дерево: cam-w3 (main e925ddb85). Код не правился, ничего не коммичено. Живой прогон не запускался: хватило логов и БД стенда `stand/logs/`.

## Вывод

Дефекта в плагине `camera_device` и в дороге метрики НЕТ. `open_ms` и `regrab_ms` доехали до агрегатора и записаны в структурном снимке (`observability.db`, `kind='stats'`). Пропали они только из строки `performance.log`: эта строка режется до 2048 байт (`LogStatsChannel._format_snapshot`), отрезается хвост окна, а метрики плагина стоят в хвосте. Строка сама говорит об этом («… опущено N из M метрик, предел 2048 байт»), в отчёте стенда этот хвост не учтён. Причина находки: стенд читал `performance.log` (усечённая копия «для глаз», задача 3.4), а не структурную запись. Класс: стенд (источник замера выбран не тот) + нерекомендуемое поведение framework (усечение с головы, без приоритета), но сам предел задуман и с голосом о потере.

Чем это НЕ является (гипотезы из брифа):
- потеря записи из потока-владельца: отвергнута. В БД `regrab_ms` count 3 (окно 22:23:41) + 1 (окно 22:25:01) = 4 = ровно столько перезахватов (`policy=restart`), `open_ms` count 1 (окно 22:22:51). Все — из потока-владельца сеанса.
- «снимок выводит не все имена по фильтру имён»: нет фильтра по имени; есть бюджет байт, режет по порядку вставки серий в окне.
- «`apply` в снимке — чужая метрика»: нет, в БД `apply` с тегом `plugin=camera_device` и счётом, совпадающим с числом правок (5 в окне 22:23:41).

## Предложение (текст, не применено)

1. Стенд/процесс приёмки (основное). Метрики плагина читать из структурной записи `kind='stats'` (`observability.db`, `extra.metrics`) или `introspect_observability`, а `performance.log` считать усечённой копией: перед выводом «метрики нет» проверять хвост строки на «опущено N из M».
2. Если нужна видимость в `performance.log` (не обязательна): стенд/рецепт задаёт `stats.log_line_max_bytes` больше 2048 (схема: `statistics_module/configs/stats_config.py:91`, допустимо 0..1 048 576, 0 без предела). Для 15 серий хватило бы ~3300 байт; для стартового окна с 219 сериями (`devices` и т.п.) всё равно будет усечение.
3. Улучшение framework (по желанию владельца, не по этому поводу срочное): в `LogStatsChannel._format_snapshot` (`multiprocess_framework/modules/statistics_module/channels/log_stats_channel.py:76-111`) при усечении держать приоритет коротких имён: хвост-«опущено» сопровождать списком ОПУЩЕННЫХ имён метрик (имена, без бакетов — как делает `record_display.py:160-195` для стора). Тогда «опущено 6 из 15: regrab_ms, ...» отвечает на вопрос «какая метрика пропала» без открытия БД. Предел 2048 и его обоснование (фон ≤ ~2 МиБ/ч, `stats_config.py:88-91`) не трогаются.

## Что я оставил открытым / ненадёжно

- Живой прогон не делал (бриф: сначала дешёвое). Вывод опирается на лог и БД предыдущего прогона стенда (`stand/logs/`), а не на свежий запуск; `observability.db` читалась только на чтение.
- Проба 1 (`ctx.record_timing` из основного и из отдельного потока) слабая: `PluginContext` + `MockProcessServices` + настоящий `StatsManager` ушли в ОБХОД порта наблюдений (голос `attach_observation_port не вызывался`, в боевой сборке порт подключён). Результат `['apply', 'open_ms', 'regrab_ms']` доказывает только то, что поток вызова не влияет на запись в менеджер; путь `ctx -> порт -> hub -> снимок` проверен не пробой, а наличием записей в БД стенда (сильнее: боевая сборка, поток-владелец).
- Порядок вставки серий в окно (почему метрики плагина в хвосте) установлен по записи 253; кто именно задаёт порядок у `get_all_metrics`/агрегата, в код не лез.
- Гейт политики чисел (`NumbersGate`, `system.yaml` `telemetry.publish`, `default_enabled: false`) как причина отвергнут косвенно: `regrab_ms`/`open_ms` в БД есть, значит гейт их пропустил. `numbers_policy_dropped/throttled` не читал.
- Всё сказанное про `apply`: «в БД стоит тег `plugin=camera_device`» проверено; что это именно наш замер, а не чужой, следует из тега и совпадения счёта с числом правок; соседний чужой `apply` без тега в окнах не видел.
- Предложение 3 не оценивал по стоимости (размер строки при добавлении имён опущенных серий) и не проверял на тесты `test_bucket_cost_bench.py` / тесты предела строки.

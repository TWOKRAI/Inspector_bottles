## Ответы на вопросы брифа

### 1. `_resolve_word` / `_ensure_assembler` против спеки

- Основные порядки соответствуют п. 3–5 спеки (B1–B20 зелёные, сверено чтением `plugin.py:241-267, 354-394`).
- **Отказ `_write_word` в ветке отката — лог на каждом item** (P4): после отказа `val != _own_word` остаётся истинным.
  На каждом следующем item выходят `log_error` и `log_info` «пустое слово в регистре не принято — действует 'МИР'»:
  5 items дают 5 + 5 строк. Строка info при этом ложна: регистр остался `''` (`plugin.py:254-258` — info выходит
  без проверки результата `_write_word`). Путь сейчас скрытый: `update_field` поля `str` без правил отказать не может.
  Ветка — контракт спеки п. 2.
- Слово с порта, нормализуемое в текущее (P5a): в регистре сырое «мир», ячейки сохранены, строк смены 0. Так задумано.
- `word_source` меняется во время работы (P5b): `''` — порт игнорируется; `signal_3` — работает, журнал называет
  `порт signal_3`. Так задумано.
- Запись того же сырого значения (P5c) — не событие: ограничение (д).
- Повторный `configure` (P5d) затирает слово с телефона значением из YAML (`base.py:1490-1492`). В работе пути нет:
  `_do_configure` только из IDLE. Поведение было и до C-37.

### 2. Реальная цепочка

- Цепочка с C1 расходится только в том, что спека и так не покрывает: пикл, `chain_queue`, поток.
  `DataReceiver._build_item` (`data_receiver.py:517-550`) переносит ключ `signal_2` как есть.
  `InspectorManager` без `total_regions` отдаёт item сразу (`inspector_manager.py:56-60`): батч из одного item, как в C1.
  `set_config` в процессе layout регистрирует первый плагин с `register_class`, это `word_layout`
  (`base.py:1681-1693`, рецепт `:307`). Значит, путь GUI `set_config` попадает в нужный регистр.
- Поток pipeline пишет в управляемый регистр одновременно с `register_update` — безопасно, проверено.
  Откат `apply_values` срабатывает только на исключении. Для `target_word: str` исключения нет, откат не исполняется.
  Копия и замена `__dict__` в pydantic-core идут под GIL без вызова Python: у схемы регистра только внешний
  after-валидатор модели, правил полей нет. P2: 20000 записей при `setswitchinterval(1e-6)` — 0 потерь, своих и чужих
  полей. P1: 3000 записей обработчиком против 275 циклов pipeline — исключений нет, все `success`, итог согласован.
  305 и 211 строк смены показывают, что записи реально перемежались.
- README (а) подтверждено (P3a): внешняя запись между `update_field` порта и `_own_word = w` принимается на следующем item.
- README (б) подтверждено (P3b), но описано не полностью. P3c: оператор очистил слово и сразу ввёл «РИМ». Запись
  отката `_write_word(_own_word)` затирает «РИМ»: обработчик ответил `success`, в журнале «РИМ» нет. В (б) названа
  только запись порта.

### 3. Качество тестов

- Ветку отказа (спека п. 2) не проверяет ни один тест: мутант MJ зелёный.
- Сырое значение в регистре (спека п. 4) не закреплено: мутант MK зелёный. Во всех тестах слово порта заглавное.
- H2: его проверка `norm(target_word) == word_norm` следует из устройства кода. Последний пустой item сводит регистр
  и раскладку при любой реализации, которая перечитывает регистр. Поэтому I1, I2, I12, ML и MN оставляют H2 зелёным.
  Пользу H2 приносит только как smoke «нет исключений». H1 и H2 не доказывают, что записи перемежаются: писатель
  мог закончить до цикла, утверждения об этом нет. H2 оставить как smoke. Свойства (а)/(б) закрепить
  детерминированными крючками вокруг `_write_word`, как P3a/P3b. Тест по P3a убьёт ML: источник «ЛЕС» должен
  быть `регистр`.

Источник investigator — тот же: `introspect_status(processor).workers.pipeline_executor.cycle_duration_ms` (`investigator/stand5c.py.txt:165-172`), шаг ≈ 2 с. Сравнение шагом 1 с и каждым вторым отсчётом (≈ 2 с) на одном прогоне:

### 5.8a — `plugin_ms` плагина `database` против цикла storage
- **Находка в спеке:** `introspect_plugins` времени плагина не отдаёт (только имя/категория/манифест, P1). `plugin_ms` — в `introspect_telemetry(storage).levels.state.plugin_ms.database` (EMA α = 0.1, `plugin_runner.py:200`; публикация мимо гейта, `process_heartbeat.py:1475`). Спеку `task-5.8.md:78` поправить. В P2 мой фильтр ключей терял лист `database` (дефект зонда, исправлен) — число только из P3.
- P3: медиана EMA `plugin_ms` = 1.1 мс, медиана `cycle_duration_ms` storage = 0.98 мс → доля медиан 112 %, формально ≥ 30 % (эскалации нет).
- **Но правило «доля медиан» к узкому месту слепо.** Ряд EMA: обычно 0.6–1.2 мс, и регулярно скачки 9.2 / 12.3 / 14.1 / 14.7 / 14.9 / 15.0 / 16.7 / 23.5 мс. Скачок EMA с 0.8 до 23.5 при α = 0.1 — это один вызов ≈ (23.5 − 0.9·0.8)/0.1 ≈ 228 мс. `cycle_duration_ms` — длительность последнего цикла, медиана их не видит.
- Причина по коду: при заполнении буфера `process()` сбрасывает пачку **в потоке исполнителя** (`Plugins/io/database/plugin.py:127-133`), сброс — `execute` + `commit` на строку (`:158`). Поток `db_flush_worker` (`:99`) сбрасывает только по таймеру.
- Следствие: исполнитель storage — 33–90 циклов/с при входе ~100; `data_receiver` storage — `lag_dropped_items` 184 (P2) и 209 (P3) уже через 10 с после ready.
- **Посылка DESIGN 5.8a подтверждена** (узкое место — коммит в потоке исполнителя), но доказывает её распределение (скачки), а не доля медиан. Предложение для спеки: критерий зонда — «есть вызовы ≥ 10 × медианы цикла» по ряду EMA или по максимуму, а не «доля медиан < 30 %».

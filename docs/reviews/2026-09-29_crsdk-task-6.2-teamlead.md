## Устройство сессии

- Одно открытие на `start()`, один поток захвата на открытие, своё `threading.Event` на открытие.
- Прибор отпускает (`stop_grabbing` + `close`) **только поток захвата**, в `finally` после выхода
  из цикла. `stop()` поднимает событие и ждёт `timeout + timeout_ms/1000`; сам ничего не закрывает.
  Отсюда: close ровно раз на открытие, и никогда — под идущим `get_frame`.
- Отказ на `start_grabbing` закрывает handle в `start()` (поток ещё не создан).
- Два замка: `_life` сериализует start/stop (SDK-вызовы открытия идут под ним), короткий `_lock` —
  состояние и счётчики; `stats()` не ждёт медленного `EnumDevices`.
- `on_error` зовётся вне замков; его исключения ловятся и логируются (`logging`, не фреймворк).

## Что я интерпретировал, а не выполнил дословно

1. DESIGN: «stop() … then stop_grabbing + close, guard with a lock/flag». Сделано иначе: закрывает
   только поток; `stop()` только ждёт. Причина — при истёкшем join закрыть из `stop()` значит закрыть
   под `get_frame`; флаг оказался невесомым (инъекция D).
2. Исходное состояние — `"stopped"` (контракт молчит). `stop()` из `error`/`busy`/`not_found` → `"stopped"`.
3. Любое исключение `get_frame` (не только `SdkError`) идёт в счётчик «подряд» — чтобы поток не умер молча.
4. Каждая одиночная ошибка `get_frame` уходит в `on_error` (не только итоговая третья).
5. Сбой `enum_devices` (нет DLL, `SdkNotFoundError`) → `start()` = False, `state == "error"`, без исключения.
6. Не-`E_ACCESS_DENIED` ошибка `open`/`start_grabbing` → `state == "error"`.
7. `stop()` при зависшем дольше дедлайна `get_frame`: возвращается в срок, `state == "stopped"`,
   прибор закроет поток позже; повторный `start()` до этого — False (второе открытие поверх живого handle).
8. `decode_image` для mono8 возвращает копию (`frombuffer` над bytes — только для чтения).
9. `text` кода: `chCode[:nLen]` — c_char-массив обрезает на первом NUL.

## Что осталось открытым / ненадёжным

- Живой прибор не трогал (вне объёма): поведение `stop()` на настоящем SDK, реальное время
  `CloseDevice`, и уважает ли SDK свой `timeout_ms` — не проверено. Дедлайн `stop()` держится ровно на этом.
- Если `get_frame` на железе зависнет навсегда, поток и handle не освободятся никогда; `stop()` честно
  вернётся, но «прибор свободен» тогда ложь — сообщение только в `last_error` и лог (не в `on_error`:
  колбэк, вызвавший `stop()`, взял бы `_life` повторно).
- Бинарный код с NUL внутри обрежется на первом NUL (`chCode` как c_char). Для QR с текстом — не проблема.
- `interfaces.py` теперь тянет cv2/numpy при импорте — всем потребителям, включая TCP-плагин.
- Проверка «DLL не грузится при импорте interfaces» — слабая (смотрел `sys.modules`); настоящая —
  тест слоя `sdk/` на ленивую загрузку, он зелёный.
- Гонки под GIL тестами не доказаны: hazards — детерминированные сценарии (ворота-Event), шторм потоков не гонял.
- Инъекции против слепого набора делал только E; полная матрица — за лидом.

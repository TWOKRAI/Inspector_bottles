## ВАЖНОЕ РАСХОЖДЕНИЕ С БРИФОМ (проверено, не догадка)

REDS в брифе ожидал `ModuleNotFoundError for Services.line_sim`. Фактически —
`ImportError` (не `ModuleNotFoundError`). Причина воспроизведена: FILES требует
создать `Services/line_sim/tests/__init__.py` ДО того, как появится
`Services/line_sim/__init__.py`. Как только на диске появляется
`Services/line_sim/tests/`, Python (PEP 420) резолвит `Services.line_sim` как
**implicit namespace package** — он "существует" (`import Services.line_sim` не
падает), но в нём ничего не определено, поэтому `from Services.line_sim import X`
падает с `ImportError: cannot import name 'X' ... (unknown location)`, а не с
`ModuleNotFoundError`. Проверено командой:
`python3 -c "import Services.line_sim; print(Services.line_sim.__path__)"` — импорт
проходит, путь — namespace-path без файла. Это неизбежное следствие требуемой
структуры FILES, не ошибка тестового файла: как только teamlead создаст
`Services/line_sim/__init__.py`, обычный пакет затенит namespace-пакет и все
тесты станут падать уже по реальной логике модуля, как и задумано.

По букве ACCEPTANCE ("all collected tests fail on import of Services.line_sim, 0
syntax/collection errors of your own") критерий выполнен: 0 collected, 1 error,
ошибка — именно на импорте `Services.line_sim`, не в синтаксисе моего файла. Но
REDS explicitly обещал другой класс исключения — называю это отдельно, честно,
как измеренное несоответствие, а не как факт мимо брифа.

## Все предположенные сигнатуры (сведены в один блок в начале файла теста)

- `ObjectPassport(object_id, class_name, angle_deg, defect, spawn_encoder, layer_params={})`
  — kwargs-dataclass; `layer_params` добавлен мной под AC 3.1a, имя поля не дано планом.
- `LayerSpec(name, mode, sprite_source, offset_px=(0,0), angle_deg=0.0, scale=1.0,
  augment=None, defect_probability=0.0)` — **`defect_probability` — ДОГАДКА об имени
  поля**, план называет только "вероятность" у defect-слоя без имени атрибута.
  `sprite_source` — ndarray ИЛИ zero-arg callable (план явно разрешает оба).
- `LayerAugment(offset_x_px, offset_y_px, angle_deg, scale, hue_shift_deg)` — по Fields.
- `LayeredObject(passport, layers, rng)` — **вся выборка аугментации/дефекта в
  `__init__`**, `.render()` БЕЗ аргументов, идемпотентен (кэш). Это осознанное
  расхождение с исходной сигнатурой `render(rng)` из Files Task 3.1 — сам план 3.1a
  прямо требует её пересмотреть под свойство "один раз при создании". Если
  реализация сохранит `render(rng)`, мои вызовы `obj.render()` упадут `TypeError`
  (missing positional argument) — сигнал для teamlead, не архитектурная ошибка теста.
- `obj.passport.layer_params[layer_name]["offset_x_px"]` — ключи словаря = имена
  полей `LayerAugment` — ДОГАДКА, план не даёт точную форму.
- `ScenePreset.from_dict({"layers": [...]})` — форма словаря целиком придумана мной
  (план описывает состав пресета прозой: "каталог классов, диапазон углов, список
  слоёв-дефектов + вероятности", но не JSON-схему). `sprite_source` внутри dict/YAML —
  строка (path/id), НЕ ndarray — отдельное допущение от прямой Python-конструкции
  `LayerSpec` в остальных тестах.

## Что истолковал, а не выполнил буквально

- AC 3.1 "LayeredObject с ОДНИМ слоем и angle_deg=90 даёт РАЗНЫЙ результат" и AC 3.1a
  "у объекта" — истолковал `angle_deg=90` как **`ObjectPassport.angle_deg`** (поворот
  объекта целиком), а не `LayerSpec.angle_deg` (поворот слоя относительно объекта).
  Обоснование: Pre-условие `LayeredObject.render()`, упомянутое в Files ("все слои
  одного паспорта имеют согласованный angle_deg"), и то, что для одиночного
  симметричного маркера поворот СЛОЯ на месте не сдвинул бы центроид вообще, а тест
  должен быть наблюдаемым.
- "Замена базового варианта" дефект-слоем (AC defect_probability) истолкована как
  **визуальное перекрытие по z-order** (defect рисуется поверх static на той же
  позиции), не как переключение паспортного поля `passport.defect` — это осознанно,
  т.к. привязка вероятности к паспорту — контракт Task 3.3/спавнера, не Task 3.1.
- Для теста "поворот CCW" и "offset_px" использую метод **вектор якорь→маркер внутри
  одного кадра**, а не абсолютные пиксельные координаты — так тест не зависит от
  того, как именно канва объекта расширяется/кадрируется при повороте (это деталь
  реализации, которую план явно оставляет открытой: "канва расширяется... а не
  обрезает").

## Что оставил открытым / ненадёжно

- **Класс исключения RED** — `ImportError`, не `ModuleNotFoundError`, как объяснено
  выше (структурное следствие FILES, не ошибка теста).
- `test_import_has_no_heavy_optional_deps` — слабая проверка (`sys.modules`
  order-dependent: если ЧТО-ТО ДРУГОЕ в тестовой сессии уже импортировало torch
  раньше, тест ложно упадёт даже на правильной реализации). Реальная проверка
  "нет обязательной зависимости" — это разбор `pyproject.toml`/`import` графа, не
  сделано здесь.
- `test_augment_angle_range_seed_determinism` (seed=1 vs seed=2 различны) —
  теоретически не 100% гарантия: если оба сэмпла `rng.uniform(-30,30)` случайно
  совпадут для разных seed, тест ложно упадёт на правильной реализации. Вероятность
  для float uniform с разными seed практически нулевая, но не строго доказана.
- Все геометрические тесты (`offset_px`, `augment offset`, `CCW`) НЕ запускались
  против реальной реализации (её ещё нет) — верны только "на бумаге" по формуле
  `cv2.getRotationMatrix2D`, взятой из докстринга `compose.py`. Валидация — только
  break-injection лида после того, как teamlead реализует модуль.
- Точное имя поля `defect_probability` и форма `layer_params`/dict-схемы `ScenePreset`
  — прямые догадки (см. блок выше), teamlead может выбрать другие имена; тесты
  придётся тогда поправить, сама acceptance-логика (границы 0.0/1.0, round-trip)
  останется в силе.
- Файлы `Services/line_sim/README.md` / `STATUS.md` / `DECISIONS.md` пока не
  существуют (создаст teamlead per module-contract) — `test_module_docs_present`
  сейчас падает вместе со всеми остальными на общей `ImportError`, отдельно не
  проверялся на реальных файлах.

## Тесты — имя / RED-или-guard / что закрепляет

1. `test_joint_move_never_leaves_zone` — **RED**. Ход (-250,350)->(-450,-150)
   (боевые дефолты, дословно из брифинга): каждый тик обязан проходить
   `geometry.check_point`. Падает:
   `нарушения: [(-355.8, 85.4, -75.0, 0.0), (-361.4, 71.5, ...), (-367.0, 57.5, ...)]`
   — сегодняшний JOINT идёт по прямой в Cartesian и вылетает за угловой сектор
   [-165,165]° (это и есть баг, который чинит T2.J).
2. `test_joint_path_is_curved_not_chord` — **RED**. Максимальное отклонение
   тик-поз от прямой хорды start->target обязано быть >20мм (независимо
   пересчитано через `ScaraModel()` до написания теста: реальное отклонение при
   суставной интерполяции доходит до ≈814мм на этой паре точек). Падает:
   `получено 0.06мм` — прямое доказательство, что сегодня путь идёт РОВНО по
   хорде (в пределах шума округления регистров 0.1мм).
3. `test_home_uses_joint_path` — **RED**. Старт (-250,350), HOME. Тест сначала
   независимым оракулом (`geometry.check_point`, без обращения к sim_core_v2)
   доказывает, что прямая хорда start->home действительно покидает зону — эта
   проверка прошла (не упала), сама предпосылка подтверждена. Основная
   проверка падает: `нарушения: [(2.0, 93.4, -59.0, -45.8), (12.5, 82.7, ...),
   ...]` — прямая ныряет ближе r_min=100мм к оси J1 (r≈93 на первом
   нарушении), сегодняшний HOME идёт по той же прямой.
4. `test_joint_ticks_match_timing_contract` — **guard**, GREEN сейчас.
   Тайминг (`path_len/speed`, `MAX_STEP_MM`, `TICK_INTERVAL_S`) не меняется
   T2.J по брифингу — литерал посчитан в тесте из `P_SPD_L`×`P_SPD_DEFAULT`,
   `spd_pct=0` явно бьёт по дефолтной скорости.
5. `test_joint_final_pose_equals_target` — **guard**, GREEN сейчас (после
   правки бага теста — см. «что я оставил открытым»). Финальная поза = цель
   (0.1мм) — не меняется T2.J.
6. `test_joint_rz_reaches_target_exactly_and_monotonic` — **guard**, GREEN
   сейчас. RZ=J1+J2+J4 — сумма трёх ЛИНЕЙНО интерполируемых суставов
   остаётся аффинной функцией прогресса хода, как и сегодняшняя прямая в
   Cartesian (которая тоже линейно интерполирует RZ) — монотонность и точное
   прибытие математически совпадают до и после T2.J, поэтому это регрессионный
   якорь, а не новое поведение.
7. `test_ik_none_falls_back_to_straight_line` — **guard**, GREEN сейчас.
   Фейковая модель (делегирует всё в реальную `ScaraModel`, кроме `ik` — всегда
   `None`) проверяет фолбэк T2.J на прямую в Cartesian. Сегодняшний код вообще
   не обращается к `model.ik` для интерполяции пути (интерполирует по прямой
   безусловно), поэтому поведение с этой фейковой моделью неотличимо от
   сегодняшнего — GREEN уже сейчас, станет РЕАЛЬНОЙ проверкой фолбэка только
   после T2.J (тогда без фолбэка тест был бы RED).
8. `test_line_move_stays_straight` — **guard**, GREEN сейчас. LINE не меняется
   T2.J (брифинг: «LINE ... stay straight Cartesian — unchanged»).
9. `test_hand_change_during_joint` — **guard**, GREEN сейчас (после
   переработки сценария — см. ниже). PARAM_SET P_HAND на другую руку +
   скромный JOINT-ход (+50мм по X у дома) — все тики в зоне, TLM_HAND
   становится новой рукой при прибытии. GREEN уже сейчас (маленький ход у дома
   не пересекает сектор даже по прямой), регрессионный якорь на смену руки.

## Что я интерпретировал, а не следовал дословно

- **MODE не был указан явным заголовком** ("MODE: red | regression" отсутствует
  как отдельная строка) — по CHAIN/DESIGN/FILES/REDS и роли (`before developer`)
  однозначно RED; трактовал как RED (см. memory
  `feedback_freeform_brief_without_mode_header`).
- **`test_hand_change_during_joint` (REDS помечен «RED or guard, state which»,
  без конкретных координат) — я САМ выбрал координаты и в итоге пересмотрел их.**
  Первая попытка — та же пара пересечения сектора (-250,350)->(-450,-150), но
  ЦЕЛЬ через `ik(target, hand=0)` (P_HAND сменился на противоположную от старта
  руку TLM_HAND=1). Независимый расчёт через `ScaraModel` ДО написания теста
  показал: суставная интерполяция с разными руками на старте/цели для ЭТОЙ пары
  точек САМА выходит за r_max≈600мм (82 нарушения из 201 точки сетки) — то есть
  даже ПОСЛЕ T2.J этот конкретный сценарий небезопасен из-за огромного скачка J2
  при смене конфигурации локтя. Это не мой тест сломан — это свойство
  ЗАДАННОЙ геометрии (я его не выдумал, дважды пересчитал независимо). Раз
  DESIGN не давал точки для этого теста, я заменил их на скромный ход у дома
  (+50мм X), где смена руки безопасна на сетке 201 точки (0 нарушений) — тест
  стал GUARD, а не RED. **Открытый вопрос ведущему**: комбинация «пересечение
  сектора + смена руки» с точками из брифинга технически невозможна безопасно
  при буквальной («длинной») линейной интерполяции суставов без учёта
  wrap-aware кратчайшего пути — это может быть находкой для разработчика/ревью,
  не решение тестера.
- **`test_joint_rz_reaches_target_exactly_and_monotonic` помечен «RED or guard,
  state which»** — доказал аналитически (сумма трёх линейно интерполируемых
  суставов остаётся аффинной по прогрессу, как и сегодняшняя прямая) и
  эмпирически (тест зелёный на сегодняшнем коде), что это guard, не RED.
- **DESIGN не давал конкретных z/rz для точек пересечения** — выбрал z=-75.0
  (середина [-150,0]), rz=0.0 (нейтрально, изолирует XY-геометрию); проверил
  оба выбора через `check_point` — обе точки валидны индивидуально.
- Читал `sim_core_v2.py` целиком как read-only reference (разрешено брифингом
  явно: "Read-only references: ... sim_core_v2.py (public surface...)") —
  реализация T2.J в этом дереве ЕЩЁ НЕ существует (ворктри на 6bec0ae1, до
  T2.J), поэтому сам файл на момент чтения содержит ТОЛЬКО текущее (баговое)
  поведение — слепота к T2.J обеспечена деревом, не нарушена.

## Что я оставил открытым / ненадёжным

- **Нашёл и исправил баг в собственном тесте** во время первого прогона:
  `test_joint_final_pose_equals_target` сравнивал `core.read(REG["TLM_X"])`
  (сырой u16) напрямую с `mm(CROSS_TARGET[0])` (знаковое значение) без `s16()`
  — для отрицательного X это ложный RED (`61036 != -4500`, оба на самом деле
  означают -450.0мм). Исправлено, перепрогнано, теперь честный GREEN.
- **Порог 20мм в `test_joint_path_is_curved_not_chord`** — очень консервативен
  относительно независимо посчитанного ожидаемого отклонения (≈814мм для этой
  пары точек), выбран с большим запасом умышленно; если разработчик применит
  wrap-aware (кратчайший путь) интерполяцию суставов вместо буквальной линейной
  (что дало бы гораздо меньшее физическое отклонение, а не 814мм) — порог 20мм
  всё ещё должен устоять, но я это не проверял на альтернативной реализации,
  только на прямом соответствии дословному DESIGN («linearly from ik(start)
  to ik(target)», без упоминания wrap-aware).
- **`test_hand_change_during_joint` ослаблен относительно REDS-намерения** (см.
  выше) — не пересекает сектор, значит НЕ ловит регрессию «смена руки внутри
  ломающего сектор хода», только «смена руки не ломает обычный ход». Считаю
  это правильным решением при данных ограничениях геометрии, но это сужение
  покрытия относительно первоначального REDS-пункта, и решение принято мной, не
  ведущим — стоит подтвердить.
- **Не проверял** поведение при `spd_pct` ≠ 100/0 для суставного пути (только
  timing-guard использует spd=0), и не писал property-based тест (Hypothesis)
  на класс входов «любая валидная по зоне пара точек» — DESIGN дал ровно один
  конкретный сценарий, тестов от него хватило для приёмки; более широкое
  property-покрытие (напр. «suставный путь всегда в зоне для случайной валидной
  пары точек, если исходная хорда её нарушает») осталось за рамками этого RED.
- **`_assert_straight_chord_leaves_zone`** сэмплирует хорду 101 точкой — не
  доказательство «для ЛЮБОЙ точки сегмента», просто плотная сетка; для этой
  конкретной пары дала явное нарушение (`hits > 0` прошло), этого достаточно
  для доказательства предпосылки, но не строгое доказательство супремума.
- **`inject_motion_fault`/стоп-плоскость/FAULT** не пересекались с этим RED
  (вне REDS этого таска) — не проверял, ломает ли что-то из T2.J их
  (маловероятно, но не проверено мной).

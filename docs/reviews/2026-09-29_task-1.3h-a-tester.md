## Что интерпретировал, а не следовал (двусмысленности контракта)

1. Имя метода не закреплено (`cmd_preset_layout` — догадка по идиоме). Вызов идёт только через `plugin.commands`;
   не-dict в G — через тот же map без `dict(data)`.
2. `canvas_px`: закреплена только форма (два положительных int); значение не закреплено (что такое «холст» — не сказано).
3. `center_px`: числа — int или float не закреплено; допуск ±1. Тип элементов не проверяется.
4. Поза объекта: угол объекта в контракте не описан. Фикстура ставит `angle_range_deg=(0,0)`, чтобы поза не влияла;
   поведение при ненулевом объектном угле не закреплено.
5. `class://`-слой: размер класса-спрайта не закреплён (фабрика может масштабировать); закреплён только `center_px≈[0,0]`.
6. `seed`: невалидные значения (`-1`, `True`, строка) контрактом не описаны — не тестировались; `bad_request` для
   них не требуется, но и не запрещён. Так же `seed` как ключ отсутствует в проверках G.
7. Порядок RGBA в PNG: декодирую как BGRA через cv2; «RGBA PNG» из брифа понят как 4 канала с альфой (проверено `shape[2]==4`).
8. Тело запроса в I — < 4096 байт; потолок тела маршрута layout контрактом не задан (общий 4096 или 256 КБ как у commit?)
   — не закреплён, не проверялся.
9. `class_name` при layers-only пресете (без `catalog_dir`) — не закреплён; фикстура всегда с каталогом.
10. Два критерия брифа объединены в один тест (C: размеры + направление; D: номинал + детерминизм; I: 4 ветки) —
    как в списке REDS; при провале одной ветки следующие не выполняются (кроме G, где ошибки собираются списком).
    Разработчику: после зелёного первого провала могут вылезти следующие — это ожидаемо.

## Что оставил открытым / ненадёжно

- Положительные ветки A-F ни разу не выполнялись против реальной реализации: допуски ±1 и ожидаемые размеры
  подтверждены только независимыми контролями (пункты 1, 3 выше), не прогоном `preset.layout`. Возможен ложный красный
  на верно реализованной команде, если реальный движок округляет иначе (наиболее вероятно — размер после `rotate_expand`:
  для 40x20 при 90° движок даёт 21 в ширину, допуск ±1 это покрывает, но ±0 не покрыл бы).
- D слаб к реализации, применяющей ТОЛЬКО часть augment: закреплены offset/scale/angle, но не `hue_shift_deg`.
- E проверяет заливку по непрозрачным пикселям целиком; частичную заливку (края) диск 60x60 без антиалиасинга не ловит.
- F: два класса и 20 сидов — вероятность ложного красного на верной реализации ≈ 2·2^-20 при равномерном выборе;
  если выбор класса по seed детерминирован «первыми N сидами -> один класс», тест упадёт, хотя контракт это не запрещает.
- В G сообщение об ошибке не проверяется на отсутствие утечки путей (в отличие от `test_client_path_outside_roots…`
  для preview) — контракт про это не говорит.
- I: двойник синхронный и не исполняет `timeout=`; реальный отказ транспорта смоделирован ответом `{"status":"error","message":"timeout"}`
  (форма из `Plugins/hub/device_hub/client.py`), настоящего таймаута нет.
- Не прошёл break-injection: пометки для лида — какие свойства кажутся хрупкими: сортировка слоёв (A), знак Y (B),
  направление поворота (C), применение augment (D), заливка (E), независимость class_name от seed (F).
- Отдельный побочный след: одна моя контрольная выборка случайно создала каталог в `data/` рабочего дерева
  (был внутри REPO_ROOT, поэтому «вне корней» вернул ok) — каталог удалён, `git status` чист, кроме двух новых файлов.

## Воспроизведение (CTO, шлюз light)

Проба ревьюера: во время `topology.apply`, который убирает только `slow`, `in_transition(other)` = `True`; 64 relay в
`other` приняты; `process.stop other` → `{'success': False, 'error': 'executor_busy'}`; CM пишет одну строку
`Command 'process.stop' failed: executor_busy`. Базис порядка: R8, R9, H11 — `3 passed`.

## 1. Вариант (д)

Один FIFO; `max_pending = L_cap + T_cap`; шлюз `_TransitionGate` отказывает T сверх `T_cap` тем же `executor_busy`.

- Порядок: одна очередь — семантика T/L на одной цели прежняя (R8/R9). (а) меняет порядок и заводит вторую очередь со
  своим потолком — больше механизма, слабее гарантия.
- Голодание: при `T_pending ≤ T_cap` у L всегда ≥ `L_cap` мест — по построению. (в) только снижает частоту (64 relay в
  `slow` при стопе `slow` дают тот же отказ `process.stop other`); ключи diff на подаче неизвестны — улучшение потом (О4).
- Слои: счётчик в существующем шлюзе по образцу `_LifecycleSubmit` (`process_manager_process.py:4641-4683`: +1 под
  `_routing_lock` до подачи, −1 в `finally` вокруг `reply`). `KeyedExecutor` классов не знает; (б) тащит политику PM
  в `worker_module` и трогает API полосы Р2.
- Следующие задачи: 1.9c — свой исполнитель, не затронут; 1.11 удлиняет переходы → копится T, отказ получает только T,
  L защищён по построению; Р2 — `register_command(executor=)` и API исполнителя без изменений.
- Проверка на приёмке: резерв T — check-and-increment под `_routing_lock`; счётчик T отдельно от счётчиков перехода
  `_LifecycleSubmit`; отказ шлюза — через тот же `reply` (CM пишет свою одну WARNING); оба потолка — явные константы PM,
  `max_pending` в `create(...)` явно. `T_cap` пока литерал 64; число — владельцу после S3, в замер включить
  `telemetry.broadcast` (тоже T, `targets="all"`).

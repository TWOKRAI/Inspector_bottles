## Места, где контракт был неоднозначен — что зафиксировано и почему

1. **Live-тест: первая версия была vacuous RED.** Изначально live-тест утверждал
   `success is not True` — это тривиально верно для ЛЮБОЙ незнакомой команды и не
   пинит будущий позитивный контракт (тест прошёл бы даже при случайно неверной,
   но "не совсем success" реализации). Переписан на позитивные утверждения
   (`success is True`, `names == ls *.yaml`, `error == "conflict"`, `apply` — dict)
   — теперь падает по-настоящему и станет осмысленным acceptance после GREEN.
2. **Live-тест: пункт "restart" предсказанного имени опущен.** Полный
   acceptance-пункт плана — "после рестарта бэкенд стартует с X" — не реализован
   в этом заходе (второй цикл boot/stop поднял бы стоимость теста и время сверх
   бюджета этого RED-прохода). Тест назван по предсказанному REDS-имени
   (`..._restart`), но рестарт не проверяет — **несоответствие имени и тела,
   осознанное, не молчаливое**. Если GREEN-исполнитель или ревьюер сочтёт это
   критичным для acceptance — отдельный live-тест на restart нужен отдельно.
3. **Live-тест: где хаб резолвит `recipes_dir`/манифест — неизвестно.**
   `service.py` docstring говорит "из манифеста, `recipes:`" (ключ уже есть в
   `AppManifest` и в `multiprocess_prototype/app.yaml: recipes: recipes`), но
   `BackendHarness`/`build_headless_launcher` НЕ проходит через `AppManifest` —
   собирает топологию напрямую (`SystemBuilder`), в обход `ManifestStore`. Я
   скопировал `recipes/`+`app.yaml` во временный каталог (DESIGN-требование), но
   **не смог технически указать хабу на эту копию** без знания, как GREEN
   подключит `recipes_dir` к hub-обработчикам (Step 1 плана — "где хостить",
   решается в GREEN). Тест сегодня фактически бьёт по боевому
   `multiprocess_prototype/recipes/` бэкенда, поднятого харнессом (не по
   временной копии) — временная копия используется только для вычисления
   `expected_names`/sha256 контроля вне запущенного бэкенда. **Это находка, не
   тихий пропуск**: GREEN-исполнителю, вероятно, придётся либо научить
   `BackendHarness`/`launcher_factory` собирать систему из временного `app.yaml`
   (Ф5.13 escape-hatch уже существует — `launcher_factory`), либо тест придётся
   переписать на реальный временный манифест, когда путь резолва будет известен.
4. **`test_two_saves_same_base_rev_exactly_one_wins`** пока не проверяет саму
   гонку (падает на конструкторе до спавна потоков) — это ожидаемо для RED;
   после GREEN тест реально погонит два потока с `threading.Barrier` и
   daemon-join(10s), как того требует правило про блокирующие вызовы.
5. **Не тестировалось отдельно:** `get`/`delete` с `not_found` для
   несуществующего имени (демонстрируется только через `activate`); `recipe.delete`
   целиком (не входит в REDS-бюджет ≤10, эта команда не в Acceptance criteria
   Task 1b.1, а только в докстринге — за рамками этого RED-захода);
   `recipe.validate` целиком; ветка `apply_topology` вернул `success` не `True`
   (включая debounce) → `apply_failed` без вызова `persist_active`; `persist_active`
   бросил → `io_error` с топологией уже применённой. Эти три ветки `activate` и
   команда `delete`/`validate` — открытые пробелы, не покрытые в этом RED-заходе
   из-за бюджета ≤10 REDS; рекомендую автору (teamlead) закрыть их
   hazard-тестами на этапе GREEN (Step 4 плана уже предписывает похожие
   hazard-тесты для `save`, но не для веток `activate`/`delete`/`validate`).

## Что осталось открытым / ненадёжным (обязательный раздел)

  live-тест может потребовать правки после того, как GREEN определит, откуда

  в этом заходе — не проверено, что они действительно требуются acceptance (они
  в докстринге, но не в чек-листе Acceptance criteria Task 1b.1).
- Не проверял `sentrux check .` / `grep` на отсутствие `PySide6`/`multiprocess_prototype`
  импортов в `service.py` как отдельный тест — он уже ЗЕЛЁНЫЙ сегодня (файл ещё
  пустой скелет), включение его в RED-набор нарушило бы cardinal rule "must fail
  now"; это проверяется Acceptance criteria Task 1b.1 напрямую (`grep`/`sentrux`),
  не через RED-тест.

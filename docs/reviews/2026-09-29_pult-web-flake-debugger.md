# pult-flake: флейк ранних отказов pult_web на Windows — отчёт debugger (2026-09-29)

Ветка `fix/pult-web-early-reject-flake` (от main d2216c8b). Роль: debugger.

## Причина (измерено)

`close()` сокета с непрочитанными байтами в приёмном буфере — либо с телом, пришедшим ПОСЛЕ
ответа сервера (клиент шлёт заголовки и тело двумя `send`) — даёт на Windows RST, и он обгоняет
чтение ответа клиентом: `ConnectionResetError [WinError 10054]` / `ConnectionAbortedError [WinError 10053]`.
Затрагивает все ранние отказы (400/403/404/413/415). У 413 дренаж был — остальные пути нет.

Принудительная частота: `test_early_reject_close.py`-семейство (по настоящему сокету, N обменов на отказ).
- ДО (3 прогона по 200): 403 — 27/35/6; 415 — 48/54/13; 404 — 19/41/1; `Content-Length: -1` с телом — 6/53/0;
  413 — 0/0/0 (дренаж был). Вариант «тело 600 КБ» на потолке доотдачи 64 КБ: 12/100 (400) и 7/100 (415).
- ПОСЛЕ (1 МиБ, 3 прогона по 200 на 7 отказов): 0 из 4200.

## Фикс

Один общий `_linger_close` в `handle()` (Plugins/sim/pult_web/plugin.py): если у запроса есть тело
(Content-Length != 0 или Transfer-Encoding) и команда его не читала (`_body_consumed`) — полузакрытие на
запись и чтение с отбрасыванием до EOF клиента; потолок `_MAX_DRAIN_BYTES` = 1 МиБ и общий дедлайн
`_DRAIN_TIMEOUT_S` = 2.0 с. `_drain_body` удалён (413 больше не дренирует особо — тот же механизм).
Таймаутов на классе обработчика нет, чтение валидного тела не тронуто.

## Итерации

1. Потолок 64 КБ: серия из 20 — прогон 3 упал: `test_negative_content_length_is_400_and_never_reaches_scene`
   (тело 200 КБ при `Content-Length: -1`, `WinError 10054` на `sock.shutdown(SHUT_WR)`). Байты сверх потолка
   дают тот же RST. Изолированный опыт (голые сокеты): потолок 64 КБ / тело 200 КБ — 12 сбоев из 300;
   потолок 1 МиБ — 0. Прогоны 4-7 после этого зелёные, но серия остановлена и начата заново.
2. Потолок 1 МиБ (вчетверо от 256 КБ у `/api/preset/commit`): серия из 20 — 20/20 зелёных, 95 passed каждый.

## Приёмка

`pytest -q --tb=short Plugins/sim/pult_web/tests` x 20 подряд: 0 падений (95 passed, ~94 с на прогон).
Базовая частота (~1 из 3-4 прогонов набора) — цифра лида, полным набором на старом коде мной не мерялась;
мной измерены только принудительные частоты выше и один падающий прогон первой итерации.

## Предсказание при откате фикса

Откат `plugin.py` к HEAD: красными становятся 6 из 7 параметров `test_early_reject_close.py`
(403, 415, 404, `-1`, `-1`+600 КБ, 415+600 КБ); 413 остаётся зелёным (старый дренаж). Проверено дважды:
6 failed, 1 passed оба раза. Откат только потолка к 64 КБ: красными могут стать два «huge»-параметра
(12/100 и 7/100 на замере — вероятностно, не гарантированно). Остальные семейные тесты 5.3a/hazards —
флейкуют вероятностно, в предсказании не участвуют.

## Что не проверено / ненадёжно

- Серия из 20 идёт на общей машине, где параллельно бегут pytest других сессий; чистой изоляции нет.
  20 зелёных при исходной частоте ~1/3.5 — это (0.71)^20 ~ 0.1% случайного везения, но не нуль.
- Остаточная граница: клиент, прислав в ранний отказ больше 1 МиБ или замолчав дольше 2 с, по-прежнему
  получит RST — ограничение задумано (потолок 413 остаётся потолком).
- Долг B (`rfile.read(length)` без таймаута/408) не тронут.
- Тест — вероятностный по природе (RST зависит от планировщика): при N=150 на отказ вероятность ложно-
  зелёного на старом коде мала, но не нулевая (403/415/404 на старом коде давали от 1% до 54%).

## Что оставлено открытым / ненадёжно

- Тесты `frame_from_raw` и почти все тесты сессии зависят от догадок п.2 — при неверном имени поля будет `AttributeError` из `make_raw` уже ПОСЛЕ реализации;
  это дефект тестов, не кода, чинится правкой констант. `make_raw` на настоящих структурах не запускался (их ещё нет).
- Не проверил: на каком уровне в C лежит `nNoReadNum`; чему равен `no_read_num` кадра, если `nNoReadNum` per-record (тест `bad.no_read_num == 1` тогда может быть неверным).
- Не покрыто (контракт молчит): сбрасывает ли `None` (NODATA) счётчик «подряд»; учитывает ли `errors` ошибки `get_frame`; какой `state` при иной ошибке `open`
  (не access denied) или `start_grabbing`; что делает `start()` из `error`; сколько ждёт `stop()` при `timeout` < `timeout_ms`; порядок `on_frame`/потоки (в каком потоке зовётся `on_frame`).
- Тайминговые тесты (stop-дедлайн, `wait_until` 3 с) на перегруженной машине могут дать ложный красный.
- Моё поле `bad.status` для двух нечитаемых (`BAD_CODE`) выведено из решения 3; порядок `codes` = порядок в структуре — принят, в контракте явно нет.
- Break-injection против этого набора не делал (не моя роль и кода нет).

## Где спецификация неоднозначна

- Контракт `CodeQuality.grades` перечисляет ключи, но не сопоставляет их с полями структуры — сопоставление (п.2) угадано по совпадению имён.
- «`close` вызван для созданного handle» при access denied: `open` в `sdk/api` (CreateHandle+OpenDevice) при отказе на OpenDevice сам должен уничтожить handle — граница ответственности api vs reader не задана.
- `SdkFrame.no_read_num`: чей это счётчик (записи или результата) не сказано.
- `pixel_format` для неизвестного: точный формат hex ("0x12345678" vs "0x12345678".upper()) не задан; проверяю по подстроке в нижнем регистре.
- `decode_image` для JPEG «серое» — принял `IMREAD_GRAYSCALE` (цветной JPEG -> 2D); если потребитель хочет BGR — контракт надо менять.

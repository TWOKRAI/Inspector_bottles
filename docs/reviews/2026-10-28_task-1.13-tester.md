## Открыто / ненадёжно

- Сценарий C: в брифе «база сдвигается» после `unregister`. Факт: ревизия — хеш содержимого; пара register+unregister возвращает прежние байты, поэтому база после unregister РАВНА захваченной. Я убрал утверждение «база != прежней»; тест проверяет `база == rev файла` (нет ложного конфликта ревизий) и что отказ идёт именно по ссылке. Если реализация 1.11 когда-либо изменит байты при unregister, тест остаётся валидным.
- D: в тесте Save идёт с `expected_rev=None` (рецепт без секции `displays` — пара «нечитаемый для store.read» файл; сессионную базу `_chain` захватывает до Save, но не используется). Проверяю, что в тексте есть `main` (первая из 4 привязок фикстуры); реализация может перечислять не все id — тест это допускает. Читаемость файла после отказа в D не проверяется (он нечитаем и до Save).
- Не проверено: формат текста ошибки целиком (только вхождение `display_id`), поведение при нескольких неопределённых id, регистр/пробелы в id, привязка с пустым `display_id`.
- B2 меняет привязку на существующий `phone`; не покрывает привязку к дисплею, добавленному в том же Save (определение приходит не через Save — Save дисплеи не пишет; это контракт, не проверяемый тут).
- Ни одного прохода под break-injection: B-тесты зелёные и до реализации, поэтому их сила — «не ломать старое»; пустая реализация «всегда бросать» их покраснит (B1/B2), реализация «никогда не бросать» покраснит A/C/D.
- Тест A2/C/D используют обёртку `_SpyStore` с `__getattr__`; если Save начнёт писать через иной метод стора, чем `save_raw`, счётчик 0 станет слабее (байты прежние всё равно проверяются).
- Ничего не закоммичено и не запушено; worktree оставлен.

## Что красное и почему (input → observed output)

### Критерий 3 — `test_backend_ctl_sees_robot_and_status`

```
overview = drv.system_overview()
# {'success': True, 'processes': {}, 'telemetry': {'fps': {}},
#  'anomalies': [{'kind': 'empty_topology',
#                 'detail': 'state-топология пуста — бэкенд не прогрет или нет соединения'}, ...]}
```

`processes` пуст: у `ProcessManager` нет обработчика `state.get_subtree`
(`No handler for key 'state.get_subtree'` в stderr процесса) — `system_overview`
строит список процессов ИЗ state-топологии (`backend_ctl/overview.py`), а
генерик-оркестратор (`GENERIC_ORCHESTRATOR_CLASS_PATH`, тот же, что у
`examples/minimal_app`) не заводит `StateStoreManager` вовсе.

**Воспроизведено байт-в-байт на `examples/minimal_app`** (не моя правка —
канонический образец, который DESIGN велел копировать «один в один»):

```python
h = BackendHarness(launcher_factory=lambda: build_app(Path("examples/minimal_app/app.yaml")), port=8797)
drv = h.start(); time.sleep(2); drv.system_overview()
# → 'processes': {}, тот же anomaly 'empty_topology'
```

Совпадает дословно с планом: «StateProxy в процессе создаёт прототипный
`GenericProcessApp`; фреймворковый `GenericProcess` его не заводит… carve-out
уезжает в Task 2.0» (`phase-1-vertical-slice.md`, разведка). Разница в том, что
carve-out там про `ctx.state_proxy` ВНУТРИ плагина, а здесь — про
`state.get_subtree` на самом `ProcessManager`; но следствие то же: второе
приложение на генерик-оркестраторе НЕ публикует топологию в StateStore, и
`system_overview()` не может отдать список процессов ни для `line_sim`, ни для
`minimal_app`.

### Критерий 4 — `test_job_counts_writes_in_status_and_history`

`writes_seen` доезжает (проверено `sim_robot.status.writes_seen == 4` после
`send_job` — эта часть работает), но `history_query(metric="sim_robot.writes")`
после полных 10с ретраев отдаёт `rows: []`.

Прямая проверка `introspect.observability` процесса `robot`:
`stats.counters.channel_written_records: {'log_stats': 1, 'hub_stats': 1}` (число
снятий метрики РАСТЁТ — механизм считает), но `history.rows: {'log': N, 'error': 0,
'stats': 0, 'observation': 0}` — **`stats: 0` всегда**, при любом числе записей.

Причина, найденная в коде фреймворка (`multiprocess_framework/modules/process_module/core/process_module.py::_wire_observability_hub`):

```python
self._observability_store, self._observability_store_taps = wire_observability_store(
    self.error_manager, self.logger_manager,   # <- stats_manager НЕ передан
    db_path=..., process=self.name, min_level=policy["level"], ...
)
```

Персистентный SQLite-стор (тот, что читает `history_query`) тапает ТОЛЬКО
`error_manager` и `logger_manager` — `stats_manager` не тап-источник вообще.
Мост «метрика → строка истории с `metric=`» рассчитан на `stats.log_snapshots`
(дефолт `True`) — периодическую сводку через `LoggerManager` (`kind='log'`,
поле `metric` внутри). В пределах полного тестового бюджета (10с ожидания
`writes_seen`, затем ещё 10с ожидания `history_query`, `stats.flush_interval:
1.0` в `system.yaml`) ни одной строки с `metric='sim_robot.writes'` в историю не
доехало — это framework-плоскость наблюдаемости общего пользования (тот же путь
для ЛЮБОГО плагина, не специфика `sim_robot_host`), её починка выходит за
FILES этой задачи.

### Критерий 5 — `test_without_pymodbus_plugin_errors_process_lives`

Обе половины (контроль с `pymodbus`, целевой прогон без) дали пустой
`errors.log` и `anomalies` без слова «modbus». Прямая проверка `introspect.
observability` процесса `robot` (контрольный прогон, с pymodbus): `error.
channels_active: ['critical_file', 'errors_file', 'warnings_file']`, но
`error.idle_sinks` — **те же три канала** — то есть каналы объявлены, но ни
разу не приняли запись за весь прогон, включая штатные фреймворковые warning'и
процесса (не только мой `report_error`). Это тот же класс, что и критерий 4:
плоскость ошибок объявлена (`errors.enabled: true` в `system.yaml` дошёл —
подтверждено в `provenance`), но маршрутизация в файловые синки для
генерик-оркестратора не собирается «из коробки» — вероятно нужен `channels:`/
`loggers:` блок по образцу `multiprocess_prototype/backend/config/system.yaml`
(250 строк, из которых DESIGN явно просил взять только errors/stats/history).
Не успел разобрать до конца в рамках бюджета задачи — **честно: не проверено**,
воспроизводится ли то же самое на `examples/minimal_app` (по аналогии с
критерием 3 весьма вероятно, но НЕ подтверждено прогоном).

### Критерий 6 — `test_no_prototype_imports_in_apps_and_plugins_sim`

```
hits = ['.../apps/line_sim/tests/test_f1_task11_acceptance.py:21: - ``apps/`` и ...
        не импортируют ``multiprocess_prototype``.',
        '.../test_f1_task11_acceptance.py:423: pattern = re.compile(r"multiprocess_prototype")',
        ... ещё 5 строк из ТОГО ЖЕ файла ...]
```

**Находка о тестерском файле.** `_find_prototype_imports` сканирует
`root.rglob("*.py")` под `apps_dir` = `apps/`. Файл теста
(`apps/line_sim/tests/test_f1_task11_acceptance.py`) физически лежит ВНУТРИ
`apps/` и содержит подстроку `"multiprocess_prototype"` семь раз в
собственных докстрингах/комментариях/regex-литерале, описывающих сам этот
критерий. Наивный построчный grep без исключения себя не может дать `hits ==
[]` НИ ПРИ КАКОЙ реализации `apps/line_sim` — тест красен по конструкции,
не по коду. (Убрал 2 лишних совпадения из собственного `Plugins/sim/__init__.py`
— он объяснял границу словами, не спойлером ADR-номера; не помогло сделать
тест зелёным, но и не добавляет шума сверх неизбежного.)

## Что интерпретировал, а не исполнил

- **Пробный `bind()` перед стартом `SimRobotServer`** (DESIGN не называл этот
  приём явно). `SimRobotServer.start()` поднимает `pymodbus` в фоновом daemon-
  потоке и не сообщает об ошибке бинда синхронно — синхронный `try/except`
  вокруг `.start()` эту ошибку никогда не поймает. Решение: собственный
  пробный `socket.bind()`/`close()` ДО обращения к `pymodbus`, синхронно.
  Обоснование и известный риск (TOCTOU-окно между закрытием пробного сокета и
  реальным биндом) — в докстринге `plugin.py` и `STATUS.md`.
- **Счётчик записей — буферизация под `Lock`, публикация НЕ с потока
  `pymodbus`.** DESIGN явно просил решить и сказать в отчёте: `_on_write`
  зовётся на СВОЁМ потоке `pymodbus`-сервера; `ctx.record_metric` не
  документирован как безопасный с чужого потока. Инкремент — под `Lock`
  (безопасен с любого потока); перенос в `record_metric` — дельтой, только из
  `cmd_status`/`shutdown` (штатные потоки плагина).
- **`system.yaml` — 7 листовых ключей** (`errors.enabled`, `errors.level`,
  `stats.enabled`, `stats.aggregation_interval`, `stats.flush_interval`,
  `history.enabled`, `history.level`), не 250 строк прототипа. `flush_interval:
  1.0` (не дефолтный пол 10.0) — чтобы снапшот успевал доехать в тестовое окно
  10с (не помогло — см. критерий 4, но само по себе решение обоснованно).

## 1. Ф3 — по задачам

### 3.1 (закрыта) — три факта, на которые встал экспортёр
`NUMBER_SEVERITY = "number"` + `severity_number = UNSPECIFIED` (К7), маркер `origin` в `extra` (К1), идентичность `metric = "<writer>.<metric>"` (К4). Otel 1.1/1.3 читают ровно их. Стража их **как контракта для внешнего подписчика** нет: `test_record_forward.py` держит 4 теста нормализатора, `test_stats_aggregate_delivery.py:68` — один конверт. См. §4.

Мелочь в контракте К3: `NumberRecord.unit` документирован примерами `'s', 'Hz', 'count'` (`number_record.py:89`). `count` — не единица ни в одной системе; см. 3.4.

### 3.2 — база цены для этапа 7
Задача роняет объём `INFO` (цель < 100 строк на бут). Otel 3.2 меряет цену экспорта **после** неё, иначе число протухнет. **Предложение:** добавить в критерии одно число — строк/ч `INFO` на 8 процессов до/после, с хэшем; это база и для closure 3.8, и для otel 3.2.

### 3.3 — форма предохранителя, которую экспортёр повторит
Bounded-канал, `history.queue_capacity`, `drop_oldest`, `store_evicted` голосом, `flush: N записано, M потеряно`. Otel 2.4 строит ту же форму поверх `BatchLogRecordProcessor` SDK (свой батчер, поэтому **общий код не нужен** — у SDK своя очередь). Общими обязаны быть **лексика и форма readback**: суффикс `_evicted`, ключ ёмкости в политике/регистре, литерал строки flush. **Предложение:** в ADR задачи 3.3 назвать эту форму переиспользуемой и зафиксировать три имени; второй потребитель (otel 2.4) ссылается на ADR, не изобретает.

### 3.4 — единицы: выбрать UCUM сейчас, иначе таблица перевода в v2
Задача вводит `unit` в объявление метрики: `unit="Hz"`, `unit="s"`, `process.rss` в `MiB`. OTel metrics ждёт единицу строкой **UCUM** (`s`, `ms`, `Hz`, `By`, `MiBy`, безразмерное `1`, аннотации `{frame}`). `Hz` и `s` совпадают, `MiB` — нет (UCUM: `MiBy`), `count` — нет (`1` или `{frame}`). Это единственная точка, где closure и otel могут разойтись словарём дёшево сейчас и дорого потом: экспорт чисел (otel v2, Р-8) без UCUM потребует таблицу перевода, которая протухнет на первой новой метрике.
**Предложения:**
1. В 3.4 — правило одной строкой: «единица — строка UCUM»; страж `record_timing` (`unit="s"`) уже в задаче, добавить страж «`MiB`/`count`/`msec` → отказ с адресом и подсказкой UCUM».
2. Сигнатура `declare_metric(name, *, owner, unit, description, kind)` — otel-плагин объявляет 6–7 счётчиков через `ctx.declare_metric`. Если otel Ф2 ляжет **до** 3.4 — внести `Plugins/io/otel_export` в список миграции 3.4 явной строкой (сейчас там «все объявления фреймворка и `capture`»).
3. Роды `counter|gauge|timing|histogram` ↔ инструменты OTel `Counter|Gauge|Histogram`: `timing` = гистограмма с единицей времени. Записать соответствие одной строкой в README `NumberRecord` — это спасёт v2 от спора «timing — это что».

### 3.6 — имена восьми метрик: где есть semconv, брать его
Создаются `inference.latency`, `camera.open_failed`, `router.send.duration`, `worker.cycle.duration`, `chain.stage.duration`, `queue.evicted`, `process.rss`. Из них `process.rss` имеет прямой аналог semconv — `process.memory.usage` (единица `By`). Остальные — доменные, свои имена законны. **Предложение:** правило именования в задаче — «если у понятия есть имя в OTel semconv, берём его; иначе своё, без единицы в имени». Переименование позже — третья волна после `fps→rate_hz` (4.6).

### 3.7 — пересечений нет.

### 3.8 — стенд Ф3: пять минут для снимка otel 1.0
Otel Task 1.0 блокирует всю Ф1 экспортёра и требует ровно одного: `observability_tail` уровня `DEBUG` на 5 минут с записями шести форм (`log`, `error`, `stats`-агрегат, `stats`-одиночная, `observation`, конверт `data.records`/`data.record`). **Предложение:** строка в шагах 3.8 «окно 5 минут для снимка этапа 7», чтобы не поднимать второй стенд.

## 2. Ф4 — по задачам

### 4.1 — `changed_only` меняет то, что видят ВСЕ подписчики хвоста
Карта последних значений с эмиссией только изменившихся — записи `observation` перестают приходить каждый такт. Подписчики хвоста трое: GUI, `backend_ctl`, otel. Критерии задачи — про `dropped` и стор; про подписчиков — ничего. **Предложение:** критерий «подписчик хвоста получает `observation` только при смене значения; ряд в `history_query(metric=…)` с разрывами — норма, документировано в `CONNECTORS`»; ёмкость `observability.hub.capacity` читается подписчиками из readback (тождество потерь otel 3.4).

### 4.3 — `counters()` обязан отдавать счётчики форвардера per-subscriber
Первый внешний потребитель протокола `ObservabilityReadback` — otel 3.4: ему нужны `written`/`evicted`/`send_failed` канала `observability_forward::<subscriber>::batch` у **каждого источника**, чтобы свести `отправлено = принято + потери`. Сегодня эти числа читаются из `introspect.observability` ключами «по факту». **Предложение:** критерий 4.3 — «`counters()` содержит форвардеры по подписчикам, ключи литералами в `CONTROL_PANEL`»; `flare` включает список активных подписчиков хвоста.

### 4.4 — реестр намерений: подписчик-процесс, а не только сессия backend_ctl
Задача говорит о `log.tail`/`observability.tail`/`ui.tap` с `forget_session` и replay на `instance.started` — то есть о клиентах-сессиях. Экспортёр — **подписчик-процесс** с `subscribe_all` (как GUI), и у него два сценария, которых в критериях нет: (а) сам подписчик перезапущен — новая инкарнация с тем же именем объявляет намерение заново, старые форвардеры источников адресованы по имени и живы; (б) подписчик убит SIGKILL — кто и через сколько снимает форвардеры-сироты (`forget_subscriber` есть, триггер — снятие с топологии; при авто-рестарте под тем же именем топология не меняется). Otel 2.5 записывает (б) ссылкой на 4.4, не чинит. **Предложение:** два критерия-пары в 4.4: «рестарт подписчика-процесса → хвост восстановлен, дублей форвардеров нет (число каналов до/после)»; «SIGKILL подписчика без рестарта → сироты сняты через N с, N названо».

### 4.5 — Protocol контекста публикует фреймворк, а не каждый сервис
`ServiceContext` зеркалит `PluginContext`. `Services/otel_export` — библиотека, которой нужен минимальный контекст (`log_*`, `record_metric`, `report_error`); otel 0.4 сейчас объявляет свой Protocol с оговоркой «которому удовлетворят оба». Правильнее, чтобы **имя и место Protocol'а принадлежали фреймворку**: `service_module/interfaces.py`, и `PluginContext`, и `ServiceContext` проходят один оракул. **Предложение:** критерий 4.5 — «минимальный Protocol наблюдаемости опубликован в `service_module/interfaces.py`; контракт-тест: `PluginContext` и `ServiceContext` удовлетворяют ему поимённо»; otel 0.4 тогда импортирует, а не объявляет.

### 4.6 — две границы и один открытый вопрос владельцу
1. `frame_trace → register_sink_factory` заводит реестр фабрик логгер-стоков. Экспорт наружу — **подписчик хвоста, не sink**: форма «tap/sink в каждом процессе» отвергнута в otel ред. 4 (SDK в каждом из 8 процессов, зависимость через фреймворк). **Предложение:** одна строка в ADR 4.6 — «внешние экспортёры не регистрируются как sink factory», чтобы граница не размылась первым, кому это покажется удобным.
2. Алиасы `fps`/`latency_ms` рядом с `rate_hz`/`cycle_ms` на период снятия: в числовой плоскости на это время живут оба имени. Otel v1 числа не экспортирует — влияния нет; для v2 записать, что алиасы наружу не едут.
3. **Открытый вопрос (не блокер, решение владельца 2026-09-01 в силе):** `rate_hz`/`cycle_ms` несут единицу в имени, а 3.4 вводит единицу метаданными — дубль. OTel semconv единицу в имени не держит (`http.server.request.duration` + `unit=s`). Если когда-нибудь числа поедут наружу, `cycle_ms` с `unit="ms"` — избыточно, но не ошибочно. Называю, не настаиваю.

### 4.7 — пересечений нет; критерий «0 правок в Plugins/Services» после появления otel-плагина покрывает и его.

### 4.9 — регистры плагинов как кандидат-потребитель
Параметры батчера экспортёра (`max_queue_size`, `schedule_delay_ms`, `compression`…) живут в регистрах плагина — это ручки **вне секции `observability`**, с дорогой `set_config` → регистр → readback. Инвентарь шага 1 задачи 4.9 перечисляет observability, регистры backend_ctl, `telemetry.*`, `FW_*`, камеру, рецепты — регистры плагинов как класс стоит внести в инвентарь явно. Otel своей ручечной механики не заводит; при появлении адаптера «регистр ↔ `KnobSpec`» примет его.

### 4.10, 4.11, 4.12 — внутренности фреймворка, пересечений нет.

### 4.8 — стенд на 20 процессах
Otel 3.2 хочет число цены экспорта на 20 процессах. **Предложение:** «если фрагмент `otel_export` подключён — его CPU и байты на проводе в отчёт» как опциональная строка; не поднимать второй стенд.

## 4. Сквозная рекомендация — контракт display-формы для внешних подписчиков

Сегодня форму записи, которую получает подписчик хвоста, **не пинит ни один тест как целое**: конверт (`_ENVELOPE_KEYS`), размещение `trace_id`/пятёрки Resource/`origin` на `extra.context.*`, шкала `severity_number` и `NUMBER_SEVERITY`, конверт сообщения `data.records`/`data.record`. Ф4 closure трогает ровно эти места (4.1 hub/дренаж, 4.3 readback, 4.6 имена), а otel Ф1 строит маппер на снимке этой формы. Без стража любая правка Ф4 ломает otel молча — и наоборот, otel не сможет отличить «фреймворк изменил форму» от «мой маппер неверен».

**Предложение — одна задача Middle, один файл, в Ф4 (до 4.1) или в 5.1:**
`channel_routing_module/tests/test_subscriber_display_contract.py` — шесть золотых записей литералами (те же, что снимок otel 1.0), утверждения: ключи конверта, адреса структурных наборов, шкала, конверт пачки. Потребители названы в докстринге: GUI, `backend_ctl`, `otel_export`. Пара: инъекция «перенести `trace_id` на `extra.trace_id`» → красный поимённо. Проза — таблица в `CONNECTORS` (§3, 5.1), страж паритета таблица ↔ тест — в `docs_verify`.

Это делает два плана **независимыми по расписанию**: closure правит фреймворк под стражем, otel строит маппер на зафиксированной форме, и любое расхождение называет себя само.

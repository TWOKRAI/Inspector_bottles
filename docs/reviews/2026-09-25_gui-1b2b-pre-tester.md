## Находка вне контракта 1b.2b (задокументирована как ОДНА ДОГАДКА в шапке файла)

Эмпирически измерено ДО написания AC4: `RegistersManager.validate()` (через
`SchemaMixin.validate_field` → `FieldMeta.validate_value`) проверяет **только**
`access_level` и числовой диапазон `[min, max]` — принадлежность Literal-полю **не
проверяется вообще**, даже на живом `from_registry`-менеджере:

```
rm.validate('center_crop', 'size_mode', '__not_a_choice__') → (True, None)  # уже сегодня, на эталоне
```

Бриф предполагал абсолютный контракт "invalid choice → False на обоих менеджерах" — я
переписал AC4 на **паритет поведения** (catalog должен вести себя ТОЧНО так же, как
from_registry, включая эту слабость), а не на абсолютную корректность, которой не имеет
даже эталон. Это решение по существу: если лид/разработчик считают, что "invalid choice
→ False" — часть контракта 1b.2b (а не отдельный баг вне scope), тест нужно переписать
на абсолютный вариант — сегодня он был бы RED **на обоих** менеджерах одновременно, что
не отличило бы catalog-специфичный дефект от преднаселённого. Из DESIGN брифинга
("Python-код валидаторы... вне scope, бэкенд остаётся финальным судьёй") я прочитал это
как согласующееся с паритетным толкованием, но не проверял это с лидом.

## Что я интерпретировал, а не просто следовал брифу

1. **AC4 — паритет вместо абсолюта** (см. выше) — самое существенное отклонение.
2. **Action в AC6 — лёгкий объект, не pydantic `Action`.** Бриф сослался на
   `test_bridge_integration.py`, который сам использует `MockAction`-датакласс (4
   атрибута), а не настоящий `Action` (там обязателен `action_type` и другие поля). Я
   зеркалил их подход — `_FieldSetAction` с теми же 4 атрибутами, что читает
   `FieldSetHandler.apply` (`register_name`, `field_name`, `forward_patch`,
   `backward_patch`).
3. **AC8 — "здоровый плагин" выбран по индексу, а не по имени.** Бриф не называл
   конкретные плагины; я взял `with_register[0..2]` (детерминированный порядок
   `PluginRegistry.list()`), не "contour_draw" specifically, — устойчивее к порядку
   обнаружения плагинов.
4. **Payload для `_build_catalog_payload`** — не копировал 1b.2a-файл дословно (там
   вручную реализован `_type_tag`/`_field_dict` — кодека `FieldInfo.to_dict()` тогда
   ещё не было). Бриф явно разрешил "real `FieldInfo.to_dict` is allowed" — я
   воспользовался этим, что сильно упростило файл и держит его in-sync с реальным
   кодеком 1b.2a, а не с параллельной копией логики тегирования типов.

## Что я оставил открытым / ненадёжным в своей же работе

- **AC2/AC7 гоняются по ВСЕМ 43 плагинам с регистром** (не выборочно) — быстро (полный
  прогон файла 1.25 с), но если разработчик добавит новый плагин с полем, для которого
  тег типа классифицируется как `"unsupported"` НЕ через синтетическую инъекцию (а
  реально, например новый Python-тип), тест по AC2 начнёт падать с сообщением "фикстура
  изменилась, пересчитать" вместо тихого исключения — это осознанный компромисс
  (см. правило "LISTED explicitly, not silently skipped"), но будущему разработчику
  придётся руками добавить исключение, а не просто перезапустить.
- **Инъекция излома НЕ проводилась** — этот прогон RED **до** реализации; break-injection
  (сорвать каждую гарантию по отдельности) относится к стадии 3 конвейера (лид, после
  зелёного прохода разработчика), не к этой RED-приёмке. Сегодняшний RED демонстрирует,
  что тесты падают на ОТСУТСТВИИ фичи (правильный тип отказа), но не демонстрирует, что
  они не останутся зелёными под частичной/неверной реализацией — это будет проверено
  после того, как разработчик сделает `from_catalog` зелёным.
- **Не проверял, ловит ли что-то из моих тестов чрезмерно широкую реализацию** (например,
  если разработчик просто скопирует ВСЕ поля как `SchemaBase`-совместимые без
  сохранения реального типа) — только паритет по значению/дампу, не по точному
  Python-типу поля после `from_dict`.
- **AC1 assert `len(expected_names) > 20`** — литерал ниже измеренных 43, чтобы не быть
  хрупким к небольшим изменениям фикстуры плагинов; не переизмерял на момент написания
  отчёта повторно (числа собраны одним и тем же прогоном скрипта, см. выше).
- **Действие в AC5/AC6 (`color_b` у `contour_draw`)** — конкретное поле выбрано вручную
  (не параметризовано по всем полям) согласно брифу "one or more tests each" — это ОДИН
  репрезентативный кейс на каждую из этих двух AC, не исчерпывающий перебор.

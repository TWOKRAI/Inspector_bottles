## Решения, принятые при реализации (DESIGN не менялся)

- Зонд работает на уровне `MV_CC_*` настоящего `MvCamera`; `FakeMvCamera` повторяет имена и параметры методов (тест сверяет сигнатуры с `MvCamera`, по `inspect.signature`). Журнал фейка — `calls: [(имя, args)]`, хук `_journal`.
- Выбор камеры: `chSerialNumber` / `nCurrentIp` из `MV_CC_DEVICE_INFO` (`entry_from_info`, проверено на собранной вручную структуре); оба флага — оба должны совпасть; не ровно одна подходящая — код 1.
- Коды выхода: 0 / 1 (отказ, камеры нет, ошибка опыта, ошибка аргументов) / 2 только `RESTORE MISMATCH`. Для этого `ArgumentParser.error` переопределён на выход 1 (argparse по умолчанию даёт 2).
- H5 (addendum cto): запись `Width` отказала `0x80000106`, restore прочёл значение == `--orig` — код 0.
- Порядок при `--write` (addendum cto): StopGrabbing, затем возврат; возврат стоит в `Session.finish()`, она идемпотентна и вызывается и на нормальном пути (поток B), и из `finally` главного потока (исключение, Ctrl+C).
- Поток — одно место `threading.Thread(...)` (`_run_in_thread`), только для `h2 --mode split`, `join` до выхода, срок `THREAD_JOIN_S` (переменная: G6 R3 запрещает числовой литерал в `join`).
- Исходные: до записи читается idle-значение; узел нечитаем или не int/enum — отказ без записи. Файл `--orig` пишется в `phase_a` до первого `MV_CC_Set*`; тест проверяет это журналом фейка (подкласс видит файл на диске в момент первого Set).

## Что я истолковал, а не выполнил буквально

1. Семантика опытов в брифе названа кратко. Принято: **H1** = open, старт, стоп, пауза `--delay`, запись `TriggerMode` (другое значение enum), чтение, возврат; **H2** = запись `TriggerMode` ДО StartGrabbing (поток A или главный), стоп/пауза/возврат/close в потоке B или главном; **H5** = запись `Width` (на `inc` меньше текущего) при захвате, чтение, затем стоп и возврат. 2. Во время выдержки кадры не забираются (`GetImageBuffer` не зовётся): для вопросов H1/H2/H5 нужен сам режим захвата, а не кадры.
3. Строка возврата дополнена ` thread=<поток>` (нужно для H2), перед `node=` печатается ещё `write node=<имя> value=<..>`. Префиксы `node= rc= read= ms=` и `restore node= rc= read=` из брифа сохранены.
4. `device` в JSON берётся из перечисления (`chModelName`, `chSerialNumber`), а не из узлов `DeviceModelName` / `DeviceSerialNumber` (они есть среди `nodes`). Для `--orig` иначе пришлось бы читать лишние узлы.
5. `access` для `AM_Undefined` / `AM_CycleDetect` (внутренние значения SDK, в схеме их нет) записывается как `NI`. Для типа `command` и неподдержанных `IFT_*` значение `null`, `rc` `0x00000000`.
6. `--mode split` для не-h2 — отказ (код 1): бриф говорит «поток только в h2».
7. Строка `devices=<n>` печатается для всех режимов, не только `--dump`; следом по строке `device serial= ip= model=`.

## Что осталось открытым / ненадёжно

- **Ничего не проверено на приборе.** Фейк — моя модель поведения: что отсутствующий узел даёт `0x80000100`, что `Width` при захвате отвечает `RO` / `0x80000106`, что `MV_CC_GetEnumEntrySymbolic` и `GetIntValueEx` заполняют поля именно так, как их читает зонд. Единственная проверка реальных обёрток — один тест на фейковой DLL (три вызова `read_node`, int-узел); enum / float / bool / string через настоящие обёртки не прогонялись.
- Выбор по `--serial` / `--ip` на приборе не проверен (разбор структуры проверен только на собранной вручную `MV_CC_DEVICE_INFO`); `chSerialNumber` декодируется как ASCII.
- Значения float читаются через `MVCC_FLOATVALUE` (float32): сравнение «возврат == исходное» для float-узлов идёт по float32-округлённым значениям, опыты их не пишут.
- Ctrl+C при `--mode split`: главный поток в `join` получает `KeyboardInterrupt`, `finally` вызывает `finish()` в главном потоке, пока поток B может ещё работать — возможна гонка двух потоков на одном handle. Не тестировалось. Для опыта оператор должен дать завершиться потоку.
- Если камера не отпускает `OpenDevice` (клиент IDMVS жив) — отказ с подсказкой, повтор вручную.
- Запись `TriggerMode=On` на настоящей камере в H1/H2 меняет режим; при обрыве процесса возврат — только `--restore <orig.json>` (значения также печатаются строкой `orig saved; вручную (IDMVS): ...`). `UserSetSave` зонд не зовёт никогда.
- Тест `test_сбой_при_захвате…` и `test_h1_задержка…` подменяют `mvs_probe.time.sleep` (это глобальный `time.sleep` на время теста).

### Что оставил открытым (р.1)

- Если поток завис ВНУТРИ вызова SDK и после отмены (второй `join` не помог), `finish()` всё равно идёт в главном потоке (возврат нужнее) — на одном handle возможна гонка с зависшим вызовом. Печатается «жив и после отмены». Не воспроизводилось на железе.
- Отмена проверяется перед вызовами SDK, но не внутри длинного `time.sleep(seconds/delay)` фазы B (он укладывается в потолок по построению).
- Проверка `device.serial` в `--restore` сравнивает с серийником из перечисления; файл без поля `device` отклоняется. Правка вручную серийника в файле обходит защиту — это не защита от злого умысла.
- `--restore` с `--write` по-прежнему возвращает значения без проверки, что камера «не в захвате»: камера открывается свежим handle и простаивает по построению, но чужой клиент не исключён (эксклюзивный `OpenDevice` его отсекает).
- `restore_nodes` ловит `Exception` по узлу; `KeyboardInterrupt` между узлами многоузлового `--restore` пропустит остальные (в опытах узел один). Прибор по-прежнему не проверялся.
- Находки 3 и 9 (колбэк, плагин) — не мои.

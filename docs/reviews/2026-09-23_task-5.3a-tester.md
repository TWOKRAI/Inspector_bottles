## Что я интерпретировал, а не взял дословно из контракта

1. **Форма ответа `GET /api/truth`** (успех): §1 говорит только «как у `/api/journal` — dict
   отдаётся как есть». Для сборки литерала §2 я предположил обёртку `{"status": "ok", "counters": {...}}`
   по аналогии с `/api/journal` (`{"status": "ok", "counters": {...}, "recent": [...]}`) — сам §1-тест
   (`test_get_truth_goes_to_scene_process_and_passes_through`) НЕ завязан на эту форму (проверяет
   произвольный dict как есть), а §2-тесты (`test_page_truth_line_literal` и др.) уже используют
   конкретную обёртку с `counters`, т.к. без неё `c = j.counters` со страницы неоткуда взять.
2. **Текст ошибки в 504 для «не-dict» случая** — НЕ стал сверять с конкретным литералом
   (`"bad_response"` по аналогии с существующим `_dispatch`), ослабил до `"error" in body` — риск
   зафиксировать деталь реализации, которой в контракте нет буквально.
3. **Имя второго конфиг-ключа `scene_process`** — взял дословно из §1 («Конфиг `scene_process`
   (дефолт `"camera"`)»), не догадка.
4. **Название узла `_client_for(target_process)`** поверх общего `_FakeDeviceHubClient.instances` —
   моя реализация харнесса, не из плана; повторяет уже подтверждённый шов патчинга
   `Plugins.sim.pult_web.plugin.DeviceHubClient` по имени (зелёный тест 5.1 это подтверждает).
5. **Node-сценарии `truth_line`/`truth_unavailable`/`truth_reset`** в `page_offline.mjs` — мой выбор
   имён и таймингов опроса (1200 мс на цикл, чтобы гарантированно попасть в опрос раз в 1000 мс из §2);
   старые сценарии (`no_press`, `multitouch`, `slow_jog_hold`, `freq_change`, `status_error`) не тронуты.
6. **`test_truth_routes_forbidden_host_403` предсказан зелёным ДО запуска**, по чтению
   `plugin.py` (строки 364-368 `do_GET`, 386-389 `do_POST`) — общий `_host_allowed()` страж
   срабатывает раньше любого сопоставления пути. Прогон подтвердил предсказание.

## Что я оставляю открытым / ненадёжным

- **Форма ответа `/api/truth` (пункт 1 выше) — предположение, не факт.** Если разработчик выберет
  другую обёртку (например, `counters` на верхнем уровне без `status`/`recent`), часть §2-тестов
  (`test_page_truth_line_literal`, `unavailable`, `reset_posts_then_repolls`) может остаться красной
  по СВОЕЙ причине (форма ответа), а не по отсутствию функциональности — это надо будет различить
  при разборе результата разработчика, не считать автоматическим провалом реализации.
- **`test_truth_reset_bad_body_never_reaches_command` объединяет три проверки (415/400/413) в один
  тест** — по образцу существующего `test_bad_json_400_unknown_404_oversize_413`; если разработчик
  уронит только одну из трёх, весь тест покажет один traceback на первой сработавшей, не все три —
  это то же компромиссное решение, что уже принято в существующих тестах плагина, не новое.
- **`test_get_truth_error_or_non_dict_is_504` не проверяет точный текст `error`** (см. пункт 2) —
  слабее, чем мог бы быть; настоящая проверка «только код + `ok:false`+наличие `error`».
- **Не проверял историческую сторону 5.1b** (окно недавних заданий, «те же X/Y» из журнала робота) —
  вне области контракта 5.3a; не трогал и не читал этот код.
- **`_run_page_js` таймауты (15 с на процесс, 1200/300 мс сна внутри сценариев)** — подобраны по
  аналогии с существующими сценариями (400 мс на цикл опроса 250 мс), не измерены отдельно на
  медленной машине; при повторном использовании в CI может понадобиться коррекция, если опрос
  окажется медленнее заявленных в контракте 1000 мс.
- **Полный набор тестов плагина (33 после добавления)** гоняется быстро (~26 с) — не полный
  прогон проекта, только `Plugins/sim/pult_web/tests` по инструкции ACCEPTANCE.

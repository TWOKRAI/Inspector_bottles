## Находки (по тяжести)

### Н1. [spec, blocker] Задание CVT в ходе: стоп процесса пишется дважды, при молчащем эхе тик держит `remove_worker` 1,0 с — ВОСПРОИЗВЕДЕНО

- Где: `Services/device_hub/drivers/robot_driver_v2.py:862-868` (`_run_next_job`, ветка `_JobStopped` ->
  `client.stop(STOP_LEVEL["HARD"])` мимо защёлки); путь продукта — `Plugins/hub/device_hub/plugin.py:442`
  (`drv.tick(stop_evt)`, событие ставит `remove_worker`). `wait_done` зовёт `on_poll` ДО проверки итога
  (`client_v2.py:654-656`), поэтому `_JobStopped` срабатывает почти всегда, даже если робот уже оборвал задание.
- Вход -> итог: робот sim, одно задание `enqueue_job {x_mm 400, y_mm 100}`, тик в потоке с событием; задание в ходе
  0,2 с; `request_stop(now + 2.5)`; затем `ev.set()` (как `remove_worker`):
  - эхо есть: записи `STOP_REQ` после t0 — `[0.0, 0.016]` с; тик вышел через 0,038 с;
  - эхо молчит: записи `[0.0, 0.013]` с; тик вышел через **1,031 с** (ожидание эха второго стопа).
- Что нарушено: §2 «защёлка … повтор только после неудачной записи»; §4 «1 робот молчит -> ровно 1 запись стопа».
  Вторая запись идёт после удачной первой. Ожидание 1,0 с на робота с заданием идёт внутри `remove_worker` (по
  очереди) и съедает бюджет `scope.close`: у соседей поводок и исполнитель станут ложными выжившими.
- Сторожа круга 2 этого не видят: сценария с заданием нет ни в `test_t53r2_stop_hazards.py`, ни в
  `test_t53r2_stop_acceptance.py`; `FakeWorkerManager` событие тика не ставит.
- Исправление: в ветке `_JobStopped` при `_shutdown` стоп не писать (фаза 1 уже записала HARD через защёлку) или
  писать через защёлку без эха (`_write_stop` только при `_latch_level < HARD` или `_latch_failed`). Ветку
  `RobotTimeout` (не остановка) оставить, но через `_stop_and_wait`, чтобы защёлка видела запись.
  Сторож: задание в ходе -> `request_stop` -> событие тика -> ровно 1 запись; при молчащем эхе тик выходит за 0,1 с.

### Н2. [architecture, major] Драйвер без `spawn`: `return_job` принят, `tick()` падает `RuntimeError`, возврат потерян — ВОСПРОИЗВЕДЕНО

- Где: `robot_driver_v2.py:886-907` (`_start_next_return` -> `start_return` -> `_launch` -> `_spawn_fn()` на
  `:1194`, вне `try`); вызов `_dispatch` в `tick` (`:795-796`) не защищён.
- Вход -> итог: `RobotDriverV2(..., spawn=None)`, подключён к sim; `call("return_job", {x_mm 400, y_mm 100})` ->
  `{'status': 'ok', 'return_queue_len': 1}`; `tick()` -> **`raised RuntimeError: RobotDriverV2 без spawn не запускает
  потоки`**; очередь возвратов 1 -> 0; `returns_failed` = 0.
- Почему major: лид оставил путь без `spawn` как контракт («без потоков драйвер работает как прежде», отклонение 1).
  Путь без живого вызывающего — контракт (принцип 3): он должен отказывать громко и сразу, а не терять работу и
  ронять тик. Продукт этот путь не строит (фабрика отказывает), поэтому не blocker.
- Исправление: `_op_return_job` при `self._spawn is None` — постоянный текст отказа до очереди; или
  `_start_next_return` ловит отказ -> `returns_failed += 1` + `last_error`. Тест — рядом с
  `test_driver_without_spawn_refuses_threaded_ops`.

### (2) Ожидание эха в отдельном `disconnect` простого робота: оставить

- Посылка лида неточна: `cmd_device_disconnect` асинхронный — кладёт задачу в `_conn_queue` и отвечает сразу
  (`plugin.py:803-816`). Поток команд не ждёт. Ждёт поток supervisor: соседние connect / disconnect в очереди
  сдвигаются до 2,0 с.
- То же ожидание уже есть у отдельного `disconnect` робота в движении (jog: 2,0 с). Ручной `disconnect` по решению
  CTO круга 1c «без изменений». Простой робот повторяет это поведение, нового класса задержки нет.
- Решение: оставить в этом круге. Перевод ВСЕХ стопов отдельного `disconnect` (движение и покой) на «запись + одно
  чтение эха без ожидания» — пункт T5.3c. Только для простого робота делать его не стоит: два правила для одного
  действия.
- Minor: при молчащем эхе лог пишет «стоп простого робота не доставлен», а запись прошла — не пришло только эхо.
  Нужен текст «стоп не подтверждён роботом» и `last_error` (сейчас пусто).

### (4) ADR-DH-009 против кода

- Гарантия, уровни (простой — SOFT, неподключённый — без записи) и «защёлка гасит вторую запись простому» совпадают с
  кодом и сторожами.
- Исключения: «вторая запись — только если первая не покрывает движение (упавшая запись или команда после стопа:
  О5 / H-B); до трёх записей» — совпадает с моим замером О5 из разбора n-матрицы.
- Условия CTO на месте: L-9 до стенда T4.x; текст T5.3c «эхо не читалось (нет окна)» при `timeout_sec ≥ 1,25`.
- Не хватает (minor): отдельный `disconnect` ждёт эхо до `soft_echo_timeout_s` (2,0 с), стоп процесса — нет.

### Вопрос к CTO (не блокер)

Защёлка поколения гасит стоп при выключении, если с последней команды движения стоп уже писался, даже давно
(release jog, стоп оператора). ADR это называет («стоп оператора этого поколения»), сторож
`test_idle_robot_process_stop_after_operator_stop_no_second_write` это закрепляет. Буква владельца — «всех на стоп».
Физически робот уже стоит после этого стопа. Подтвердить, что так и задумано.

### Что осталось открытым / ненадёжным (раунд 2d)

- Случай «release jog давно, потом выключение» по отдельному тесту не проверял: механизм тот же, что в сторожe со
  стопом оператора.
- Задержку supervisor 2,0 с на соседних роботах не измерял — вывод по чтению очереди `_conn_queue`.

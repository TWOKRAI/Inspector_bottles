## Находки

### 1. [major] `_is_large_array` (`frame_shm_middleware.py:67`) пускает ссылкой любой ndarray ≥ 8192 Б

Формат слота хранит dtype одним символом, а форму — только как (H, W, C). Проверено через `on_receive` в другом `MemoryManager` (rv_dtypes.py / rv_shapes.py):

| Массив | Что происходит |
|---|---|
| `<U16` (20×8), object (40×40) | `by_ref=True`, а у получателя `None` («itemsize cannot be zero» / «cannot create an OBJECT array»). Данные теряются молча; до 4.1 они доходили через pickle. |
| `datetime64[s]` | приходит как `datetime64` без единицы — dtype меняется молча. |
| 1D `float32[2048]` | на каждое сообщение ERROR «allocate SHM error: tuple index out of range» без троттлинга и `frame_pickle_fallbacks` +1. |
| 4D | fallback на каждом сообщении — засоряется метрика приёмки. |

- Сейчас таких производителей нет (grep по Plugins/prototype/Services пуст) — дефект латентный.
- **Фикс:** гейт `dtype.kind in "biufc" and ndim in (2, 3)`, остальное inline; тест на U / object / 1D. Сузить формулировку C1 в плане.

### 2. [major] F1 при включённом loan-протоколе (воспроизведено, rv_f1_loan.py)

**Сценарий:** цепочка p1 → p2 → p3, coll=2.
1. p2 пересылает `_shm_refs.mask` с owner=p1, idx 0.
2. Сообщение p2 → p3 вытесняется.
3. `RouterManager._on_frame_evicted(m2, "p3")` шлёт в p1 `('output_frames__mask', 0, 'p3')`.
4. Refcount маски у p1: `[1, 1] → [0, 1]`, хотя слот 0 держит p2 (сообщение m1c).
5. Следующая отправка p1 берёт `mask idx 0` — **запись поверх живых данных p2**.

Тот же класс дефекта даёт view-тикеты от p3 в чужой пул: снимается доля, которой p3 никогда не имел.

Правило «процесс пересылает только свои ссылки» верное. Уточнения для 4.2:
- (а) фильтровать в send-middleware по `owner == self._owner`. Свежий пустой dict не годится: при повторе fan-out после частичного сбоя записи он потеряет уже снятые ключи;
- (б) чистить и плоские поля `frame`, и мету `_frame_is_view` / `_shm_view_*` — `write_and_publish` её не снимает;
- (в) в `_on_frame_evicted` отпускать только ссылки своего owner. Посылка докстринга «owner≠sender при fan-in» при этом отпадает.

**Хуже воскрешения** (выведено из кода, не запускалось):
- torn-ключ приходит как `None`, а `_large_entries` пропускает `None`;
- поэтому p3 читает маску из более новой записи слота p1;
- итог — маска и кадр от разных кадров.

### 3. [minor] `_ring_by_slot` (`frame_shm_middleware.py:482`) отправляет неизвестный непустой `slot` в кольцо frame

- **Воспроизведено (rv_misc.py):** `evicted=True` с таким тикетом снимает чужой займ кадра, refcount `[1, 0] → [0, 0]`.
- **Фикс:** fallback на кольцо frame только при отсутствии `slot`; неизвестный slot отбрасывать и считать.

### 4. [было до 4.1, 4.1 распространил на все ключи; статически] `pipeline_executor.py:223–236`

- Release флашится до `_send_results`.
- Проходящая насквозь view-страница копируется в собственный SHM уже после release, а `_frame_views_valid` к этому моменту уже пройдена.
- Порванная копия уходит дальше незамеченной. При 60–100 fps и насыщенном кольце — реалистично.
- **Фикс:** накапливать release после отправки.

### 5. [было до 4.1; статически] `router_manager.py:767`

- `on_evict` вешается на все отправки, в том числе на copy-out GUI, который не входит в `num_consumers`.
- Вытеснение у GUI делает `release_evicted(reader="gui")` и снимает долю loan-aware потребителя.

## Проверено без замечаний

- (a) Copy-on-write `_rings` корректен: `_ring_by_slot` итерирует неизменяемый dict, `release_handles_cache` трогает только поток release.
- (b) При исчерпании займы отменяются; сбой ключа → `refs.pop` + abort; reclaim идёт по всем кольцам.
- (c) Мета view ключей попадает в тикеты и в перепроверку.
- (d) `_large_entries` — 11.03 мкс на сообщение из 22 ключей, пренебрежимо. Но число колец не ограничено: динамические ключи вида `crop_{i}` дают coll сегментов на каждый ключ до teardown.

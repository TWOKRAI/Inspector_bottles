# Task 1.1 — выход процесса не ждёт очередь к мёртвому читателю (teamlead)

План: `plans/lifecycle-graceful-stop.md`. Ветка `fix/lifecycle-graceful-stop`, база a74d561f.

## Итог

`release_queues_at_exit` в `finally` `run_process_function` после `shutdown()`. Стоп `inspection_full`
5.03–5.54 с → 0.98–1.74 с; `did not stop in` — ноль.

## Главная находка: DESIGN не покрывал живой дефект

Первая реализация строго по DESIGN (только очереди из `ProcessData.queues`) дала зелёные REDs 1–2, но
live-тест остался красным: 5.04 с. Диагностика (временные DBG-строки, удалены):

- PM на выходе: `queues at exit: 7 дожато, 0 брошено за 0.00 с`, при этом `feeders alive: 1`;
- `faulthandler` через 2 с: главный поток в `queues._finalize_join`, feeder в `connection._send`;
- буфер этого feeder'а: `{'type': 'system_event', 'event_type': 'process_state_changed',
  'process_name': 'ProcessManager', 'old_status': 'running', 'new_status': 'stopping', ...}`;
- владелец буфера через `gc.get_referrers` не найден: объект очереди уже собран GC, остались поток и
  запись `_finalize_join` в `multiprocessing.util._finalizer_registry` («сирота»).

Решение: второй источник feeder'ов — записи `_finalize_join` реестра финализаторов с живым потоком;
отпуск сироты — `Finalize.cancel()`. Приватное API CPython, записано в ADR-SRM-015 и комментариях.

## Механизм отпуска и доказательство

- известная очередь: `close()` → `thread.join(остаток общего дедлайна)` → не дожал →
  `cancel_join_thread()`; сирота: то же ожидание → `Finalize.cancel()`;
- доказательство: без ветки сирот live 5.04 с; с ней `7 дожато, 1 брошено за 0.26 с`, стоп < 2 с;
  `TestOrphanFeeder` краснеет при снятии ветки (инъекция INJ1).

## Бюджет

Замер: живой feeder дожимает за ≤0.0005 с (6 стопов, все дожатые). 1.0 с → стоп 1.71/1.71/2.48 с
(приёмка падает); 0.5 с → 1.90–1.98 с; 0.25 с → 0.98–1.74 с. Выбрано 0.25 с.

## Что я интерпретировал, а не выполнил

- DESIGN п.1–2 «перечислять очереди из ProcessData» — расширено сиротами из реестра финализаторов:
  без этого live-приёмка недостижима (замер выше).
- Бюджет: DESIGN «начать с 1.0 с» — 1.0 с проваливает приёмку, взято 0.25 с по замеру.
- Счёт «дожато/брошено» — по feeder'ам (включая сирот), не по очередям.

## Открыто / ненадёжно

- **Кто бросает очередь с недописанным буфером** (рассылка `process_state_changed` от PM) — не найдено.
  Это отдельный дефект: очередь создаётся/заменяется и теряется, пока в неё пишут.
- **INFO-строка `queues at exit: N дожато, 0 брошено` в файлы логов не доходит**: после `shutdown()`
  LoggerManager закрыт; видна только WARNING-строка (fallback в stderr). Требование «одна строка на
  процесс» выполнено лишь для M>0.
- В одном прогоне дочерний процесс тоже бросил 1 feeder (`1 дожато, 1 брошено`) — адресат не выяснен.
- `SHM fallback failed` (ERROR) — 215 строк в одном live-прогоне с фиксом; в скриптовом сравнении
  base=1, fix=0. Связь с фиксом не доказана и не опровергнута.
- Приватное API CPython 3.12.13 (`_thread`, `_finalizer_registry`, `Finalize._callback/_args`).
- Запас live-приёмки 0.26–1.0 с; остальные ~0.7–1.5 с стопа — PM-shutdown, вне задачи.

## 2. Направление: (в) — вычерпывание в буфер без диспетчеризации

Подвид (а). Пока поток ждёт, он только переносит сообщения из pipe своих каналов в FIFO-буфер роутера. Разбор,
middleware, pending и диспетчеризация остаются в следующем `receive()`, после возврата обработчика.

- Ответ команды синхронный, после подтверждённой смерти — как сегодня. backend_ctl, GUI, `process_restart_verified`
  не меняются; решение владельца не нужно.
- Реентерабельности нет: внутри ожидания не исполняется ни одна команда.
- Порядок сохраняется: обработка в том же порядке, меняется только момент ухода сообщения из pipe.
- Одна точка закрывает все пути из п. 1.
- Примитив — в `router_module`, годится любому приёмному потоку (framework-first). Прецедент метки потока —
  `_assert_not_receive_thread` (:1004-1027).

Отвергнуто:
- (а) с диспетчеризацией — внутри `restart_process` между stop и `create_and_register` исполнился бы `topology.apply`:
  дубли и сломанный реестр.
- (б) ожидание в другом потоке — message_processor сегодня неявно сериализует рестарт, switch и прочие команды
  (`process_monitor.py:1480-1481` на это опирается); вынос ожидания требует FIFO жизненного цикла и разбора гонок со
  всеми командами PM. Механика отложенного ответа при этом есть (`manages_own_reply` + `reply_to_request` с любого
  потока, `router_manager.py:1343`, PM :3248-3328) — цена (б) в потере сериализации.

## 4. DESIGN

**D1. `router_module/core/router_manager.py`**
- `__init__`: `self._inbound_stash: dict[str, deque] = {}`, `self._stash_lock = threading.Lock()`.
- `receive()`: на входе сохранить прежнее `_recv_local.filter` и поставить `(input_channels_only, channel_types)`;
  в `finally` восстановить вместе с depth.
- Выбор каналов из `_poll_all_channels` (:1538-1552) вынести в `_selected_channels(input_channels_only, channel_types)`;
  им пользуются оба метода.
- Публичный `pump_inbound() -> int`:
  - pre: при `depth == 0` вернуть 0 и ничего не читать (иначе гонка с настоящим приёмником);
  - для каждого канала фильтра текущего `receive`: буфер канала ≥ `POLL_DRAIN_CEILING` — канал пропустить и один раз
    за эпизод записать WARNING «канал <имя>: буфер полон (<n>), вычерпывание приостановлено» (без содержимого);
  - иначе `ch.poll(0.0)`, поставить `_source_channel`, положить в буфер под локом;
  - не бросает: ошибка — `_log_error`, как на :1559;
  - post: FIFO внутри канала сохранён; в буфере не больше 2×потолок−1 на канал; возвращает число перенесённых.
- `_poll_all_channels`: охрана `if self._inbound_stash` (пустой буфер — ноль затрат). Буфер канала не пуст — взять
  из буфера не больше потолка и в этом такте pipe канала не опрашивать (содержимое pipe новее).

**D2. `core/child_process_stop.py`** — kwarg `idle: Callable[[float], None] | None = None` (по умолчанию `time.sleep`);
в `join_until` (:221) `idle(pause)`; idle бросил — один WARNING, затем `time.sleep(pause)`; путь стопа не бросает.

**D3. `core/process_registry.py`** — `self.stop_wait_idle = None` в `__init__`; `_build_child_stop` (:424) передаёт
`idle=self.stop_wait_idle` — покрыты `stop_one`, `stop_many`, `stop_all`, `children_stop`.

**D4. `process_manager_process.py`** — сразу после создания `_process_registry`:
`self._process_registry.stop_wait_idle = self._stop_wait_idle`. `_stop_wait_idle(pause_s)`: `end = monotonic() + pause_s`;
`router_manager` не None — `pump_inbound()` в try (ошибка — `_log_error` один раз); затем спать остаток, если > 0.
Роутер читается в момент вызова. Обработчики, `stop_process`, `restart_process`, топологию не трогать.

**D5. ADR.** ADR-PMM-037 «Ожидание стопа вычерпывает свои каналы»: контекст (L-9, проба, 8 КБ), решение D2–D4,
отвергнутое ((а) с диспетчеризацией, (б), отпуск по таймауту, метка на очередях PM), предел 2×4096 на канал, не покрыто —
системный стоп. ADR-RTR-<следующий>: контракт `pump_inbound`. `python -m scripts.sync`.

## Эскалация (ревьюер → cto)

Системный стоп — та же блокировка для очередей PM? По чтению `process_module.py:273-278`: `workers` (с
message_processor) регистрируется в `work` после детей PM и по LIFO закрывается первым; ребёнок при `system_stop` метит
только свои очереди (`reader_gone.py:121-124`); pump здесь не сработает (поток раннера, depth=0). Блокер — проверка на
стенде через `system.shutdown` с 2 роботами. **Решение лида:** сначала замер (агент замера, режим `system.shutdown`
×3), к CTO — с числами, если зависание воспроизведётся.

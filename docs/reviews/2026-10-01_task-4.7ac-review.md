## 4.7c — находки

### C-1 [spec, воспроизведено] Порт-провода блюпринта считаются писателями кольца глубины 8
`blueprint.py:600-604`: каждый `Wire` между разными процессами добавляет получателю глубину
`DEFAULT_FRAME_RING_DEPTH`. Но `Wire` блюпринта — только привязка портов (`source/target/description`,
без транспорта и без `buffer_slots`); при сборке он нужен лишь для проверки типов и циклов.
Кадр идёт по кольцу писателя (`frame_ring_depth`). Итог: глубина писателя больше 8 обнуляется,
если между парой процессов есть порт-провод, а он есть в живых рецептах.

Вход и выход (`q8_wire_cap.py`, `phone_sketch`, `camera_0.extras.frame_ring_depth = 12`):
```
wires=True  camera_0.ring=12 -> seg queue=4 lag=2
wires=False camera_0.ring=12 -> seg queue=8 lag=2
wires into seg: camera_0.phone_camera.frame -> seg.segmentation.frame (transport None)
```
Acceptance 4.7c «`frame_ring_depth: 12` у писателя даёт очередь 8» на реальном рецепте не выполняется
(тесты собирают чертежи без порт-проводов). Направление ошибки безопасное (очередь меньше), но ручка
глубины для получателя мертва.
**Fix:** для провода брать глубину кольца процесса-источника (`by_name[src_proc].frame_ring_depth or
DEFAULT`) или не считать порт-провода вовсе (своего кольца у них нет). Тест: тот же чертёж с
порт-проводом рядом с `chain_targets` даёт очередь 8.

### C-2 [architecture, major; вопрос к CTO] Правило шире, чем «процесс за кольцом кадров»
Писателем кольца считается любой процесс, назвавший получателя в `chain_targets`. Получатели сигналов
без кадра тоже получают очередь 4 / lag 2 (было 50 / 0, где lag 0 = «блокировать, не дропать»).

Найденный случай (`q1_build_all.py`): `phone_sketch`, `points` получает от `pult` и `lines`, сборка даёт
`points dataq=4 lag=2`. `pult` шлёт item `out_1 = True, data_type = signal` — кнопку «Рисовать» (провод
`pult.control_panel.out_1 -> points.robot_draw.trigger`), одноразовый триггер робота.
`q13_queue.py`, настоящая очередь из собранного proc_dict и `QueueRegistry.send_to_queue`:
```
maxsize 4  : signal survived = False data_evicted = 1      # 1 сигнал + 4 кадра
maxsize 50 : signal survived = True
DataReceiver lag=2, executor busy, 1 signal + 2 frame collections -> остались только frame_ref 1 и 2, lag_dropped_total = 1
```
Триггер теряется после 4 кадров в транспорте или после 2 коллекций отставания исполнителя.
Ещё: в `pult_demo` и `qr_reader_demo` `gui` получает 4/2, хотя кадрового кольца на входе нет;
`color_inspect.modbus_sink` и `saver` (решения, сохранение) теперь дропают по lag 2 — раньше, чем 4.7d
введёт маркер `not_inspected`. Это следует из буквы правила («одно для всех узлов»), поэтому это не
дефект кода, а решение: исключать ли сигнальные входы (сигналы в command-плоскость или писатель = только
процесс, чьи items несут кадр) и включать ли lag > 0 на инспекции до 4.7d. См. ESCALATION ниже.

### C-3 [quality, advisory] `webcam_sketch`: явный `chain_max_lag_items: 4` даёт `lines`/`points` очередь 2
Сборка: `lines dataq=2 lag=4`, `points dataq=2 lag=4` (сумма 6 = 8 - 2, по контракту верно). Явный lag 4
появился до инварианта и теперь съедает бюджет; с сигналом `pult -> points` из C-2 два слота транспорта
вытесняются ещё быстрее. Живьём не проверял. Предложение: снять явный lag в рецепте (получится 4/2),
решает владелец рецепта.

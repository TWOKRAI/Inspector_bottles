## Фейки харнесса (названы явно)

- **`_FakeObj`/`_FakeSpawner`** (оба новых файла geometry-теста) — дьюк-тайпнутый
  спавнер с одним объектом вместо реального `ObjectSpawner`/`ObjectFactory`
  (которым нужны `LayerSpec`+`rng` — лишняя сложность для геометрического теста).
  `SceneCompositor.render()` читает только `spawner.active_objects()`,
  `obj.passport`, `obj.render()` — проверено чтением `scene_compositor.py` в этом
  же коммите, фейк реализует ровно эту поверхность.
- **`job_ticks_spy`** (job_ms-тест) — шпион вокруг `RobotSimCore`, импортированного
  В МОДУЛЕ плагина; делегирует реальному классу, запоминает переданный
  `job_ticks`. Контракт не даёт публичного способа прочитать применённый
  `job_ticks` (нет такой команды) — полный Modbus-раунд-трип с ожиданием тиков
  `free` тяжелее и сам завязан на тайминги реализации.
- **Каталожный инструмент — через `subprocess -m ...`**, не через угаданное
  Python-имя функции: контракт называет только CLI-форму
  (`--src --letters --diameter-px --out`), внутреннего API не описывает. Прямой
  вызов гипотетической `make_letter_catalog.build_catalog(...)` был бы угадыванием
  имени символа (ловушка «RED без interface.py») — subprocess даёт тот же чистый
  RED (`No module named`) без домыслов об устройстве модуля.

## Что я интерпретировал, а не следовал буквально

1. **YAML-структура рецептов.** `multiprocess_prototype/recipes/*.yaml` хранит
   процессы под `blueprint.processes`, а не под `processes` верхнего уровня (это
   выяснилось только по факту чтения файла — контракт не уточняет схему рецепта).
   `apps/line_sim/pipeline.yaml`, наоборот, плоский (`processes` на верхнем уровне,
   конфиг плагина — прямо в его словаре, без вложенного `config:`). Обе схемы
   прочитаны как данные, не предположены.
2. **Диаметр диска в дрейф-тесте** — взял литерал `300` px из таблицы §4.1
   (диаметр диска сима), а НЕ импортировал его из `make_letter_catalog` (тот модуль
   тестируется отдельно, `test_disc_diameter_inside_circle_detector_window`) —
   иначе один отсутствующий модуль ломал бы оба теста одной и той же причиной.
3. **`test_invalid_direction_raises`** обёрнут в `pytest.raises(ValueError)`, хотя
   сегодня реально прилетает `TypeError` (параметра нет) — тест ПАДАЕТ (не
   проходит инверсией полярности), потому что `pytest.raises` не ловит `TypeError`
   и он прорывается наружу необработанным. RED сохраняется, причина в трейсбеке
   видна честно.
4. **`test_bad_job_ms_fails_plugin_not_process`** проверяет `cmd_status()["state"]`
   (публичная команда), а не приватный `plugin._state` — контракт называет
   `_fail`, но это приватный метод; наблюдаемый эффект `_fail` — `state` в ответе
   `sim_robot.status`.

## Что осталось открытым / ненадёжным

- **Ключи `belt_direction`/`entry_x_px` в `apps/line_sim/pipeline.yaml` сегодня не
  существуют** — дрейф-тест берёт их через `.get(..., 1)`/`.get(..., 0.0)` (дефолты
  контракта §4.2.1/§4.2.2). Если разработчик добавит другие дефолты — тест не
  заметит рассинхрон дефолтов сам, только прямое несовпадение чисел после
  реализации даст сигнал.
- **`test_letter_catalog_tool_missing_letter`** проверяет, что имя буквы попадает в
  `stderr` процесса — контракт говорит `SystemExit` с именем буквы; я предполагаю,
  что `argparse`/`sys.exit(msg)` печатает это в stderr процесса (стандартное
  поведение), но НЕ проверял это на реальном коде (модуля нет) — если разработчик
  выведет имя буквы в stdout, а не stderr, тест ошибочно останется RED уже ПОСЛЕ
  реализации и потребует правки.
- **Диаметр 300 px в дрейф-тесте** — подобран по литералу таблицы §4.1, но НЕ
  сверен independently с тем, что на самом деле выберет `make_letter_catalog` по

  `DEFAULT_DIAMETER_PX`, чтобы не завязывать один провал на два разных модуля).

  тот же провал воспроизводится и без моих файлов. Пред-существующие тесты

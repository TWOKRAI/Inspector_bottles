Сырой кадр 1440×1080×3 = 4 665 600 Б; ×25 = 116,64 МБ/с; 60 с = 7,0 ГБ; 120 с = 14,0 ГБ на камеру: сырой буфер в RAM при 16 ГБ и двух камерах не помещается.

Прочее: `time.time()` шаг 1,000 мс (py 3.12.12, сейчас, зависит от системного таймера); `perf_counter` разрешение 1e-07 с; запись на C: 1060 МиБ/с, свободно 30 ГиБ; на D: свободно 452 ГиБ, скорость не мерилась.

| вариант | размер на камеру, 60 / 120 с | оценка |
|---|---|---|
| сырой BGR в RAM или SHM-кольце | 7,0 / 14,0 ГБ | не помещается |
| сырой на диск (mmap) | то же; 233 МБ/с на две камеры ≈ 20 ТБ/сутки | отвергнуть: износ диска |
| JPEG q90 в RAM | 0,9 / 1,8 ГБ (0,6 МБ/кадр); худший случай 2,1 / 4,2 ГБ | рекомендуется для буфера |
| JPEG q80 в RAM | 0,59 / 1,18 ГБ | то же, дешевле |
| JPEG-сегменты на диске | то же место; 30 МБ/с на две камеры ≈ 2,6 ТБ/сутки | только когда идёт запись |
| H.264 | в 5-10 раз меньше JPEG (оценка, не замер на реальном кадре) | для архива; для ползунка плохо: доступ через ключевой кадр, в `VideoWriter` нет времени кадра |

**Рекомендация.** Кадр кодируется один раз в JPEG (каждый кадр независим, доступ по времени — один декод 5-9 мс). Буфер — байтовое кольцо JPEG в RAM процесса записи. Видео — те же байты, дописанные в файлы-сегменты на диск; контейнер склейкой без перекодирования (проверено).
**Бюджет.** `ожидаемо = buffer_seconds × fps × средний_размер`; жёсткий потолок `buffer_max_mb` отдельно. Вытеснение всегда самого старого: сначала по времени (`capture_ns < newest − buffer_seconds`), затем по байтам. Кольцо считает секунды, не штуки: при 11,7 кадр/с те же 120 с занимают 0,47 от объёма (≈0,84 ГБ при q90). Если потолок по байтам сработал раньше времени, метрика `span_s` показывает фактическую глубину.

## Б. Разделение путей

Пути расходятся на выходе источника, в рецепте: камера шлёт одну и ту же SHM-ссылку в gui (дисплей, «последний на ключ», T1-T3 без изменений) и в отдельный процесс `recorder_N` на камеру. От gui и Qt запись не зависит.
- Камера не блокируется никем: писатель SHM перезаписывает старое, IPC-очередь вытесняет у отправителя.
- Процесс записи — обычный `GenericProcess` с `overflow: every` (`generic_process.py:154`; `data_receiver.py:278-286` заменяет выброшенный кадр маркером). Работа на кадр — JPEG 6,1 мс, 15 % такта при 25 Гц. Запас до потери — окно кольца: 8 блоков = 320 мс.
- Политика потерь явная: каждый пропуск (маркер lag/stale или разрыв `seq_id` / `device_frame_num`, `plugin_base.py:592,600`) — запись о разрыве с числом кадров в индексе. Обещание «не теряет никогда» давать нельзя: не воспроизведено.
- Медленный диск: между кодированием и диском очередь с пределом в байтах и поток-писатель. При переполнении выбрасывается самое старое незаписанное, пишется разрыв `reason=disk`, ошибка health. Приём и буфер в RAM работают.
- Изоляция: падение `recorder_N` перезапускает supervision; камера и дисплей не затронуты. Кодировать внутри процесса камеры не надо: сбой кодека или диска оказался бы в процессе камеры.
- Риск: `overflow: every` сейчас не использует ни один рецепт (`git grep` — 0 файлов). Запись будет первым живым пользователем.

## В. Время кадра

- **Контракт (T8):** два поля в каждом кадровом item, ставит источник в самой ранней точке, запасной штамп в `SourceProducer`. `capture_ns: int` = `time.perf_counter_ns()` — монотонные, общие для процессов одной машины часы (framework уже опирается на это для `_t_sent_ns`, `source_producer.py:313`); ключ индекса буфера и общая шкала камер и считывателей. `capture_ts: float` (wall, уже есть) — для подписи и имён файлов; ключом быть не может: wall-часы прыгают.
- Аппаратный штамп прибора (`Services/code_reader/sdk/structures.py:286-287`) едет как `device_ts`, метаданные, не общая шкала.
- Перенос: в `data` сообщения (`capture_ts` уже в списке переносимых ключей, `plugin_runner.py:65`; добавить `capture_ns`). В заголовок SHM не класть: ссылка с поколением уже связывает пиксели с сообщением.
- **«Кадр на момент t» без нагрузки на gui:** процесс буфера сам становится источником кадров для дисплея. Команды: `buffer.range` -> `{t_min_ns, t_max_ns, frames, gaps}`; `buffer.seek {t_ns, mode: nearest|prev|next, max_width, max_height}`; `buffer.live`. На `seek` процесс декодирует один JPEG и шлёт обычное кадровое сообщение в gui (SHM-ссылка, `capture_ns` настоящего кадра); в gui оно идёт тем же путём: `LatestMailbox` (ключ = sender) -> `FramePump` -> слот. Быстрое движение ползунка: в процессе буфера запросы тоже «последний выигрывает».

## Д. Решения владельца

1. **Буфер в RAM или на диске.** RAM (рекомендовано): две камеры, 60 с q80 ≈ 1,2 ГБ; 120 с q90 ≈ 3,6 ГБ, худший случай 8,4 ГБ. Диск: ≈2,6 ТБ записи в сутки.
2. **Глубина и потолок по умолчанию.** Предложение: 60 с и `buffer_max_mb` 1024 на камеру; 120 с — осознанно.
3. **Качество.** JPEG с потерями: q80 (394 КБ, 4,6 мс) или q90 (596 КБ, 6,1 мс). Допустимы ли потери для разбора дефектов; вариант без потерь не мерился.
4. **Видео всегда или по триггеру.** Всегда в MJPEG q90 = 15 МБ/с ≈ 1,3 ТБ в сутки на камеру — нужен H.264 (ffmpeg как зависимость или DLL openh264) и срок хранения. По триггеру с предзаписью из кольца достаточно MJPEG.
5. **Ротация и хранение:** длина сегмента, предел ГБ или суток, диск (на C: свободно 30 ГиБ).
6. **Глубина SHM-кольца записываемых камер:** 8 -> 25 блоков (+80 МБ на камеру) даёт записи запас 1 с вместо 320 мс.
7. **Процесс записи на камеру** (рекомендовано, изоляция) или один общий сервис.
8. Прежние решения 1-4 и 6 остаются; 5 снято.

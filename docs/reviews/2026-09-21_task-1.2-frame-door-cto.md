## Что воспроизведено (одноразовые стенды на чужих портах, стенд ведущего на 8091 не трогал)

Зонд: `scratchpad/stand_probe.py` — `BackendHarness(launcher_factory=build_app(...))`, копия
`system.yaml` сима, `discovery` на `Plugins/sim` + `Plugins/sources/camera_service`, свой лог-каталог.
Метрика: сырой HTTP GET 3 с (первые 200 байт + число `--mjpegsinkboundary`), `cv2.VideoCapture` 5 с.

| | Стенд ведущего (8091, текущий `pipeline.yaml`) | (а) два процесса, 8092 | (б) один процесс, `chain_targets: [camera]`, 8093 |
|---|---|---|---|
| Валидация блюпринта | проходит | **без провода — `BlueprintError: Вход 'mjpeg.mjpeg_sink.frame' (image/bgr) не подключен`**; с проводом проходит | проходит |
| Первые байты | `curl -s -m 3` → **0 байт** (мой прогон, exit 0) | `--mjpegsinkboundary\r\nContent-Type: image/jpeg\r\nContent-Length: 8709` | то же, `Content-Length: 8536` |
| Границ за 3 с | 0 | **76** (≈25 fps = темп источника) | **241** (≈80/с при источнике 25 fps) |
| `cv2` ret=True за 5 с | 0 | **120** | 382 |
| Через 20 с | — | не мерил | 233 за 3 с — не гаснет |
| errors/warnings | пусто | пусто | stderr процесса `camera`: `RouterSendError @ router.send_error:delivery_failed: ни один из 1 адресатов не принял: … type='data' targets=['camera'] (подавлено с прошлой записи: 9)` — трижды за 15 с |

**Причина дефекта текущей проводки** (код + лог стенда `camera/messages.log` #24–26): `SourceProducer`
(`source_producer.py:223-251`) шлёт items ТОЛЬКО через `send_message` в `chain_targets`; processing/sink-плагины
процесса питает `DataReceiver` (`data_receiver.py:236-239`) из входящей IPC-очереди `data`. Внутрипроцессной
дороги «источник → сосед» нет. При `chain_targets: []` кадр рождается и умирает в `SourceProducer`.

**Почему (б) — петля, а не проводка.** `PipelineExecutor._send_results` (`pipeline_executor.py:382-409`)
шлёт КАЖДЫЙ item после цепочки в `chain_targets` без исключения для sink; сток pass-through (`plugin.py`,
`process()` возвращает items). С `[camera]` item возвращается в свою же очередь → сток → снова. Замер: раздача
в 3,2 раза выше темпа источника (241 против 76 за те же 3 с) — каждый кадр кодируется ~3 раза; петлю
ограничивает только насыщение собственной очереди (`queue_size=64`) и дропы с `delivery_failed`.
**Критерий приёмки 3 при этом зелёный** — ровно тот класс «работает, но сломано», о котором TRAPS.
Loan-счёт `_count_loan_aware_consumers` даст 1 (camera не в copy-out) — при включении `FW_SHM_LOAN_PROTOCOL`
владелец стал бы ждать release от самого себя; не воспроизводил (флаг выключен), отмечаю как второй риск.

**Почему не (в).** `PluginContext` (`plugins/base.py:87-148`) даёт `send_message`/`receive_message`/
`router_manager`/`state_proxy`/`memory_manager` — подписки на кадры нет; `receive_message(channel_types=["data"])`
из плагина конкурировал бы с `DataReceiver` за ту же очередь, а источник всё равно шлёт только в `chain_targets`.
(в) = новый механизм фреймворка ради сима, и дверь перестала бы имитировать боевую форму — а она для того и есть.

**Прецедент.** 18 рецептов прототипа, 107 процессов, 24 процесса-источника: **ни одного** с source + другой
плагин в одном процессе, **ни одного** `chain_targets` на себя (скан `blueprint.processes`, yaml). Источник —
всегда отдельный процесс, выход всегда покидает его по IPC.

## Почему (а) — с опорой на фазы 3–4

1. Ф3 Task 3.4 меняет источник (`camera_service` → `Plugins/sim/scene_source`) — при (а) это правка одного
   блока `camera` и адреса провода; процесс `mjpeg` не трогается. Ф4 (ROI, color_mode, фотометрия) — команды в
   процесс `camera`; сток не участвует.
2. Источник в Ф3–Ф4 — самый живой код стенда; при (а) на него можно поставить `restart_policy` как на `camera_0`
   в бою, и порт 8091 переживёт рестарт источника (при (б) падение источника гасит HTTP-сервер и рвёт
   `cv2.VideoCapture` прототипа). **Рестарт не воспроизводил** — довод структурный, не замеренный.
3. Цена: третий процесс и SHM-перегон 640×480 — на замере 25 fps без единой ошибки; на симе это не бюджет.
4. Все механизмы кадрового тракта (frame_trace, loan, телеметрия fps на процесс) стоят на боевой форме;
   (б) — единственная в репозитории самопосылка, её не покрывает ни один тест.

## Follow-up вне задачи (в `docs/claude/OPEN_QUESTIONS.md`)

Валидатор блюпринта `_is_covered_by_auto_wiring` (`blueprint.py:922-944`) считает вход плагина покрытым
выходом ПРЕДЫДУЩЕГО по позиции, включая `source` — а рантайм источник в соседа не питает. Разошлись модель
валидатора и рантайм: форма «source → sink в одном процессе» принимается и молча не работает. Либо валидатор
отвергает processing после source в одном процессе, либо рантайм это поддерживает — решение фреймворка, не сима.

### 1. Класс T: механизм D2 несовместим со слитым контрактом 1.9a
D2: «регистрация с `manages_own_reply=True`, обработчик либо отвечает сам сразу, либо подаёт с `reply` той же формы».
- `CommandManager.register_command` отказывает `executor=` вместе с `manages_own_reply` (`command_manager.py:306-307`);
  без `executor=` роутер не передаёт `reply` (`router_manager.py:1356-1371`, только `metadata.executor`);
  `handle_command` использует `reply` только в ветке исполнителя (`command_manager.py:393-442`), иначе — синхронно.
- Прямая дверь: `_cmd_process_relay(data=None, **kwargs)` не получает билет — ответить через `reply_to_request` нечем.
- Вложенная дверь: `_handle_process_command` (PMP:3292-3372) получит от обработчика T его возврат и ответит СРАЗУ;
  у `inner_msg` нет `request_id` — собственный ответ обработчика будет no-op. Отложенный relay ответил бы до исполнения.

**Решение.** Класс T регистрируется с `executor=self._transition_gate` — адаптер PM с методом
`submit(action, key, reply, *, inline_if_idle=False)` (протокол `OrderedExecutor`, атрибут `.name`):
ключ занят (`key is None` → `_lifecycle_busy()`; иначе любой `k in key` → `_in_transition(k)`) →
`self._lifecycle_executor.submit(action, key, reply)`; свободен → `action()` и `reply(result)` на вызывающем потоке,
исключение → `{"success": False, "error": "<тип>: <текст>"}`, возврат `False`. ADR-CMD-006 это допускает
(«`DEFERRED` … или уже ушёл на вызывающем», `command_manager.py:35-37`). Ключи: `process.relay` —
`key_from="target_process"`, `process.pause/resume` — `key_from="process_name"`; `telemetry.broadcast`,
`observability.tail.subscribe_all/unsubscribe_all` — `targets="all"`. `command_module` не трогается.
Гонки «проверка → подача L» нет: все подачи L идут с `message_processor` (обе двери; монитор шлёт `process.restart`
в свою очередь, `process_monitor.py:1508-1519`, поле `process_name` — ключ извлекается).
Класс L — тоже через адаптер: `executor=self._lifecycle_submit` — счётчик целей `+1` под локом PM до `submit`,
`-1` в `finally` обёртки `reply` (в том числе на отказах). `recipe.activate` в `multiprocess_prototype/orchestrator.py`
регистрируется с ЭТИМ адаптером, не с голым исполнителем — иначе relay во время `recipe.activate` уйдёт на месте.
`_in_transition(name) = count_all > 0 or count[name] > 0`; `_lifecycle_busy() = count_all > 0 or any(count)`.

## (а)–(ж)

### 3. (а) `max_workers` и `max_pending` исполнителя готовности (для D5, где бы он ни был)
`max_workers = max(_READY_GATE_MIN_WORKERS, число детей processes_config в initialize())`, константа `= 16` в PMP,
БЕЗ ключа конфига (ключ, который никто не ставит, — лишняя поверхность схемы). После каждого `topology.apply`:
живых детей больше `max_workers` → один WARNING. Перегрузка — задержка, не потеря (срок от старта действия, PMP:1656).
`max_pending` — явно `1024`: умолчание 64 вводит ПОТЕРЮ там, где сегодня очередь без потолка: свежую досылку
отклонит `executor_busy`, а устаревшие снимет поколение → ребёнок не получит ничего. `reply` гейта пишет отказ
WARNING с меткой. Отступление от ADR-WRK-005 («не меньше числа детей») — строкой в ADR-PMM-039.

### 4. (б) готовность вне лока исполнителя
Механизм описи верен, признак — нет: `get_ident()` вызывающего совпадёт, если вызывающий — сам рабочий гейта и

### 5. Новый hazard D5: рабочих гейта теперь ждёт `_WorkersStop`
Рабочие `KeyedExecutor` — SYSTEM-воркеры; `work/workers` зарегистрирован последним → в LIFO-фазе 2 ждётся ПЕРВЫМ,
до детей (`process_module.py:274-277`, `process_lifecycle.py:176-202`, `stop_all_workers(timeout=остаток)`).
Ждущее действие гейта стопа не видит (до 15–30 с) → `stop_all_workers` съедает бюджет `work` → детям остаётся меньше
срока → `terminate`. Сегодня daemon-потоки гейта никто не ждёт. Исправление: `still_relevant` гейта =
`not self._pm_stopping() and (orig is None or orig())`; `_ready_gate_executor.request_stop()` (не блокирует) в
`_ChildrenStop.request_stop()`. Hazard-тест: ребёнок не готов + стоп PM → рабочие гейта вышли ≤ 0,5 с,
`_WorkersStop.join_until` → `True`.

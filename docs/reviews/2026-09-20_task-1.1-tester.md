## Что не смог проверить вслепую и почему

- Форму ответа `system_overview()` (ключи `processes`/`anomalies`, структура записи
  процесса) — файл `backend_ctl/overview.py` не входил в список разрешённых для чтения.
  Тесты 1, 3, 5 используют защитный разбор (`_find_process_entry`/`_entry_is_running`),
  терпимый к двум разумным формам, а не жёсткий пин одной.
- Реальную форму `sim_robot.status` (кроме описанных в брифе полей) и точное имя файла
  errors.log процесса (`<log_dir>/<process>/errors.log` — по аналогии с докстрингом
  `minimal_app_backend`, не подтверждено чтением реализации логгера).
- Поведение `history_query` под реальной нагрузкой (WAL-задержка 94-112 мс по докстрингу
  driver.py) — числа в тесте (10 с деадлайн) взяты с запасом, не измерены на живой системе.

## Что интерпретировал, а не исполнил

- `system_overview()` — форма НЕ зафиксирована брифом (файл вне списка разрешённых), написал
  двух-вариантный разбор вместо жёсткого пина одной структуры. Это ослабляет тест: если
  реализация вернёт третью форму (например, `overview["robot"]` без вложенного `processes`),
  тест не поймает ни успех, ни его отсутствие корректно.
- Критерий 5 «пара прогонов» — интерпретировал как ОДИН тест с ДВУМЯ последовательными
  поднятиями harness (контроль -> целевой), а не два отдельных теста, буквально следуя
  формулировке DESIGN "с pymodbus → ... 0; без → ... ≥ 1" и списку REDS (в нём ровно одна
  строка на этот критерий).
- `errors.log` путь `<log_dir>/<process>/errors.log` — по аналогии со структурой логов у
  `minimal_app` (докстринг `minimal_app_backend`: `logs/{ticker,console_sink}/`), не видел
  реализацию логгера line_sim. Если реализация кладёт errors.log иначе — проверка тихо
  вернёт `""` (не отказ теста напрямую), эстафету по факту "modbus" несёт только
  `anomalies` — см. следующий пункт.

## Что оставил открытым / ненадёжно

- Тест 6 падает `AssertionError`, а не `FileNotFoundError`/`ImportError`, как в общем
  описании REDS ("во всех шести ... FileNotFoundError/ImportError в фикстуре") — у теста 6
  нет фикстуры вовсе (чистая файловая проверка), поэтому механизм красного другой, хотя
  цель (красный без реализации) достигнута. Прогон подтвердил это: `AssertionError`, не
  `FileNotFoundError`.
- `_errors_log_text` при отсутствующем файле возвращает `""` молча (не отказ) — по правилу
  памяти "negative wording assertion needs an existence anchor" я СОЗНАТЕЛЬНО не завязал
  критерий 5 только на errors.log: якорь существования — `system_overview()["anomalies"]`
  (это список, гарантированно присутствующий по контракту brief'а: `DESIGN` явно использует
  синтаксис `system_overview()["anomalies"]`), а errors.log — вторичный, необязательный канал.
  Если РЕАЛЬНАЯ реализация пишет "modbus" ТОЛЬКО в errors.log и НЕ в anomalies, а путь к
  errors.log окажется другим — тест 5 может остаться красным на исправной реализации
  (ложный красный). Разработчику стоит свериться с реальным путём лога и, если нужно,
  ослабить/поправить `_errors_log_text`.
- `_assert_modbus_port_free()` бьёт `pytest.fail` при занятости 5021 ДО подъёма
  системы — не проверено вживую (порт был свободен на момент прогона), логика не
  испытана на реальной коллизии.
- Тест 5 — тяжёлый (два полных подъёма harness подряд), `timeout=120`. Число не измерено
  (не было живой реализации для замера), взято с запасом от базовых 60 с других тестов.
- send_job: контракт брифа отсылал к `Services/robot_comm/tests/test_sim_e2e.py`, сигнатура

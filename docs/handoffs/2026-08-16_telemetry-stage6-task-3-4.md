## Цель сессии

Закрыть **Task 3.4** плана `plans/telemetry-stage6.md`: адресная (per-process) runtime-правка
телеметрии должна переживать respawn своего ребёнка. Первым шагом план требовал **живое репро до
правки** — с явной оговоркой «если не воспроизводится, задача снимается, а не исполняется по
инерции».

## Сделано

- **Живое репро до правки — воспроизвелось, задача не снята.** Стенд, ребёнок `lines`, baseline
  `gate_active=false`. Адресная правка `fps=7.0` (`verified_effect=true`), глобальная
  `latency_ms=11.0` (reached 7/7). После respawn (pid 36592 → 39268, epoch 0→1): `latency_ms`
  жива, ключ `fps` **исчез из `publish.metrics` целиком**. Контроль встроен в пару — глобальная
  дельта пережила respawn, значит доигрывание ПМ работает и readback не сломан.
- **Независимый тестировщик** — 7 приёмочных тестов от acceptance, без доступа к реализации
  (запрещённые пути названы поимённо). 3 красных на старом коде.
- **Реализация** (teamlead, три захода) — журнал правок `_telemetry_delta_log`; ребёнку уезжает
  его **срез** (фан-аутные + личные) в порядке ЗАПИСИ; свёртка стирающих и смежных merge;
  tombstone на адресный `publish=None`; забвение записей процессов вне топологии.
- **Инъекции — 14 в двух наборах**, предсказания записаны до каждого прогона. Две дали ноль и
  вскрыли незащищённые гарантии (см. ниже).
- **Ревью** — синхронное, две итерации, с воспроизведениями. Нашло блокер.
- Коммиты: `c8d761d1` (код, 14 файлов, +1471/−73), `9f93f917` (память, dual-write).
- Прогоны: модуль `process_manager_module` **817 passed**, фреймворк **8179 passed, 8 skipped**,
  `ruff` чисто, `scripts/validate.py` ок, `python -m scripts.sync` прогнан.

## Что НЕ сработало

- **«Лестница уровней» — ошибка спеки, моя.** Я вписал в план решение «глобальная дельта →
  адресная дельта, доигрывать по приоритету уровней» по аналогии со слоями L0–L3. У приёмника на
  ребёнке (`ProcessHeartbeat.reconfigure_telemetry`, `process_heartbeat.py:482`) **модели слоёв
  нет**: он либо применяет секцию целиком, либо мержит поверх текущей эффективной. Приоритет там
  один — порядок приёма. Реализация честно исполнила спеку и получила **зеркальный** дефект:

  ```
  оператор: адресно lines fps=7.0 → фан-аутом fps=20.0
  выживший      fps = 20.0
  пересозданный fps =  7.0
  ```

  Пережило **806 тестов и 8 инъекций**: во всех сценариях адресная правка стояла последней, и
  фиксированный порядок случайно совпадал с временным. Нашло ревью запуском.
- **Вторая моя правка («монотонный номер поверх двух уровней») тоже неверна.** Отвергнута
  teamlead'ом с воспроизведением: накопление **по уровню** схлопывает историю через голову чужой
  записи (`фан-аут fps=3 → адресно fps=7 → фан-аут latency=11` даёт уровню «фан-аут» склейку
  1-й и 3-й записей, и порядок по номерам всё равно врёт).
- **Инъекция, давшая ноль вместо предсказанных четырёх — дважды, и оба раза это был пробел
  покрытия, а не промах предсказания.**
  1. Эквивалентность не проверялась на пути `process.restart` — том самом, где дефект нашли
     живьём; там стоял только прокси по порядку доставки.
  2. Эквивалентность не проверялась **у соседа**. При поломке свёртки сосед терял свою фан-аутную
     правку целиком (`выживший seg fps=3.0` против `пересозданный seg = None`) — при **813
     зелёных**. Существовавший тест стерёг обратное: «соседу не досталось лишнего». Из него не
     следует «у соседа не отняли своего».
- **Собственное репро падало на верном коде.** Передавал режим ключом `mode`, а команда читает
  `telemetry_mode` (`process_manager_process.py`, разбор args). Тест краснел убедительно и
  неправильно. Поймал сверкой с исходником, не со спекой.
- **Живой прогон на новом коде не выполнен.** `system.shutdown` через backend-ctl **заблокирован
  классификатором разрешений**. Обходить киллом корневого PID (3564) не стал — это ровно обход
  смысла запрета. Второй бэкенд поднимать нельзя: `SystemLauncher.start()` реапит общий
  PID-реестр и чистит SHM по именам из конфига, то есть может снести живой стенд.

## Принятые решения

- **Хранить журнал, а не уровни.** ПМ не моделирует приоритет за приёмника, которого не видит;
  доигрывается порядок записи. ADR-PMM-028.
- **Адресный `publish=None` — tombstone, а не забвение записи.** Иначе respawn доиграл бы одну
  фан-аутную правку и воскресил gate, который оператор погасил именно этому ребёнку, при
  выжившем соседе с gate off.
- **Забвение записей вне топологии — по `_process_configs`, НЕ по живости.** Процесс в
  перезапуске из топологии не выбывал, терять его правку по мигнувшей живости нельзя.
- **Отвергнутые рекомендации оставлены в плане**, а не стёрты — ошибка спеки должна остаться в
  истории.
- **Критерий приёмки переформулирован**: не «конверт доехал», а **эквивалентность с выжившим
  соседом**, параметризованная обоими порядками × обоими call-site'ами, на значениях,
  расходящихся по уровням.
- **Формулировка «повторный reload файла без изменений → 0 рассылок» признана расхожей**: гейта
  по содержимому файла не существует, реальная гарантия — «нет записей → 0 отправок».

## Открытые концы

- **Приёмка 3.4, пункт 2 — ОТКРЫТ.** Живого прогона на новом коде нет. В плане помечен явно, за
  сделанное не выдан.
- **K-15** — фан-аутный `publish=None` забывает журнал вместо tombstone: ребёнок с секцией
  `telemetry.publish` в boot-конфиге возвращается после respawn с включённым gate при выжившем
  соседе с выключенным. Наследство Task 3.2, воспроизведено. Закрытие требует правки теста
  приёмки.
- **K-16** — `child_command_ready_timeout_s = 0` выключает досылку фан-аутных записей, но
  адресное доигрывание флаг игнорирует (`_late_delivery_deadline() or 15.0`) → половина среза.
  Форма от 3.2, наблюдаемой её сделала 3.4.
- **Оформленное `/code-review` перед merge** — в транскрипте его нет, классификатор заблокирует
  merge. Запускается только пользователем. В ветке ~100 коммитов не в main, поэтому ultra по всей
  ветке будет огромным: резать по фазам или ревьюить PR.

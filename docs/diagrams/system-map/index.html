Главная идея

Framework — универсальный конструктор многопроцессных приложений. Он не знает ни о камерах, ни о буквах: процессы, сообщения, разделяемая память для кадров, регистры, состояние, цепочки узлов, GUI-каркас.

Компьютерное зрение — один из наборов поверх него (опциональный): сервисы и плагины для камер, обработки, нейросети, сохранения, синтетики и обучения.

Инспектор (прототип) — одно приложение, собранное из этого набора. Для него контур зрения — основной сервис. Буквы — это задача, заданная моделью, рецептом и одним узлом решения (word_layout), а не свойство системы.

Новый продукт = новый рецепт и новая модель, а не новый код. Код пишут только для нового вида узла: новый детектор, новое правило решения, новый приёмник.

2. Контур компьютерного зрения — главная схема

Два кольца. Боевое идёт каждый кадр: от камеры до действия. Обучающее идёт вне такта линии: кадры и синтетика превращаются в модель, а модель возвращается в боевое кольцо через реестр data/models. Буквы появляются только в узле 7 и в выбранной модели.

3. Как любой узел встаёт в систему

Любой инструмент из каталога подключается одинаково. Поэтому модернизация почти всегда — это новый плагин или новый регистр, а не правка framework.

Правило выбора места для нового кода. Логика без зависимости от конвейера (движок, драйвер, рендер) — в Services/. Узел конвейера, который её вызывает, — в Plugins/ или в Services/<x>/plugin. Настройка конкретной задачи — в рецепте, не в коде. GUI только выбирает рецепт и правит регистры, сам ничего не запускает (принцип владельца 6).

7. Что улучшать, по порядку

Порядок выбран так, чтобы каждый шаг сразу давал рабочий результат и не ломал соседей.

  1. DS-1: сохранение по полям. frame_saver раскладывает кадры по шаблону пути ({verdict.label}/{verdict.angle_deg|45}), отдельная папка «не распознана», имена без гонок, .json пишется раньше картинки. Решение «распознано» отдаёт word_layout. Saver — в своём процессе, а не рядом с роботом.
  2. Чистый кадр (решение владельца 2026-11-11). ml_inference выдаёт результат данными и на кадр не рисует. Подпись рисует существующий overlay_draw — тот же узел, что рисует линии, точки и подписи. Три условия:
    • overlay_draw стоит на ветке показа (свой процесс, как draw), а не в основной цепочке: любой узел рисования перезаписывает frame, и всё, что ниже по цепочке, получило бы грязный кадр;
    • текст рисуется с кириллицей: функцию на PIL переносят из ml_inference в общее место, и подписи точек тоже перестают давать «???»;
    • overlay_draw не знает формат нейросети: подпись берётся по шаблону полей item ({predictions.0.label} {predictions.0.confidence}) — тот же механизм шаблона, что раскладка папок в DS-1.
    Затронуты рецепты с draw_overlay: true: letter_robot_sim, hikvision_letter_robot, letter_angle_inspect. Регистр draw_overlay замораживают, а не удаляют (FREEZE, не KILL).
  3. Универсальный модуль рисования и разметки (предложение владельца 2026-11-11, до плана). Вместо пяти узлов рисования (circle_draw, contour_draw, overlay_draw, render_overlay, надпись в ml_inference) — один узел, который рисует по конфигу:
    • фигуры — общий словарь-dict: точка, линия, контур, круг, рамка, маска, текст;
    • сопоставление в конфиге: какое поле item во что превращается (detections → круги, contours → контуры, predictions → текст по шаблону);
    • стили — таблица цветов по типу, группе и условию (основа уже есть в overlay_draw);
    • разметка — те же фигуры пишутся в .json рядом с кадром (frame_saver), откуда их читает обучение.
    Ядро отрисовки — чистая функция в Services/, плагин тонкий. Старые узлы замораживают, рецепты переводят постепенно.
    Основа — overlay_draw: его уже сделали общим (7e1640c97, 2026-10-15: рамки и надписи code_reader из рецепта; отдельный code_view отклонили). render_overlay пишет в rendered_frame; в рецептах recipes/ его нет, но он живой в топологиях backend/topology/inspection_basic.yaml и inspection_full.yaml (дисплей там привязан прямо к rendered_frame), поэтому перевод требует миграции этих топологий, а не просто заморозки.
    Урок истории: в старом прототипе был общий RendererService (апрель–май 2026, удалён в 261b90f13). Он рисовал рамки, контуры и маску, но ещё сохранял кадры и решал «брак» (should_reject). Новый модуль только рисует и отдаёт фигуры; сохранение — у frame_saver, решение — у узла решения.
    Наглядно «как сейчас / как будет»: рисовальщик до и после.
  4. Запись видео. Режим в frame_saver или отдельный приёмник: тот же буфер, другой формат на выходе.
  5. Общий узел решения. Правила «класс + уверенность → годен / брак / действие» для инспекции; word_layout остаётся отдельной задачей.
  6. Датасет из папок в обучение. ml_train читает папки frame_saver и синтетику dataset_gen одним форматом.
  7. Разметчик в GUI. Перенос кадра между классами вместе с .json.

После шагов 1–5 кольцо «камера → модель → кадры → обучение → новая модель» замыкается без ручных скриптов и без привязки к буквам.

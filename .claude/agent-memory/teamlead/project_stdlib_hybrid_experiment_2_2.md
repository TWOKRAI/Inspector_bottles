Эксперимент 2.2 на worker_module (worktree agent-a60f8dcb20f9133a4, коммиты 4e9a3b65+50907eb4, НЕ мержился).

Факты, проверенные запуском:
- Гибрид работает целиком: StdBridgeHandler → сплиттер worker-слота, доставка байт-в-байт
  (тот же system.log, тот же штамп источника), spawn на Windows закрыт установкой моста в
  `_wire_observability_hub`. Live webcam_sketch: маркер моста + записи воркеров во всех процессах.
- Отклонённая запись: миксин 1849 нс → гибрид 306 нс (голый stdlib 118, LoggerAdapter +200).
  Цель плана ≤400 нс достигается и гибридом, и (следовательно) bound named view.
- **Оценка «удалится ~900–1400 строк» НЕ подтвердилась**: на пилоте net +167 production-строк;
  экстраполяция удаляемого на полную миграцию ~380–400 строк (std_facade 160 + _fallback 86 +
  _ProcessLogger 57 + куски ProxyCreator/миксина). Ядро (гейт/роутинг/учёт потерь/буферы) не
  удаляется — оно и есть приёмники.
- Рантайм-источник (имя процесса) из `__name__` не выводится: пришлось LoggerAdapter(extra)
  per-instance — та же работа Ф2.1, переодетая. Несколько инстансов одного класса в процессе
  (WorkerManager у chain_module) при module-level getLogger теряют идентичность.
- Зеркалирование уровней: stdlib-дерево — копия нашего конфига, runtime reconfigure/set_sink_enabled
  в него сами не доезжают (нужна прошивка в observability_reload).
- Цена миграции тестов оказалась НУЛЕВОЙ (0 правок на 71 тест) — тесты worker_module не ассертили
  лог-вызовы. На модулях с лог-ассертами будет иначе.

**Why:** владелец потребовал проверку запуском вместо оценки строк; главный вопрос был
«удаление или переодевание» — ответ: переодевание.
**How to apply:** при постановке 2.2 (bound named view) не аргументировать выигрышем в строках;
аргументы — перф call-site и единый путь. См. [[project_logging_foundations_2_2]].

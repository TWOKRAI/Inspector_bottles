Прежде чем доигрывать сохранённое состояние «по уровням» (узкий поверх широкого, L0→L3,
per-process поверх глобального) — спроси, есть ли **у приёмника** модель уровней. Если он
умеет только «поставить целиком» и «смержить поверх текущего», у него ОДИН приоритет —
порядок приёма, и статический приоритет уровней совпадает с истиной лишь в той половине
случаев, где узкая правка оказалась последней по времени. Храни и доигрывай ЖУРНАЛ правок
в порядке записи.

**Why:** Task 3.4 `telemetry-stage6` (ADR-PMM-028). Спека предлагала лестницу «boot →
глобальная дельта → адресная», реализация её исполнила, тесты были зелёными — потому что
все они случайно ставили адресную правку последней. Обратная (обычная операторская!)
последовательность «точечно ребёнку, затем общий проход по системе» давала пересозданному
ребёнку чужое значение; худший случай — адресный сброс перед фан-аутной правкой оставлял
его вообще без телеметрии при живом соседе с включённой.
Промежуточная правка «монотонный номер у каждой записи, накопление по уровням» тоже
неверна: накопление ПО УРОВНЮ схлопывает историю через голову чужой записи и теряет
чередование — воспроизведено на боевом приёмнике.

**How to apply:** признак опасности — фраза «уровень X имеет приоритет над Y» рядом с
приёмником, у которого нет понятия уровня. Проверяй ОБЕ последовательности пары правок как
параметризацию, а не одну; равенство констант по уровням прячет дефект. Смежные merge
складывать можно, несмежные — нет.
Эквивалентность проверяй у ДВУХ адресатов: правленого И СОСЕДА, который делит с ним общие
записи. «Соседу не досталось лишнего» и «у соседа не отняли своего» — разные утверждения, и
второе легко остаётся без единого теста: свёртка, потерявшая сверку получателя, отнимала у
соседа всю его долю при 813 зелёных.

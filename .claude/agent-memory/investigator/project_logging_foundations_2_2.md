Исследование перед Ф2.2 (иерархия имён), 2026-07-27. Замеры на машине проекта (Win10, py3.12, min-of-rounds):
stdlib rejected debug() = 116 нс, isEnabledFor кэш = 78 нс; наш rejected целиком = 785 нс, через миксин со штампом = 1694 нс, гейт = 324–379 нс.
picologging 0.9.3: rejected ×1.9, accepted ×15 к stdlib — но проект заморожен (PyPI 2023, нет колёс 3.13+).
OTel Logs Python = статус Development, API ломается между минорами (1.39, 1.44); единственная библиотека со встроенным учётом дропов.
stdlib/structlog/loguru — учёта потерь нет ни у кого (handleError/catch=True → stderr или тишина).
**Why:** решение владельца — не начинать 2.2 без сравнения с готовыми; вердикт: рантайм не брать, взять семантику stdlib-резолва + конфиг-поверхность loguru filter-dict, из OTel только словарь полей.
**How to apply:** при работе над Ф2.2/Ф3 не перепроверять эти числа заново; при появлении соблазна «перейти на stdlib» — сначала вопрос трёх плоскостей на одном process-global дереве и Handler-контракта без accept/refuse.

Раунд 3 (сборщик-агент, проверено): под GUI-родителем (pythonw/двойной клик) stdout spawn-детей = None, fd1 невалиден, print() МОЛЧА ничего не делает — stdout-модель не транспорт для этого приложения. Входа «stdout чужого процесса» нет ни у одного сборщика (Vector exec = сборщик сам родитель); вне контейнеров сборщики берут файлы/EventLog/TCP. Вердикт: наши плоскости = «до диска», сборщик = «после диска»; гибрид = 1 JSONL-канал через register_sink_factory (log_channel.py:838), когда появится потребитель централизации.

Раунд 2 (проверено запуском): тезис «учёт потерь непереносим» ОПРОВЕРГНУТ — все 4 класса + пол работают через Handler-мост поверх нашего канала + Logger-подкласс (exp1). Но пол держится на приватном side-channel (`last_written`) и слепнет на любом чужом хендлере — доказано контрпримером. Роспись отклонённой записи 1897 нс: миксин 985 (штамп 515 + _call_manager 470), обвязка log() 297+65, гейт 344 (из них tuple-ключ кэша 271 против 57 у int-ключа). Съём ~1500 нс даёт НЕ stdlib-семантика, а модель call-site «bound named view» (объект-логгер с int-ключевым кэшем) — цель 2.2: отклонённая ≤300 нс. На реальной нагрузке (~21 Гц × 8 проц.) разница ничтожна — перф не аргумент выбора, а гигиена.

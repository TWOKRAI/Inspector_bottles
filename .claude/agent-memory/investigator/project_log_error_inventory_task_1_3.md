Инвентарь точек логирования ошибок (шаг 1 Task 1.3, `observability-closure`) собран
2026-08-31 на `97fe2123` → `plans/observability-closure/inventory-log-error.md`.
315 точек вызова: A 240 / B 51 / C 14 / W 10 (обёртки).

**Числа расходятся, потому что считают РАЗНОЕ:**
- `252` (постановка задачи) = греп `_log_error(` минус определения. Не включает
  65 вызовов `.log_error(` — а в `Plugins` из 33 точек `_log_error` ровно одна,
  остальное `ctx.log_error`.
- `226` (текст плана) = совпадает с числом точек во фреймворке, не с общим.
- `315` = все узлы вызова по AST (отсекает 9 `def` и 3 докстринга, которые греп считает).

Три из четырёх адресов, названных спекой Task 1.3, — это `.log_error`, а не `_log_error`
(`plugin_orchestrator` ×3 через `self._services.log_error`, `capture/plugin.py:288`).
Греп по `_log_error(` их не находит.

**Why:** любое «сколько точек» в этом треке нужно квалифицировать семейством вызова,
иначе инвентарь молча теряет весь слой плагинов.

**How to apply:** при возврате к Task 1.3/1.4 не пересчитывать заново — перегенерировать
срез скриптом (номера строк сдвигаются от любой правки), но держать разделение
`_log_error` / `ctx.log_error` / `self._services.log_error` явным.

**Коллизия, решение по которой не принято:** шаг 2 Task 1.3 требует стража «соседние
`_log_error` и `report_error`/`_track_error` в одной функции запрещены». Найдено 46 таких
пар в 36 функциях, и у плагинов парность поставлена СОЗНАТЕЛЬНО по ADR-PM-030 / задаче C2
(докстринг `PluginContext.health`, `process_module/plugins/base.py:190-210` разводит
`ctx.log_error` = диагностическая строка и `ctx.health.report_error` = инцидент).
`HealthState.report_error` при этом сам пишет и строку `[health]`, и запись в плоскость
ошибок — то есть соседний `log_error` даёт вторую строку об одном инциденте. Страж
покраснеет на всех 46; решение (whitelist против снятия второй строки) нужно принять ДО
написания стража. Связано с [[state-gate-vs-fence]] по стилю: имя механизма не отвечает
за его поведение.

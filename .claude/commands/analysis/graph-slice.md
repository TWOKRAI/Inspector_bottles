---
description: Границы модуля из графа graphify — кто зависит от него и от чего зависит он
---

Срез графа по границе модуля:

```bash
python scripts/graph_slice/graph_slice.py $ARGUMENTS
```

Что показывает:
- **КТО ЗАВИСИТ ОТ МОДУЛЯ** (входящие рёбра) — список тех, кого заденет правка, сгруппированный по соседним модулям.
- **ОТ ЧЕГО ЗАВИСИТ МОДУЛЬ** (исходящие рёбра).
- Первой строкой — **свежесть графа**: собран на коммите X, HEAD Y, сколько файлов модуля изменилось с тех пор.

Цель — имя модуля (`logger_module`), путь (`Services/sql`, `Plugins/processing`) или произвольный префикс (`multiprocess_prototype/frontend/widgets/tabs/pipeline`). Список целей: `--list`.

**Когда использовать:**
- Перед правкой модуля: «кого я задену» — до того, как менять сигнатуру или контракт.
- Перед выносом/переименованием: увидеть всю поверхность, которой модуль торчит наружу.
- Ревью: сверить, что новая связь не пробивает слой (`framework → Services → Plugins → prototype`).

Полезные варианты:
- `--inbound-only` — только зависимые, самый частый режим перед правкой.
- `--symbol ChannelRoutingManager` — граница одного символа.
- `--format json` — машинный вывод, поля `dependents` / `dependencies` / `dependent_modules` / `freshness`.
- `--inner` — плюс внутренние связи, `--all` — без ограничений вывода.

**Две ловушки, которые надо помнить при чтении вывода:**

1. Если первой строкой стоит «срез может врать» — граф устарел по этому модулю. Обнови (`graphify update .`) или считай результат ориентировочным. Не выдавай устаревший срез за факт.
2. У `--symbol` с методом (`.flush()`) входящих почти всегда ноль: граф вешает внешние вызовы на класс/файл. Это **не** значит «никто не зависит» — скрипт сам подскажет владельца, смотри по нему.

Инструмент отвечает на «кого заденет». Смежное: `mcp__qex__search_code` — «где используется по смыслу», `mcp__sentrux__dsm` — «связность и циклы», `mcp__graphify__get_neighbors` — «что связано с конкретным узлом».
